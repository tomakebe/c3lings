# 11. Физика: интеграторы, коллизии, broadphase, разрешение контактов

> Упражнения главы: `e1101_integrators` … `e1106_physics_world`.
> Предполагается, что вы прошли главы 01 (игровой цикл и fixed timestep),
> 03 (handles и контейнеры), 04 (математика) и 08 (сцена и пространственные структуры).

Физический движок — самая «математическая» подсистема игры, но устроен он
очень инженерно: это конвейер из простых стадий, у каждой из которых есть
бюджет по времени, свои структуры данных и свои способы сломаться. Почти
всё, что вы увидите в Box2D, Bullet, PhysX или Jolt, укладывается в одну
схему:

```
            один шаг симуляции (dt фиксирован!)
 ┌──────────────────────────────────────────────────────────────────────┐
 │ 1. интеграция скоростей   v += (F/m + g) * dt                         │
 │ 2. broadphase             AABB всех тел -> список пар-кандидатов      │
 │ 3. narrowphase            пара -> контакт-манифолд (n, depth, точки)  │
 │ 4. построение островов    связные компоненты графа контактов          │
 │ 5. солвер скоростей       N итераций последовательных импульсов       │
 │ 6. интеграция положений   x += v * dt                                 │
 │ 7. солвер положений       выталкивание остаточного проникновения      │
 │ 8. сон                    острова в покое перестают симулироваться    │
 └──────────────────────────────────────────────────────────────────────┘
```

Глава идёт по этим стадиям. Мы ограничимся 2D и кругами/выпуклыми
многоугольниками — все идеи один в один переносятся в 3D, меняется лишь
количество осей и сложность narrowphase.

## 1. Время: почему шаг фиксирован

Из главы 01 вы помните аккумулятор:

```c3
fn int World.advance(&self, double frame_dt)
{
    self.accumulator += frame_dt;
    int steps = 0;
    while (self.accumulator >= DT && steps < MAX_SUBSTEPS)
    {
        self.step();
        self.accumulator -= DT;
        steps++;
    }
    if (self.accumulator >= DT) self.accumulator = 0;   // выбрасываем долг
    self.alpha = self.accumulator / DT;                  // для интерполяции рендера
    return steps;
}
```

Для физики фиксированный `dt` — не вопрос удобства, а вопрос корректности:

* **Устойчивость.** Каждая схема интегрирования устойчива лишь при `dt`
  меньше некоторого порога, зависящего от жёсткости системы (для пружины
  — `dt < 2/ω`). Переменный шаг рано или поздно перешагнёт порог на
  «тяжёлом» кадре, и мир взорвётся.
* **Настройка.** Restitution, трение, Baumgarte-коэффициенты, пороги сна
  подбираются под конкретный `dt`. Смените 60 Гц на 144 Гц — и стопка
  ящиков начнёт вести себя иначе.
* **Детерминизм.** Одинаковые входы + одинаковый `dt` + одинаковый порядок
  операций = побитово одинаковый результат. На этом держатся реплеи,
  lockstep-сеть (глава 18) и воспроизводимые баги.

`MAX_SUBSTEPS` защищает от «спирали смерти»: если шаг физики дороже
реального `dt`, то каждый кадр копит всё больший долг, и игра встаёт.
Лучше честно замедлить время игры, чем зависнуть.

Типичные частоты: 60 Гц для большинства игр, 120–240 Гц для гонок и
файтингов (жёсткие подвески и быстрые удары), 30 Гц для стратегий с
тысячами юнитов. Unity по умолчанию — 50 Гц, Unreal (Chaos) поддерживает
async-физику с фиксированным шагом.

## 2. Интеграторы

Состояние тела — положение `x` и скорость `v`, а законы Ньютона дают
производные: `x' = v`, `v' = a(x, v, t)`. Интегратор превращает их в
шаг `(x, v) -> (x', v')`. В упражнении `e1101` вы сравните четыре схемы
на гармоническом осцилляторе — у него известно точное решение и энергия.

| схема | вычислений a(x) | порядок | энергия | где используется |
|---|---|---|---|---|
| явный Эйлер | 1 | 1 | растёт экспоненциально | нигде (учебный антипример) |
| полунеявный (симплектический) Эйлер | 1 | 1 | ограничена, колеблется | Box2D, Bullet, PhysX, Jolt — почти все игровые движки |
| velocity Verlet | 1 (с кешем) | 2 | ограничена, точнее | частицы, молекулярная динамика |
| position Verlet | 1 | 2 | ограничена | ткань, верёвки (Jakobsen, Hitman), PBD |
| RK4 | 4 | 4 | медленно затухает | орбиты, пружины подвески, камеры, гладкие силы |

### Явный и полунеявный Эйлер

```
явный:         x' = x + v  * dt        полунеявный:   v' = v + a(x) * dt
               v' = v + a(x) * dt                     x' = x + v'   * dt
```

Разница в одной букве, а поведение противоположное. У явного Эйлера на
осцилляторе энергия умножается на `(1 + ω²dt²)` каждый шаг — пружина сама
себя раскачивает. Полунеявный Эйлер **симплектичен**: он сохраняет
площадь в фазовом пространстве, поэтому энергия не уходит, а колеблется
около правильного значения. Цена та же — одно вычисление сил.

Есть и вторая причина любви к полунеявному Эйлеру: он естественно
сочетается с **солвером скоростей**. Схема шага «сначала обнови скорости
(силами и импульсами контактов), потом подвинь положения новыми
скоростями» — это и есть полунеявный Эйлер, и все контактные ограничения
применяются ровно между этими двумя половинками.

### Verlet

Position Verlet хранит не скорость, а предыдущее положение:
`x' = 2x - x_prev + a*dt²`. Скорость неявная (`(x - x_prev)/dt`), и это
удобно для ограничений: хотите, чтобы частицы были на расстоянии `L` —
просто сдвиньте их, скорость «подтянется» сама. На этом построены
ткань в Hitman (Jakobsen, «Advanced Character Physics», GDC 2001) и
современный Position Based Dynamics (Müller et al.) и его XPBD-вариант
(Macklin), на котором работают физика тканей и мягких тел во многих
движках.

### RK4

Четыре оценки производной на шаг, четвёртый порядок точности. Отлично
работает для гладких сил (гравитация планет, пружины), но для твёрдых тел
с контактами почти бесполезен: контакты — это разрывы, и промежуточные
оценки «видят» мир, где тела проходят друг сквозь друга. Кроме того,
четыре вычисления сил — это в четыре раза дороже, а за те же деньги можно
сделать четыре подшага полунеявного Эйлера, что для игр обычно лучше.

**Вывод:** по умолчанию — полунеявный Эйлер + фиксированный шаг + солвер
ограничений. Остальное — для специальных подсистем.

### Вращение

В 2D ориентация — один угол `θ`, угловая скорость `ω`, момент инерции
`I`. В 3D ориентация — кватернион, угловая скорость — вектор, инерция —
тензор 3×3, который хранят в локальных осях тела и поворачивают в мир
каждый шаг (`I_world⁻¹ = R · I_local⁻¹ · Rᵀ`). Интеграция кватерниона:
`q' = normalize(q + 0.5 * (0, ω) * q * dt)`. Нормализация обязательна —
иначе кватернион «распухнет» от ошибок округления. Отдельная тема —
гироскопический момент (`ω × Iω`): если его игнорировать, вытянутые тела
вращаются неестественно стабильно; Box2D (2D) его не имеет, Jolt и PhysX
учитывают опционально.

## 3. Формы и тесты пересечения

Форма (shape) отделена от тела (body): тело — это масса, скорость,
трансформ; форма — геометрия в локальных координатах тела. У одного тела
может быть несколько форм (compound). Набор форм в движках удивительно
стабилен:

```
 круг/сфера      капсула         AABB/OBB          выпуклый многоугольник/
   (c, r)       (a, b, r)       (c, half, R)       многогранник (вершины)
    .--.         .------.        +------+               /\
   (    )       (        )       |      |              /  \
    `--'         `------'        +------+             /____\
```

Сферы и капсулы — самые дешёвые и самые стабильные (гладкая поверхность,
одна точка контакта): поэтому персонажей почти всегда делают капсулами.
Кроме выпуклых форм есть треугольные сетки (статический уровень) и
height-field (ландшафт) — они участвуют только как статика, потому что
тест «сетка против сетки» дорог и неустойчив.

### Булевы тесты и тесты с контактом

В `e1102` вы реализуете базовые тесты. Для каждого полезно иметь две
версии: булеву (триггеры, AI, отсечение) и с контактом — нормаль, глубина
и точка, нужные солверу.

* **AABB–AABB:** перекрытие по каждой оси. Это частный случай SAT.
* **Круг–круг:** сравнивайте квадраты расстояний — `sqrt` нужен только
  при пересечении. Совпавшие центры — вырожденный случай, который
  обязательно надо обработать (выберите любую нормаль), иначе получите
  `NaN`, и он расползётся по всему миру за пару шагов.
* **Круг–AABB:** ближайшая точка коробки — `clamp(c, min, max)`. Если центр
  внутри, ближайшая точка совпадает с ним, и нормаль берут по грани
  наименьшего проникновения.
* **Луч–AABB (slab-метод):** пересекаем интервалы `[t_вход, t_выход]` по
  каждой оси. Деление на ноль даёт `±inf`, и IEEE-754 делает всё правильно —
  классический пример, где float-семантика работает на вас. Raycast —
  вторая по важности функция физического движка после `step()`:
  стрельба, видимость, камеры, ноги персонажа на ступеньках.

### Числа и NaN

Физика — главный источник `NaN` в движке. Источники: нормализация
нулевого вектора, деление на нулевую массу, `sqrt` отрицательного числа
из-за ошибки округления, `acos` от 1.0000001. Правила гигиены:

* у каждой нормализации — проверка длины;
* у статических тел — `inv_mass = 0`, а не `mass = inf`;
* `assert(!x.is_nan())` в debug-сборке после интеграции — дешёвый способ
  поймать проблему в момент появления, а не через сто кадров.

## 4. Broadphase

Наивная проверка всех пар — `n(n-1)/2` тестов. 1000 тел — полмиллиона
тестов за шаг; даже по 20 нс это 10 мс — весь кадровый бюджет. Задача
broadphase — дёшево отбросить заведомо далёкие пары, работая только с
AABB (у каждой формы — «толстая» AABB, расширенная на запас по
скорости). Три классических варианта:

### Sort-and-sweep (sweep-and-prune, SAP)

```
 x ─────────────────────────────────────────────►
   A [=======]
   B     [==========]
   C                    [=====]
   D                       [========]
       сортируем по min.x, идём слева направо, держим "активный" список
       при входе C активны {B}; B кончился раньше C.min -> выброшен
```

Ключевое свойство — **временная когерентность**: между кадрами тела
почти не двигаются, массив остаётся почти отсортированным, и сортировка
вставками работает за `O(n + k)`, где `k` — число перестановок.
Инкрементальный SAP (Bullet `btAxisSweep3`, старый PhysX) хранит
отсортированные концы интервалов по всем трём осям и поддерживает
множество пар через события «начало/конец перекрытия».

Слабые места: все тела «в одну линию» по выбранной оси (дорога вдоль x —
и SAP вырождается в O(n²)); телепортации и массовое создание объектов
ломают когерентность. Смягчение — выбирать ось с максимальной дисперсией
центров (Ericson, гл. 7.5).

### Равномерная сетка и spatial hash

Мир делится на клетки размера чуть больше типичного объекта; тело
регистрируется во всех клетках, которые накрывает его AABB, пары ищутся
внутри клеток.

```
 +----+----+----+----+
 |    | A  |A B |    |     пару (A,B) видят две клетки;
 +----+----+----+----+     сообщаем её только в клетке,
 |    |    | B  |    |     где лежит min-угол ПЕРЕСЕЧЕНИЯ AABB
 +----+----+----+----+
```

Плюсы: O(1) вставка/удаление, идеально для множества похожих по
размеру объектов (частицы, пули, толпы), тривиально параллелится.
Минусы: плохо переносит разброс размеров (огромное тело попадает в сотни
клеток), а плотная сетка требует ограниченного мира. Для бесконечного
мира — **spatial hash**: `hash(cx, cy) % buckets`, коллизии бакетов
безопасны, если в бакете хранить координаты клетки. Дедупликация пар —
правило «клетки угла пересечения» из `e1103`, оно избавляет от хеш-сета
пар.

### BVH (иерархия ограничивающих объёмов)

Дерево AABB: листья — тела, узлы — объединения детей. Запрос
«кто пересекает эту AABB» спускается только в пересекающиеся узлы.

```
                 [  root  ]
               /            \
         [ L ]                [ R ]
        /     \              /     \
      (A)     (B)          (C)     (D)
```

Box2D (b2DynamicTree) и Jolt используют динамическое AABB-дерево:
вставка выбирает соседа по эвристике стоимости поверхности (SAH —
surface area heuristic), после вставки дерево балансируется поворотами,
а листья хранят «толстые» AABB, чтобы маленькие движения не требовали
переставлять лист. Jolt дополнительно делит тела на слои
(статика/динамика/«не двигается») с отдельными деревьями: статическое
дерево строится один раз и качественно, динамическое — быстро.

BVH универсален (разные размеры, raycast, frustum-запросы), поэтому
именно он — выбор по умолчанию в современных движках. SAP и сетка
остаются нишевыми: SAP — когда очень много мелких тел в почти
статичной сцене, сетка — для частиц и толп.

### Кеш и данные

Broadphase почти полностью упирается в память, а не в арифметику:

* храните AABB плотным массивом (SoA: `min_x[]`, `max_x[]`, …), а не
  внутри «толстой» структуры тела — sweep читает только `min.x/max.x`;
* узлы BVH — в массиве по индексам, а не указателями (глава 03); узел
  на 32–64 байта, чтобы влезал в одну кеш-линию;
* пары складывайте в заранее выделенный кадровый буфер (глава 02),
  не в `List`, который растёт с аллокациями посреди шага.

## 5. Narrowphase и SAT

Narrowphase получает пару форм и возвращает **контакт-манифолд**:
нормаль, до двух (в 3D — до четырёх) точек контакта и глубину каждой.

### Теорема о разделяющей оси (SAT)

Два выпуклых тела не пересекаются ⟺ существует ось, на которую их
проекции не перекрываются. Для 2D-многоугольников кандидаты — нормали
рёбер обоих тел; для 3D-многогранников — нормали граней обоих тел плюс
попарные векторные произведения рёбер (`E_A × E_B`), что для двух
ящиков даёт 3 + 3 + 9 = 15 осей.

```
     ось n ───────────────────────────────►
        |---- A ----|      |---- B ----|      зазор => разделены
        |---- A -------|-- B ---|             overlap = min(maxA,maxB) - max(minA,minB)
```

Если разделяющей оси нет, ось с минимальным перекрытием — нормаль
контакта, а перекрытие — глубина. Не забудьте ориентировать нормаль от A
к B. В `e1104` вы реализуете это для многоугольников и увидите важный
практический момент — ранний выход и **кеширование разделяющей оси**:
в следующем кадре её проверяют первой, и в 90% случаев она по-прежнему
разделяет.

### Точки контакта: клиппинг

Одной «самой глубокой точки» хватает кругам, но ящик, лежащий на полу
плашмя, должен иметь две точки контакта, иначе он будет качаться.
Стандартный алгоритм (Box2D `b2CollidePolygons`, Catto «Contact
Manifolds», GDC 2007):

1. reference face — грань с нормалью, давшей минимальное перекрытие;
2. incident face — грань второго тела, наиболее антипараллельная ей;
3. отсечь incident face боковыми плоскостями reference face
   (Sutherland–Hodgman);
4. оставить точки, лежащие под reference face; это и есть манифолд.

Для устойчивости reference face выбирают с небольшим гистерезисом
(«предпочитай грань A, если её перекрытие не сильно больше»), иначе
манифолд дёргается между двумя почти равными вариантами.

### GJK и EPA

SAT хорош для ящиков и многоугольников с небольшим числом граней. Для
произвольных выпуклых форм (капсулы, цилиндры, выпуклые оболочки на
сотни вершин) используется **GJK** — алгоритм, работающий только через
функцию опоры `support(dir)` (вершина, самая дальняя вдоль `dir`, —
вы её тоже пишете в `e1104`). GJK ищет расстояние между телами через
разность Минковского; при пересечении глубину и нормаль даёт **EPA**.
Классика: Gino van den Bergen «Collision Detection in Interactive 3D
Environments», доклад Casey Muratori «Implementing GJK». Jolt
использует GJK+EPA практически для всех выпуклых пар.

### Таблица диспетчеризации

Narrowphase — это матрица функций `collide[shapeA][shapeB]`. Держите её
треугольной (пара (box, circle) обслуживается функцией (circle, box) с
развёрнутой нормалью), а саму таблицу — массивом указателей на функции,
а не `switch` по двум типам: так легче добавлять формы и тестировать
каждую пару изолированно.

## 6. Разрешение контактов

### Импульсы

Контакт — это ограничение «тела не сближаются вдоль n». Для одного
контакта решение в скоростях выводится в одну строку. Скорость точки
контакта тела `v_p = v + ω × r`, где `r = p − pos`. Относительная
нормальная скорость `vn = dot(v_pB − v_pA, n)`; если `vn > 0`, тела
расходятся и делать ничего не надо. Иначе ищем импульс `P = j·n`,
после которого `vn' = −e·vn`:

```
           -(1 + e) * vn
   j = ─────────────────────────────────────────────────────────
        1/mA + 1/mB + (rA × n)² / IA + (rB × n)² / IB

   vA -= P / mA     ωA -= (rA × P) / IA
   vB += P / mB     ωB += (rB × P) / IB
```

Знаменатель — обратная **эффективная масса** вдоль нормали: удар в
край ящика тратит часть импульса на вращение. Статическое тело — это
просто `1/m = 1/I = 0`, формулы его не трогают (и поэтому в движках
хранят именно обратные массы).

**Восстановление (restitution) `e`.** 0 — пластилин, 1 — идеальный
мяч. Берут `max`, `min` или произведение коэффициентов двух тел —
это дизайнерское решение (Box2D по умолчанию берёт `max`, мы в
упражнениях — `min`). Важная тонкость: при маленькой скорости удара
отскок обнуляют (порог порядка 1 м/с), иначе лежащее тело бесконечно
«подпрыгивает» от гравитации каждого шага.

**Трение по Кулону.** После нормального импульса ищем касательный
`jt`, гасящий скольжение, и ограничиваем его конусом:
`|jt| <= μ·j`. Если ограничение не сработало — сцепление (тело катится
или стоит), если сработало — скольжение. `μ` комбинируют как
`sqrt(μA·μB)`. В `e1105` вы убедитесь, что при достаточном трении диск,
упавший с горизонтальной скоростью, сразу начинает катиться со
скоростью 2/3 от исходной — ровно как в учебнике механики.

### Много контактов: последовательные импульсы

Когда контактов много (стопка, куча), решить все ограничения разом —
это линейная задача дополнительности (LCP). Игровые движки решают её
итеративно — **Projected Gauss-Seidel**, он же **sequential impulses**
в терминах Эрина Катто: проходим по всем контактам N раз (обычно 4–10),
каждый раз применяя импульс по текущим скоростям. Каждый контакт видит
результат предыдущих, и система постепенно сходится.

```
 итерация 1: контакт пол-A, A-B, B-C   -> C ещё давит на B
 итерация 2: пол-A, A-B, B-C           -> давление "доходит" до пола
 ...
 итерация 8: почти сошлось
```

Три приёма, без которых стопки не стоят:

1. **Накопленные импульсы и клампинг суммы.** Ограничение `j >= 0`
   применяют не к приращению, а к накопленному за шаг импульсу:
   `new = max(old + dj, 0); dj = new - old`. Иначе ранняя итерация,
   оттолкнувшая тело слишком сильно, не может быть «откачена».
2. **Warm starting.** Накопленный импульс контакта сохраняют между
   кадрами (контакты сопоставляют по id признаков — feature id) и
   применяют в начале шага. Солвер стартует почти с решения, и
   четырёх итераций хватает там, где без warm starting нужны десятки.
3. **Порядок и детерминизм.** Gauss-Seidel зависит от порядка
   контактов. Порядок должен быть детерминирован (сортировка пар по id
   тел), иначе одинаковые сцены ведут себя по-разному.

### Позиционная ошибка

Импульсы исправляют скорости, но не уже случившееся проникновение. Три
подхода:

* **Прямая коррекция положений** (наш `e1105`): сдвинуть тела вдоль `n`
  на долю `PERCENT` от `depth − SLOP`, пропорционально обратным массам.
  Просто и надёжно, но не учитывает вращение.
* **Baumgarte-стабилизация:** добавить в целевую скорость член
  `β/dt · max(depth − slop, 0)`. Дёшево, но вносит энергию — тела
  «выстреливают» из глубокого проникновения.
* **Split impulse / псевдоскорости / NGS** (Box2D v2): отдельный
  солвер, который исправляет положения, не трогая настоящих скоростей.
  Box2D v3 перешёл на **soft step** — «мягкие» ограничения с
  подшагами (Catto «Solver2D», 2024), Jolt использует
  sub-stepping с PGS для скоростей и NGS для положений.

`SLOP` (несколько миллиметров) — допустимое проникновение. Оно
гарантирует, что лежащие тела остаются в контакте (контакт находится
каждый кадр), а не отпрыгивают на ноль и падают снова — что выглядело
бы как дрожание.

### Туннелирование и CCD

Быстрая пуля за один шаг перепрыгивает тонкую стену — narrowphase
просто не видит пересечения. Решения: ограничить скорость (иногда
приемлемо), raycast по траектории для пуль (самое частое в играх),
**speculative contacts** (контакт создаётся заранее, если тела сблизятся
за шаг; ограничение `vn >= −distance/dt`; Box2D v3, Unity), **time of
impact** (conservative advancement — двигаем до первого касания, Box2D
`b2TimeOfImpact`). CCD включают точечно (bullet-флаг на теле): он дорог.

## 7. Сон и острова

Большая часть тел в игре большую часть времени лежит. Без сна они:

* съедают солвер (стопка из 100 ящиков — сотни контактов каждый шаг);
* медленно «ползут» от шумов округления.

Острова (islands) — связные компоненты графа «тела — контакты/джойнты»
(статические тела рёбра не связывают). Остров засыпает целиком, когда
все его тела медленнее порога заданное время (0.5 с — обычное
значение), и просыпается целиком при любом внешнем воздействии: контакт
с бодрствующим телом, приложенная сила, удаление соседа, изменение
джойнта. Острова — ещё и естественная единица параллелизма солвера
(глава 12): разные острова не делят тел. Jolt и Box2D v3 идут дальше и
раскрашивают граф ограничений (graph coloring), чтобы параллельно решать
контакты даже внутри одного острова.

В `e1106` сон пообъектный и спящее тело в солвере ведёт себя как
статическое — упрощение, которое работает для разреженного мира, но
ломается для стопок, где засыпает нижний, а верхний продолжает давить.

## 8. Детерминизм

Детерминизм бывает трёх уровней:

1. **Один бинарник, одна машина** — бесплатно, если вы не зависите от
   порядка итерации хеш-таблиц, адресов указателей и `dt` кадра.
2. **Один бинарник, разные машины одной архитектуры** — требует
   контроля над FMA, флагами округления, `-ffast-math` (запрещён),
   реализациями `sin/cos/sqrt` (libm разных ОС отличается — нужны
   свои реализации), порядком параллельных редукций.
3. **Кросс-платформенный** (x64 ↔ ARM) — всё вышеперечисленное плюс
   строгое IEEE без расширенной точности; Jolt поддерживает это
   отдельным режимом сборки (`CROSS_PLATFORM_DETERMINISTIC`), Box2D v3
   спроектирован детерминированным из коробки. Альтернатива — fixed-point
   арифметика, на которой работают многие RTS и файтинги.

Практика: сортируйте пары и контакты по id тел, а не по адресам;
никогда не итерируйте `HashMap` при построении солвера; результаты
параллельных задач объединяйте в фиксированном порядке; храните хеш
состояния мира за каждый шаг в debug-режиме и сравнивайте его между
клиентами — так ловят рассинхронизацию в lockstep-играх.

## 9. Как устроены реальные движки

**Box2D** (Erin Catto). Эталон 2D-физики и лучший учебник по
устройству солвера. v2: динамическое AABB-дерево, SAT + клиппинг,
sequential impulses с warm starting, NGS для положений, острова и сон,
TOI для «пуль». v3 (2024): SoA-хранилище, graph coloring, SIMD-солвер,
soft step, многопоточность через внешнюю job system, детерминизм.

**Bullet** (Erwin Coumans). Открытый 3D-движок 2000-х: SAP и
динамическое дерево, GJK/EPA, PGS-солвер (`btSequentialImpulseConstraintSolver`),
мягкие тела. Сейчас развивается в сторону робототехники (Featherstone,
PyBullet).

**PhysX** (NVIDIA). Стандарт в Unity и (до Chaos) Unreal. TGS-солвер
(temporal Gauss-Seidel, по сути подшаги), GPU-ускорение, CCD,
character controller, ткань.

**Jolt** (Jorrit Rouwe, Guerrilla, Horizon Forbidden West). Современный
многопоточный движок с упором на большие миры: отдельные broadphase-слои,
lock-free добавление тел, job system, детерминизм, подшаги. Исходники
отлично читаются — рекомендую как следующий шаг после этой главы.

**Havok** — коммерческий ветеран (Half-Life 2, большинство AAA), сейчас
у Microsoft.

Общая картина:

```
         ┌──────── игровой код ─────────┐
         │ запросы: raycast, overlap,   │  <- синхронно, read-only
         │ события: контакты, триггеры  │  <- из буфера прошлого шага
         └──────────────┬───────────────┘
                        │ команды (add/remove/apply force)
         ┌──────────────▼───────────────┐
         │   PhysicsSystem::step(dt)    │  <- в отдельной job, фикс. шаг
         └──────────────────────────────┘
```

Игровой код почти никогда не трогает внутренние структуры физики
напрямую: тела адресуются **хендлами** (глава 03), изменения
складываются в очередь команд, события контактов выдаются массивом после
шага (глава 06). Это и позволяет запускать физику параллельно с
остальным кадром.

## 10. Типичные ошибки

* Переменный `dt` в физике. Всегда фиксированный, с аккумулятором.
* Хранить `mass` вместо `inv_mass` и делить на ноль для статики.
* Нормаль, направленная не туда (от B к A): солвер «склеивает» тела.
  Заведите одно соглашение (у нас — от A к B) и проверяйте его тестами.
* Отскок на малых скоростях: лежащие тела вибрируют. Нужен порог.
* Нулевой `SLOP`: контакт пропадает каждый второй кадр, всё дрожит.
* Перекрестное влияние порядка: контакты в порядке появления в
  хеш-таблице — недетерминизм.
* Слишком разные массы (1 кг на 1000 кг): итеративный солвер сходится
  медленно, стопка «проседает». Лечится подшагами, warm starting,
  ограничением соотношения масс в контенте.
* Отсутствие масштаба: движки настроены на метры и объекты от 0.1 до
  10 м. Мир в пикселях (1 единица = 1 пиксель) ломает все пороги.
* Сон без пробуждения: удалили пол под спящим ящиком — он висит в
  воздухе. Любое изменение мира должно будить затронутые острова.
