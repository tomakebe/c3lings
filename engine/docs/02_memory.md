## Карта главы

**Что вы узнаете.** Почему движки почти не пользуются обычным `malloc`; что такое
выравнивание и как компилятор раскладывает поля структур; как устроены пять основных
«инструментов» engine-программиста: арена, стек с маркерами, пул, кадровый аллокатор и
общий интерфейс аллокатора; как делить память на бюджеты и как ловить ошибки памяти.

**Зачем это нужно.** Память — фундамент: все контейнеры (гл. 03), ECS (гл. 05), ресурсы
(гл. 07) и рендер (гл. 09) берут байты у аллокаторов из этой главы. Ошибки здесь — самые
коварные: программа падает через три часа и не там, где ошибка.

**Что нужно знать заранее.** Из первого трека: указатели и арифметика указателей, срезы
(`char[]`), `usz`/`sz`, интерфейсы и `@dynamic`, аллокаторы C3 (`mem`, `tmem`, `@pool`)

`&`, `|`, `~` — здесь мы их кратко повторим.

## 0. Короткое повторение: адреса, байты, двоичные числа

**Память** — это огромный массив байтов. У каждого байта есть номер — **адрес**.
**Указатель** — переменная, хранящая адрес. **Аллокатор** (allocator, «распределитель») —
код, который отвечает на просьбу «дай мне N байт» адресом свободного куска и потом
(возможно) принимает этот кусок обратно. `malloc`/`free` — один из аллокаторов, далеко не
единственный.

**Смещение** (offset) — расстояние в байтах от начала буфера. Если буфер начинается по
адресу 1000, то байт со смещением 24 лежит по адресу 1024. В аллокаторах удобно хранить
именно смещения: они не зависят от того, где буфер оказался в памяти.

Двоичные операции, которые понадобятся:

| операция | смысл | пример (8 бит) |
|---|---|---|
| `a & b` | бит = 1, если 1 в обоих | `0b1101 & 0b0111 = 0b0101` |
| `a \| b` | бит = 1, если 1 хотя бы в одном | `0b1000 \| 0b0001 = 0b1001` |
| `~a` | перевернуть все биты | `~0b00000111 = 0b11111000` |
| `x % a` | остаток от деления | `13 % 8 = 5` |

**Степень двойки** — 1, 2, 4, 8, 16, 32, 64… В двоичной записи у неё ровно одна единица:
`8 = 0b1000`. А `8 − 1 = 7 = 0b0111` — все единицы *ниже* неё. Этот факт — основа всех
трюков с выравниванием.

**Коротко:** память — массив байтов с адресами; аллокатор раздаёт куски; смещение —
позиция от начала буфера.

## 1. Почему не просто malloc

`malloc`/`free` (и `new`/`delete` в C++) — **аллокатор общего назначения** (general purpose).
Он должен обслуживать любые размеры, любое время жизни, любые потоки. За эту
универсальность игра платит.

**Аналогия: склад.** `malloc` — огромный склад, куда кто угодно в любой момент приносит
и забирает коробки любых размеров. Кладовщику приходится каждый раз искать подходящую
полку, вести учёт, следить, чтобы два грузчика не схватили одну полку. А теперь
представьте, что вы знаете: «все эти коробки одного размера» или «всё, что принесли
сегодня, вечером выбросят разом». Для таких случаев можно сделать отдельную полку с
гораздо более простыми правилами — это и есть специализированные аллокаторы.

Что именно стоит универсальность:

1. **Скорость.** Хороший `malloc` стоит 20–100 нс в быстром пути, но имеет медленные
   пути (поиск в свободных списках, **системный вызов** `mmap`/`VirtualAlloc` — просьба к ОС
   выдать ещё памяти, это очень дорого; **блокировки** при многопоточности — потоки ждут
   друг друга) — и заранее неизвестно, на какой вы попадёте. Тысяча аллокаций за кадр —
   это уже заметная доля бюджета 16 мс, а главное — **непредсказуемые пики**.
2. **Фрагментация.** **Фрагментация** — состояние, когда свободная память есть, но
   разбросана мелкими кусками между занятыми. После часов игры куча превращается в
   швейцарский сыр: свободно 200 МБ, но нет непрерывного куска в 8 МБ под текстуру. На ПК с
   **виртуальной памятью** (ОС умеет «склеивать» разрозненные физические страницы и
   сбрасывать лишнее на диск) это «лишь» медленнее; на консолях прошлых поколений без
   подкачки и на мобильных — падение через три часа игры, которое не воспроизводится в QA
   (отдел тестирования) за 20 минут.
3. **Локальность.** **Локальность** — свойство «данные, которые используют вместе, лежат
   рядом». Объекты, выделенные в разные моменты, лежат в разных местах памяти. Обход
   связанных структур превращается в цепочку промахов кэша (гл. 00, раздел 6.1).
4. **Отсутствие контроля.** Невозможно ответить на вопросы «сколько памяти ест звук?»,
   «кто течёт?», «влезем ли мы в 5 ГБ на консоли?».

**Пример фрагментации шаг за шагом.** Куча 10 МБ. Выделяем по очереди A, B, C, D, E по 2 МБ:

```
 [AA][BB][CC][DD][EE]        занято 10, свободно 0
 free(B), free(D):
 [AA][..][CC][..][EE]        свободно 4 МБ, но кусками по 2
 malloc(3 МБ) -> НЕУДАЧА, хотя свободно 4 МБ
```

Отсюда главный принцип: **каждая аллокация в движке принадлежит конкретному аллокатору,
выбранному по времени жизни и паттерну использования данных.** Большая часть памяти
выделяется *большими блоками* у ОС один раз и дальше раздаётся специализированными
аллокаторами, которые в 10–100 раз проще и быстрее `malloc`.

**Коротко:** `malloc` универсален, а значит медленен в худшем случае, фрагментирует
память и ничего не говорит о том, кто её съел. Движки берут у ОС большие блоки и
раздают их своими простыми аллокаторами.

## 2. Время жизни — главный критерий

**Время жизни** (lifetime) — промежуток от выделения объекта до его освобождения. Почти
все данные игры попадают в одну из категорий:

```
   время жизни           примеры                                 аллокатор
 ─────────────────────────────────────────────────────────────────────────────────
   вся программа         движок, системы, глобальные таблицы     линейный (при старте)
   уровень/сессия        меши уровня, навмеш, сущности уровня    стек с маркерами, арена уровня
   объект (вразнобой)    пули, частицы, звуки, сетевые пакеты    пул фиксированного размера
   кадр                  списки видимых объектов, команды,       кадровый (линейный, сброс
                         временные строки, результаты запросов    каждый кадр)
   2–3 кадра             данные для потока рендера, GPU          двойной/тройной буфер кадров
   произвольное          редактор, tools, стриминг               general purpose (TLSF, mimalloc)
```

(**Навмеш**, navmesh — сетка, по которой ИИ ищет пути.)

Чем более «одинаковы» времена жизни, тем проще аллокатор. Данные кадра освобождаются
одной операцией `offset = 0`. Данные уровня — одним «откатом» к маркеру. Пули — O(1)
вставкой в свободный список. Лишь небольшая часть действительно требует `free` в
произвольном порядке.

(**O(1)** — «за постоянное время»: операция занимает одинаково мало времени, сколько бы
объектов ни было. O(n) — время растёт пропорционально числу объектов.)

**Аналогия: посуда.** Одноразовые стаканчики на вечеринке (кадр) выбрасывают все разом,
пакетом. Посуду в съёмной квартире (уровень) оставляют при выезде всю сразу. А личную
кружку (объект с произвольным временем жизни) моют и ставят на полку по одной. Для
каждого случая — свой способ уборки.

**Коротко:** выбирайте аллокатор по тому, *как долго* живут данные. Одинаковое время
жизни = простой и быстрый аллокатор.

## 3. Выравнивание

### 3.1 Что это и зачем

Прежде чем писать аллокаторы, надо научиться выравнивать. Каждый тип имеет
**выравнивание** (`Type::alignment` в C3): адрес объекта обязан делиться на него.

| тип | выравнивание |
|---|---|
| `char` | 1 |
| `short` | 2 |
| `int`, `float` | 4 |
| `double`, `long`, указатели | 8 |
| SSE-вектор `@simd float[<4>]` | 16 |
| AVX-вектор | 32 |
| кэш-линия | 64 |
| страница памяти | 4096 |

**Почему так.** Процессор читает память не по байту, а порциями (4, 8, 16, 64 байта),
начиная с адресов, кратных размеру порции. **Аналогия: книжная полка, разделённая на
секции по 8 книг.** Если ваша 8-томная энциклопедия стоит ровно в одной секции, её
снимают одним движением. Если она «съехала» и лежит в двух секциях — нужно два движения
и ещё собрать её вместе.

Невыровненный доступ на x86 обычно просто медленнее, на ARM и для SIMD-инструкций
может быть исключением (падением программы), а **атомарные операции** (операции, которые
другой поток не может «застать посередине», гл. 12) на невыровненных данных не атомарны.

### 3.2 Формулы

Для степени двойки `a`:

```
 align_up(x, a)  = (x + a - 1) & ~(a - 1)
 is_aligned(x,a) = (x & (a - 1)) == 0
 padding(x, a)   = align_up(x, a) - x

 x = 13, a = 8:   13 + 7 = 20 = 0b10100;  ~7 = ...11000  ->  0b10000 = 16
```

**Как это работает, по-человечески.**

* `a − 1` для степени двойки — это «маска младших битов». Для `a = 8`: `0b111`.
* Число делится на 8 ⇔ его три младших бита — нули. Поэтому `is_aligned` проверяет:
  `x & 0b111 == 0`.
* `~(a − 1)` — «все биты, кроме трёх младших». `x & ~7` обнуляет три младших бита, то
  есть округляет *вниз* до кратного 8. Это `align_down`.
* Чтобы округлить *вверх*, сначала прибавляем `a − 1`, потом округляем вниз. Если `x`
  уже кратно 8, прибавка 7 не дотягивает до следующего кратного — результат не меняется.

Трассировка для `a = 8`:

| x | x + 7 | двоично | & ~7 | align_up | padding | is_aligned |
|---|---|---|---|---|---|---|
| 0 | 7 | 0b00111 | 0b00000 | 0 | 0 | да |
| 1 | 8 | 0b01000 | 0b01000 | 8 | 7 | нет |
| 8 | 15 | 0b01111 | 0b01000 | 8 | 0 | да |
| 13 | 20 | 0b10100 | 0b10000 | 16 | 3 | нет |
| 16 | 23 | 0b10111 | 0b10000 | 16 | 0 | да |

Можно было бы писать `(x + a - 1) / a * a` — работает для любого `a`, но деление
медленнее, а все выравнивания на практике — степени двойки.

### 3.3 Раскладка полей структуры

Компилятор применяет то же правило к полям структур:

1. каждое поле кладётся на ближайшее смещение, кратное своему выравниванию;
2. выравнивание структуры = максимум выравниваний полей;
3. размер структуры округляется до её выравнивания, чтобы в массиве следующий элемент
   тоже был выровнен.

```
 struct Bad  { char a; double b; char c; }   // 1 + 7pad + 8 + 1 + 7pad = 24
 struct Good { double b; char a; char c; }   // 8 + 1 + 1 + 6pad      = 16
   offset:  0       8        16
   Bad:    [a.......][bbbbbbbb][c.......]
   Good:   [bbbbbbbb][ac......]
```

Трассировка «компилятора раскладок» для `Bad`:

| поле | выравнивание | текущее смещение | align_up | поле занимает | смещение после |
|---|---|---|---|---|---|
| `a: char` | 1 | 0 | 0 | 0..0 | 1 |
| `b: double` | 8 | 1 | 8 (дыра 7) | 8..15 | 16 |
| `c: char` | 1 | 16 | 16 | 16..16 | 17 |
| итог | max = 8 | 17 | align_up(17, 8) = **24** | хвост 7 | |

Для `Good`: `b` в 0..7, `a` в 8, `c` в 9, смещение 10, `align_up(10, 8) = 16`.

**Зачем хвостовое выравнивание (шаг 3)?** Представьте массив `Bad[2]`. Если бы размер
был 17, второй элемент начался бы со смещения 17, и его поле `b` оказалось бы на 25 —
не кратно 8. С размером 24 второй элемент начинается на 24, его `b` — на 32. Порядок.

Проверить можно прямо в C3 (программа проверена на c3c 0.8.5):

```c3
import std::io;

struct Bad  { char a; double b; char c; }   // поля "вразнобой"
struct Good { double b; char a; char c; }   // крупные поля первыми

fn void main()
{
    io::printfn("Bad:  size=%d align=%d", Bad::size, Bad::alignment);
    $foreach $m : Bad::members:                      // цикл времени компиляции по полям
        io::printfn("  %s at offset %d", $m.name, $m.offset);
    $endforeach
    io::printfn("Good: size=%d align=%d", Good::size, Good::alignment);
}
```

**Что здесь происходит.** `Bad::size` и `Bad::alignment` — свойства типа, известные
компилятору. `$foreach $m : Bad::members` — цикл, который разворачивается **во время
компиляции**: для каждого поля структуры подставляется отдельный `printfn`. `$m.offset` —
смещение поля. Вывод:

```
Bad:  size=24 align=8
  a at offset 0
  b at offset 8
  c at offset 16
Good: size=16 align=8
```

Ровно так вы будете сверять свой «компилятор раскладок» в e0201.

### 3.4 Оптимизация порядка полей

Сортировка полей по убыванию выравнивания — простейшая оптимизация памяти; на
миллионе компонентов это 8 МБ и, что важнее, на треть меньше кэш-линий при обходе.
(24 → 16 байт: экономия 8 байт × 1 000 000 = 8 МБ.)
C3 не переупорядочивает поля сам (порядок важен для C-ABI — соглашения о том, как
структуры выглядят в памяти, чтобы C3 и C-код понимали друг друга), так что это ваша работа.

**Стабильная сортировка** — сортировка, при которой элементы с равным ключом сохраняют
исходный порядок. В e0201 при равном выравнивании поля должны остаться в том порядке,
в каком были.

Упражнение **e0201_alignment** — реализовать эти формулы и «компилятор раскладок».

### 3.5 False sharing

Ещё одна деталь: **false sharing** («ложное разделение»). Если два потока пишут в разные
переменные, лежащие в одной кэш-линии, линия «пинг-понгует» между ядрами: каждое ядро
вынуждено забирать линию себе, хотя данные на самом деле разные. Счётчики per-thread
(по одному на поток) выравнивают по 64 байта (`@align(64)`) — тогда каждый в своей линии.
Подробнее — в главе 12.

> **Частые ошибки**
>
> * `~a - 1` вместо `~(a - 1)` — приоритет операций.
> * Забыли хвостовое выравнивание размера структуры.
> * Используют `$m.alignment` вместо `$m.type.alignment` — первое учитывает место поля в
>   структуре и может быть больше (см. шапку e0201).
> * Нестабильная сортировка в `optimal_size` (например, quicksort) — при равных
>   выравниваниях порядок может перемешаться.

**Коротко:** адрес объекта должен делиться на его выравнивание. `align_up` округляет вверх
битовым трюком; компилятор раскладывает поля с дырами, и порядок полей влияет на размер.

## 4. Линейный аллокатор (арена, bump allocator)

### 4.1 Идея

Самый простой и самый важный аллокатор. Есть буфер и смещение; выделение — сдвиг
смещения, освобождения отдельных объектов нет, только сброс всего сразу.

**Аналогия: блокнот.** Вы пишете заметки подряд, страница за страницей. Чтобы «выделить
место», просто пишете дальше. Вычеркнуть одну заметку в середине нельзя, но можно вырвать
все исписанные страницы разом и начать сначала. Закладка, показывающая, где вы
остановились, — это и есть `offset`. («Bump» — «подтолкнуть»: выделение лишь подталкивает
закладку вперёд.)

```
 buf: [##########AAAA##BBBBBBBB####CC..................................]
      ^                                ^                               ^
      start                          offset                           end
 alloc(n, a): p = align_up(offset, a); if (p + n > end) fail; offset = p + n; return p
 reset():     offset = 0
```

(`#` — выравнивающие дыры и старые данные, буквы — объекты, точки — свободно.)

### 4.2 Трассировка

Буфер 64 байта, начинается с адреса, кратного 64. Выделяем по очереди:

| запрос | выравнивание | offset до | align_up | дыра | новый offset | peak |
|---|---|---|---|---|---|---|
| 13 байт | 1 | 0 | 0 | 0 | 13 | 13 |
| 8 байт | 8 | 13 | 16 | 3 | 24 | 24 |
| 4 байта | 4 | 24 | 24 | 0 | 28 | 28 |
| 32 байта | 16 | 28 | 32 | 4 | 64 | 64 |
| 1 байт | 1 | 64 | 64 | 0 | — нет места, `null` | 64 |
| `reset()` | | | | | 0 | 64 (пик сохраняется) |

Обратите внимание на неудачный запрос: offset **не меняется** — неудача не должна портить
состояние арены.

### 4.3 Выравнивать адрес, а не смещение

Если буфер начинается с «круглого» адреса, выравнивать смещение и адрес — одно и то же.
Но буфер может начинаться где угодно. Пример: буфер по адресу `0x1004` (= 4100), offset 12,
нужно выравнивание 16.

* Неправильно: `align_up(12, 16) = 16` → адрес `0x1004 + 16 = 0x1014` (4116) — **не**
  кратен 16!
* Правильно: `align_up(0x1004 + 12, 16) = align_up(0x1010, 16) = 0x1010` → смещение
  `0x1010 − 0x1004 = 12`. Адрес выровнен, и даже без дыры.

Поэтому выравнивают **адрес** `base + offset`, а потом переводят обратно в смещение.

### 4.4 Проверка «влезет ли» без переполнения

`usz` — 64-битное беззнаковое. Если кто-то попросит `size` около 2⁶⁴, то `start + size`
**переполнится** и «завернётся» в маленькое число — проверка `start + size > cap` скажет
«влезает»! Безопасная форма: `size > cap − start` (при `start <= cap` вычитание не уходит
в минус).

Пример с 8-битными числами для наглядности: `cap = 200`, `start = 100`, `size = 250`.
`100 + 250 = 350`, в 8 битах это `350 − 256 = 94 < 200` — «влезает» (ошибка!).
`cap − start = 100`, `250 > 100` — не влезает (верно).

### 4.5 Свойства и где используется

Свойства: выделение — несколько инструкций, нет фрагментации, нет **заголовков**
(служебных байтов перед блоком; есть лишь выравнивание), идеальная локальность (объекты,
выделенные подряд, лежат подряд). Освобождение отдельного объекта невозможно — и именно
поэтому быстро.

Где используется: загрузка всего «навсегда» при старте; временные вычисления;
**кадровый аллокатор**; построение структур, которые потом «замораживаются»
(загруженный уровень, скомпилированный шейдерный граф). В C3 это `ArenaAllocator`
и `tmem`/`@pool` (временная арена, сбрасываемая при выходе из `@pool`). В Unreal —
`FMemStack` и `TMemStackAllocator`; в Unity — `Allocator.Temp` (живёт кадр) и
`Allocator.TempJob` (до 4 кадров); в Bitsquid — `TempAllocator` на стеке.

### 4.6 High-water mark

Важно отслеживать **high-water mark** («отметка самой высокой воды», как на стене после
наводнения) — максимальное смещение за всё время. Это ответ на вопрос «какого размера
должен быть буфер»: прогоните самые тяжёлые сцены и добавьте запас. В таблице 4.2 — это
`peak`. Упражнение **e0202_linear_arena**.

### 4.7 Виртуальная арена

Отдельный приём — **виртуальная арена**: зарезервировать огромный диапазон адресов
(например, 64 ГБ через `mmap(PROT_NONE)`/`VirtualAlloc(MEM_RESERVE)`), а физические
страницы подключать по мере роста смещения. **Зарезервировать адреса** — значит попросить
ОС «не отдавай никому эти номера», не выделяя под них реальную память; реальная память
(**физические страницы** по 4 КБ) подключается, только когда её начинают использовать.
Арена растёт без копирования и без перемещения указателей, а лимит фактически
определяется бюджетом. Так устроены арены в Our Machinery, в RAD Debugger и во многих
современных «handmade»-движках.

> **Частые ошибки**
>
> * Выравнивают смещение, а не адрес.
> * Проверка `start + size > cap` (переполнение).
> * При неудаче всё равно двигают `offset` или забывают `failed++`.
> * `reset()` сбрасывает `peak` — а он должен пережить сброс.

**Коротко:** арена = буфер + смещение. Выделение — выровнять адрес и сдвинуть смещение;
освобождение — только всё разом.

## 5. Стековый аллокатор с маркерами

### 5.1 Идея

Линейный аллокатор, который умеет откатываться не только к нулю, но и к сохранённой
позиции — **маркеру**. Маркер — это просто запомненное значение смещения.

**Аналогия: закладки в блокноте.** Перед тем как начать черновые расчёты, вы кладёте
закладку. Закончили — вырываете всё после закладки, а то, что было до, остаётся.

```
 Marker m0 = stack.mark();             // [.........................]
 load_level_static();                  // [LLLLLLLL.................]
 Marker m1 = stack.mark();             //          ^m1
 load_section_a();                     // [LLLLLLLLAAAAA............]
 stack.free_to(m1);                    // [LLLLLLLL.................]  секция A выгружена
 load_section_b();                     // [LLLLLLLLBBBBBBB..........]
 stack.free_to(m0);                    // [.........................]  уровень выгружен
```

**Что здесь происходит.** `mark()` возвращает текущее смещение (m0 = 0, m1 = 8 в клетках
схемы). `free_to(m1)` возвращает смещение в 8 — всё, что выделено после, считается
свободным (байты никто не стирает, их просто перезапишут).

Освобождение строго в порядке, обратном выделению (**LIFO** — last in, first out,
«последним пришёл — первым ушёл») — как у стека вызовов. Это идеально совпадает с
вложенными временами жизни: игра ⊃ уровень ⊃ секция ⊃ временные данные загрузки.

### 5.2 Двусторонний стек

**Двусторонний стек** (double-ended stack, Gregory 6.2.1.4) растёт с двух концов одного
буфера: снизу — долгоживущие данные (уровень), сверху — временные (буферы распаковки при
загрузке). Ни одна из сторон не имеет фиксированного лимита: им общий бюджет. Так делала
Hydro Thunder (Midway) — пример из книги Грегори. Упражнение **e0203_stack_markers**.

```
 0                                                       len
 [LLLLLLLLLLLL lo->  ....свободно....   <-hi TTTTTTTTTTT]
```

**Аналогия: книжная полка, которую заполняют с двух концов.** Слева ставят книги навсегда,
справа — библиотечные на время. Пока они не встретились в середине, места хватает обоим.

Верхний стек растёт **вниз**: новый блок кладётся *ниже* текущей вершины `hi`. Начало
блока — `hi − size`, но его ещё нужно выровнять — и уже *вниз* (`align_down(x, a) = x & ~(a − 1)`),
потому что вверх нельзя: там занято.

Трассировка (буфер 100 байт, начало буфера выровнено, `lo = 0`, `hi = 100`):

| операция | вычисление | lo | hi |
|---|---|---|---|
| старт | | 0 | 100 |
| `alloc_lo(30, 1)` | блок 0..29 | 30 | 100 |
| `m = mark_hi()` | m = 100 | 30 | 100 |
| `alloc_hi(20, 8)` | 100 − 20 = 80, align_down(80, 8) = 80 | 30 | 80 |
| `alloc_hi(10, 8)` | 80 − 10 = 70, align_down(70, 8) = **64** | 30 | 64 |
| `alloc_lo(40, 1)` | 30 + 40 = 70 > hi = 64 → **неудача** | 30 | 64 |
| `free_to_hi(m)` | hi = 100 | 30 | 100 |
| `alloc_lo(40, 1)` | 70 ≤ 100 — теперь влезает | 70 | 100 |

### 5.3 Недействительные маркеры

Подводный камень: маркер, взятый *после* другого маркера, становится недействительным
после отката к более раннему. Отладочная версия может хранить счётчик «поколения»
маркеров или стек маркеров и ловить такие ошибки.

Пример: `m1 = mark()` при `lo = 8`, потом `free_to(m0)` → `lo = 0`. Теперь `free_to(m1)`
«откатил» бы стек *вверх* до 8 — объявив занятыми байты, которые уже никто не использует.
Правило: маркер нижнего стека годен, только если он **не выше** текущего `lo`; для верхнего —
если он **не ниже** `hi`. Плюс маркер нижнего стека нельзя применять к верхнему.

> **Частые ошибки**
>
> * В верхнем стеке округляют вверх (`align_up`) — блок залезает на занятое.
> * Проверка места для верхнего стека должна учитывать `lo`: новый блок не может начаться
>   ниже `lo`.
> * Не проверяют сторону маркера.
> * Вычитание `hi − size` в `usz` при `size > hi` уходит «в минус» и заворачивается — проверяйте
>   до вычитания.

**Коротко:** стек = арена с закладками; откат строго в обратном порядке. Двусторонний стек
делит один буфер между долгоживущими и временными данными.

## 6. Пул (аллокатор блоков фиксированного размера)

### 6.1 Идея

Для объектов одного размера с произвольным временем жизни (пули, частицы, узлы, звуки,
сетевые сообщения) идеален пул: буфер разбит на N блоков одного размера, а свободные
блоки связаны в **интрузивный свободный список** — указатель «следующий свободный»
хранится *внутри самого свободного блока* (он всё равно не используется).

**Аналогия: гардероб.** Все крючки одинаковые. Свободные номерки висят на гвоздике
стопкой; приходит гость — снимаем верхний номерок; уходит — вешаем его номерок сверху.
Никакого поиска «подходящего» крючка.

**«Интрузивный»** («встроенный») значит: служебная информация живёт внутри самих данных,
а не в отдельной структуре. Пока блок свободен, его первые 8 байт хранят указатель на
следующий свободный блок. Когда блок выдан, пользователь затирает эти байты своими
данными — и это нормально, блок ведь уже не в списке.

```
 блоки:     [0][1][2][3][4][5][6][7]
 занято:     X     X  X        X
 free_head ──> 1 ──> 4 ──> 5 ──> 6 ──> null

 alloc(): b = free_head; free_head = b.next; return b         O(1)
 free(b): b.next = free_head; free_head = b                   O(1)
```

### 6.2 Трассировка

Пул из 4 блоков. После `init` все свободны, список по возрастанию: `0 → 1 → 2 → 3`.

| операция | выдано / вернули | список свободных после | used |
|---|---|---|---|
| init | — | 0 → 1 → 2 → 3 | 0 |
| alloc | блок 0 | 1 → 2 → 3 | 1 |
| alloc | блок 1 | 2 → 3 | 2 |
| free(0) | блок 0 | 0 → 2 → 3 | 1 |
| alloc | блок 0 (LIFO!) | 2 → 3 | 2 |
| alloc | блок 2 | 3 | 3 |
| alloc | блок 3 | (пусто) | 4 |
| alloc | `null` — пул исчерпан | (пусто) | 4 |

Почему `init` строит список так, чтобы первым выдавался блок 0? Для детерминизма и
удобства тестов (e0204 проверяет порядок). Построить такой список проще всего, идя от
последнего блока к первому и каждый раз вставляя в голову — или идя вперёд и связывая
`i → i + 1`.

### 6.3 Размер блока

Требования: размер блока ≥ размера указателя (или индекса — тогда можно хранить 16- или
32-битный индекс), блок выровнен. Значит, `block_size = align_up(item_size, align)`, но
не меньше размера указателя (8 байт на 64-битной системе):

| item_size | align | align_up | итог block_size |
|---|---|---|---|
| 12 | 8 | 16 | 16 |
| 4 | 4 | 4 | 8 (иначе некуда записать `next`) |
| 24 | 8 | 24 | 24 |

### 6.4 Проверка «чужих» указателей

`free(p)` дешёво проверить: `p` должен лежать внутри буфера, а `(p − base) % block_size == 0`
(начало блока). Пример: `block_size = 16`, `p − base = 20` → `20 % 16 = 4` — это середина
блока 1, такой указатель отвергаем. Такую проверку стоит держать даже в релизе.

Никакого поиска, никакой фрагментации (все блоки одинаковы), нулевой оверхед
(**overhead** — «накладные расходы», служебная память) на заголовки.

### 6.5 Варианты

* **Пулы по классам размеров** (8, 16, 32, 64, …): так устроены «small block
  allocators» практически всех general-purpose аллокаторов (jemalloc, mimalloc, `FMallocBinned`
  в Unreal). Мелкие аллокации обслуживаются пулом, крупные — другим механизмом.
  Запрос на 20 байт попадает в пул блоков по 32.
* **Пул объектов** (object pool) — пул + конструирование/сброс, с `active`-флагами;
  классический паттерн Nystrom «Object Pool».
* Индексы вместо указателей и **поколения** — это уже handles (глава 03).
* LIFO-порядок свободного списка выгоден для кэша: только что освобождённый блок
  «тёплый» (недавно использовался, поэтому, скорее всего, ещё в кэше) и выдаётся первым.

Упражнение **e0204_pool**.

> **Частые ошибки**
>
> * Не учли минимум `FreeNode::size` для крошечных объектов.
> * Последний блок списка не указывает на `null` — список «уходит» в мусор.
> * `free` не обновляет `used` или пропускает проверку границы блока.
> * Двойной `free` одного блока создаёт цикл в списке (в отладке это ловят флагами или
>   заливкой).

**Коротко:** пул режет буфер на одинаковые блоки; свободные связаны списком прямо внутри
себя; выделение и освобождение — O(1) без поиска.

## 7. Кадровый и двухбуферный кадровый аллокатор

### 7.1 Кадровая арена

Огромное количество данных живёт ровно один кадр: список видимых объектов, отсортированные
draw-команды (команды «нарисуй это»), временные строки для UI и отладки, результаты
физических запросов, массивы событий. Для них — линейный аллокатор, сбрасываемый в начале
каждого кадра:

```c3
fn void begin_frame() => frame_arena.reset();
// ... в течение кадра:
VisibleItem[] vis = frame_new_array(VisibleItem, count);   // освобождать не нужно
```

**Что здесь происходит.** В начале кадра арена сбрасывается одним присваиванием. Всё, что
выделено за кадр, «умрёт» само при следующем `begin_frame`. Никаких `free`, никаких утечек.
(Это фрагмент: `frame_arena` и `frame_new_array` — условные имена.)

### 7.2 Почему нужны две арены

Но если кадры **конвейеризованы** (глава 00, раздел 5) — игровой поток готовит кадр N+1,
пока поток рендера ещё обрабатывает кадр N, — данные кадра N должны прожить до конца
следующего кадра. Отсюда **double-buffered frame allocator** (Gregory 6.2.1.6): две арены,
которые меняются ролями на границе кадров:

```
 кадр:        N             N+1            N+2
 арена A:  [пишем N]     [читает рендер] [сброс, пишем N+2]
 арена B:  [рендер N-1]  [сброс, пишем N+1] [читает рендер]
```

**Аналогия: две доски в классе.** Учитель пишет на левой доске, пока ученики переписывают
с правой. Потом правую стирают и пишут на ней, а ученики переписывают с левой. Если бы
доска была одна, учитель стирал бы то, что ещё не успели переписать.

Трассировка (`current` — номер арены, в которую пишет игра):

| begin_frame № | current после переключения | эту арену сбрасываем | рендер читает арену |
|---|---|---|---|
| 1 | 1 | 1 | 0 (кадр 0) |
| 2 | 0 | 0 | 1 (кадр 1) |
| 3 | 1 | 1 | 0 (кадр 2) |

Переключение — `current ^= 1` (XOR с единицей: 0 → 1, 1 → 0).

При конвейере глубиной три кадра (CPU → render thread → GPU) нужны три арены; для
GPU-памяти это **кольцевой буфер** (буфер, по которому пишут по кругу) с «заборами»
(**fences** — сигналы от GPU «я закончил с этим кадром»): участок можно переиспользовать
только после того, как GPU подтвердил, что закончил кадр. Unity `Allocator.TempJob`
с проверкой «прожил больше 4 кадров — предупреждение» — та же идея с отладочной страховкой.

### 7.3 Заливка шаблоном («отравление»)

Полезная отладочная техника — **заливка шаблоном** при сбросе: всю освобождённую память
заполнить, скажем, `0xCD` (так делает отладочная куча MSVC: `0xCD` — выделено, но не
инициализировано, `0xDD` — освобождено, `0xFD` — guard bytes). Указатель на данные
прошлого кадра, по ошибке сохранённый «навсегда», в отладке сразу даст мусорные
значения `0xCDCDCDCD`, которые легко узнать, — вместо тихого бага, проявляющегося раз в час.

Пример: вы сохранили указатель на `int` с числом 42 из кадровой памяти. Без заливки
через кадр там может всё ещё лежать 42 (никто не перезаписал) — баг невидим. С заливкой
там будет `0xCDCDCDCD` = −842150451: сразу видно, что читаем мёртвую память.

Заливать достаточно **использованную** часть (`0..offset`), а не весь буфер: это быстрее.
Упражнение **e0205_frame_allocator**.

> **Частые ошибки**
>
> * Сначала сбросили `offset`, потом заливаем `0..offset` — то есть ничего.
> * Заливают не ту арену (текущую до переключения, а не ту, что начнёт использоваться).
> * Лимит берут только из `budget` или только из длины буфера — нужен меньший из двух
>   (`min(budget, buf.len)`).

**Коротко:** кадровая арена сбрасывается каждый кадр; при конвейере нужны две (или три)
арены по очереди; в отладке освобождённую память заливают узнаваемым мусором.

## 8. Бюджеты

### 8.1 Идея

На консоли память — это фиксированное число (например, ~13.5 ГБ доступных игре на PS5),
и её нужно **поделить заранее**: текстуры 4 ГБ, меши 1.5, звук 400 МБ, анимации 300,
геймплей 200, кадровая память 64 МБ × 2, … Каждая подсистема получает свой аллокатор
с лимитом, и превышение — это ошибка, видимая сразу у конкретной команды, а не «OOM
(out of memory, «память кончилась») через 3 часа в непонятном месте».

**Аналогия: семейный бюджет по конвертам.** Зарплату раскладывают по конвертам: «еда»,
«квартплата», «развлечения». Если конверт «развлечения» пуст — вы узнаёте об этом сразу и
именно про развлечения, а не в конце месяца, когда нечем платить за квартиру.

```
 ┌───────────────────────────── 5 GB игровая память ───────────────────────────┐
 │ Textures 2048M │ Meshes 900M │ Audio 300M │ Anim 250M │ Game 200M │ Frame 2x64M│...
 └─────────────────────────────────────────────────────────────────────────────┘
   каждая подсистема:  used / peak / budget / число аллокаций / неудачи
```

### 8.2 Практика

* **Теги памяти** (memory tags/categories): каждая аллокация помечена подсистемой
  (`LLM` — Low Level Memory tracker — в Unreal, `MemLabel` в Unity, теги в Frostbite).
  Отчёт по тегам — первое, что открывают при борьбе за память.
* **Иерархия аллокаторов**: аллокатор подсистемы берёт память у родителя большими
  кусками. Bitsquid и Our Machinery строили дерево аллокаторов, где каждый узел
  отслеживал свою статистику, а при выходе проверял, что всё освобождено (поиск утечек
  *по подсистеме*).
* **Peak важнее current**: бюджет нарушается в пике (загрузка уровня, взрыв с тысячей
  частиц), а не в среднем.
* Отказ при превышении бюджета — это решение дизайна: где-то (частицы, **декали** —
  наклейки на поверхностях вроде следов от пуль) лучше тихо не создать объект и посчитать
  неудачу, где-то (загрузка уровня) — сразу упасть.

**Пример.** Бюджет частиц — 1 МБ, частица — 64 байта, значит 16 384 частицы. Во время
взрыва запросили 20 000. Первые 16 384 создались, 3 616 — нет (счётчик неудач = 3 616).
Игрок видит чуть менее густой взрыв, игра не упала, а в отчёте профайлера горит красным
«particles: 3616 failures» — сигнал художнику по эффектам.

**Коротко:** память делят по подсистемам заранее; каждая ведёт статистику (текущий объём,
пик, неудачи); превышение видно сразу и «адресно».

## 9. Интерфейс аллокатора

### 9.1 Зачем общий интерфейс

Чтобы контейнеры и подсистемы не зависели от конкретного аллокатора, нужен общий
интерфейс. Тогда один и тот же `List{int}` может жить в куче, в арене уровня или в
кадровой арене — смотря что ему передали. Варианты:

* **Шаблонный параметр** (C++ STL `std::allocator<T>`, EASTL, `TArray<T, TInlineAllocator<16>>`):
  без косвенного вызова, но тип контейнера зависит от аллокатора — `vector<int, A>` и
  `vector<int, B>` несовместимы.
* **Указатель на интерфейс** (Bitsquid `Allocator&`, Zig `std.mem.Allocator`, Odin
  `context.allocator`, C3 `Allocator`): **косвенный вызов** (вызов через таблицу функций —
  программа узнаёт, какую функцию вызвать, только во время работы) на каждую аллокацию
  (дёшево по сравнению с самой аллокацией), зато любой контейнер работает с любым аллокатором.

### 9.2 Интерфейс C3

В C3 это интерфейс из `std::core::mem::alloc`:

```c3
interface Allocator
{
    fn void*? acquire(sz size, AllocInitType init_type, sz alignment = 0);  // выделить
    fn void*? resize(void* ptr, sz new_size, sz alignment = 0);            // изменить размер
    fn void release(void* ptr, bool aligned);                              // освободить
}
```

**Что здесь происходит.** Три метода — всё, что нужно контейнеру. `void*?` — Optional:
либо указатель, либо ошибка (например, `mem::OUT_OF_MEMORY`). Свою структуру делают
аллокатором так: `struct BudgetArena (Allocator) { ... }` и методы с `@dynamic`, а передают
её как `&arena`.

Тонкости реализации:

* `alignment == 0` означает «по умолчанию» (16 байт для heap-аллокатора C3).
* `init_type == ZERO` — память надо обнулить.
* `resize` для арены: если `ptr` — **последняя** выделенная область, её можно
  расширить на месте (сдвинуть смещение). Иначе — выделить новую и скопировать.
  Это критично для `List`, который растёт удвоением: без расширения на месте
  арена теряет всю предыдущую ёмкость при каждом росте.
* `release` для арены: можно освободить на месте, если это последняя аллокация,
  иначе — ничего не делать.
* Чтобы `resize` знал старый размер, аллокатор хранит **заголовок** перед блоком
  (как `ArenaAllocatorHeader` в stdlib) — или требует, чтобы размер передавал вызывающий
  (так сделано в Zig и Odin: «sized deallocation», экономит заголовки).

### 9.3 Заголовок и рост «на месте»: трассировка

Пусть заголовок `Header { usz size; usz start; }` занимает 16 байт и лежит **прямо перед**
пользовательским указателем, а `start` — смещение арены *до* этой аллокации. Выравнивание
16. Смещения считаем от начала буфера (буфер выровнен).

| операция | start | где заголовок | ptr (смещение) | новый offset | что произошло |
|---|---|---|---|---|---|
| `acquire(24)` (List на 3 элемента) | 0 | 0..15 | align_up(0 + 16, 16) = 16 | 16 + 24 = 40 | новый блок |
| `resize(ptr16, 48)` | — | — | 16 | 16 + 48 = 64 | блок последний: **на месте** |
| `acquire(8)` (кто-то другой) | 64 | 64..79 | 80 | 88 | новый блок |
| `resize(ptr16, 96)` | 88 | 96..111 | align_up(88 + 16, 16) = 112 | 208 | блок не последний: **новый блок + копирование 48 байт** |
| `release(ptr16)` | | | | 208 | не последний — ничего не делаем |

Как проверить «блок последний»: `ptr + header.size == base + offset`. Для первой строки
resize: 16 + 24 = 40 = offset — последний. Для четвёртой: 16 + 48 = 64 ≠ 88 — нет.

Обратите внимание: в строке 4 выравнивается **пользовательский** указатель, а заголовок
встаёт непосредственно перед ним (96..111), между `start = 88` и заголовком осталась
дыра 8 байт. Если бы мы выровняли заголовок, а пользовательский указатель поставили бы
«после заголовка», то при выравнивании 32 или 64 указатель мог бы оказаться
невыровненным.

**Почему это важно для `List`.** `List` растёт удвоением: 8 → 16 → 32 → … → 1 048 576
элементов. Если в арене никто не вклинивается между ростами, каждый рост — просто сдвиг
`offset`, ноль копирований. Без этой оптимизации каждый рост оставлял бы старый блок
мёртвым грузом: суммарно ещё столько же памяти, сколько итоговый массив, плюс копирование.

Упражнение **e0206_allocator_interface** — реализовать этот интерфейс для арены с
бюджетом и статистикой и использовать её со стандартными `List{T}` и `HashMap{K,V}`.

> **Частые ошибки**
>
> * Не обработали `alignment == 0`.
> * Выровняли заголовок вместо пользовательского указателя.
> * В `resize` при копировании копируют `new_size` байт — при уменьшении это нормально, но
>   при росте читается чужая память; копировать надо `min(старый, новый)`.
> * Рост «на месте» забыл проверить бюджет или обновить `size` в заголовке.
> * `release(null)` — контейнеры иногда так делают; не разыменовывайте заголовок `null`.

**Коротко:** общий интерфейс позволяет любому контейнеру жить в любом аллокаторе. Для
арены `resize`/`release` дешёвые, только если блок последний; размер блока хранится в
заголовке перед ним.

## 10. Общего назначения и всё остальное

Для того, что не вписывается в схемы выше (редактор, **стриминг** ассетов разного
размера — подгрузка данных по ходу игры), нужен general-purpose аллокатор. В движках
популярны:

* **TLSF** (Two-Level Segregated Fit) — O(1) гарантированно, низкая фрагментация,
  используется в реалтайм-системах и для GPU-кучи;
* **buddy allocator** («аллокатор-приятель») — блоки степеней двойки, быстрое слияние
  соседей; часто для крупных блоков и виртуальной памяти текстур. Блок 64 КБ делится
  пополам на два «приятеля» по 32, те — по 16 и т.д.; когда оба приятеля свободны, они
  снова сливаются;
* **mimalloc / rpmalloc / jemalloc** — быстрые многопоточные аллокаторы с
  **thread-local кэшами** (у каждого потока своя маленькая заначка блоков, поэтому
  потокам не нужно ждать друг друга); Unreal использует `FMallocBinned2/3`, многие движки
  подключают rpmalloc или mimalloc.
* **Дефрагментация с перемещением** — возможна, только если на объекты ссылаются
  через handles (глава 03), а не через сырые указатели: тогда аллокатор может
  сдвинуть блоки и обновить таблицу. Так работали старые консольные движки и
  текстурные пулы.

**Коротко:** для «всего остального» берут проверенный общий аллокатор; двигать объекты
в памяти можно, только если на них ссылаются через handles.

## 11. Отладка памяти

* **Tracking allocator**: оборачивает другой аллокатор и считает выделения, байты,
  пики, а при завершении печатает утечки (в C3 — `TrackingAllocator`, упр. 102 трека 1).
* **Guard bytes / canaries** («канарейки» — как у шахтёров, которые брали птицу, чтобы
  заметить газ): несколько байт с известным значением до и после блока; проверка при
  освобождении ловит выход за границы. Если там уже не `0xFD`, кто-то писал за край.
* **Fill patterns**: `0xCD`, `0xDD`, `0xFEEEFEEE` — мусор, который легко узнать.
* **Page guards**: каждая аллокация на своей странице, за ней — недоступная страница;
  выход за границу = мгновенный **segfault** (аварийная остановка при обращении к
  запрещённой памяти) в точном месте (Electric Fence, PageHeap, AddressSanitizer работает
  похожим образом через **теневую память** — отдельную карту «какие байты можно трогать»).
* **Callstack-трекинг** в отладочных сборках: при каждой аллокации записывается стек
  вызовов, и утечку можно найти по месту выделения.

Всё это включается в отладочных сборках и выключается в релизе — поэтому аллокаторы в
движке почти всегда пишут с условной компиляцией (`$if $feature(MEM_DEBUG): ... $endif`).

**Коротко:** в отладке аллокаторы считают, помечают и «отравляют» память, чтобы ошибки
проявлялись сразу и в нужном месте.

## 12. Как это делают реальные движки

* **Unreal**: глобальный `GMalloc` (`FMallocBinned2/3`, опционально `FMallocAnsi`,
  `FMallocStomp` для поиска порч памяти), `FMemStack` для временных данных, `TArray` с
  подключаемыми политиками (`TInlineAllocator`, `TFixedAllocator`), LLM для тегов.
* **Unity** (DOTS): `Allocator.Temp` (кадр, сбрасывается автоматически),
  `Allocator.TempJob` (до 4 кадров, предупреждение при утечке), `Allocator.Persistent`;
  `NativeArray<T>` требует явный `Dispose`, а система безопасности ловит утечки и гонки.
* **Bitsquid/Stingray**: `Allocator` — абстрактный класс; `HeapAllocator`,
  `PageAllocator`, `TempAllocator<N>` (буфер на стеке + fallback), `ScratchAllocator`
  (кольцевой). Каждая подсистема получает свой аллокатор и при уничтожении проверяет утечки.
  Статья «Custom Memory Allocation in C++» (Niklas Frykholm) — классика.
* **id Tech** (Doom 3 BFG): `idBlockAlloc`, отдельные кучи для фреймовых данных,
  frame-local аллокаторы для рендера (`R_FrameAlloc`) с двойной буферизацией под SMP
  (многопроцессорность).
* **Our Machinery**: виртуальные арены, `tm_allocator_i` с явным размером при free,
  трекинг по «scope»-именам.
* **C3**: `mem` (heap), `tmem` (временная арена) + `@pool`, интерфейс `Allocator`,
  `ArenaAllocator`, `DynamicArenaAllocator`, `TrackingAllocator`, `OnStackAllocator`.
  Соглашения stdlib: `new_*`/`init(allocator)` принимает аллокатор явно, `t*` — временный.

## 13. Подводные камни

* **Висячие указатели после сброса арены.** **Висячий указатель** (dangling pointer) —
  указатель на память, которая уже освобождена или переиспользована. Самая частая ошибка с
  кадровыми аллокаторами: указатель из кадровой памяти сохранили в долгоживущей структуре.
  Лекарство — fill patterns в отладке, явные типы-обёртки «FrameSlice», ревью.
* **Смешивание аллокаторов.** Освобождение через не тот аллокатор, который выделил.
  Контейнер должен помнить свой аллокатор (как `List` в C3).
* **Выравнивание заголовка.** Если перед блоком лежит заголовок, выравнивать надо
  *пользовательский* указатель, а заголовок ставить непосредственно перед ним.
* **Переполнение при выравнивании.** `offset + size` может переполниться при огромном
  `size` — проверяйте `size > capacity - offset`, а не `offset + size > capacity`.
* **Многопоточность.** Арена не **потокобезопасна** (два потока одновременно могут получить
  один и тот же кусок). Решения: арена на поток (thread-local), атомарный `fetch_add`
  смещения (lock-free bump), или кадровая арена на каждый job worker (глава 12).
* **«Умный» resize.** Расширение на месте работает, только если блок — последний.
  Чередование роста двух `List` в одной арене всё равно приведёт к копированиям.

## 14. Как это связано с упражнениями

### e0201_alignment

* **Что просят:** `align_up`, `is_aligned`, `padding`, `compute_layout` (смещения полей,
  размер и выравнивание структуры) и `optimal_size` (размер после стабильной сортировки
  полей по убыванию выравнивания).
* **Что перечитать:** 0 (двоичные операции), 3.2 (трассировка формул), 3.3 (таблица
  раскладки `Bad`), 3.4 (стабильная сортировка).
* **На что обратить внимание:** три правила раскладки, включая хвостовое выравнивание;
  `$m.type.alignment`, а не `$m.alignment`; сортировка должна быть стабильной.

### e0202_linear_arena

* **Что просят:** `LinearArena.alloc` и `reset`.
* **Что перечитать:** 4.2 (трассировка), 4.3 (адрес, а не смещение), 4.4 (переполнение), 4.6.
* **На что обратить внимание:** при неудаче — `null`, `failed++`, `offset` не трогаем;
  `peak` переживает `reset`; `allocs` считает успешные выделения с последнего сброса.

### e0203_stack_markers

* **Что просят:** `alloc_lo`, `alloc_hi`, `free_to_lo`, `free_to_hi`.
* **Что перечитать:** 5.2 (трассировка двустороннего стека), 5.3 (недействительные маркеры).
* **На что обратить внимание:** верхний стек выравнивается **вниз**; граница для нижнего
  стека — `hi`, для верхнего — `lo`; маркер чужой стороны или «выше вершины» отвергается
  без изменений состояния.

### e0204_pool

* **Что просят:** `Pool.init` (размер блока и построение списка), `alloc`, `free`.
* **Что перечитать:** 6.2 (трассировка, порядок выдачи), 6.3 (размер блока), 6.4 (проверка).
* **На что обратить внимание:** первым выдаётся блок 0, освобождённый блок выдаётся
  следующим (LIFO); `free` отвергает указатели вне буфера и не на границе блока; `used` и `peak`.

### e0205_frame_allocator

* **Что просят:** `begin_frame` (переключить арену, залить её использованную часть
  `0xCD`, обнулить offset, `frame++`) и `alloc` (линейно, с бюджетом).
* **Что перечитать:** 7.2 (две арены и трассировка), 7.3 (заливка), 8 (бюджет).
* **На что обратить внимание:** порядок «переключить → залить → сбросить»; лимит — меньшее из
  `budget` и длины буфера; при превышении `null` и `over_budget++`; обновляйте `peak`.

### e0206_allocator_interface

* **Что просят:** `acquire`, `resize`, `release` для `BudgetArena`.
* **Что перечитать:** 9.2, 9.3 (трассировка заголовков), 4.3–4.4 (выравнивание и проверка места).
* **На что обратить внимание:** `alignment == 0` → 16; заголовок прямо перед
  пользовательским указателем; бюджет проверяется по концу блока; ошибка —
  `mem::OUT_OF_MEMORY~` и `failures++`; рост на месте — только для последнего блока с
  подходящим выравниванием; счётчики `in_place`, `moved`, `reclaimed`.

## Словарик

| Термин | Простыми словами |
|---|---|
| **Адрес** | номер байта в памяти |
| **Смещение (offset)** | расстояние в байтах от начала буфера |
| **Аллокатор** | код, выдающий куски памяти по запросу и принимающий их обратно |
| **General purpose аллокатор** | универсальный аллокатор (`malloc`): любые размеры и порядок |
| **Системный вызов** | обращение программы к ОС; дорого |
| **Фрагментация** | свободная память есть, но разбита на мелкие куски |
| **Виртуальная память** | механизм ОС, отображающий адреса программы на физические страницы |
| **Страница** | порция памяти, которой оперирует ОС (обычно 4 КБ) |
| **Локальность** | данные, используемые вместе, лежат рядом |
| **Время жизни** | период от выделения до освобождения |
| **O(1)** | время операции не зависит от количества данных |
| **Выравнивание** | требование «адрес кратен N» |
| **align_up / align_down** | округлить вверх / вниз до кратного |
| **Padding (дыра)** | пустые байты, вставленные ради выравнивания |
| **ABI** | соглашение о раскладке данных и вызовах между скомпилированным кодом |
| **Стабильная сортировка** | равные элементы сохраняют исходный порядок |
| **False sharing** | потоки мешают друг другу, работая с разными данными в одной кэш-линии |
| **Арена / линейный / bump-аллокатор** | буфер + смещение; освобождение только всё разом |
| **High-water mark (peak)** | максимальное использование за всё время |
| **Переполнение** | результат не помещается в тип и «заворачивается» |
| **Виртуальная арена** | арена, резервирующая адреса и подключающая страницы по мере роста |
| **Стековый аллокатор** | арена с откатом к маркеру, освобождение LIFO |
| **Маркер** | сохранённое значение смещения стека |
| **LIFO** | «последним пришёл — первым ушёл» |
| **Двусторонний стек** | два стека в одном буфере, растущие навстречу |
| **Пул** | аллокатор одинаковых блоков |
| **Свободный список** | список свободных блоков |
| **Интрузивный** | служебные данные хранятся внутри самих объектов |
| **Overhead** | накладные расходы, служебная память |
| **Кадровый аллокатор** | арена, сбрасываемая каждый кадр |
| **Двухбуферный кадровый аллокатор** | две кадровые арены по очереди |
| **Кольцевой буфер** | буфер, заполняемый по кругу |
| **Fence** | сигнал «GPU закончил работу с этим кадром» |
| **Fill pattern / заливка** | заполнение освобождённой памяти узнаваемым значением |
| **Бюджет** | заранее назначенный лимит памяти подсистемы |
| **OOM** | out of memory, память кончилась |
| **Теги памяти** | пометки «какая подсистема выделила» |
| **Косвенный вызов** | вызов функции через таблицу/указатель |
| **Заголовок (header)** | служебные байты перед блоком (размер и т.п.) |
| **Sized deallocation** | при освобождении размер передаёт вызывающий |
| **TLSF / buddy** | general-purpose аллокаторы с гарантированной скоростью |
| **Thread-local** | у каждого потока своя копия |
| **Дефрагментация** | сдвиг занятых блоков, чтобы собрать свободное в одно место |
| **Guard bytes / canary** | контрольные байты вокруг блока для поиска выхода за границы |
| **Segfault** | аварийная остановка при обращении к запрещённой памяти |
| **Утечка** | выделили и не освободили |
| **Висячий указатель** | указатель на уже освобождённую память |
| **Потокобезопасный** | корректно работает при одновременном вызове из нескольких потоков |
