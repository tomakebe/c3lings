# 02 · Память

> Упражнения главы: `e0201_alignment`, `e0202_linear_arena`, `e0203_stack_markers`,
> `e0204_pool`, `e0205_frame_allocator`, `e0206_allocator_interface`.

В первом треке вы уже видели аллокаторы C3: `mem`, `tmem`, `@pool`, интерфейс `Allocator`
и даже написали свой (упр. 103). Эта глава — про то, **как и почему движки управляют
памятью иначе, чем обычные программы**, и какие аллокаторы составляют «набор
инструментов» engine-программиста.

---

## 1. Почему не просто malloc

`malloc`/`free` (и `new`/`delete` в C++) — аллокатор общего назначения. Он должен
обслуживать любые размеры, любое время жизни, любые потоки. За эту универсальность
игра платит:

1. **Скорость.** Хороший `malloc` стоит 20–100 нс в быстром пути, но имеет медленные
   пути (поиск в свободных списках, системный вызов `mmap`/`VirtualAlloc`, блокировки
   при многопоточности) — и заранее неизвестно, на какой вы попадёте. Тысяча
   аллокаций за кадр — это уже заметная доля бюджета 16 мс, а главное — **непредсказуемые
   пики**.
2. **Фрагментация.** После часов игры куча превращается в швейцарский сыр: свободно
   200 МБ, но нет непрерывного куска в 8 МБ под текстуру. На ПК с виртуальной памятью
   это «лишь» медленнее; на консолях прошлых поколений без подкачки и на мобильных — падение
   через три часа игры, которое не воспроизводится в QA за 20 минут.
3. **Локальность.** Объекты, выделенные в разные моменты, лежат в разных местах памяти.
   Обход связанных структур превращается в цепочку промахов кэша.
4. **Отсутствие контроля.** Невозможно ответить на вопросы «сколько памяти ест звук?»,
   «кто течёт?», «влезем ли мы в 5 ГБ на консоли?».

Отсюда главный принцип: **каждая аллокация в движке принадлежит конкретному аллокатору,
выбранному по времени жизни и паттерну использования данных.** Большая часть памяти
выделяется *большими блоками* у ОС один раз и дальше раздаётся специализированными
аллокаторами, которые в 10–100 раз проще и быстрее `malloc`.

## 2. Время жизни — главный критерий

Почти все данные игры попадают в одну из категорий:

```
   время жизни           примеры                                 аллокатор
 ─────────────────────────────────────────────────────────────────────────────────
   вся программа         движок, системы, глобальные таблицы     линейный (при старте)
   уровень/сессия        меши уровня, навмеш, сущности уровня    стек с маркерами, арена уровня
   объект (вразнобой)    пули, частицы, звуки, сетевые пакеты    пул фиксированного размера
   кадр                  списки видимых объектов, команды,       кадровый (линейный, сброс
                         временные строки, результаты запросов    каждый кадр)
   2–3 кадра             данные для потока рендера, GPU          двойной/тройной буфер кадров
   произвольное          редактор, tools, стриминг               general purpose (TLSF, mimalloc)
```

Чем более «одинаковы» времена жизни, тем проще аллокатор. Данные кадра освобождаются
одной операцией `offset = 0`. Данные уровня — одним «откатом» к маркеру. Пули — O(1)
вставкой в свободный список. Лишь небольшая часть действительно требует `free` в
произвольном порядке.

## 3. Выравнивание

Прежде чем писать аллокаторы, надо научиться выравнивать. Каждый тип имеет
**выравнивание** (`Type::alignment` в C3): адрес объекта обязан делиться на него. `int` — 4,
`double` и указатели — 8, SSE-вектор `@simd float[<4>]` — 16, AVX — 32. Кэш-линия — 64,
страница — 4096. Невыровненный доступ на x86 обычно просто медленнее, на ARM и для SIMD-
инструкций может быть исключением, а атомарные операции на невыровненных данных не атомарны.

Для степени двойки `a`:

```
 align_up(x, a)  = (x + a - 1) & ~(a - 1)
 is_aligned(x,a) = (x & (a - 1)) == 0
 padding(x, a)   = align_up(x, a) - x

 x = 13, a = 8:   13 + 7 = 20 = 0b10100;  ~7 = ...11000  ->  0b10000 = 16
```

Компилятор применяет то же правило к полям структур: каждое поле — по смещению,
кратному своему выравниванию, а размер структуры округляется до её выравнивания
(максимума выравниваний полей), чтобы в массиве следующий элемент тоже был выровнен:

```
 struct Bad  { char a; double b; char c; }   // 1 + 7pad + 8 + 1 + 7pad = 24
 struct Good { double b; char a; char c; }   // 8 + 1 + 1 + 6pad      = 16
   offset:  0       8        16
   Bad:    [a.......][bbbbbbbb][c.......]
   Good:   [bbbbbbbb][ac......]
```

Сортировка полей по убыванию выравнивания — простейшая оптимизация памяти; на
миллионе компонентов это 8 МБ и, что важнее, на треть меньше кэш-линий при обходе.
C3 не переупорядочивает поля сам (порядок важен для C-ABI), так что это ваша работа.
Упражнение **e0201_alignment** — реализовать эти формулы и «компилятор раскладок».

Ещё одна деталь: **false sharing**. Если два потока пишут в разные переменные, лежащие в
одной кэш-линии, линия «пинг-понгует» между ядрами. Счётчики per-thread выравнивают по
64 байта (`@align(64)`). Подробнее — в главе 12.

## 4. Линейный аллокатор (арена, bump allocator)

Самый простой и самый важный аллокатор. Есть буфер и смещение; выделение — сдвиг
смещения, освобождения отдельных объектов нет, только сброс всего сразу.

```
 buf: [##########AAAA##BBBBBBBB####CC..................................]
      ^                                ^                               ^
      start                          offset                           end
 alloc(n, a): p = align_up(offset, a); if (p + n > end) fail; offset = p + n; return p
 reset():     offset = 0
```

Свойства: выделение — несколько инструкций, нет фрагментации, нет заголовков (лишь
выравнивание), идеальная локальность (объекты, выделенные подряд, лежат подряд).
Освобождение отдельного объекта невозможно — и именно поэтому быстро.

Где используется: загрузка всего «навсегда» при старте; временные вычисления;
**кадровый аллокатор**; построение структур, которые потом «замораживаются»
(загруженный уровень, скомпилированный шейдерный граф). В C3 это `ArenaAllocator`
и `tmem`/`@pool` (временная арена, сбрасываемая при выходе из `@pool`). В Unreal —
`FMemStack` и `TMemStackAllocator`; в Unity — `Allocator.Temp` (живёт кадр) и
`Allocator.TempJob` (до 4 кадров); в Bitsquid — `TempAllocator` на стеке.

Важно отслеживать **high-water mark** — максимальное смещение за всё время. Это ответ
на вопрос «какого размера должен быть буфер»: прогоните самые тяжёлые сцены и добавьте
запас. Упражнение **e0202_linear_arena**.

Отдельный приём — **виртуальная арена**: зарезервировать огромный диапазон адресов
(например, 64 ГБ через `mmap(PROT_NONE)`/`VirtualAlloc(MEM_RESERVE)`), а физические
страницы подключать по мере роста смещения. Арена растёт без копирования и без
перемещения указателей, а лимит фактически определяется бюджетом. Так устроены
арены в Our Machinery, в RAD Debugger и во многих современных «handmade»-движках.

## 5. Стековый аллокатор с маркерами

Линейный аллокатор, который умеет откатываться не только к нулю, но и к сохранённой
позиции — **маркеру**:

```
 Marker m0 = stack.mark();             // [.........................]
 load_level_static();                  // [LLLLLLLL.................]
 Marker m1 = stack.mark();             //          ^m1
 load_section_a();                     // [LLLLLLLLAAAAA............]
 stack.free_to(m1);                    // [LLLLLLLL.................]  секция A выгружена
 load_section_b();                     // [LLLLLLLLBBBBBBB..........]
 stack.free_to(m0);                    // [.........................]  уровень выгружен
```

Освобождение строго в порядке, обратном выделению (LIFO) — как у стека вызовов.
Это идеально совпадает с вложенными временами жизни: игра ⊃ уровень ⊃ секция ⊃ временные
данные загрузки.

**Двусторонний стек** (double-ended stack, Gregory 6.2.1.4) растёт с двух концов одного
буфера: снизу — долгоживущие данные (уровень), сверху — временные (буферы распаковки при
загрузке). Ни одна из сторон не имеет фиксированного лимита: им общий бюджет. Так делала
Hydro Thunder (Midway) — пример из книги Грегори. Упражнение **e0203_stack_markers**.

Подводный камень: маркер, взятый *после* другого маркера, становится недействительным
после отката к более раннему. Отладочная версия может хранить счётчик «поколения»
маркеров или стек маркеров и ловить такие ошибки.

## 6. Пул (аллокатор блоков фиксированного размера)

Для объектов одного размера с произвольным временем жизни (пули, частицы, узлы, звуки,
сетевые сообщения) идеален пул: буфер разбит на N блоков одного размера, а свободные
блоки связаны в **интрузивный свободный список** — указатель «следующий свободный»
хранится *внутри самого свободного блока* (он всё равно не используется):

```
 блоки:     [0][1][2][3][4][5][6][7]
 занято:     X     X  X        X
 free_head ──> 1 ──> 4 ──> 5 ──> 6 ──> null

 alloc(): b = free_head; free_head = b.next; return b         O(1)
 free(b): b.next = free_head; free_head = b                   O(1)
```

Никакого поиска, никакой фрагментации (все блоки одинаковы), нулевой оверхед на
заголовки. Требования: размер блока ≥ размера указателя (или индекса — тогда можно
хранить 16- или 32-битный индекс), блок выровнен.

Варианты:

* **Пулы по классам размеров** (8, 16, 32, 64, …): так устроены «small block
  allocators» практически всех general-purpose аллокаторов (jemalloc, mimalloc, `FMallocBinned`
  в Unreal). Мелкие аллокации обслуживаются пулом, крупные — другим механизмом.
* **Пул объектов** (object pool) — пул + конструирование/сброс, с `active`-флагами;
  классический паттерн Nystrom «Object Pool».
* Индексы вместо указателей и **поколения** — это уже handles (глава 03).
* LIFO-порядок свободного списка выгоден для кэша: только что освобождённый блок
  «тёплый» и выдаётся первым.

Упражнение **e0204_pool**.

## 7. Кадровый и двухбуферный кадровый аллокатор

Огромное количество данных живёт ровно один кадр: список видимых объектов, отсортированные
draw-команды, временные строки для UI и отладки, результаты физических запросов, массивы
событий. Для них — линейный аллокатор, сбрасываемый в начале каждого кадра:

```c3
fn void begin_frame() => frame_arena.reset();
// ... в течение кадра:
VisibleItem[] vis = frame_new_array(VisibleItem, count);   // освобождать не нужно
```

Но если кадры **конвейеризованы** (глава 00, раздел 5) — игровой поток готовит кадр N+1,
пока поток рендера ещё обрабатывает кадр N, — данные кадра N должны прожить до конца
следующего кадра. Отсюда **double-buffered frame allocator** (Gregory 6.2.1.6): две арены,
которые меняются ролями на границе кадров:

```
 кадр:        N             N+1            N+2
 арена A:  [пишем N]     [читает рендер] [сброс, пишем N+2]
 арена B:  [рендер N-1]  [сброс, пишем N+1] [читает рендер]
```

При конвейере глубиной три кадра (CPU → render thread → GPU) нужны три арены; для
GPU-памяти это кольцевой буфер с «заборами» (fences): участок можно переиспользовать
только после того, как GPU подтвердил, что закончил кадр. Unity `Allocator.TempJob`
с проверкой «прожил больше 4 кадров — предупреждение» — та же идея с отладочной страховкой.

Полезная отладочная техника — **заливка шаблоном** при сбросе: всю освобождённую память
заполнить, скажем, `0xCD` (так делает отладочная куча MSVC: `0xCD` — выделено, но не
инициализировано, `0xDD` — освобождено, `0xFD` — guard bytes). Указатель на данные
прошлого кадра, по ошибке сохранённый «навсегда», в отладке сразу даст мусорные
значения `0xCDCDCDCD`, которые легко узнать, — вместо тихого бага, проявляющегося раз в час.
Упражнение **e0205_frame_allocator**.

## 8. Бюджеты

На консоли память — это фиксированное число (например, ~13.5 ГБ доступных игре на PS5),
и её нужно **поделить заранее**: текстуры 4 ГБ, меши 1.5, звук 400 МБ, анимации 300,
геймплей 200, кадровая память 64 МБ × 2, … Каждая подсистема получает свой аллокатор
с лимитом, и превышение — это ошибка, видимая сразу у конкретной команды, а не «OOM
через 3 часа в непонятном месте».

```
 ┌───────────────────────────── 5 GB игровая память ───────────────────────────┐
 │ Textures 2048M │ Meshes 900M │ Audio 300M │ Anim 250M │ Game 200M │ Frame 2x64M│...
 └─────────────────────────────────────────────────────────────────────────────┘
   каждая подсистема:  used / peak / budget / число аллокаций / неудачи
```

Практика:

* **Теги памяти** (memory tags/categories): каждая аллокация помечена подсистемой
  (`LLM` — Low Level Memory tracker — в Unreal, `MemLabel` в Unity, теги в Frostbite).
  Отчёт по тегам — первое, что открывают при борьбе за память.
* **Иерархия аллокаторов**: аллокатор подсистемы берёт память у родителя большими
  кусками. Bitsquid и Our Machinery строили дерево аллокаторов, где каждый узел
  отслеживал свою статистику, а при выходе проверял, что всё освобождено (поиск утечек
  *по подсистеме*).
* **Peak важнее current**: бюджет нарушается в пике (загрузка уровня, взрыв с тысячей
  частиц), а не в среднем.
* Отказ при превышении бюджета — это решение дизайна: где-то (частицы, декали) лучше
  тихо не создать объект и посчитать неудачу, где-то (загрузка уровня) — сразу упасть.

## 9. Интерфейс аллокатора

Чтобы контейнеры и подсистемы не зависели от конкретного аллокатора, нужен общий
интерфейс. Варианты:

* **Шаблонный параметр** (C++ STL `std::allocator<T>`, EASTL, `TArray<T, TInlineAllocator<16>>`):
  без косвенного вызова, но тип контейнера зависит от аллокатора — `vector<int, A>` и
  `vector<int, B>` несовместимы.
* **Указатель на интерфейс** (Bitsquid `Allocator&`, Zig `std.mem.Allocator`, Odin
  `context.allocator`, C3 `Allocator`): косвенный вызов на каждую аллокацию (дёшево по
  сравнению с самой аллокацией), зато любой контейнер работает с любым аллокатором.

В C3 это интерфейс из `std::core::mem::alloc`:

```c3
interface Allocator
{
    fn void*? acquire(sz size, AllocInitType init_type, sz alignment = 0);
    fn void*? resize(void* ptr, sz new_size, sz alignment = 0);
    fn void release(void* ptr, bool aligned);
}
```

Тонкости реализации:

* `alignment == 0` означает «по умолчанию» (16 байт для heap-аллокатора C3).
* `init_type == ZERO` — память надо обнулить.
* `resize` для арены: если `ptr` — **последняя** выделенная область, её можно
  расширить на месте (сдвинуть смещение). Иначе — выделить новую и скопировать.
  Это критично для `List`, который растёт удвоением: без расширения на месте
  арена теряет всю предыдущую ёмкость при каждом росте.
* `release` для арены: можно освободить на месте, если это последняя аллокация,
  иначе — ничего не делать.
* Чтобы `resize` знал старый размер, аллокатор хранит **заголовок** перед блоком
  (как `ArenaAllocatorHeader` в stdlib) — или требует, чтобы размер передавал вызывающий
  (так сделано в Zig и Odin: «sized deallocation», экономит заголовки).

Упражнение **e0206_allocator_interface** — реализовать этот интерфейс для арены с
бюджетом и статистикой и использовать её со стандартными `List{T}` и `HashMap{K,V}`.

## 10. Общего назначения и всё остальное

Для того, что не вписывается в схемы выше (редактор, стриминг ассетов разного размера),
нужен general-purpose аллокатор. В движках популярны:

* **TLSF** (Two-Level Segregated Fit) — O(1) гарантированно, низкая фрагментация,
  используется в реалтайм-системах и для GPU-кучи;
* **buddy allocator** — блоки степеней двойки, быстрое слияние соседей; часто для
  крупных блоков и виртуальной памяти текстур;
* **mimalloc / rpmalloc / jemalloc** — быстрые многопоточные аллокаторы с
  thread-local кэшами; Unreal использует `FMallocBinned2/3`, многие движки
  подключают rpmalloc или mimalloc.
* **Дефрагментация с перемещением** — возможна, только если на объекты ссылаются
  через handles (глава 03), а не через сырые указатели: тогда аллокатор может
  сдвинуть блоки и обновить таблицу. Так работали старые консольные движки и
  текстурные пулы.

## 11. Отладка памяти

* **Tracking allocator**: оборачивает другой аллокатор и считает выделения, байты,
  пики, а при завершении печатает утечки (в C3 — `TrackingAllocator`, упр. 102 трека 1).
* **Guard bytes / canaries**: несколько байт с известным значением до и после блока;
  проверка при освобождении ловит выход за границы.
* **Fill patterns**: `0xCD`, `0xDD`, `0xFEEEFEEE` — мусор, который легко узнать.
* **Page guards**: каждая аллокация на своей странице, за ней — недоступная страница;
  выход за границу = мгновенный segfault в точном месте (Electric Fence, PageHeap,
  AddressSanitizer работает похожим образом через теневую память).
* **Callstack-трекинг** в отладочных сборках: при каждой аллокации записывается стек,
  и утечку можно найти по месту выделения.

Всё это включается в отладочных сборках и выключается в релизе — поэтому аллокаторы в
движке почти всегда пишут с условной компиляцией (`$if $feature(MEM_DEBUG): ... $endif`).

## 12. Как это делают реальные движки

* **Unreal**: глобальный `GMalloc` (`FMallocBinned2/3`, опционально `FMallocAnsi`,
  `FMallocStomp` для поиска порч памяти), `FMemStack` для временных данных, `TArray` с
  подключаемыми политиками (`TInlineAllocator`, `TFixedAllocator`), LLM для тегов.
* **Unity** (DOTS): `Allocator.Temp` (кадр, сбрасывается автоматически),
  `Allocator.TempJob` (до 4 кадров, предупреждение при утечке), `Allocator.Persistent`;
  `NativeArray<T>` требует явный `Dispose`, а система безопасности ловит утечки и гонки.
* **Bitsquid/Stingray**: `Allocator` — абстрактный класс; `HeapAllocator`,
  `PageAllocator`, `TempAllocator<N>` (буфер на стеке + fallback), `ScratchAllocator`
  (кольцевой). Каждая подсистема получает свой аллокатор и при уничтожении проверяет утечки.
  Статья «Custom Memory Allocation in C++» (Niklas Frykholm) — классика.
* **id Tech** (Doom 3 BFG): `idBlockAlloc`, отдельные кучи для фреймовых данных,
  frame-local аллокаторы для рендера (`R_FrameAlloc`) с двойной буферизацией под SMP.
* **Our Machinery**: виртуальные арены, `tm_allocator_i` с явным размером при free,
  трекинг по «scope»-именам.
* **C3**: `mem` (heap), `tmem` (временная арена) + `@pool`, интерфейс `Allocator`,
  `ArenaAllocator`, `DynamicArenaAllocator`, `TrackingAllocator`, `OnStackAllocator`.
  Соглашения stdlib: `new_*`/`init(allocator)` принимает аллокатор явно, `t*` — временный.

## 13. Подводные камни

* **Висячие указатели после сброса арены.** Самая частая ошибка с кадровыми
  аллокаторами: указатель из кадровой памяти сохранили в долгоживущей структуре.
  Лекарство — fill patterns в отладке, явные типы-обёртки «FrameSlice», ревью.
* **Смешивание аллокаторов.** Освобождение через не тот аллокатор, который выделил.
  Контейнер должен помнить свой аллокатор (как `List` в C3).
* **Выравнивание заголовка.** Если перед блоком лежит заголовок, выравнивать надо
  *пользовательский* указатель, а заголовок ставить непосредственно перед ним.
* **Переполнение при выравнивании.** `offset + size` может переполниться при огромном
  `size` — проверяйте `size > capacity - offset`, а не `offset + size > capacity`.
* **Многопоточность.** Арена не потокобезопасна. Решения: арена на поток
  (thread-local), атомарный `fetch_add` смещения (lock-free bump), или кадровая арена
  на каждый job worker (глава 12).
* **«Умный» resize.** Расширение на месте работает, только если блок — последний.
  Чередование роста двух `List` в одной арене всё равно приведёт к копированиям.

## Вопросы для самопроверки

1. Почему `align_up(x, a) = (x + a - 1) & ~(a - 1)` работает только для степеней двойки?
2. Какой порядок полей минимизирует размер структуры `{ char, double, short, int, char }`?
   Каков размер до и после?
3. Чем стековый аллокатор с маркерами отличается от линейного? Приведите сценарий,
   где без маркеров не обойтись.
4. Почему свободный список пула может храниться внутри свободных блоков? Каково
   минимальное ограничение на размер блока?
5. Нарисуйте временную диаграмму двухбуферного кадрового аллокатора при конвейере
   «игровой поток → поток рендера». Что сломается, если арен будет одна?
6. Зачем `resize` арены проверяет, что блок последний? Что произойдёт с `List`, который
   растёт до 1 млн элементов в арене без этой оптимизации?
7. Как бы вы организовали бюджеты памяти для игры с открытым миром и стримингом?
8. Почему дефрагментация с перемещением требует handles вместо указателей?
