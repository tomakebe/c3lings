# Глава 15. Профилирование и отладка

> Упражнения главы: `e1501`–`e1506`. Читайте главу целиком до них — упражнения
> ссылаются на конкретные разделы.

Игровой движок отличается от большинства программ тем, что у него есть **жёсткий
бюджет времени**: 16,6 мс на кадр при 60 Гц, 8,3 мс при 120 Гц, 11,1 мс для VR при
90 Гц — и этот бюджет делится между десятком подсистем, каждая из которых пишется
своими людьми. Второе отличие — **огромное пространство состояний**: тысячи
объектов, физика, ИИ, скрипты, сеть. Баг, который проявляется раз в двадцать минут
игры на одном уровне, — норма жизни.

Поэтому в серьёзных движках отладочная инфраструктура — не «прикрутим потом», а
первоклассная подсистема, проектируемая с первого дня: профилировщик, отслеживание
памяти, логирование, assert'ы, debug draw, консоль с переменными. Хорошие
инструменты окупаются многократно: команда из 50 человек, каждый из которых
экономит полчаса в день, — это три человеко-года в год.

Эта глава — о том, как эти инструменты устроены внутри и какие решения при их
проектировании принимают.

## 1. Карта инструментов

```
                 ┌─────────────────────── CPU ───────────────────────┐   ┌──── GPU ────┐
                 │  сэмплирующие            инструментирующие         │   │             │
  внешние        │  Superluminal, VTune,    Tracy, Optick, Remotery,  │   │ RenderDoc   │
                 │  perf, Instruments       Unreal Insights, PIX(CPU) │   │ PIX, Nsight │
                 └────────────────────────────────────────────────────┘   └─────────────┘
                 ┌──────────────────────── в самой игре ──────────────────────────────┐
  встроенные     │ оверлей зон и графики кадра · счётчики · трекер памяти · лог      │
                 │ debug draw · консоль + cvars · assert'ы · capture-on-hitch          │
                 └─────────────────────────────────────────────────────────────────────┘
```

**Сэмплирующий профилировщик** (Superluminal, Intel VTune, Linux `perf`, macOS
Instruments) периодически (раз в 0,1–1 мс) останавливает потоки и снимает стек
вызовов. Плюсы: не нужно менять код, видна *вся* программа, включая драйвер и
библиотеки. Минусы: статистика, а не точная хронология; редкие короткие события
(один кадр-спайк на 50 мс раз в минуту) тонут в среднем; нужна отладочная
информация и нормальные стеки.

**Инструментирующий профилировщик** (Tracy, Optick, Remotery, Unreal Insights,
Unity Profiler) записывает события, которые программист явно расставил в коде:
«зона `physics` началась в такт T1 и закончилась в такт T2». Плюсы: точная
хронология каждого кадра на каждом потоке, видны ожидания и спайки, можно
оставить включённым в игре. Минусы: видно только то, что размечено; каждая зона
стоит десятки наносекунд, поэтому на мелкие функции её не ставят.

На практике используют оба: инструментирующий показывает, *в каком кадре и какой
подсистеме* проблема, сэмплирующий — *какие именно инструкции* горят внутри.

**GPU-инструменты** (RenderDoc, PIX, NVIDIA Nsight Graphics, AMD RGP) захватывают
кадр целиком — все вызовы графического API, состояния, текстуры — и позволяют
пошагово его разобрать. Это отдельный мир; движку нужно лишь не мешать им
(именовать ресурсы и проходы через debug-маркеры API) и, желательно, уметь
программно инициировать захват (у RenderDoc есть in-application API).

## 2. Инструментирующий профилировщик

### 2.1. Зона и её стоимость

Зона — пара событий begin/end с одним и тем же именем. Главное требование —
**сбалансированность**: каждый begin должен получить свой end, даже при `return`,
`break` или ошибке посередине. В C++ это решает RAII (`ZoneScoped` в Tracy создаёт
объект на стеке, деструктор пишет end). В C3 тот же эффект даёт `defer`, а самый
удобный синтаксис — макрос с trailing-блоком:

```c3
macro @zone(String name; @body)
{
    g_prof.begin(name);
    defer g_prof.end();
    @body();
}

fn int find_path(int target)
{
    @zone("find_path")
    {
        if (target < 0) return -1;   // return выйдет из find_path, end() всё равно сработает
        ...
    };
    return ...;
}
```

Тело макроса встраивается в место вызова, поэтому `return` внутри `@body`
возвращает из объемлющей функции, а `defer` макроса выполняется при выходе из его
области видимости. Это ровно RAII-семантика.

Сколько стоит зона? В Tracy — порядка 5–20 нс на пару событий. Из чего она
складывается:

1. **Чтение часов.** `rdtsc` на x86 — ~20 тактов. `QueryPerformanceCounter` /
   `clock_gettime(CLOCK_MONOTONIC)` — 20–50 нс через vDSO. Системный вызов на
   каждую зону недопустим.
2. **Запись события** в буфер: несколько слов памяти. Буфер *свой у каждого
   потока* — никаких мьютексов и атомиков в горячем пути.
3. **Имя.** Строку никто не копирует: событие хранит указатель (или id) на
   статическое описание «места» — имя, файл, строку, цвет. В Tracy это
   `static const SourceLocationData` в каждой точке раскрытия макроса. В C3 срез
   `String` строкового литерала указывает на данные в сегменте только для чтения
   и живёт вечно — его можно хранить как есть.

```
     поток 0 (main)                    поток 1 (worker)
  ┌──────────────────────┐         ┌──────────────────────┐
  │ ring buffer событий  │         │ ring buffer событий  │   запись без блокировок
  │ [B frame t=100]      │         │ [B job  t=130]       │
  │ [B phys  t=102]      │         │ [E      t=170]       │
  │ [E       t=140]      │         │ ...                  │
  └──────────┬───────────┘         └──────────┬───────────┘
             └────────────┬───────────────────┘
                          ▼   раз в кадр / фоновый поток
                 сбор, сортировка по времени, отправка в
                 просмотрщик (сеть) или агрегация для оверлея
```

### 2.2. Часы

Профилировщику нужны монотонные часы высокого разрешения. На x86 инвариантный
TSC (`rdtsc`) тикает с постоянной частотой независимо от энергосбережения и
синхронизирован между ядрами на современных CPU; переводить такты в наносекунды
нужно один раз — при отображении, по откалиброванной частоте. На ARM есть
`CNTVCT_EL0`. Переносимый вариант — `QueryPerformanceCounter` на Windows и
`clock_gettime(CLOCK_MONOTONIC)` на POSIX.

Важное архитектурное решение: **часы — это зависимость, а не глобальная
функция**. Профилировщик получает указатель на функцию `fn ulong()`. В игре это
`rdtsc`, в тестах — подставные часы, которые тест двигает вручную:

```c3
alias ClockFn = fn ulong();
ulong g_now;
fn ulong fake_clock() => g_now;
fn void work(ulong ticks) { g_now += ticks; }   // «работа» в тестах
```

Так проверки профилировщика полностью детерминированы. Тот же приём используют
для времени игры вообще (см. главу 01): игровая логика никогда не читает
системные часы напрямую.

### 2.3. Буфер фиксированного размера

Профилировщик не имеет права аллоцировать память в горячем пути: аллокация сама
по себе может стоить микросекунды, захватывать блокировку и — хуже всего —
искажать измерения той самой системы, которую мы меряем. Поэтому буфер событий
фиксированный, и надо решить, что делать при переполнении:

* **Кольцевой буфер** (перезаписываем старые события) — для «чёрного ящика»:
  всегда есть последние N миллисекунд.
* **Отбрасывать новые и считать `dropped`** — для покадрового захвата. Важно
  сохранить баланс стека: даже отброшенная зона кладёт в стек маркер `-1`, чтобы
  её `end()` ничего не испортил.
* **Сброс в фоновый поток** (Tracy) — буфер периодически сливается, а при
  отсутствии подключённого просмотрщика события копятся в памяти.

### 2.4. Сколько зон ставить

Правило большого пальца — **не мельче ~1 мкс работы** в зоне. Зона на каждую
функцию `vec3_add` превратит профилировщик в главный потребитель времени
(«эффект наблюдателя»). Типичная разметка: кадр, каждая система, каждая фаза
рендера, каждая задача job system, загрузка ассетов, сборка мусора скриптов. Для
очень частых, но важных мест используют счётчики, а не зоны.

Ещё одно решение — **компилируемость в ноль**. Зоны оборачивают в макрос, который
в retail-сборке раскрывается в пустоту. В C3 это `$if` по флагу компиляции
(`-D PROFILE`) внутри макроса: тело без begin/end.

## 3. Агрегация: от событий к дереву

Сырая хронология незаменима для анализа одного кадра, но оверлей в игре должен
показывать агрегированные числа. Из событий строят три представления:

```
 timeline (сырые)          call tree (агрегат по пути)          flat (агрегат по имени)
 frame   [0..34]           frame    calls=1 total=34 self=1     step   calls=3 self=15
  phys   [2..17]            phys    calls=1 total=15 self=0     render calls=1 self=7
   step  [2..7]              step   calls=3 total=15 self=15    ...
   step  [7..12]            render  calls=1 total=7  self=7
   step  [12..17]
  render [27..34]
```

* **total (inclusive)** — время узла вместе с вложенными.
* **self (exclusive)** — total минус total прямых детей. Именно self показывает,
  где исполняется код; узел с большим total и нулевым self — просто «папка».

### 3.1. Построение дерева за один проход

События записаны в порядке открытия (preorder) вместе с глубиной. Значит, родитель
события глубины `d` — последний узел, в который мы вошли на глубине `d-1`. Держим
массив `path[depth]`:

```c3
fn void ZoneTree.add_event(&self, ZoneEvent e)
{
    int parent = self.path[e.depth];
    int node   = self.find_or_add_child(parent, e.name);
    self.nodes[node].calls++;
    self.nodes[node].total += e.end - e.begin;
    self.path[e.depth + 1] = node;
}
```

Дети хранятся интрузивным списком `first_child / next_sibling` *на индексах*.
Индексы вместо указателей дают три вещи: дерево можно скопировать `memcpy` (в
историю кадров), сбросить одной записью `count = 1` и сериализовать для отправки
в просмотрщик. Это тот же принцип, что в главе 03 и в «дереве в арене» из трека 1.

Сравнение имён строк при агрегации — дорого. Реальные профилировщики сравнивают
указатели на статическое описание места (`SourceLocation*`) или его числовой id,
а строку смотрят только при отображении.

### 3.2. История кадров и статистика

Одно измерение ничего не значит: кадры шумят на ±10% от кеша, планировщика ОС,
турбобуста. Оверлей показывает **min/avg/max за последние N кадров** — кольцевой
буфер фиксированного размера. Для поиска спайков полезнее не среднее, а **95-й и
99-й перцентили** и **худший кадр** в окне. Многие движки умеют
**capture-on-hitch**: если кадр превысил порог (скажем, 33 мс), полная хронология
этого кадра сохраняется на диск автоматически. Сэмплирующий профилировщик такой
кадр почти никогда не поймает.

```
   frame time, мс
   40 |                    *            <- hitch: сохранить хронологию
   30 |
   20 |
   16 |--*--*-*---*--*--------*--*-*--  бюджет 16.6
   10 |
      +---------------------------------> кадры
```

### 3.3. Счётчики и графики

Помимо зон, профилировщик собирает **счётчики** (plots в терминах Tracy):
draw calls, треугольники, число активных тел физики, байты выделенной памяти,
размер очереди задач. Их значение записывается раз в кадр и рисуется графиком
рядом с хронологией. Классический приём отладки производительности — найти кадр,
где выросло время рендера, и увидеть на соседнем графике скачок draw calls.

### 3.4. Многопоточность и GPU

В многопоточном движке (глава 12) у каждого потока свой буфер событий и свой
стек зон; события связываются по времени, и просмотрщик рисует дорожки потоков
одну под другой. Сразу видно, где воркеры простаивают в ожидании зависимости, —
это и есть главный инструмент настройки job system.

GPU-время меряют timestamp-запросами графического API, вставленными в командный
буфер. Результаты приходят на 2–3 кадра позже, поэтому запросы хранят в
кольцевом буфере на несколько кадров и читают без ожидания. Синхронизация
CPU-часов и GPU-часов — отдельная калибровка.

## 4. Отслеживание памяти

Вопрос «кто съел 40 МБ на этом уровне?» на консольном проекте задают каждую
неделю. Ответ даёт **отслеживающий аллокатор-обёртка**: он реализует тот же
интерфейс, что и обычный аллокатор (в C3 — интерфейс `Allocator` с методами
`acquire`, `resize`, `release`), и перед делегированием «настоящему» аллокатору
ведёт учёт.

### 4.1. Где хранить метаданные блока

**Вариант A: заголовок перед блоком.**

```
  backing.acquire(size + 32)
  |<------- AllocHeader (32) ------->|<-------- size байт --------->|
  | prev | next | size | id | tag    |  данные пользователя          |
  ^ raw                              ^ отдаём raw + 32
```

Быстро (O(1) на всё), но меняет раскладку памяти (блоки растут на 32 байта,
что маскирует переполнения буфера или, наоборот, создаёт новые), а заголовок надо
выравнивать: 32 байта сохраняют 16-байтное выравнивание malloc, а для
выровненных на 64 запросов заголовок кладут с отступом и хранят смещение.

**Вариант B: таблица на стороне** — хеш-таблица `адрес → метаданные`. Раскладка
не меняется, можно трекать чужие аллокаторы, но каждый вызов — поиск в таблице и
(в многопоточном случае) блокировка. Так работают инструменты вроде Unreal
Insights Memory и heaptrack.

Живые блоки связывают в **интрузивный двусвязный список** (или хранят в таблице),
чтобы в конце уровня пройти по ним и напечатать утечки. Тонкость с `resize`:
`realloc` может *переместить* блок, а соседи по списку хранят указатели на
старый адрес. Поэтому порядок такой: вынуть заголовок из списка → resize →
вставить заголовок по новому адресу обратно. При ошибке resize старый блок жив,
и его нужно вернуть в список.

### 4.2. Теги и бюджеты

Каждое выделение помечается **тегом подсистемы** (Unreal: LLM — Low Level Memory
tracker; во многих движках `MemTag`/`MemCategory`). Текущий тег лежит на вершине
стека тегов (thread-local), который удобно двигать тем же scoped-макросом, что и
зоны:

```c3
@mem_tag(&tracker, PHYSICS)
{
    bodies.push(...);   // все выделения внутри помечены PHYSICS
};
```

Для каждого тега держат живые байты, их **пик** и число блоков. Пик важнее
текущего значения: на консоли падение происходит в пиковый момент, а не в
среднем. Тегам назначают **бюджеты** («текстуры — 1,5 ГБ, аудио — 200 МБ»), и
сборка на CI падает, если тестовый уровень их превысил.

Тег фиксируется при выделении. При `resize` блок сохраняет исходный тег, даже
если вызов пришёл из другого контекста, — иначе учёт рассыплется.

### 4.3. Утечки и стеки

Отчёт об утечках в конце уровня — список живых блоков с id, тегом и размером.
Id — порядковый номер выделения: если утечка воспроизводится детерминированно,
можно поставить условную точку останова «на выделении №1234». Более богатые
трекеры записывают стек вызовов каждого выделения (дорого — десятки–сотни нс
на unwinding), поэтому его включают по флагу или для выборки (каждое N-е
выделение).

Стандартная библиотека C3 уже содержит `TrackingAllocator`
(`std::core::mem::allocators`), а в упражнении `e1504` вы напишете свой, с
тегами и пиками.

## 5. Логирование

`printf` для лога движка не годится. Требования:

1. **Категории и уровни.** Категории — по подсистемам (CORE, RENDER, PHYSICS,
   AI, NET); уровни — ERROR, WARN, INFO, VERBOSE. Порог задаётся **на категорию**:
   отлаживаете физику — `log PHYSICS VERBOSE`, остальное молчит. Unreal:
   `DECLARE_LOG_CATEGORY_EXTERN(LogPhysics, Log, All)` и `UE_LOG(LogPhysics,
   Verbose, ...)`.
2. **Отфильтрованное сообщение почти бесплатно.** Нельзя ни форматировать
   строку, ни даже *вычислять аргументы*, если сообщение не пройдёт фильтр.
   Поэтому лог — это всегда макрос вида `if (enabled(cat, lvl)) log_impl(...)`.
   В C3 аргументы макроса ленивые: `...$vaarg` подставляет сами выражения,
   поэтому

   ```c3
   macro @log(Category cat, Level lvl, String fmt, ...)
   {
       if (g_log.enabled(cat, lvl))
       {
           char[128] buf;
           String msg = (String)io::bprintf(&buf, fmt, ...$vaarg) ?? "<too long>";
           g_log.dispatch(cat, lvl, msg);
       }
   }
   @log(RENDER, VERBOSE, "drawcalls=%d", count_drawcalls());   // не вызовется, если выключено
   ```
3. **Compile-time stripping.** В retail-сборке VERBOSE и INFO вырезаются целиком
   (`$if` по уровню-константе) — ни кода, ни строк в бинарнике (строки лога
   выдают много информации реверс-инженерам).
4. **Несколько приёмников (sinks)**: консоль, файл, отладчик (`OutputDebugString`),
   сеть, внутриигровая консоль и **кольцевой буфер последних сообщений**, который
   попадает в crash dump. Последние 200 строк лога перед падением часто ценнее
   самого стека.
5. **Без кучи** в пути логирования: формат в буфер на стеке. Логирование из
   обработчика нехватки памяти не должно само требовать памяти.
6. **Потоки.** Писать в файл из 12 потоков с мьютексом — значит сериализовать
   движок на логе. Обычно поток кладёт готовую строку в lock-free очередь, а
   отдельный поток пишет на диск. При падении очередь надо успеть слить.
7. **Контекст.** Номер кадра, имя потока, категория, уровень — в каждой строке.
   Время — номер кадра и игровое время, а не только wall clock: так лог
   сопоставим с реплеем.

Анти-паттерн — лог как способ отладки в горячем цикле: 10 000 строк в кадр не
прочитает никто, а производительность умрёт. Для потоковых данных — счётчики и
графики профилировщика, для пространственных — debug draw.

## 6. Assert'ы

Assert — исполняемая документация инварианта. В движках их несколько видов
(терминология Unreal, похожие есть везде):

| вид | debug | release | поведение |
|---|---|---|---|
| `check(x)` | проверяется, падение | вырезан, `x` не вычисляется | фатальный инвариант |
| `verify(x)` | проверяется | `x` вычисляется, не проверяется | выражение с побочным эффектом |
| `ensure(x)` | сообщение + break один раз | сообщение, игра продолжается | «так не должно быть, но выживем» |

Хороший движковый assert:

* сообщает **текст выражения**, файл, строку и функцию. В C3:
  `$stringify(#expr)`, `$$FILE`, `$$LINE`, `$$FUNC` (внутри макроса они дают
  место *вызова* макроса);
* вычисляет выражение **ровно один раз** — в макросе это значит использовать
  `#expr` в одном месте;
* **возвращает bool**, чтобы можно было обработать ошибку «мягко»:
  `if (!@check(target != null, "no target")) return;`;
* умеет **«Ignore always»**: каждое место вызова сообщает о себе один раз, а не
  60 раз в секунду. Трюк — `static bool reported;` внутри макроса: у каждой
  точки раскрытия своя статическая переменная;
* в отладочной сборке **останавливает отладчик** на месте вызова
  (`__debugbreak()`, `raise(SIGTRAP)`), а не внутри функции-обработчика;
* перед падением **сбрасывает лог** и пишет crash dump.

```c3
macro bool @check(#expr, String msg)
{
    static bool reported;
    if (#expr) return true;
    g_check_failures++;
    if (!reported)
    {
        reported = true;
        @log(CORE, ERROR, "check failed: %s (%s) in %s", $stringify(#expr), msg, $$FUNC);
    }
    return false;
}
```

Частая ошибка — побочный эффект в выражении `check`, который пропадает в
release (`check(list.remove(x))`). Её ловят правилом ревью и `verify`. Вторая —
assert там, где нужна обработка ошибки: битый файл сохранения от игрока — это не
нарушение инварианта, а ожидаемая ситуация, для неё — Optional и `excuse`.

## 7. Debug draw

Debug draw — «нарисуй мне это» из любой точки кода: луч, по которому стреляет ИИ;
AABB тел физики; путь навигации; текст над головой юнита. Самый полезный
инструмент отладки геймплея: пространственную ошибку глазами находят за
секунды, а по логу — за час.

### 7.1. API

```c3
dd.line(from, to, color, PHYSICS);                 // этот кадр
dd.sphere(hit_point, 0.2, RED, GAMEPLAY, frames: 60);   // висит секунду
dd.text(unit.pos + up, "state: ATTACK", AI);
```

Принципы:

* **Immediate mode.** Никаких объектов, хендлов и регистрации: вызвать и забыть.
  Код геймплея, физики и скриптов не знает о графическом API.
* **Команды копируются в буфер**, рисует их рендерер одним проходом в конце кадра
  (обычно один динамический вершинный буфер линий + один для треугольников,
  с depth test и без).
* **Время жизни.** `frames = 1` — только этот кадр (по умолчанию: код вызывается
  каждый кадр). Большая длительность — для одиночных событий: место удара,
  траектория броска. Длительность лучше задавать в *игровом* времени, чтобы
  пауза не стирала картинку.
* **Категории с маской**, переключаемые из консоли (`dd_physics 1`). Выключенная
  категория отбрасывается сразу при вызове — дешевле, чем рисовать и скрывать.
  Ещё лучше — проверка маски *до* вычисления аргументов, как в логе.
* **Фиксированный буфер и `dropped`.** Переполнение — не падение, а счётчик в
  оверлее.
* **Текст копируется** внутрь команды или в кадровую арену. Срез `String`,
  переданный в `text()`, часто указывает на временный буфер (`tformat`, стек);
  команда, живущая 60 кадров, получит висячий указатель.
* **Потоки.** Физика и задачи job system вызывают debug draw из воркеров. Либо
  буфер на поток (сливаются при flush), либо атомарный счётчик-курсор в общем
  массиве (`idx = cursor.add(1)`).
* **Компилируется в ноль** в retail.

### 7.2. Flush

```
  кадр N: системы вызывают dd.*()  ──►  [cmd0 cmd1 cmd2 cmd3 cmd4]
  render: нарисовать все по порядку ──►  холст / вершинный буфер
  затем: frames_left--, удалить истёкшие СТАБИЛЬНО ──►  [cmd0 cmd3]
```

Стабильное уплотнение (а не swap-remove) сохраняет порядок рисования: поздние
команды остаются поверх ранних, картинка не «мигает».

## 8. Консоль и cvars

Внутриигровая консоль (Quake, Source, Unreal, id Tech) — центр всех отладочных
инструментов: включить профилировщик, поменять параметр физики на лету,
телепортироваться, выполнить конфиг. Её три части:

### 8.1. Токенизатор

`sim_steps 4; echo "hello ; world"` — две инструкции. Токены разделяются
пробелами; текст в кавычках — один токен; `;` вне кавычек разделяет
инструкции. Токены — срезы исходной строки, без аллокаций.

### 8.2. Cvars

Console variable — типизированная именованная настройка: имя, тип, значение по
умолчанию, диапазон, флаги, справка, иногда колбэк на изменение.

```c3
CVar* cv_steps = con.register_int("sim_steps", 2, 1, 8, "physics substeps");
...
for (int i = 0; i < cv_steps.i; i++) step();   // каждый кадр — без поиска по имени
```

Ключевое решение — **регистрация возвращает стабильный указатель**, и горячий код
читает поле напрямую. Поиск по строке — только при вводе команды. Поэтому cvars
хранят в массиве фиксированного размера или в пуле (глава 02): указатель на
элемент растущего `List` будет инвалидирован при реаллокации.

Флаги, встречающиеся почти везде:

* `READONLY` — только для чтения (версия, имя карты);
* `CHEAT` — меняется только при `sv_cheats 1` (защита мультиплеера в Source/Quake);
* `ARCHIVE`/`SAVE` — сохраняется в конфиг пользователя;
* `REPLICATED` — сервер рассылает значение клиентам;
* `RENDER_THREAD` — изменение применяется на границе кадра (иначе гонка с
  потоком рендера; в Unreal так устроены `r.*` переменные).

Значения валидируются: числа зажимаются в диапазон, мусор отвергается с
сообщением и *не* меняет значение. Булевы принимают `0/1/true/false/on/off`.

### 8.3. Команды, автодополнение, история

Команда — имя и обработчик `fn void(Console*, String[] args)`. Полезный набор:
`help [prefix]`, `exec file.cfg`, `bind key "command"`, `prof_dump`, `mem_report`,
`dd_<category>`, `teleport x y z`, `god`. Автодополнение по Tab — все имена с
префиксом в **отсортированном** виде (поиск по префиксу в отсортированном массиве
или trie). История — кольцевой буфер введённых строк.

Консоль — это ещё и *скриптовый интерфейс*: те же команды выполняются из
конфигов, из автотестов (`-exec smoke_test.cfg`), по сети с dev-сервера и из
бенчмарков (`timedemo`). Поэтому вывод команд должен быть детерминированным и
машиночитаемым.

Для сложного UI инструментов (иерархия сцены, инспектор свойств, графики)
движки используют **Dear ImGui** поверх тех же cvars и команд; интерфейс
инспектора свойств строится на рефлексии (глава 13).

## 9. Внешние инструменты: как с ними дружить

* **Tracy.** Клиент — заголовочная библиотека с макросами `ZoneScoped`,
  `FrameMark`, `TracyPlot`, `TracyAlloc/Free`, `TracyMessage`. Ваш профилировщик
  может быть тонким слоем, который при `-D TRACY` транслирует `@zone` в вызовы
  Tracy C API (`___tracy_emit_zone_begin`), — тогда встроенный оверлей и Tracy
  размечены одними и теми же зонами.
* **Superluminal.** Сэмплирующий, с отличным UI для Windows/консолей; принимает
  пользовательские события через PerformanceAPI, которые показываются поверх
  сэмплов.
* **RenderDoc.** Захват кадра GPU. Движку стоит: именовать ресурсы
  (`SetObjectName`), расставлять debug-маркеры проходов, поддержать
  in-application API (`StartFrameCapture/EndFrameCapture`) и консольную команду
  `r_capture`.
* **PIX** (Windows/Xbox) — и CPU-хронология, и GPU-захват; маркеры `PIXBeginEvent`.
* **Отладчики** (Visual Studio, RemedyBG, gdb/lldb): натвизы/pretty-printers для
  хендлов и строк движка, функции «напечатать сущность по id», которые можно
  вызвать из окна watch.

## 10. Подводные камни

* **Измерение искажает результат.** Слишком мелкие зоны, глобальный мьютекс в
  профилировщике, аллокации в логе — и вы оптимизируете инструмент, а не игру.
* **Debug ≠ release.** Профилировать надо оптимизированную сборку с символами
  («Development»/«Profile»). В debug-сборке узкие места другие.
* **Средние лгут.** 16 мс в среднем при одном кадре на 80 мс — это заметный
  рывок. Смотрите максимум, перцентили и хронологию худшего кадра.
* **Несбалансированные зоны** ломают всё дерево ниже — begin/end только через
  scoped-конструкцию, никаких ручных пар.
* **Висячие строки** в отложенных командах (debug draw, лог в очереди): либо
  литералы, либо копия.
* **Время в тестах.** Любой инструмент, читающий системные часы напрямую,
  нельзя протестировать детерминированно — внедряйте часы.
* **Assert с побочным эффектом** исчезает в release.
* **Отладочный код в retail.** Всё из этой главы должно уметь компилироваться в
  ноль, а cheat-команды — отсутствовать в бинарнике.
* **Утечки в инструментах.** Трекер памяти, который сам течёт или
  аллоцирует через себя (рекурсия!), — классика. Внутренние структуры трекера
  берут память напрямую у backing-аллокатора.

## Вопросы для самопроверки

1. Чем сэмплирующий профилировщик отличается от инструментирующего? Какой из них
   найдёт спайк в одном кадре из тысячи, а какой — горячий цикл внутри функции
   без разметки?
2. Почему у каждого потока свой буфер событий профилировщика? Что произойдёт с
   хронологией, если писать в общий буфер под мьютексом?
3. Что такое self и total время зоны? Как по дереву с total=30, self=0 понять,
   куда смотреть дальше?
4. Почему зона не должна копировать строку имени и что вместо этого хранят Tracy
   и Optick?
5. Как сохранить баланс стека зон, если буфер событий переполнился?
6. Зачем профилировщику внедряемые часы? Назовите два источника времени на x86 и
   их стоимость.
7. Почему среднее время кадра — плохая метрика для оценки плавности? Что
   показывать вместо него?
8. Сравните заголовок перед блоком и таблицу на стороне для трекера памяти.
   Какие баги может замаскировать заголовок?
9. Почему в `resize` трекера нужно вынимать блок из списка до вызова
   backing-аллокатора?
10. Почему логирование отфильтрованного сообщения не должно вычислять аргументы
    и как это обеспечивает макрос в C3?
11. Чем `check`, `verify` и `ensure` отличаются по поведению в release? Почему
    `static` внутри макроса даёт «ignore always» для каждого места вызова?
12. Почему текст debug draw нужно копировать, а не хранить срез? Почему при
    удалении истёкших команд важна стабильность порядка?
13. Почему cvars хранят в массиве фиксированного размера, а игра читает значение
    через указатель, полученный при регистрации?
14. Какие флаги cvar'ов вы бы ввели для мультиплеерной игры и почему изменение
    некоторых cvar'ов откладывают до границы кадра?
15. Как сделать так, чтобы все инструменты этой главы не попали в retail-сборку?
