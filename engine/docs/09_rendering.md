# Глава 09. Рендеринг: архитектура рендерера и софтверный растеризатор

> Упражнения главы: `e0901_sort_keys` … `e0906_soft_renderer`.
> Читайте главу целиком до упражнений: первые две части (архитектура) нужны для e0901–e0902,
> последняя (растеризатор) — для e0903–e0906.

Рендерер — самая большая и самая «видимая» подсистема движка. Именно в ней чаще всего
проваливаются начинающие архитекторы: первая версия обычно выглядит как обход сцены, в котором
каждый объект сам вызывает `glBindTexture`, `glUseProgram` и `glDrawElements`. Это работает
для двадцати объектов и одной камеры, а потом приходят тени (сцену надо нарисовать ещё раз из
точки зрения источника света), отражения, многопоточность, второй графический API, консоль с
другим SDK — и код, где логика сцены переплетена с вызовами API, приходится выбрасывать.

Эта глава о том, как устроены рендереры, которые переживают такие изменения, и о том, что
происходит «под капотом» GPU. Мы не будем писать код для Vulkan — для упражнений курса это
внешняя зависимость и сотни строк инициализации. Зато мы напишем свой растеризатор: с ним
понятнее, что именно делает GPU с треугольниками, и почему архитектурные решения выше по
стеку (сортировка, батчинг, порядок проходов) выглядят именно так.

## 1. Что делает GPU: конвейер за одну страницу

Прежде чем проектировать рендерер, нужно понимать, чем он управляет. Логический конвейер
растеризации (одинаковый для OpenGL, Direct3D, Vulkan, Metal) выглядит так:

```
 вершины + индексы           константы, текстуры, сэмплеры
        |                              |
        v                              v
 [Input Assembler] -> [Vertex Shader] -> [(Tess/Geometry/Mesh)] -> [Clipping]
                                                                       |
                                     perspective divide, viewport      v
 [Output Merger] <- [Depth/Stencil] <- [Pixel/Fragment Shader] <- [Rasterizer]
   blend, запись          test               цвет фрагмента       треугольник -> фрагменты
        |
        v
  render target (цвет) + depth buffer
```

* **Vertex shader** переводит каждую вершину из пространства объекта в clip space
  (умножение на матрицу model-view-projection) и вычисляет атрибуты для интерполяции.
* **Clipping** обрезает треугольники по усечённой пирамиде видимости (frustum), прежде
  всего — по ближней плоскости, иначе деление на w взорвётся.
* **Perspective divide и viewport transform**: `(x/w, y/w, z/w)` -> пиксельные координаты.
* **Rasterizer** определяет, какие пиксели (точнее, сэмплы) покрывает треугольник, и
  интерполирует атрибуты. Это фиксированная, не программируемая стадия — и именно её мы
  напишем в e0904–e0905.
* **Pixel shader** вычисляет цвет фрагмента: текстуры, освещение.
* **Depth test** и **blending** решают, попадёт ли фрагмент в буфер и как смешается с тем,
  что там уже есть.

Две вещи из этой картины определяют всю архитектуру рендерера.

Первая: **GPU — отдельный процессор, работающий асинхронно**. CPU не «рисует»; он записывает
команды в буфер, который GPU выполнит позже, часто через кадр или два. Любая синхронизация
(«дай мне прочитать результат прямо сейчас») останавливает конвейер.

Вторая: **смена состояния стоит дорого**. Каждый draw call работает в некотором состоянии:
какие шейдеры, какой формат вершин, режим смешивания, какие текстуры и константные буферы.
Смена шейдера (точнее, pipeline state object) может стоить как сотни draw call'ов с тем же
состоянием. Отсюда — сортировка, батчинг, инстансинг и вся «бухгалтерия» фронтенда.

## 2. Фронтенд и бэкенд

Почти все зрелые рендереры разделены на две половины с узким интерфейсом посередине:

```
   игровой код / сцена
          |
  +-------v--------------------------------------------------+
  | ФРОНТЕНД (что рисовать)                                  |
  |  - видимость: frustum/occlusion culling (глава 08)       |
  |  - выбор LOD, материалов, проходов (shadow, gbuffer,...) |
  |  - запись draw-команд + 64-битных ключей                 |
  +-------+--------------------------------------------------+
          |   командные буферы: [key | cmd] [key | cmd] ...
          |   сортировка по key
  +-------v--------------------------------------------------+
  | БЭКЕНД (как рисовать)                                    |
  |  - превращает команды в вызовы API                       |
  |  - отслеживает текущее состояние, выкидывает избыточное  |
  |  - управляет памятью GPU, барьерами, кадрами в полёте    |
  +-------+--------------------------------------------------+
          v
   Vulkan / D3D12 / Metal / OpenGL / консольный API
```

Что даёт такое разделение:

* **Переносимость.** Бэкенд — единственное место, которое знает API. Порт на новую платформу
  = новый бэкенд, остальной рендерер не меняется. В Unreal это слой RHI (Render Hardware
  Interface), в Godot — `RenderingDevice`, в bgfx — бэкенды под каждый API.
* **Многопоточность.** Фронтенд можно запустить в нескольких потоках: каждый пишет команды в
  свой буфер (без блокировок), потом буферы сливаются и сортируются. Бэкенд может жить в
  отдельном render thread'е, который исполняет кадр N, пока игровой поток готовит кадр N+1.
  Так устроены Unreal (game thread -> render thread -> RHI thread) и Bitsquid/Stingray.
* **Порядок независим от обхода сцены.** Фронтенд выдаёт команды в любом порядке, правильный
  порядок задаёт сортировка. Добавить новый проход (скажем, тени) — значит записать ещё
  команды с другим значением поля «проход» в ключе.
* **Отладка.** Командный буфер — это данные. Его можно сохранить, распечатать, воспроизвести,
  сравнить между кадрами.

Интерфейс между половинами должен быть **данными**, а не вызовами виртуальных функций. Плохой
дизайн: `IRenderer::draw_mesh(mesh, material, transform)`, вызываемый из обхода сцены. Он
снова привязывает порядок к обходу, а каждый вызов — косвенный переход. Хороший дизайн: плоский
массив POD-команд, который можно сортировать, копировать и отправлять между потоками.

### Где заканчивается «рендерер»

Полезно различать уровни абстракции:

| Уровень | Что знает | Примеры |
|---|---|---|
| Сцена/мир | объекты, камеры, источники света | `World`, ECS-компоненты `MeshRenderer` |
| Render views | что видит каждая «камера» (основная, тени, отражения) | `FSceneView` в Unreal |
| Фронтенд | меши, материалы, проходы, ключи | Bitsquid render package |
| RHI/бэкенд | буферы, текстуры, пайплайны, командные списки | Unreal RHI, bgfx, sokol_gfx, SDL_GPU, WebGPU |
| API | то, что даёт драйвер | Vulkan, D3D12, Metal |

Тонкий RHI («один-в-один с Vulkan, но кроссплатформенный») — популярный выбор в последние
годы: WebGPU, SDL_GPU, NVRHI, The Forge. Над ним пишется уже ваш собственный фронтенд.

## 3. Командный буфер

Командный буфер фронтенда — это кадровая (frame-scoped) структура данных. Её память выделяется
линейным аллокатором из главы 02 и сбрасывается целиком в начале кадра. Простейший формат —
массив команд фиксированного размера:

```c3
struct DrawCmd
{
    ushort shader;
    ushort material;
    ushort mesh;
    uint   instance_data;   // смещение в кадровом буфере констант
}

struct CommandBuffer
{
    DrawCmd[MAX] cmds;
    SortItem[MAX] items;    // { ulong key; uint index; }
    uint count;
}
```

Обратите внимание: сортируются не сами команды, а пары `{key, index}`. Команда может быть
большой (матрицы, параметры), а пара — 16 байт; перестановка пар дешевле, и при сортировке в
кеш попадает только то, что нужно. Бэкенд потом проходит по отсортированным парам и читает
команды по индексу — это «случайный» доступ, но последовательный по возрастанию в пределах
одного батча, если фронтенд писал похожие объекты подряд.

Более гибкий вариант (Bitsquid, «Stingray Renderer Walkthrough») — **команды переменной
длины** в байтовом буфере: заголовок с типом и размером, затем payload. Тогда в одном буфере
живут draw call'ы, dispatch'и вычислительных шейдеров, смены render target'ов, копирования.
Ключ при этом указывает на смещение команды в байтовом буфере.

Отдельные вопросы дизайна:

* **Ресурсы в командах — хендлы, не указатели.** `ushort mesh`, а не `Mesh*`. Хендлы (глава 03)
  переживают перезагрузку ассетов, проверяются на устаревание и занимают меньше места.
* **Данные для шейдера** (матрицы объекта, параметры) пишутся в отдельный большой кадровый
  буфер констант, а команда хранит смещение. Бэкенд делает один upload на кадр.
* **Двойная буферизация.** Если бэкенд работает в своём потоке, фронтенд кадра N+1 пишет во
  второй набор буферов, пока бэкенд читает первый (та же идея, что и в главе 06 про события).
* **Потоки записи.** Каждый рабочий поток пишет в свой командный буфер; в ключе есть биты,
  по которым после слияния восстанавливается детерминированный порядок.

## 4. Ключи сортировки

Классическая статья Кристера Эриксона «Order your graphics draw calls around!» (2008) и
блог Bitsquid («Rendering in Bitsquid») описывают приём, который сегодня встречается почти в
каждом движке: упаковать все критерии порядка в одно 64-битное целое так, чтобы **старшие биты
соответствовали самым важным критериям**. Тогда весь порядок кадра — это сортировка массива
`ulong`, а сравнение двух команд — одна инструкция.

Типичная раскладка:

```
 63      56 55 54           40 39                 16 15             0
 +---------+--+---------------+---------------------+---------------+
 |  layer  |T |   material    |       depth         |   sequence    |
 +---------+--+---------------+---------------------+---------------+
  проход/    полупрозрачный?   15 бит                24 бита          стабильность,
  viewport                                                           отладка
```

Почему именно так:

* **Слой (layer/pass/viewport)** — самое старшее: всё, что рисуется в shadow map, должно
  быть нарисовано до основного прохода, а UI — после мира.
* **Бит прозрачности.** Непрозрачные объекты рисуются раньше полупрозрачных: блендинг читает
  то, что уже лежит в буфере, значит под стеклом мир уже должен быть нарисован.
* **Для непрозрачных — материал, затем глубина front-to-back.** Группировка по материалу
  уменьшает смены состояния; внутри группы ближние объекты рисуются первыми, чтобы ранний
  тест глубины (early-z) отбросил фрагменты дальних, и дорогие пиксельные шейдеры не
  выполнялись зря (меньше overdraw).
* **Для полупрозрачных — только глубина back-to-front.** Корректность смешивания важнее
  смен состояния. Чтобы дальние шли первыми при сортировке по возрастанию, пишут
  инвертированную глубину: `MAX - depth`. Материал в этих битах обнуляют — иначе он «перебьёт»
  глубину.

Раскладка не универсальна: в некоторых движках материал стоит выше слоя, depth prepass
сортируется только по глубине, у декалей свой порядок. Ключ — **ваш** инструмент: поменять
порядок полей = поменять стратегию рендеринга, не трогая остальной код.

В C3 ключ удобно описывать `bitstruct`'ом: компилятор сам сгенерирует сдвиги и маски, а
перепутать поля невозможно:

```c3
bitstruct DrawKey : ulong
{
    ushort id          : 0..15;
    uint   depth       : 16..39;
    ushort material    : 40..54;
    bool   translucent : 55;
    char   layer       : 56..63;
}

DrawKey k = { .layer = 1, .material = 7, .depth = q };
ulong raw = (ulong)k;          // сортируем как число
DrawKey back = (DrawKey)raw;   // и распаковываем для отладки
```

**Квантование глубины.** Глубина — float, а в ключе 24 бита. Обычно берут view-space
расстояние и нормируют на [near, far] (или логарифмически: больше точности вблизи). Значения
вне диапазона обязательно зажимаются — переполнение поля молча испортит соседние поля, если
вы пакуете ключ вручную сдвигами (bitstruct тут чуть безопаснее, но не спасает от логической
ошибки).

**Чем сортировать.** 64-битные ключи — идеальный вход для **LSD radix sort**: 8 проходов
сортировки подсчётом по байтам, O(n) без сравнений и без ветвлений, предсказуемый доступ к
памяти. Проход, у которого все байты одинаковы (а старшие байты ключа часто одинаковы для
всего кадра), можно пропустить — это проверяется по гистограмме. На десятках тысяч команд
radix sort заметно обгоняет quicksort. Важное свойство — **устойчивость**: именно она делает
LSD-вариант корректным (каждый следующий проход сохраняет порядок, выстроенный предыдущими).
Вы напишете его в e0902.

## 5. Смены состояния и stateful-бэкенд

Бэкенд получает команды по порядку и помнит, что сейчас привязано:

```c3
if (cmd.shader != cur_shader)     { bind_pipeline(cmd.shader); cur_shader = cmd.shader;
                                    cur_material = -1; cur_mesh = -1; }
if (cmd.material != cur_material) { bind_material(cmd.material); cur_material = cmd.material; }
if (cmd.mesh != cur_mesh)         { bind_vertex_buffers(cmd.mesh); cur_mesh = cmd.mesh; }
draw(cmd);
```

Это так называемая **фильтрация избыточных состояний**. Иерархия стоимости (очень грубо,
сильно зависит от API и железа): смена render target'а > смена PSO/шейдера > смена набора
ресурсов (descriptor set, текстуры) > смена вершинного буфера > смена констант > draw.
Порядок полей ключа повторяет эту иерархию.

Дальнейшие шаги той же идеи:

* **Инстансинг.** Подряд идущие команды с одинаковыми shader/material/mesh схлопываются в один
  `draw_instanced` с массивом per-instance данных. После сортировки такие команды как раз
  стоят рядом.
* **Bindless.** В современных API (D3D12, Vulkan с descriptor indexing) все текстуры лежат в
  одном огромном массиве дескрипторов, а шейдер получает индекс. Тогда смена материала — это
  просто другое число в константах, и бэкенд почти не делает bind'ов.
* **GPU-driven rendering.** Видимость и формирование draw-команд делает сам GPU
  (compute + `DrawIndirect`/`ExecuteIndirect`). CPU отправляет всего несколько команд на
  кадр. Так работают рендереры Assassin's Creed Unity, Frostbite, Unreal Nanite. Архитектура
  «фронтенд пишет данные, бэкенд их исполняет» сохраняется — меняется только исполнитель.

## 6. Графические API: обзор

**OpenGL** (1992) — глобальная машина состояний. `glBindTexture` меняет «текущую» текстуру,
и следующий draw её использует. Драйвер делает огромную скрытую работу: валидацию, компиляцию
вариантов шейдеров под текущее состояние, отслеживание опасностей (hazards), управление
памятью. Это удобно, но непредсказуемо: «случайные» подтормаживания при первом использовании
комбинации состояний — классика. Многопоточная запись почти невозможна (контекст привязан к
потоку).

**Direct3D 11** — объектная модель (state objects вместо отдельных флагов), но драйвер всё
ещё делает много работы за вас. До сих пор хороший выбор для простых проектов под Windows.

**Vulkan, Direct3D 12, Metal** — «явные» API (explicit APIs). Ключевые понятия:

* **Pipeline State Object (PSO).** Шейдеры + формат вершин + блендинг + depth state +
  форматы render target'ов компилируются в один неизменяемый объект заранее. Смена PSO —
  дорогая операция, создание PSO — очень дорогая (компиляция шейдеров в машинный код GPU),
  поэтому движки кешируют PSO на диск и прогревают кеш.
* **Командные списки (command buffers/lists).** Записываются на CPU в любом потоке и
  отправляются в очередь (queue). Это напрямую ложится на архитектуру из разделов 2–3.
* **Барьеры и синхронизация.** Приложение само говорит GPU, что текстура перестала быть
  render target'ом и стала читаемой из шейдера (resource barrier / layout transition), и само
  синхронизирует CPU и GPU (fences) и очереди между собой (semaphores).
* **Память.** Приложение само выделяет крупные блоки видеопамяти и раскладывает в них ресурсы
  (обычно через VMA/D3D12MA).
* **Кадры в полёте (frames in flight).** CPU готовит кадр N+1 (или N+2), пока GPU рисует N.
  Все кадровые ресурсы (константные буферы, командные аллокаторы) существуют в 2–3 копиях, и
  перед повторным использованием копии CPU ждёт fence того кадра. Ошибка здесь — перезапись
  данных, которые GPU ещё читает, — один из самых коварных багов: картинка «иногда дёргается».

**Metal** проще Vulkan (меньше церемоний, автоматическое отслеживание опасностей по
умолчанию), **WebGPU** — переносимое подмножество этих идей с валидацией, удобное как
«учебный Vulkan» и как реальный кроссплатформенный RHI.

Явные API переносят сложность из драйвера в движок. Без render graph'а (раздел 8) вручную
расставлять барьеры для сотни проходов — путь к ошибкам.

## 7. Материалы и шейдеры

**Шейдер** — программа для GPU. **Материал** — шейдер плюс набор параметров (текстуры, цвета,
числа). **Экземпляр материала** (material instance) — материал с переопределёнными
параметрами: тысяча камней с разными текстурами, но одним шейдером. С точки зрения бэкенда
материал — это PSO + набор ресурсов (descriptor set) + блок констант.

Главная инженерная проблема — **взрыв перестановок** (shader permutations). Шейдер «стандартный
PBR» с опциями «есть ли normal map», «скиннинг», «туман», «тип источника света», «число
источников», «с тенями или без» даёт 2^N вариантов. Подходы:

* **Препроцессорные варианты** (`#ifdef NORMAL_MAP`) — быстрые шейдеры, но тысячи вариантов,
  долгая компиляция, раздутые PSO-кеши. Unreal шипит игры с сотнями тысяч шейдеров.
* **Ubershader** — один шейдер с динамическими ветвлениями по константам. Меньше вариантов,
  чуть медленнее; на современных GPU (когерентные ветвления) часто приемлемо.
* **Специализационные константы** (Vulkan) — компромисс: один исходник, константы
  подставляются при создании PSO.
* **Shader graph** (Unreal Material Editor, Unity Shader Graph, Godot visual shaders) —
  художник собирает узлы, движок генерирует код. Ещё больше вариантов, ещё важнее кеш.

Шейдеры пишут на HLSL (де-факто стандарт), GLSL, MSL, всё чаще на **Slang**. Кросс-компиляция:
HLSL -> DXC -> DXIL (D3D12) или SPIR-V (Vulkan) -> SPIRV-Cross -> MSL/GLSL. Компиляция —
часть оффлайн-пайплайна ассетов (глава 07): в рантайм попадает уже байткод, а лучше — ещё и
прогретый PSO-кеш.

Ещё одна важная граница — **между игровым кодом и шейдером**: раскладка констант (std140 /
HLSL packing rules, выравнивание по 16 байт) должна совпадать на CPU и GPU. Генерация структур
из рефлексии шейдера (или наоборот) убирает целый класс ошибок; в C3 тут помогают `@align` и
compile-time проверки `$assert(Foo::size == 64)`.

## 8. Render graph (FrameGraph)

Современный кадр — это десятки проходов: depth prepass, shadow maps для каждого источника,
G-buffer, SSAO, освещение, прозрачные объекты, постобработка (bloom, tonemap, TAA), UI. Между
ними — промежуточные текстуры. Если писать это «вручную», возникают проблемы:

* кто отвечает за барьеры между проходами?
* как переиспользовать память текстуры SSAO, когда она уже не нужна?
* как выключить проход (настройки графики) и не сломать соседей?
* как распараллелить запись и использовать асинхронную вычислительную очередь?

Ответ, популяризированный докладом Юрия О'Доннелла «FrameGraph: Extensible Rendering
Architecture in Frostbite» (GDC 2017), — **граф рендеринга**. Каждый кадр заново строится
граф: проходы объявляют, какие ресурсы читают и пишут; ресурсы объявляются виртуально
(«текстура 1920x1080 RGBA16F»), а не создаются.

```
  setup:    [Depth] --depth--> [GBuffer] --gbuf--> [Lighting] --hdr--> [Tonemap] --> backbuffer
                                   |                    ^
                                   +--depth--> [SSAO] --ao
  compile:  - отбросить проходы, результаты которых никто не читает
            - вычислить время жизни ресурсов -> алиасинг памяти (SSAO и bloom в одной памяти)
            - расставить барьеры/переходы layout'ов автоматически
            - (опционально) разнести проходы по очередям graphics/async compute
  execute:  вызвать лямбду каждого прохода с уже готовыми ресурсами
```

Три фазы (setup, compile, execute) — это та же идея «описание как данные, исполнение
отдельно», что и у командного буфера, только на уровень выше. Unreal использует RDG (Render
Dependency Graph), у Unity — Render Graph в SRP, у Godot 4 — граф на уровне
`RenderingDevice`. Для своего движка граф — правильная цель, как только проходов становится
больше пяти, а API — явный.

Пара слов о высокоуровневых архитектурах освещения, чтобы знать термины:

* **Forward** — каждый объект освещается всеми источниками прямо в своём пиксельном шейдере.
  Просто, работает с прозрачностью и MSAA, но плохо масштабируется по числу источников.
* **Deferred** — сначала геометрия пишет в G-buffer (альбедо, нормали, шероховатость, глубина),
  затем освещение считается в экранном пространстве по G-buffer'у. Много источников дёшево,
  но толстый G-buffer и проблемы с прозрачностью.
* **Forward+ / clustered** — экран (или пирамида видимости) делится на тайлы/кластеры,
  compute-шейдер раскладывает источники по кластерам, а forward-проход берёт только свои.
  Сегодня — популярный выбор по умолчанию (Doom 2016, многие движки).

## 9. Софтверный растеризатор

Теперь спустимся на уровень, который на GPU скрыт в железе. Софтверный растеризатор — не
только учебная игрушка: такие есть в движках для occlusion culling (Intel Masked Occlusion
Culling, растеризатор окклюдеров в Frostbite и Killzone), в эмуляторах, в WARP (D3D на CPU),
llvmpipe/lavapipe (Mesa). И это лучший способ по-настоящему понять GPU.

### 9.1. Фреймбуфер

Фреймбуфер — плоский массив пикселей, строка за строкой (row-major), `index = y * width + x`,
ось y направлена **вниз**. Отдельные буферы (планы) для цвета и глубины. Для вывода без
библиотек есть формат **PPM (P6)**: текстовый заголовок `P6\n<w> <h>\n255\n` и затем
`w*h*3` байт RGB. Для отладки в терминале — ASCII: яркость -> символ из «рампы»
`" .:-=+*#%@"`.

### 9.2. Линии: Брезенхэм

Алгоритм Брезенхэма рисует отрезок целочисленной арифметикой: идём по главной оси по
одному пикселю, по второй копим ошибку и шагаем, когда она превысила полпикселя. Компактный
вариант Алоиса Цингла обрабатывает все восемь октантов одним циклом:

```c3
int dx =  abs(x1 - x0), sx = x0 < x1 ? 1 : -1;
int dy = -abs(y1 - y0), sy = y0 < y1 ? 1 : -1;
int err = dx + dy;
while (true)
{
    plot(x0, y0);
    if (x0 == x1 && y0 == y1) break;
    int e2 = 2 * err;
    if (e2 >= dy) { err += dy; x0 += sx; }
    if (e2 <= dx) { err += dx; y0 += sy; }
}
```

Инварианты, которые стоит проверять тестами: оба конца нарисованы; пикселей ровно
`max(|dx|, |dy|) + 1`; по главной оси ровно один пиксель на координату; линия 8-связна. Линии
нужны движку для debug draw (глава 15) — хотя там их, конечно, рисует GPU.

### 9.3. Треугольники: функции рёбер

Старый подход — сканлайны: сортируем вершины по y, идём по строкам, считаем левую и правую
границы. Он быстрый на одном ядре, но полон особых случаев (плоский верх, плоский низ). GPU
используют подход Пинеды (1988) — **функции рёбер**:

```
edge(a, b, p) = (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x)
```

Это z-компонента векторного произведения `(b - a) x (p - a)`. Знак показывает сторону от
прямой ab, модуль равен удвоенной площади треугольника `(a, b, p)`. Точка внутри треугольника,
если все три значения `w0 = edge(b, c, p)`, `w1 = edge(c, a, p)`, `w2 = edge(a, b, p)` одного
знака. Алгоритм:

```
area = edge(a, b, c); если 0 — выход; если < 0 — поменять b и c
bbox = min/max вершин, обрезанный экраном
для каждого пикселя в bbox:
    p = центр пикселя (x + 0.5, y + 0.5)
    если w0 >= 0 и w1 >= 0 и w2 >= 0 — пиксель покрыт
```

Почему это хорошо для железа: каждый пиксель независим (параллельно хоть на тысяче ядер);
`edge` линейна по p, значит при шаге на пиксель вправо `w` меняется на константу — вместо
умножений получаются сложения; тест можно делать сразу для блока 8x8 по углам (иерархическая
растеризация, отбрасывание целых тайлов).

```
         a
         *\
         | \        w2 = edge(a, b, p) >= 0  (с внутренней стороны ab)
         |  \       w0 = edge(b, c, p) >= 0
     p . |   \      w1 = edge(c, a, p) >= 0
         |    \
         *-----*
         c      b
```

**Фиксированная точка.** Вершины после проекции дробные, но в float считать функции рёбер
опасно: ошибки округления дадут дыры и двойное покрытие на общих рёбрах. GPU переводят
экранные координаты в фиксированную точку (D3D: 8 бит подпикселя) и считают функции рёбер в
целых числах — точно. Мы используем 4 бита (`SUB = 16`). Произведения надо считать в 64 битах.

**Top-left rule.** Если центр пикселя лежит ровно на общем ребре двух треугольников (`w == 0`),
пиксель должен достаться ровно одному. Правило D3D/OpenGL: пиксель на ребре принадлежит
треугольнику, только если ребро «верхнее» (горизонтальное, внутренность ниже) или «левое».
Реализуется смещением: `bias = top_left ? 0 : -1` и тест `w + bias >= 0` (в целых это
то же, что `w > 0` для остальных рёбер). Для ориентации «y вниз, `edge(a, b, c) > 0`»:
верхнее ребро — `dy == 0 && dx > 0`, левое — `dy < 0`. Без этого правила полупрозрачная
сетка покажет светлые «швы» на диагоналях — двойное смешивание.

### 9.4. Z-буфер

Алгоритм художника (сортировка треугольников по глубине) не работает для взаимопроникающих и
циклически перекрывающихся треугольников. Z-буфер (Кэтмелл, 1974) решает видимость попиксельно:
для каждого пикселя хранится глубина ближайшего фрагмента; новый фрагмент записывается,
только если он ближе. Результат не зависит от порядка рисования непрозрачной геометрии — а
скорость зависит: при front-to-back большинство фрагментов отбрасывается тестом, пиксельный
шейдер не выполняется (вот откуда front-to-back в ключах раздела 4). Вы увидите это в e0905
прямо в счётчиках `written`/`rejected`.

GPU делают тест глубины до пиксельного шейдера (early-z), если шейдер не пишет глубину сам и
не делает `discard`. Хранят глубину с иерархией (Hi-Z: максимум по тайлу), чтобы отбрасывать
целые блоки. Отсюда же **depth prepass**: сначала рисуем только глубину (дёшево), потом
полный проход с тестом `EQUAL` — ноль overdraw дорогих шейдеров.

**Что именно хранить.** После перспективного деления view-space z меняется по экрану
нелинейно, а `1/z` — линейно. Поэтому интерполировать барицентриками можно `1/z` (у GPU —
`z/w`, тоже аффинную по экрану функцию). Следствие: точность z-буфера распределена
неравномерно — почти вся у ближней плоскости. Поэтому near-плоскость не делают слишком
маленькой, а современные движки используют **reversed-Z** (1 у near, 0 у far) с float-буфером:
плотность float у нуля компенсирует гиперболическое распределение.

### 9.5. Атрибуты и освещение

Веса `w0, w1, w2` из теста покрытия — это ненормированные **барицентрические координаты**:
`w0 + w1 + w2 = area`, и любой атрибут вершины интерполируется как
`(w0 * A_a + w1 * A_b + w2 * A_c) / area`. Для атрибутов в перспективе нужна
**perspective-correct interpolation**: интерполируются `A/w` и `1/w`, и в каждом пикселе
делится одно на другое; без этого текстуры «плывут» (знаменитое аффинное искажение PlayStation 1).

Простейшая модель освещения — **Ламберт**: диффузная яркость пропорциональна косинусу угла
между нормалью и направлением на свет, `I = max(0, dot(n, l))`. Где её считать:

* **flat** — одна нормаль на треугольник, одна яркость (видны грани);
* **Гуро** — освещение в вершинах, интерполяция цвета (дёшево, но блики «теряются»);
* **Фонг** — интерполируется нормаль, освещение в каждом пикселе. Это то, что делает любой
  современный пиксельный шейдер, с PBR-моделями (GGX) вместо Ламберта.

### 9.6. Вершинная стадия, отсечение, отбрасывание граней

Вершина проходит путь object -> world -> view -> clip -> NDC -> screen. В e0906 мы упрощаем:
объект поворачивается и переносится сразу в пространство камеры, затем перспективное деление
`sx = cx + x * f / z`.

**Backface culling.** У замкнутого меша задние грани всегда закрыты передними. Их
отбрасывают до растеризации по знаку экранной площади (ориентации обхода вершин): это примерно
половина треугольников. Порядок обхода — соглашение ассет-пайплайна (обычно CCW = лицевые);
его нарушение даёт «вывернутые» модели. Грани ребром (площадь 0) отбрасываются тоже.

**Клиппинг.** Треугольник, пересекающий ближнюю плоскость, нельзя просто проецировать: вершины
за камерой дают `z <= 0`. Его обрезают в clip space (Sutherland–Hodgman по плоскости
`w = near`), получая 1–2 треугольника. По остальным плоскостям GPU обычно не режут, а
используют guard band — растеризатор и так ограничен экраном (наш bounding box тоже).

## 10. Производительность и подводные камни

* **Overdraw.** Каждый пиксель, закрашенный несколько раз, — потраченный шейдер. Лечится
  front-to-back, depth prepass, occlusion culling. Полупрозрачные частицы — главный
  источник overdraw; их рисуют в пониженном разрешении.
* **Мелкие треугольники.** GPU шейдит пиксели квадами 2x2 (нужно для производных и выбора
  mip-уровня). Треугольник в один пиксель стоит четыре вызова шейдера. Отсюда LOD'ы и
  софтверная растеризация микрополигонов в Nanite.
* **Тайловые GPU** (мобильные, Apple). Экран бьётся на тайлы, геометрия сначала сортируется
  по тайлам, затем каждый тайл рисуется в быстрой on-chip памяти. Загрузка/выгрузка
  render target'ов в начале/конце прохода дорога — load/store actions в Vulkan/Metal
  существуют ради них.
* **Синхронизация CPU-GPU.** Чтение результата GPU в том же кадре (query, readback) ставит
  CPU в ожидание. Читайте с задержкой в 2–3 кадра.
* **Перезапись кадровых данных** до того, как GPU их прочитал (frames in flight) — см. раздел 6.
* **Draw call-ы как мера.** «Не больше 2000 draw call'ов» — правило эпохи D3D9/D3D11. В явных
  API и с bindless ограничение сдвигается, но сортировка и инстансинг по-прежнему окупаются.
* **Детерминизм.** Ваш рендерер не обязан давать бит-в-бит одинаковую картинку на разных GPU
  (и не будет), но тесты на софтверном растеризаторе или на снимках кадров (golden images с
  допуском) — полезная практика для регрессий.
* **Float в ключах.** Нельзя просто взять биты float'а глубины как целое для отрицательных
  значений (порядок инвертируется); квантуйте явно.
* **Обратная зависимость.** Рендерер не должен знать про игровую логику и ECS-компоненты
  напрямую — фронтенд получает от мира плоские данные (extract-фаза в Bevy, «render proxies»
  в Unreal). Это и даёт возможность рендерить кадр N, пока игра симулирует N+1.

## Вопросы для самопроверки

1. Почему интерфейс между фронтендом и бэкендом лучше делать массивом команд, а не набором
   виртуальных методов `draw_mesh(...)`? Назовите минимум три преимущества.
2. Почему для непрозрачных объектов поле материала в ключе стоит выше глубины, а для
   полупрозрачных его обнуляют? Что сломается, если этого не сделать?
3. Зачем сортировать пары `{key, index}`, а не сами команды?
4. Почему LSD radix sort обязан быть устойчивым на каждом проходе? Когда проход можно
   пропустить?
5. Что такое PSO и почему его создание стоит дорого? Как движки борются с «подтормаживанием
   при первом появлении эффекта»?
6. Какие три проблемы решает render graph? Почему он перестраивается каждый кадр?
7. Почему функции рёбер считают в фиксированной точке, а не во float? Что даст float на общих
   рёбрах сетки?
8. Сформулируйте top-left rule и объясните, зачем оно нужно, на примере двух треугольников
   квадрата с полупрозрачным материалом.
9. Почему в z-буфер пишут `1/z` (или `z/w`), а не view-space z? Что такое reversed-Z и
   зачем оно?
10. Почему результат z-буфера не зависит от порядка отрисовки непрозрачной геометрии, а
    производительность — зависит?
11. Чем Гуро отличается от Фонга? Где бы вы считали освещение для очень крупных треугольников
    пола?
12. Почему треугольник, пересекающий ближнюю плоскость, нельзя просто спроецировать?
13. Что такое frames in flight и какой баг возникает, если кольцевой буфер констант на 2 кадра,
    а GPU отстаёт на 3?
