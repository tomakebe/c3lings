## Карта главы

**О чём глава.** Как заставить игровой движок использовать *все* ядра процессора, а не одно,
и при этом не утонуть в странных багах, которые появляются «раз в час». Мы пройдём путь от
самых основ (что такое поток и почему два потока могут «потерять» прибавление к счётчику) до
устройства настоящей системы задач (job system), как в движках Naughty Dog, Unreal и Unity.

**Зачем это нужно.** Современный процессор — это 6–16 ядер. Если движок считает всё в одном
потоке, он использует 1/8–1/16 мощности машины. Многопоточность — единственный способ
уложить в 16 мс (60 кадров в секунду) анимацию, физику, ИИ и подготовку рендера для
тысяч объектов.

**Что нужно знать заранее.**

* Указатели, структуры, методы в C3 — из трека по языку.
* Примитивы `Thread`, `Mutex`, `ConditionVariable`, `Atomic` — вы их видели в треке 1
  (упражнения 096–099, 112). Если подзабыли — не страшно, в разделе «Азбука
  многопоточности» ниже всё объяснено заново, с нуля.
* Кадровый аллокатор (глава 02) и хендлы с поколениями (глава 03) упоминаются мимоходом.

## Азбука многопоточности

Этот раздел — фундамент. Здесь нет ничего специфичного для игр, только базовые понятия.
Кто уверенно знает, что такое гонка данных, мьютекс, условная переменная и порядок памяти
у атомиков, — может пролистать до раздела «Проблема». Остальным — читать обязательно.

### Ядро, поток, планировщик

**Ядро (core)** — это «исполнитель» внутри процессора: он берёт инструкции программы одну за
другой и выполняет их. В процессоре с 8 ядрами одновременно могут исполняться 8 независимых
последовательностей инструкций.

**Поток (thread)** — это одна такая последовательность инструкций внутри программы, со своим
указателем «где я сейчас» и своим стеком (местом для локальных переменных). У любой
программы есть минимум один поток — тот, что запускает `main`. Можно создать ещё.

**Планировщик ОС (scheduler)** — часть операционной системы, которая решает, какой поток на
каком ядре сейчас выполняется. Потоков в системе обычно больше, чем ядер (браузер, музыка,
сама ОС), поэтому планировщик постоянно ставит потоки на ядра и снимает их — это называется
**вытеснением (preemption)**. Вытеснить поток могут **в любой момент, между любыми двумя
инструкциями**, и на сколько угодно долго. Из этого вытекают почти все сложности главы.

> **Аналогия.** Ядра — это повара на кухне. Потоки — это рецепты, по которым кто-то готовит.
> Шеф (планировщик) решает, какой повар сейчас готовит по какому рецепту, и может в любой
> момент сказать «отложи, займись другим». Повара работают одновременно, а продукты
> (память) — общие, на одном столе.

**Самое важное:** все потоки одной программы видят **одну и ту же память**. Глобальная
переменная, массив в куче, структура, на которую у двух потоков есть указатель, — общие.
Это удобно (не нужно ничего пересылать) и опасно (два потока могут одновременно менять
одно и то же).

В C3 поток создаётся так:

```c3
import std::io, std::thread;

fn int worker(void* arg)       // функция потока: принимает void*, возвращает int
{
    int* x = arg;              // приводим «что угодно» к тому, что мы передали
    return *x * 2;             // результат вернётся из join()
}

fn void main()
{
    int input = 21;
    Thread t;
    t.create(&worker, &input)!!;   // запустить worker(&input) в новом потоке
    int result = t.join()!!;       // дождаться окончания и забрать результат
    io::printfn("%d", result);     // 42
}
```

Что происходит: `create` просит ОС завести новый поток и начать в нём выполнять `worker`.
С этого момента два потока — `main` и новый — работают *одновременно*, и мы не знаем, кто
из них продвинется дальше. `join` — это «подождать, пока поток закончит, и забрать его
`int`». После `join` поток уничтожен, а всё, что он записал в память, гарантированно видно
вызвавшему потоку.

Обратите внимание: `&input` указывает на переменную в стеке `main`. Это безопасно только
потому, что `main` дожидается потока (`join`) до выхода. Если бы `main` вернулся раньше,
поток читал бы память, которой уже нет. Мы ещё встретим это правило в `e1202`.

**Коротко:** поток — независимая последовательность инструкций; все потоки делят одну
память; ОС может приостановить любой поток в любой момент.

### Гонка данных: почему `counter++` ломается

Пусть два потока миллион раз делают `counter++` с общей переменной. Ожидаем 2 000 000.
Вот реальная программа (проверена на c3c 0.8.5):

```c3
import std::io, std::thread, std::atomic;

int plain_counter;          // обычная переменная: гонка данных
Atomic{int} atomic_counter; // атомарная: гонки нет

fn int worker(void* arg)
{
    for (int i = 0; i < 1_000_000; i++)
    {
        plain_counter++;        // read-modify-write из трёх шагов — НЕ атомарно
        atomic_counter.add(1);  // один неделимый шаг
    }
    return 0;
}

fn void main()
{
    Thread a;
    Thread b;
    a.create(&worker, null)!!;
    b.create(&worker, null)!!;
    a.join()!!;
    b.join()!!;
    io::printfn("plain:  %d", plain_counter);
    io::printfn("atomic: %d", atomic_counter.load());
}
```

Два запуска подряд на одной машине дали:

```
plain:  1999847        plain:  1999862
atomic: 2000000        atomic: 2000000
```

Обычный счётчик «потерял» полторы сотни прибавлений, и каждый раз — разное число (на
другой машине или с оптимизациями потери бывают гораздо больше). Атомарный — ровно два
миллиона. Почему?

Строчка `counter++` для процессора — это **три** шага: прочитать значение из памяти в
регистр, прибавить 1 в регистре, записать обратно. Такая операция называется
**read-modify-write** («прочитать-изменить-записать»). Между шагами поток могут вытеснить, а
второй поток на другом ядре в это время делает то же самое. Разберём по шагам, пусть
`counter = 5`:

| Шаг | Поток A | Поток B | `counter` в памяти | регистр A | регистр B |
|---|---|---|---|---|---|
| 1 | прочитать → 5 | | 5 | 5 | — |
| 2 | | прочитать → 5 | 5 | 5 | 5 |
| 3 | прибавить 1 | | 5 | 6 | 5 |
| 4 | | прибавить 1 | 5 | 6 | 6 |
| 5 | записать 6 | | **6** | 6 | 6 |
| 6 | | записать 6 | **6** | 6 | 6 |

Оба потока сделали `++`, а счётчик вырос на 1. Одно прибавление **потерялось** (это так и
называется — *lost update*). Причём так бывает не всегда, а только когда шаги потоков
«перемешались» неудачно. Порядок, в котором перемешиваются шаги разных потоков, называется
**чередованием (interleaving)**. Удачных чередований много, неудачных мало — поэтому баг
проявляется редко и непредсказуемо.

**Гонка данных (data race)** — ситуация, когда два потока одновременно обращаются к одной
ячейке памяти, хотя бы один из них пишет, и между ними нет синхронизации. В C3 (как и в C,
C++) гонка данных — это неопределённое поведение: компилятор вправе считать, что её нет, и
оптимизировать код так, что результат будет ещё страннее, чем в таблице.

> **Аналогия.** Двое ведут учёт в одной тетради. Оба смотрят на число «5», оба в уме
> прибавляют один, оба пишут «6». Каждый честно сделал свою работу, а итог неверен.

**Коротко:** даже `x++` — это несколько шагов; если два потока делают их вперемешку,
результат портится. Это гонка данных, и она проявляется случайно.

### Мьютекс: «один за раз»

Первый способ починить гонку — **взаимное исключение**. **Мьютекс (mutex, от mutual
exclusion)** — это замок: `lock()` захватывает его (если он занят — поток ждёт, пока
освободят), `unlock()` отпускает. Код между `lock` и `unlock` называется **критической
секцией**: в ней в каждый момент находится не больше одного потока.

```c3
self.mtx.lock();          // занять замок (или подождать, пока освободят)
defer self.mtx.unlock();  // гарантированно отпустить при любом выходе из функции
counter++;                // теперь три шага выполняются без вмешательства
```

Таблица из прошлого раздела с мьютексом становится такой:

| Шаг | Поток A | Поток B | `counter` |
|---|---|---|---|
| 1 | `lock()` — успех | | 5 |
| 2 | | `lock()` — занято, **ждёт** | 5 |
| 3 | прочитать 5, прибавить, записать 6 | (ждёт) | 6 |
| 4 | `unlock()` | | 6 |
| 5 | | `lock()` — успех | 6 |
| 6 | | прочитать 6, прибавить, записать 7 | **7** |
| 7 | | `unlock()` | 7 |

Мьютекс не только запрещает одновременность — он ещё гарантирует **видимость**: всё, что
поток A записал до `unlock()`, поток B обязательно увидит после своего `lock()`. Это
важная деталь, к ней мы вернёмся в разделе про порядок памяти.

Цена мьютекса: если он занят, поток ждёт. Если ожидание длинное, ОС усыпляет поток, а
усыпить и разбудить поток через ядро ОС — это 5–50 микросекунд. Для игры, у которой на кадр
16 миллисекунд, тысяча таких ожиданий — уже заметно.

> **Аналогия.** Мьютекс — ключ от единственной туалетной кабинки в кафе. Ключ один; пока
> он у кого-то, остальные стоят в очереди.

**Коротко:** мьютекс пускает в критическую секцию по одному и делает записи «до unlock»
видимыми «после lock». Пишите `lock(); defer unlock();` — так не забудете отпустить.

### Условная переменная: «разбуди меня, когда…»

Мьютекс решает «не мешать друг другу». Но часто нужно ещё **ждать события**: рабочий поток
хочет задачу, а очередь пуста. Крутиться в цикле «проверить — нет — проверить — нет» —
значит жечь ядро впустую. Нужен способ уснуть и проснуться, когда что-то изменилось.

**Условная переменная (condition variable)** — это «зал ожидания» при мьютексе. У неё три
операции:

* `cv.wait(&mtx)` — *атомарно* отпустить мьютекс и уснуть. Когда поток разбудят, он снова
  захватит мьютекс и только потом вернётся из `wait`.
* `cv.signal()` — разбудить **одного** спящего (если есть).
* `cv.broadcast()` — разбудить **всех** спящих.

Почему `wait` сам отпускает мьютекс: условие («очередь не пуста») проверяется под
мьютексом, а изменить его может только другой поток, которому мьютекс нужен. Если бы мы
уснули с захваченным мьютексом, никто не смог бы положить задачу — вечное ожидание.

Канонический шаблон (вы его будете писать в `e1201`):

```c3
self.mtx.lock();                                    // 1. захватили замок
while (!условие) self.cv.wait(&self.mtx);           // 2. пока условие ложно — спим
// 3. здесь условие истинно И мьютекс наш
... работаем с общими данными ...
self.mtx.unlock();                                  // 4. отпустили
```

И с другой стороны — тот, кто меняет условие:

```c3
self.mtx.lock();
... меняем данные так, что условие стало истинным ...
self.cv.signal();                                   // будим одного ждущего
self.mtx.unlock();
```

Почему `while`, а не `if`, — разберём на конкретной истории в разделе «Очередь задач»;
там же — почему при завершении нужен `broadcast`, а не `signal`.

> **Аналогия.** Вы в поликлинике ждёте вызова. Вместо того чтобы каждые две секунды
> заглядывать в кабинет (это и есть «крутиться»), вы садитесь в зал ожидания и дремлете.
> Медсестра выходит и зовёт «следующий!» (`signal`) или «все заходите!» (`broadcast`).
> Проснувшись, вы *всё равно* смотрите, свободен ли кабинет, — вдруг кто-то проскочил
> раньше вас.

**Коротко:** условная переменная позволяет спать до события. `wait` вызывается под
мьютексом, всегда в цикле `while`, и сам отпускает мьютекс на время сна.

### Атомики: неделимые операции

Мьютекс — тяжёлое орудие для одной переменной. Для простых случаев («прибавить к счётчику»,
«поставить флаг») процессор умеет делать операции **атомарно** — как один неделимый шаг,
который никто не может разорвать посередине. В C3 это тип `Atomic{T}` из `std::atomic`:

```c3
Atomic{int} c;
c.store(10);          // записать
int v = c.load();     // прочитать
int old = c.add(3);   // прибавить 3 и вернуть СТАРОЕ значение (10), теперь c == 13
old = c.sub(1);       // вычесть 1 и вернуть старое (13), теперь c == 12
```

Ключевое и часто забываемое: **`add` и `sub` возвращают значение, которое было ДО
операции.** Такая операция в литературе называется *fetch-and-add*: «достать старое и
прибавить». Это свойство — основа половины приёмов этой главы:

* `next_chunk.add(1)` в `parallel_for` выдаёт **каждому** потоку уникальный номер куска:
  первый получит 0, второй 1 и т. д., даже если они пришли одновременно (`e1203`).
* `pending.sub(1) == 1` означает «именно мой вызов довёл счётчик до нуля» — и это узнает
  ровно один поток из всех (`e1204`).

Почему fetch-and-add раздаёт уникальные номера — таблица с тем же сценарием, что и для
`counter++`, только теперь операция неделима:

| Шаг | Поток A | Поток B | `next` в памяти |
|---|---|---|---|
| 0 | | | 0 |
| 1 | `add(1)` → получил **0** | | 1 |
| 2 | | `add(1)` → получил **1** | 2 |

Шаги 1 и 2 могут идти в любом порядке (тогда B получит 0, а A — 1), но **никогда** не
бывает так, что оба получили одно и то же число: второй `add` всегда видит результат
первого.

Ещё одна атомарная операция — **CAS, compare-and-swap** (в C3 — `compare_exchange`):
«если сейчас там значение `expected`, запиши `desired` и верни true; иначе ничего не
меняй, верни false (и запиши в `expected` фактическое значение)». Это «условная запись»,
на ней строят lock-free структуры (Chase–Lev deque ниже).

> **Аналогия.** Атомик — это автомат с талончиками в банке: нажал кнопку — получил
> номерок. Два человека не могут получить одинаковый номерок, как бы одновременно они ни
> нажали.

**Коротко:** атомики — неделимые операции над одной переменной. `add`/`sub` возвращают
старое значение — это и есть главный инструмент.

### Порядок памяти: самое тонкое место

Этот подраздел — самый абстрактный в главе. Не страшно, если с первого раза он уложится не
полностью: в упражнениях все атомики используют безопасный режим по умолчанию. Но *понимать
идею* нужно, чтобы читать доклады и чужой код.

**Проблема.** Хочется так: поток-производитель готовит данные и ставит флаг «готово»;
поток-потребитель ждёт флаг и читает данные.

```
производитель:          потребитель:
  payload = 42;           while (!ready) {}
  ready = true;           print(payload);   // 42? не обязательно!
```

Кажется очевидным, что если потребитель увидел `ready == true`, то и `payload == 42`. Но
это **не гарантировано** с обычными переменными, потому что:

1. **Компилятор** вправе переставить две независимые записи местами (`ready = true` раньше
   `payload = 42`) — с его точки зрения в однопоточной программе это ничего не меняет.
2. **Процессор** тоже переставляет операции с памятью ради скорости: записи сначала
   ложатся в буфер записи ядра и становятся видны другим ядрам позже и не обязательно по
   порядку. На x86 переупорядочений мало, на ARM (телефоны, Apple M1/M2, Switch) — много.

Получается, другое ядро может увидеть новую `ready` и **старую** `payload`.

> **Аналогия.** Вы отправили другу два письма: первое — «посылка в ячейке 17», второе —
> «код ячейки 4242». Почта не обещает доставить письма в том порядке, в каком вы их
> отправили. Друг может получить код раньше, чем узнает, о какой ячейке речь. Чтобы этого
> не было, нужен способ сказать почте: «это письмо не доставлять раньше предыдущих».

**Решение — порядок памяти (memory ordering) у атомиков.** Каждой атомарной операции можно
указать, какие гарантии упорядочения она даёт остальным (неатомарным) операциям вокруг:

* **RELEASE** (у записи): «всё, что этот поток записал *до* меня, станет видно тому, кто
  увидит мою запись». Это как поставить печать на конверт: всё, что положили в конверт до
  печати, доедет вместе с ним.
* **ACQUIRE** (у чтения): «если я увидел значение, записанное чьей-то RELEASE-записью, то
  все мои чтения *после* меня увидят и всё, что тот поток записал до своей RELEASE». Это
  вскрытие конверта: после него вы видите всё содержимое.
* **SEQ_CONSISTENT** (последовательная согласованность) — самый строгий режим: все
  такие операции во всех потоках выстраиваются в один общий порядок, как будто потоки
  исполнялись по очереди. Это дефолт в C3 (и в C++) — безопасно, но чуть дороже.
* **RELAXED** — только атомарность, никаких гарантий порядка для остальных данных.
  Подходит для счётчиков статистики («сколько задач выполнено»), которые читают в конце
  после `join`.

Пара «RELEASE-запись → ACQUIRE-чтение того же атомика» и есть способ безопасно **передать
данные** между потоками. Проверенная программа:

```c3
import std::io, std::thread, std::atomic;

int payload;            // обычные данные
Atomic{bool} ready;     // флаг «данные готовы»

fn int producer(void* arg)
{
    payload = 42;                       // 1. пишем данные
    ready.store(true, RELEASE);         // 2. публикуем: всё, что выше, станет видно
    return 0;
}

fn int consumer(void* arg)
{
    while (!ready.load(ACQUIRE)) thread::yield(); // 3. ждём флаг
    return payload;                     // 4. гарантированно 42
}

fn void main()
{
    Thread p;
    Thread c;
    c.create(&consumer, null)!!;
    p.create(&producer, null)!!;
    p.join()!!;
    int got = c.join()!!;
    io::printfn("consumer saw %d", got);   // consumer saw 42
}
```

Разбор по строкам:

* Строка 1 — обычная запись. Сама по себе она могла бы «задержаться».
* Строка 2 — RELEASE-запись: компилятор и процессор обязаны сделать строку 1 видимой не
  позже строки 2.
* Строка 3 — ACQUIRE-чтение в цикле. `thread::yield()` — «уступи ядро другим потокам», чтобы
  не жечь его впустую.
* Строка 4 — раз мы увидели `true`, записанное RELEASE-ом, то видим и `payload = 42`.

Эту связку называют **happens-before** («случилось-до»): запись `payload` *случилась до*
чтения `payload`, потому что между ними цепочка «release → acquire». Мьютекс устроен так
же: `unlock` — это release, `lock` — acquire. Поэтому всё, что записано под мьютексом, видно
следующему, кто его захватит. И `join` тоже даёт happens-before: после `join` видно всё,
что поток сделал.

**Что нужно запомнить для этой главы:**

1. Обычные переменные между потоками передаются только через **синхронизацию**: мьютекс,
   атомик с release/acquire (или seq_cst), `join`.
2. Атомики в C3 по умолчанию `SEQ_CONSISTENT` — самый безопасный режим. Во всех
   упражнениях главы этого достаточно, и указывать порядок не нужно.
3. Ослаблять порядок (`RELAXED`, `ACQUIRE`/`RELEASE`) стоит только тогда, когда вы точно
   понимаете, какие данные вы публикуете, и профилировщик показал, что это важно.

**Коротко:** без синхронизации другие ядра могут увидеть ваши записи в другом порядке.
RELEASE-запись «запечатывает» всё, что было до неё, ACQUIRE-чтение «распечатывает». В
упражнениях хватает дефолтного `SEQ_CONSISTENT`.

### Частые ошибки (Азбука)

> * **«Это же просто `x++`, оно атомарно».** Нет: три шага, см. таблицу выше.
> * **`volatile` вместо атомика.** `volatile` запрещает компилятору выкидывать обращения, но
>   не делает операцию атомарной и не упорядочивает процессор. Для потоков — `Atomic`.
> * **Забытый `unlock`** на одном из путей выхода (ранний `return`). Пишите `defer unlock()`
>   сразу после `lock()`.
> * **Сон с захваченным мьютексом** (`sleep`, долгий IO под замком) — все остальные стоят.
> * **Чтение «обычной» переменной в цикле ожидания** (`while (!flag) {}` с `bool flag`):
>   компилятор может прочитать её один раз и крутиться вечно. Флаг между потоками — только
>   атомик.

## Проблема

Ещё в середине 2000-х игровой цикл почти всегда был однопоточным: `input → update →
render`, всё на одном ядре, иногда отдельный поток для звука и загрузки файлов. Тактовая
частота процессоров с тех пор почти не растёт, зато растёт число ядер: у PlayStation 4 и
Xbox One — по 8 слабых ядер Jaguar (из которых игре доступны 6–7), у PS5 и Xbox Series —
8 ядер Zen 2 с SMT, у типичного игрового ПК — от 6 до 16 ядер. Однопоточный движок на такой
машине использует 1/8–1/16 доступной мощности.

(*SMT, simultaneous multithreading*, у Intel — Hyper-Threading: одно физическое ядро
притворяется двумя «аппаратными потоками», которые делят его вычислительные блоки. Это
даёт прирост, но не двукратный.)

Значит, работу кадра — анимацию, физику, ИИ, отсечение, построение команд рендера,
микширование звука, распаковку ассетов — надо раскладывать по ядрам. Сделать это так,
чтобы:

* **все ядра были заняты** на протяжении всего кадра, а не только в «удобных» местах;
* **накладные расходы** на распределение работы были малы по сравнению с самой работой;
* **результат не зависел** от того, как ОС распланировала потоки (иначе — плавающие баги,
  несовместимость реплеев, рассинхрон в сетевой игре);
* **код геймплея оставался простым** — большинство программистов студии не должны думать о
  мьютексах.

Эта глава — о том, как этого добиваются. Язык и примитивы (`Thread`, `Mutex`,
`ConditionVariable`, `Atomic`) вы знаете из трека 1 (096–099, 112) и из «Азбуки» выше.
Здесь — архитектура.

**Коротко:** ядер много, частота не растёт; движок должен загрузить все ядра, дёшево,
детерминированно и так, чтобы геймплейщики не думали о потоках.

## Эволюция: от «поток на систему» к задачам

### Поток на систему (system-per-thread)

Первая попытка, которую делали почти все студии в эпоху Xbox 360/PS3:

```
core 0: [ game logic ......................... ]
core 1: [ render submit ............ ]  (ждёт)
core 2: [ physics ...... ]  (простаивает)
core 3: [ audio .. ]        (простаивает)
```

Каждой подсистеме — свой поток, между ними очереди сообщений. Просто и понятно, но
масштабируется ровно до числа подсистем, а загрузка ядер определяется самой тяжёлой
системой. Если физике нужно 3 мс, а логике 12 мс, — кадр 12 мс, а ядро физики 9 мс
простаивает. Добавили ядер — ничего не изменилось.

> **Аналогия.** Ресторан, где у каждого повара своё блюдо: один делает только супы, другой
> только салаты. В вечер, когда все заказывают суп, «салатный» повар стоит без дела, а
> нанять ещё пятерых поваров бесполезно — у них нет своих блюд.

**Коротко:** «поток на систему» прост, но не масштабируется: число потоков = число систем,
а кадр длится столько, сколько самая медленная.

### Задачи (jobs)

Современный подход: потоков столько, сколько ядер (точнее, «ядер минус что-то» — см.
ниже), и они **не принадлежат никаким подсистемам**. Работа описывается как множество
мелких независимых задач, которые любой поток может выполнить:

```
           ┌───────── очередь задач ─────────┐
submit ──► │ anim0 anim1 phys0 cull0 cull1 … │
           └───┬──────────┬──────────┬───────┘
               ▼          ▼          ▼
            worker 0   worker 1   worker 2   ...   (по одному на ядро)
```

> **Аналогия.** Теперь ресторан работает иначе: заказы вешаются на общую ленту, и любой
> свободный повар берёт следующий. Нанял ещё повара — заказы разбираются быстрее.

**Рабочий поток (worker)** — поток, который ничего не умеет, кроме как в цикле брать
задачи из очереди и выполнять их.

Задача — это не поток и не объект с виртуальными методами. В хорошей job system задача —
это пара «функция + указатель на данные», 16–32 байта, без аллокаций:

```c3
alias JobFn = fn void(void* data);  // тип: «функция, принимающая void* и ничего не возвращающая»

struct Job
{
    JobFn func;       // что сделать
    void* data;       // над чем (у каждой задачи — свой кусок данных)
    Counter* counter; // кому сообщить о завершении (см. ниже)
}
```

Выполнить задачу — значит просто вызвать `job.func(job.data)`. Функция сама знает, к
какому типу привести `void*` (например, `Particles* p = data;`).

Почему не замыкания и не `std::function`-подобное: такое создаётся тысячами за кадр, а
каждая аллокация в куче — это потенциальный глобальный lock в аллокаторе и промах кеша.
Данные задачи обычно лежат в кадровом аллокаторе (глава 02) или прямо в массиве, который
обрабатывается.

**Коротко:** задача — это «указатель на функцию + указатель на данные», крошечная запись без
аллокаций. Потоки-рабочие общие и берут любые задачи.

## Потоки против задач

**Поток** — сущность ОС: свой стек (обычно 1–8 МБ виртуальной памяти), своё место в
планировщике ядра, создание стоит десятки микросекунд, переключение — микросекунды.
**Задача** — запись в очереди; «запуск» задачи — это вызов функции по указателю, десятки
наносекунд.

Чтобы почувствовать масштаб: 1 мс = 1000 мкс = 1 000 000 нс. Если за кадр запускается
5000 задач и на каждую создавать поток (~20 мкс), то только на создание уйдёт 100 мс —
шесть кадров. А 5000 вызовов по указателю — около 0,1 мс.

Правила, которых придерживаются почти все движки:

1. **Пул рабочих потоков создаётся один раз** при старте. Никогда не создавайте поток на
   задачу.
2. **Число рабочих** ≈ числу аппаратных потоков минус те, что заняты особыми потоками
   (главный, рендер-поток, аудио, стриминг). На консолях рабочие ещё и **прибиты к
   ядрам** (affinity), чтобы ОС их не таскала.
3. **Задача не должна блокироваться на ОС**: никаких `sleep`, синхронного чтения файлов,
   долгих мьютексов. Заблокированная задача держит целый рабочий поток. Для ввода-вывода
   есть отдельные IO-потоки (глава 07).
4. **Задача должна быть достаточно крупной**: от единиц до сотен микросекунд. Задача на 50
   наносекунд тратит больше на очередь, чем на работу.

Пояснения к терминам: **пул (pool)** — заранее созданный набор чего-то (здесь — потоков),
который переиспользуется. **Affinity («привязка»)** — указание ОС запускать поток только на
определённом ядре: тогда кеш ядра остаётся «тёплым» для этого потока. **Блокироваться** —
останавливаться в ожидании чего-то внешнего (диска, сети, другого потока) так, что поток
ничего не делает.

### Кто на каком потоке в реальных движках

| Поток | Что делает | Почему отдельно |
|---|---|---|
| Главный (game thread) | цикл кадра, геймплей-скрипты, запуск графов задач | API ОС (окна, ввод) часто требуют один поток |
| Рендер-поток (Unreal: RenderThread, RHIThread) | преобразует сцену в команды GPU | драйверы старых API не любят многопоточность; конвейеризация кадра |
| Рабочие (workers) | всё, что разбито на задачи | масштабируются по числу ядер |
| Аудио-поток | микширование, жёсткий дедлайн ~5–10 мс | нельзя ждать конца кадра — будет треск |
| IO / стриминг | чтение и распаковка ассетов | блокирующие системные вызовы |

Unreal Engine: GameThread + RenderThread + RHIThread + пул TaskGraph-рабочих (+ новый
`UE::Tasks`). Unity: главный поток + рендер-поток + рабочие C# Job System. Движок Naughty
Dog (Uncharted 4, The Last of Us Remastered): **все** потоки, кроме нескольких системных,
— рабочие, а «игровой цикл» сам является задачей; об этом ниже.

**Коротко:** потоки дорогие и создаются один раз; задачи дешёвые и их тысячи. Задача не
должна спать и не должна быть слишком мелкой.

## Очередь задач

Простейшая job system (упражнение `e1201`): общая кольцевая очередь под мьютексом и
условная переменная, на которой спят рабочие.

### Кольцевой буфер с бесконечными индексами

**Кольцевой буфер (ring buffer)** — массив фиксированного размера, который используется «по
кругу»: дойдя до конца, запись продолжается с начала. Это очередь без аллокаций.

```
          head                     tail
           ▼                        ▼
ring: [ .  J3  J4  J5  J6  .  .  .  . ]     count = tail - head
```

* `head` — номер следующей задачи, которую *заберут* (голова очереди).
* `tail` — номер следующего *свободного* места, куда положат (хвост).
* Элементы живут в полуинтервале `[head, tail)`; их количество — `tail - head`.

Трюк: `head` и `tail` **никогда не сбрасываются в ноль**, они только растут. В массив
обращаемся по `index % CAP`. Проследим очередь ёмкостью `CAP = 4`:

| Действие | head | tail | count = tail − head | ring[0..3] |
|---|---|---|---|---|
| старт | 0 | 0 | 0 | `. . . .` |
| push A → ring[0 % 4] | 0 | 1 | 1 | `A . . .` |
| push B → ring[1 % 4] | 0 | 2 | 2 | `A B . .` |
| push C → ring[2 % 4] | 0 | 3 | 3 | `A B C .` |
| pop → ring[0 % 4] = A | 1 | 3 | 2 | `. B C .` |
| push D → ring[3 % 4] | 1 | 4 | 3 | `. B C D` |
| push E → ring[4 % 4] = ring[0] | 1 | 5 | 4 (полна!) | `E B C D` |
| pop → ring[1 % 4] = B | 2 | 5 | 3 | `E . C D` |

Заметьте: в последней строке `tail = 5`, а `5 % 4 = 1` — следующая запись пойдёт в ячейку
1, которую только что освободили. «Пусто» — это `count == 0`, «полно» — `count == CAP`, и
никаких особых случаев с перескоком через конец массива. (Переполнения `usz` за время жизни
программы не случится: 2^64 задач не выполнить и за тысячу лет.)

**Коротко:** `head` и `tail` только растут, ячейка — `index % CAP`, количество — `tail −
head`. Ёмкость — степень двойки, тогда `%` превращается в быстрое `&`.

### pop под мьютексом

```c3
fn bool JobQueue.pop(&self, Job* out)
{
    self.mtx.lock();                         // всё ниже — под замком
    defer self.mtx.unlock();                 // отпустим на любом return
    while (self.count() == 0 && !self.quitting) self.not_empty.wait(&self.mtx);
                                             // пусто и не завершаемся — спим
    if (self.count() == 0) return false;     // пусто и завершаемся
    *out = self.ring[self.head % QUEUE_CAP]; // забрали самую старую задачу
    self.head++;                             // сдвинули голову
    self.not_full.signal();                  // место освободилось — разбудим производителя
    return true;
}
```

Что тут происходит словами. Рабочий захватывает мьютекс. Если задач нет и пул не
завершается, он засыпает на `not_empty` (мьютекс при этом отпускается, чтобы кто-то мог
положить задачу). Проснувшись, он снова проверяет условие — цикл `while`. Выйти из цикла
можно по двум причинам: появилась задача или объявлено завершение. Если задач по-прежнему
нет, значит, причина — завершение, и `pop` возвращает `false`: «работы больше не будет,
поток может выходить». Иначе берём задачу и будим производителя, который, возможно, спит на
`not_full`, потому что очередь была полна.

`push` — зеркальный: ждёт на `not_full`, пока очередь полна, кладёт в `ring[tail % CAP]`,
сдвигает `tail`, будит одного рабочего на `not_empty`.

У очереди **две** условные переменные, потому что ждут два разных события: рабочие ждут
«стало не пусто», производитель ждёт «стало не полно». Если бы переменная была одна,
`signal` мог бы разбудить «не того» (например, другого производителя вместо рабочего).

### Почему `while`, а не `if`: история с перехватом

Детали, на которых спотыкаются:

* **`while`, а не `if`** вокруг `wait`. Условная переменная может проснуться ложно, а между
  `signal` и пробуждением задачу может забрать другой поток.

Вот конкретное чередование, где `if` ломается. Очередь пуста, рабочий W1 спит в `wait`.

| Шаг | Производитель P | Рабочий W1 | Рабочий W2 | count |
|---|---|---|---|---|
| 1 | | спит в `wait` | (выполняет прошлую задачу) | 0 |
| 2 | `lock`, кладёт J, `signal`, `unlock` | разбужен, ждёт мьютекс | | 1 |
| 3 | | (ещё ждёт мьютекс) | вернулся за новой задачей, `lock` успел первым | 1 |
| 4 | | | count == 1, ждать не надо, забрал J, `unlock` | 0 |
| 5 | | захватил мьютекс, вышел из `wait` | | 0 |
| 6 | | с `if`: **не проверяет снова**, читает `ring[head]` — мусор, `head` уходит дальше `tail` | | −1 (!) |

С `while` на шаге 6 W1 снова видит `count == 0` и спокойно засыпает. Кроме того, стандарты
потоков разрешают **ложные пробуждения (spurious wakeups)** — `wait` может вернуться вообще
без `signal`. Поэтому правило без исключений: **условие после `wait` всегда перепроверяется
в цикле**.

**Коротко:** после пробуждения мир мог измениться — перепроверяйте условие. Всегда `while`.

### Ограниченная ёмкость и backpressure

* **Ограниченная ёмкость и backpressure.** Бесконечная очередь — это бесконечная память в
  плохой день. Либо производитель ждёт (`not_full`), либо (чаще в движках) ёмкость
  подбирается с запасом и переполнение — это assert.

**Backpressure** («обратное давление») — когда потребитель не успевает, производитель
вынужден притормозить. В `e1201` ёмкость специально маленькая (16), а задач больше —
производитель регулярно будет засыпать на `not_full`. Если забыть `not_full.signal()` в
`pop`, производитель уснёт навсегда.

* **Индексы растут бесконечно**, в массив обращаемся по модулю. `count = tail - head`
  считается без особых случаев «пусто/полно». Ёмкость — степень двойки, чтобы `%`
  превращался в `&`.

### Завершение: почему `broadcast`

* **Завершение**: флаг под мьютексом + `broadcast`. С `signal` проснётся один рабочий,
  остальные будут спать вечно, и `join` зависнет.

Пошагово, три рабочих спят, очередь пуста:

| Шаг | Главный поток | W0 | W1 | W2 |
|---|---|---|---|---|
| 1 | `lock`, `quitting = true` | спит | спит | спит |
| 2 | `signal()` + `unlock` | разбужен | спит | спит |
| 3 | `join(W0)` | count == 0 и quitting → `pop` вернул false → выход | спит | спит |
| 4 | `join(W1)` — **ждёт вечно** | — | спит (его никто не разбудит) | спит |

С `broadcast` на шаге 2 проснутся все трое, каждый увидит `quitting` и выйдет. Обратите
внимание, флаг меняется **под мьютексом**: иначе рабочий мог бы проверить `quitting`
(false), затем мы поставили бы флаг и сделали `broadcast`, и только потом рабочий уснул бы
— пропустив побудку навсегда. Это называется **потерянное пробуждение (lost wakeup)**.

И ещё одна тонкость `e1201`: рабочий выходит, только если очередь **пуста И** стоит флаг.
Значит, задачи, отправленные до `shutdown`, обязательно доделываются.

### Как рабочие ждут в настоящих движках

* **Сколько ждать**: рабочие в движках часто не засыпают сразу, а несколько микросекунд
  крутятся (spin), потом `yield`, и только потом спят на ОС-примитиве: засыпание и
  пробуждение через ядро стоят 5–50 мкс — заметная доля кадра.

**Spin (кручение)** — проверять условие в цикле, не засыпая. **`yield`** — сказать ОС «я
пока не нужен, дай поработать другим», но остаться готовым к выполнению.

### Слабое место общей очереди

У общей очереди есть фундаментальный недостаток: **все потоки дерутся за один мьютекс и
одну кеш-линию**. При 4 рабочих это незаметно, при 16 и мелких задачах — очередь становится
узким местом. Ответ — work stealing (ниже).

> **Частые ошибки (очередь задач)**
> * `if` вместо `while` вокруг `wait`.
> * Забыли `not_full.signal()` в `pop` или `not_empty.signal()` в `push` — кто-то спит вечно.
> * `signal` вместо `broadcast` при завершении — `join` зависает.
> * Флаг `quitting` ставится без мьютекса — потерянное пробуждение.
> * Выход рабочего по одному лишь `quitting`, без проверки пустоты — недоделанные задачи.
> * Вызов `job.func` **под мьютексом очереди** — пока задача работает, никто не может ни
>   положить, ни взять другую. Задачу выполняют после того, как `pop` вернулся.

**Коротко:** очередь задач — кольцевой буфер + мьютекс + две условные переменные. Ждём в
`while`, будим «противоположную сторону», при завершении — `broadcast` под мьютексом.

## Счётчики вместо future

Отправить задачи — полдела. Нужно ещё **дождаться** их: отсечение нельзя начинать, пока
физика не обновила позиции. Варианты:

* **future/promise на задачу** — объект, у которого можно спросить результат. Удобно, но
  это аллокация и синхронизация на каждую задачу.
* **барьер на всю систему** — «дождаться, пока очередь опустеет». Грубо: ждём заодно и
  чужую, никак не связанную работу.
* **атомарный счётчик на пачку** — подход Naughty Dog (Christian Gyrling, GDC 2015,
  «Parallelizing the Naughty Dog Engine Using Fibers»). Он же в упражнении `e1202`.

(**Future** — «обещание результата в будущем»: объект, у которого можно спросить «готово?»
и «дай значение». **Барьер** — точка, где все ждут всех.)

> **Аналогия.** Вы раздали 10 курьерам по посылке и повесили на стену табло с числом 10.
> Каждый курьер, доставив посылку, уменьшает число на 1. Вам не нужно звонить каждому —
> достаточно смотреть на табло, пока там не станет 0.

```c3
Counter c;
js.run_jobs(&batch, &c);    // c += batch.len, затем задачи в очередь
js.wait_for_counter(&c);    // вернётся, когда все задачи пачки выполнены
```

Каждая задача несёт указатель на счётчик и после выполнения делает `counter.sub(1)`.
Один атомик на пачку из сотни задач — практически бесплатно.

### Порядок: сначала счётчик, потом очередь

Порядок операций в `run_jobs` важен: **увеличить счётчик до публикации задач**. Если
сначала положить задачу в очередь, быстрый рабочий может выполнить её и уменьшить счётчик
до того, как мы его увеличили: ожидающий увидит ноль и пойдёт дальше, а задачи ещё
выполняются. Классическая гонка «check-then-act».

Вот это чередование, если `run_jobs` (неправильно) делает «push, затем `add`» по одной
задаче, а пачка — две задачи J1, J2:

| Шаг | Главный поток | Рабочий | counter |
|---|---|---|---|
| 1 | push(J1) | | 0 |
| 2 | | взял J1, выполнил, `sub(1)` | **−1** |
| 3 | `add(1)` | | 0 |
| 4 | push(J2) | | 0 |
| 5 | `wait_for_counter`: counter == 0 → **ушёл** | взял J2, выполняет… | 0 |
| 6 | читает результат J2 — **ещё не готов** | | |

Ещё хуже вариант «положить всю пачку, потом `add(len)`»: между ними счётчик может пройти
через отрицательные значения и случайно оказаться нулём в момент проверки.

Правильно: **один `add(jobs.len)` до первого push**. Тогда счётчик никогда не бывает
меньше числа ещё не завершённых задач. В `e1202` есть и полезная страховка: `sub()`
возвращает старое значение, и оно обязано быть `> 0` — если это не так, кто-то уменьшил
счётчик лишний раз.

**Коротко:** сначала «повесить табло» с полным числом, потом раздавать посылки.

### Ожидание внутри задачи и deadlock

Самое интересное начинается, когда задача сама порождает подзадачи и ждёт их
(рекурсивные алгоритмы, иерархии, «обнови всех детей узла»). Наивное ожидание —
`while (c != 0) yield();` — держит рабочий поток. Если все рабочие так ждут, а дети лежат в
очереди, их некому выполнить:

```
worker 0: [ A: wait(A1, A2) ........ ∞ ]
worker 1: [ B: wait(B1, B2) ........ ∞ ]
queue:    A1 A2 B1 B2                       ← никто не возьмёт
```

**Взаимная блокировка (deadlock)** — ситуация, когда потоки ждут друг друга по кругу и никто
никогда не продвинется. Здесь круг такой: рабочий 0 ждёт A1, A1 ждёт свободного рабочего,
свободный рабочий — это рабочий 0 (или 1), а он ждёт…

> **Аналогия.** Два повара, каждый ждёт, пока кто-нибудь нарежет ему лук. Лук лежит на
> общей ленте заказов, но резать его некому: оба повара стоят и ждут.

Решения:

1. **Помощь при ожидании (help while waiting)**: пока счётчик не обнулился, ожидающий сам
   достаёт и выполняет задачи из очереди. Это делаете вы в `e1202`. Минусы: стек растёт
   (задача внутри задачи внутри задачи…), и ожидающий может «залипнуть» в долгой чужой
   задаче, когда его собственные дети уже давно готовы, — латентность непредсказуема.

Как это выглядит пошагово. Два рабочих W0, W1; задача A порождает A1, A2 и ждёт их; задача
B порождает B1, B2 и ждёт их.

| Шаг | W0 | W1 | очередь | c(A) | c(B) |
|---|---|---|---|---|---|
| 1 | выполняет A, `run_jobs(A1, A2)` | выполняет B | A1 A2 | 2 | — |
| 2 | `wait(A)`: c≠0 → берёт A1 из очереди | `run_jobs(B1, B2)` | A2 B1 B2 | 2 | 2 |
| 3 | выполнил A1 → c(A): 2→1 | `wait(B)`: c≠0 → берёт A2 | B1 B2 | 1 | 2 |
| 4 | `wait(A)`: c≠0 → берёт B1 | выполнил A2 → c(A): 1→0 | B2 | 0 | 2 |
| 5 | выполнил B1 → c(B): 2→1; снова проверяет c(A) == 0 → A завершается | `wait(B)`: c≠0 → берёт B2 | — | 0 | 1 |
| 6 | свободен, берёт следующую работу | выполнил B2 → c(B): 1→0 → B завершается | — | 0 | 0 |

(Какую именно задачу кто возьмёт, зависит от планировщика — это лишь одно из возможных
чередований. Важно другое: ни на одном шаге никто не стоит без дела, пока в очереди есть
работа, поэтому deadlock невозможен.)

Обратите внимание на шаг 3: W1, ожидая *свои* задачи B1/B2, выполняет *чужую* A2. Это
нормально — главное, чтобы кто-то двигал работу вперёд. А на шаге 4–5 видно и минус
подхода: дети A уже готовы, но W0 «застрял» в чужой B1 и продолжит A только после неё.

Стек W0 на шаге 4 выглядит так:
`worker_main → execute(A) → wait_for_counter → execute(B1)` — задача внутри задачи.

2. **Файберы (fibers)** — решение Naughty Dog. Файбер — это лёгкий контекст исполнения со
   своим стеком, переключаемый вручную (в пространстве пользователя, ~сотни наносекунд).
   Каждая задача выполняется на файбере. `wait_for_counter` не блокирует поток: текущий
   файбер кладётся в список ожидающих этот счётчик, а поток берёт новый файбер из пула и
   продолжает выполнять задачи. Когда счётчик достигает нуля, ожидавший файбер снова
   становится готовым и будет продолжен **любым** потоком.

```
thread 1:  [fiber A: ...wait(c)] → switch → [fiber B: job ...] → [fiber A resumes ...]
                       │ park A on counter c                       ▲ c == 0
```

> **Аналогия для файбера.** Поток — это повар, файбер — это «рабочее место с недоделанным
> блюдом». Повар может отойти от недоделанного блюда (оно остаётся на своём месте со всеми
> ингредиентами — это стек файбера), подойти к другому месту и готовить там. Когда
> недостающий ингредиент привезут, к первому месту может подойти *любой* свободный повар и
> продолжить с того же шага.

«В пространстве пользователя» значит: переключение делает сама программа (сохранила
регистры, сменила указатель стека), без обращения к ОС. Поэтому оно в десятки раз дешевле
переключения потоков.

В докладе Гиллинга: 6 рабочих потоков прибиты к 6 ядрам, 160 файберов (128 с малым стеком
64 КБ и 32 с большим 512 КБ), три очереди задач с приоритетами, весь движок, включая
игровую логику и рендер, — задачи. Цена: нельзя держать мьютекс ОС через `wait` (файбер
может проснуться на другом потоке, а мьютекс принадлежит потоку), thread-local storage
перестаёт работать как ожидалось, отладчики и профилировщики должны понимать файберы.
Вместо мьютексов ОС — спинлоки уровня задач.

(**Thread-local storage (TLS)** — переменные, у которых у каждого потока своя копия. Если
файбер начал работу на потоке 1, а продолжил на потоке 3, «его» TLS-переменная внезапно
другая. **Спинлок** — замок, который ждёт кручением, а не засыпанием; он не привязан к
потоку ОС.)

3. **Продолжения (continuations)** — не ждать вовсе: «когда эти задачи закончатся,
   запусти вот эту». Это уже граф задач (ниже) — так устроены `TaskFlow`, Unreal
   TaskGraph и Unity Job System (`JobHandle` зависимости).

| Способ | Как ждёт | Цена |
|---|---|---|
| Помощь при ожидании | выполняет чужие задачи в своём стеке | растущий стек, непредсказуемая задержка |
| Файберы | паркует файбер, поток берёт другую работу | сложная реализация, нет мьютексов ОС и TLS |
| Продолжения / граф | не ждёт вовсе, «следующее» запускается само | код надо разрезать на куски «до» и «после» |

> **Частые ошибки (счётчики)**
> * `add` после `push` — ожидающий уходит раньше времени.
> * Задача не уменьшает счётчик, если `counter == null` проверено неверно, — вечное
>   ожидание; или уменьшает дважды — счётчик уходит в минус.
> * Ожидание через `while (c != 0) yield();` без помощи — deadlock при вложенности.
> * Блокирующий `wait_pop` вместо неблокирующего `try_pop` внутри ожидания: если очередь
>   пуста, ожидающий уснёт и не заметит, что его счётчик обнулился.

**Коротко:** один атомарный счётчик на пачку задач; увеличивается до публикации,
уменьшается каждой задачей. Ждать внутри задачи можно только «с помощью», файберами или
продолжениями — иначе deadlock.

## parallel_for: гранулярность и редукции

Подавляющая часть параллельной работы в движке — «одно и то же для N элементов»: обновить
частицы, отсечь объекты, посчитать матрицы костей. Это `parallel_for` (упражнение `e1203`).

**Гранулярность** — насколько мелко нарезана работа. **Редукция (reduction)** — свёртка
многих значений в одно: сумма, минимум, «объединение всех ограничивающих коробок».

### Статическое и динамическое разбиение

* **Статическое**: N элементов делим на T равных частей по числу потоков. Просто, но если
  элементы неравноценны (у одних персонажей 200 костей, у других 20) или один поток
  вытеснен ОС, все ждут самого медленного.
* **Динамическое**: режем на куски (chunks) фиксированного размера, потоки забирают
  следующий кусок через один атомарный счётчик:

```c3
while (true)
{
    usz chunk = pf.next_chunk.add(1);         // fetch-add: вернёт старое значение
    usz begin = chunk * pf.chunk_size;        // первый элемент куска
    if (begin >= pf.count) break;             // кусков больше нет — выходим
    usz end = min(begin + pf.chunk_size, pf.count); // последний кусок может быть короче
    pf.body(begin, end, chunk, pf.ctx);       // обработать [begin, end)
}
```

Каждый поток крутит этот цикл. `add(1)` выдаёт ему уникальный номер куска (см. «Атомики» в
Азбуке). Если номер «за краем» — работа кончилась.

> **Аналогия.** Статическое разбиение — каждому грузчику заранее выдали по 25 коробок.
> Если один заболел, его коробки стоят. Динамическое — коробки лежат стопкой, каждый берёт
> следующую, когда освободился. Сильный грузчик просто унесёт больше.

Проследим `count = 10`, `chunk_size = 3`, два потока A и B. Кусков `⌈10/3⌉ = 4`: `[0,3)`,
`[3,6)`, `[6,9)`, `[9,10)`.

| Шаг | Кто | `add(1)` вернул | begin | end | next_chunk после |
|---|---|---|---|---|---|
| 1 | A | 0 | 0 | 3 | 1 |
| 2 | B | 1 | 3 | 6 | 2 |
| 3 | B (быстрее) | 2 | 6 | 9 | 3 |
| 4 | A | 3 | 9 | **10** (обрезан) | 4 |
| 5 | B | 4 | 12 ≥ 10 → выход | — | 5 |
| 6 | A | 5 | 15 ≥ 10 → выход | — | 6 |

Каждый кусок обработан ровно один раз, хотя потоки ни разу не договаривались явно.
Счётчик в конце «перелетает» за число кусков — это нормально, каждый поток один раз
промахивается и выходит.

Быстрые потоки сами берут больше кусков. Вызывающий поток тоже участвует в работе, а не
просто ждёт — иначе ядро простаивает.

**Коротко:** куски раздаются через `next_chunk.add(1)`; кто быстрее — тот больше
обработает; последний кусок обрезается по `count`.

### Размер куска

```
слишком мелко:  |.|.|.|.|.|.|.|.|.|.|.|.|.|  — каждый кусок = атомик + промах кеша + вызов
слишком крупно: |    A    |    B    |  C  |  — «хвост»: в конце работает один поток
в самый раз:    |  |  |  |  |  |  |  |  |  — 4–16 кусков на поток, кусок ≥ ~10–50 мкс
```

**Хвост (tail)** — конец параллельной работы, когда большинство потоков уже закончили, а
один ещё доделывает свой большой кусок. Временная шкала для 3 потоков и 3 больших кусков,
один из которых тяжелее:

```
время ──────────────────────────────►
поток 0: [ кусок A ......... ]
поток 1: [ кусок B ..... ]   простой
поток 2: [ кусок C ......................... ]   ← все ждут его
```

С мелкими кусками освободившиеся потоки 0 и 1 разобрали бы остаток работы.

Хорошая эвристика: кусок кратен размеру кеш-линии в элементах (чтобы два потока не писали
в одну линию на границе кусков) и при этом на поток приходится несколько кусков для
балансировки. Unity Job System называет это `innerloopBatchCount` и перекладывает выбор на
программиста; многие движки подбирают по профилю.

**Коротко:** мелкие куски — дорогие накладные расходы, крупные — «хвост». Берите 4–16
кусков на поток и не меньше нескольких десятков микросекунд работы на кусок.

### Детерминированные редукции

Сумма, минимум, объединение AABB, подсчёт видимых объектов — это редукции. Наивно:

```c3
// ПЛОХО: гонка за кеш-линию И недетерминированный результат для float
atomic_float_add(&total, local_sum);
```

Сложение float неассоциативно: `(a + b) + c` и `a + (b + c)` отличаются в последних битах.
Если частичные суммы складываются в порядке завершения потоков, результат меняется от
запуска к запуску. Для физики, реплеев, lockstep-сети (глава 18) и даже для
воспроизводимости багов это неприемлемо.

**Ассоциативность** — свойство «неважно, как расставить скобки». Для целых чисел оно есть,
для чисел с плавающей точкой — нет, потому что после каждой операции результат
округляется до ближайшего представимого float. Нагляднее всего на крайнем примере
(проверено в C3):

```c3
float a = 100000000.0f; // 1e8
float b = -100000000.0f;
float c = 1.0f;
float left = (a + b) + c;   // (1e8 - 1e8) + 1 = 0 + 1 = 1.0
float right = a + (b + c);  // -1e8 + 1 округляется обратно до -1e8 → 1e8 - 1e8 = 0.0
```

Программа печатает `1.0` и `0.0`. У float около 7 значащих десятичных цифр, и «единица» на
фоне ста миллионов просто теряется при округлении. В реальных суммах разница обычно в
последнем бите, но для детерминизма важен *любой* бит.

Решение — **каждый кусок пишет в свой слот, свёртка — после ожидания, в фиксированном
порядке**:

```
chunk:    0      1      2      3
partial: [s0]   [s1]   [s2]   [s3]       ← пишут разные потоки, в разные слоты
total = ((s0 + s1) + s2) + s3            ← один поток, всегда в этом порядке
```

Почему это детерминированно, по шагам:

| Что | От чего зависит | От чего НЕ зависит |
|---|---|---|
| Какие элементы в куске k | `chunk_size` | числа потоков, планировщика |
| `partial[k]` (сумма внутри куска, слева направо) | элементов куска | того, *какой* поток его считал |
| Итог `((s0 + s1) + s2) + s3` | всех `partial` и фиксированного порядка | того, кто закончил первым |

Разные потоки пишут в *разные* ячейки `partial` — гонки нет. Свёртку делает один поток
*после* того, как все закончили (после `join`), — поэтому он видит все записи.

Результат зависит от размера куска, но **не** от числа потоков и планировщика. В `e1203`
это проверяется побитово для 1, 2, 4 и 7 потоков. Обратите внимание: размер куска
становится частью «спецификации» симуляции — если он зависит от числа ядер машины,
детерминизм между машинами потерян.

> **Частые ошибки (parallel_for)**
> * Забыли, что `add` возвращает **старое** значение, и прибавили 1 сами — первый кусок
>   пропущен.
> * `end = begin + chunk_size` без `min(…, count)` — выход за границы массива на последнем
>   куске.
> * Слоты `partial` по номеру **потока**, а не куска — результат зависит от того, сколько
>   кусков взял каждый поток.
> * Свёртка в порядке завершения, а не по индексам.
> * Выделили `partial`, но забыли освободить (`defer free(...)`).
> * Вызывающий поток только ждёт, вместо того чтобы тоже обрабатывать куски.

**Коротко:** float-сумма зависит от порядка сложения. Каждый кусок — в свой слот, потом один
поток складывает слоты по порядку индексов.

## Зависимости и графы задач

Кадр — это граф: анимация → скиннинг → отсечение → рендер; ИИ → физика → отсечение;
аудио — параллельно со всем.

```
        input
       /  |  \
    anim  ai  audio
      |    \      \
    skin  physics  \
       \   /        \
       cull          |
         \          /
          render ──┘
```

Термины. **Граф** — набор узлов (здесь — задач) и стрелок между ними. Стрелка `A → B`
читается «B зависит от A», то есть B нельзя начинать, пока A не закончилась. **Зависимости
(deps)** задачи — те, от кого она зависит (входящие стрелки). **Последователи
(successors)** — те, кто зависит от неё (исходящие стрелки). **Цикл** — замкнутая цепочка
`A → B → C → A`: такие задачи ждут друг друга вечно, исполнить граф невозможно. Граф без
циклов называют **DAG** (directed acyclic graph, направленный ациклический граф).

> **Аналогия.** Рецепт обеда: «сварить макароны» и «сделать соус» можно одновременно, а
> «смешать» — только когда готово и то, и другое. Граф задач — это рецепт, записанный так,
> чтобы на кухне с несколькими поварами было видно, что можно делать параллельно.

Если записывать это кодом через `wait_for_counter`, легко получить лишние ожидания
(«дождались всей физики, хотя отсечению нужна только её первая половина»). Граф задач
делает зависимости данными (упражнение `e1204`):

1. **Компиляция графа** (один раз или при изменении): для каждой задачи строим список
   последователей (обратные рёбра) и проверяем отсутствие циклов алгоритмом Кана. Побочный
   продукт — топологический порядок: он нужен для однопоточного режима отладки и для
   визуализации.
2. **Запуск**: у каждой задачи атомарный `pending = число зависимостей`. Задачи с нулём —
   в очередь.
3. **Завершение задачи**: для каждого последователя `if (pending.sub(1) == 1) push(s)`.
   Ровно один поток — тот, кто довёл счётчик до нуля, — публикует последователя. Никаких
   глобальных блокировок графа.

Разберём каждый шаг подробно.

### Шаг 1а: обратные рёбра

Когда задачи добавляются, у каждой записано, *от кого* она зависит (`deps`). А во время
исполнения нужно обратное: задача закончилась — *кого* теперь, возможно, можно запускать?
Поэтому один раз проходим по всем задачам и для каждой зависимости `d` задачи `i`
дописываем `i` в список последователей `d`.

Пример на маленьком графе «загрузка уровня» (не путать с графом из упражнения):

| индекс | задача | deps | → successors (строим) |
|---|---|---|---|
| 0 | fetch | — | decode |
| 1 | decode | fetch | build |
| 2 | sound | — | mix |
| 3 | mix | sound | show |
| 4 | build | decode | show |
| 5 | show | build, mix | — |

### Шаг 1б: алгоритм Кана — топологический порядок и поиск циклов

**Топологический порядок** — такая последовательность всех задач, в которой каждая стоит
*после* всех своих зависимостей. Если выполнять задачи по нему в одном потоке, всё будет
корректно. **Входящая степень (indegree)** — число ещё не выполненных зависимостей задачи.

**Алгоритм Кана** (Kahn, 1962) — словами: «выписывай любую задачу, у которой не осталось
невыписанных зависимостей; выписав, вычеркни её из зависимостей последователей; повторяй».
Чтобы порядок был детерминированным, среди готовых берём задачу с **наименьшим индексом**.

Трассировка на графе загрузки уровня. Начальные indegree: fetch 0, decode 1, sound 0,
mix 1, build 1, show 2.

| Шаг | Готовы (indegree 0, не выписаны) | Берём | Уменьшаем indegree | order |
|---|---|---|---|---|
| 1 | fetch(0), sound(2) | fetch | decode: 1→0 | fetch |
| 2 | decode(1), sound(2) | decode | build: 1→0 | fetch decode |
| 3 | sound(2), build(4) | sound | mix: 1→0 | … sound |
| 4 | mix(3), build(4) | mix | show: 2→1 | … mix |
| 5 | build(4) | build | show: 1→0 | … build |
| 6 | show(5) | show | — | fetch decode sound mix build show |

Шесть шагов — шесть задач, всё выписано: циклов нет.

А если цикл есть? Пусть `a` зависит от `c`, `b` от `a`, `c` от `b`. Начальные indegree
1, 1, 1 — на первом же шаге нет ни одной задачи с нулём. Алгоритм «застрял» до того, как
выписал все задачи, — это и есть признак цикла. Общее правило: **если на каком-то шаге
нет готовой задачи, а выписаны не все — граф содержит цикл**.

**Коротко:** обратные рёбра говорят «кого будить после меня»; алгоритм Кана выписывает
задачи без невыполненных зависимостей и заодно ловит циклы.

### Шаги 2–3: запуск и «кто довёл до нуля, тот и публикует»

Во время исполнения у каждой задачи свой атомик `pending`, в начале равный числу её
зависимостей. Задачи с `pending == 0` сразу кладутся в очередь готовых. Каждый рабочий:
берёт готовую задачу, выполняет, а потом для каждого последователя делает `sub(1)`.

```
pending(cull) = 2
skin    done ── sub(1) → вернул 2 → ничего
physics done ── sub(1) → вернул 1 → push(cull)
```

Помним из «Азбуки»: `sub` возвращает **старое** значение. «Вернул 1» значит «было 1, стало
0» — этот поток сделал последнее уменьшение.

Почему это корректно даже когда skin и physics заканчиваются *одновременно* на разных
потоках:

| Шаг | Поток X (закончил skin) | Поток Y (закончил physics) | pending(cull) |
|---|---|---|---|
| 0 | | | 2 |
| 1 | `sub(1)` → вернул 2 | | 1 |
| 2 | 2 ≠ 1 → ничего не делает | `sub(1)` → вернул 1 | 0 |
| 3 | | 1 == 1 → `push(cull)` | 0 |

Если шаги 1 и 2 поменять местами, push сделает X, а не Y. Но **ровно один** из них всегда
получит 1 — потому что `sub` атомарен и два потока не могут получить одно и то же старое
значение. Никто не может запустить `cull` дважды или не запустить вовсе. Для этого не нужен
мьютекс на весь граф.

Видимость данных: задача `cull` читает результаты `skin` и `physics`, записанные другими
потоками. Корректность обеспечивает цепочка «запись результата → атомарный `sub`
(release) → атомарный `sub` другим потоком (acquire) → push/pop через мьютекс очереди».
Атомики в C3 по умолчанию `SEQ_CONSISTENT`, что сильнее необходимого — безопасно, хотя
и чуть дороже.

(Перечитайте подраздел «Порядок памяти» в Азбуке: здесь ровно та же история с
`payload`/`ready`, только «флаг» — это счётчик `pending`.)

> **Частые ошибки (граф задач)**
> * Проверка `sub(1) == 0` вместо `== 1` — забыли, что возвращается старое значение;
>   последователь не запустится никогда.
> * Отдельные `sub(1)` и `load() == 0` — между ними другой поток тоже может увидеть 0, и
>   задачу запустят дважды. Решение должно приниматься по результату *той же*
>   атомарной операции.
> * Не обнулили `succ_count` перед построением обратных рёбер — при повторной компиляции
>   последователи дублируются.
> * В алгоритме Кана берут «любую» готовую задачу — порядок недетерминирован.
> * Выписали задачу, но не пометили как выписанную — она будет выбрана снова.

### Frame graph и render graph

Тот же принцип в рендере называется **frame graph / render graph** (Frostbite, Yuriy
O'Donnell, GDC 2017): проходы рендера объявляют, какие ресурсы читают и пишут, а система
строит граф, выбрасывает неиспользуемые проходы, вычисляет время жизни временных текстур
(алиасинг памяти) и расставляет барьеры GPU. Граф задач на CPU и граф проходов на GPU
часто строятся одним механизмом.

(**Проход рендера (pass)** — один этап рисования кадра, например «тени» или «размытие».
**Алиасинг памяти** — две временные текстуры, которые никогда не нужны одновременно,
занимают одну и ту же память.)

### Статический и динамический граф

* **Статический** (собран заранее, исполняется каждый кадр): дёшево запускать, легко
  визуализировать и профилировать, легко проверить на циклы. Bevy ECS строит такой граф
  систем автоматически из того, какие компоненты каждая система читает и пишет (глава 05).
* **Динамический** (задачи порождают задачи по ходу): гибко, но сложнее отлаживать и
  предсказывать.

Большинство движков комбинируют: статический каркас кадра, внутри узлов — динамические
`parallel_for`.

**Коротко:** граф задач — зависимости как данные. Компилируем один раз (последователи +
порядок Кана), исполняем с атомарным `pending` у каждой задачи; запускает последователя
тот, чей `sub` вернул 1.

## Work stealing

Общая очередь — точка конкуренции. Планировщики TBB, Cilk, Rust `rayon`, Go runtime и
многие движки дают **каждому рабочему свою двустороннюю очередь** (упражнение `e1205`):

**Двусторонняя очередь (deque, «дек»)** — очередь, в которую можно класть и из которой
можно брать с обоих концов. **Кража работы (work stealing)** — поток, у которого кончились
свои задачи, забирает задачу из чужой очереди.

> **Аналогия.** У каждого повара своя стопка заказов на его столе. Новые заказы, которые он
> сам себе создаёт («нарезать лук для этого блюда»), он кладёт сверху своей стопки и сам же
> оттуда берёт. Если стопка опустела, повар идёт к соседу и тихо забирает заказ *снизу* его
> стопки — самый старый. Сосед этого почти не замечает: он работает с другим краем.

```
      top  ← воры забирают отсюда (FIFO — самые старые задачи)
       ▼
     [ t0  t1  t2  t3  t4 ]
                        ▲
                        bottom ← владелец кладёт и снимает (LIFO)
```

* **Владелец работает со своим концом в режиме LIFO**: только что порождённая подзадача
  трогает те же данные, что и родитель, — они ещё в кеше этого ядра.
* **Вор берёт с противоположного конца (FIFO)**: там самые старые задачи, обычно —
  крупные куски работы, которые ещё будут дробиться. Украсть одну такую — значит
  обеспечить себя работой надолго, и кражи остаются редкими.
* Владелец и воры трогают разные концы, поэтому почти не конфликтуют.
* Выбор жертвы: случайный или по кругу. Случайный — стандарт (теоретические гарантии
  Blumofe–Leiserson), по кругу — детерминированнее для отладки.

(**LIFO** — last in, first out, «последним пришёл — первым ушёл», как стопка тарелок.
**FIFO** — first in, first out, обычная очередь в магазине.)

### Как меняется дек: пошагово

Индексы те же, что у кольцевого буфера: элементы живут в `[top, bottom)`, `top` и
`bottom` только растут, ячейка — `index % CAP`.

| Действие | top | bottom | содержимое | вернули |
|---|---|---|---|---|
| старт | 0 | 0 | — | |
| владелец push t0 | 0 | 1 | t0 | |
| владелец push t1 | 0 | 2 | t0 t1 | |
| владелец push t2 | 0 | 3 | t0 t1 t2 | |
| владелец pop_bottom | 0 | 2 | t0 t1 | **t2** (самая новая) |
| вор steal_top | 1 | 2 | t1 | **t0** (самая старая) |
| владелец pop_bottom | 1 | 1 | — | **t1** |
| вор steal_top | 1 | 1 | — | пусто: top == bottom → false |

Обратите внимание на асимметрию: `pop_bottom` сначала **уменьшает** `bottom` и берёт
элемент по новому значению (ведь `bottom` указывает *за* последний элемент), а `steal_top`
берёт элемент по текущему `top` и потом **увеличивает** его.

### Временная шкала: как работа расползается по потокам

В `e1205` вся работа сначала лежит у рабочего 0: корневые задачи, каждая из которых
порождает много дочерних в *свою* очередь. Примерно так это выглядит во времени (R —
корневая задача, c — дочерние; 3 рабочих):

```
время ──────────────────────────────────────────────────────►
W0: [R0 → +c c c][c][c][c][c] ...                  ← берёт своё снизу (LIFO)
W1:   пусто → steal R1 from W0 ─[R1 → +c c c][c][c] ...   ← украл старое сверху
W2:   пусто → steal R2 from W0 ─[R2 → +c c c][c][c] ...
                    ▲
          после первой кражи каждый вор сам порождает себе работу
          и дальше обращается к W0 редко
```

Именно в этом сила FIFO-кражи: вор забирает **крупную** корневую задачу, которая потом
сама наполнит его дек, — и дальше ему воровать не нужно.

### Цикл рабочего

Псевдокод цикла каждого рабочего (словами, без деталей упражнения):

```
пока есть невыполненная работа:
    если смог снять задачу со своего дека снизу → выполнить
    иначе если смог украсть у кого-то сверху     → выполнить (и посчитать кражу)
    иначе                                        → yield, попробовать снова
```

Обход жертв «по кругу, начиная с соседа» (`(id + 1) % N`, `(id + 2) % N`, …) — себя
пропускаем — даёт каждому вору свою начальную жертву, и воры не толпятся у одного дека.

**Коротко:** у каждого рабочего свой дек; своё берём снизу (свежее, тёплый кеш), чужое
крадём сверху (старое, крупное). Кражи редки, конфликты ещё реже.

### Chase–Lev deque

Lock-free реализация (Chase & Lev, 2005; корректная версия с моделью памяти C11 — Lê et al.,
2013). Идея: владелец меняет только `bottom`, воры — только `top` через CAS. Конфликт
возможен лишь за последний элемент:

**Lock-free** — структура данных без мьютексов: потоки синхронизируются только атомиками,
и вытеснение одного потока не может остановить остальных.

```c3
// Набросок, НЕ готовый к продакшену (нужны правильные барьеры памяти)
fn bool Deque.pop_bottom(&self, Job* out)
{
    long b = self.bottom.load() - 1;   // «забронировали» последний элемент
    self.bottom.store(b);
    // здесь нужен полный барьер: store bottom должен стать видимым до load top
    long t = self.top.load();          // сколько осталось с точки зрения воров
    if (t > b) { self.bottom.store(b + 1); return false; }  // было пусто
    *out = self.buf[b & MASK];
    if (t != b) return true;                                // элементов > 1, вор не мешает
    // последний элемент: соревнуемся с ворами за него
    bool won = self.top.compare_exchange(&t, t + 1);
    self.bottom.store(b + 1);
    return won;
}
```

Как читать этот набросок. Владелец сначала *объявляет* всем, что забирает нижний элемент
(уменьшил `bottom`), и только потом смотрит на `top`. Если между `top` и `b` больше одного
элемента, вор до нашего элемента не дотянется — забираем спокойно. Если остался ровно один
(`t == b`), то за него могут одновременно бороться и владелец, и вор; спор решает CAS на
`top`: кто первым сдвинул `top` с `t` на `t + 1`, тот и забрал. Проигравший получает
`false`.

Это одна из самых тонких структур данных в индустрии: ошибка в одном барьере проявляется
раз в несколько часов на конкретной архитектуре (ARM особенно беспощаден). В упражнении мы
защищаем каждую deque своим мьютексом — это сохраняет архитектуру (локальность, редкие
конфликты) и избавляет от тонкостей модели памяти. Переходить на lock-free стоит, только
когда профилировщик показывает, что мьютексы deque — узкое место.

### Lock-free: базовые правила

* **Lock-free ≠ быстро.** Атомарная операция на загруженной кеш-линии стоит как промах в
  L3 или дороже. Главный выигрыш lock-free — отсутствие блокировок при вытеснении потока,
  а не скорость сама по себе.
* **Начинайте с SPSC** (один производитель, один потребитель, трек 1, упражнение 112): это
  единственная lock-free структура, которую стоит писать самому без глубокой экспертизы.
* **Проблема ABA**: CAS видит то же значение, но объект уже был удалён и создан заново.
  Лечится счётчиками поколений (как у хендлов, глава 03) или безопасным освобождением памяти
  (epoch-based reclamation, hazard pointers).
* **Порядок памяти**: `SEQ_CONSISTENT` — безопасный дефолт. `ACQUIRE`/`RELEASE` для пары
  «опубликовать данные / прочитать данные» — достаточно почти всегда. `RELAXED` — только для
  счётчиков статистики, где не важна видимость других данных.

Про ABA подробнее, по шагам. Поток 1 читает указатель на вершину стека: там узел по адресу
`A`. Его вытесняют. Поток 2 снимает `A`, снимает `B`, освобождает оба и кладёт новый узел,
который аллокатор разместил *по тому же адресу* `A`. Поток 1 просыпается, делает CAS
«если вершина всё ещё `A`, поставь `A.next`» — CAS успешен (адрес тот же!), но `A.next`
указывает на уже освобождённый `B`. Название — от последовательности значений
«A → B → A», которую CAS не может отличить от «A всё время».

> **Частые ошибки (work stealing)**
> * Перепутали концы: владелец берёт сверху, вор снизу — теряется локальность, а в
>   lock-free версии ещё и корректность.
> * В `pop_bottom` взяли элемент по старому `bottom` (а он указывает *за* последний).
> * Обход жертв включает себя — поток «крадёт» у самого себя через мьютекс, лишняя работа и
>   неверная статистика краж.
> * Проверка «пусто?» вне мьютекса, а изъятие — под ним: между ними вор мог забрать
>   последний элемент.

## False sharing

Кеш работает линиями по 64 байта (на Apple M1/M2 — 128). Если два потока **пишут в разные
переменные одной линии**, протокол когерентности MESI гоняет линию между ядрами при каждой
записи:

Сначала термины. **Кеш** — маленькая быстрая память рядом с каждым ядром, куда копируются
данные из основной памяти. Копируется не по байту, а блоками — **кеш-линиями** по 64 байта.
**Когерентность** — гарантия, что все ядра видят согласованные данные: если одно ядро
пишет в линию, копии этой линии в кешах других ядер становятся недействительными.
**MESI** — самый известный протокол когерентности (по первым буквам состояний линии:
Modified, Exclusive, Shared, Invalid).

```
            одна кеш-линия (64 байта)
          ┌────────┬────────┬────────┬────────┐
          │stats[0]│stats[1]│stats[2]│stats[3]│
          └───▲────┴───▲────┴───▲────┴───▲────┘
           core0    core1    core2    core3      ← каждый пишет «своё», но линия общая
```

Что происходит по шагам, когда ядра 0 и 1 по очереди увеличивают «свои» счётчики:

| Шаг | Действие | Линия в кеше ядра 0 | Линия в кеше ядра 1 |
|---|---|---|---|
| 1 | ядро 0 пишет `stats[0]` | Modified (только у него) | Invalid |
| 2 | ядро 1 хочет писать `stats[1]` — линии у него нет, запрашивает её | → Invalid (отдал) | Modified |
| 3 | ядро 0 снова пишет `stats[0]` — его копия недействительна, запрашивает | Modified | → Invalid |
| 4 | ядро 1 снова пишет `stats[1]` … | Invalid | Modified |

Каждая запись — это пересылка 64 байт между ядрами (десятки наносекунд) вместо записи в
свой кеш (около наносекунды). Линия «пинг-понгом» летает туда-сюда.

> **Аналогия.** Два человека заполняют разные графы *одного* бланка. Бланк один, поэтому
> они передают его друг другу после каждой буквы. Каждый пишет только в свою графу, никто
> никому не мешает по смыслу, а работа идёт в десять раз медленнее.

Гонки данных нет — каждый пишет в своё поле, — а код медленнее в разы. Классические места:

* массив per-thread счётчиков и статистики;
* `head` и `tail` очереди в одной структуре (производитель пишет одно, потребитель —
  другое);
* атомарный флаг рядом с часто читаемыми данными;
* границы кусков `parallel_for`, если кусок не кратен линии.

Лечение — выравнивание и паддинг до размера линии:

```c3
struct WorkerStats @align(64)   // каждый экземпляр начинается с границы 64 байт
{
    long executed;              // 8 байт
    long stolen;                // 8 байт
}                               // + 48 байт «пустоты» (паддинга) до 64
// WorkerStats::size == 64, каждый элемент массива — в своей линии
```

Проверено в C3: без `@align(64)` `WorkerStats::size == 16` (четыре элемента массива
умещаются в одну линию), с ним — 64. **Выравнивание (alignment)** — требование, чтобы адрес
объекта был кратен числу; **паддинг (padding)** — неиспользуемые байты, которые компилятор
добавляет, чтобы выполнить это требование. Мы тратим 48 байт на поток — копейки — и
избавляемся от пинг-понга.

В C++ есть `std::hardware_destructive_interference_size`; в C3 размер линии задаётся
константой движка. Ещё лучше — накапливать статистику в локальной переменной и записывать
в общий массив один раз в конце задачи.

> **Частые ошибки (false sharing)**
> * Думать, что раз гонки нет — всё хорошо. False sharing — проблема скорости, а не
>   корректности, и тесты её не ловят; ловит профилировщик.
> * Выровнять поле внутри структуры, но не саму структуру (или наоборот) — проверяйте
>   `Type::size` и `Type::alignment`.
> * Считать, что на всех машинах линия 64 байта (Apple M1/M2 — 128).

**Коротко:** разные переменные в одной 64-байтной линии, в которые пишут разные ядра, —
это пинг-понг кеша. Лечится `@align(64)` (или локальными накоплениями).

## Конвейер кадров

Даже с идеальной job system в кадре есть последовательные зависимости: рендер нельзя
готовить, пока симуляция не закончила. Решение — **перекрывать кадры** (упражнение `e1206`):

**Конвейер (pipeline)** — когда работа идёт стадиями, и разные стадии одновременно
обрабатывают разные «изделия». **Латентность (latency)** — задержка от входа до результата.

> **Аналогия.** Прачечная: стирка, сушка, глажка. Пока гладится первая партия, сушится
> вторая и стирается третья. Одна партия проходит путь так же долго, как и раньше
> (латентность не уменьшилась, даже чуть выросла), но партий в час выходит втрое больше
> (выросла пропускная способность).

Последовательно (как `run_sequential` в `e1206`) — каждая стадия ждёт предыдущую:

```
время ─────────────────────────────────────────────────────►
sim:     [ sim 0 ]         [ sim 1 ]         [ sim 2 ]
render:           [ rnd 0 ]         [ rnd 1 ]         [ rnd 2 ]
```

Конвейером:

```
время ─────────────────────────────────────────────────────►
game/sim:   [ sim 0 ][ sim 1 ][ sim 2 ][ sim 3 ]
render:              [ rnd 0 ][ rnd 1 ][ rnd 2 ][ rnd 3 ]
GPU:                          [ gpu 0 ][ gpu 1 ][ gpu 2 ]
```

Пока симуляция считает кадр N, рендер строит команды для N-1, а GPU рисует N-2. Каждая
стадия работает со своей копией данных:

* **двойная буферизация состояния**: sim(N) пишет в `states[N % 2]`, а читает кадр N-1 из
  `states[(N+1) % 2]`, из которого же читает и render(N-1). Оба только читают общий буфер,
  пишет каждый в своё — мьютексы не нужны.
* **извлечение (extract)**: вместо двойного буфера всего мира рендер в начале своего кадра
  копирует себе только то, что ему нужно (трансформы видимых объектов, параметры камеры и
  света). Так делают Unreal (`FPrimitiveSceneProxy` — копия примитива на стороне
  рендер-потока) и Bevy (extract-стадия в отдельный render world).

### Кто какой буфер трогает: таблица

Буферов два: `states[0]` и `states[1]`. Для каждого шага конвейера («такта») — кто пишет и
кто читает:

| Такт | sim(N) пишет | sim(N) читает (кадр N-1) | render(N-1) читает | Пересечение «пишет/читает»? |
|---|---|---|---|---|
| 0 | sim(0) → `states[0]` | `states[1]` (начальное состояние) | — (рендерить ещё нечего) | нет |
| 1 | sim(1) → `states[1]` | `states[0]` | render(0) ← `states[0]` | нет: оба *читают* `states[0]` |
| 2 | sim(2) → `states[0]` | `states[1]` | render(1) ← `states[1]` | нет |
| 3 | sim(3) → `states[1]` | `states[0]` | render(2) ← `states[0]` | нет |

Правило, которое видно из таблицы: **в каждом такте один буфер «на запись» (только sim),
другой «на чтение» (sim и render оба читают)**. А между тактами — ожидание счётчика: такт
N+1 не начнётся, пока обе задачи такта N не закончились. Поэтому, когда sim(2) начинает
перезаписывать `states[0]`, render(0), который его читал, гарантированно уже завершён.

И после последнего такта остаётся «хвост» конвейера: последний кадр симулирован, но ещё
не отрендерен — его нужно дорендерить отдельно.

### Штампы кадров

В упражнении буферы помечены номером кадра, и запуск стадии проверяет штамп. Такие
дешёвые проверки (в отладочной сборке) — лучшая защита от перепутанных индексов, которые
иначе выглядят как «объекты иногда дрожат».

Как это работает: в буфере есть поле `frame` — «какой кадр сейчас здесь лежит». sim(N)
перед стартом проверяет, что во входном буфере лежит кадр N-1, а записав, ставит штамп N.
render(N) проверяет, что в его буфере кадр N. Если вы перепутали индексы, assert
сработает сразу и скажет, какой кадр ожидался, — вместо того чтобы молча нарисовать
позапрошлый кадр.

### Цена конвейера

Цена — **латентность**: картинка отстаёт от ввода на дополнительный кадр. Поэтому
считать «input lag» в движке — отдельное искусство, а стадии иногда сдвигают (например,
читают ввод как можно позже и обновляют камеру прямо перед рендером, late latching в VR).

**Input lag** — время от нажатия кнопки до появления реакции на экране. При 60 FPS каждый
лишний кадр в конвейере — это +16,7 мс.

Naughty Dog в том же докладе описывают конвейер, где одновременно «в полёте» до трёх
кадров: игровая логика кадра N, рендер-логика N-1, GPU — N-2. Данные кадра выделяются из
кадровых аллокаторов (глава 02), помеченных номером кадра, и освобождаются целиком, когда
кадр проходит через все стадии. Это и есть причина, по которой кадровые аллокаторы бывают
«двойными» и «тройными».

> **Частые ошибки (конвейер)**
> * sim(N) пишет в тот же буфер, из которого render(N-1) читает, — гонка, «дрожащие»
>   объекты.
> * Забыли дорендерить последний кадр после цикла.
> * Свели результат рендера (`finish_render`) до ожидания счётчика — читаете незаконченное.
> * Рендерите кадр N вместо N-1 в такте N — данные ещё пишутся.

**Коротко:** sim(N) и render(N-1) работают одновременно, каждый со своим буфером; один
буфер пишется, другой только читается. Плата — +1 кадр задержки.

## Детерминизм и отладка

Многопоточный код должен давать один и тот же результат независимо от планирования:

**Детерминизм** — свойство «одинаковый вход → побитово одинаковый выход», при любом
числе ядер и любом поведении планировщика ОС.

* **Никаких общих аккумуляторов** с порядком «кто первый» — только слоты + свёртка
  (см. редукции).
* **Нет порядка между независимыми задачами.** Если две задачи добавляют объекты в общий
  список, порядок в списке случайный. Решения: каждой задаче свой список и склейка по
  индексу задачи; или сортировка по стабильному ключу (ID сущности) после ожидания.
* **Генераторы случайных чисел** — свой на задачу/сущность, с seed от стабильного ID, а
  не один общий.
* **Однопоточный режим**: флаг, при котором job system выполняет все задачи сразу в
  вызывающем потоке в топологическом порядке. Если баг исчезает — это гонка; если
  остаётся — логика. Бесценно для отладки.

Почему общий генератор случайных чисел ломает детерминизм: генератор — это состояние,
которое меняется при каждом вызове. Если две задачи по очереди берут из него числа, то
*какая* задача получит *какое* число, зависит от того, кто первым дошёл до вызова. А с
генератором «на сущность» (seed = ID) сущность 17 всегда получает одну и ту же
последовательность.

Инструменты: **ThreadSanitizer** (`-fsanitize=thread` в Clang) находит гонки данных;
профилировщики с временной шкалой по потокам — **Tracy**, **Superluminal**, **Intel
VTune**, **PIX**, **Razor** на PlayStation — показывают простой ядер, длинные хвосты
`parallel_for` и ожидание мьютексов (подробнее в главе 15). Главная метрика job system —
не «сколько задач в секунду», а **сколько времени ядра простаивают в кадре** и **сколько
длится критический путь графа**.

**Критический путь** — самая длинная по времени цепочка зависимых задач в графе. Кадр не
может быть короче неё, сколько бы ядер ни было. Например, если input → ai → physics → cull
→ render занимают 1 + 3 + 4 + 2 + 3 = 13 мс, то кадр — не меньше 13 мс, даже на 64 ядрах.
Ускорять имеет смысл в первую очередь задачи на критическом пути.

**Коротко:** не зависьте от порядка завершения; держите однопоточный режим для отладки;
меряйте простой ядер и критический путь.

## Типичные ошибки

1. **Задача ждёт ОС** (`sleep`, синхронный IO, долгий мьютекс) — рабочий потерян на всё
   время ожидания.
2. **Наивное ожидание внутри задачи** — deadlock при глубокой вложенности (`e1202`).
3. **Счётчик увеличивается после публикации задачи** — ожидающий уходит раньше времени.
4. **Слишком мелкие задачи** — время уходит на очереди и атомики. Слишком крупные —
   плохая балансировка.
5. **False sharing** в per-thread данных.
6. **Захват указателя на стековую переменную**, которая умирает раньше задачи (запустили
   задачи и вернулись из функции, не дождавшись). В `e1202` дочерние `SumJob` лежат на
   стеке родителя — это корректно только потому, что родитель ждёт детей до выхода.
7. **Печать / логирование из задач без синхронизации** — перемешанный вывод и скрытая
   сериализация на мьютексе stdout. Логи пишутся в per-thread буферы.
8. **Недетерминированные редукции** float.
9. **Lock-free «потому что быстро»** без профилирования и без понимания модели памяти.
10. **Забыли, что `Atomic.add`/`sub` возвращают старое значение** — отсюда «на единицу»
    ошибки в `parallel_for` и графе задач.
11. **`if` вместо `while` вокруг `wait`** и **`signal` вместо `broadcast` при завершении**
    (`e1201`).

## Как это выглядит целиком

Каркас job system хорошего движка (упражнения главы покрывают каждую строку):

```
JobSystem
 ├─ N рабочих потоков, прибитых к ядрам
 ├─ на каждого рабочего: deque (work stealing) + стек файберов (опционально)
 ├─ очереди приоритетов: HIGH (кадр), NORMAL, LOW (стриминг, фоновые вычисления)
 ├─ Counter: атомик + список ожидающих (файберов или продолжений)
 ├─ API:
 │    run_jobs(jobs, &counter)
 │    wait_for_counter(&counter)        — помощь или парковка файбера
 │    parallel_for(count, chunk, body)  — поверх run_jobs
 │    TaskGraph: compile() / run()      — статические зависимости кадра
 └─ режим отладки: однопоточное исполнение в топологическом порядке
```

Кадр: главный поток (или задача «кадр») запускает граф кадра; внутри узлов —
`parallel_for`; данные кадра — в кадровом аллокаторе; рендер получает извлечённые данные
и работает на кадр позади.

Соответствие строк каркаса и упражнений:

| Строка каркаса | Где вы это пишете |
|---|---|
| рабочие потоки, очередь, завершение | `e1201` |
| `Counter`, `run_jobs`, `wait_for_counter` с помощью | `e1202` |
| `parallel_for` и детерминированные редукции | `e1203` |
| `TaskGraph: compile() / run()` | `e1204` |
| deque на рабочего, кражи, выравнивание статистики | `e1205` |
| «рендер работает на кадр позади» | `e1206` |

## Как это связано с упражнениями

Здесь — что спрашивает каждое упражнение, что перечитать и где обычно ошибаются. Решений
нет — только ориентиры.

### e1201 · Пул потоков и очередь задач

* **Что просят:** реализовать `JobQueue.push`, `JobQueue.pop`, `JobQueue.shutdown`. Пул
  рабочих, `worker_main` и проверки уже написаны.
* **Перечитать:** «Азбука» → «Мьютекс», «Условная переменная»; «Очередь задач» целиком,
  особенно таблицы про `while` и `broadcast`.
* **На что смотреть:** у каждой функции своя условная переменная «на ожидание» и своя «на
  побудку» — `push` ждёт одного, будит другое, `pop` наоборот. Ёмкость очереди специально
  маленькая, так что ожидание на `not_full` реально случится. Выход из `pop` с `false` —
  только когда пусто *и* идёт завершение. В `shutdown` флаг меняется под мьютексом.
  Если программа зависла на выходе — подумайте, всех ли разбудили.

### e1202 · Счётчики и ожидание с помощью

* **Что просят:** `execute_job`, `JobSystem.run_jobs`, `JobSystem.wait_for_counter`.
* **Перечитать:** «Атомики» (что возвращает `sub`), «Счётчики вместо future» — порядок
  «сначала счётчик» и таблицу «помощь при ожидании».
* **На что смотреть:** счётчик увеличивается *одним* `add` на всю пачку и *до* первого
  `push`. У задачи может не быть счётчика (`null`). Ожидание обязано помогать: брать
  задачи **неблокирующим** способом, а если очередь пуста — уступать ядро. Тест специально
  запускает глубоко вложенные ожидания на двух рабочих: наивное ожидание зависнет.

### e1203 · parallel_for и детерминированная редукция

* **Что просят:** цикл `pf_worker` и `parallel_sum` поверх `parallel_for`.
* **Перечитать:** «parallel_for» — таблицу раздачи кусков и «Детерминированные редукции».
* **На что смотреть:** `add(1)` возвращает старое значение; последний кусок короче
  остальных; функция возвращает число обработанных кусков. Слот частичной суммы — по
  номеру *куска*. Свёртка — по порядку индексов, в одном потоке, после того как
  `parallel_for` вернулся. Не забудьте освободить временный массив. Проверка — побитовое
  совпадение при 1, 2, 4 и 7 потоках с однопоточным эталоном.

### e1204 · Граф задач

* **Что просят:** `TaskGraph.compile` (последователи + алгоритм Кана + поиск цикла) и
  `TaskGraph.on_task_done`.
* **Перечитать:** «Зависимости и графы задач» — обе трассировки (Кан и «кто довёл до
  нуля»).
* **На что смотреть:** перед построением обнулите списки последователей. Среди готовых
  задач берите наименьший индекс — от этого зависит ожидаемый вывод. Нужно помнить, какие
  задачи уже выписаны. Если на шаге нет готовой задачи — это цикл. В `on_task_done`
  решение «публиковать или нет» принимается по результату самого `sub`, а не отдельным
  `load`.

### e1205 · Кража работы и false sharing

* **Что просят:** `WorkDeque.pop_bottom`, `WorkDeque.steal_top`, `try_steal` и
  выравнивание `WorkerStats`.
* **Перечитать:** «Work stealing» — таблицу «как меняется дек»; «False sharing».
* **На что смотреть:** элементы живут в `[top, bottom)` — `bottom` указывает *за*
  последний. Владелец уменьшает `bottom` и берёт новое значение; вор берёт по `top` и
  потом его увеличивает. Обход жертв — начиная с `(id + 1)`, себя не трогать. Успешную
  кражу засчитывайте вору. Выравнивание проверяется через `WorkerStats::size`. Сначала
  всё прогоняется в одном потоке — удобно отлаживать.

### e1206 · Конвейер кадров

* **Что просят:** `run_pipelined` — тот же результат, что у `run_sequential`, но sim(f)
  параллельно с render(f-1).
* **Перечитать:** «Конвейер кадров» — таблицу «кто какой буфер трогает» и «Штампы кадров».
* **На что смотреть:** индексы буферов возьмите из `run_sequential` — они те же, меняется
  только *когда* запускается рендер. Один счётчик на такт, обе стадии вешаются на него.
  Рендер первого такта не запускается (рендерить ещё нечего), а после цикла нужно
  дорендерить последний кадр. Перепутаете буфер — сработает assert штампа с понятным
  сообщением: читайте, какой кадр ожидался.

## Вопросы для самопроверки

1. Почему архитектура «поток на подсистему» плохо масштабируется с ростом числа ядер?
2. Почему ожидание на условной переменной записывают в цикле `while`, а не `if`? Что
   произойдёт, если при завершении пула вызвать `signal` вместо `broadcast`?
3. Почему счётчик в `run_jobs` нужно увеличить до публикации задач? Опишите конкретное
   чередование потоков, при котором иначе всё ломается.
4. Объясните, как возникает deadlock при наивном ожидании внутри задачи. Какие три
   способа его избежать вы знаете, и чем каждый платит?
5. Что такое файбер и почему с файберами нельзя держать мьютекс ОС через `wait`?
6. Как размер куска `parallel_for` влияет на производительность? Что такое «хвост»?
7. Почему параллельная сумма float может давать разный результат от запуска к запуску и
   как сделать её детерминированной? От чего результат всё ещё зависит?
8. Почему в графе задач последователя публикует тот поток, у которого `sub(1)` вернул 1, и
   почему это не требует блокировки графа?
9. Зачем владелец deque работает в режиме LIFO, а вор — FIFO?
10. Что такое false sharing? Найдите три места в типичной job system, где он возникает.
11. Сколько кадров «в полёте» в конвейере sim/render/GPU и какова цена конвейеризации?
    Чем подход «extract» отличается от двойной буферизации всего мира?
12. Как бы вы искали гонку, которая проявляется раз в час? Какой режим job system для
    этого нужен?
13. Нарисуйте таблицу чередования, при которой два потока, делающие `counter++`, теряют
    одно прибавление. Почему с `Atomic.add` так не бывает?
14. Что гарантирует пара «RELEASE-запись → ACQUIRE-чтение»? Где в этой главе такая пара
    встречается неявно (подсказка: мьютекс, счётчик `pending`, `join`)?

|---|---|
| **Ядро (core)** | «исполнитель» в процессоре; сколько ядер — столько потоков реально идут одновременно |
| **Поток (thread)** | независимая последовательность инструкций в программе со своим стеком; все потоки делят память |
| **Планировщик ОС** | часть ОС, которая решает, какой поток на каком ядре сейчас работает |
| **Вытеснение (preemption)** | ОС снимает поток с ядра в произвольный момент |

| **Пул потоков** | набор потоков, созданных один раз и переиспользуемых |
| **Рабочий (worker)** | поток, который в цикле берёт задачи и выполняет их |
| **Задача (job)** | «указатель на функцию + указатель на данные», единица работы |
| **Affinity** | привязка потока к конкретному ядру |

| **Чередование (interleaving)** | конкретный порядок, в котором перемешались шаги разных потоков |

| **Критическая секция** | код между `lock` и `unlock` |

| **CAS (compare-and-swap)** | «если там X — запиши Y», атомарно (`compare_exchange`) |
| **Порядок памяти** | какие гарантии видимости даёт атомарная операция другим записям |
| **RELEASE / ACQUIRE** | «запечатать всё записанное до» / «увидеть всё запечатанное» |
| **SEQ_CONSISTENT** | самый строгий порядок, дефолт в C3 |
| **RELAXED** | только атомарность, без порядка — для статистики |
| **Happens-before** | «A гарантированно видно B»: цепочка через release/acquire, мьютекс, `join` |
| **Spin / spinlock** | ждать, крутясь в цикле, вместо засыпания |
| **yield** | уступить ядро другим потокам, оставаясь готовым |
| **Кольцевой буфер** | массив, используемый по кругу; очередь без аллокаций |
| **Backpressure** | производитель тормозит, когда потребитель не успевает |
| **Счётчик (Counter)** | атомик «сколько задач пачки ещё не выполнено» |
| **Future / promise** | объект «результат будет потом» на каждую задачу |
| **Барьер** | точка, где все потоки ждут друг друга |
| **Deadlock** | потоки ждут друг друга по кругу и никогда не продвинутся |
| **Помощь при ожидании** | ожидающий сам выполняет задачи из очереди |
| **Файбер (fiber)** | лёгкий контекст исполнения со своим стеком, переключаемый программой без ОС |
| **TLS** | переменная, у каждого потока своя копия |
| **Продолжение (continuation)** | «когда это закончится — запусти вот это» |
| **parallel_for** | «сделай одно и то же для каждого из N элементов» на нескольких потоках |
| **Кусок (chunk)** | непрерывный диапазон элементов, обрабатываемый одним вызовом |
| **Гранулярность** | насколько мелко нарезана работа |
| **Хвост (tail)** | конец параллельной работы, когда трудится один поток, а остальные ждут |
| **Редукция** | свёртка многих значений в одно (сумма, минимум, AABB) |
| **Ассоциативность** | «скобки можно ставить как угодно»; у float её нет |
| **Граф задач / DAG** | задачи и зависимости между ними, без циклов |
| **Последователи (successors)** | задачи, которые зависят от данной |
| **Входящая степень (indegree)** | число невыполненных зависимостей |
| **Топологический порядок** | порядок, где каждая задача после всех своих зависимостей |
| **Алгоритм Кана** | построение топологического порядка с обнаружением циклов |
| **Frame graph / render graph** | граф проходов рендера с объявленными ресурсами |

| **Deque (дек)** | очередь с двумя концами |

| **Chase–Lev deque** | классический lock-free дек для work stealing |
| **ABA** | CAS не замечает, что значение успело смениться и вернуться |
| **Кеш, кеш-линия** | быстрая память у ядра; обмен блоками по 64 байта |
| **Когерентность, MESI** | протокол, согласующий копии линий в кешах ядер |
| **False sharing** | разные данные в одной кеш-линии, в которые пишут разные ядра |
| **Выравнивание, паддинг** | адрес кратен числу; пустые байты для этого |
| **Конвейер (pipeline)** | стадии работают одновременно над разными кадрами |
| **Двойная буферизация** | два экземпляра данных: один пишется, другой читается |
