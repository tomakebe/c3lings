## Вступление: что такое «сцена»

«Сцена» — одно из самых перегруженных слов в движкостроении. В редакторе Unity это файл
`.unity`, в Godot — дерево `Node`, в Unreal — `UWorld` с уровнями и акторами, в рендерере —
список видимых мешей. В этой главе нас интересуют две вещи, которые нужны почти любому
движку независимо от его философии:

1. **Иерархия трансформаций.** Колесо прикреплено к машине, машина — к платформе, пистолет —
   к кости руки. Объекты задаются *относительно* родителя, а остальному движку нужны
   *мировые* координаты.
2. **Пространственные запросы.** «Что видит камера?», «Кто в радиусе взрыва?», «С кем я могу
   столкнуться?». Отвечать на них перебором всех объектов нельзя уже при нескольких тысячах
   сущностей.

Это две разные задачи с разными структурами данных, и одна из главных ошибок
дизайна — пытаться решить их одним деревом. К этому мы ещё вернёмся (раздел 7).

Пара слов, которые будут встречаться постоянно:

* **Трансформация** (transform) — «где объект и как он повёрнут/растянут». Обычно это три
  вещи: **перенос** (сдвиг, translation), **поворот** (rotation) и **масштаб** (scale).
* **Узел** (node) — один элемент дерева: объект сцены, у которого может быть родитель и
  дети.
* **Родитель / ребёнок / потомки / предки.** Если колесо прикреплено к машине, машина —
  родитель колеса, колесо — ребёнок машины. Потомки — дети, дети детей и так далее вниз;
  предки — родитель, родитель родителя и так далее вверх. **Корень** — узел без родителя.
* **Поддерево** узла — сам узел плюс все его потомки.

## 1. Local и world

### 1.1 Интуиция: «относительно чего?»

Представьте, что вы едете в поезде и сидите на месте №12. Если спросить «где вы?», можно
ответить двумя способами:

* «В вагоне 5, место 12» — это **локальные** координаты: относительно вагона.
* «На 347-м километре от Москвы» — это **мировые** координаты: относительно всего мира.

Чтобы из первого ответа получить второй, нужно знать, где сейчас вагон (а для этого — где
поезд). Когда поезд едет, ваше локальное положение не меняется (вы сидите на месте), а
мировое меняется постоянно.

В игре всё точно так же. Каждый узел хранит **локальную** трансформацию — положение,
поворот и масштаб относительно родителя. **Мировая** трансформация получается композицией
(последовательным применением) трансформаций всех предков:

```
world(root) = local(root)
world(n)    = world(parent(n)) * local(n)
            = local(root) * ... * local(parent) * local(n)
```

Здесь `*` — умножение матриц, то есть «применить одно преобразование вслед за другим».
Что это значит точно и почему порядок именно такой — в разделах 2 и 3.

### 1.2 Почему не хранить сразу мировые?

Потому что художник и геймплей мыслят локально: «башня повёрнута на 30° относительно
корпуса», «меч в руке». Если хранить только world, то при повороте корпуса придётся вручную
пересчитать все вложенные объекты — то есть всё равно реализовать иерархию, но в худшем
месте. Поэтому движки хранят **оба** представления: local — **источник истины** (то, что
мы меняем руками), world — **кэш**, производное значение (то, что мы вычисляем из local
и можем в любой момент пересчитать заново).

> **Кэш** — сохранённый результат вычисления, чтобы не считать его повторно. Кэш может
> **устареть** (если исходные данные изменились), и тогда его надо пересчитать.

### 1.3 Пример дерева

```
          city (local: translate 100,0)
           |
         car  (local: translate 10,0; rotate 90)
         /  \
    wheel   turret (local: translate 0,1; rotate -45)
                \
               barrel (local: translate 3,0)

  world(barrel) = L(city) * L(car) * L(turret) * L(barrel)
```

Читается это так: «ствол сдвинут на 3 вперёд относительно башни; башня — на 1 вверх и
повёрнута на −45° относительно машины; машина — на 10 вправо и повёрнута на 90° относительно
города; город сдвинут на 100 относительно мира». Чтобы узнать, где ствол в мире, мы
применяем эти преобразования одно за другим, начиная с самого «внутреннего» (ствола) и
поднимаясь к корню.

### 1.4 Простейший случай: только сдвиги

Если у всех узлов нет поворотов и масштабов, а есть только сдвиги, то «умножение
трансформаций» превращается в обычное сложение векторов. Так устроены упражнения `e0803` и
`e0806` — там трансформация это просто целочисленный сдвиг `IVec`, и
`world = world(parent) + local`.

Возьмём солнечную систему из `e0801`, пока без поворотов:

| Узел | Родитель | local | Как считаем world | world |
|---|---|---|---|---|
| sun | — | (100, 100) | это корень: world = local | (100, 100) |
| planet | sun | (10, 0) | (100, 100) + (10, 0) | (110, 100) |
| moon | planet | (2, 0) | (110, 100) + (2, 0) | (112, 100) |

Луна «знает» только то, что она в 2 единицах от планеты. Но её мировая позиция — 112 по X.
Если сдвинуть солнце на (+5, 0), мировые позиции планеты и луны сдвинутся сами, хотя их
local никто не трогал.

С поворотами всё интереснее: если солнце **повернётся** на 90°, планета должна «облететь»
его — её смещение (10, 0) повернётся и станет (0, 10). Сложением этого не выразить, поэтому
нужны матрицы.

**Коротко:** local — положение относительно родителя (его мы задаём), world — положение в
мире (его мы вычисляем, проходя по цепочке предков). Движки хранят оба: local как
источник истины, world как кэш.

## 2. Как хранить трансформацию

### 2.1 Варианты

Варианты, от простого к сложному:

| Представление | Плюсы | Минусы |
|---|---|---|
| Матрица 4x4 (3x3 в 2D) | композиция — одно умножение, сразу для GPU | 64 байта, нельзя интерполировать, накапливает ошибку (перекос) |
| Аффинная 3x4 (2x3 в 2D) | на 25% меньше, нижняя строка всегда (0,0,0,1) | всё ещё неинтерполируема |
| TRS: translation + quaternion + scale | 40 байт, интерполируется (анимация!), удобно редактировать | композиция дороже, неравномерный масштаб + поворот у родителя ломает TRS |

Расшифруем слова из таблицы:

* **Аффинное преобразование** — любое сочетание поворота, масштаба, перекоса и сдвига.
  Прямые линии остаются прямыми, параллельные — параллельными. Почти всё, что делают с
  объектами в игре, — аффинные преобразования.
* **Интерполировать** — плавно перейти от одного значения к другому («на 30% пути от позы A
  к позе B»). Для позиций это просто `a + (b - a) * t`. С матрицами так нельзя: если
  поэлементно смешать матрицу «поворот на 0°» и «поворот на 180°», посередине получится
  матрица, сплющивающая объект в точку. TRS интерполируется по частям: перенос — линейно,
  поворот-кватернион — через slerp (глава 04), масштаб — линейно.
* **TRS** — хранение трансформации тремя отдельными частями: **T**ranslation (перенос),
  **R**otation (поворот, в 3D обычно кватернион), **S**cale (масштаб).
* **Накапливает ошибку.** Если много раз подряд домножать матрицу на маленький поворот,
  ошибки округления float копятся, и матрица перестаёт быть «чистым поворотом» — объект
  начинает слегка перекашиваться.

На практике: **локальная** трансформация хранится как TRS (её крутит анимация, редактор,
геймплей), **мировая** — как аффинная матрица (её потребляют рендер и физика). Unreal хранит
`FTransform` (кватернион + перенос + 3D-масштаб) и для local, и для world; Unity —
TRS в `Transform` плюс кэш `localToWorldMatrix`; Bitsquid/Stingray в своём `SceneGraph`
держал local как `Matrix4x4` или TRS-«Pose» и world как матрицу.

**Коротко:** для редактирования и анимации удобен TRS, для быстрой композиции и рендера —
матрица. Движки обычно держат local в TRS, а world — в матрице.

### 2.2 Матрица 2x3 «на пальцах»

В упражнениях `e0801` и `e0802` трансформация — это структура из шести чисел:

```
struct Affine2 { float a, b, c, d, tx, ty; }
```

Её удобно рисовать как матрицу, где третья строка всегда `0 0 1` (поэтому её и не хранят):

```
    | a  c  tx |   | x |     x' = a*x + c*y + tx
    | b  d  ty | * | y |     y' = b*x + d*y + ty
    | 0  0  1  |   | 1 |
```

Как это понять без линейной алгебры? Посмотрите на столбцы:

* `(a, b)` — **куда попадает единичный шаг по оси X** объекта.
* `(c, d)` — **куда попадает единичный шаг по оси Y** объекта.
* `(tx, ty)` — **куда попадает начало координат** объекта (его «центр»).

Тогда формула `x' = a*x + c*y + tx` читается так: «точка (x, y) — это x шагов по оси X
плюс y шагов по оси Y от центра; подставим, куда уехали оси и центр».

Пример. Пусть объект сдвинут в (5, 0) без поворота: `a=1, b=0, c=0, d=1, tx=5, ty=0`.
Оси остались на месте, центр уехал в (5, 0). Точка (1, 0):

```
x' = 1*1 + 0*0 + 5 = 6
y' = 0*1 + 1*0 + 0 = 0      -> (6, 0): точка просто сдвинулась на 5
```

### 2.3 Откуда в повороте синус и косинус

Поворот на угол θ против часовой стрелки переносит единичный шаг по X из (1, 0) в точку
единичной окружности (cos θ, sin θ) — это школьное определение синуса и косинуса. А шаг по Y
из (0, 1) уходит в (−sin θ, cos θ) — он всегда «на 90° дальше».

```
         y
         ^
   (-sinθ, cosθ)        ось Y после поворота
         \   |
          \  |   ,(cosθ, sinθ)   ось X после поворота
           \ | ,'
            \|'  θ
   ----------+----------> x
             |
```

Поэтому функция `from_trs` в `e0801` строит `{ cs, sn, -sn, cs, x, y }`, где
`cs = cos(θ)*scale`, `sn = sin(θ)*scale` — масштаб просто удлиняет обе оси.

Для поворота на 90°: cos 90° = 0, sin 90° = 1, значит `a=0, b=1, c=-1, d=0`. Проверим на
точке (1, 0):

```
x' = 0*1 + (-1)*0 + 0 = 0
y' = 1*1 +   0*0  + 0 = 1      -> (0, 1): точка с оси X переехала на ось Y. Верно!
```

> Углы в коде почти всегда в **радианах**: 180° = π радиан, поэтому градусы переводят как
> `deg * PI / 180`. Передать в `cos` градусы вместо радиан — классическая ошибка.

**Коротко:** шесть чисел аффинной матрицы — это «куда уехала ось X», «куда уехала ось Y» и
«куда уехал центр». Применить матрицу к точке — значит собрать точку из новых осей и центра.

### 2.4 Неравномерный масштаб и перекос

Отдельная тонкость — **неравномерный масштаб** (по X растянули сильнее, чем по Y). Если
родитель растянут по X в 2 раза, а ребёнок повёрнут на 45°, то мировая матрица ребёнка
содержит **перекос** (shear) — квадрат превращается в ромб, а не в прямоугольник. Такой
ромб нельзя выразить в TRS: там есть только поворот и растяжение по собственным осям.

```
  ребёнок (квадрат,           родитель растягивает
  повёрнут на 45°)            по X в 2 раза
        /\                       __--/\--__
       /  \          ->        <__        __>   ромб: углы уже не 90°
       \  /                       --\/--
        \/
```

Unreal и Unity честно предупреждают в документации, что разложение мировой матрицы обратно
в TRS в этом случае приближённо. Многие движки (и Godot для 2D) просто запрещают или не
рекомендуют неравномерный масштаб на родителях с повёрнутыми детьми. Решение для
собственного движка: мировые трансформации — матрицы, а API `get_world_rotation()` честно
документирует, что он неточен при перекосе.

**Коротко:** поворот внутри неравномерного масштаба даёт перекос, который не помещается в
TRS. Мировые трансформации поэтому держат матрицами.

## 3. Порядок умножения

### 3.1 Правило

Это самый частый баг в иерархиях. Для векторов-столбцов (`p' = M * p`, конвенция OpenGL,
большинства учебников и этого курса) запись `A * B` означает **«сначала B, затем A»** —
читаем справа налево, как в математике `f(g(x))`: сначала `g`, потом `f`.

Мировая матрица — это `parent * local`: сначала точка переводится из пространства ребёнка в
пространство родителя (local), затем дальше вверх.

```c3
// self * c : сначала c, потом self.
fn Affine2 Affine2.mul(self, Affine2 c) { ... }

Affine2 world = world_of_parent.mul(local);   // правильно
Affine2 wrong = local.mul(world_of_parent);   // «почти работает»
```

Что здесь происходит: метод `mul` вызывается у левого множителя (`self`) и принимает правый
(`c`). Результат — матрица, которая делает «сначала `c`, потом `self`». В первой строке
`self` — мир родителя, `c` — локальная матрица ребёнка: сначала переводим точку из системы
ребёнка в систему родителя, потом из системы родителя в мир. Во второй строке всё
наоборот, и это ошибка.

### 3.2 Почему порядок вообще важен: пример на бумаге

Возьмём два преобразования: `T` — сдвиг на (5, 0), `R` — поворот на 90°. Применим их к
точке (1, 0) в разном порядке:

| Шаг | `R * T` (сначала T, потом R) | `T * R` (сначала R, потом T) |
|---|---|---|
| старт | (1, 0) | (1, 0) |
| первое действие | T: (1+5, 0) = (6, 0) | R: (0, 1) |
| второе действие | R: (6, 0) поворачиваем → (0, 6) | T: (0+5, 1) = (5, 1) |
| итог | **(0, 6)** | **(5, 1)** |

```
     y                                   y
   6 +  * (0,6)   <- R*T                 |
     |                                   |
     |                                 1 +           * (5,1)  <- T*R
     +---------------> x                 +-----------------> x
```

Результаты совершенно разные. В жизни то же самое: «шаг вперёд, потом поворот налево» и
«поворот налево, потом шаг вперёд» приводят в разные места. Этот пример есть в самотестах
`e0801` — можете проверить им свою функцию.

### 3.3 Умножение двух матриц по шагам

Формулы произведения `P * C` (они есть в шапке `e0801`):

```
a  = P.a*C.a + P.c*C.b        c  = P.a*C.c + P.c*C.d
b  = P.b*C.a + P.d*C.b        d  = P.b*C.c + P.d*C.d
tx = P.a*C.tx + P.c*C.ty + P.tx
ty = P.b*C.tx + P.d*C.ty + P.ty
```

Смысл без зубрёжки: новая ось X — это ось X ребёнка `(C.a, C.b)`, пропущенная через
поворот/масштаб родителя (без сдвига — оси не сдвигаются); новый центр — центр ребёнка
`(C.tx, C.ty)`, пропущенный через родителя целиком (со сдвигом).

Теперь солнечная система: солнце в (100, 100) **повёрнуто на 90°**, планета в (10, 0)
относительно солнца.

```
P = sun    = { a=0, b=1, c=-1, d=0, tx=100, ty=100 }
C = planet = { a=1, b=0, c=0,  d=1, tx=10,  ty=0   }
```

Считаем `P * C` (правильный порядок):

| Поле | Формула | Подстановка | Результат |
|---|---|---|---|
| a | P.a*C.a + P.c*C.b | 0*1 + (−1)*0 | 0 |
| b | P.b*C.a + P.d*C.b | 1*1 + 0*0 | 1 |
| c | P.a*C.c + P.c*C.d | 0*0 + (−1)*1 | −1 |
| d | P.b*C.c + P.d*C.d | 1*0 + 0*1 | 0 |
| tx | P.a*C.tx + P.c*C.ty + P.tx | 0*10 + (−1)*0 + 100 | 100 |
| ty | P.b*C.tx + P.d*C.ty + P.ty | 1*10 + 0*0 + 100 | 110 |

Планета в мире — в точке (100, 110): солнце повернулось, и планета «уехала» с правой
стороны солнца наверх. Именно этого мы и ждём.

А теперь **неправильный** порядок `C * P` (формулы те же, но P и C поменялись ролями):

| Поле | Подстановка | Результат |
|---|---|---|
| tx | C.a*P.tx + C.c*P.ty + C.tx = 1*100 + 0*100 + 10 | 110 |
| ty | C.b*P.tx + C.d*P.ty + C.ty = 0*100 + 1*100 + 0 | 100 |

Планета оказалась в (110, 100) — будто солнце и не поворачивалось.

### 3.4 Почему ошибка «почти работает»

Коварство в слове «почти»: если у родителя нет поворота и масштаба, оба варианта дают
одинаковый перенос. Проверьте сами: при неповёрнутом солнце и `P * C`, и `C * P` дают
(110, 100). Ошибка проявится через месяц, когда художник повернёт корневой объект.
Поэтому в `e0801` тесты специально крутят и масштабируют родителя.

DirectX-конвенция (векторы-строки, `p' = p * M`) переворачивает порядок: там
`world = local * parent`. Выберите одну конвенцию на весь движок и запишите её в
комментарии рядом с типом матрицы.

> **Частые ошибки**
>
> * `local * parent` вместо `parent * local`. Лечится тестом, где родитель повёрнут.
> * При подъёме по предкам в цикле домножать **не с той стороны**. Если вы идёте от узла
>   вверх, у вас уже есть «кусок цепочки снизу» `M = L(parent) * L(node)`; очередной предок
>   должен встать **слева**: `M = L(grandparent) * M`. Нарисуйте цепочку на бумаге и
>   посмотрите, с какой стороны появляется каждый новый множитель.
> * Градусы вместо радиан в `sin`/`cos`.
> * Сравнение float через `==`. Из-за округления `cos(90°)` даёт не 0, а примерно
>   `-4.37e-8`. Сравнивайте с допуском (`near` в тестах) и не удивляйтесь `-0.00`.

### 3.5 Цена наивного подхода

Наивная реализация `world_matrix(i)` из `e0801` поднимается по родителям и перемножает:
O(глубина) на каждый запрос. Если 10 000 объектов, глубина 8 и каждый объект спрашивают
три системы за кадр, получаем 240 000 умножений матриц, большинство — повторные. Нужен кэш.

> **O(…)** («О большое») — грубая оценка, как растёт работа с ростом входа. O(глубина) —
> «число шагов пропорционально глубине дерева», O(N) — «пропорционально числу объектов»,
> O(1) — «не зависит от размера».

**Коротко:** `A * B` = «сначала B, потом A». Мир ребёнка = `мир родителя * local ребёнка`.
Тестируйте с повёрнутым родителем — иначе ошибка порядка невидима.

## 4. Dirty flags: ленивый пересчёт

### 4.1 Интуиция

Представьте бухгалтера, который ведёт итоговую сумму по отделу. Каждый раз, когда кто-то
меняет одну цифру, он мог бы пересчитывать весь отчёт заново — но если цифры меняют
двадцать раз за час, а итог спрашивают раз в день, это глупо. Умный бухгалтер просто
ставит на отчёте пометку «устарел», а пересчитывает его, только когда итог кто-то спросит.

Эта пометка и есть **грязный флаг** (dirty flag): булева переменная «кэш устарел».
«Грязный» — значит, сохранённому значению нельзя верить; «чистый» — можно.

Паттерн «Dirty Flag» подробно описан у Nystrom'а (Game Programming Patterns, глава
«Dirty Flag»), и иерархия трансформаций — его каноничный пример. Идея: world — это кэш,
кэш помечается устаревшим при изменении источника и пересчитывается при чтении. Такой
подход называют **ленивым** (lazy): работа откладывается до момента, когда результат
действительно нужен.

### 4.2 Алгоритм

```
set_local(i):  local[i] = v; mark_dirty(i)       // дёшево, ничего не считает
get_world(i):  if dirty[i]:
                   world[i] = get_world(parent) * local[i]   // рекурсивно чистит предков
                   dirty[i] = false
               return world[i]
```

По строчкам:

* `set_local` только записывает новое значение и вызывает `mark_dirty`. Никаких матриц.
* `get_world` сначала смотрит на флаг. Если узел чистый — сразу отдаёт кэш (самый частый и
  самый дешёвый случай).
* Если грязный — просит мир родителя **тем же самым** `get_world` (рекурсия: родитель,
  если он тоже грязный, сам попросит своего родителя и т.д.), умножает на свой local,
  кладёт результат в кэш и снимает флаг.

### 4.3 Флаг течёт вниз: главный инвариант

Флаг должен распространяться **вниз**: когда двигается родитель, устаревают миры всех
потомков (поезд поехал — пассажиры тоже переместились). Отсюда ключевой инвариант:

> если узел грязный, то все его потомки тоже грязные.

> **Инвариант** — утверждение о данных, которое всегда истинно между операциями. Код
> может опираться на него, а каждая операция обязана его сохранять.

Благодаря ему `mark_dirty` останавливается на уже грязном узле — ниже всё помечено. Без
этой оптимизации геймплей, двигающий корень персонажа пять раз за кадр, пять раз обходит
всё дерево скелета. С ней — один раз плюс четыре проверки флага.

### 4.4 Трассировка на примере

Дерево из четырёх узлов (дети хранятся списком first_child / next_sibling, как в `e0802`):

```
        0 root
        |
        1 body
       / \
  2 arm   3 head
```

Пусть всё чистое. Выполним последовательность операций и посмотрим на флаги
(`D` — dirty, `.` — чистый) и счётчики:

| Шаг | Операция | Посещённые узлы mark_dirty | Флаги 0 1 2 3 | Пересчётов |
|---|---|---|---|---|
| 0 | — | — | `. . . .` | 0 |
| 1 | set_local(1) | 1 → 2 → 3 (все были чистыми, идём вниз) | `. D D D` | 0 |
| 2 | set_local(1) | 1 (уже грязный — сразу выходим) | `. D D D` | 0 |
| 3 | set_local(0) | 0, затем 1 (грязный — выход) | `D D D D` | 0 |
| 4 | get_world(2) | — | `. . . D` | 3 (узлы 0, 1, 2) |
| 5 | get_world(3) | — | `. . . .` | 4 (только узел 3: 1 уже чистый) |
| 6 | get_world(2) | — | `. . . .` | 4 (кэш, ничего не считаем) |

Обратите внимание на шаг 3: `mark_dirty(0)` посетил узел 1, увидел, что тот уже грязный, и
не пошёл к 2 и 3 — по инварианту они и так грязные. На шаге 4 `get_world(2)` «вытащил»
цепочку 0 → 1 → 2 и почистил её, но узел 3 остался грязным: его никто не спрашивал. Это и
есть ленивость.

Посчитайте, что было бы на шаге 2 без раннего выхода: снова 3 посещения. Тысяча вызовов
`set_local(root)` на дереве из N узлов — это `1000 * N` посещений без раннего выхода и
`N + 999` с ним (эта арифметика есть в шапке `e0802`).

### 4.5 Что получаем и чего стоит

Что получаем:

* **Ленивость.** Если объект за кадром никто не читал (он вне экрана, физика спит), его мир
  не пересчитывается вовсе.
* **Объединение изменений.** N изменений до чтения стоят одного пересчёта.

Чего стоит:

* **Ветвления и непредсказуемый доступ.** Каждый `get_world` — проверка флага, возможно
  рекурсия вверх. Читатели разбросаны по кадру, кэш процессора холодный («холодный» —
  нужных данных нет в быстрой памяти процессора, приходится ждать обычную память).
* **Сложность многопоточности.** `get_world` — это *запись* (он обновляет кэш). Два потока,
  читающие мир одного объекта, устраивают **гонку** (data race: два потока одновременно
  трогают одни данные, и хотя бы один пишет — результат непредсказуем). Unity поэтому до
  DOTS требовал обращения к `Transform` только с главного потока; Unreal обновляет
  `ComponentToWorld` в `UpdateComponentToWorld` из игрового потока и затем копирует в
  рендер-поток.
* **«Протухшие» кэши в обход API.** Если кто-то записал `local` напрямую, не вызвав
  `mark_dirty`, баг проявится нерегулярно. Поле должно быть закрыто, изменение — только
  через функцию (в C3 — `@private` или модульные границы).

### 4.6 Вариант с явной фазой обновления

Вариант, который используют многие движки: **dirty flag + явная фаза обновления**. Изменения
лишь помечают узлы (и, например, кладут корень изменённого поддерева в список), а в
определённой точке кадра (после геймплея, перед физикой/рендером) одна функция обновляет
все грязные поддеревья подряд. Чтения в остальное время просто отдают кэш — он может быть
на кадр старым, и это нужно документировать. Unity делает именно так в
`TransformHierarchy` (там есть `TransformChangeDispatch`, собирающий изменённые
иерархии), Godot — через `notification(NOTIFICATION_TRANSFORM_CHANGED)` и отложенную
очередь обновления.

Плюс этого варианта: во время чтения никто ничего не пишет, поэтому читать можно из многих
потоков одновременно. Минус: в середине кадра мир может быть «вчерашним».

> **Частые ошибки**
>
> * Забыть ранний выход в `mark_dirty` — всё работает правильно, но медленно (и тест
>   `e0802` по счётчику посещений это заметит).
> * Сделать ранний выход, но помечать **только сам узел**, а не потомков. Тогда инвариант
>   нарушен: потомок чистый, но его мир устарел, — и ранний выход начинает прятать баги.
> * В `get_world` посчитать мир, но забыть **сохранить** его в кэш или **снять** флаг —
>   тогда каждый вызов пересчитывает заново.
> * Спрашивать мир родителя напрямую из поля `world`, а не через `get_world`: если родитель
>   грязный, вы возьмёте устаревшее значение.

**Коротко:** изменение лишь ставит флаг «устарел» на узел и всё его поддерево; пересчёт
происходит при чтении. Инвариант «грязный ⇒ потомки грязные» позволяет `mark_dirty`
останавливаться на уже грязном узле.

## 5. Плоская иерархия: «родитель раньше ребёнка»

### 5.1 Почему деревья из указателей медленные

Деревья из объектов с указателями `children` — естественны для редактора и ужасны для
**кэша процессора**.

> **Кэш процессора** — маленькая очень быстрая память внутри CPU. Процессор подтягивает в
> неё данные кусками по 64 байта («кэш-линиями»). Если следующие нужные данные лежат рядом
> с предыдущими — они уже в кэше, и чтение почти бесплатно. Если они где-то далеко в
> памяти — **промах кэша**, процессор ждёт сотни тактов.

Каждый узел — отдельная аллокация, обход — прыжки по памяти, `std::vector<Node*>` детей —
ещё одна косвенность. Это как читать книгу, в которой каждая следующая страница лежит в
другой комнате.

Bitsquid/Stingray (Niklas Frykholm, серия «Building a Data-Oriented Entity System» и пост
про scene graph), позже Our Machinery, иерархии костей в любой системе анимации, Unity DOTS
(`LocalToWorldSystem`) делают иначе: иерархия — это **несколько параллельных массивов**
(SoA), отсортированных так, что **родитель всегда стоит раньше ребёнка**.

> **SoA** (structure of arrays, «структура массивов») — вместо массива структур
> `Node[]` храним по отдельному массиву на каждое поле: `parent[]`, `local[]`, `world[]`.
> i-й узел — это i-е элементы всех массивов. Так цикл, которому нужно одно поле, читает
> память подряд и не тащит в кэш ненужные поля.

### 5.2 Один цикл вместо рекурсии

```
 index:   0      1      2      3      4      5
 parent: -1     -1      0      0      1      3
 local:  L0     L1     L2     L3     L4     L5
 world:  W0     W1     W2     W3     W4     W5

 for i in 0..n:
     world[i] = parent[i] < 0 ? local[i] : world[parent[i]] * local[i]
```

Почему это работает? Инвариант `parent[i] < i` гарантирует: когда цикл дошёл до узла `i`,
его родитель уже обработан (он стоит левее), значит `world[parent[i]]` уже посчитан и
актуален. Это как заполнять генеалогическую таблицу: если бабушки всегда записаны раньше
внуков, то, дойдя до внука, вы уже знаете всё про бабушку.

Трассировка с целыми сдвигами (как в `e0803`, где `world = world(parent) + local`):

| i | parent | local | Что берём | world |
|---|---|---|---|---|
| 0 | −1 | (10, 0) | корень: local | (10, 0) |
| 1 | −1 | (0, 50) | корень: local | (0, 50) |
| 2 | 0 | (1, 1) | world[0] + local = (10,0)+(1,1) | (11, 1) |
| 3 | 0 | (2, 0) | world[0] + (2,0) | (12, 0) |
| 4 | 1 | (0, 5) | world[1] + (0,5) | (0, 55) |
| 5 | 3 | (0, 1) | world[3] + (0,1) | (12, 1) |

Ни одной рекурсии: каждая строка таблицы использует только строки выше неё.

Один линейный проход, ноль рекурсии, ноль стека, предсказуемые ветвления, массивы читаются
последовательно (кроме `world[parent[i]]`, но родитель почти всегда «недалеко позади» и
уже в кэше). Для скелета из 100 костей это десятки наносекунд на всё. Можно добавить и
dirty flags: пропускать узлы, чей флаг и флаг родителя сброшены, — в одном проходе флаг
распространяется сам: `dirty[i] |= dirty[parent[i]]`.

**Коротко:** если родитель всегда стоит в массиве раньше ребёнка, мировые трансформации
считаются одним циклом слева направо, без рекурсии.

### 5.3 Плата: поддерживать порядок (и перенумеровывать ссылки)

Плата — **поддерживать порядок**. Когда узлы загружаются в произвольном порядке или
меняют родителя, массивы приходится переставлять. Простейшая стратегия из `e0803` —
**устойчивая сортировка по глубине**.

* **Глубина** узла — сколько шагов вверх до корня (у корня 0, у его детей 1, ...).
  Родитель всегда на 1 мельче ребёнка, поэтому если отсортировать узлы по глубине, все
  родители окажутся раньше детей.
* **Устойчивая** (stable) сортировка — та, что не переставляет между собой элементы с
  одинаковым ключом: если два узла глубины 1 стояли в порядке «arm, head», они так и
  останутся.

Важнейший момент любой перестановки: **все ссылки по индексам становятся неверными**.
Нужна таблица `remap[old] = new`, через которую перенумеровываются `parent` — и всё, что
снаружи хранило индексы.

Разберём пример по шагам. Узлы пришли в «плохом» порядке:

| старый индекс | имя | parent (старый) | глубина |
|---|---|---|---|
| 0 | arm | 2 | 1 |
| 1 | hand | 0 | 2 |
| 2 | body | −1 | 0 |
| 3 | head | 2 | 1 |

Инвариант нарушен: у `arm` (индекс 0) родитель с индексом 2 — стоит *позже*.

**Шаг 1. `order[new] = old`** — какой старый узел встанет на каждое новое место. Берём сначала
все узлы глубины 0 в прежнем порядке, затем глубины 1, затем 2:

```
глубина 0: body(2)
глубина 1: arm(0), head(3)     <- в прежнем порядке: 0 раньше 3
глубина 2: hand(1)

order = [2, 0, 3, 1]
```

**Шаг 2. Обратная таблица `remap[old] = new`** — куда переехал каждый старый узел. Просто
«переворачиваем» order: если `order[new] = old`, то `remap[old] = new`.

| new | order[new] (= old) | значит remap[old] = new |
|---|---|---|
| 0 | 2 | remap[2] = 0 |
| 1 | 0 | remap[0] = 1 |
| 2 | 3 | remap[3] = 2 |
| 3 | 1 | remap[1] = 3 |

```
remap = [1, 3, 0, 2]
```

**Шаг 3. Перекладываем данные и перенумеровываем parent.** Для нового места `new` берём
данные старого узла `order[new]`, а его старого родителя пропускаем через `remap`:

| new | имя | старый parent | новый parent = remap[старый] |
|---|---|---|---|
| 0 | body | −1 | −1 (корень так и остаётся корнем) |
| 1 | arm | 2 | remap[2] = 0 |
| 2 | head | 2 | remap[2] = 0 |
| 3 | hand | 0 | remap[0] = 1 |

Проверяем инвариант: parent = [−1, 0, 0, 1], у каждого не-корня `parent[i] < i`. Готово.

Обратите внимание на ловушку в шаге 3: если перекладывать данные **на месте**, не сделав
копии, вы затрёте старые значения, которые ещё не прочитали. Поэтому сначала копия
(`Hierarchy old = *self;` в `e0803` — структура с массивами фиксированного размера
копируется целиком), потом раскладка из копии.

Две таблицы нужны, потому что они отвечают на разные вопросы: `order` — «кто стоит на
месте new?» (удобно, чтобы заполнять новые места по порядку), `remap` — «куда переехал
old?» (нужно, чтобы исправлять ссылки).

### 5.4 Handles вместо сырых индексов

Поэтому внешний код никогда не должен держать «сырой» индекс узла иерархии: только handle
(глава 03), который через таблицу индирекции отображается в текущий индекс. Ровно так
устроен `SceneGraph` в Bitsquid: пользователь держит `Instance`, а внутренний массив
свободно переупорядочивается.

Как часто происходит переупорядочивание? В игре — редко: смена родителя (подобрал
предмет, сел в машину) — это единичные события за кадр, а не тысячи. Поэтому платить
O(n) за пересортировку при reparent обычно приемлемо, а в критичных случаях можно
переносить поддерево целиком в конец массива (оно остаётся «после» нового родителя, если
родитель стоит раньше) без полной сортировки.

> **Частые ошибки**
>
> * Перенумеровать `parent` через `order` вместо `remap` (или наоборот). Спросите себя:
>   «у меня в руках старый индекс, и я хочу новый» — значит, `remap`.
> * Пропустить через `remap` значение `NO_PARENT` (−1) — это выход за границы массива.
>   Корень надо обработать отдельно.
> * Неустойчивая сортировка: узлы одной глубины перемешались. Иерархия будет корректной,
>   но вывод `e0803` не совпадёт с ожидаемым.
> * Перекладывать на месте без копии.

**Коротко:** порядок «родитель раньше ребёнка» поддерживают сортировкой по глубине. После
любой перестановки все индексы-ссылки надо перевести через `remap[old] = new`, а наружу
отдавать handles.

## 6. Порядок DFS и непрерывные поддеревья

### 6.1 Что такое DFS preorder

**Обход в глубину** (DFS, depth-first search) — способ обойти дерево: заходим в узел, затем
полностью обходим первого ребёнка со всеми его потомками, затем второго ребёнка и т.д.
**Preorder** («прямой порядок») означает, что сам узел записывается **до** своих детей. Это
как читать оглавление книги: «Глава 1, раздел 1.1, подраздел 1.1.1, раздел 1.2, Глава 2…».

Частный случай порядка «родитель раньше ребёнка» — как раз **обход в глубину (preorder)**. У
него есть бонус: всё поддерево узла лежит в массиве **подряд**:

```
          A
        /   \
       B     E
      / \     \
     C   D     F

 index:        0  1  2  3  4  5
 node:         A  B  C  D  E  F
 subtree_end:  6  4  3  4  6  6      поддерево узла i = [i, subtree_end[i])
```

Запись `[i, subtree_end[i])` — **полуоткрытый интервал**: `i` входит, `subtree_end[i]` — нет.
Для B: `[1, 4)` = индексы 1, 2, 3 = B, C, D. Верно — это B и его дети. Для листа C:
`[2, 3)` = только C. `subtree_end[i]` — это «первый индекс **после** поддерева», то есть
место, где начинается следующий «соседний» кусок дерева.

Почему поддерево непрерывно? Потому что DFS, войдя в B, не выходит из него, пока не обойдёт
всех его потомков. Никакой «чужой» узел не может вклиниться в середину.

### 6.2 Что это даёт

* **Пропуск поддерева** за O(1): `i = subtree_end[i]`. Это основа иерархического
  отсечения в `e0806`. Пример: стоим на B (i=1) и решили, что вся ветка B нам не нужна —
  прыгаем на `subtree_end[1] = 4`, то есть сразу к E. C и D даже не смотрим.
* **Удаление/перемещение поддерева** — это `memmove` одного непрерывного диапазона.
* **Обратный проход** (`i` от n-1 до 0) обрабатывает детей раньше родителей — идеально для
  «агрегатов снизу вверх»: границы поддерева (bounding volume), суммарная масса, флаг «есть
  ли в поддереве что-то видимое».

### 6.3 Почему обратный проход «собирает снизу вверх»

В любом порядке «родитель раньше ребёнка» верно и обратное: **ребёнок позже родителя**.
Значит, если идти с конца массива, к моменту, когда мы дошли до узла, все его дети уже
пройдены. Каждый узел, будучи пройденным, «вливает» свой итог в родителя — и когда очередь
доходит до родителя, его итог уже собран.

Пример: посчитаем размер поддерева (число узлов) для дерева выше. Начинаем с `size[i] = 1`
и идём с конца, добавляя `size[i]` к родителю:

| Шаг (i) | Узел | parent | Действие | size A B C D E F |
|---|---|---|---|---|
| старт | | | | 1 1 1 1 1 1 |
| 5 | F | E(4) | size[E] += 1 | 1 1 1 1 2 1 |
| 4 | E | A(0) | size[A] += 2 | 3 1 1 1 2 1 |
| 3 | D | B(1) | size[B] += 1 | 3 2 1 1 2 1 |
| 2 | C | B(1) | size[B] += 1 | 3 3 1 1 2 1 |
| 1 | B | A(0) | size[A] += 3 | 6 3 1 1 2 1 |
| 0 | A | — | корень, некуда вливать | 6 3 1 1 2 1 |

Обратите внимание: когда мы на шаге 1 вливаем B в A, size[B] уже равен 3 — оба ребёнка
успели влиться. А если бы шли **вперёд**, B влился бы в A, когда size[B] ещё был 1.

В `e0806` ровно так же собираются не размеры, а **границы поддерева** (объединение
коробок) — вместо `+=` там `merge`.

Именно так хранятся иерархии в форматах, ориентированных на скорость загрузки (например,
скелеты в glTF после импорта, сцены в cooked-форматах движков): после «выпекания» сцена
загружается одним блоком и сразу готова к линейному обновлению.

**Коротко:** в DFS-порядке поддерево узла `i` — это непрерывный кусок `[i, subtree_end[i])`.
Прыжок `i = subtree_end[i]` пропускает всё поддерево; проход с конца собирает итоги снизу
вверх.

## 7. Граф сцены против плоских структур

В 90-х и 2000-х «граф сцены» (scene graph — OpenInventor, OpenSceneGraph, Ogre, Java3D)
был универсальным ответом: одно дерево, в котором узлы — трансформации, группы, материалы,
переключатели LOD, геометрия. Рендер обходил дерево рекурсивно, накапливая состояние,
отсекая поддеревья по их bounding sphere (ограничивающей сфере — шару, в который целиком
помещается объект).

Почему движки от этого ушли (Tom Forsyth, «Scene Graphs — just say no»; доклады DICE и
Bitsquid про data-oriented design):

* **Одно дерево — несколько несовместимых иерархий.** Трансформационная иерархия (меч в
  руке) не совпадает с пространственной (меч рядом со стеной, а не рядом с корнем
  персонажа), с иерархией состояний рендера (все объекты с одним материалом) и с
  логической (команда, отряд). Дерево, оптимальное для одного, плохо для остальных.
  Аналогия: в библиотеке книги можно расставить по автору, по теме или по размеру полки,
  но не всеми способами сразу. Поэтому заводят несколько каталогов.
* **Рекурсивный обход объектов с виртуальными функциями** — худший паттерн доступа к памяти.
* **Плохая параллельность** — дерево с общим состоянием обхода трудно делить между потоками.

Современный подход — **разделение ответственностей**:

```
  трансформационная иерархия   ->  плоские SoA-массивы, линейный проход (e0803/e0806)
  пространственный индекс      ->  сетка / квадродерево / BVH, отдельная структура (e0804/e0805)
  рендер                        ->  плоский список видимых объектов -> command buffer (глава 09)
  логика                        ->  ECS-запросы (глава 05)
```

При этом **дерево в редакторе** никуда не делось: Godot целиком построен на дереве `Node`,
у Unity — `GameObject`/`Transform`, у Unreal — `USceneComponent` с attach-родителями. Но
это удобная *модель для человека*; внутри (особенно в Unity DOTS, в `FScene` рендера
Unreal, в серверах Godot 4 — `RenderingServer`, `PhysicsServer`) данные раскладываются
плоско и обрабатываются пакетно.

**Коротко:** одно универсальное дерево плохо решает разные задачи. Современные движки
держат отдельную структуру под каждую задачу, а дерево оставляют для редактора.

## 8. Пространственные структуры

Теперь вторая задача. Есть N объектов с bounding boxes; нужно быстро отвечать на запросы
«пересечение с областью», «ближайшие соседи», «луч». Общая идея — разбить пространство или
множество объектов так, чтобы большую часть можно было отбросить одной проверкой.

> **AABB** (axis-aligned bounding box, «коробка, выровненная по осям») — прямоугольник
> (в 3D — параллелепипед), стороны которого параллельны осям координат и который целиком
> содержит объект. Задаётся двумя углами: `(min_x, min_y)` и `(max_x, max_y)`. Его
> любят за то, что проверка пересечения двух AABB — четыре сравнения.
>
> **Bounding volume** (ограничивающий объём) — общее название для простой фигуры (AABB,
> сфера), внутри которой гарантированно лежит сложный объект. Если запрос не задевает
> фигуру, он точно не задевает и объект.

Аналогия для всего раздела: как найти в городе всех людей на одной улице? Можно обойти
всех жителей города и спросить адрес (перебор). А можно сначала взять нужный район, в нём
нужный квартал — и опрашивать только живущих там. Сетка, квадродерево и BVH — три способа
нарезать «город» на «районы».

### 8.0 Подготовка: когда пересекаются два отрезка и две коробки

Вся эта глава держится на одной проверке. Два отрезка на числовой прямой `[a1, a2]` и
`[b1, b2]` (концы включительно) пересекаются, если **ни один не лежит целиком левее
другого**:

```
  пересекаются:        a1-------a2
                              b1--------b2

  НЕ пересекаются:     a1----a2
                                  b1----b2      (a2 < b1: A целиком левее)
```

Формула: `a1 <= b2 && b1 <= a2`. Проверим на числах:

| A | B | a1 <= b2 | b1 <= a2 | Пересекаются? |
|---|---|---|---|---|
| [0, 5] | [3, 9] | 0 <= 9 да | 3 <= 5 да | да |
| [0, 5] | [5, 9] | 0 <= 9 да | 5 <= 5 да | да (касаются в точке 5) |
| [0, 5] | [6, 9] | да | 6 <= 5 нет | нет |
| [7, 9] | [0, 5] | 7 <= 5 нет | да | нет |

Две коробки (AABB) пересекаются, если пересекаются их «тени» на ось X **и** на ось Y —
ровно это делает `Box.overlaps` в `e0806`. Точка `(x, y)` лежит в прямоугольнике, если
`min_x <= x <= max_x` и `min_y <= y <= max_y`.

Ещё одна мелочь, на которой спотыкаются: границы бывают **включительные** `[x, x+size-1]` и
**полуоткрытые** `[x, x+size)`. Для целых чисел это одно и то же множество. Квадрат узла
квадродерева в `e0805` задан как `[x, x+size)`, а сравнивать с запросом удобнее
включительно — `[x, x+size-1]`. Не перепутайте, иначе потеряете точки ровно на границе.

**Коротко:** отрезки пересекаются, когда `a1 <= b2 && b1 <= a2`; коробки — когда это верно
по обеим осям.

### 8.1 Равномерная сетка

#### Идея

Мир делится на клетки размера `CELL`; объект попадает в клетку (или клетки, если он
большой) по координатам. Запрос перебирает только задетые клетки.

```
  +----+----+----+----+
  |  . |    |  ..|    |       запрос [###] задевает 4 клетки,
  +----+----+-[##+##]-+       проверяем только объекты в них
  |    |  . | [##+##] |
  +----+----+----+----+
```

Аналогия — шкаф с ящиками, подписанными по алфавиту. Чтобы найти носки на букву «Н», вы
открываете один ящик, а не перебираете весь шкаф.

Номер клетки по координате — целочисленное деление: `cx = x / CELL`. При `CELL = 32` точка
с `x = 70` лежит в столбце `70 / 32 = 2`. В 2D клетки нумеруют построчно, как буквы на
странице: `cell = cy * GRID_W + cx` (сначала целые строки над нами, потом позиция в
строке). При `GRID_W = 8` клетка `(cx=2, cy=1)` имеет номер `1*8 + 2 = 10`.

Плюсы: O(1) вставка, тривиальная реализация, отличная константа (каждая операция очень
дешёвая), легко распараллелить. Минусы: один размер клетки на всех. Мелкие клетки — много
пустой памяти и большие объекты в десятках клеток; крупные — толпа в одной клетке.

#### Компактное хранение: сортировка подсчётом

Хранение. «List в каждой клетке» — тысячи аллокаций. В `e0804` мы делаем **компактную
сетку через сортировку подсчётом** (так строят broadphase в физике частиц, спатиал-хеш в
SPH-жидкостях, а на GPU — тайловый light culling в Forward+):

```
  1) count[cell]++ для каждого объекта
  2) start = exclusive prefix sum(count)
  3) entries[start[cell] + k] = id
```

Аналогия: в классе 30 учеников надо рассадить по рядам в один длинный список «сначала все
из ряда 0, потом из ряда 1…». Сначала **считаем**, сколько учеников в каждом ряду. Потом
вычисляем, **с какого места** списка начинается каждый ряд. Потом раскладываем учеников
по местам.

**Префиксная сумма** (prefix sum) — массив «сумм всех предыдущих элементов».
**Exclusive** («исключающая») — без текущего элемента: `start[c]` = сумма `count[0..c)`.
Удобно делать массив `start` на один элемент длиннее числа клеток: тогда `start[CELLS]` —
общее число объектов, и содержимое любой клетки — `entries[start[c] .. start[c+1])` без
особых случаев для последней клетки.

Вот префиксная сумма как настоящая программа на C3 (проверено на c3c 0.8.5):

```c3
import std::io;

fn void main()
{
    int[5] count = { 2, 0, 3, 1, 0 };    // сколько объектов в клетках 0..4
    int[6] start;                        // на один элемент больше, чем клеток
    start[0] = 0;
    for (int c = 0; c < 5; c++)
    {
        start[c + 1] = start[c] + count[c];
    }
    foreach (s : start) io::printf("%d ", s);
    io::printn();
}
```

Программа печатает `0 2 2 5 6 6`. Читаем: клетка 0 занимает места `[0, 2)`, клетка 1 —
`[2, 2)` (пусто), клетка 2 — `[2, 5)`, клетка 3 — `[5, 6)`, клетка 4 — `[6, 6)` (пусто).
Последнее число 6 — всего объектов. Каждый шаг цикла берёт предыдущий итог и добавляет
`count` текущей клетки.

#### Полный пример по шагам (1D)

Для простоты — одномерный мир `[0, 40)`, `CELL = 10`, значит 4 клетки. Шесть объектов:

| id | x | клетка = x / 10 |
|---|---|---|
| 0 | 25 | 2 |
| 1 | 3 | 0 |
| 2 | 27 | 2 |
| 3 | 14 | 1 |
| 4 | 8 | 0 |
| 5 | 22 | 2 |

**Шаг 1. Подсчёт:** `count = [2, 1, 3, 0]` (в клетке 0 — id 1 и 4, в клетке 1 — id 3, …).

**Шаг 2. Префиксная сумма:** `start = [0, 2, 3, 6, 6]`.

**Шаг 3. Раскладка.** Нужно помнить, сколько объектов уже положили в каждую клетку (это и
есть `k` из формулы). Заведём «курсоры» — для каждой клетки следующее свободное место; в
начале курсор клетки равен её `start`:

| Объект | Клетка | Курсор клетки до | Пишем | Курсоры после (кл. 0 1 2 3) |
|---|---|---|---|---|
| — | | | | 0 2 3 6 |
| id 0 | 2 | 3 | entries[3] = 0 | 0 2 4 6 |
| id 1 | 0 | 0 | entries[0] = 1 | 1 2 4 6 |
| id 2 | 2 | 4 | entries[4] = 2 | 1 2 5 6 |
| id 3 | 1 | 2 | entries[2] = 3 | 1 3 5 6 |
| id 4 | 0 | 1 | entries[1] = 4 | 2 3 5 6 |
| id 5 | 2 | 5 | entries[5] = 5 | 2 3 6 6 |

Итог:

```
 entries: [ 1  4 | 3 | 0  2  5 | ]
            кл.0  кл.1  кл.2    кл.3 (пусто)
```

Клетка 2 = `entries[start[2] .. start[3])` = `entries[3..6)` = id 0, 2, 5. Верно!

Где взять память под курсоры? Можно отдельным массивом, а можно схитрить: после того как
`start` посчитан, массив `count` больше не нужен — его можно обнулить и использовать как
«сколько уже положили» (тогда место = `start[c] + count[c]`).

**Запрос.** Ищем объекты с `x` в `[15, 30]`. Клетки: от `15 / 10 = 1` до `30 / 10 = 3`.
Перебираем объекты клеток 1, 2, 3: id 3 (x=14 — мимо!), id 0 (25, да), id 2 (27, да),
id 5 (22, да). Проверено 4 объекта вместо 6, найдено 3. Заметьте: id 3 лежит в задетой
клетке, но сам не попадает в запрос — поэтому точная проверка каждого кандидата
**обязательна**. Клетка лишь говорит «может быть здесь», а не «точно здесь».

Перестройка O(N + cells) за кадр, ноль аллокаций, содержимое каждой клетки в памяти подряд.
Это часто быстрее инкрементального перемещения объектов между клетками — особенно когда
двигается большинство объектов (частицы, толпы).

#### Пространственный хеш

Если мир бесконечный или разреженный — **пространственный хеш**: `hash(cx, cy) % TABLE`
вместо `cy * W + cx`. Коллизии хеша дают лишние кандидаты, но не ошибки (точная проверка
всё равно выполняется).

> **Хеш** — функция, превращающая значение (здесь пару координат клетки) в число
> из ограниченного диапазона. **Коллизия хеша** — когда двум разным клеткам выпало одно и
> то же число: их объекты попадут в один «ящик».

> **Частые ошибки (сетка)**
>
> * Забыть обнулить `count` перед подсчётом — после второго `build` числа удвоятся.
> * Раскладывать по `start[c]` без `+ k` — все объекты клетки запишутся в одно место.
> * Испортить `start`, используя его же как курсор, и потом читать как начало клеток.
> * Считать клетки запроса делением без ограничения: координата вне мира даст клетку за
>   пределами массива. В `e0804` для этого есть `cell_coord`, который «прижимает» номер к
>   краю сетки.
> * Не проверять каждый объект точно — в результат попадут лишние.

**Коротко:** сетка раскладывает объекты по клеткам; компактная сетка строится сортировкой
подсчётом (подсчёт → префиксная сумма → раскладка) и хранит всё в одном массиве.

### 8.2 Квадродерево и октодерево

#### Идея

Квадродерево (2D) и октодерево (3D) адаптируются к плотности: узел делится на 4 (8)
квадрантов, когда в нём слишком много объектов (`e0805`). Где пусто — дерево мелкое, где
густо — глубокое.

> **Квадрант** — одна из четырёх равных четвертей квадрата. **Лист** — узел без детей
> (в нём лежат сами точки). **Внутренний узел** — узел с детьми (точек не хранит, только
> направляет поиск вниз).

Аналогия — карта в навигаторе: пока вы смотрите на всю страну, город — одна точка; когда
приближаете, область делится на всё более мелкие плитки, но только там, где есть что
показать. Над океаном плитки так и остаются крупными.

#### Пример split по шагам

Мир 16x16, `CAP = 2` (лист делится, когда в нём больше двух точек), y растёт вниз, как на
экране. Квадранты нумеруются битами, как в `e0805`: бит 0 — правая половина, бит 1 — нижняя.

```
   номер квадранта k:     правая? (бит 0)   нижняя? (бит 1)
        0                      нет               нет
        1                      да                нет
        2                      нет               да
        3                      да                да
```

Вставляем точки A(1,1), B(3,2), C(12,3), D(2,6).

1. A и B попадают в корень (узел 0, квадрат [0,16)). В нём 2 точки — не больше CAP, ничего
   не делаем.
2. C попадает в корень — теперь 3 > 2. **Split корня.** Половина `half = 16/2 = 8`. Создаём
   4 ребёнка подряд (узлы 1..4) и раздаём точки:

   | Точка | x >= 0+8? | y >= 0+8? | k | Ребёнок |
   |---|---|---|---|---|
   | A(1,1) | нет | нет | 0 | узел 1: [0,8)x[0,8) |
   | B(3,2) | нет | нет | 0 | узел 1 |
   | C(12,3) | да | нет | 1 | узел 2: [8,16)x[0,8) |

   Корень становится внутренним: `first_child = 1`, точек в нём больше нет.

3. D(2,6): спускаемся от корня. В корне `x=2 < 8`, `y=6 < 8` → квадрант 0 → узел 1. Узел 1 —
   лист, кладём туда: теперь A, B, D = 3 > 2. **Split узла 1** (`half = 4`, дети — узлы 5..8):

   | Точка | x >= 0+4? | y >= 0+4? | k | Ребёнок |
   |---|---|---|---|---|
   | A(1,1) | нет | нет | 0 | узел 5: [0,4)x[0,4) |
   | B(3,2) | нет | нет | 0 | узел 5 |
   | D(2,6) | нет | да | 2 | узел 7: [0,4)x[4,8) |

Итоговая картинка:

```
   0   4   8          16
 0 +---+---+-----------+
   |A B|   |           |
   | 5 | 6 |     C     |
 4 +---+---+     2     |
   | D |   |           |
   | 7 | 8 |           |
 8 +---+---+-----------+
   |       |           |
   |   3   |     4     |
   |       |           |
16 +-------+-----------+
```

И массив узлов (все узлы в одном списке, дети каждого узла — четыре подряд):

| узел | квадрат (x, y, size) | depth | first_child | точки |
|---|---|---|---|---|
| 0 | 0,0,16 | 0 | 1 | — (внутренний) |
| 1 | 0,0,8 | 1 | 5 | — (внутренний) |
| 2 | 8,0,8 | 1 | NONE | C |
| 3 | 0,8,8 | 1 | NONE | — |
| 4 | 8,8,8 | 1 | NONE | — |
| 5 | 0,0,4 | 2 | NONE | A, B |
| 6 | 4,0,4 | 2 | NONE | — |
| 7 | 0,4,4 | 2 | NONE | D |
| 8 | 4,4,4 | 2 | NONE | — |

**Запрос** прямоугольника `[10, 15] x [0, 5]`: корень пересекается → заходим в детей.
Узел 1 `[0,7]x[0,7]` — по X `0 <= 15` и `10 <= 7`? нет → **весь узел 1 с поддеревом
отброшен одной проверкой** (точки A, B, D даже не смотрим). Узел 2 `[8,15]x[0,7]`
пересекается — проверяем C(12,3): попадает. Узлы 3 и 4 (`y` от 8) мимо. Итого посещено
4 узла + корень, проверена 1 точка.

#### Хранение точек: интрузивный список

В `e0805` точки листа хранятся **интрузивным односвязным списком**: у листа есть `head`
(первая точка), а у каждой точки — `next[id]` (следующая точка того же листа или NONE).
«Интрузивный» — потому что ссылка «следующий» хранится не в отдельном узле списка, а прямо
в данных об объекте (в общем массиве `next`). Ноль аллокаций на точку.

```
  лист 5:  head = B  ->  next[B] = A  ->  next[A] = NONE
```

Добавление в начало списка: `next[id] = head; head = id`. Тонкость: при раздаче точек из
списка детям вы **меняете** `next[id]` (точка вставляется в чужой список). Если сначала
вставить, а потом прочитать `next[id]`, чтобы перейти к следующей точке, вы пойдёте уже по
списку ребёнка. Запоминайте «следующего» **до** вставки.

#### Практические детали, которые важнее теории

* **Узлы в пуле с индексами**, а не `new Node` с указателями; 4 ребёнка подряд — достаточно
  хранить `first_child`. Это сразу и компактнее, и дружелюбнее к кэшу, и легко сериализуется.
* **Ограничение глубины.** Несколько объектов в одной точке иначе делили бы дерево
  бесконечно (сколько ни дели квадрат, три точки с одинаковыми координатами всегда попадут
  в один квадрант). Лист на максимальной глубине просто хранит сколько угодно объектов.
* **Объекты с размером.** Точку легко положить в один лист. Объект с AABB может пересекать
  границы квадрантов. Варианты: класть в наименьший узел, целиком его содержащий (так
  делает «loose» дерево, но объект на границе корня застревает в корне); класть во все
  пересекаемые листья (дубликаты, нужна дедупликация результатов); **loose octree**
  (Ulrich, Game Programming Gems 1) — узлы с «раздутыми» в 2 раза границами, и любой объект
  размером не больше узла помещается ровно в один узел своего уровня.
* **Движущиеся объекты** — главная боль деревьев: удалить и вставить заново, с возможным
  слиянием опустевших узлов. Для динамики чаще выбирают сетку или BVH с «толстыми» AABB.

Октодеревья хорошо подходят для статики, вокселей (SVO — sparse voxel octree, разреженное
октодерево вокселей), разреженных полей освещения.

> **Частые ошибки (квадродерево)**
>
> * Держать указатель `QNode*` на элемент `List`, а потом делать `push` — список может
>   переехать в другую память, и указатель повиснет (подробно — раздел 10).
> * Портить `next[id]` до того, как прочитали следующего в списке.
> * После split все точки ушли в одного ребёнка, и он тоже переполнен — его надо делить
>   дальше (с учётом MAX_DEPTH).
> * Перепутать биты квадранта (правая/нижняя) или считать половину от 0, а не от `n.x`.
> * В запросе забыть вернуть/протащить счётчик найденных `n` из рекурсивных вызовов.

**Коротко:** квадродерево делит квадрат на 4 только там, где тесно. Запрос спускается лишь
в узлы, пересекающие область, и отбрасывает остальные поддеревья целиком.

### 8.3 BVH — иерархия ограничивающих объёмов

Сетка и квадродерево делят **пространство**. BVH (bounding volume hierarchy) делит
**множество объектов**: каждый узел хранит AABB, охватывающий всех потомков; листья —
объекты. Объект ровно в одном листе, дубликатов нет; узлы могут перекрываться.

Аналогия: коробки с вещами при переезде. Мелкие вещи лежат в коробках, коробки — в больших
коробках. Если большая коробка не та, в маленькие вы не заглядываете. При этом коробки
могут стоять вплотную и даже «налезать» друг на друга — главное, что каждая вещь лежит
ровно в одной.

```
            [ AABB всех ]
            /           \
     [AABB A,B]       [AABB C,D,E]
      /     \          /        \
     A       B       C       [AABB D,E]
                               /    \
                              D      E
```

Где используется:

* **Трассировка лучей** — BVH стандарт де-факто (DXR/Vulkan RT строят его в драйвере,
  Embree на CPU). Построение — SAH (surface area heuristic: эвристика, выбирающая разбиение
  с наименьшей ожидаемой стоимостью поиска по площадям коробок).
* **Динамический broadphase** — Box2D `b2DynamicTree`, Bullet `btDbvt`: инкрементальный AABB-
  tree с «толстыми» (fat) AABB: объект пересоздаёт лист только когда вылез за запас.
  Вставка выбирает соседа по минимальному росту площади, дерево балансируется вращениями.
  (Broadphase — «грубая фаза» физики: быстро найти пары объектов, которые *могут*
  столкнуться; подробнее в главе 11.)
* **Отсечение статики** — построенный офлайн BVH сцены.

Иерархия трансформаций с границами поддеревьев из `e0806` — частный случай BVH, где
структура дерева задана не пространством, а логикой сцены. Работает, пока логическая
иерархия пространственно компактна (здания района лежат рядом). Если персонаж бегает по
всей карте, а родитель у него — «корень уровня», граница корня огромна и ничего не
отсекает. Поэтому движки строят отдельный пространственный индекс, а не полагаются на
трансформационное дерево.

**Коротко:** BVH группирует объекты в вложенные коробки. Каждый объект ровно в одном листе;
непопавшая коробка отбрасывает всё своё содержимое.

### 8.4 Как выбрать

| Структура | Вставка/перемещение | Запрос | Неравномерная плотность | Где |
|---|---|---|---|---|
| Перебор (SIMD) | O(1) | O(N) | всё равно | до ~1–5 тыс. объектов это честно быстро! |
| Сетка / хеш | O(1) | O(клеток + кандидатов) | плохо | частицы, толпы, 2D-игры, broadphase |
| Квадро/октодерево | O(log N) | O(log N + k) | хорошо | статика, большие открытые миры |
| BVH (динамический) | O(log N) | O(log N + k) | хорошо | физика, лучи, отсечение |

(`k` — число найденных объектов; `log N` — «сколько раз можно поделить N пополам», для
миллиона это около 20.)

Не забывайте первую строку. Перебор массива AABB в SoA с SIMD проверяет 4–8 коробок за
инструкцию, без промахов кэша и без ветвлений. (**SIMD** — инструкции процессора,
обрабатывающие сразу несколько чисел за раз.) Frostbite (доклад Daniel Collin, «Culling the
Battlefield», GDC 2011) заменил иерархическую структуру отсечения на **линейный перебор**
плоских массивов сфер, разбитых по ячейкам грубой сетки, — и стал быстрее в разы. Сначала
измеряйте.

**Коротко:** маленькие сцены — перебор; равномерная толпа — сетка; неравномерная статика —
дерево; динамика и лучи — BVH. И всегда измеряйте.

## 9. Отсечение (culling)

### 9.1 Виды отсечения

Отсечение — отбрасывание объектов, которые точно не повлияют на картинку, до отправки на
GPU. Аналогия: фотограф не наводит свет на людей, стоящих у него за спиной. Виды, от
дешёвого к дорогому:

1. **Frustum culling** — объект вне пирамиды видимости камеры. **Frustum** (усечённая
   пирамида) — область пространства, которую видит камера: от ближней плоскости до
   дальней, расширяясь в стороны.

   ```
          дальняя плоскость
        +-------------------+
         \                 /
          \   видно       /     объект X снаружи — не рисуем
           \             /   X
            +-----------+
            ближняя плоскость
                 [камера]
   ```

   В 3D пирамида задаётся шестью плоскостями; AABB проверяется против каждой (тест
   «ближайшей/дальней вершины» или «центр + проекция полуразмеров на нормаль»). В 2D и в
   наших упражнениях — пересечение с прямоугольником вида.
2. **Distance / detail culling** — слишком далёкие или крошечные на экране (screen size
   culling) объекты. Часто совмещается с выбором LOD (level of detail — упрощённые версии
   модели для дальних расстояний).
3. **Occlusion culling** — объект заслонён другими. Офлайн: PVS (potentially visible sets) —
   id Tech 1–3 разбивали уровень BSP-деревом и для каждого листа заранее считали видимые
   листья; порталы (Unreal 1, Doom 3) для индорных уровней. Онлайн: software-растеризация
   окклюдеров в маленький буфер глубины (Frostbite, Intel Masked Occlusion Culling), Hi-Z
   на GPU с данными прошлого кадра, GPU-driven отсечение в compute (Unreal Nanite,
   «two-pass occlusion culling»).

**Коротко:** не рисуем то, что вне камеры, слишком далеко или чем-то закрыто. Самое простое
и важное — frustum culling.

### 9.2 Иерархическое отсечение: трассировка по шагам

Иерархическое отсечение в `e0806` иллюстрирует общий принцип: проверяем границу группы,
и если она мимо — отбрасываем группу целиком одной проверкой.

Возьмём сцену в DFS-порядке (как в шапке `e0806`, координаты придуманы для примера). У групп
(city, distA, distB) своей геометрии нет — пустой box. Здания — коробки 4x4.

| i | узел | parent | local_pos | world_pos | world_box (x; y) | subtree_end |
|---|---|---|---|---|---|---|
| 0 | city | −1 | (0,0) | (0,0) | пусто | 7 |
| 1 | distA | 0 | (0,0) | (0,0) | пусто | 5 |
| 2 | bldg | 1 | (10,10) | (10,10) | [10..14; 10..14] | 4 |
| 3 | lamp | 2 | (5,0) | (15,10) | [15..16; 10..11] | 4 |
| 4 | bldg | 1 | (30,10) | (30,10) | [30..34; 10..14] | 5 |
| 5 | distB | 0 | (200,0) | (200,0) | пусто | 7 |
| 6 | bldg | 5 | (10,10) | (210,10) | [210..214; 10..14] | 7 |

**Проход 1 (вперёд)** дал столбцы world_pos и world_box (сдвиг родителя + свой сдвиг —
как в разделе 5.2).

**Проход 2 (назад)** собирает `sub_box` — коробку всего поддерева. Начинаем с
`sub_box[i] = world_box[i]` и идём с конца, вливая каждый узел в родителя:

| Шаг i | Вливаем в | Результат у родителя |
|---|---|---|
| 6 | distB(5) | sub[5] = [210..214; 10..14] |
| 5 | city(0) | sub[0] = [210..214; 10..14] |
| 4 | distA(1) | sub[1] = [30..34; 10..14] |
| 3 | bldg(2) | sub[2] = [10..16; 10..14] (здание + фонарь) |
| 2 | distA(1) | sub[1] = [10..34; 10..14] |
| 1 | city(0) | sub[0] = [10..214; 10..14] |
| 0 | — | корень |

Пустой box кодируется как `min > max` (`EMPTY` в `e0806`: min = int::max, max = int::min).
Почему это удобно: объединение с ним (`min` от минимумов, `max` от максимумов) ничего не
меняет, а пересечение с чем угодно всегда ложно — никаких `if (empty)` в коде.

**Проход 3 (отсечение).** Вид камеры `[-100..-50; 0..50]` (слева от всего):

| i | Проверка | Результат | Действие | tests |
|---|---|---|---|---|
| 0 | sub[0] против вида | мимо | i = subtree_end[0] = 7 → конец | 1 |

Одна проверка вместо четырёх (перебор проверил бы все 4 здания). Вид `[200..250; 0..50]`:

| i | Проверка | Результат | Действие | tests |
|---|---|---|---|---|
| 0 | sub[0] = [10..214] | задели | своя коробка пуста → i = 1 | 1 |
| 1 | sub[1] = [10..34] | мимо | i = subtree_end[1] = 5 (прыжок через 2, 3, 4) | 2 |
| 5 | sub[5] | задели | своя коробка пуста → i = 6 | 3 |
| 6 | sub[6], потом world_box[6] | задели оба | видим узел 6 | 5 |

А вот вид `[0..50; 0..50]`, где видно почти всё: узлы 0 и 1 — по одной проверке, 2, 3, 4 —
по две (sub_box и свой box), на узле 5 — промах и прыжок. Итого 1+1+2+2+2+1 = 9 проверок,
хотя перебор четырёх зданий обошёлся бы в 4.

Обратите внимание на вывод упражнения: когда видно всё, иерархия делает *больше* проверок,
чем перебор (лишние проверки групп). Это нормальная цена; иерархия выигрывает, когда видна
малая доля сцены, — а в играх с большим миром так почти всегда.

### 9.3 Что дальше

Результат отсечения — **плоский список видимых объектов** (индексы или handles),
который дальше превращается в команды рендера с ключами сортировки (глава 09). В
многопоточном движке отсечение — одна из первых задач, которую распараллеливают: массив
объектов делится на куски, каждый поток пишет свой список, списки склеиваются.

> **Частые ошибки (отсечение)**
>
> * После прыжка `i = subtree_end[i]` ещё и сделать `i++` — пропустите следующий узел.
> * Идти во втором проходе вперёд: родитель вольёт в себя детей раньше, чем те соберут
>   своих.
> * Вливать в родителя `world_box` ребёнка вместо его `sub_box` — потеряете внуков.
> * Добавить в результат группу с пустой коробкой.
> * Пропустить пустую коробку через `offset`: `int::max + 10` переполнится. В `e0806`
>   `Box.offset` уже обходит это, используйте его.

**Коротко:** коробка поддерева, собранная проходом с конца, позволяет одним сравнением
отбросить целую ветку сцены прыжком `i = subtree_end[i]`.

  родителя.
* **Висячие указатели на элементы динамических массивов.** `QNode* n = &nodes[i];` затем
  `nodes.push(...)` — и `n` может указывать в освобождённую память. В `e0805` это ловушка
  в `split`. Берите копию или индекс.

  Почему так: `List` хранит элементы в одном куске памяти. Когда место кончается, `push`
  выделяет кусок побольше, копирует туда всё и освобождает старый. Указатель продолжает
  смотреть в старый, уже освобождённый кусок. Копия же живёт сама по себе, а индекс
  остаётся верным в любом куске (проверено на c3c 0.8.5):

  ```c3
  import std::io;
  import std::collections::list;

  struct Item { int value; }

  fn void main()
  {
      List{Item} items;
      defer items.free();
      items.push({ 1 });

      Item copy = items[0];          // копия: живёт сама по себе
      int idx = 0;                   // индекс: переживает перевыделение

      for (int i = 0; i < 100; i++) items.push({ i });   // List может переехать

      io::printfn("copy=%d by_index=%d", copy.value, items[idx].value);
  }
  ```

  Программа печатает `copy=1 by_index=1`. Если бы мы взяли `Item* p = &items[0]` до цикла и
  прочитали `p.value` после, получили бы мусор или падение — и, что хуже, не всегда:
  только когда `push` действительно перевыделил память.
* **Индексы после перестановки.** Любая сортировка иерархии инвалидирует внешние индексы.
  Наружу — только handles.
* **Обновление в середине кадра.** Если физика читает world до фазы обновления иерархии, а
  рендер — после, они видят разные миры. Определите явный порядок фаз кадра (глава 01) и
  точку, где мировые трансформации консистентны.
* **Точность float на больших координатах.** На расстоянии 10 км от начала координат
  float даёт шаг около миллиметра, на 100 км — сантиметры: дрожание камеры и
  анимаций. Решения: перенос начала координат (floating origin, Unity/KSP), относительные
  к камере координаты при рендере, double для мировых позиций (Unreal 5 Large World
  Coordinates, Star Citizen).

  Откуда это: float хранит примерно 7 значащих десятичных цифр. Число 10 000,001 (10 км и
  1 мм, в метрах) — это уже 9 цифр, и float вынужден округлить его до ближайшего
  представимого значения; соседние представимые числа около 10 000 отстоят друг от друга
  примерно на 0,001. Чем дальше от нуля, тем «крупнее шаг сетки» float.
* **Отрицательный масштаб** меняет ориентацию треугольников (winding) — рендер должен
  переключать culling граней по знаку детерминанта мировой матрицы. (В 2D детерминант
  нашей матрицы — `a*d - b*c`; он показывает, во сколько раз меняется площадь, а его знак —
  «отзеркалено или нет». Для поворота он 1, для зеркала по X `a=-1, d=1` он −1.)
* **Слишком мелкие клетки сетки** для больших объектов: объект в 100 клетках — 100 записей
  и дубликаты в запросах.
* **Квадродерево без лимита глубины** — бесконечная рекурсия на совпадающих координатах.

## 11. Как это устроено в реальных движках

* **Unreal Engine.** `USceneComponent` хранит `RelativeLocation/Rotation/Scale` и кэш
  `ComponentToWorld` (`FTransform`); attach-иерархия компонентов; `UpdateComponentToWorld`
  рекурсивно обновляет детей при изменении (не лениво, но с флагами для пропуска). Рендер
  живёт в отдельном `FScene` с плоскими массивами примитивов (`FPrimitiveSceneInfo`),
  отсечение — параллельный перебор bounds + occlusion queries/Hi-Z, в UE5 — Nanite с
  иерархией кластеров на GPU.
* **Unity.** `Transform` с иерархией; внутренне `TransformHierarchy` хранит иерархию
  плоскими массивами, отдельными для каждого корня (поэтому совет «держите глубокие
  иерархии под разными корнями» влияет на параллельность обновления через
  `TransformAccessArray`). Отсечение — `CullingGroup`, umbra для occlusion.
* **Godot 4.** Дерево `Node` для пользователя; `Node3D` кэширует глобальную трансформацию с
  dirty-флагом; рендер-сервер держит свои плоские структуры и использует
  `DynamicBVH` для отсечения.
* **Bitsquid/Stingray.** `SceneGraph` как плоские массивы local/world/parent с порядком
  «родитель раньше ребёнка», handles-`Instance` наружу; отсечение по плоским массивам.
* **id Tech.** BSP + PVS + порталы в классике; в id Tech 6/7 — GPU-driven рендер с отсечением
  кластеров в compute.
* **Frostbite.** «Culling the Battlefield»: грубая сетка + линейный SIMD-перебор + software
  occlusion.

Обратите внимание на общий мотив: снаружи — удобное дерево для человека, внутри — плоские
массивы и пакетная обработка. Ровно это вы и строите в упражнениях.

## 12. Как это связано с упражнениями

### `e0801_transform_hierarchy`

* **Что просят:** написать `Affine2.mul` (композицию), `Affine2.apply` (применение к точке) и
  `world_matrix` (подъём по родителям с перемножением).
* **Перечитать:** разделы 2.2–2.3 (что значат шесть чисел), 3.2–3.3 (порядок и пример
  перемножения).
* **На что обратить внимание:** в `mul` легко перепутать, где `self`, а где `c` — сверьте
  с формулами для `P * C`, подставив `P = self`. В `world_matrix` вы идёте снизу вверх —
  перечитайте в «Частых ошибках» раздела 3.4 пункт о том, с какой стороны появляется
  каждый новый множитель, и выпишите цепочку для трёх узлов на бумаге. Если тест про
  «повёрнутое солнце» падает, а про неповёрнутое проходит — почти наверняка порядок.
  Пересчитайте на бумаге таблицу из раздела 3.3.

### `e0802_dirty_flags`

* **Что просят:** `Scene.mark_dirty` (пометить узел и поддерево, с ранним выходом) и
  `Scene.get_world` (ленивый пересчёт через кэш).
* **Перечитать:** раздел 4 целиком, особенно таблицу трассировки 4.4.
* **На что обратить внимание:** `mark_visits` увеличивается на **каждый** вызов, включая
  ранний выход (эта строка уже стоит в начале функции — не убирайте её). Ранний выход
  проверяется **до** пометки: если узел уже грязный — выходим. `recomputes` растёт только
  при реальном пересчёте, а не при каждом вызове `get_world` (сейчас в заготовке он
  увеличивается всегда). Мир родителя берите через `get_world`, а не из поля.

### `e0803_flat_hierarchy`

* **Что просят:** `update_world` (один линейный проход) и `sort_by_depth` (устойчивая
  перестановка с перенумерацией `parent`).
* **Перечитать:** разделы 5.2 и 5.3 — особенно пример с `order` и `remap`.
* **На что обратить внимание:** глубину уже считает `self.depth(i)`. Устойчивость легко
  получить без библиотечной сортировки: перебирайте глубину `d = 0, 1, 2, …` и на каждой
  глубине проходите узлы в старом порядке. Сделайте копию структуры перед раскладкой.
  `NO_PARENT` не пропускайте через `remap`.

### `e0804_uniform_grid`

* **Что просят:** `Grid.build` (сортировка подсчётом) и `Grid.query` (обход задетых клеток с
  точной проверкой каждой точки).
* **Перечитать:** раздел 8.0 (точка в прямоугольнике) и 8.1 (пример по шагам с курсорами).
* **На что обратить внимание:** `start` длиной `CELLS + 1`, тест проверяет
  `start[CELLS] == N`. Обнуляйте `count` в начале `build`. Для раскладки нужен счётчик
  «сколько уже положено в клетку». В запросе используйте `cell_coord` для обоих углов,
  клетки — включительно; `self.tested++` на **каждую** проверенную точку, даже не
  попавшую. Границы прямоугольника — включительно.

### `e0805_quadtree`

* **Что просят:** `split`, `insert`, `query`.
* **Перечитать:** раздел 8.2 (пример split по шагам, интрузивный список), 8.0 (границы
  квадрата узла), 10 (висячие указатели).
* **На что обратить внимание:** в `split` сначала **копия** узла (`QNode n = ...`), потом
  `push` детей. Перед вставкой точки в ребёнка запомните, кто следующий в старом списке.
  После раздачи проверьте, не переполнен ли какой-то ребёнок. В `query` счётчик `visited`
  растёт на каждый посещённый узел (в том числе отброшенный), `tested` — на каждую
  проверенную точку; новое `n` возвращается и передаётся в следующий рекурсивный вызов.

### `e0806_scene_culling`

* **Что просят:** три прохода — `update_world`, `update_bounds`, `cull`.
* **Перечитать:** разделы 6 (DFS и `subtree_end`), 6.3 (проход с конца), 9.2 (полная
  трассировка этих трёх проходов).
* **На что обратить внимание:** у корня база мира — (0, 0). Для сдвига коробки используйте
  `Box.offset` (он корректно обрабатывает пустые). Во втором проходе сначала скопируйте
  `world_box` в `sub_box` для всех узлов, затем идите с конца и вливайте. В `cull` —
  цикл `while`, а не `for`: шаг бывает либо `i++`, либо прыжок; каждая проверка
  коробки — `tests++`. Видимыми считаются только узлы с непустым `world_box`.

## Вопросы для самопроверки

1. Почему движки хранят и local, и world трансформации? Какое из них — источник истины?
2. Чем отличаются `parent * local` и `local * parent` в конвенции векторов-столбцов? Почему
   ошибка незаметна, пока у родителя нет поворота?
3. Сформулируйте инвариант dirty-флагов в иерархии. Что сломается, если `mark_dirty`
   выходит рано, а `get_world` у ребёнка снимает флаги с предков, не трогая потомков?
4. Почему `get_world` с ленивым кэшем — проблема для многопоточности? Как её решает явная
   фаза обновления?
5. Какой инвариант позволяет посчитать мировые трансформации одним циклом без рекурсии?
   Что нужно сделать со ссылками после перестановки узлов?
6. Чем порядок DFS preorder лучше просто «родитель раньше ребёнка»? Как за O(1) пропустить
   поддерево?
7. Почему для вычисления границ поддеревьев проход идёт с конца массива?
8. Опишите компактную сетку на сортировке подсчётом. Почему её перестраивают целиком каждый
   кадр, а не обновляют инкрементально?
9. Когда квадродерево лучше сетки? Как в нём хранить объекты с размером, а не точки?
10. Чем BVH принципиально отличается от октодерева? Почему физические движки
    используют для broadphase динамический AABB-tree с «толстыми» коробками?
11. Почему иерархия трансформаций — плохой пространственный индекс?
12. В каком случае линейный перебор быстрее любой иерархической структуры? Что сделал
    Frostbite в «Culling the Battlefield»?

Дополнительные вопросы-тренажёры (ответы можно проверить, посчитав на бумаге):

13. Объект с матрицей поворота на 90° и сдвигом (3, 4) — куда он переводит точку (2, 0)?
    (Ответ: (3, 6).)
14. `count = [1, 3, 0, 2]`. Чему равен `start` (длины 5)? (Ответ: `[0, 1, 4, 4, 6]`.)
15. Узлы со старыми родителями `[1, -1, 1]`. Постройте `order`, `remap` и новые `parent`.
    (Ответ: `order = [1, 0, 2]`, `remap = [1, 0, 2]`, `parent = [-1, 0, 0]`.)

## Словарик

| Термин | Простыми словами |
|---|---|
| **AABB** | Прямоугольник (коробка) со сторонами вдоль осей, целиком содержащий объект. Задаётся `min` и `max`. |
| **Аффинное преобразование** | Сочетание поворота, масштаба, перекоса и сдвига; прямые остаются прямыми. |
| **Broadphase** | Грубая фаза поиска столкновений: быстро отобрать пары, которые *могут* столкнуться. |
| **BVH** | Иерархия ограничивающих объёмов: дерево вложенных коробок над множеством объектов. |
| **Culling (отсечение)** | Отбрасывание объектов, которые точно не видны, до отрисовки. |
| **DFS preorder** | Обход дерева в глубину, где узел записывается раньше своих детей; поддерево лежит подряд. |
| **Dirty flag (грязный флаг)** | Пометка «кэш устарел, пересчитай при чтении». |
| **Frustum** | Усечённая пирамида — область, которую видит камера. |
| **Handle** | Устойчивая «ручка» на объект; через таблицу превращается в текущий индекс (глава 03). |
| **Local / world** | Трансформация относительно родителя / относительно мира. |
| **O(…)** | Оценка роста работы с ростом входа: O(1) — постоянно, O(N) — пропорционально N. |
| **Occlusion culling** | Отсечение объектов, заслонённых другими. |
| **SIMD** | Инструкции, обрабатывающие несколько чисел за одну операцию. |
| **SoA** | «Структура массивов»: по отдельному массиву на каждое поле вместо массива структур. |
| **TRS** | Трансформация как три части: перенос, поворот, масштаб. |
| **Вектор-столбец** | Конвенция `p' = M * p`; в ней `A * B` = «сначала B, потом A». |
| **Глубина узла** | Число шагов от узла вверх до корня. |
| **Детерминант** | Для 2D-матрицы `a*d - b*c`: во сколько раз меняется площадь; знак минус — зеркало. |
| **Инвариант** | Утверждение о данных, которое всегда верно между операциями. |
| **Интерполяция** | Плавный переход между двумя значениями по параметру `t` от 0 до 1. |
| **Интрузивный список** | Список, где ссылка «следующий» хранится прямо в данных объекта (у нас — массив `next`). |
| **Кэш (значение)** | Сохранённый результат вычисления, который может устареть. |
| **Кэш процессора** | Быстрая память в CPU; данные, лежащие подряд, читаются из неё почти бесплатно. |
| **Квадрант** | Одна из четырёх четвертей квадрата узла квадродерева. |
| **Квадродерево / октодерево** | Дерево, где узел-квадрат (куб) делится на 4 (8) частей там, где много объектов. |
| **Корень, лист, внутренний узел** | Узел без родителя; узел без детей; узел с детьми. |
| **Перекос (shear)** | Искажение, превращающее квадрат в ромб; не выражается в TRS. |
| **Полуоткрытый интервал `[a, b)`** | Все значения от `a` включительно до `b` не включительно. |
| **Префиксная сумма** | Массив сумм всех предыдущих элементов; «exclusive» — без текущего. |
| **Пространственный хеш** | Сетка, где номер клетки получается хешем координат — для бесконечных миров. |
| **Поддерево** | Узел вместе со всеми потомками. |
| **Промах кэша** | Нужных данных нет в кэше процессора — долгое ожидание памяти. |
| **remap** | Таблица `remap[old] = new`: куда переехал каждый узел после перестановки. |
| **Сортировка подсчётом** | Раскладка по корзинам: подсчёт → префиксная сумма → раскладка. |
| **Устойчивая сортировка** | Сортировка, сохраняющая порядок элементов с равными ключами. |
| **Висячий указатель** | Указатель на память, которая уже освобождена или переехала. |
