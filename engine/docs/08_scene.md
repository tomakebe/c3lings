# Глава 08. Сцена: иерархия трансформаций и пространственные структуры

> Упражнения главы: `e0801_transform_hierarchy` … `e0806_scene_culling`.
> Предполагается, что вы прошли главы 03 (handles, плоские массивы), 04 (матрицы и
> преобразования) и 05 (ECS).

«Сцена» — одно из самых перегруженных слов в движкостроении. В редакторе Unity это файл
`.unity`, в Godot — дерево `Node`, в Unreal — `UWorld` с уровнями и акторами, в рендерере —
список видимых мешей. В этой главе нас интересуют две вещи, которые нужны почти любому
движку независимо от его философии:

1. **Иерархия трансформаций.** Колесо прикреплено к машине, машина — к платформе, пистолет —
   к кости руки. Объекты задаются *относительно* родителя, а остальному движку нужны
   *мировые* координаты.
2. **Пространственные запросы.** «Что видит камера?», «Кто в радиусе взрыва?», «С кем я могу
   столкнуться?». Отвечать на них перебором всех объектов нельзя уже при нескольких тысячах
   сущностей.

Это две разные задачи с разными структурами данных, и одна из главных ошибок
дизайна — пытаться решить их одним деревом. К этому мы ещё вернёмся.

---

## 1. Local и world

Каждый узел хранит **локальную** трансформацию — положение, поворот и масштаб относительно
родителя. **Мировая** трансформация получается композицией всех предков:

```
world(root) = local(root)
world(n)    = world(parent(n)) * local(n)
            = local(root) * ... * local(parent) * local(n)
```

Почему не хранить сразу мировые? Потому что художник и геймплей мыслят локально: «башня
повёрнута на 30° относительно корпуса», «меч в руке». Если хранить только world, то при
повороте корпуса придётся вручную пересчитать все вложенные объекты — то есть всё равно
реализовать иерархию, но в худшем месте. Поэтому движки хранят **оба** представления:
local — источник истины, world — кэш, производное значение.

```
          city (local: translate 100,0)
           |
         car  (local: translate 10,0; rotate 90)
         /  \
    wheel   turret (local: translate 0,1; rotate -45)
                \
               barrel (local: translate 3,0)

  world(barrel) = L(city) * L(car) * L(turret) * L(barrel)
```

## 2. Как хранить трансформацию

Варианты, от простого к сложному:

| Представление | Плюсы | Минусы |
|---|---|---|
| Матрица 4x4 (3x3 в 2D) | композиция — одно умножение, сразу для GPU | 64 байта, нельзя интерполировать, накапливает ошибку (перекос) |
| Аффинная 3x4 (2x3 в 2D) | на 25% меньше, нижняя строка всегда (0,0,0,1) | всё ещё неинтерполируема |
| TRS: translation + quaternion + scale | 40 байт, интерполируется (анимация!), удобно редактировать | композиция дороже, неравномерный масштаб + поворот у родителя ломает TRS |

На практике: **локальная** трансформация хранится как TRS (её крутит анимация, редактор,
геймплей), **мировая** — как аффинная матрица (её потребляют рендер и физика). Unreal хранит
`FTransform` (кватернион + перенос + 3D-масштаб) и для local, и для world; Unity —
TRS в `Transform` плюс кэш `localToWorldMatrix`; Bitsquid/Stingray в своём `SceneGraph`
держал local как `Matrix4x4` или TRS-«Pose» и world как матрицу.

Отдельная тонкость — **неравномерный масштаб**. Если родитель растянут по X в 2 раза, а
ребёнок повёрнут на 45°, то мировая матрица ребёнка содержит перекос (shear), который нельзя
выразить в TRS. Unreal и Unity честно предупреждают в документации, что разложение
мировой матрицы обратно в TRS в этом случае приближённо. Многие движки (и Godot для 2D)
просто запрещают или не рекомендуют неравномерный масштаб на родителях с повёрнутыми
детьми. Решение для собственного движка: мировые трансформации — матрицы, а API
`get_world_rotation()` честно документирует, что он неточен при перекосе.

## 3. Порядок умножения

Это самый частый баг в иерархиях. Для векторов-столбцов (`p' = M * p`, конвенция OpenGL,
большинства учебников и этого курса) запись `A * B` означает «сначала B, затем A». Мировая
матрица — это `parent * local`: сначала точка переводится из пространства ребёнка в
пространство родителя (local), затем дальше вверх.

```c3
// self * c : сначала c, потом self.
fn Affine2 Affine2.mul(self, Affine2 c) { ... }

Affine2 world = world_of_parent.mul(local);   // правильно
Affine2 wrong = local.mul(world_of_parent);   // «почти работает»
```

Коварство в слове «почти»: если у родителя нет поворота и масштаба, оба варианта дают
одинаковый перенос. Ошибка проявится через месяц, когда художник повернёт корневой объект.
Поэтому в `e0801` тесты специально крутят и масштабируют родителя. DirectX-конвенция
(векторы-строки, `p' = p * M`) переворачивает порядок: там `world = local * parent`. Выберите
одну конвенцию на весь движок и запишите её в комментарии рядом с типом матрицы.

Наивная реализация `world_matrix(i)` из `e0801` поднимается по родителям и перемножает:
O(глубина) на каждый запрос. Если 10 000 объектов, глубина 8 и каждый объект спрашивают
три системы за кадр, получаем 240 000 умножений матриц, большинство — повторные. Нужен кэш.

## 4. Dirty flags: ленивый пересчёт

Паттерн «Dirty Flag» подробно описан у Nystrom'а (Game Programming Patterns, глава
«Dirty Flag»), и иерархия трансформаций — его каноничный пример. Идея: world — это кэш,
кэш помечается устаревшим при изменении источника и пересчитывается при чтении.

```
set_local(i):  local[i] = v; mark_dirty(i)       // дёшево, ничего не считает
get_world(i):  if dirty[i]:
                   world[i] = get_world(parent) * local[i]   // рекурсивно чистит предков
                   dirty[i] = false
               return world[i]
```

Флаг должен распространяться **вниз**: когда двигается родитель, устаревают миры всех
потомков. Отсюда ключевой инвариант:

> если узел грязный, то все его потомки тоже грязные.

Благодаря ему `mark_dirty` останавливается на уже грязном узле — ниже всё помечено. Без
этой оптимизации геймплей, двигающий корень персонажа пять раз за кадр, пять раз обходит
всё дерево скелета. С ней — один раз плюс четыре проверки флага.

Что получаем:

* **Ленивость.** Если объект за кадром никто не читал (он вне экрана, физика спит), его мир
  не пересчитывается вовсе.
* **Объединение изменений.** N изменений до чтения стоят одного пересчёта.

Чего стоит:

* **Ветвления и непредсказуемый доступ.** Каждый `get_world` — проверка флага, возможно
  рекурсия вверх. Читатели разбросаны по кадру, кэш процессора холодный.
* **Сложность многопоточности.** `get_world` — это *запись* (он обновляет кэш). Два потока,
  читающие мир одного объекта, устраивают гонку. Unity поэтому до DOTS требовал обращения
  к `Transform` только с главного потока; Unreal обновляет `ComponentToWorld` в
  `UpdateComponentToWorld` из игрового потока и затем копирует в рендер-поток.
* **«Протухшие» кэши в обход API.** Если кто-то записал `local` напрямую, не вызвав
  `mark_dirty`, баг проявится нерегулярно. Поле должно быть закрыто, изменение — только
  через функцию (в C3 — `@private` или модульные границы).

Вариант, который используют многие движки: **dirty flag + явная фаза обновления**. Изменения
лишь помечают узлы (и, например, кладут корень изменённого поддерева в список), а в
определённой точке кадра (после геймплея, перед физикой/рендером) одна функция обновляет
все грязные поддеревья подряд. Чтения в остальное время просто отдают кэш — он может быть
на кадр старым, и это нужно документировать. Unity делает именно так в
`TransformHierarchy` (там есть `TransformChangeDispatch`, собирающий изменённые
иерархии), Godot — через `notification(NOTIFICATION_TRANSFORM_CHANGED)` и отложенную
очередь обновления.

## 5. Плоская иерархия: «родитель раньше ребёнка»

Деревья из объектов с указателями `children` — естественны для редактора и ужасны для
кэша. Каждый узел — отдельная аллокация, обход — прыжки по памяти, `std::vector<Node*>`
детей — ещё одна косвенность.

Bitsquid/Stingray (Niklas Frykholm, серия «Building a Data-Oriented Entity System» и пост
про scene graph), позже Our Machinery, иерархии костей в любой системе анимации, Unity DOTS
(`LocalToWorldSystem`) делают иначе: иерархия — это **несколько параллельных массивов**
(SoA), отсортированных так, что **родитель всегда стоит раньше ребёнка**:

```
 index:   0      1      2      3      4      5
 parent: -1     -1      0      0      1      3
 local:  L0     L1     L2     L3     L4     L5
 world:  W0     W1     W2     W3     W4     W5

 for i in 0..n:
     world[i] = parent[i] < 0 ? local[i] : world[parent[i]] * local[i]
```

Один линейный проход, ноль рекурсии, ноль стека, предсказуемые ветвления, массивы читаются
последовательно (кроме `world[parent[i]]`, но родитель почти всегда «недалеко позади» и
уже в кэше). Для скелета из 100 костей это десятки наносекунд на всё. Можно добавить и
dirty flags: пропускать узлы, чей флаг и флаг родителя сброшены, — в одном проходе флаг
распространяется сам: `dirty[i] |= dirty[parent[i]]`.

Плата — **поддерживать порядок**. Когда узлы загружаются в произвольном порядке или
меняют родителя, массивы приходится переставлять. Простейшая стратегия из `e0803` — устойчивая
сортировка по глубине. Важнейший момент любой перестановки: **все ссылки по индексам
становятся неверными**. Нужна таблица `remap[old] = new`, через которую перенумеровываются
`parent` — и всё, что снаружи хранило индексы. Поэтому внешний код никогда не должен держать
«сырой» индекс узла иерархии: только handle (глава 03), который через таблицу
индирекции отображается в текущий индекс. Ровно так устроен `SceneGraph` в Bitsquid:
пользователь держит `Instance`, а внутренний массив свободно переупорядочивается.

Как часто происходит переупорядочивание? В игре — редко: смена родителя (подобрал
предмет, сел в машину) — это единичные события за кадр, а не тысячи. Поэтому платить
O(n) за пересортировку при reparent обычно приемлемо, а в критичных случаях можно
переносить поддерево целиком в конец массива (оно остаётся «после» нового родителя, если
родитель стоит раньше) без полной сортировки.

## 6. Порядок DFS и непрерывные поддеревья

Частный случай порядка «родитель раньше ребёнка» — **обход в глубину (preorder)**. У него
есть бонус: всё поддерево узла лежит в массиве **подряд**:

```
          A
        /   \
       B     E
      / \     \
     C   D     F

 index:        0  1  2  3  4  5
 node:         A  B  C  D  E  F
 subtree_end:  6  4  3  4  6  6      поддерево узла i = [i, subtree_end[i])
```

Что это даёт:

* **Пропуск поддерева** за O(1): `i = subtree_end[i]`. Это основа иерархического
  отсечения в `e0806`.
* **Удаление/перемещение поддерева** — это `memmove` одного непрерывного диапазона.
* **Обратный проход** (`i` от n-1 до 0) обрабатывает детей раньше родителей — идеально для
  «агрегатов снизу вверх»: границы поддерева (bounding volume), суммарная масса, флаг «есть
  ли в поддереве что-то видимое».

Именно так хранятся иерархии в форматах, ориентированных на скорость загрузки (например,
скелеты в glTF после импорта, сцены в cooked-форматах движков): после «выпекания» сцена
загружается одним блоком и сразу готова к линейному обновлению.

## 7. Граф сцены против плоских структур

В 90-х и 2000-х «граф сцены» (scene graph — OpenInventor, OpenSceneGraph, Ogre, Java3D)
был универсальным ответом: одно дерево, в котором узлы — трансформации, группы, материалы,
переключатели LOD, геометрия. Рендер обходил дерево рекурсивно, накапливая состояние,
отсекая поддеревья по их bounding sphere.

Почему движки от этого ушли (Tom Forsyth, «Scene Graphs — just say no»; доклады DICE и
Bitsquid про data-oriented design):

* **Одно дерево — несколько несовместимых иерархий.** Трансформационная иерархия (меч в
  руке) не совпадает с пространственной (меч рядом со стеной, а не рядом с корнем
  персонажа), с иерархией состояний рендера (все объекты с одним материалом) и с
  логической (команда, отряд). Дерево, оптимальное для одного, плохо для остальных.
* **Рекурсивный обход объектов с виртуальными функциями** — худший паттерн доступа к памяти.
* **Плохая параллельность** — дерево с общим состоянием обхода трудно делить между потоками.

Современный подход — **разделение ответственностей**:

```
  трансформационная иерархия   ->  плоские SoA-массивы, линейный проход (e0803/e0806)
  пространственный индекс      ->  сетка / квадродерево / BVH, отдельная структура (e0804/e0805)
  рендер                        ->  плоский список видимых объектов -> command buffer (глава 09)
  логика                        ->  ECS-запросы (глава 05)
```

При этом **дерево в редакторе** никуда не делось: Godot целиком построен на дереве `Node`,
у Unity — `GameObject`/`Transform`, у Unreal — `USceneComponent` с attach-родителями. Но
это удобная *модель для человека*; внутри (особенно в Unity DOTS, в `FScene` рендера
Unreal, в серверах Godot 4 — `RenderingServer`, `PhysicsServer`) данные раскладываются
плоско и обрабатываются пакетно.

## 8. Пространственные структуры

Теперь вторая задача. Есть N объектов с bounding boxes; нужно быстро отвечать на запросы
«пересечение с областью», «ближайшие соседи», «луч». Общая идея — разбить пространство или
множество объектов так, чтобы большую часть можно было отбросить одной проверкой.

### 8.1 Равномерная сетка

Мир делится на клетки размера `CELL`; объект попадает в клетку (или клетки, если он
большой) по координатам. Запрос перебирает только задетые клетки.

```
  +----+----+----+----+
  |  . |    |  ..|    |       запрос [###] задевает 4 клетки,
  +----+----+-[##+##]-+       проверяем только объекты в них
  |    |  . | [##+##] |
  +----+----+----+----+
```

Плюсы: O(1) вставка, тривиальная реализация, отличная константа, легко распараллелить.
Минусы: один размер клетки на всех. Мелкие клетки — много пустой памяти и большие объекты
в десятках клеток; крупные — толпа в одной клетке.

Хранение. «List в каждой клетке» — тысячи аллокаций. В `e0804` мы делаем **компактную
сетку через сортировку подсчётом** (так строят broadphase в физике частиц, спатиал-хеш в
SPH-жидкостях, а на GPU — тайловый light culling в Forward+):

```
  1) count[cell]++ для каждого объекта
  2) start = exclusive prefix sum(count)
  3) entries[start[cell] + k] = id
```

Перестройка O(N + cells) за кадр, ноль аллокаций, содержимое каждой клетки в памяти подряд.
Это часто быстрее инкрементального перемещения объектов между клетками — особенно когда
двигается большинство объектов (частицы, толпы).

Если мир бесконечный или разреженный — **пространственный хеш**: `hash(cx, cy) % TABLE`
вместо `cy * W + cx`. Коллизии хеша дают лишние кандидаты, но не ошибки (точная проверка
всё равно выполняется).

### 8.2 Квадродерево и октодерево

Квадродерево (2D) и октодерево (3D) адаптируются к плотности: узел делится на 4 (8)
квадрантов, когда в нём слишком много объектов (`e0805`). Где пусто — дерево мелкое, где
густо — глубокое.

Практические детали, которые важнее теории:

* **Узлы в пуле с индексами**, а не `new Node` с указателями; 4 ребёнка подряд — достаточно
  хранить `first_child`. Это сразу и компактнее, и дружелюбнее к кэшу, и легко сериализуется.
* **Ограничение глубины.** Несколько объектов в одной точке иначе делили бы дерево
  бесконечно. Лист на максимальной глубине просто хранит сколько угодно объектов.
* **Объекты с размером.** Точку легко положить в один лист. Объект с AABB может пересекать
  границы квадрантов. Варианты: класть в наименьший узел, целиком его содержащий (так
  делает «loose» дерево, но объект на границе корня застревает в корне); класть во все
  пересекаемые листья (дубликаты, нужна дедупликация результатов); **loose octree**
  (Ulrich, Game Programming Gems 1) — узлы с «раздутыми» в 2 раза границами, и любой объект
  размером не больше узла помещается ровно в один узел своего уровня.
* **Движущиеся объекты** — главная боль деревьев: удалить и вставить заново, с возможным
  слиянием опустевших узлов. Для динамики чаще выбирают сетку или BVH с «толстыми» AABB.

Октодеревья хорошо подходят для статики, вокселей (SVO), разреженных полей освещения.

### 8.3 BVH — иерархия ограничивающих объёмов

Сетка и квадродерево делят **пространство**. BVH делит **множество объектов**: каждый узел
хранит AABB, охватывающий всех потомков; листья — объекты. Объект ровно в одном листе,
дубликатов нет; узлы могут перекрываться.

```
            [ AABB всех ]
            /           \
     [AABB A,B]       [AABB C,D,E]
      /     \          /        \
     A       B       C       [AABB D,E]
                               /    \
                              D      E
```

Где используется:

* **Трассировка лучей** — BVH стандарт де-факто (DXR/Vulkan RT строят его в драйвере,
  Embree на CPU). Построение — SAH (surface area heuristic).
* **Динамический broadphase** — Box2D `b2DynamicTree`, Bullet `btDbvt`: инкрементальный AABB-
  tree с «толстыми» (fat) AABB: объект пересоздаёт лист только когда вылез за запас.
  Вставка выбирает соседа по минимальному росту площади, дерево балансируется вращениями.
* **Отсечение статики** — построенный офлайн BVH сцены.

Иерархия трансформаций с границами поддеревьев из `e0806` — частный случай BVH, где
структура дерева задана не пространством, а логикой сцены. Работает, пока логическая
иерархия пространственно компактна (здания района лежат рядом). Если персонаж бегает по
всей карте, а родитель у него — «корень уровня», граница корня огромна и ничего не
отсекает. Поэтому движки строят отдельный пространственный индекс, а не полагаются на
трансформационное дерево.

### 8.4 Как выбрать

| Структура | Вставка/перемещение | Запрос | Неравномерная плотность | Где |
|---|---|---|---|---|
| Перебор (SIMD) | O(1) | O(N) | всё равно | до ~1–5 тыс. объектов это честно быстро! |
| Сетка / хеш | O(1) | O(клеток + кандидатов) | плохо | частицы, толпы, 2D-игры, broadphase |
| Квадро/октодерево | O(log N) | O(log N + k) | хорошо | статика, большие открытые миры |
| BVH (динамический) | O(log N) | O(log N + k) | хорошо | физика, лучи, отсечение |

Не забывайте первую строку. Перебор массива AABB в SoA с SIMD проверяет 4–8 коробок за
инструкцию, без промахов кэша и без ветвлений. Frostbite (доклад Daniel Collin, «Culling the
Battlefield», GDC 2011) заменил иерархическую структуру отсечения на **линейный перебор**
плоских массивов сфер, разбитых по ячейкам грубой сетки, — и стал быстрее в разы. Сначала
измеряйте.

## 9. Отсечение (culling)

Отсечение — отбрасывание объектов, которые точно не повлияют на картинку, до отправки на
GPU. Виды, от дешёвого к дорогому:

1. **Frustum culling** — объект вне пирамиды видимости камеры. В 3D пирамида задаётся
   шестью плоскостями; AABB проверяется против каждой (тест «ближайшей/дальней вершины» или
   «центр + проекция полуразмеров на нормаль»). В 2D и в наших упражнениях — пересечение с
   прямоугольником вида.
2. **Distance / detail culling** — слишком далёкие или крошечные на экране (screen size
   culling) объекты. Часто совмещается с выбором LOD.
3. **Occlusion culling** — объект заслонён другими. Офлайн: PVS (potentially visible sets) —
   id Tech 1–3 разбивали уровень BSP-деревом и для каждого листа заранее считали видимые
   листья; порталы (Unreal 1, Doom 3) для индорных уровней. Онлайн: software-растеризация
   окклюдеров в маленький буфер глубины (Frostbite, Intel Masked Occlusion Culling), Hi-Z
   на GPU с данными прошлого кадра, GPU-driven отсечение в compute (Unreal Nanite,
   «two-pass occlusion culling»).

Иерархическое отсечение в `e0806` иллюстрирует общий принцип: проверяем границу группы,
и если она мимо — отбрасываем группу целиком одной проверкой. Обратите внимание на вывод
упражнения: когда видно всё, иерархия делает *больше* проверок, чем перебор (лишние
проверки групп). Это нормальная цена; иерархия выигрывает, когда видна малая доля
сцены, — а в играх с большим миром так почти всегда.

Результат отсечения — **плоский список видимых объектов** (индексы или handles),
который дальше превращается в команды рендера с ключами сортировки (глава 09). В
многопоточном движке отсечение — одна из первых задач, которую распараллеливают: массив
объектов делится на куски, каждый поток пишет свой список, списки склеиваются.

## 10. Подводные камни

* **Порядок умножения матриц** (раздел 3). Тестируйте иерархии с поворотом и масштабом
  родителя.
* **Висячие указатели на элементы динамических массивов.** `QNode* n = &nodes[i];` затем
  `nodes.push(...)` — и `n` может указывать в освобождённую память. В `e0805` это ловушка
  в `split`. Берите копию или индекс.
* **Индексы после перестановки.** Любая сортировка иерархии инвалидирует внешние индексы.
  Наружу — только handles.
* **Обновление в середине кадра.** Если физика читает world до фазы обновления иерархии, а
  рендер — после, они видят разные миры. Определите явный порядок фаз кадра (глава 01) и
  точку, где мировые трансформации консистентны.
* **Точность float на больших координатах.** На расстоянии 10 км от начала координат
  float даёт шаг около миллиметра, на 100 км — сантиметры: дрожание камеры и
  анимаций. Решения: перенос начала координат (floating origin, Unity/KSP), относительные
  к камере координаты при рендере, double для мировых позиций (Unreal 5 Large World
  Coordinates, Star Citizen).
* **Отрицательный масштаб** меняет ориентацию треугольников (winding) — рендер должен
  переключать culling граней по знаку детерминанта мировой матрицы.
* **Слишком мелкие клетки сетки** для больших объектов: объект в 100 клетках — 100 записей
  и дубликаты в запросах.
* **Квадродерево без лимита глубины** — бесконечная рекурсия на совпадающих координатах.

## 11. Как это устроено в реальных движках

* **Unreal Engine.** `USceneComponent` хранит `RelativeLocation/Rotation/Scale` и кэш
  `ComponentToWorld` (`FTransform`); attach-иерархия компонентов; `UpdateComponentToWorld`
  рекурсивно обновляет детей при изменении (не лениво, но с флагами для пропуска). Рендер
  живёт в отдельном `FScene` с плоскими массивами примитивов (`FPrimitiveSceneInfo`),
  отсечение — параллельный перебор bounds + occlusion queries/Hi-Z, в UE5 — Nanite с
  иерархией кластеров на GPU.
* **Unity.** `Transform` с иерархией; внутренне `TransformHierarchy` хранит иерархию
  плоскими массивами, отдельными для каждого корня (поэтому совет «держите глубокие
  иерархии под разными корнями» влияет на параллельность обновления через
  `TransformAccessArray`). Отсечение — `CullingGroup`, umbra для occlusion.
* **Godot 4.** Дерево `Node` для пользователя; `Node3D` кэширует глобальную трансформацию с
  dirty-флагом; рендер-сервер держит свои плоские структуры и использует
  `DynamicBVH` для отсечения.
* **Bitsquid/Stingray.** `SceneGraph` как плоские массивы local/world/parent с порядком
  «родитель раньше ребёнка», handles-`Instance` наружу; отсечение по плоским массивам.
* **id Tech.** BSP + PVS + порталы в классике; в id Tech 6/7 — GPU-driven рендер с отсечением
  кластеров в compute.
* **Frostbite.** «Culling the Battlefield»: грубая сетка + линейный SIMD-перебор + software
  occlusion.

## Вопросы для самопроверки

1. Почему движки хранят и local, и world трансформации? Какое из них — источник истины?
2. Чем отличаются `parent * local` и `local * parent` в конвенции векторов-столбцов? Почему
   ошибка незаметна, пока у родителя нет поворота?
3. Сформулируйте инвариант dirty-флагов в иерархии. Что сломается, если `mark_dirty`
   выходит рано, а `get_world` у ребёнка снимает флаги с предков, не трогая потомков?
4. Почему `get_world` с ленивым кэшем — проблема для многопоточности? Как её решает явная
   фаза обновления?
5. Какой инвариант позволяет посчитать мировые трансформации одним циклом без рекурсии?
   Что нужно сделать со ссылками после перестановки узлов?
6. Чем порядок DFS preorder лучше просто «родитель раньше ребёнка»? Как за O(1) пропустить
   поддерево?
7. Почему для вычисления границ поддеревьев проход идёт с конца массива?
8. Опишите компактную сетку на сортировке подсчётом. Почему её перестраивают целиком каждый
   кадр, а не обновляют инкрементально?
9. Когда квадродерево лучше сетки? Как в нём хранить объекты с размером, а не точки?
10. Чем BVH принципиально отличается от октодерева? Почему физические движки
    используют для broadphase динамический AABB-tree с «толстыми» коробками?
11. Почему иерархия трансформаций — плохой пространственный индекс?
12. В каком случае линейный перебор быстрее любой иерархической структуры? Что сделал
    Frostbite в «Culling the Battlefield»?
