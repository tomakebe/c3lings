# 04 · Математика движка

> Упражнения главы: `e0401_vectors`, `e0402_mat4`, `e0403_quaternions`, `e0404_slerp`,
> `e0405_transforms`, `e0406_culling`.

Математическая библиотека — первое, что пишут в движке, и последнее, что в нём меняют:
на ней стоят рендер, физика, анимация, камера, ИИ, редактор. Ошибка в соглашениях
(порядок умножения, раскладка матриц, направление осей) расползается по всему коду
и порождает бесконечные «тут почему-то надо транспонировать». Поэтому в этой главе
важны не столько формулы (их можно найти в любой книге), сколько **соглашения,
представление данных и численная устойчивость**.

---

## 1. Вектора на SIMD-типах C3

В C3 есть встроенные векторные типы: `float[<3>]`, `float[<4>]`. Арифметика над ними
поэлементная и компилируется в SIMD-инструкции, есть swizzle (`v.xy`, `v.zxy`) и
редукции (`v.sum()`, `v.max()`):

```c3
alias Vec3 = float[<3>];

fn float dot(Vec3 a, Vec3 b) => (a * b).sum();
fn Vec3 cross(Vec3 a, Vec3 b) => a.yzx * b.zxy - a.zxy * b.yzx;
fn float length(Vec3 v) => math::sqrt(dot(v, v));
```

Формула `cross` через swizzle — классический SIMD-трюк: вместо шести скалярных
умножений — два векторных умножения и вычитание.

Несколько фактов о векторах C3 0.8.5, которые важно знать:

* **Выравнивание.** Простой `float[<4>]`, вложенный в структуру или массив, имеет
  выравнивание элемента (4 байта), как `float[4]`. Чтобы получить SIMD-выравнивание
  (16 байт), нужен тип с атрибутом: `typedef Simd4 = float[<4>] @simd;`. Локальные
  переменные компилятор выравнивает сам.
* **`float[<3>]` занимает 12 байт** (как массив). Многие движки (DirectXMath,
  Unreal `VectorRegister`) держат 3D-вектора в 16-байтных регистрах с мусорной `w`, чтобы
  все операции были выровнены; при хранении в памяти же используют 12-байтные
  `XMFLOAT3`/`FVector3f`. Это разделение «тип для хранения» vs «тип для вычислений» —
  распространённый приём.
* **`typedef` над вектором** создаёт отдельный тип, но swizzle и редукции на нём
  возвращают *базовый* тип и некоторые методы недоступны. Поэтому в упражнениях мы
  используем `alias` и свободные функции.
* **Сравнение `a == b`** для векторов поэлементное и даёт `bool[<N>]`; операторы `<`, `>`
  для векторов запрещены — используйте `a.comp_lt(b)`, `a.comp_ge(b)` и т.п. из `std::math`.
* В stdlib уже есть многое: `float[<3>].cross`, `.length()`, `std::math::Matrix4f`,
  `Quat`. Читать их исходники (`lib/std/math/`) полезно, но в главе мы пишем всё сами —
  чтобы понимать каждый знак.

### AoS против SoA для SIMD

Вектор `float[<4>]` с x, y, z, w — это **AoS SIMD**: один вектор — одна точка. Это удобно,
но плохо использует SIMD: скалярное произведение требует горизонтального сложения
(медленно), а 3D-вектор тратит четверть регистра впустую.

**SoA SIMD** — в одном регистре четыре разные точки:

```
 AoS:  [x0 y0 z0 _] [x1 y1 z1 _] [x2 y2 z2 _] [x3 y3 z3 _]
 SoA:  X = [x0 x1 x2 x3]   Y = [y0 y1 y2 y3]   Z = [z0 z1 z2 z3]

 dot четырёх пар за раз:  D = X*X' + Y*Y' + Z*Z'     (3 умножения, 2 сложения,
                                                       без горизонтальных операций)
```

Так считают отсечение по пирамиде видимости для тысяч объектов, скиннинг, частицы.
Unity Burst и `Unity.Mathematics` поощряют SoA-код, ISPC построен вокруг этой
модели. Правило: *типы-вектора для удобства, SoA для массовой обработки*.

## 2. Соглашения: самый важный раздел

### 2.1 Система координат

Нет «правильной» системы координат, есть *ваша* — и её надо записать в документации:

| Движок | Вверх | Вперёд | Рука |
|---|---|---|---|
| Unreal | +Z | +X | левая |
| Unity | +Y | +Z | левая |
| Godot | +Y | −Z | правая |
| Blender | +Z | −Y | правая |
| OpenGL (клип) | +Y | −Z | правая (view) |

Левая/правая рука определяет знак векторного произведения: в правой системе
`cross(X, Y) = Z` и поворот на положительный угол — против часовой стрелки, если
смотреть с конца оси. Импорт ассета из Blender в Unity — это смена базиса, и её
надо делать в пайплайне ассетов (глава 07), а не «в шейдере, где-то».

### 2.2 Вектор-столбец или вектор-строка

Это вопрос *математической записи*:

```
 вектор-столбец:  p' = M * p          композиция: M = P * V * W  (применяется справа налево)
 вектор-строка:   p' = p * M          композиция: M = W * V * P  (слева направо)
```

Матрицы в двух соглашениях — транспонированы друг относительно друга. OpenGL, GLM,
большинство учебников и наш курс — столбцы (`M * p`). DirectXMath и классический
Direct3D — строки (`p * M`). Unreal (FMatrix) — тоже строки.

### 2.3 Раскладка в памяти: column-major или row-major

Это вопрос *хранения*, независимый от предыдущего:

```
          | m00 m01 m02 m03 |      column-major: m00 m10 m20 m30 | m01 m11 ...  (по столбцам)
 M   =    | m10 m11 m12 m13 |      row-major:    m00 m01 m02 m03 | m10 m11 ...  (по строкам)
          | m20 m21 m22 m23 |
          |  0   0   0   1  |      трансляция — (m03, m13, m23)
```

GLM и наш курс: вектор-столбец + хранение по столбцам. Матрица — четыре `float[<4>]`
столбца: `cols[3].xyz` — трансляция. Удобство такой раскладки: `M * p` — это линейная
комбинация столбцов:

```
 M * p = cols[0]*p.x + cols[1]*p.y + cols[2]*p.z + cols[3]*p.w
```

— четыре SIMD-умножения на скаляр и три сложения, без горизонтальных операций.

Знаменитая «путаница с транспонированием» возникает, когда соглашение записи и
раскладка комбинируются по-разному в разных частях кода (например, CPU-библиотека
row-major, а шейдер ожидает column-major). Комбинация «строки + row-major» и
«столбцы + column-major» дают *одинаковые байты в памяти* — поэтому D3D и GL могут
читать одни и те же 16 float'ов. Упражнение **e0402_mat4**.

### 2.4 Точки и направления

В однородных координатах точка имеет `w = 1`, направление — `w = 0`. Трансляция
действует на точки и не действует на направления. Нормали — особый случай: при
неравномерном масштабе их надо умножать на **обратно-транспонированную** матрицу
(иначе нормаль перестаёт быть перпендикулярной поверхности).

## 3. Матрицы

Аффинное преобразование 4×4 (без проекции) имеет нижнюю строку `0 0 0 1`. Многие
движки хранят только 3×4 (Unreal `FTransform` хранит TRS отдельно, id Tech — `idMat3`
+ `idVec3`), экономя память и операции. Полная 4×4 нужна для проекции.

Стоимость: умножение 4×4 на 4×4 — 64 умножения и 48 сложений (16 SIMD-умножений
на скаляр при раскладке по столбцам). Обращение 4×4 общего вида — около 200 операций;
поэтому для аффинных матриц используют специализированное обращение, а для
ортонормированных (поворот + перенос) — транспонирование поворота:

```
 M = [R | t]   =>   M^-1 = [R^T | -R^T t]
```

## 4. Кватернионы

Повороты можно хранить как матрицу 3×3 (9 чисел), углы Эйлера (3 числа) или
кватернион (4 числа).

**Углы Эйлера** удобны людям (рыскание/тангаж/крен), но плохи для вычислений: порядок
применения (XYZ? ZXY?) — ещё одно соглашение; интерполяция углов даёт кривые пути;
и **gimbal lock** — при тангаже ±90° две оси совпадают, одна степень свободы теряется.

**Кватернион** единичной длины `q = (v sin(θ/2), cos(θ/2))` задаёт поворот на угол θ
вокруг единичной оси v. Мы храним его как `float[<4>]` с `xyz` — векторная часть,
`w` — скалярная (порядок как в Unity/Unreal/GLM ≥ 0.9.9; Eigen хранит `xyzw`, но
конструктор принимает `w` первым — ещё одна ловушка).

Основные операции:

```
 произведение (Гамильтон): q1*q2 = ( w1 v2 + w2 v1 + v1 x v2,   w1 w2 - v1 . v2 )
 сопряжение:               q* = (-v, w)        для единичного q: q^-1 = q*
 поворот вектора:          p' = q * (p, 0) * q*
   быстрая форма:          t = 2 * cross(q.xyz, p);  p' = p + q.w * t + cross(q.xyz, t)
 композиция:               сначала q1, потом q2  =>  q2 * q1   (как матрицы со столбцами)
```

Свойства, о которых надо помнить:

* `q` и `-q` задают **один и тот же** поворот (двойное покрытие). При интерполяции
  это важно: из двух вариантов выбирают тот, у которого `dot(q1, q2) >= 0` — иначе
  интерполяция пойдёт «длинным путём» (на 360° − θ).
* После многих умножений длина «уплывает» от 1 из-за ошибок округления — кватернионы
  периодически **нормализуют**. Это намного дешевле, чем ортонормализация матрицы.
* Поворот кватернионом дороже, чем матрицей (≈15 vs 9 умножений), поэтому для
  массовых операций (скиннинг тысяч вершин) кватернион сначала превращают в матрицу.

Упражнение **e0403_quaternions**.

## 5. Интерполяция поворотов

**Lerp** компонентов кватерниона с последующей нормализацией (**nlerp**) — дёшево,
коммутативно, путь правильный (по дуге), но угловая скорость неравномерна (быстрее в
середине для больших углов).

**Slerp** — сферическая линейная интерполяция, постоянная угловая скорость:

```
 slerp(q1, q2, t) = q1 * sin((1-t)Ω)/sin Ω + q2 * sin(tΩ)/sin Ω,     cos Ω = dot(q1, q2)
```

Подводные камни: при `dot < 0` надо взять `-q2` (короткий путь); при `Ω → 0` деление
на `sin Ω ≈ 0` — переключаемся на nlerp. Для анимации часто достаточно nlerp
(Джонатан Блоу, «Understanding Slerp, Then Not Using It»): блендинг поз — это много
маленьких углов, где разница незаметна, а nlerp коммутативен и дёшев. Упражнение
**e0404_slerp**.

## 6. Трансформ TRS

Объекты сцены хранят не матрицу, а **TRS**: translation (Vec3), rotation (Quat),
scale (Vec3 или float). Причины: легко редактировать и интерполировать по
компонентам; 10 чисел вместо 16; нет накопления ошибок «перекоса». Матрица
вычисляется по требованию: `M = T * R * S` (сначала масштаб, потом поворот, потом
перенос — при векторах-столбцах читаем справа налево).

Композиция двух TRS (родитель * ребёнок):

```
 world.scale = parent.scale * child.scale
 world.rot   = parent.rot * child.rot
 world.pos   = parent.pos + parent.rot * (parent.scale * child.pos)
```

Это точно только при **однородном** масштабе (или когда масштаб и поворот
«не смешиваются»). Неоднородный масштаб родителя + поворот ребёнка дают сдвиг
(shear), который TRS не может представить. Unreal `FTransform` честно предупреждает
об этом, Unity хранит `lossyScale` («с потерями»), Godot использует `Transform3D`
с базисом 3×3 (умеет shear). Многие движки просто запрещают неоднородный масштаб в
иерархиях для анимированных объектов.

Обратный TRS (однородный масштаб s): `inv.rot = conj(rot)`, `inv.scale = 1/s`,
`inv.pos = -(inv.rot * pos) / s`. Упражнение **e0405_transforms**.

## 7. Ограничивающие объёмы

* **AABB** (axis-aligned bounding box) — `min`, `max`. Пересечение — 6 сравнений.
  Преобразование AABB матрицей (метод Arvo, «Transforming Axis-Aligned Bounding Boxes»,
  Graphics Gems 1990): новый центр = M * центр, новые полуразмеры = |R| * старые
  полуразмеры (абсолютные значения элементов поворотно-масштабной части).
* **Сфера** — центр и радиус: проверки самые дешёвые, но описывает плохо вытянутые объекты.
* **OBB** — ориентированный бокс; точнее, но дороже (SAT, 15 осей).

## 8. Отсечение по пирамиде видимости

Пирамида видимости (frustum) — 6 плоскостей. Плоскость: `n · p + d = 0`, нормаль
внутрь. Точка внутри, если для всех плоскостей `n · p + d >= 0`.

* **Сфера vs плоскость**: `dist = n · c + d`; если `dist < -r` — снаружи.
* **AABB vs плоскость**: берём вершину бокса, «самую положительную» по нормали
  (p-vertex), или считаем проекцию полуразмера `r = |n.x| e.x + |n.y| e.y + |n.z| e.z`
  и сравниваем `n · c + d < -r`.

Плоскости можно извлечь прямо из матрицы `VP = P * V` (метод Gribb–Hartmann):
для векторов-столбцов `left = row3 + row0`, `right = row3 - row0`, `bottom = row3 + row1`,
`top = row3 - row1`, `near = row3 + row2` (для GL-клипа z ∈ [−w, w]), `far = row3 - row2`.
Плоскости надо нормализовать, если нужны реальные расстояния (для сфер).

Тест консервативен: объект, пересекающий пирамиду «за углом», может пройти тест,
не будучи видимым — это допустимо (лишний объект нарисуют, но видимый не потеряют).
Упражнение **e0406_culling**.

Отсечение тысяч объектов — классика SoA: центры и радиусы в отдельных массивах,
4 или 8 объектов за итерацию, результат — битовая маска видимости. Доклад Frostbite
«Culling the Battlefield» (Даниэль Коллин, GDC 2011) — эталон этого подхода.

## 9. Точность плавающей точки

`float` — 24 бита мантиссы, ≈7 десятичных знаков. Важные последствия:

* **Большие миры.** На расстоянии 10 км от начала координат шаг между соседними float —
  ≈1 мм; на 100 км — ≈8 мм. Физика начинает дрожать, анимации «шумят», z-fighting.
  Решения: **сдвиг начала координат** (origin rebasing — Unity-игры, KSP), координаты в
  `double` (Unreal 5 Large World Coordinates: `FVector` стал double), **рендер
  относительно камеры** (camera-relative rendering): мировые координаты в double, а на
  GPU передаётся `pos - camera_pos` в float — числа маленькие и точные.
* **Катастрофическое сокращение.** Разность двух близких больших чисел теряет почти
  все значащие цифры. `(a + 1e8) - 1e8` в float — это не `a`.
* **Сравнение с эпсилоном.** `==` для float почти всегда ошибка. Абсолютный
  эпсилон не годится для больших чисел, относительный — для чисел около нуля;
  используют комбинацию (`|a-b| <= max(abs_eps, rel_eps * max(|a|,|b|))`).
* **Денормалы** (числа меньше ~1e-38) обрабатываются на многих CPU в десятки раз
  медленнее. Аудио-фильтры и физика с затухающими значениями могут внезапно
  «затормозить». Движки включают режим flush-to-zero / denormals-are-zero.
* **`-0.0`** печатается как `-0.000`. Тесты, сравнивающие текст, должны это учитывать.
* **Детерминизм** — см. главу 01: `-ffast-math`, FMA и разные `sin` дают разные биты.

## 10. Тесты для математики

Математическую библиотеку легко проверять — и *обязательно* надо, потому что ошибка
в знаке или порядке умножения может годами жить в «невидимых» местах. Полезные виды
тестов (все упражнения главы построены на них):

* **Тесты-соглашения**: «поворот на +90° вокруг Z переводит X в Y», «TRS-матрица
  переводит (1,0,0) в (10,2,0)». Они документируют соглашения лучше любого текста.
* **Алгебраические свойства**: `(AB)C = A(BC)`, `(AB)^T = B^T A^T`, `q * conj(q) = 1`,
  `inverse(T) * T = I`, `|R v| = |v|` для поворота, `dot(cross(a,b), a) = 0`.
* **Согласованность представлений**: поворот кватернионом и его матрицей дают один
  результат; композиция TRS совпадает с произведением матриц.
* **Граничные случаи**: нулевой вектор, совпадающие кватернионы в slerp, угол 180°,
  `dot` чуть больше 1 из-за округления.
* **Рандомизированные тесты** с фиксированным seed: тысячи случайных векторов и
  поворотов, проверка свойств с эпсилоном, зависящим от величины чисел.

Эпсилон в тестах подбирают честно: ошибка растёт с величиной координат и числом
операций (в e0405 обратный трансформ на координатах ~130 с масштабом 8 даёт
погрешность ~1e-4 — и это нормально для float).

### SoA-скетч отсечения

Как выглядит отсечение тысяч сфер в SoA-стиле на векторах C3:

```c3
import std::math;            // comp_lt и другие comp_* живут в std::math
alias Vec4 = float[<4>];

// 4 сферы за раз против одной плоскости (nx, ny, nz, d).
fn bool[<4>] outside4(Vec4 cx, Vec4 cy, Vec4 cz, Vec4 r, float[<4>] plane)
{
    Vec4 dist = cx * plane.x + cy * plane.y + cz * plane.z + plane.w;
    return dist.comp_lt(-r);     // `<` для векторов запрещён: только == и comp_*
}
```

Никаких горизонтальных операций: четыре сферы проверяются тремя умножениями и
сложениями, результат — маска. Для 6 плоскостей маски объединяются через `|`.

## 11. Как это сделано в реальных движках

* **DirectXMath** — SIMD-типы `XMVECTOR` для вычислений и `XMFLOAT3/4` для хранения,
  вектор-строка, row-major.
* **GLM** — копия GLSL на C++, вектор-столбец, column-major. Наш курс следует ему.
* **Unreal** — `FVector` (double в UE5), `FQuat`, `FTransform` (TRS), `FMatrix`
  (вектор-строка), `VectorRegister` для SIMD.
* **Unity.Mathematics** — `float3`, `float4x4`, `quaternion`, синтаксис HLSL, SoA
  поощряется Burst-компилятором.
* **Godot** — `Vector3`, `Basis` (3×3), `Transform3D`, `real_t` может быть double
  (сборка с `precision=double` для больших миров).
* **Handmade Math, cglm, sokol, rtm** (Realtime Math Николаса Фреше) — компактные
  библиотеки, удобные для чтения.

## 12. Подводные камни

* **Порядок умножения.** `T * R * S` и `S * R * T` — разные вещи. Пишите тест:
  «точка (1,0,0), масштаб 2, поворот 90° вокруг Z, перенос (10,0,0) → (10,2,0)».
* **Неединичные кватернионы.** Поворот ненормализованным кватернионом ещё и масштабирует.
* **Нормализация нуля.** `normalize((0,0,0))` — деление на 0, NaN, который расползается
  по всей сцене. Всегда проверяйте длину или возвращайте безопасное значение.
* **NaN.** NaN не равен сам себе, все сравнения с ним ложны: `if (x < 0)` и `if (x >= 0)`
  оба ложны. Отлов NaN — отладочные assert'ы на границах систем.
* **acos/asin вне [-1, 1]** из-за округления → NaN. Клампите аргумент.
* **Углы в градусах vs радианах.** Определите один раз: внутри — радианы.
