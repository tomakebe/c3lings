**Зачем это нужно.** Почти в каждой игре есть логика, которую пишет не программист
движка: катсцены, квесты, диалоги, поведение дверей и ловушек. Эта логика меняется
десятки раз в день, и ей нельзя позволять ронять игру. Скриптовый слой решает обе
задачи — быстро менять и безопасно исполнять.

**Что нужно знать заранее.**

* Желательно — упражнения 115–116 трека по языку (байткодовая VM) и глава 03 движкового
  трека (хендлы с поколениями, слот-карта). Если подзабыли — не страшно, всё нужное

## 0. Несколько слов, без которых дальше никак

Эти термины встречаются в каждом разделе, поэтому разберём их сразу, на пальцах.

* **Скрипт** — небольшая программа на «лёгком» языке, которую движок исполняет во
  время игры. Пример: «когда игрок вошёл в комнату — закрыть дверь, подождать 2
  секунды, включить свет».
* **Хост (host)** — программа, *внутри* которой живёт скрипт. У нас хост — это игровой
  движок на C3. Аналогия: хост — хозяин дома, скрипт — гость. Гость может пользоваться
  только тем, что ему выдали.
* **Виртуальная машина (VM)** — «процессор, написанный программой». Настоящий процессор
  исполняет машинные инструкции; VM — это обычная функция на C3, которая в цикле читает
  *свои* инструкции из массива и выполняет их.
* **Байткод** — программа для VM: массив простых инструкций вроде `PUSH 2`, `ADD`,
  `JMP 5`. Название историческое: часто каждая инструкция кодируется одним байтом.
  У нас инструкция — это структура `Instr { Op op; int arg; }`.
* **Опкод (opcode)** — «что делать»: `PUSH`, `ADD`, `JMP`... Это поле `op`.
  **Операнд** (аргумент) — «с чем делать»: число в поле `arg`.
* **Интерпретатор** — программа, которая исполняет код «по одной инструкции», не
  превращая его в машинный код. Наша VM — интерпретатор байткода.
* **Нативный код** — код, скомпилированный в машинные инструкции процессора (то, что
  делает `c3c`). «Натив», «нативная функция» — функция движка, которую можно позвать из
  скрипта.
* **Тик** — один шаг игрового времени (обычно один кадр или один шаг фиксированного
  обновления из главы 01).

> **Коротко:** скрипт — гость, движок — хозяин. Скрипт записан байткодом —
> массивом простых инструкций, а VM — это цикл на C3, который их по одной выполняет.

## 1. Зачем движку скрипты

### 1.1. Пять инженерных причин

Скриптовый слой появляется в движке не потому, что C/C++/C3 «слишком сложны для
дизайнеров». Причины инженерные:

1. **Скорость итерации.** Пересборка и перезапуск игры — минуты. Перезагрузка скрипта —
   доли секунды, и игра при этом не теряет состояние: босс остаётся на второй фазе,
   игрок — у двери. Для геймплея, где 90% работы — подбор чисел и порядка событий, это
   разница между десятью итерациями в день и сотней.
2. **Изоляция.** Скрипт — недоверенный код. Ошибка в нём должна выключить один
   скрипт и показать сообщение, а не уронить процесс. Нативный код такой гарантии не
   даёт: один выход за границу массива — и вы отлаживаете порчу кучи.
3. **Разделение ролей.** Программист движка отвечает за *механизмы* (физика, анимация,
   ИИ-навигация), дизайнер — за *политику* (когда открыть дверь, что сказать NPC).
   Скриптовый API — это контракт между ними.
4. **Моддинг и живые игры.** Скрипты можно скачать с сервера или из Steam Workshop.
   Нативный код — нельзя (и не нужно: это дыра в безопасности).
5. **Выразительность во времени.** Геймплей — это последовательности: «подождать 3
   секунды», «дождаться, пока игрок войдёт в зону», «проиграть реплику и дождаться её
   конца». На сопрограммах это пишется линейно; в нативном коде — как конечный автомат
   с ручным хранением состояния.

**Аналогия.** Представьте театр. Сцена, свет, механика декораций — это движок; их
строят инженеры, долго и надёжно. Сценарий спектакля — это скрипт: его переписывают
на каждой репетиции, и если актёр забыл реплику, театр не должен рухнуть. Инженеры
дают режиссёру пульт с понятными кнопками («поднять занавес», «включить прожектор №3») —
это и есть скриптовый API.

### 1.2. Цена

Цена тоже понятна: интерпретатор в 10–50 раз медленнее нативного кода, граница
«скрипт ↔ движок» стоит дорого, отладка сложнее (нужен свой отладчик), появляется второй
язык со своей системой типов и управлением памятью, а сборщик мусора приносит паузы.

Почему интерпретатор медленнее? Потому что на каждую инструкцию скрипта VM выполняет
десяток-другой машинных инструкций: прочитать `Instr` из массива, выбрать ветку
`switch`, проверить стек, выполнить действие. Нативное `a + b` — это одна машинная
инструкция `add`.

> **Коротко:** скрипты дают скорость итерации, изоляцию ошибок, разделение ролей,
> моддинг и удобную запись «действий во времени». Платим за это скоростью и
> сложностью инструментов.

### 1.3. Общая схема

```
          ┌──────────────── редактор / пайплайн ассетов ────────────────┐
          │  intro.cs (текст) ──► компилятор ──► intro.csb (байткод)    │
          └──────────────────────────────────────────┬──────────────────┘
                                                     │ загрузка / hot reload
┌───────────────────────────── runtime ─────────────▼──────────────────────┐
│  ┌────────────┐  resume()  ┌────────────────────┐  CALL i  ┌───────────┐ │
│  │ Scheduler  │ ─────────► │ VM: pc, stack, env │ ───────► │ natives[] │ │
│  │ (по тикам) │ ◄───────── │  бюджет, проверки  │ ◄─────── │  (движок) │ │
│  └────────────┘ WAIT/END   └────────────────────┘  результат└─────┬─────┘ │
│                                                                   │       │
│                         хендлы, а не указатели ──────────► World / ECS    │
└────────────────────────────────────────────────────────────────────────────┘
```

Как читать эту картинку, сверху вниз:

1. Дизайнер пишет текст скрипта (`intro.cs`). Инструмент сборки ассетов (глава 07)
   превращает его в байткод (`intro.csb`) — §9.
2. Движок загружает байткод, а при изменении файла — перезагружает его на лету (§8).
3. **Планировщик** (Scheduler) каждый тик решает, какой скрипт «разбудить», и вызывает
   у него `resume()` (§7).
4. **VM** исполняет инструкции скрипта, следит за бюджетом и проверяет каждую операцию
   (§3–4).
5. Когда скрипту нужно что-то от движка, VM делает `CALL i` — вызывает i-ю нативную
   функцию из таблицы `natives[]` (§5).
6. Нативы работают с миром игры, но скрипту отдают только **хендлы**, а не указатели
   (§6).

Эта картинка — карта главы: VM и песочница (§3–4), привязки (§5), объекты движка в
скрипте (§6), сопрограммы и планировщик (§7), перезагрузка (§8).

### 1.4. Когда скрипты не нужны

Не каждый движок их имеет, и это нормальное решение:

* **Unreal Engine** отказался от UnrealScript в UE4. Геймплей пишут на C++ (с горячей
  перезагрузкой модулей — Live Coding) и в визуальных графах **Blueprints**, которые
  компилируются в байткод собственной VM. То есть VM осталась, но языка-текста нет.
* **Unity** использует C# — управляемый язык с JIT/AOT (IL2CPP). Это «скриптинг» по роли,
  но не по реализации: компилятор и рантайм чужие.
* Многие движки выбирают **data-driven** подход: поведение задаётся данными (таблицы,
  графы состояний, деревья поведения), а код интерпретирует данные. Правило: *данные
  описывают ЧТО, скрипт — КАК и КОГДА*. Если дизайнеру нужно только менять числа и
  связи — дайте ему редактор данных, а не язык программирования. Язык — когда нужна
  логика с ветвлениями и временем.
* Горячая перезагрузка нативного кода (глава 17) закрывает «скорость итерации» для
  программистов, но не изоляцию и не моддинг.

Пример, чтобы почувствовать разницу «данные vs скрипт». «У гоблина 30 HP и скорость 4» —
это данные, их правят в таблице. «Если гоблин ранен меньше чем наполовину — убегает к
ближайшему союзнику, ждёт 2 секунды и зовёт на помощь» — здесь ветвления и ожидание,
это уже скрипт (или дерево поведения).

> **Коротко:** скрипты — не обязательная часть движка. Если нужно менять только
> числа — хватит данных. Язык нужен, когда есть логика «если… то… подождать… потом…».

## 2. Пространство решений: взять готовое или написать своё

| Вариант | Плюсы | Минусы | Где встречается |
|---|---|---|---|
| **Lua 5.x** | крошечный (≈ 30 тыс. строк C), быстрый для интерпретатора, сопрограммы из коробки, отличный C API | динамическая типизация, 1-based индексы, GC-паузы, нет типов для больших кодовых баз | WoW (UI), Defold, Roblox (как Luau), CryEngine, десятки AAA-проектов |
| **LuaJIT** | на порядок быстрее Lua, FFI | застрял на Lua 5.1, JIT запрещён на консолях/iOS (нет W^X-страниц) | серверы, PC-игры, инструменты |
| **Luau** (Roblox) | постепенная типизация, песочница by design, interrupt-колбэк, быстрый интерпретатор | моложе, своя экосистема | Roblox, Alan Wake 2 и др. |
| **C# (Mono/CoreCLR/IL2CPP)** | статические типы, огромная экосистема, инструменты | тяжёлый рантайм, GC, «граница» дорогая | Unity, Godot (опционально), Stride |
| **AngelScript / Squirrel / Wren** | синтаксис «как C++» / классы, встраиваемость | меньше людей знает | Amnesia, Left 4 Dead 2 (Squirrel), инди |
| **Свой DSL + своя VM** | ровно те возможности, что нужны; детерминизм, бюджет, сериализуемые сопрограммы — под вашим контролем | вы пишете компилятор, отладчик, документацию, подсветку синтаксиса... | Naughty Dog (GOAL, позже DC/state scripts), HaloScript, многие студии |
| **Визуальный скриптинг** | доступен не-программистам, наглядность потоков | «спагетти», плохо диффится и мёржится, медленнее текста | Blueprints, Unity Visual Scripting, Frostbite |

Несколько слов из таблицы, которые могут быть незнакомы:

* **JIT** (just-in-time compilation) — компиляция байткода в машинный код *во время
  работы* программы. Очень быстро, но требует выделять память, в которую можно и
  писать, и потом исполнять.
* **W^X** («write xor execute») — правило защиты памяти: страница памяти может быть
  *либо* доступна для записи, *либо* исполняема, но не то и другое. На консолях и iOS
  это правило жёсткое, поэтому JIT там запрещён.
* **GC** (garbage collector, сборщик мусора) — механизм, который сам находит и
  освобождает ненужную память. Удобно, но иногда «останавливает мир» на несколько
  миллисекунд — в игре это заметный рывок.
* **DSL** (domain-specific language) — маленький язык под одну задачу (например, только
  для катсцен).
* **FFI** (foreign function interface) — способ вызвать C-функцию прямо из скрипта.
* **AOT** (ahead-of-time) — компиляция заранее, до запуска, а не во время работы (как
  делает IL2CPP в Unity).

Своя VM оправдана, когда вам нужно что-то, чего готовые не дают: **жёсткий детерминизм**
(lockstep-сеть, реплеи), **сериализуемые сопрограммы** (сохранение посреди катсцены),
**строгий бюджет** в микросекундах, интеграция с ECS без «объектов» или очень узкий
домен (диалоги, катсцены, ИИ-состояния). Именно такую маленькую VM мы строим в
упражнениях — и всё, что вы в ней сделаете, есть и в Lua, только спрятано за C API.

> **Коротко:** чаще всего берут Lua/Luau или C#. Свою VM пишут, когда нужен полный
> контроль: детерминизм, бюджет, сохранение посреди катсцены.

## 3. Внутренности VM: стековая vs регистровая, диспетчеризация

### 3.1. Из чего состоит VM

Минимальная VM — это всего четыре вещи:

| Часть | Что это | Аналогия |
|---|---|---|
| `code` | массив инструкций (байткод) | рецепт, по шагам |
| `pc` (program counter, счётчик команд) | номер **следующей** инструкции | палец, которым вы ведёте по строчкам рецепта |
| `stack` + `sp` | стек значений и число занятых ячеек (stack pointer) | стопка тарелок: кладём сверху, берём сверху |
| цикл диспетчеризации | `while` + `switch`, который выполняет инструкции | повар, который читает строчку и делает |

**Стек** — структура данных «последним положил — первым взял» (LIFO, last in — first
out). `push(x)` кладёт `x` наверх, `pop()` снимает верхний элемент. **Вершина стека** —
верхний, последний положенный элемент. В наших упражнениях `sp` — это *количество*
элементов: пустой стек — `sp == 0`, вершина лежит в `stack[sp - 1]`.

### 3.2. Стековая VM

Операнды лежат на стеке значений, инструкции неявно снимают и кладут:

```
a = b + c * 2          PUSH b ; PUSH c ; PUSH 2 ; MUL ; ADD ; STORE a
```

«Неявно» значит: у `ADD` нет аргументов вроде «сложи регистр 1 и регистр 2». Она всегда
берёт **два верхних** значения со стека и кладёт результат обратно.

Плюсы: тривиальный компилятор (обход AST в постфиксном порядке), компактные
инструкции (часто 1 байт + операнд). Минусы: много инструкций, много трафика через
стек. Так устроены JVM, CPython, WebAssembly, clox из «Crafting Interpreters».

**Постфиксный порядок** — сначала операнды, потом операция: вместо `2 + 3` пишем
`2 3 +`. Как на старых калькуляторах HP: набираете числа, потом жмёте операцию.

#### Пошаговый разбор: `(2 + 3) * 4 - 1`

Программа (это та же программа, что проверяет `e1401`):

```
0: PUSH 2
1: PUSH 3
2: ADD
3: PUSH 4
4: MUL
5: PUSH 1
6: SUB
7: HALT
```

Проследим состояние VM после каждой инструкции. Стек записываем слева направо, вершина
— справа.

| Шаг | pc до | Инструкция | Что происходит | Стек после | sp |
|---|---|---|---|---|---|
| 1 | 0 | `PUSH 2` | кладём 2 | `[2]` | 1 |
| 2 | 1 | `PUSH 3` | кладём 3 | `[2 3]` | 2 |
| 3 | 2 | `ADD` | снимаем b=3, снимаем a=2, кладём a+b=5 | `[5]` | 1 |
| 4 | 3 | `PUSH 4` | кладём 4 | `[5 4]` | 2 |
| 5 | 4 | `MUL` | b=4, a=5, кладём 20 | `[20]` | 1 |
| 6 | 5 | `PUSH 1` | кладём 1 | `[20 1]` | 2 |
| 7 | 6 | `SUB` | b=1, a=20, кладём **a − b** = 19 | `[19]` | 1 |
| 8 | 7 | `HALT` | снимаем вершину — это результат | `[]` | 0 |

Результат — 19, выполнено 8 инструкций.

**Порядок операндов важен.** На стеке лежит `a b`, где `b` — вершина (положен
последним). Значит, первый `pop()` возвращает **b**, второй — **a**. Для `ADD` и `MUL`
порядок не важен, а для `SUB` и сравнения `LT` — очень: `20 1 SUB` должно дать 19, а не
−18.

> **Частая ошибка.** Написать `self.push(self.pop()! - self.pop()!)`. Порядок
> вычисления двух `pop()` в одном выражении легко перепутать в голове, и результат
> окажется `b - a`. Снимайте операнды в отдельные переменные: сначала `b`, потом `a`.

#### Переходы: как устроены циклы

Чтобы у скрипта были `if` и `while`, нужны инструкции, которые меняют `pc`:

* `JMP n` — «безусловный переход»: следующей выполнится инструкция `n`.
* `JZ n` — «jump if zero»: снять значение со стека; если оно 0 — перейти на `n`, иначе
  идти дальше по порядку.
* `JNZ n` — наоборот, перейти, если **не** ноль.

Цикл `n = 0; while (n < 5) n = n + 1;` в стековом байткоде (из `e1401`):

```
0: PUSH 0      ; n
1: DUP         ; n n         <- начало цикла
2: PUSH 5      ; n n 5
3: LT          ; n (n<5)     1, если n<5, иначе 0
4: JZ 8        ; n           если условие ложно — выход из цикла
5: PUSH 1      ; n 1
6: ADD         ; n+1
7: JMP 1       ;             назад, на проверку условия
8: HALT
```

`DUP` («duplicate») копирует вершину: значение `n` нужно и для сравнения (оно
«съедается» `LT`), и для дальнейшей работы.

Посчитаем, сколько инструкций выполнится:

| Часть | Инструкции | Сколько раз | Итого |
|---|---|---|---|
| начало | `PUSH 0` | 1 | 1 |
| полная итерация (n = 0..4) | `DUP PUSH LT JZ PUSH ADD JMP` = 7 | 5 | 35 |
| последняя проверка (n = 5) | `DUP PUSH LT JZ` = 4 | 1 | 4 |
| выход | `HALT` | 1 | 1 |
| **всего** | | | **41** |

Эти 41 шаг — ровно то число, которое `e1401` ожидает в `vm.steps`. Полезно уметь
считать такие вещи на бумаге: так вы понимаете, *что* именно измеряет бюджет (§4).

`JMP 1` — это **обратный переход**: адрес назначения меньше текущего. Любой цикл
обязательно содержит обратный переход. Запомните это — пригодится в §4.

> **Коротко:** стековая VM берёт операнды с вершины стека и кладёт туда результат.
> Первым снимается правый операнд. Циклы — это обратные переходы `JMP`.

### 3.3. Регистровая VM

Инструкции адресуют «регистры» — слоты в кадре функции:

```
a = b + c * 2          MUL  r3, r2, K(2)
                       ADD  r0, r1, r3
```

Здесь `r0..r3` — не регистры процессора, а просто ячейки массива внутри вызова функции
(«кадра»): r0 = a, r1 = b, r2 = c, r3 — временная. `K(2)` — «константа 2». Одна
инструкция сама говорит, откуда брать операнды и куда положить результат, поэтому
`PUSH`/`POP` не нужны.

Инструкций в 1,5–2 раза меньше, значит меньше итераций цикла диспетчеризации — а
именно он доминирует в стоимости интерпретатора (непредсказуемый косвенный переход).
Цена — более сложный компилятор (распределение регистров) и широкие инструкции
(Lua 5: 32 бита — опкод 6 бит, A 8 бит, B/C по 9 бит). Lua перешла со стековой VM на
регистровую в версии 5.0 и описала выигрыш в статье «The Implementation of Lua 5.0» —
обязательное чтение.

Для игровой VM важнее другое: **размер и раскладка инструкций**. Байткод скрипта читается
последовательно, и «плотная» кодировка лучше ложится в кеш. В упражнениях инструкция —
`struct Instr { Op op; int arg; }` (8 байт с выравниванием). В продакшене кодируют в
`uint`: `op = ins & 0x3F`, `a = (ins >> 6) & 0xFF` и т.д.

Почему 8 байт? `Op` — это `enum Op : char`, то есть 1 байт, а `int arg` — 4 байта и
должен лежать по адресу, кратному 4 (глава 02, выравнивание). Компилятор вставляет 3
байта «пустоты» после `op`: 1 + 3 + 4 = 8.

> **Коротко:** регистровая VM выполняет меньше инструкций, но её сложнее компилировать.
> Для наших целей хватит стековой.

### 3.4. Цикл диспетчеризации

Сердце любой VM:

```c3
while (true)                                    // крутимся, пока скрипт не закончится
{
    if (self.steps++ >= budget) return BUDGET_EXCEEDED~;   // песочница, §4
    Instr ins = code[self.pc++];                // читаем инструкцию, pc -> следующая
    switch (ins.op)                             // «диспетчеризация»: выбор обработчика
    {
        case PUSH: self.push(ins.arg)!;         // ! — если push упал, выходим с ошибкой
        case ADD:
            int b = self.pop()!;                // сначала правый операнд (вершина)
            int a = self.pop()!;                // потом левый
            self.push(a + b)!;
        ...
    }
}
```

Что здесь происходит, по шагам:

1. Проверяем, не исчерпан ли бюджет (подробно — в §4).
2. Читаем инструкцию по адресу `pc` и **сразу** увеличиваем `pc`. Поэтому внутри
   обработчика `pc` уже указывает на следующую инструкцию, а `JMP` просто
   перезаписывает его.
3. `switch` выбирает ветку по опкоду. В C3 ветки `case` не «проваливаются» друг в
   друга, `break` в конце не нужен.
4. Любая операция может вернуть ошибку; `!` немедленно выходит из `run` с этой
   ошибкой. Скрипт остановлен, хост получает понятный fault.

**Диспетчеризация** — это и есть шаг 3: «посмотреть на опкод и прыгнуть в нужный
обработчик».

`switch` компилируется в таблицу переходов с ОДНИМ косвенным переходом на все опкоды —
предсказатель переходов CPU видит одну точку и угадывает плохо. Приёмы ускорения:

* **threaded code / computed goto** — переход на следующий обработчик в конце каждого
  обработчика, у каждого опкода своя точка перехода и своя история предсказаний.
  CPython и Lua используют его там, где компилятор умеет (`&&label` в GCC). В C3
  аналог — `@jump` на `switch` (упражнение 117 в треке по языку).
* **суперинструкции** — частые пары (`LOAD x; PUSH 1; ADD; STORE x`) склеиваются в одну
  (`INC x`): меньше диспетчеризаций.
* **кеширование вершины стека** в регистре, **inline caches** для поиска полей.
* и в предельном случае — JIT, который на консолях и iOS запрещён (нельзя выделять
  исполняемую память), поэтому быстрый *интерпретатор* для игр важнее JIT'а.

Что такое **предсказатель переходов**, в двух словах: процессор не ждёт, пока станет
известно, куда пойдёт `if` или `switch`, а *угадывает* и начинает выполнять заранее.
Угадал — бесплатно, не угадал — потерял 15–20 тактов. У `switch` в VM один «прыжок» на
все опкоды, и его история похожа на случайный шум — угадывать трудно. Если у каждого
обработчика свой прыжок, процессор может запомнить закономерности вида «после `LOAD`
обычно идёт `PUSH`».

Практическое правило: если скрипт тратит больше 1–2% кадра, проблема почти всегда не в
диспетчеризации, а в том, что скрипт делает работу движка (ищет сущности перебором,
считает расстояния в цикле). Лечится нативом, а не оптимизацией VM.

> **Коротко:** цикл диспетчеризации — `while` + `switch`: прочитать инструкцию,
> сдвинуть `pc`, выполнить. Самая дорогая часть интерпретатора — сам выбор ветки, но
> в играх тормоза обычно от того, *что* делает скрипт, а не от VM.

## 4. Песочница: VM обязана пережить любой байткод

**Песочница** (sandbox) — среда, в которой чужой код может делать только разрешённое и
не может навредить хозяину. Аналогия — детская песочница: внутри можно копать что
угодно, но песок не должен оказаться в квартире.

Скрипт мог написать моддер, дизайнер или вы сами в три часа ночи. Движок должен
пережить **любую** последовательность байтов. Линии обороны:

```
            ┌─ загрузка ───────────────┐  ┌─ выполнение ────────────────────┐
байткод ──► │ валидация: опкоды,       │─►│ бюджет инструкций за квант      │
            │ индексы глобальных,      │  │ проверки стека (over/underflow) │
            │ адреса переходов,        │  │ проверка pc / границ            │
            │ арность нативов          │  │ лимит памяти (свой аллокатор)   │
            └──────────────────────────┘  │ ошибка нативa -> ошибка скрипта │
                                          └─────────────────────────────────┘
```

Слева — проверки, которые делаются **один раз**, когда байткод загружается. Справа —
проверки, которые делаются **во время выполнения**, на каждой инструкции (или на
некоторых).

### 4.1. Бюджет инструкций

Бесконечный цикл — самая частая ошибка в скриптах. VM считает выполненные инструкции и
прерывает скрипт по исчерпании квоты. В Lua это делает
`lua_sethook(L, hook, LUA_MASKCOUNT, n)`, в Luau — колбэк `interrupt`, который
вызывается на обратных переходах и вызовах функций. Дешевле считать не каждую
инструкцию, а только **обратные переходы и вызовы** — любой бесконечный цикл обязан
их содержать. (`e1401`)

**Аналогия.** Бюджет — как монетки в игровом автомате: на каждую инструкцию тратится
монетка. Кончились — игра окончена, даже если скрипт «ещё не наигрался».

Важно договориться, **когда** проверять бюджет. В `e1401` правило такое: проверка стоит
*до* выполнения очередной инструкции, поэтому «бюджет 20» означает «ровно 20 выполненных
инструкций, а на попытке 21-й — ошибка». Проследим на цикле из §3.2 с бюджетом 3:

| Итерация цикла VM | steps до проверки | steps ≥ 3? | Выполняем | steps после |
|---|---|---|---|---|
| 1 | 0 | нет | `PUSH 0` | 1 |
| 2 | 1 | нет | `DUP` | 2 |
| 3 | 2 | нет | `PUSH 5` | 3 |
| 4 | 3 | **да** | — `BUDGET_EXCEEDED` | 3 |

Выполнено ровно 3 инструкции. Если перепутать `>` и `>=` или проверять *после*
выполнения, получится 2 или 4 — ошибка «на единицу», классика.

Почему достаточно считать только обратные переходы и вызовы? Программа без обратных
переходов и без вызовов — прямая «лента» инструкций: она обязательно дойдёт до конца за
`code.len` шагов. Зациклиться можно только прыгнув назад (или вызвав функцию, которая
вызывает себя). Значит, если ограничить число прыжков назад, ограничено и всё время
работы. В учебной VM мы для простоты считаем каждую инструкцию.

### 4.2. Проверки стека

`push` в полный стек и `pop` из пустого — ошибки скрипта, а не выходы за границу
массива хоста. Глубина рекурсии ограничивается так же.

* **Stack overflow** (переполнение) — попытка положить элемент в уже полный стек.
  Пример-«бомба»: `0: PUSH 1; 1: JMP 0` — кладёт единицы, пока стек не кончится.
* **Stack underflow** (опустошение) — попытка снять элемент из пустого стека. Пример:
  `PUSH 1; ADD` — для сложения нужно два значения, а есть одно.

Без проверок `stack[self.sp++] = v` при `sp == STACK_MAX` пишет *за конец массива* — в
соседние поля структуры или в чужую память. В safe-режиме C3 это паника (весь процесс
падает), в release — тихая порча памяти. Ни то, ни другое для «гостя» недопустимо.

### 4.3. Проверка `pc`

Перед чтением `code[self.pc]` убедитесь, что `0 <= pc < code.len`. Как `pc` может
оказаться за пределами?

* `JMP 99` в программе из 5 инструкций — «мусорный адрес перехода».
* Программа без `HALT` в конце: после последней инструкции `pc == code.len`, и VM
  «проваливается» за конец кода.

Оба случая в `e1401` называются `BAD_JUMP`.

### 4.4. Валидация при загрузке

Всё, что можно проверить статически, проверяйте один раз при загрузке: индексы констант
и глобальных, адреса переходов, арность вызовов нативов. Тогда в горячем цикле остаются
только динамические проверки. JVM делает это «верификатором байткода»; WebAssembly
валидирует модуль целиком до исполнения. (`e1402`, `e1405`)

Что значит «статически» и «динамически»?

* **Статически** — можно проверить, *не запуская* программу, просто глядя на байткод.
  `JMP 99` при длине кода 5 — ошибка, видна сразу. `LOAD 7` при 3 глобальных — тоже.
* **Динамически** — зависит от хода выполнения. Хватит ли места на стеке, зависит от
  того, сколько раз прокрутится цикл; это узнаешь только во время работы.

**Горячий цикл** — код, который выполняется очень много раз (здесь — цикл
диспетчеризации). Каждая проверка, вынесенная из него в загрузку, экономит время на
каждой инструкции.

### 4.5. Лимит памяти

VM выделяет память только через свой аллокатор с бюджетом (`lua_newstate` принимает
функцию-аллокатор именно для этого). Скрипт, создавший миллион таблиц, получает ошибку
«out of memory», а не съедает память игры. (Аллокаторы — глава 02.)

### 4.6. Возможности, а не запреты

Скрипт может делать только то, что ему дали нативами. Нет натива `open_file` — нет
доступа к диску. Это модель capability-based security, и она надёжнее, чем «чёрный
список опасных функций». Разным скриптам можно давать разные таблицы нативов
(UI-скрипту — одни, моду — урезанные).

**Аналогия.** Гостю в гостинице выдают ключ-карту, которая открывает только его номер и
спортзал. Не нужно составлять список «куда нельзя» — всё, что не разрешено картой,
закрыто само собой. Забыть запретить что-то опасное невозможно: опасного просто нет в
списке выданного.

> **Коротко:** пять линий обороны — бюджет, проверки стека, проверка `pc`, валидация
> при загрузке, лимит памяти — плюс принцип «скрипт может только то, что ему выдали».

### 4.7. Ошибки как Optional'ы C3

Ошибки в C3 удобно моделировать Optional'ами: каждая операция VM возвращает `T?`, а `!`
пробрасывает ошибку наверх. Любая инструкция может «упасть», и падение мгновенно
завершает квант — ровно та семантика, что нужна:

```c3
excuse STACK_OVERFLOW, STACK_UNDERFLOW, BUDGET_EXCEEDED, BAD_JUMP;  // виды ошибок VM

fn int? Vm.pop(&self)                              // int? — «int или ошибка»
{
    if (self.sp <= 0) return STACK_UNDERFLOW~;     // пусто: возвращаем ошибку, ~ делает из неё Optional
    return self.stack[--self.sp];                  // иначе уменьшаем sp и отдаём вершину
}
```

Обратите внимание на `--self.sp` (префиксный декремент): сначала уменьшаем `sp`, потом
читаем ячейку. Если `sp == 3`, вершина лежит в `stack[2]` — как раз `--sp` даёт 2.

Ниже — полная маленькая VM, которая собирается и запускается на c3c 0.8.5. В ней
другие опкоды, чем в `e1401` (`NEG` и `PRINT`), но все линии обороны на месте — это
образец того, как выглядит «VM, которая не падает».

```c3
module mini_vm;
import std::io;

excuse STACK_OVERFLOW, STACK_UNDERFLOW, BUDGET_EXCEEDED, BAD_JUMP;

enum Op : char
{
    PUSH,   // положить arg на стек
    NEG,    // a -> -a
    PRINT,  // снять вершину и напечатать
    JMP,    // pc = arg
    HALT,   // остановиться
}

struct Instr
{
    Op op;
    int arg;
}

struct Vm
{
    int[4] stack;   // крошечный стек: 4 ячейки
    int sp;         // сколько ячеек занято
    int pc;         // номер следующей инструкции
    int steps;      // сколько инструкций уже выполнено
}

fn void? Vm.push(&self, int v)
{
    if (self.sp >= 4) return STACK_OVERFLOW~;   // некуда класть
    self.stack[self.sp++] = v;                  // кладём и сдвигаем sp
}

fn int? Vm.pop(&self)
{
    if (self.sp <= 0) return STACK_UNDERFLOW~;  // нечего снимать
    return self.stack[--self.sp];
}

fn void? Vm.run(&self, Instr[] code, int budget)
{
    *self = {};                                  // обнуляем sp, pc, steps
    while (true)
    {
        if (self.steps >= budget) return BUDGET_EXCEEDED~;          // монетки кончились
        if (self.pc < 0 || self.pc >= code.len) return BAD_JUMP~;   // pc вне кода
        Instr ins = code[self.pc++];
        self.steps++;
        switch (ins.op)
        {
            case PUSH: self.push(ins.arg)!;
            case NEG: self.push(-self.pop()!)!;                    // pop может упасть -> выходим
            case PRINT: io::printfn("print %d", self.pop()!);
            case JMP: self.pc = ins.arg;                            // проверим на следующей итерации
            case HALT: return;
        }
    }
}

fn void main()
{
    Vm vm;
    Instr[] ok = { { PUSH, 5 }, { NEG, 0 }, { PRINT, 0 }, { HALT, 0 } };
    vm.run(ok, 100)!!;                                   // print -5

    Instr[] bad = { { PRINT, 0 } };                      // pop из пустого стека
    if (catch err = vm.run(bad, 100)) io::printfn("bad: %s", err);

    Instr[] spin = { { JMP, 0 } };                       // вечный цикл
    if (catch err = vm.run(spin, 10)) io::printfn("spin: %s after %d steps", err, vm.steps);
}
```

Вывод:

```
print -5
bad: mini_vm::STACK_UNDERFLOW
spin: mini_vm::BUDGET_EXCEEDED after 10 steps
```

Что стоит заметить:

* Ни одна «вредная» программа не уронила процесс: каждая получила свою ошибку, а `main`
  продолжил работу.
* `JMP` не проверяет адрес сам — проверка `pc` в начале следующей итерации ловит и
  плохой прыжок, и «провал за конец кода» одной строкой.
* `self.push(-self.pop()!)!` — здесь два `!`: первый пробрасывает ошибку `pop`, второй —
  ошибку `push`.
* `!!` в `main` означает «я уверен, что ошибки не будет; если будет — паника». Для
  тестов это нормально, для движка — нет: движок ловит ошибку через `catch`.

### 4.8. Что делать с упавшим скриптом

Что делать с упавшим скриптом — политика движка: выключить и показать ошибку на экране
(в разработке), молча выключить и записать в лог (в релизе), перезапустить объект.
Важно лишь, что ошибка **локальна**: остальные скрипты и кадр продолжают работать.

> **Частые ошибки (песочница).**
> * Проверять бюджет после выполнения инструкции или через `>` вместо `>=` — получаете
>   на одну инструкцию больше или меньше, чем обещано.
> * Проверять `pc` только в `JMP`, а «провал за конец» без `HALT` забыть.
> * Проверять стек в одних опкодах и не проверять в других. Проще всего, когда
>   *все* опкоды ходят только через безопасные `push`/`pop`.
> * Использовать `!!` внутри VM: это паника всего процесса — ровно то, от чего
>   песочница должна защищать.

## 5. Привязки: граница «скрипт ↔ движок»

**Привязка** (binding) — прослойка, через которую скрипт вызывает функцию движка.
Аналогия — розетка и вилка: у приборов разная начинка, но к сети все подключаются
через один стандартный разъём.

### 5.1. Единая сигнатура

Скрипту нужен доступ к движку: заспавнить врага, проиграть звук, прочитать позицию.
Все нативные функции приводятся к одной сигнатуре, которую понимает VM:

```c3
alias NativeFn = fn int?(int[] args, void* ctx);   // тип «указатель на функцию натива»

struct Native
{
    String name;      // как функцию зовут в скрипте: "move"
    int arity;        // сколько аргументов она принимает
    NativeFn func;    // что вызывать
}
```

**Сигнатура** — «форма» функции: какие у неё параметры и что она возвращает. Зачем
одна на всех? VM не может знать, что у `move` два аргумента, а у `spawn` — один.
Поэтому все нативы выглядят для VM одинаково: «дай мне срез аргументов и контекст, верну
число или ошибку».

* `args` — **окно стека VM**, а не копия: `stack[base : arity]`. Так устроен Lua C API —
  натив работает с аргументами прямо на стеке `lua_State`.
* `ctx` — непрозрачный указатель на хост (мир, игру). VM не знает, что это.
* `int?` — натив может завершиться ошибкой, и она станет ошибкой скрипта.

**Арность** — число аргументов функции. У `move(h, dx)` арность 2, у `answer()` — 0.

**Непрозрачный указатель** (`void*`) — указатель «на что-то», тип которого VM не знает и
не должна знать. VM лишь передаёт его нативу. Натив знает, что там `Game*` или
`World*`, и приводит: `Game* g = ctx;`. Так VM остаётся независимой от конкретной игры.

### 5.2. Вызов: окно стека

Вызов из VM:

```
стек до CALL move/2:   [... h dx]          base = sp - 2
                              ^^^^ args = stack[base:2]
стек после:            [... result]        sp = base; push(result)
```

Разберём на числах. Пусть на стеке `[7 100 -5]` (sp = 3), и скрипт вызывает `move` с
арностью 2.

| Шаг | Действие | stack | sp |
|---|---|---|---|
| 0 | перед `CALL` | `[7 100 -5]` | 3 |
| 1 | `base = sp - arity = 3 - 2 = 1` | `[7 100 -5]` | 3 |
| 2 | `args = stack[1:2]` → это `{100, -5}`; вызываем `func(args, ctx)` → допустим, 95 | `[7 100 -5]` | 3 |
| 3 | «снимаем» аргументы: `sp = base` | `[7]` (ячейки 1 и 2 теперь свободны) | 1 |
| 4 | кладём результат | `[7 95]` | 2 |

Значение 7 «ниже» аргументов не тронуто — это чужие данные скрипта.

Почему окно, а не копия? Копирование — лишняя работа на каждом вызове. Срез C3 —
это просто «указатель + длина», он ничего не копирует. Натив читает `args[0]` и
`args[1]` прямо из стека VM.

Перед вызовом VM обязана убедиться, что на стеке есть хотя бы `arity` значений (иначе
`base` станет отрицательным и окно вылезет за начало массива), и что результат натива
не ошибка. Если натив вернул ошибку — инструкция «падает», скрипт останавливается, и
**следующие** инструкции не выполняются (в `e1402` это проверяется: после ошибки в
`div` натив `give_gold` вызваться не должен).

### 5.3. Линковка по имени, вызов по индексу

Человек пишет `call move`, но искать строку на каждом вызове — дорого. Поэтому имена
разрешаются **один раз** — при загрузке скрипта: `"move" → 1`. Заодно проверяется
арность, и опечатка в имени функции обнаруживается при загрузке уровня, а не через
двадцать минут игры. Динамические проверки в VM всё равно остаются, потому что байткод
может прийти в обход загрузчика (файл с диска, сеть).

**Линковка** (связывание) — замена символических имён на конкретные адреса или индексы.
Аналогия: в записной книжке вы ищете «Мама» один раз и пишете номер на стикере у
телефона, а не листаете книжку при каждом звонке.

Пример. Таблица нативов и «сырой» байткод:

```
natives:  0 add/2   1 mul/2   2 clamp/3   3 answer/0   4 give_gold/1

до линковки                  после линковки
PUSH 2                       PUSH 2
PUSH 3                       PUSH 3
CALL "add",  передаёт 2  ─►  CALL 0, передаёт 2     (имя найдено, 2 == 2 — ок)
CALL "give_gld", 1       ─►  ошибка UNKNOWN_NATIVE  (опечатка, нашли при загрузке)
CALL "add",  передаёт 1  ─►  ошибка ARITY_MISMATCH  (add ждёт 2)
```

Индексы стабильны только в пределах одной сборки движка. Если байткод хранится на диске
долго (моды!), храните в нём имена, а индексы вычисляйте при загрузке — иначе
добавление нового натива в середину таблицы сломает все старые скрипты. Это тот же
вопрос версионирования, что и в главе 13.

Пример поломки: в версии 1.0 таблица `[spawn, move, play_sound]`, мод сохранил
`CALL 2` (= `play_sound`). В версии 1.1 добавили `damage` вторым: `[spawn, damage, move,
play_sound]`. Старый `CALL 2` теперь вызывает `move` — и мод вместо звука двигает
сущность. С именами в файле такого не случится.

> **Коротко:** имена → индексы один раз при загрузке (и там же проверка арности и
> опечаток). В рантайме — только быстрый вызов по индексу плюс дешёвые проверки.

### 5.4. Генерация трамплинов

**Трамплин** — маленькая функция-переходник: принимает «универсальные» `args` и
вызывает «настоящую» функцию с нормальными параметрами. Пример, написанный вручную:

```c3
fn int clamp(int v, int lo, int hi) => v < lo ? lo : (v > hi ? hi : v);   // обычная функция

fn int? clamp_trampoline(int[] args, void* ctx)        // форма NativeFn
{
    return clamp(args[0], args[1], args[2]);           // распаковываем окно стека
}
```

Писать для каждой функции движка прослойку `args → параметры` вручную скучно и опасно.
В C++ это делают шаблоны (sol2, LuaBridge, pybind11). В C3 хватает макроса с
рефлексией — число параметров функции известно на этапе компиляции, а срез можно
распаковать в аргументы вызова:

```c3
fn int clamp(int v, int lo, int hi) => v < lo ? lo : (v > hi ? hi : v);

macro int? @bind(NativeTable* t, String name, $f)
{
    $if $Typeof($f)::params.len == 0:                                     // функция без параметров
        return t.add(name, 0, fn int?(int[] a, void* ctx) => $f());
    $else
        return t.add(name, $Typeof($f)::params.len,                       // арность — из типа функции
                     fn int?(int[] a, void* ctx) => $f(...a[:$Typeof($f)::params.len]));
    $endif
}

@bind(&natives, "clamp", &clamp)!!;     // арность 3 выведена компилятором
```

Разберём по кусочкам:

* `$f` — параметр макроса времени компиляции (знак `$`). Сюда приходит `&clamp`.
* `$Typeof($f)` — тип этого значения: «указатель на функцию `fn int(int, int, int)`».
* `::params` — рефлексия: список параметров этого типа функции; `.len` = 3.
* `...a[:3]` — **распаковка** среза в аргументы: то же самое, что `a[0], a[1], a[2]`.
  Длина должна быть известна при компиляции — здесь она известна, это константа 3.
* `$if ... $else ... $endif` — условие времени компиляции. Нужна отдельная ветка для
  функций без параметров: распаковывать срез нулевой длины нельзя.
* `fn int?(int[] a, void* ctx) => ...` — лямбда. Её тип совпадает с `NativeFn`, поэтому
  её можно положить в таблицу.

Лямбда внутри макроса ссылается на `$f` — это не захват переменной, а подстановка
константы времени компиляции, поэтому для каждой привязанной функции получается своя
маленькая функция-трамплин. Тот же приём расширяется на типы параметров (`$p.type` из
`::params`) — float, bool, хендлы — с проверкой типа значения на стеке. (`e1402`)

Напомним: лямбды C3 **не захватывают** переменные. `fn ... => x + 1`, где `x` — обычная
локальная переменная, не скомпилируется. Но `$f` — не переменная, а константа, которую
компилятор просто вписывает в тело лямбды. Поэтому `@bind(&natives, "clamp", &clamp)`
и `@bind(&natives, "add", &add)` порождают две *разные* лямбды.

Чтобы убедиться, что приём рабочий, — полная программа (проверена на c3c 0.8.5):

```c3
module bind_demo;
import std::io;

excuse TABLE_FULL;

alias NativeFn = fn int?(int[] args, void* ctx);   // единая сигнатура натива

struct Native
{
    String name;     // имя, по которому скрипт зовёт функцию
    int arity;       // сколько аргументов она ждёт
    NativeFn func;   // указатель на трамплин
}

struct NativeTable
{
    Native[8] items;
    int count;
}

fn int? NativeTable.add(&self, String name, int arity, NativeFn func)
{
    if (self.count >= 8) return TABLE_FULL~;
    self.items[self.count] = { name, arity, func };
    return self.count++;                            // индекс нового натива
}

fn int clamp(int v, int lo, int hi) => v < lo ? lo : (v > hi ? hi : v);
fn int seven() => 7;

macro int? @bind(NativeTable* t, String name, $f)
{
    $if $Typeof($f)::params.len == 0:
        return t.add(name, 0, fn int?(int[] a, void* ctx) => $f());
    $else
        return t.add(name, $Typeof($f)::params.len,
                     fn int?(int[] a, void* ctx) => $f(...a[:$Typeof($f)::params.len]));
    $endif
}

fn void main()
{
    NativeTable natives;
    @bind(&natives, "clamp", &clamp)!!;
    @bind(&natives, "seven", &seven)!!;
    int[3] args = { 20, 0, 15 };                    // «окно стека»: clamp(20, 0, 15)
    Native n = natives.items[0];
    io::printfn("%s/%d -> %d", n.name, n.arity, n.func(args[:3], null)!!);
    io::printfn("%s/%d -> %d", natives.items[1].name, natives.items[1].arity,
                natives.items[1].func(args[:0], null)!!);
}
```

Вывод:

```
clamp/3 -> 15
seven/0 -> 7
```

Обратите внимание: функцию C3 передаём как `&clamp` — в C3 функция как значение
берётся только через `&`.

> **Коротко:** трамплин превращает `args` в нормальные параметры. Макрос с рефлексией
> генерирует трамплины сам и сам узнаёт арность — ни одной ручной прослойки.

### 5.5. Стоимость границы

Каждый вызов натива — это проверка арности, (у динамических языков) проверка типов
аргументов, косвенный вызов, иногда упаковка результата. Это десятки наносекунд.
Скрипт, который в цикле на 1000 врагов вызывает `get_pos`, `distance`, `get_hp` —
это тысячи пересечений границы за кадр. Правила хорошего API:

* **крупные нативы** — `find_enemies_in_radius(pos, r)` вместо перебора в скрипте;
* **пакетные операции** — отдать скрипту массив, а не по одному элементу;
* **скрипт принимает решения, движок выполняет работу**: скрипт решает «атаковать»,
  а поиск пути, анимация и физика происходят в нативных системах.

Прикинем. Пусть один вызов натива — 50 нс, и скрипт для 1000 врагов делает 3 вызова на
каждого. Это 3000 × 50 нс = 150 мкс — почти 1% кадра в 16,6 мс только на «переход
границы», ещё до работы самого скрипта. Один натив `find_enemies_in_radius` заменяет
3000 переходов одним.

**Аналогия.** Таможня: каждое пересечение границы — проверка документов. Возить товар
по одной коробке дорого; выгоднее одна большая фура.

> **Частые ошибки (привязки).**
> * Искать натив по строке при каждом `CALL` вместо линковки.
> * Проверить арность только при линковке и забыть, что байткод может прийти «сырым»,
>   в обход `link()`: VM всё равно должна убедиться, что на стеке достаточно значений.
> * Снимать аргументы по одному через `pop()` во временный массив: они окажутся в
>   **обратном** порядке (первым снимется последний аргумент). Окно стека
>   `stack[base:arity]` уже лежит в правильном порядке и ничего не копирует.
> * Положить результат, не «сняв» аргументы (`sp = base`): стек будет расти с каждым
>   вызовом.
> * Делать мелкие нативы и звать их в цикле тысячи раз.

## 6. Объекты движка в скрипте: хендлы, а не указатели

### 6.1. Проблема: скрипт помнит дольше, чем живёт объект

Скрипт живёт дольше, чем вы думаете. Он сохранил «цель» в переменную, подождал три
секунды — а цель за это время умерла, и её слот занял новый враг. Если скрипт хранил
указатель, он теперь молча бьёт чужую сущность или читает освобождённую память. Это
use-after-free, запущенный недоверенным кодом.

**Use-after-free** — обращение к памяти после того, как её освободили (или отдали
другому объекту). Аналогия: вы записали номер комнаты в гостинице, где живёт друг. Друг
выехал, в номер заселился незнакомец. Вы приходите «к другу» — и вручаете подарок
незнакомцу. Номер комнаты (указатель) по-прежнему «правильный», но *жилец* уже другой.

### 6.2. Решение: хендл с поколением

Решение — скрипт видит только **хендл** с поколением (глава 03):

```
int handle:   31 ........ 12 11 ...... 0
              [ generation ][   index   ]

destroy(index):  slots[index].gen++     ← все выданные хендлы на слот протухли
resolve(h):      index < used && alive && slots[index].gen == gen(h)
                 иначе STALE_HANDLE
```

* **Хендл** (handle, «ручка») — число, по которому движок может найти объект, но
  которое само по себе не даёт доступа к памяти.
* **index** (младшие 12 бит) — номер слота в массиве сущностей.
* **generation** (старшие биты) — «номер жильца»: сколько раз слот переиспользовали.
* **Протухший** (stale) хендл — хендл, чьё поколение не совпадает с текущим поколением
  слота: объект, на который он указывал, уже уничтожен.

Продолжая аналогию с гостиницей: хендл — это «комната 3, гость №5». Когда гость №5
выезжает, на табличке у двери пишут «гость №6». Ваша записка «комната 3, гость №5» уже
не подходит — портье вас не пустит.

Упаковка — обычная работа с битами из главы 03: поколение сдвигается влево на
`INDEX_BITS`, индекс занимает младшие биты, а вынуть их обратно помогают сдвиг вправо и
маска `INDEX_MASK`. Например, при `INDEX_BITS = 12` хендл «индекс 3, поколение 5»
равен `5 · 4096 + 3 = 20483`.

**Почему поколения начинаются с 1?** Тогда хендл, равный 0, невозможен (у него
поколение 0), и 0 можно использовать как «пустой хендл» — аналог `null` для скрипта.
Неинициализированная глобальная переменная скрипта (= 0) автоматически невалидна.

### 6.3. Пошаговая история одного слота

Мир на 4 слота. Проследим слот 0:

| Шаг | Событие | slots[0].gen | alive | Хендлы, которые есть у скрипта |
|---|---|---|---|---|
| 1 | `spawn` гоблина → слот 0 | 1 | да | goblin = (idx 0, gen 1) |
| 2 | `damage(goblin, 12)` → resolve: gen 1 == 1 ✓ | 1 | да | goblin |
| 3 | `damage(goblin, 100)` → hp ≤ 0 → `destroy(0)` | **2** | нет | goblin (уже протух!) |
| 4 | `alive(goblin)` → gen 1 ≠ 2 → «нет» | 2 | нет | goblin |
| 5 | `spawn` летучей мыши → свободный слот 0 | 2 | да | goblin (gen 1), bat = (idx 0, gen 2) |
| 6 | `damage(goblin, 1)` → gen 1 ≠ 2 → **STALE_HANDLE** | 2 | да | мышь не тронута |
| 7 | `damage(bat, 1)` → gen 2 == 2 ✓ | 2 | да | работает |

Ключевой момент — шаг 6. С указателем `Entity*` скрипт ударил бы мышь (она лежит в той
же памяти). С хендлом поколения не совпали, и удар отклонён.

Обратите внимание на шаг 4: недостаточно проверить только поколение. Между шагами 3 и
5 слот пуст (`alive == false`), а поколение уже увеличено — тут хендл и так не
совпадёт. Но что, если кто-то сконструирует хендл `(idx 0, gen 2)` ровно в этот момент?
Поэтому `resolve` проверяет все три условия: индекс в пределах выданных слотов, слот
жив, поколение совпадает.

### 6.4. Одна дверь из мира хендлов в мир указателей

Каждый натив переводит хендл в указатель через **одну** функцию `resolve` и не хранит
указатель дольше вызова. Протухший хендл — либо ошибка скрипта (строгие нативы:
`damage`, `move`), либо нормальный ответ «нет» (мягкие: `is_alive`). Хорошее API
обычно предлагает оба стиля. (`e1403`)

Почему «одна функция»? Если проверка размазана по двадцати нативам, где-нибудь её
обязательно забудут. Одна дверь — одно место, которое нужно сделать правильно и
протестировать.

Почему «не хранить указатель дольше вызова»? Внутри одного натива мир не меняется
(никто не уничтожит сущность посреди `n_move`), поэтому указатель там безопасен. Но
между вызовами может случиться что угодно.

### 6.5. Прокси в языках со сборщиком мусора

В языках со сборщиком мусора (Lua, C#) объекты движка обычно отдаются как *userdata* /
*прокси-объект*, внутри которого лежит тот же хендл. Ошибка «держать указатель в
userdata» — классика: сборщик скрипта держит прокси живым, а движок уже уничтожил
сущность. Владение всегда у движка; скрипт владеет только ссылкой.

**Userdata** в Lua — блок памяти, которым управляет Lua, но содержимое которого
понимает только C-код. **Прокси** — объект-заместитель: выглядит как сущность («у него
есть методы `move`, `damage`»), а внутри хранит лишь хендл и каждый раз спрашивает
движок.

Две смежные проблемы:

* **Идентичность.** Два прокси на одну сущность должны быть равны (`==`). Либо
  кешируйте прокси по хендлу (слабая таблица в Lua), либо сравнивайте хендлы.
* **ECS.** В ECS «сущность» — просто id, и хендл ложится на неё естественно. Компоненты
  скрипту лучше отдавать через нативы-запросы (`get_health(e)`), а не по указателю на
  массив компонентов — массивы переезжают при росте и при смене архетипа.

> **Коротко:** скрипт держит только хендлы «индекс + поколение». `destroy` увеличивает
> поколение — и все старые хендлы протухают. Указатель живёт только внутри натива,
> получен через единственную функцию `resolve`.

> **Частые ошибки (хендлы).**
> * Забыть увеличить поколение в `destroy` — тогда старый хендл «оживает», как только
>   слот займут снова.
> * Проверять в `resolve` индекс по `MAX_ENTITIES`, а не по числу реально выданных
>   слотов: невыданный слот содержит нули и может случайно «совпасть».
> * Перепутать, какие биты где: проверьте на примере, что `index(make(3, 5)) == 3` и
>   `gen(make(3, 5)) == 5`.
> * Сохранить `Entity*` в поле «на потом».

## 7. Сопрограммы: геймплей во времени

### 7.1. Проблема: «подожди 3 секунды» в игре

В обычной программе «подождать 3 секунды» — это `sleep(3)`. В игре так нельзя: если
скрипт двери уснёт по-настоящему, остановится весь кадр — и вся игра. Игровой цикл
должен каждые 16 мс рисовать кадр, а дверь должна «ждать» *параллельно* с этим.

Сравните одну и ту же катсцену:

```
// конечный автомат в нативном коде            // сопрограмма в скрипте
switch (self.state) {                         say "door opens"
  case OPENING:                               wait 3
    say("door opens");                        say "door closes"
    self.timer = 3; self.state = WAITING;     end
  case WAITING:
    if (--self.timer > 0) return;
    self.state = CLOSING;
  case CLOSING: ...
}
```

Слева — **конечный автомат** (state machine): объект хранит поле `state` («в какой я
фазе»), и каждый кадр функция смотрит на него и решает, что делать. Это работает, но
логика «открыть → ждать → закрыть» размазана по веткам `switch`, а каждое новое
ожидание добавляет новое состояние и новое поле-таймер. Справа — то же самое, но
читается сверху вниз, как рецепт.

Сопрограмма — функция, которая может **приостановиться** (yield) и позже
**продолжиться** с того же места, сохранив локальные переменные. Именно этим
выразительность скриптов выигрывает у нативного кода.

* **yield** («уступить») — приостановиться и отдать управление обратно тому, кто нас
  вызвал (планировщику).
* **resume** («продолжить») — вызвать сопрограмму снова; она продолжает со следующей
  после yield строки.

**Аналогия.** Закладка в книге. Вы читаете, доходите до «подождать 3 дня», кладёте
закладку и закрываете книгу. Через 3 дня открываете на закладке и читаете дальше. Вся
«память» о том, где вы были, — в закладке, а не в вашей голове. Сопрограмма — книга с
закладкой; `pc` — это и есть закладка.

### 7.2. Секрет: состояние сопрограммы — это просто структура

Самое важное наблюдение главы: если всё, что нужно для продолжения, лежит в структуре,
то «приостановиться» — это обычный `return`. Вот сопрограмма двери без всякой VM, на
голом C3 (компилируется и работает):

```c3
module coro_demo;
import std::io;

// «Сопрограмма» без VM: всё её состояние — в структуре.
struct Door
{
    int pc;          // на каком шаге мы остановились (закладка)
    long wake_tick;  // когда проснуться
    bool done;
}

// Вызывается каждый тик. Возвращает управление (= yield), когда надо ждать.
fn void Door.resume(&self, long now)
{
    if (self.done || now < self.wake_tick) return;   // ещё спим (или уже всё)
    switch (self.pc)
    {
        case 0:
            io::printfn("t=%d door opens", now);
            self.wake_tick = now + 3;    // «wait 3»: запомнили, когда будить
            self.pc = 1;                 // запомнили, откуда продолжить
            return;                      // yield: просто выходим
        case 1:
            io::printfn("t=%d door closes", now);
            self.done = true;            // «end»
    }
}

fn void main()
{
    Door d;
    for (long t = 0; t < 6; t++) d.resume(t);   // игровой цикл: 6 тиков
}
```

Вывод:

```
t=0 door opens
t=3 door closes
```

Посмотрим, что происходит в каждом тике:

| Тик | pc до | wake_tick до | Что делает `resume` | pc после | wake_tick после |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 ≥ 0 → `case 0`: печать «opens», «wait 3» | 1 | 3 |
| 1 | 1 | 3 | 1 < 3 → сразу `return` (спим) | 1 | 3 |
| 2 | 1 | 3 | 2 < 3 → спим | 1 | 3 |
| 3 | 1 | 3 | 3 ≥ 3 → `case 1`: печать «closes», done | 1 | 3 |
| 4–5 | — | — | done → `return` | — | — |

Это и есть сопрограмма — только «вручную». VM делает то же самое, но `pc` указывает
не на `case` в `switch`, а на инструкцию байткода, и программист скрипта вообще не
видит этой механики — он просто пишет `wait 3`.

> **Коротко:** сопрограмма = код + «закладка» (`pc`, стек, локальные) в структуре.
> Yield — это `return` из `resume()`, продолжение — повторный `resume()`.

### 7.3. Stackless vs stackful

* **Stackless (относительно хоста).** Состояние выполнения скрипта — `pc`, стек
  значений, локальные — лежит в структуре VM, а не на стеке C. Тогда yield — это просто
  `return` из `resume()`, а продолжение — повторный `resume()` с сохранённого `pc`.
  Сопрограмма стоит столько, сколько её структура: тысяча скриптов — тысяча маленьких
  объектов. Так работают сопрограммы Lua (каждая — отдельный `lua_State` со своим
  стеком значений), генераторы Python, наша VM.
* **Stackful.** Сопрограмма имеет собственный машинный стек (fibers, глава 12). Можно
  уступить управление из глубины нативного вызова, но каждая стоит десятки килобайт и
  переключение контекста.

Здесь важно различать два стека:

* **стек значений VM** — наш массив `int[8] stack` внутри структуры скрипта;
* **стек хоста** (машинный стек, стек вызовов C3) — где живут локальные переменные
  функций C3 и адреса возврата.

«Stackless» значит «сопрограмме не нужен *свой собственный машинный* стек». Пока скрипт
спит, на машинном стеке от него не остаётся ничего: `resume()` уже вернулся.

Подводный камень stackless-подхода: нельзя сделать yield **изнутри натива**, вызванного
скриптом, — стек хоста к этому моменту не пуст. В Lua для этого есть `lua_yieldk` с
продолжением (continuation function). Простое решение для игровой VM: «ожидающие»
операции (`wait`, `wait_anim`, `wait_event`) — это инструкции VM или нативы, которые
лишь *ставят условие пробуждения* и возвращают специальный код «yield».

Почему нельзя из натива? Представьте цепочку вызовов: `Scheduler.tick` → `resume` →
`n_play_dialog` → `audio::play` → ... Если глубоко внутри `audio::play` мы захотим
«уснуть до конца реплики», нам придётся вернуться из всех этих функций — и их
локальные переменные пропадут. Продолжить «изнутри `audio::play`» уже нельзя. Поэтому
натив не ждёт сам: он *говорит* VM «усыпи скрипт до события X» и спокойно возвращается.

> **Коротко:** stackless — дёшево, но уступать можно только «на верхнем уровне»
> (в самой VM). Stackful — может уступить откуда угодно, но дорог по памяти.

### 7.4. Планировщик

**Планировщик** (scheduler) — часть движка, которая каждый тик решает, каким скриптам
дать поработать. Аналогия: учитель в классе, который по очереди спрашивает учеников;
кто сказал «я подумаю до пятницы» — того до пятницы не спрашивают.

```
tick(now):
  for s in scripts (в порядке добавления — детерминизм!):
     if s.WAITING and now >= s.wake_tick:   s -> READY
     if s.READY:
        resume(s):  выполнять, пока не WAIT / END / ошибка / бюджет кванта
           WAIT n -> s.WAITING, s.wake_tick = now + max(n, 1)
           END    -> s.DONE
           ошибка -> s.FAULTED, сообщение, остальные продолжают
```

Состояния скрипта:

```
            WAIT n                    now >= wake_tick
  READY ───────────────► WAITING ─────────────────────► READY
    │                                                     
    ├── END ──────────► DONE       (больше не запускается)
    └── ошибка/бюджет ─► FAULTED   (больше не запускается)
```

* **READY** — готов работать, получит квант в этом тике.
* **WAITING** — спит до тика `wake_tick`.
* **DONE** — дошёл до `END`.
* **FAULTED** — упал (ошибка стека, исчерпан квант и т.п.).

**Квант** (time slice) — сколько работы скрипту разрешено сделать за один `resume`.
У нас — не больше `SLICE_BUDGET` инструкций. Если скрипт за квант не дошёл ни до
`WAIT`, ни до `END`, он «забыл уступить» — это ошибка.

**Почему `max(n, 1)`?** `WAIT 0` должно означать «уступи до следующего тика», а не
«продолжай прямо сейчас». Если бы `wake_tick = now + 0`, то в этом же тике скрипт был бы
готов снова, и цикл `SAY; WAIT 0; JMP` никогда не отдавал бы управление по-честному.

#### Пошаговая временная шкала

Возьмём три скрипта из `e1404` (без «стражника», чтобы таблица была короче):

```
door:   0: SAY "opens"   1: WAIT 3   2: SAY "closes"   3: END
blink:  0: SAY "on"  1: WAIT 0  2: SAY "off"  3: WAIT 0  4: SAY "on"  5: END
hog:    0: SAY "spinning"  1: WAIT 1  2: JMP 2         ; забыл WAIT в цикле
```

| now | door | hog | blink |
|---|---|---|---|
| 0 | READY → «opens», WAIT 3 → WAITING, wake=3 | READY → «spinning», WAIT 1 → WAITING, wake=1 | READY → «on», WAIT 0 → WAITING, wake=1 |
| 1 | спит (1 < 3) | 1 ≥ 1 → READY → `JMP 2` × 64… квант исчерпан → **FAULTED** | 1 ≥ 1 → READY → «off», WAIT 0 → wake=2 |
| 2 | спит | FAULTED, пропускаем | READY → «on», END → DONE |
| 3 | 3 ≥ 3 → READY → «closes», END → DONE | — | — |

Обратите внимание:

* Скрипты обходятся **в порядке добавления**. В тике 1 сначала обрабатывается `hog`,
  потом `blink` — поэтому строка про FAULT печатается раньше «off». Порядок
  фиксирован, значит вывод одинаков при каждом запуске.
* Упавший `hog` не помешал ни `door`, ни `blink`.
* `hog` упал не в тике 0, а в тике 1: в тике 0 он честно дошёл до `WAIT`. Ловушка
  случилась после пробуждения, когда он попал в цикл `JMP 2` без единого `WAIT`.

### 7.5. Детали, о которых стоит подумать заранее

* **Время.** Ждать в тиках детерминированно (реплеи, lockstep); в секундах — удобнее
  дизайнеру. Обычно «секунды» пересчитываются в тики фиксированного шага (глава 01).
* **Условия пробуждения.** Кроме таймера: событие (`wait_event "door_opened"`),
  предикат («пока игрок не в зоне» — проверяется планировщиком, а не скриптом в цикле),
  завершение другой сопрограммы (join), окончание анимации/звука. Лучше, если
  условие проверяет движок: опрос в скрипте каждый тик стоит квант.
* **Отмена.** Сущность умерла — её сопрограммы должны быть убиты. Привяжите
  сопрограмму к владельцу (хендлу) и проверяйте его при пробуждении.
* **Квант.** Скрипт без yield в цикле съест бюджет и будет помечен FAULTED — это та же
  песочница из §4, только на уровне планировщика. (`e1404`)
* **Сохранение игры.** Если все данные сопрограммы — это `pc`, стек значений и хендлы,
  её можно сериализовать (глава 13) и восстановить. Со stackful-сопрограммами и с
  произвольными замыканиями Lua это почти невозможно — одна из причин, почему студии
  пишут свои VM для катсцен и квестов.

Про сохранение — подробнее. Структура скрипта нашей VM — это несколько чисел и
массивов чисел: `pc`, `sp`, `stack[]`, `locals[]`, `state`, `wake_tick`. Её можно
записать в файл байт в байт (глава 13) и потом прочитать — катсцена продолжится с того
же `wait`. Со stackful-сопрограммой пришлось бы сохранять *машинный стек* с адресами
возврата в нативный код — а они меняются при каждой пересборке игры.

**Аналогия для «условий пробуждения».** Будильник (таймер) — самое простое. Но иногда
нужно «разбуди, когда придёт почтальон» (событие). Плохо, если скрипт сам каждые 5
минут выглядывает в окно (опрос в цикле — тратит квант каждый тик). Хорошо, если
почтальон звонит в дверь (движок будит скрипт сам).

Аналоги в индустрии: latent functions в UnrealScript и Blueprints (узлы `Delay`),
`IEnumerator`/`yield return` в Unity, `async`/`await` в C#-движках, state scripts
Naughty Dog (описаны у Грегори), корутины Lua в Defold и Roblox.

> **Коротко:** планировщик каждый тик будит тех, чьё время пришло, и даёт каждому
> готовому скрипту один квант — в фиксированном порядке. Упавший скрипт помечается
> FAULTED, остальные работают дальше.

> **Частые ошибки (сопрограммы).**
> * В `WAIT` забыть выйти из `resume` — скрипт «ждёт», но продолжает выполняться.
> * `WAIT 0` трактовать как «не ждать вовсе».
> * Пробуждать скрипт, но не давать ему квант в том же тике (или наоборот — давать
>   квант WAITING-скрипту).
> * Обрабатывать ошибку `resume` молча (`(void)`): скрипт остаётся READY и в
>   следующем тике падает снова.
> * Обходить скрипты в порядке, который зависит от адресов или хеш-таблицы.

## 8. Горячая перезагрузка скриптов

### 8.1. Сценарий

Самое ценное, что даёт скриптовый слой. Сценарий: дизайнер правит файл, сохраняет,
файловый наблюдатель (глава 07) замечает изменение, пайплайн перекомпилирует скрипт,
движок подменяет байткод **в работающей игре**.

**Горячая перезагрузка** (hot reload) — замена кода программы, пока она работает, без
перезапуска. **Аналогия.** Поменять колесо у машины на ходу: машина едет дальше,
пассажиры (состояние) на месте, но колесо (код) — новое.

### 8.2. Главная трудность: состояние принадлежит старому коду

Трудность в том, что **состояние принадлежит старой версии кода**. Байткод обращается к
переменным по индексам — а индексы между версиями не стабильны:

```
v1.globals = [ score, ticks ]            values = [ 3, 3 ]
v2.globals = [ combo, score, ticks ]
                 │       │      │
                 │       └──────┼──── перенос по ИМЕНИ: score = 3
                 │              └──── ticks = 3
                 └──────────────────── новой нет в v1 -> инициализатор (5)
(переменные, исчезнувшие в v2, выбрасываются)
```

Что пошло бы не так при переносе **по индексам**: values = `[3, 3]` скопировались бы
как есть, и в v2 получилось бы `combo = 3, score = 3, ticks = ?` — то есть `combo`
получил бы чужое значение, `ticks` — мусор. Игра не упала бы, но счёт «поехал» бы
незаметно. Худший вид бага.

#### Перенос по именам, шаг за шагом

Состояние v1: `score = 3, ticks = 3`. Новая версия v2:
`globals = [combo, score, ticks]`, `inits = [5, 0, 0]`.

| Новый индекс | Имя | Есть в v1? | Старый индекс | Новое значение | Счётчик |
|---|---|---|---|---|---|
| 0 | combo | нет | — | init = 5 | added |
| 1 | score | да | 0 | old[0] = 3 | kept |
| 2 | ticks | да | 1 | old[1] = 3 | kept |

Итого: kept 2, added 1. А сколько выброшено? Это переменные v1, которых нет в v2. Их
можно посчитать отдельно, а можно заметить: всего в v1 было 2 переменных, из них 2
перенесены — значит, выброшено 2 − 2 = 0.

Теперь v2 → v4, где `globals = [ticks]`, `inits = [100]`. Состояние: `combo = 5,
score = 18, ticks = 6`.

| Новый индекс | Имя | Есть в v2? | Новое значение | Счётчик |
|---|---|---|---|---|
| 0 | ticks | да (индекс 2) | 6 (а **не** 100!) | kept |

kept 1, added 0, removed = 3 − 1 = 2 (`combo` и `score`).

**Важная тонкость: собирайте новый массив значений отдельно.** Если переписывать
`values` «на месте», можно затереть старое значение раньше, чем его прочитали. В
примере v1 → v2: записав `values[0] = 5` (combo), вы потеряете старое `values[0]` (score
= 3), которое ещё нужно перенести в `values[1]`. Правильно — заполнить временный
массив, а потом скопировать его целиком.

### 8.3. Алгоритм перезагрузки

1. **Скомпилировать и провалидировать** новую версию целиком. Если что-то не так —
   ничего не менять, показать ошибку. Файл могли сохранить на полуслове; игра обязана
   продолжить работать на старом коде.
2. **Перенести состояние по именам** (а не по индексам), новые переменные
   инициализировать, исчезнувшие — выбросить. Если поменялся *тип* переменной — либо
   конвертировать, либо инициализировать заново (и сообщить).
3. **Атомарно подменить** программу — между кадрами, не посреди выполнения скрипта.

**Атомарно** здесь значит «всё или ничего»: нельзя оставить игру в состоянии, где
программа уже новая, а значения ещё старые (или наоборот). Проверили → собрали новые
значения → и только в самом конце одним движением заменили и `prog`, и `values`.

Что проверяет валидация (из §4.4): каждый `LOAD`/`STORE` обращается к существующей
глобальной (индекс в `[0, globals.len)`), каждый переход ведёт внутрь кода (адрес в
`[0, code.len)`). Пример «сохранили на полуслове»: `globals = [score]`, но в коде
`LOAD 7`. Если такую версию пустить в игру, первая же инструкция прочитает чужую
память.

**Аналогия.** Замена декорации в театре во время антракта, а не посреди сцены. И сначала
проверяют, что новая декорация вообще собрана, а не принесли половину.

### 8.4. Работающие сопрограммы

Отдельный вопрос — **работающие сопрограммы**. Их `pc` указывает в старый байткод, и в
новом по этому адресу может оказаться что угодно. Варианты политики:

* перезапустить сопрограммы с начала (просто и предсказуемо, теряется прогресс);
* дождаться, пока все сопрограммы старой версии завершатся, а новые запускать на новом
  коде (две версии живут одновременно — так часто делают Erlang и серверы);
* сопоставлять точки ожидания по меткам/номерам `wait` (сложно, но идеально для
  длинных катсцен).

Пример, почему нельзя просто оставить `pc`. Сопрограмма спит на `pc = 5` (это `WAIT 3`
в старой версии). Дизайнер добавил в начало скрипта две строки — теперь по адресу 5
лежит `CALL spawn`. После пробуждения скрипт продолжит не «после ожидания», а
посередине чего-то совсем другого, со стеком, который не соответствует этому месту.

### 8.5. Как это в Lua

В Lua горячая перезагрузка обычно сводится к повторному выполнению chunk'а модуля и
переписыванию функций в существующих таблицах: данные живут в таблицах и переживают
перезагрузку, а функции заменяются. Ловушка — замыкания и upvalue, которые продолжают
ссылаться на старые функции. (`e1405`)

**Chunk** — единица компиляции Lua (файл или строка кода). **Замыкание** (closure) —
функция вместе с переменными, которые она «запомнила» из окружения; **upvalue** — такая
запомненная переменная. Если обработчик события сохранён как замыкание на старую
функцию, перезагрузка его не затронет — он продолжит вызывать старый код.

> **Коротко:** сначала проверить новую версию, потом перенести состояние **по
> именам** в отдельный массив, потом одним движением подменить. Сломанная версия не
> должна изменить вообще ничего.

> **Частые ошибки (горячая перезагрузка).**
> * Подменить `prog` до валидации, а при ошибке забыть вернуть старый.
> * Переносить значения по индексам.
> * Переписывать `values` на месте и затирать ещё не перенесённое.
> * Для переменной, которая есть в обеих версиях, взять инициализатор новой версии
>   (счёт сбросится — дизайнер очень удивится).
> * Подменять код посреди выполнения скрипта, а не между тиками.

## 9. Где компилировать скрипт

### 9.1. В рантайме или в пайплайне

* **В рантайме** (как Lua по умолчанию): простой цикл итерации, но компилятор едет в
  релизную сборку, а ошибки синтаксиса обнаруживаются на машине игрока.
* **Оффлайн в пайплайне ассетов** (глава 07): исходник → байткод на этапе сборки
  ассетов, в игре только загрузчик и VM. Плюсы: ошибки ловятся при сборке, в релизе
  нет компилятора (меньше кода, меньше поверхности атаки), можно делать дорогие
  оптимизации. Для hot reload пайплайн компилирует файл по запросу редактора.

**Поверхность атаки** — весь код, до которого может «дотянуться» злоумышленник через
входные данные. Компилятор разбирает произвольный текст — это большая поверхность.
Нет компилятора в релизе — нет и его багов.

### 9.2. Ассемблер: текст → байткод

**Ассемблер** — простейший «компилятор», в котором одна строка текста = одна
инструкция: `push 2` → `{ PUSH, 2 }`. Ему нужно разобрать строку, найти мнемонику
(название инструкции), операнд, и превратить имена (переменных, нативов, меток) в
числа.

* **Мнемоника** — человекочитаемое имя опкода: `push`, `jmp`, `call`.
* **Метка** (label) — имя для адреса в коде: строка `walk:` означает «адрес следующей
  инструкции называется walk». Переход `jnz walk` прыгает туда.

Ассемблер или компилятор должен сообщать об ошибках **с номером строки и понятной
причиной** — «строка 2: неизвестная операция `jump`», а не «assertion failed». Ссылки
вперёд на метки и функции решаются **backpatching'ом**: переход на ещё не встреченную
метку записывается с пустым адресом и заносится в список «заплаток», которые
разрешаются в конце сборки. (`e1406`)

### 9.3. Backpatching на пальцах

Проблема: ассемблер читает текст сверху вниз **один раз** (однопроходный). Встретив
`jmp door`, он ещё не знает, где будет `door:` — эта строка ниже.

**Аналогия.** Вы пишете книгу и в главе 2 хотите сослаться «см. стр. ___». Глава 5 ещё
не написана, номер страницы неизвестен. Вы оставляете пропуск и записываете на
стикере: «на стр. 14 вписать номер страницы главы 5». Когда книга дописана, проходите
по стикерам и вписываете номера. Пропуск — это `-1` в `arg`, стикер — **fixup**
(«заплатка»).

Пример. Исходник (номера строк слева, адреса инструкций — в квадратных скобках):

```
строка 1:  start:            ; метка -> адрес 0
строка 2:      push 1        ; [0]
строка 3:      jnz end       ; [1]  ссылка ВПЕРЁД
строка 4:      jmp start     ; [2]  ссылка НАЗАД
строка 5:  end:              ; метка -> адрес 3
строка 6:      end           ; [3]
```

Проход по строкам:

| Строка | Текст | Действие ассемблера | labels | fixups | code |
|---|---|---|---|---|---|
| 1 | `start:` | метка = текущая длина кода (0) | start=0 | — | — |
| 2 | `push 1` | emit | start=0 | — | `[0] PUSH 1` |
| 3 | `jnz end` | `end` ещё не известна → fixup {end, at=1, line=3}, emit `JNZ -1` | start=0 | {end, 1, 3} | `[1] JNZ -1` |
| 4 | `jmp start` | `start` известна → emit `JMP 0` сразу | start=0 | {end, 1, 3} | `[2] JMP 0` |
| 5 | `end:` | метка = 3 | start=0, end=3 | {end, 1, 3} | — |
| 6 | `end` | emit | … | … | `[3] END` |
| конец | — | разрешаем fixup: `end` = 3 → `code[1].arg = 3` | | | `[1] JNZ 3` |

Что стоит заметить:

* Метка **не порождает инструкцию**. Она лишь даёт имя текущему адресу — адресу
  *следующей* инструкции (то есть текущей длине кода).
* Если в конце для какого-то fixup'а метка так и не нашлась — ошибка `UNKNOWN_LABEL`, и
  номер строки берётся **из fixup'а** (строка, где был переход), а не последняя строка
  файла. Именно поэтому fixup хранит `line`.
* Повторное определение той же метки — тоже ошибка: непонятно, куда прыгать.

### 9.4. Имена → индексы прямо при сборке

Как и при линковке нативов (§5.3), ассемблер превращает **все** имена в числа:
`load hero` → `LOAD 0` (индекс в списке `.global`), `call move` → `CALL 1` (индекс в
таблице нативов). В рантайме не остаётся ни одной строки — только числа, и VM быстра.

Ошибки здесь тоже ловятся рано и с номером строки: `load b` без `.global b` —
`UNKNOWN_GLOBAL`, `call fly` — `UNKNOWN_NATIVE`, `push 1x` — `BAD_NUMBER`.

> **Коротко:** ассемблер — однопроходный: метки запоминают адрес, переходы назад
> получают адрес сразу, переходы вперёд — заплатку, которая разрешается в конце.
> Каждая ошибка — с номером строки.

> **Частые ошибки (ассемблер).**
> * Сделать так, чтобы метка занимала место в коде (адреса «уедут» на единицу).
> * В ошибке `UNKNOWN_LABEL` указать номер последней строки, а не строки перехода.
> * Забыть, что строка может быть пустой или состоять из одного комментария.
> * Забыть, что метка может стоять до первой инструкции или после последней.

## 10. Производительность и память

* **Выделения памяти.** Самый частый источник тормозов скриптов — не интерпретация, а
  аллокации: строки, временные таблицы, замыкания на каждый кадр. Интернируйте строки
  (имена событий и анимаций — это id, а не строки), переиспользуйте таблицы.
* **Сборщик мусора.** Stop-the-world на 5 мс посреди кадра недопустим. Lua предлагает
  инкрементальный и поколенческий режимы; движки вызывают шаг GC явно, с бюджетом, в
  конце кадра (`lua_gc(L, LUA_GCSTEP, n)`). Своя VM с хендлами и без кучи (как наша)
  вообще не нуждается в GC — данные скрипта лежат в фиксированных массивах.
* **Потоки.** VM Lua однопоточна: один `lua_State` — один поток. Параллельный
  скриптинг делают либо независимыми VM на поток (без общих объектов), либо
  выполнением скриптов в одном потоке с отложенными командами в движок. Скрипты ИИ
  тысяч NPC часто запускают «размазанно»: каждый NPC думает раз в N кадров.
* **Профилирование.** Встраиваемый профилировщик (глава 15) должен видеть скрипты:
  зона на каждый `resume`, счётчик инструкций, топ скриптов по времени. Без этого
  «игра тормозит из-за скриптов» не поддаётся диагностике.
* **Детерминизм.** Для реплеев и lockstep-сети скрипт обязан быть детерминированным:
  никакого системного времени и общего `rand()` — только нативы, выдающие тики и
  детерминированный ГСЧ из состояния мира; порядок планировщика фиксирован; итерация по
  хеш-таблицам не должна влиять на результат.

Пояснения к терминам:

* **Интернирование строк** — хранить каждую уникальную строку один раз и раздавать
  вместо неё число (id). Сравнить два id — одна инструкция; сравнить две строки —
  цикл по символам (глава 07, хеши путей).
* **Stop-the-world** — сборщик мусора останавливает всю программу, пока ищет мусор.
* **Детерминизм** — одинаковые входы всегда дают одинаковый результат. **Реплей** —
  запись только *ввода* игрока; при воспроизведении игра пересчитывается заново и
  должна прийти к тому же. **Lockstep** — сетевая модель, где все компьютеры получают
  одинаковый ввод и сами пересчитывают мир; при малейшем расхождении игры
  «разъезжаются» (глава 01).
* **ГСЧ** — генератор случайных чисел. Детерминированный ГСЧ из состояния мира даёт
  одну и ту же «случайную» последовательность при одинаковом зерне (seed).
* «**Размазанный**» запуск (time slicing): 1000 NPC, каждый думает раз в 10 кадров —
  в каждом кадре думают только 100.

> **Коротко:** тормозят чаще аллокации и GC, а не интерпретатор. Для реплеев скрипт
> должен быть детерминированным: никаких часов, общего `rand()` и случайного порядка.

## 11. Как это устроено в реальных движках

* **Unreal Engine.** Blueprints — визуальные графы, компилируемые в байткод VM
  (`UFunction` с `Script`-массивом). Граница с C++ задаётся рефлексией (`UFUNCTION`,
  `UPROPERTY`, генерация кода Unreal Header Tool). Латентные узлы (`Delay`) —
  сопрограммы на уровне графа.
* **Unity.** C# с IL2CPP (AOT) на консолях/мобилках. Корутины — итераторы
  (`IEnumerator`, `yield return new WaitForSeconds(3)`), которые движок «прокручивает»
  каждый кадр. Граница C# ↔ C++ — дорогая, поэтому Unity двигалась к DOTS/Burst.
* **Godot.** GDScript — собственный динамический язык с компиляцией в байткод и
  тесной интеграцией с системой объектов и сигналов; C# — как альтернатива.
* **Roblox.** Luau — форк Lua 5.1 с постепенной типизацией, быстрым интерпретатором,
  песочницей и interrupt-механизмом для прерывания долгих скриптов.
* **Naughty Dog.** Jak & Daxter написан почти целиком на GOAL — собственном Lisp'е с
  компилятором в машинный код. В серии Uncharted/The Last of Us — DC (data compiler на
  Racket/Scheme) для данных и «state scripts» для геймплея: скриптовые объекты с
  состояниями и сопрограммами, ожиданием событий и таймеров.
* **Bungie (Halo).** HaloScript — Lisp-подобный язык для миссий, с «потоками»
  (сопрограммами) и ожиданием условий (`sleep_until`).
* **Defold, Love2D, многие мобильные движки** — Lua как основной язык геймплея.

Общее у всех: (1) единая граница с движком через рефлексию/таблицу привязок,
(2) объекты движка доступны по хендлам или прокси, (3) время выражено сопрограммами
или их аналогами, (4) горячая перезагрузка как главная фича для команды.

Сопоставим с тем, что вы делаете в упражнениях:

| Идея из главы | В Unity | В Unreal | У нас |
|---|---|---|---|
| единая граница | C#-обёртки над C++ | `UFUNCTION` + Header Tool | `NativeFn` + `@bind` (`e1402`) |
| объекты по хендлам | `UnityEngine.Object` — обёртка с id | `UObject*` + слабые указатели | хендлы с поколением (`e1403`) |
| ожидание во времени | `yield return` | узел `Delay` | `WAIT` + планировщик (`e1404`) |
| горячая перезагрузка | domain reload | Live Coding / перекомпиляция Blueprint | перенос по именам (`e1405`) |

> **Коротко:** все большие движки решают одни и те же четыре задачи: граница, хендлы,
> время, перезагрузка. Наша маленькая VM — те же идеи без обёрток.

## 12. Частые ошибки

* Хранить указатели движка в переменных скрипта (§6).
* Делать в скрипте работу движка: перебор всех сущностей, физику, поиск пути (§5).
* Отсутствие бюджета: один `while true do end` в моде — и игра зависла (§4).
* Поиск натива по строке на каждом вызове вместо линковки при загрузке (§5).
* Порядок выполнения скриптов зависит от хеш-таблицы или адресов — прощай,
  детерминизм реплеев (§10).
* Перезагрузка, подменяющая код до валидации; перенос состояния по индексам (§8).
* Сопрограмма, переживающая своего владельца: сущность уничтожена, а её скрипт через
  три секунды «просыпается» и обращается к ней (§7).
* Отсутствие инструментов: нет номеров строк в ошибках, нет отладчика и профилировщика
  — скриптовый слой становится «чёрным ящиком», которого боятся (§9, глава 15).

Плюс несколько ошибок «уровня C3», на которых часто спотыкаются в этих упражнениях:

* `!!` вместо `!` внутри VM — паника всего процесса вместо ошибки скрипта.
* Порядок операндов в бинарной операции: первый `pop()` — это **правый** операнд.
* `(void)` перед вызовом, который может вернуть важную ошибку: ошибка исчезает
  бесследно. Используйте `if (catch err = ...)`.
* Сравнение `String` через `==` в C3 сравнивает *содержимое* — это то, что нужно для
  поиска по имени.

## Как это связано с упражнениями

Перед каждым упражнением полезно перечитать указанные разделы и сначала **на бумаге**
прогнать маленький пример из `main()` упражнения: так вы заранее увидите, какое число
ожидается и почему.

### e1401 · Песочница: стековая VM с бюджетом инструкций

**Что просят.** Сделать `push`/`pop` безопасными, добавить в начало цикла проверку
бюджета и `pc`, реализовать опкоды `SUB`, `MUL`, `LT`, `JZ`.

**Что перечитать.** §3.2 (порядок операндов, переходы, подсчёт 41 шага), §3.4 (цикл
диспетчеризации), §4.1–4.3 и §4.7 (бюджет, стек, `pc`, мини-VM).

**На что обратить внимание.**
* Тест ожидает, что при бюджете 20 выполнено *ровно* 20 инструкций. Проверьте свою
  логику на таблице из §4.1.
* В заготовке `steps` увеличивается в теле цикла — подумайте, где должна стоять
  проверка относительно этого увеличения.
* `LT` кладёт 1 или 0, а не `bool`.
* `JZ` снимает значение *всегда*, а не только когда переходит.
* «Провал за конец программы» — тоже `BAD_JUMP`.

### e1402 · Нативные привязки: таблица, линковка, арность

**Что просят.** Поиск натива по имени, макрос `@bind` на рефлексии, линковку
`link()` с проверкой арности и опкод `CALL` в VM.

**Что перечитать.** §5 целиком, особенно §5.2 (окно стека — таблица на числах), §5.3
(линковка) и §5.4 (трамплины и рабочий пример `@bind`).

**На что обратить внимание.**
* `link()` должна трогать только инструкции `CALL`; у остальных имени нет.
* Арность в `CALL` проверяется дважды: при линковке и в VM (байткод мог прийти
  «сырым» — последний тест именно об этом).
* Тест с «сырым» байткодом (`CALL` на пустом стеке) ждёт `STACK_UNDERFLOW` — значит,
  VM сама проверяет, что значений на стеке хватает, *до* построения окна.
* Ошибка натива должна остановить скрипт *до* следующих инструкций.

### e1403 · Хендлы вместо указателей

**Что просят.** Упаковку/распаковку хендла, «протухание» в `destroy` и полную
проверку в `resolve`.

**Что перечитать.** §6.2 (раскладка битов, почему поколение с 1), §6.3 (история слота —
ровно сценарий из `main`), §6.4.

**На что обратить внимание.**
* Тест требует, чтобы `make_handle(0, 1) != 0`.
* Мусорные хендлы вроде `12345` и `make_handle(3, 1)` при четырёх слотах, из которых
  выдано меньше, должны давать `STALE_HANDLE`, а не выход за границы массива.
* Три условия `resolve`: индекс среди *выданных* слотов, слот жив, поколение совпадает.

### e1404 · Сопрограммы и планировщик

**Что просят.** Опкоды `WAIT` и `END` в `Script.resume` и логику планировщика:
пробуждение и обработку упавшего скрипта (`FAULTED`, `error`, сообщение).

**Что перечитать.** §7.2 (yield = return, таблица по тикам), §7.4 (состояния,
`max(n, 1)`, временная шкала), §7.5.

**На что обратить внимание.**
* `WAIT` должен не только поменять состояние, но и **выйти** из `resume`. Внутри
  `switch` `break` выходит только из `switch`, а не из цикла `for`.
* `WAIT 0` будит на следующем тике.
* Формат сообщения об ошибке задан в шапке упражнения точно; сравните с
  ожидаемым выводом.
* Сравните свою временную шкалу с таблицей §7.4 — в упражнении к ней добавляется ещё
  «стражник».

### e1405 · Горячая перезагрузка

**Что просят.** `Program.validate` (индексы глобальных и адреса переходов) и
`Instance.reload` (перенос по именам, отчёт kept/added/removed, подмена только после
успешной проверки).

**Что перечитать.** §4.4, §8.2 (две таблицы переноса), §8.3.

**На что обратить внимание.**
* При неудачной перезагрузке `inst.prog` должен остаться прежним — значит, ничего
  нельзя менять до проверки.
* Собирайте новые значения во временный массив (§8.2, «важная тонкость»).
* `removed` — это переменные *старой* версии, которых нет в новой.
* У `Program.find` есть готовый ответ «нет такой переменной» — это Optional,
  используйте `try`/`catch`, а не `!!`.

### e1406 · Итог: ассемблер и катсцена

**Что просят.** В ассемблере: определение меток (с проверкой повторов), операнды
`load`/`store`/`call`, переходы `jmp`/`jnz` через `emit_jump`, и разрешение fixup'ов
в конце `assemble()`.

**Что перечитать.** §9 целиком (особенно таблицу backpatching'а в §9.3), §5.3 (имена →
индексы), §7.4 (планировщик уже написан, но полезно понимать вывод).

**На что обратить внимание.**
* Адрес метки — это текущая длина кода (`self.len`), метка не занимает инструкцию.
* При ошибке разрешения fixup'а `error_line` должен указывать на строку перехода —
  см. тест `"x:\n  jmp y ; nowhere\nend"`, который ждёт строку 2.
* Тест проверяет конкретные адреса: `code[16]` — `JNZ 6`, `code[17]` — `JMP 19`.
  Если не сходится, распишите адреса INTRO на бумаге, как в §9.3.
* Для `load`/`store`/`call` уже есть готовые функции поиска индекса; их ошибки нужно
  просто пробросить.

## Что почитать

* **Robert Nystrom, «Crafting Interpreters»** (craftinginterpreters.com) — вторая часть
  (clox) — лучший практический текст о байткодовой VM: стек, диспетчеризация,
  однопроходный компилятор, backpatching переходов, сборщик мусора.
* **Robert Nystrom, «Game Programming Patterns»**, глава «Bytecode» — ровно наш случай:
  маленькая VM для заклинаний в игре, с песочницей.
* **R. Ierusalimschy, L. H. de Figueiredo, W. Celes, «The Implementation of Lua 5.0»**
  (2005) — регистровая VM, кодирование инструкций, сопрограммы, таблицы.
* **Roberto Ierusalimschy, «Programming in Lua»**, части про C API и корутины — как
  выглядит граница «хост ↔ скрипт» в самом популярном встраиваемом языке.
* **Jason Gregory, «Game Engine Architecture»**, глава «Runtime Gameplay Foundation
  Systems» / разделы о скриптинге — классификация скриптовых языков, state scripts
  Naughty Dog, интеграция с объектной моделью игры.
* **Luau** (luau.org) — документация по песочнице, interrupt-колбэку и производительности
  интерпретатора; хорошие заметки о том, как делать быстрый интерпретатор без JIT.
* **Anton Ertl, David Gregg, «The Structure and Performance of Efficient Interpreters»**
  — о диспетчеризации: switch, threaded code, суперинструкции.
* **Unreal Engine docs: «Blueprints Visual Scripting», «Unreal Header Tool»** — как
  рефлексия становится границей с визуальным скриптингом.
* Исходники: **Lua** (lvm.c, ldo.c — диспетчеризация и корутины умещаются в пару
  тысяч строк), **Wren** (компактная VM с файберами), **clox**.

Если читать что-то одно — начните с главы «Bytecode» из «Game Programming Patterns»
(она короткая и бесплатная онлайн), потом — вторая часть «Crafting Interpreters».
