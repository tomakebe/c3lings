## 1. Зачем движку скрипты

Скриптовый слой появляется в движке не потому, что C/C++/C3 «слишком сложны для
дизайнеров». Причины инженерные:

1. **Скорость итерации.** Пересборка и перезапуск игры — минуты. Перезагрузка скрипта —
   доли секунды, и игра при этом не теряет состояние: босс остаётся на второй фазе,
   игрок — у двери. Для геймплея, где 90% работы — подбор чисел и порядка событий, это
   разница между десятью итерациями в день и сотней.
2. **Изоляция.** Скрипт — недоверенный код. Ошибка в нём должна выключить один
   скрипт и показать сообщение, а не уронить процесс. Нативный код такой гарантии не
   даёт: один выход за границу массива — и вы отлаживаете порчу кучи.
3. **Разделение ролей.** Программист движка отвечает за *механизмы* (физика, анимация,
   ИИ-навигация), дизайнер — за *политику* (когда открыть дверь, что сказать NPC).
   Скриптовый API — это контракт между ними.
4. **Моддинг и живые игры.** Скрипты можно скачать с сервера или из Steam Workshop.
   Нативный код — нельзя (и не нужно: это дыра в безопасности).
5. **Выразительность во времени.** Геймплей — это последовательности: «подождать 3
   секунды», «дождаться, пока игрок войдёт в зону», «проиграть реплику и дождаться её
   конца». На сопрограммах это пишется линейно; в нативном коде — как конечный автомат
   с ручным хранением состояния.

Цена тоже понятна: интерпретатор в 10–50 раз медленнее нативного кода, граница
«скрипт ↔ движок» стоит дорого, отладка сложнее (нужен свой отладчик), появляется второй
язык со своей системой типов и управлением памятью, а сборщик мусора приносит паузы.

```
          ┌──────────────── редактор / пайплайн ассетов ────────────────┐
          │  intro.cs (текст) ──► компилятор ──► intro.csb (байткод)    │
          └──────────────────────────────────────────┬──────────────────┘
                                                     │ загрузка / hot reload
┌───────────────────────────── runtime ─────────────▼──────────────────────┐
│  ┌────────────┐  resume()  ┌────────────────────┐  CALL i  ┌───────────┐ │
│  │ Scheduler  │ ─────────► │ VM: pc, stack, env │ ───────► │ natives[] │ │
│  │ (по тикам) │ ◄───────── │  бюджет, проверки  │ ◄─────── │  (движок) │ │
│  └────────────┘ WAIT/END   └────────────────────┘  результат└─────┬─────┘ │
│                                                                   │       │
│                         хендлы, а не указатели ──────────► World / ECS    │
└────────────────────────────────────────────────────────────────────────────┘
```

Эта картинка — карта главы: VM и песочница (§3–4), привязки (§5), объекты движка в
скрипте (§6), сопрограммы и планировщик (§7), перезагрузка (§8).

### Когда скрипты не нужны

Не каждый движок их имеет, и это нормальное решение:

* **Unreal Engine** отказался от UnrealScript в UE4. Геймплей пишут на C++ (с горячей
  перезагрузкой модулей — Live Coding) и в визуальных графах **Blueprints**, которые
  компилируются в байткод собственной VM. То есть VM осталась, но языка-текста нет.
* **Unity** использует C# — управляемый язык с JIT/AOT (IL2CPP). Это «скриптинг» по роли,
  но не по реализации: компилятор и рантайм чужие.
* Многие движки выбирают **data-driven** подход: поведение задаётся данными (таблицы,
  графы состояний, деревья поведения), а код интерпретирует данные. Правило: *данные
  описывают ЧТО, скрипт — КАК и КОГДА*. Если дизайнеру нужно только менять числа и
  связи — дайте ему редактор данных, а не язык программирования. Язык — когда нужна
  логика с ветвлениями и временем.
* Горячая перезагрузка нативного кода (глава 17) закрывает «скорость итерации» для
  программистов, но не изоляцию и не моддинг.

## 2. Пространство решений: взять готовое или написать своё

| Вариант | Плюсы | Минусы | Где встречается |
|---|---|---|---|
| **Lua 5.x** | крошечный (≈ 30 тыс. строк C), быстрый для интерпретатора, сопрограммы из коробки, отличный C API | динамическая типизация, 1-based индексы, GC-паузы, нет типов для больших кодовых баз | WoW (UI), Defold, Roblox (как Luau), CryEngine, десятки AAA-проектов |
| **LuaJIT** | на порядок быстрее Lua, FFI | застрял на Lua 5.1, JIT запрещён на консолях/iOS (нет W^X-страниц) | серверы, PC-игры, инструменты |
| **Luau** (Roblox) | постепенная типизация, песочница by design, interrupt-колбэк, быстрый интерпретатор | моложе, своя экосистема | Roblox, Alan Wake 2 и др. |
| **C# (Mono/CoreCLR/IL2CPP)** | статические типы, огромная экосистема, инструменты | тяжёлый рантайм, GC, «граница» дорогая | Unity, Godot (опционально), Stride |
| **AngelScript / Squirrel / Wren** | синтаксис «как C++» / классы, встраиваемость | меньше людей знает | Amnesia, Left 4 Dead 2 (Squirrel), инди |
| **Свой DSL + своя VM** | ровно те возможности, что нужны; детерминизм, бюджет, сериализуемые сопрограммы — под вашим контролем | вы пишете компилятор, отладчик, документацию, подсветку синтаксиса... | Naughty Dog (GOAL, позже DC/state scripts), HaloScript, многие студии |
| **Визуальный скриптинг** | доступен не-программистам, наглядность потоков | «спагетти», плохо диффится и мёржится, медленнее текста | Blueprints, Unity Visual Scripting, Frostbite |

Своя VM оправдана, когда вам нужно что-то, чего готовые не дают: **жёсткий детерминизм**
(lockstep-сеть, реплеи), **сериализуемые сопрограммы** (сохранение посреди катсцены),
**строгий бюджет** в микросекундах, интеграция с ECS без «объектов» или очень узкий
домен (диалоги, катсцены, ИИ-состояния). Именно такую маленькую VM мы строим в
упражнениях — и всё, что вы в ней сделаете, есть и в Lua, только спрятано за C API.

## 3. Внутренности VM: стековая vs регистровая, диспетчеризация

### Стековая VM

Операнды лежат на стеке значений, инструкции неявно снимают и кладут:

```
a = b + c * 2          PUSH b ; PUSH c ; PUSH 2 ; MUL ; ADD ; STORE a
```

Плюсы: тривиальный компилятор (обход AST в постфиксном порядке), компактные
инструкции (часто 1 байт + операнд). Минусы: много инструкций, много трафика через
стек. Так устроены JVM, CPython, WebAssembly, clox из «Crafting Interpreters».

### Регистровая VM

Инструкции адресуют «регистры» — слоты в кадре функции:

```
a = b + c * 2          MUL  r3, r2, K(2)
                       ADD  r0, r1, r3
```

Инструкций в 1,5–2 раза меньше, значит меньше итераций цикла диспетчеризации — а
именно он доминирует в стоимости интерпретатора (непредсказуемый косвенный переход).
Цена — более сложный компилятор (распределение регистров) и широкие инструкции
(Lua 5: 32 бита — опкод 6 бит, A 8 бит, B/C по 9 бит). Lua перешла со стековой VM на
регистровую в версии 5.0 и описала выигрыш в статье «The Implementation of Lua 5.0» —
обязательное чтение.

Для игровой VM важнее другое: **размер и раскладка инструкций**. Байткод скрипта читается
последовательно, и «плотная» кодировка лучше ложится в кеш. В упражнениях инструкция —
`struct Instr { Op op; int arg; }` (8 байт с выравниванием). В продакшене кодируют в
`uint`: `op = ins & 0x3F`, `a = (ins >> 6) & 0xFF` и т.д.

### Цикл диспетчеризации

Сердце любой VM:

```c3
while (true)
{
    if (self.steps++ >= budget) return BUDGET_EXCEEDED~;   // песочница, §4
    Instr ins = code[self.pc++];
    switch (ins.op)
    {
        case PUSH: self.push(ins.arg)!;
        case ADD:
            int b = self.pop()!;
            int a = self.pop()!;
            self.push(a + b)!;
        ...
    }
}
```

`switch` компилируется в таблицу переходов с ОДНИМ косвенным переходом на все опкоды —
предсказатель переходов CPU видит одну точку и угадывает плохо. Приёмы ускорения:

* **threaded code / computed goto** — переход на следующий обработчик в конце каждого
  обработчика, у каждого опкода своя точка перехода и своя история предсказаний.
  CPython и Lua используют его там, где компилятор умеет (`&&label` в GCC). В C3
  аналог — `@jump` на `switch` (упражнение 117 в треке по языку).
* **суперинструкции** — частые пары (`LOAD x; PUSH 1; ADD; STORE x`) склеиваются в одну
  (`INC x`): меньше диспетчеризаций.
* **кеширование вершины стека** в регистре, **inline caches** для поиска полей.
* и в предельном случае — JIT, который на консолях и iOS запрещён (нельзя выделять
  исполняемую память), поэтому быстрый *интерпретатор* для игр важнее JIT'а.

Практическое правило: если скрипт тратит больше 1–2% кадра, проблема почти всегда не в
диспетчеризации, а в том, что скрипт делает работу движка (ищет сущности перебором,
считает расстояния в цикле). Лечится нативом, а не оптимизацией VM.

## 4. Песочница: VM обязана пережить любой байткод

Скрипт мог написать моддер, дизайнер или вы сами в три часа ночи. Движок должен
пережить **любую** последовательность байтов. Линии обороны:

```
            ┌─ загрузка ───────────────┐  ┌─ выполнение ────────────────────┐
байткод ──► │ валидация: опкоды,       │─►│ бюджет инструкций за квант      │
            │ индексы глобальных,      │  │ проверки стека (over/underflow) │
            │ адреса переходов,        │  │ проверка pc / границ            │
            │ арность нативов          │  │ лимит памяти (свой аллокатор)   │
            └──────────────────────────┘  │ ошибка нативa -> ошибка скрипта │
                                          └─────────────────────────────────┘
```

1. **Бюджет инструкций.** Бесконечный цикл — самая частая ошибка в скриптах. VM считает
   выполненные инструкции и прерывает скрипт по исчерпании квоты. В Lua это делает
   `lua_sethook(L, hook, LUA_MASKCOUNT, n)`, в Luau — колбэк `interrupt`, который
   вызывается на обратных переходах и вызовах функций. Дешевле считать не каждую
   инструкцию, а только **обратные переходы и вызовы** — любой бесконечный цикл обязан
   их содержать. (`e1401`)
2. **Проверки стека.** `push` в полный стек и `pop` из пустого — ошибки скрипта, а не
   выходы за границу массива хоста. Глубина рекурсии ограничивается так же.
3. **Валидация при загрузке.** Всё, что можно проверить статически, проверяйте один раз
   при загрузке: индексы констант и глобальных, адреса переходов, арность вызовов
   нативов. Тогда в горячем цикле остаются только динамические проверки. JVM делает это
   «верификатором байткода»; WebAssembly валидирует модуль целиком до исполнения.
   (`e1402`, `e1405`)
4. **Лимит памяти.** VM выделяет память только через свой аллокатор с бюджетом
   (`lua_newstate` принимает функцию-аллокатор именно для этого). Скрипт, создавший
   миллион таблиц, получает ошибку «out of memory», а не съедает память игры.
5. **Возможности, а не запреты.** Скрипт может делать только то, что ему дали нативами.
   Нет натива `open_file` — нет доступа к диску. Это модель capability-based security,
   и она надёжнее, чем «чёрный список опасных функций». Разным скриптам можно давать
   разные таблицы нативов (UI-скрипту — одни, моду — урезанные).

Ошибки в C3 удобно моделировать Optional'ами: каждая операция VM возвращает `T?`, а `!`
пробрасывает ошибку наверх. Любая инструкция может «упасть», и падение мгновенно
завершает квант — ровно та семантика, что нужна:

```c3
excuse STACK_OVERFLOW, STACK_UNDERFLOW, BUDGET_EXCEEDED, BAD_JUMP;

fn int? Vm.pop(&self)
{
    if (self.sp <= 0) return STACK_UNDERFLOW~;
    return self.stack[--self.sp];
}
```

Что делать с упавшим скриптом — политика движка: выключить и показать ошибку на экране
(в разработке), молча выключить и записать в лог (в релизе), перезапустить объект.
Важно лишь, что ошибка **локальна**: остальные скрипты и кадр продолжают работать.

## 5. Привязки: граница «скрипт ↔ движок»

### Единая сигнатура

Скрипту нужен доступ к движку: заспавнить врага, проиграть звук, прочитать позицию.
Все нативные функции приводятся к одной сигнатуре, которую понимает VM:

```c3
alias NativeFn = fn int?(int[] args, void* ctx);

struct Native
{
    String name;
    int arity;
    NativeFn func;
}
```

* `args` — **окно стека VM**, а не копия: `stack[base : arity]`. Так устроен Lua C API —
  натив работает с аргументами прямо на стеке `lua_State`.
* `ctx` — непрозрачный указатель на хост (мир, игру). VM не знает, что это.
* `int?` — натив может завершиться ошибкой, и она станет ошибкой скрипта.

Вызов из VM:

```
стек до CALL move/2:   [... h dx]          base = sp - 2
                              ^^^^ args = stack[base:2]
стек после:            [... result]        sp = base; push(result)
```

### Линковка по имени, вызов по индексу

Человек пишет `call move`, но искать строку на каждом вызове — дорого. Поэтому имена
разрешаются **один раз** — при загрузке скрипта: `"move" → 1`. Заодно проверяется
арность, и опечатка в имени функции обнаруживается при загрузке уровня, а не через
двадцать минут игры. Динамические проверки в VM всё равно остаются, потому что байткод
может прийти в обход загрузчика (файл с диска, сеть).

Индексы стабильны только в пределах одной сборки движка. Если байткод хранится на диске
долго (моды!), храните в нём имена, а индексы вычисляйте при загрузке — иначе
добавление нового натива в середину таблицы сломает все старые скрипты. Это тот же
вопрос версионирования, что и в главе 13.

### Генерация трамплинов

Писать для каждой функции движка прослойку `args → параметры` вручную скучно и опасно.
В C++ это делают шаблоны (sol2, LuaBridge, pybind11). В C3 хватает макроса с
рефлексией — число параметров функции известно на этапе компиляции, а срез можно
распаковать в аргументы вызова:

```c3
fn int clamp(int v, int lo, int hi) => v < lo ? lo : (v > hi ? hi : v);

macro int? @bind(NativeTable* t, String name, $f)
{
    $if $Typeof($f)::params.len == 0:
        return t.add(name, 0, fn int?(int[] a, void* ctx) => $f());
    $else
        return t.add(name, $Typeof($f)::params.len,
                     fn int?(int[] a, void* ctx) => $f(...a[:$Typeof($f)::params.len]));
    $endif
}

@bind(&natives, "clamp", &clamp)!!;     // арность 3 выведена компилятором
```

Лямбда внутри макроса ссылается на `$f` — это не захват переменной, а подстановка
константы времени компиляции, поэтому для каждой привязанной функции получается своя
маленькая функция-трамплин. Тот же приём расширяется на типы параметров (`$p.type` из
`::params`) — float, bool, хендлы — с проверкой типа значения на стеке. (`e1402`)

### Стоимость границы

Каждый вызов натива — это проверка арности, (у динамических языков) проверка типов
аргументов, косвенный вызов, иногда упаковка результата. Это десятки наносекунд.
Скрипт, который в цикле на 1000 врагов вызывает `get_pos`, `distance`, `get_hp` —
это тысячи пересечений границы за кадр. Правила хорошего API:

* **крупные нативы** — `find_enemies_in_radius(pos, r)` вместо перебора в скрипте;
* **пакетные операции** — отдать скрипту массив, а не по одному элементу;
* **скрипт принимает решения, движок выполняет работу**: скрипт решает «атаковать»,
  а поиск пути, анимация и физика происходят в нативных системах.

## 6. Объекты движка в скрипте: хендлы, а не указатели

Скрипт живёт дольше, чем вы думаете. Он сохранил «цель» в переменную, подождал три
секунды — а цель за это время умерла, и её слот занял новый враг. Если скрипт хранил
указатель, он теперь молча бьёт чужую сущность или читает освобождённую память. Это
use-after-free, запущенный недоверенным кодом.

Решение — скрипт видит только **хендл** с поколением (глава 03):

```
int handle:   31 ........ 12 11 ...... 0
              [ generation ][   index   ]

destroy(index):  slots[index].gen++     ← все выданные хендлы на слот протухли
resolve(h):      index < used && alive && slots[index].gen == gen(h)
                 иначе STALE_HANDLE
```

Каждый натив переводит хендл в указатель через **одну** функцию `resolve` и не хранит
указатель дольше вызова. Протухший хендл — либо ошибка скрипта (строгие нативы:
`damage`, `move`), либо нормальный ответ «нет» (мягкие: `is_alive`). Хорошее API
обычно предлагает оба стиля. (`e1403`)

В языках со сборщиком мусора (Lua, C#) объекты движка обычно отдаются как *userdata* /
*прокси-объект*, внутри которого лежит тот же хендл. Ошибка «держать указатель в
userdata» — классика: сборщик скрипта держит прокси живым, а движок уже уничтожил
сущность. Владение всегда у движка; скрипт владеет только ссылкой.

Две смежные проблемы:

* **Идентичность.** Два прокси на одну сущность должны быть равны (`==`). Либо
  кешируйте прокси по хендлу (слабая таблица в Lua), либо сравнивайте хендлы.
* **ECS.** В ECS «сущность» — просто id, и хендл ложится на неё естественно. Компоненты
  скрипту лучше отдавать через нативы-запросы (`get_health(e)`), а не по указателю на
  массив компонентов — массивы переезжают при росте и при смене архетипа.

## 7. Сопрограммы: геймплей во времени

Сравните одну и ту же катсцену:

```
// конечный автомат в нативном коде            // сопрограмма в скрипте
switch (self.state) {                         say "door opens"
  case OPENING:                               wait 3
    say("door opens");                        say "door closes"
    self.timer = 3; self.state = WAITING;     end
  case WAITING:
    if (--self.timer > 0) return;
    self.state = CLOSING;
  case CLOSING: ...
}
```

Сопрограмма — функция, которая может **приостановиться** (yield) и позже
**продолжиться** с того же места, сохранив локальные переменные. Именно этим
выразительность скриптов выигрывает у нативного кода.

### Stackless vs stackful

* **Stackless (относительно хоста).** Состояние выполнения скрипта — `pc`, стек
  значений, локальные — лежит в структуре VM, а не на стеке C. Тогда yield — это просто
  `return` из `resume()`, а продолжение — повторный `resume()` с сохранённого `pc`.
  Сопрограмма стоит столько, сколько её структура: тысяча скриптов — тысяча маленьких
  объектов. Так работают сопрограммы Lua (каждая — отдельный `lua_State` со своим
  стеком значений), генераторы Python, наша VM.
* **Stackful.** Сопрограмма имеет собственный машинный стек (fibers, глава 12). Можно
  уступить управление из глубины нативного вызова, но каждая стоит десятки килобайт и
  переключение контекста.

Подводный камень stackless-подхода: нельзя сделать yield **изнутри натива**, вызванного
скриптом, — стек хоста к этому моменту не пуст. В Lua для этого есть `lua_yieldk` с
продолжением (continuation function). Простое решение для игровой VM: «ожидающие»
операции (`wait`, `wait_anim`, `wait_event`) — это инструкции VM или нативы, которые
лишь *ставят условие пробуждения* и возвращают специальный код «yield».

### Планировщик

```
tick(now):
  for s in scripts (в порядке добавления — детерминизм!):
     if s.WAITING and now >= s.wake_tick:   s -> READY
     if s.READY:
        resume(s):  выполнять, пока не WAIT / END / ошибка / бюджет кванта
           WAIT n -> s.WAITING, s.wake_tick = now + max(n, 1)
           END    -> s.DONE
           ошибка -> s.FAULTED, сообщение, остальные продолжают
```

Детали, о которых стоит подумать заранее:

* **Время.** Ждать в тиках детерминированно (реплеи, lockstep); в секундах — удобнее
  дизайнеру. Обычно «секунды» пересчитываются в тики фиксированного шага (глава 01).
* **Условия пробуждения.** Кроме таймера: событие (`wait_event "door_opened"`),
  предикат («пока игрок не в зоне» — проверяется планировщиком, а не скриптом в цикле),
  завершение другой сопрограммы (join), окончание анимации/звука. Лучше, если
  условие проверяет движок: опрос в скрипте каждый тик стоит квант.
* **Отмена.** Сущность умерла — её сопрограммы должны быть убиты. Привяжите
  сопрограмму к владельцу (хендлу) и проверяйте его при пробуждении.
* **Квант.** Скрипт без yield в цикле съест бюджет и будет помечен FAULTED — это та же
  песочница из §4, только на уровне планировщика. (`e1404`)
* **Сохранение игры.** Если все данные сопрограммы — это `pc`, стек значений и хендлы,
  её можно сериализовать (глава 13) и восстановить. Со stackful-сопрограммами и с
  произвольными замыканиями Lua это почти невозможно — одна из причин, почему студии
  пишут свои VM для катсцен и квестов.

Аналоги в индустрии: latent functions в UnrealScript и Blueprints (узлы `Delay`),
`IEnumerator`/`yield return` в Unity, `async`/`await` в C#-движках, state scripts
Naughty Dog (описаны у Грегори), корутины Lua в Defold и Roblox.

## 8. Горячая перезагрузка скриптов

Самое ценное, что даёт скриптовый слой. Сценарий: дизайнер правит файл, сохраняет,
файловый наблюдатель (глава 07) замечает изменение, пайплайн перекомпилирует скрипт,
движок подменяет байткод **в работающей игре**.

Трудность в том, что **состояние принадлежит старой версии кода**. Байткод обращается к
переменным по индексам — а индексы между версиями не стабильны:

```
v1.globals = [ score, ticks ]            values = [ 3, 3 ]
v2.globals = [ combo, score, ticks ]
                 │       │      │
                 │       └──────┼──── перенос по ИМЕНИ: score = 3
                 │              └──── ticks = 3
                 └──────────────────── новой нет в v1 -> инициализатор (5)
(переменные, исчезнувшие в v2, выбрасываются)
```

Алгоритм перезагрузки:

1. **Скомпилировать и провалидировать** новую версию целиком. Если что-то не так —
   ничего не менять, показать ошибку. Файл могли сохранить на полуслове; игра обязана
   продолжить работать на старом коде.
2. **Перенести состояние по именам** (а не по индексам), новые переменные
   инициализировать, исчезнувшие — выбросить. Если поменялся *тип* переменной — либо
   конвертировать, либо инициализировать заново (и сообщить).
3. **Атомарно подменить** программу — между кадрами, не посреди выполнения скрипта.

Отдельный вопрос — **работающие сопрограммы**. Их `pc` указывает в старый байткод, и в
новом по этому адресу может оказаться что угодно. Варианты политики:

* перезапустить сопрограммы с начала (просто и предсказуемо, теряется прогресс);
* дождаться, пока все сопрограммы старой версии завершатся, а новые запускать на новом
  коде (две версии живут одновременно — так часто делают Erlang и серверы);
* сопоставлять точки ожидания по меткам/номерам `wait` (сложно, но идеально для
  длинных катсцен).

В Lua горячая перезагрузка обычно сводится к повторному выполнению chunk'а модуля и
переписыванию функций в существующих таблицах: данные живут в таблицах и переживают
перезагрузку, а функции заменяются. Ловушка — замыкания и upvalue, которые продолжают
ссылаться на старые функции. (`e1405`)

## 9. Где компилировать скрипт

* **В рантайме** (как Lua по умолчанию): простой цикл итерации, но компилятор едет в
  релизную сборку, а ошибки синтаксиса обнаруживаются на машине игрока.
* **Оффлайн в пайплайне ассетов** (глава 07): исходник → байткод на этапе сборки
  ассетов, в игре только загрузчик и VM. Плюсы: ошибки ловятся при сборке, в релизе
  нет компилятора (меньше кода, меньше поверхности атаки), можно делать дорогие
  оптимизации. Для hot reload пайплайн компилирует файл по запросу редактора.

Ассемблер или компилятор должен сообщать об ошибках **с номером строки и понятной
причиной** — «строка 2: неизвестная операция `jump`», а не «assertion failed». Ссылки
вперёд на метки и функции решаются **backpatching'ом**: переход на ещё не встреченную
метку записывается с пустым адресом и заносится в список «заплаток», которые
разрешаются в конце сборки. (`e1406`)

## 10. Производительность и память

* **Выделения памяти.** Самый частый источник тормозов скриптов — не интерпретация, а
  аллокации: строки, временные таблицы, замыкания на каждый кадр. Интернируйте строки
  (имена событий и анимаций — это id, а не строки), переиспользуйте таблицы.
* **Сборщик мусора.** Stop-the-world на 5 мс посреди кадра недопустим. Lua предлагает
  инкрементальный и поколенческий режимы; движки вызывают шаг GC явно, с бюджетом, в
  конце кадра (`lua_gc(L, LUA_GCSTEP, n)`). Своя VM с хендлами и без кучи (как наша)
  вообще не нуждается в GC — данные скрипта лежат в фиксированных массивах.
* **Потоки.** VM Lua однопоточна: один `lua_State` — один поток. Параллельный
  скриптинг делают либо независимыми VM на поток (без общих объектов), либо
  выполнением скриптов в одном потоке с отложенными командами в движок. Скрипты ИИ
  тысяч NPC часто запускают «размазанно»: каждый NPC думает раз в N кадров.
* **Профилирование.** Встраиваемый профилировщик (глава 15) должен видеть скрипты:
  зона на каждый `resume`, счётчик инструкций, топ скриптов по времени. Без этого
  «игра тормозит из-за скриптов» не поддаётся диагностике.
* **Детерминизм.** Для реплеев и lockstep-сети скрипт обязан быть детерминированным:
  никакого системного времени и общего `rand()` — только нативы, выдающие тики и
  детерминированный ГСЧ из состояния мира; порядок планировщика фиксирован; итерация по
  хеш-таблицам не должна влиять на результат.

## 11. Как это устроено в реальных движках

* **Unreal Engine.** Blueprints — визуальные графы, компилируемые в байткод VM
  (`UFunction` с `Script`-массивом). Граница с C++ задаётся рефлексией (`UFUNCTION`,
  `UPROPERTY`, генерация кода Unreal Header Tool). Латентные узлы (`Delay`) —
  сопрограммы на уровне графа.
* **Unity.** C# с IL2CPP (AOT) на консолях/мобилках. Корутины — итераторы
  (`IEnumerator`, `yield return new WaitForSeconds(3)`), которые движок «прокручивает»
  каждый кадр. Граница C# ↔ C++ — дорогая, поэтому Unity двигалась к DOTS/Burst.
* **Godot.** GDScript — собственный динамический язык с компиляцией в байткод и
  тесной интеграцией с системой объектов и сигналов; C# — как альтернатива.
* **Roblox.** Luau — форк Lua 5.1 с постепенной типизацией, быстрым интерпретатором,
  песочницей и interrupt-механизмом для прерывания долгих скриптов.
* **Naughty Dog.** Jak & Daxter написан почти целиком на GOAL — собственном Lisp'е с
  компилятором в машинный код. В серии Uncharted/The Last of Us — DC (data compiler на
  Racket/Scheme) для данных и «state scripts» для геймплея: скриптовые объекты с
  состояниями и сопрограммами, ожиданием событий и таймеров.
* **Bungie (Halo).** HaloScript — Lisp-подобный язык для миссий, с «потоками»
  (сопрограммами) и ожиданием условий (`sleep_until`).
* **Defold, Love2D, многие мобильные движки** — Lua как основной язык геймплея.

Общее у всех: (1) единая граница с движком через рефлексию/таблицу привязок,
(2) объекты движка доступны по хендлам или прокси, (3) время выражено сопрограммами
или их аналогами, (4) горячая перезагрузка как главная фича для команды.

## 12. Частые ошибки

* Хранить указатели движка в переменных скрипта (§6).
* Делать в скрипте работу движка: перебор всех сущностей, физику, поиск пути (§5).
* Отсутствие бюджета: один `while true do end` в моде — и игра зависла (§4).
* Поиск натива по строке на каждом вызове вместо линковки при загрузке (§5).
* Порядок выполнения скриптов зависит от хеш-таблицы или адресов — прощай,
  детерминизм реплеев (§10).
* Перезагрузка, подменяющая код до валидации; перенос состояния по индексам (§8).
* Сопрограмма, переживающая своего владельца: сущность уничтожена, а её скрипт через
  три секунды «просыпается» и обращается к ней (§7).
* Отсутствие инструментов: нет номеров строк в ошибках, нет отладчика и профилировщика
  — скриптовый слой становится «чёрным ящиком», которого боятся (§9, глава 15).
