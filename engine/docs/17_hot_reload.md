# Глава 17. Горячая перезагрузка кода и плагины

> Упражнения главы: `e1701_game_api` … `e1706_dlopen`. В конце главы — пошаговый проект
> настоящей горячей перезагрузки с `os::dlopen`, проверенный на c3c 0.8.5 (Linux).

Цикл «поправил строчку → пересобрал → перезапустил игру → загрузил уровень → дошёл до нужного
места → проверил» занимает в большом проекте от 30 секунд до нескольких минут. За день это
сотни итераций и часы потерянного времени, а главное — потерянная концентрация. Горячая
перезагрузка (hot reload) сокращает итерацию до секунды: пересобрали модуль, а игра **продолжает
работать** с тем же состоянием, но уже с новым кодом. Это одна из тех вещей, которые отличают
«движок, на котором можно делать игру» от «движка, который просто работает».

В главе 07 мы перезагружали **данные** (текстуры, конфиги), в главе 14 — **скрипты** в своей VM.
Здесь — нативный **код**. Это сложнее, потому что код и данные в нативной программе связаны
множеством невидимых нитей: указатели на функции, vtable, строковые литералы, глобальные
переменные, раскладка структур. Глава — о том, как эти нити найти и перерезать.

## 1. Механизм: динамические библиотеки

Операционная система умеет загружать машинный код во время работы процесса:

| ОС | загрузить | найти символ | выгрузить | файл |
|---|---|---|---|---|
| Linux/BSD | `dlopen` | `dlsym` | `dlclose` | `.so` |
| macOS | `dlopen` | `dlsym` | `dlclose` | `.dylib` |
| Windows | `LoadLibrary` | `GetProcAddress` | `FreeLibrary` | `.dll` |

В C3 0.8.5 это обёрнуто кроссплатформенно в `std::os`:

```c3
import std::os;

DylibHandle lib = os::dlopen("./libgame.so", { .resolve_now = true });
if (!lib) { /* не нашли или не загрузили */ }
void* sym = os::dlsym(lib, "game_update");        // null, если символа нет
GameUpdateFn update = (GameUpdateFn)sym;            // тип утверждаем МЫ
lib.close();
```

Есть Optional-варианты: `os::dlopen_try`, `os::dlsym_try`, `os::dlopen_any(name1, name2, ...)`.
Собрать динамическую библиотеку: `c3c dynamic-lib -o libgame game.c3 api.c3`. Чтобы функция
была видна `dlsym` под предсказуемым именем, пометьте её `@export("game_update")`.

Ключевой факт: **`dlsym` возвращает `void*`, и тип функции вы утверждаете приведением**.
Никакой проверки нет. Если хост думает, что это `fn void(GameMemory*, int)`, а модуль собран
со старым заголовком, где второй аргумент был `float`, — получите мусор. Отсюда первое
архитектурное правило: экспортируйте **одну** функцию, возвращающую **проверяемую таблицу**.

## 2. Архитектура «хост + модуль»

Подход, популяризированный Кейси Муратори в Handmade Hero (эпизоды 21–25), и до сих пор
лучший для начала:

```
  +---------------------- процесс игры ------------------------+
  |                                                            |
  |  ХОСТ (исполняемый файл, НЕ перезагружается)               |
  |   - окно, ввод, звук, ОС                                   |
  |   - главный цикл                                           |
  |   - ВСЯ память игры: один большой блок GameMemory  <----+  |
  |   - следит за файлом модуля, перезагружает             |  |
  |              |                                         |  |
  |              | game_api = get_game_api()               |  |
  |              v                                         |  |
  |  МОДУЛЬ ИГРЫ (game.so, перезагружается)                |  |
  |   - ВСЯ игровая логика                                 |  |
  |   - НЕ имеет глобального состояния                     |  |
  |   - каждый вызов получает GameMemory* ------------------+  |
  +------------------------------------------------------------+
```

Почему это работает: состояние игры — это байты в памяти хоста. Модуль — это просто функции,
которые эти байты интерпретируют и меняют. Заменили функции — байты остались. Если игра
хранит всё состояние в одном блоке памяти (арены из главы 02!), то «перезагрузка с сохранением
состояния» бесплатна. Бонусом Муратори получил **запись и воспроизведение** ввода: скопировать
блок памяти, записать ввод, потом восстановить блок и проиграть ввод в цикле — и правьте код,
наблюдая, как один и тот же кусок геймплея проигрывается с новой логикой (это прямая связь
с детерминизмом из главы 01 и воспроизведением ввода из главы 10).

### Таблица функций (ABI-договор)

```c3
const uint API_MAGIC = 0x47414D45;
const uint API_VERSION = 3;

struct GameApi
{
    uint magic;          // «это вообще наш модуль?»
    uint version;        // версия договора
    usz size;            // GameApi::size на момент сборки модуля
    LifecycleFn on_load;
    LifecycleFn on_unload;
    UpdateFn update;
}
```

Хост обязан проверить `magic`, `version` и `size` **до** первого вызова. `size` ловит самый
частый случай: в общий заголовок добавили функцию, хост пересобрали, а модуль — нет (или
наоборот). Если проверка не прошла — **оставляем старый модуль работать** и пишем в лог. Не
падать при плохой перезагрузке — обязательное свойство: вы ведь часто сохраняете файл с
опечаткой, и сборка молча оставляет старую `.so`, либо собирается частично.

Порядок перезагрузки:

```
new = загрузить новую копию; проверить new.api
  плохо -> выгрузить new, остаться на старом, сообщить
old.api.on_unload(&memory)    // модуль сбрасывает кэши, указатели на свой код
выгрузить old
api = new.api
api.on_load(&memory)          // модуль перестраивает кэши, перерегистрирует колбэки
```

Это упражнение `e1701_game_api`.

## 3. Что ломается при перезагрузке

Модуль выгружен — значит, все адреса внутри его образа в памяти стали недействительными.
Перечислим, что указывает внутрь модуля:

1. **Указатели на функции**, сохранённые в постоянной памяти: колбэки, «think»-функции
   сущностей, обработчики событий. Лечение: хранить **идентификатор** (enum, индекс, хеш
   имени) и находить адрес через таблицу текущего модуля каждый раз (`e1702_stale_pointers`).
   Это ровно та же идея, что хендлы вместо указателей в главе 03.
2. **Таблицы виртуальных методов**. В C++ у каждого объекта с виртуальными методами есть
   скрытый указатель на vtable — а vtable лежит в сегменте данных модуля. В C3 значения
   интерфейсного типа (`any`, интерфейсы с `@dynamic`) тоже несут информацию о типе и
   методах, которая живёт в образе модуля. Не храните их в постоянной памяти.
3. **Строковые литералы и константные данные.** `String name = "goblin";` — это указатель
   в `.rodata` модуля. После выгрузки строка исчезает. Лечение: копировать строки в память
   хоста (интернирование в арене), хранить идентификаторы.
4. **Глобальные переменные модуля.** Новая копия библиотеки получает свои, свежие, глобалы.
   Если игра хранила счётчик в глобале — он «обнулится». Лечение: никаких глобалов с
   состоянием; всё — в `GameMemory`.
5. **Раскладка структур.** Добавили поле — старые байты интерпретируются по-новому. Лечение:
   заголовок с версией и миграция (`e1703_state_migration`), либо рефлексия и миграция по
   именам полей (глава 13), либо просто перезапуск при изменении раскладки.
6. **Стандартная библиотека внутри модуля.** Каждая `.so`, собранная c3c, статически
   содержит свою копию нужных частей стандартной библиотеки C3 — со своими глобалами и
   thread-local данными. Например, временный аллокатор (`tmem`) и `@pool` в модуле и в хосте —
   **разные** объекты. Память, выделенную `tmem` модуля, нельзя передать хосту на следующий
   кадр. Общая куча (`mem`, поверх libc `malloc`) у них одна, поскольку libc загружена в
   процесс один раз, но надёжнее всего, чтобы модуль вообще не выделял память сам, а получал
   аллокаторы/арены от хоста (через `GameMemory` или таблицу API хоста).
7. **Потоки и задачи.** Если job system (глава 12) держит в очереди задачу с указателем на
   функцию модуля, а вы его выгрузили — падение через несколько миллисекунд, в другом потоке,
   с бессмысленным стеком. Перед перезагрузкой: дождаться опустошения очередей (барьер), и
   только потом выгружать.
8. **Статические инициализаторы** (`@init`) модуля выполняются при каждой загрузке; финализаторы
   — при выгрузке. Побочные эффекты в них должны быть идемпотентны.

Отсюда общее правило: **в постоянной памяти — только «простые данные» (POD)**: числа,
массивы, индексы, хендлы, смещения. Никаких указателей в код или в константы модуля.

## 4. Детали, о которые спотыкаются все

### Копирование перед загрузкой

Компилятор перезаписывает `libgame.so`, пока хост её использует. На Linux это обычно
«работает» (старый inode остаётся живым), но если компилятор пишет файл на месте, загруженный
образ может измениться под ногами. Плюс `dlopen` кэширует библиотеки **по пути**: повторный
`dlopen` того же пути без `dlclose` вернёт старый хендл. На Windows ещё хуже: загруженная DLL
заблокирована, и линкер не сможет её перезаписать вовсе.

Решение: перед загрузкой **копировать** модуль во временный файл с уникальным именем
(`libgame_7.so`) и загружать копию. Исходник остаётся свободным для компилятора.

### Недописанный файл

Проверка по времени модификации может сработать, когда компилятор записал файл наполовину.
Варианты: компилятор сначала пишет во временный файл и делает атомарный `rename` (многие
системы сборки так и делают), либо сборочный скрипт после успешной сборки создаёт
файл-маркер `lock.tmp`/`build.done`, и хост перезагружает только по нему (Handmade Hero:
хост ждёт, пока исчезнет `lock.tmp`).

### PDB на Windows

Visual Studio держит открытым `.pdb` загруженной DLL, и следующая сборка не может его
перезаписать. Классический трюк: линковать с уникальным именем PDB на каждую сборку
(`/PDB:game_%random%.pdb`). Это деталь, но из-за неё горячая перезагрузка на Windows у многих
«не работает».

### Отладчик

Точки останова в перезагруженном модуле отладчики поддерживают с разным успехом. Это нормально:
горячая перезагрузка — инструмент для итерации над логикой, а не замена отладчика.

## 5. Масштабирование: реестр API и плагины

Один модуль «вся игра» — хорошо для маленького проекта. Большой движок состоит из десятков
подсистем, и хочется перезагружать каждую отдельно, а также подключать сторонние расширения
(плагины редактора, инструменты). Our Machinery (движок авторов Bitsquid/Stingray,
2018–2022) построил всю архитектуру вокруг **реестра API**:

```
            +------------------------- API REGISTRY ------------------------+
            |  "tm_log_api"     v1.2   [ write | count | ... ]  implemented |
            |  "tm_render_api"  v3.0   [ ...                 ]  implemented |
            |  "tm_physics_api" v1.0   [ 0     | 0     | ... ]  (ещё нет)   |
            +-----^--------------------------^-----------------^------------+
                  | set() копирует таблицу   | get() -> указатель на СЛОТ
                  |                          |
           plugin_log.so               plugin_ui.so  (держит LogApi* навсегда)
```

* **Всё — плагины**, даже ядро. Каждый плагин экспортирует одну функцию
  `tm_load_plugin(registry, load: bool)`, в которой регистрирует свои API и получает чужие.
* `get(name, version)` возвращает указатель **на слот внутри реестра**. `set()` копирует таблицу
  функций в слот. Перезагрузили плагин — он снова вызвал `set()`, и все, кто давно держит
  указатель на слот, автоматически вызывают новый код. Не нужно рассылать уведомления.
* **Позднее связывание**: `get()` до `set()` создаёт пустой слот. Порядок загрузки плагинов
  перестаёт иметь значение для связывания (но не для инициализации — см. ниже).
* **Семантическое версионирование** API: мажорная версия ломает совместимость, минорная
  добавляет функции только в конец структуры.
* **Интерфейсы** (в терминах OM — `add_implementation`): несколько плагинов могут реализовать
  один интерфейс (например, «импортёр ассетов»), и реестр хранит их список.

В упражнении `e1704_api_registry` вы реализуете такой реестр, а в `e1705_plugin_manager` —
менеджер плагинов с топологической сортировкой зависимостей. Важная деталь: порядок
загрузки должен быть **детерминированным** (сортировка по стабильному ключу, а не по порядку
файлов в каталоге или хеш-таблице), а выгрузка — строго в обратном порядке.

## 6. Как это делают в индустрии

* **Handmade Hero** — эталонный учебный пример: хост + `game.dll`, вся память — один блок,
  запись/воспроизведение ввода. Смотрите эпизоды 21–25 и обсуждение «Loop editing».
* **Our Machinery** — реестр API, всё как плагины, перезагрузка любого плагина. Блог Our
  Machinery (статьи «The API registry», «Plugins», «Hot reloading») — лучшее чтение по теме.
* **Unreal Engine Live Coding** (на базе технологии Live++) — патчит функции **внутри
  работающего процесса**: перекомпилирует изменённые единицы трансляции, загружает их и
  переписывает начало старых функций переходом на новые. Позволяет менять код без особой
  дисциплины, но не умеет менять раскладку объектов.
* **Live++** (Molecular Matters) — коммерческий инструмент того же типа для C/C++,
  используется во многих AAA-студиях.
* **Godot / Unity** — горячая перезагрузка уровня скриптового языка (GDScript, C# domain
  reload): та же проблема сохранения состояния, решаемая сериализацией объектов перед
  перезагрузкой и восстановлением после — то есть через рефлексию (глава 13).
* **cr.h** (fungos) — однофайловая C-библиотека горячей перезагрузки с откатом при падении
  нового кода (ловит сигнал и возвращается к предыдущей версии). Полезно почитать исходники.

## 7. Альтернативы горячей перезагрузке кода

Не всегда стоит строить нативную горячую перезагрузку. Варианты:

* **Скрипты** (глава 14): перезагрузка проще, но два языка, граница вызовов, производительность.
* **Данные вместо кода**: настраиваемые параметры, кривые, графы поведения — перезагружаются
  как ассеты (глава 07), и программист вообще не нужен.
* **Быстрый перезапуск + сериализация состояния**: если игра стартует за секунду и умеет
  сохранять/загружать состояние, можно автоматически перезапускать процесс. Самый надёжный
  вариант, не требует никакой дисциплины кода.
* **Tweak-переменные**: значения в исходнике, помеченные макросом, читаются из файла во время
  работы (трюк из блога Джонатана Блоу / Mollyrocket).

Выбор — инженерный: горячая перезагрузка нативного кода окупается в проектах, где геймплейный
код пишут на том же языке, что движок, и итерации над ним постоянные.

## 8. Проект: настоящая горячая перезагрузка на C3

Этот рецепт проверен на c3c 0.8.5 под Linux. Создайте каталог **вне** курса, например
`~/hotreload/`, и три файла.

**api.c3** — общий договор хоста и модуля:

```c3
module game_api;

const uint GAME_API_VERSION = 1;

struct GameState
{
    uint version;
    int frame;
    int score;
}

struct GameMemory
{
    void* storage;
    usz size;
    bool initialized;
}

alias GameUpdateFn = fn void(GameMemory*, int);
```

**game.c3** — перезагружаемый модуль:

```c3
module game;
import game_api, std::io;

fn void game_update(GameMemory* mem, int frame) @export("game_update")
{
    GameState* s = (GameState*)mem.storage;
    if (!mem.initialized)
    {
        *s = { .version = game_api::GAME_API_VERSION };
        mem.initialized = true;
    }
    s.frame = frame;
    s.score += 1;   // поменяйте на += 100, пересоберите — и смотрите
    io::printfn("frame %d score %d", s.frame, s.score);
}
```

(Обратите внимание: константу из другого модуля нужно писать с префиксом —
`game_api::GAME_API_VERSION`, иначе компилятор выдаст ошибку.)

**host.c3** — хост:

```c3
module host;
import game_api, std::io, std::os, std::thread, std::io::file, std::time;

struct GameCode
{
    DylibHandle lib;
    GameUpdateFn update;
    Time stamp;
    int generation;
}

fn bool GameCode.load(&self)
{
    Time? t = file::last_modified("libgame.so");
    if (catch t) return false;
    // копия: компилятор может перезаписывать libgame.so, пока мы держим копию,
    // а уникальное имя обходит кэш dlopen по пути
    char[]? data = file::load(mem, "libgame.so");
    if (catch data) return false;
    defer free(data);
    String name = string::tformat("./libgame_%d.so", self.generation);
    if (catch file::save(name, data)) return false;
    DylibHandle lib = os::dlopen(name.zstr_tcopy(), { .resolve_now = true });
    (void)file::delete(name);          // на Linux файл можно удалить сразу после dlopen
    if (!lib) return false;
    void* sym = os::dlsym(lib, "game_update");
    if (!sym) { lib.close(); return false; }   // плохой модуль — остаёмся на старом
    if (self.lib) self.lib.close();
    self.lib = lib;
    self.update = (GameUpdateFn)sym;
    self.stamp = t;
    self.generation++;
    return true;
}

fn void main()
{
    GameMemory gm = { .storage = mem::calloc(1 << 20), .size = 1 << 20 };
    GameCode code;
    if (!code.load()) { io::printn("initial load failed"); return; }
    for (int frame = 0; frame < 40; frame++)
    {
        Time? t = file::last_modified("libgame.so");
        if (try t && t != code.stamp)
        {
            if (code.load()) io::printfn("-- reloaded (generation %d)", code.generation);
        }
        code.update(&gm, frame);
        thread::sleep_ms(100);
    }
    code.lib.close();
}
```

```
$ c3c dynamic-lib -o libgame game.c3 api.c3      # -> libgame.so
$ c3c compile -o host host.c3 api.c3
$ ./host &                                        # печатает frame N score N
$ # через секунду поменяйте в game.c3 "+= 1" на "+= 100" и пересоберите:
$ c3c dynamic-lib -o libgame game.c3 api.c3
```

Реальный вывод при проверке:

```
frame 17 score 18
frame 18 score 19
-- reloaded (generation 2)
frame 19 score 119
frame 20 score 219
```

Счёт продолжился с 19 — состояние пережило замену кода. Что улучшить дальше (это и есть
путь от игрушки к инструменту):

1. Экспортировать не `game_update`, а `get_game_api()`, возвращающую таблицу с
   magic/version/size, как в `e1701`.
2. `file::last_modified` имеет секундную точность: две сборки в одну секунду не заметить.
   Сравнивайте ещё и размер или хеш файла, либо используйте файл-маркер от сборочного скрипта.
3. Защита от недописанного файла: ждите, пока размер/время не перестанут меняться пару
   опросов подряд, или маркер `build.done`.
4. Запись/воспроизведение ввода и «петля» по фрагменту геймплея (Handmade Hero).
5. Вызовы `on_unload/on_load`, барьер для job system перед выгрузкой.
6. На macOS имя будет `libgame.dylib`, на Windows — `game.dll` (+ трюк с PDB).

## 9. Подводные камни (чек-лист)

* Вызов кода модуля без проверки версии/размера таблицы.
* Указатели на функции, интерфейсы, строковые литералы модуля в постоянной памяти.
* Глобальное состояние в модуле.
* Изменение раскладки состояния без версии и миграции; миграция «на месте», когда новая
  структура больше старой и перекрывается с ней (нужен временный буфер).
* `dlopen` того же пути без копирования; блокировки файлов на Windows.
* Перезагрузка, пока другие потоки исполняют код модуля.
* Память, выделенная временным аллокатором модуля и пережившая кадр.
* Падение при неудачной перезагрузке вместо отката к старому модулю.
* Недетерминированный порядок загрузки плагинов; выгрузка не в обратном порядке.
