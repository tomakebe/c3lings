# Глава 17. Горячая перезагрузка кода и плагины

> Упражнения главы: `e1701_game_api` … `e1706_dlopen`. В конце главы — пошаговый проект
> настоящей горячей перезагрузки с `os::dlopen`, проверенный на c3c 0.8.5 (Linux).

## Карта главы

**Что вы узнаете.** Как программа может подгрузить кусок машинного кода во время работы
(динамические библиотеки, `dlopen`/`dlsym`); как устроить игру, чтобы код можно было заменить,
не теряя состояния (хост + модуль, таблица функций); что именно «ломается» при замене кода и
как этого избежать (висячие указатели на функции, строки, глобалы, изменение раскладки
структур); как масштабировать идею до десятков плагинов (реестр API, зависимости, порядок
загрузки).

**Зачем это нужно.** Скорость итерации: правка → результат за секунду вместо минуты. А ещё
это лучший способ по-настоящему понять, что такое «адрес», «символ», «ABI» и «раскладка
структуры» — после этой главы они перестанут быть абстракциями.

**Что нужно знать заранее.** Указатели на функции и `alias` для их типов (трек по C3);
хендлы вместо указателей (глава 03); арены и «вся память одним блоком» (глава 02);
версионирование данных (глава 13). Опыт с динамическими библиотеками не нужен — объясним.

**Какие разделы нужны каким упражнениям.**

| упражнение | о чём | разделы главы |
|---|---|---|
| `e1701_game_api` | проверка таблицы функций, порядок перезагрузки | 1.3, 2 |
| `e1702_stale_pointers` | идентификатор поведения вместо указателя на функцию | 3.1–3.2 |
| `e1703_state_migration` | заголовок состояния и миграция через буфер | 3.3 |
| `e1704_api_registry` | реестр API: слоты, позднее связывание, версии | 5.1–5.2 |

| `e1706_dlopen` | настоящий `os::dlopen`/`dlsym` | 1, 8 |

## Введение: зачем перезагружать код на ходу

Цикл «поправил строчку → пересобрал → перезапустил игру → загрузил уровень → дошёл до нужного
места → проверил» занимает в большом проекте от 30 секунд до нескольких минут. За день это
сотни итераций и часы потерянного времени, а главное — потерянная концентрация. Горячая
перезагрузка (hot reload) сокращает итерацию до секунды: пересобрали модуль, а игра **продолжает
работать** с тем же состоянием, но уже с новым кодом. Это одна из тех вещей, которые отличают
«движок, на котором можно делать игру» от «движка, который просто работает».

Аналогия: автомеханик меняет двигатель. Обычный способ — заглушить машину, разобрать,
собрать, завести, снова доехать до нужного места. Горячая перезагрузка — заменить двигатель
**на ходу**, не останавливая машину и не высаживая пассажиров (состояние игры). Звучит
невозможно, но если машина спроектирована так, что двигатель отделён от всего остального
стандартными креплениями, — вполне.

В главе 07 мы перезагружали **данные** (текстуры, конфиги), в главе 14 — **скрипты** в своей VM.
Здесь — нативный **код** (машинные инструкции процессора, в которые компилятор превратил
ваш C3). Это сложнее, потому что код и данные в нативной программе связаны
множеством невидимых нитей: указатели на функции, vtable, строковые литералы, глобальные
переменные, раскладка структур. Глава — о том, как эти нити найти и перерезать.

> **Коротко:** горячая перезагрузка заменяет код работающей игры, сохраняя её состояние.
> Главная трудность — всё, что в памяти игры «указывает в старый код».

## 1. Механизм: динамические библиотеки

### 1.1. Что такое динамическая библиотека

Обычно компилятор собирает всё в один исполняемый файл — **статическая компоновка**:
весь код «вклеен» внутрь. **Динамическая библиотека** (shared library) — отдельный файл с
машинным кодом, который программа подгружает во время работы. Вы постоянно ими пользуетесь:
libc (стандартная библиотека C), libm (математика), драйверы видеокарты — всё это `.so` на
Linux или `.dll` на Windows.

Немного терминов:

* **Адресное пространство процесса** — вся память, которую видит программа. Каждая функция
  и каждая переменная лежит по какому-то **адресу** (номеру байта в этом пространстве).
* **Загрузка библиотеки** — ОС читает файл и размещает его код и данные где-то в адресном
  пространстве. Где именно — решает ОС, и при следующей загрузке адрес будет другим.
* **Символ** — имя функции или переменной, которое библиотека «выставляет наружу»
  (экспортирует). Внутри файла библиотеки хранится таблица «имя → смещение».
* **Выгрузка** — ОС убирает код библиотеки из памяти. Все адреса внутри неё становятся
  недействительными: обращение туда — падение (segfault) или, хуже, выполнение чужого кода.

Аналогия: библиотека — картридж игровой приставки. Вставили картридж — приставка может
вызывать программы на нём. В картридже есть «оглавление» (таблица символов): «функция
game_update — на странице 1234». Вынули картридж — страница 1234 больше не существует, и
любые закладки на неё бессмысленны. Вставили новый картридж — оглавление новое, страницы
другие.

> **Коротко:** динамическая библиотека — машинный код, подгружаемый во время работы; её
> функции находят по имени (символу); после выгрузки все адреса внутри неё мертвы.

### 1.2. API операционной системы и обёртка C3

Операционная система умеет загружать машинный код во время работы процесса:

| ОС | загрузить | найти символ | выгрузить | файл |
|---|---|---|---|---|
| Linux/BSD | `dlopen` | `dlsym` | `dlclose` | `.so` |
| macOS | `dlopen` | `dlsym` | `dlclose` | `.dylib` |
| Windows | `LoadLibrary` | `GetProcAddress` | `FreeLibrary` | `.dll` |

В C3 0.8.5 это обёрнуто кроссплатформенно в `std::os`:

```c3
import std::os;

DylibHandle lib = os::dlopen("./libgame.so", { .resolve_now = true });
if (!lib) { /* не нашли или не загрузили */ }
void* sym = os::dlsym(lib, "game_update");        // null, если символа нет
GameUpdateFn update = (GameUpdateFn)sym;            // тип утверждаем МЫ
lib.close();
```

Построчно:

1. `os::dlopen(путь, опции)` — загрузить библиотеку. `DylibHandle` — непрозрачный
   «номерок», который ОС выдала на эту загрузку; если загрузка не удалась — он пустой
   (`!lib`). Опция `resolve_now` просит сразу проверить, что все функции, которые нужны
   самой библиотеке, нашлись (иначе ошибка всплыла бы позже, посреди игры).
2. `os::dlsym(lib, "имя")` — найти адрес символа по имени. Возвращает `void*` — «просто
   адрес, тип неизвестен» — или `null`, если такого имени нет.
3. Приведение `(GameUpdateFn)sym` — мы **заявляем** компилятору: «по этому адресу лежит
   функция вот такого типа». Компилятор верит на слово.
4. `lib.close()` — выгрузить. После этого `update` указывает в никуда.

Есть Optional-варианты: `os::dlopen_try`, `os::dlsym_try`, `os::dlopen_any(name1, name2, ...)`.
Собрать динамическую библиотеку: `c3c dynamic-lib -o libgame game.c3 api.c3`. Чтобы функция
была видна `dlsym` под предсказуемым именем, пометьте её `@export("game_update")`.

Имя файла библиотеки разное на разных системах (`libm.so.6` на Linux, `libm.dylib` на
macOS, `ucrtbase.dll` на Windows), поэтому код часто перебирает список кандидатов и берёт
первый, который загрузился, — именно это делает `e1706`.

> **Коротко:** `dlopen` → `dlsym` → привести `void*` к типу функции → вызывать → `close`.

### 1.3. Ключевой факт: типы никто не проверяет

Ключевой факт: **`dlsym` возвращает `void*`, и тип функции вы утверждаете приведением**.
Никакой проверки нет. Если хост думает, что это `fn void(GameMemory*, int)`, а модуль собран
со старым заголовком, где второй аргумент был `float`, — получите мусор. Отсюда первое
архитектурное правило: экспортируйте **одну** функцию, возвращающую **проверяемую таблицу**.

Почему «мусор», а не ошибка? На x86-64 целые аргументы передаются в одних регистрах
процессора, а float — в других. Хост положит число 5 в целочисленный регистр, а модуль
прочитает float из своего регистра, где лежит что угодно от предыдущих вычислений. Никто
ничего не заметит — просто персонаж начнёт двигаться со скоростью 3.7e-12.

**ABI** (Application Binary Interface, «двоичный интерфейс») — договор на уровне байтов:
какие аргументы в каких регистрах, как разложены поля структур, сколько байт занимает
каждый тип. Если хост и модуль собраны с разными версиями общего заголовка, их ABI может
разойтись — а компилятор об этом узнать не может, потому что собирал их по отдельности.

> **Коротко:** `dlsym` не знает типов; ошибка в типе — тихий мусор. Поэтому экспортируют
> одну функцию, возвращающую таблицу с проверяемыми полями.

## 2. Архитектура «хост + модуль»

### 2.1. Разделение ролей

Подход, популяризированный Кейси Муратори в Handmade Hero (эпизоды 21–25), и до сих пор
лучший для начала:

```
  +---------------------- процесс игры ------------------------+
  |                                                            |
  |  ХОСТ (исполняемый файл, НЕ перезагружается)               |
  |   - окно, ввод, звук, ОС                                   |
  |   - главный цикл                                           |
  |   - ВСЯ память игры: один большой блок GameMemory  <----+  |
  |   - следит за файлом модуля, перезагружает             |  |
  |              |                                         |  |
  |              | game_api = get_game_api()               |  |
  |              v                                         |  |
  |  МОДУЛЬ ИГРЫ (game.so, перезагружается)                |  |
  |   - ВСЯ игровая логика                                 |  |
  |   - НЕ имеет глобального состояния                     |  |
  |   - каждый вызов получает GameMemory* ------------------+  |
  +------------------------------------------------------------+
```

**Хост** — исполняемый файл, который запускается один раз и живёт всю сессию. **Модуль** —
динамическая библиотека с игровой логикой, которую можно заменять.

Почему это работает: состояние игры — это байты в памяти хоста. Модуль — это просто функции,
которые эти байты интерпретируют и меняют. Заменили функции — байты остались. Если игра
хранит всё состояние в одном блоке памяти (арены из главы 02!), то «перезагрузка с сохранением
состояния» бесплатна.

Аналогия: настольная игра. Доска с фишками — это память хоста. Правила игры — модуль.
Можно посреди партии договориться о новых правилах («теперь ход на 2 клетки больше») — фишки
остаются на своих местах, просто дальше ходят по-новому.

Бонусом Муратори получил **запись и воспроизведение** ввода: скопировать
блок памяти, записать ввод, потом восстановить блок и проиграть ввод в цикле — и правьте код,
наблюдая, как один и тот же кусок геймплея проигрывается с новой логикой (это прямая связь
с детерминизмом из главы 01 и воспроизведением ввода из главы 10).

```
время ->   [снимок памяти]  ввод: ← ← прыжок →  [восстановить снимок] ввод: ← ← прыжок → ...
                                  ^ правите код прыжка здесь, следующий круг — уже с новым кодом
```

> **Коротко:** хост владеет памятью и живёт вечно; модуль — только функции, которые эту
> память меняют. Заменили модуль — память осталась.

### 2.2. Таблица функций (ABI-договор)

Вместо того чтобы искать через `dlsym` десять функций по отдельности, модуль экспортирует
одну функцию `get_game_api()`, которая возвращает указатель на структуру с указателями на
все остальные функции и с «паспортными данными»:

```c3
const uint API_MAGIC = 0x47414D45;
const uint API_VERSION = 3;

struct GameApi
{
    uint magic;          // «это вообще наш модуль?»
    uint version;        // версия договора
    usz size;            // GameApi::size на момент сборки модуля
    LifecycleFn on_load;
    LifecycleFn on_unload;
    UpdateFn update;
}
```

Поля:

* **magic** — «магическое число», фиксированная константа. `0x47414D45` — это байты ASCII
  `G A M E`. Если в этом поле что-то другое — нам подсунули вообще не тот файл (или указатель
  на мусор).
* **version** — номер версии договора. Меняете **смысл** или **сигнатуру** функций — увеличиваете
  версию.
* **size** — размер структуры `GameApi` в тот момент, когда **модуль** компилировался.
  Хост сравнивает с размером, который знает **он сам**.
* Остальные поля — указатели на функции.

Хост обязан проверить `magic`, `version` и `size` **до** первого вызова. `size` ловит самый
частый случай: в общий заголовок добавили функцию, хост пересобрали, а модуль — нет (или
наоборот). Если проверка не прошла — **оставляем старый модуль работать** и пишем в лог. Не
падать при плохой перезагрузке — обязательное свойство: вы ведь часто сохраняете файл с
опечаткой, и сборка молча оставляет старую `.so`, либо собирается частично.

Пример: что ловит каждая проверка.

| что подсунули | magic | version | size | вердикт |
|---|---|---|---|---|
| правильный модуль | совпал | 3 = 3 | 48 = 48 | принять |
| модуль, собранный со старым заголовком | совпал | 2 ≠ 3 | 48 | отвергнуть |
| в заголовок добавили функцию, модуль не пересобран | совпал | 3 | 40 ≠ 48 | отвергнуть |
| чужая библиотека / мусор | `0xDEADBEEF` | — | — | отвергнуть |
| `get_game_api()` вернула null | — | — | — | отвергнуть (сначала проверить null!) |

(Размеры здесь условные — важна идея «сравнить два числа».)

Зачем `size`, если есть `version`? Потому что люди забывают увеличивать версию. Размер же
меняется автоматически при добавлении поля — это «защита от забывчивости».

> **Коротко:** модуль отдаёт таблицу функций с magic/version/size; хост проверяет все три
> (и null) до первого вызова; не прошло — остаёмся на старом модуле.

### 2.3. Порядок перезагрузки

```
new = загрузить новую копию; проверить new.api
  плохо -> выгрузить new, остаться на старом, сообщить
old.api.on_unload(&memory)    // модуль сбрасывает кэши, указатели на свой код
выгрузить old
api = new.api
api.on_load(&memory)          // модуль перестраивает кэши, перерегистрирует колбэки
```

Почему именно такой порядок:

1. **Сначала проверить новое, потом трогать старое.** Если новое плохое, старое должно
   продолжить работать как ни в чём не бывало.
2. **`on_unload` старого — до выгрузки**: это последний шанс старого кода «прибраться» —
   например, отписать свои колбэки из системы событий (глава 06).
3. **`on_load` нового — после переключения**: новый код перестраивает то, что старый
   выбросил (кэши, регистрации). `on_load` вызывается при **каждой** успешной загрузке,
   включая самую первую.

Пошаговая хронология (`score` — поле состояния в памяти хоста):

| шаг | событие | активный модуль | score |
|---|---|---|---|
| 1 | загрузили v1, `on_load` | v1 | 0 |
| 2 | 5 кадров по +1·input | v1 | 15 |
| 3 | попытка загрузить «старый заголовок» → отвергнут | v1 | 15 |
| 4 | кадр | v1 | 16 |
| 5 | загрузили v2 (`score += input·10`): `on_unload` v1, `on_load` v2 | v2 | 16 |
| 6 | 3 кадра | v2 | 76 |

На шаге 5 `score` не обнулился — он лежит в памяти хоста. Это упражнение `e1701_game_api`.

> **Частые ошибки**
> * Присвоить `self.api = new_api` до проверки — при плохом модуле хост уже переключён.
> * Забыть, что при первой загрузке «старого» модуля нет (`api == null`) — не вызывайте
>   `on_unload` у null.
> * Не проверить, что `get_api()` вообще вернула не null.
> * Считать перезагрузку успешной (счётчик) до того, как она действительно прошла.

> **Коротко:** проверить новое → `on_unload` старого → переключиться → `on_load` нового.

## 3. Что ломается при перезагрузке

### 3.1. Всё, что указывает внутрь модуля

Модуль выгружен — значит, все адреса внутри его образа в памяти стали недействительными.
**Образ** модуля — это его код и константы, размещённые в памяти процесса. **Висячий
указатель** (dangling pointer) — указатель на память, которой больше нет (или которая
теперь принадлежит чему-то другому).

```
  GameMemory (живёт у хоста)            game_v1.so  (выгружена!)
  +------------------------+            +-------------------+
  | entity[0].think = 0x7f.|----------->|  ??? (unmapped)   |
  | entity[1].think = 0x7f.|----------->|                   |
  +------------------------+            +-------------------+
                                        game_v2.so (новая, по ДРУГОМУ адресу)
```

Перечислим, что указывает внутрь модуля:

1. **Указатели на функции**, сохранённые в постоянной памяти: колбэки, «think»-функции
   сущностей (функция, которую сущность вызывает каждый кадр, чтобы «подумать», что
   делать), обработчики событий. Лечение: хранить **идентификатор** (enum, индекс, хеш
   имени) и находить адрес через таблицу текущего модуля каждый раз (`e1702_stale_pointers`).
   Это ровно та же идея, что хендлы вместо указателей в главе 03.
2. **Таблицы виртуальных методов**. В C++ у каждого объекта с виртуальными методами есть
   скрытый указатель на **vtable** (таблицу адресов методов этого класса) — а vtable лежит в
   сегменте данных модуля. В C3 значения
   интерфейсного типа (`any`, интерфейсы с `@dynamic`) тоже несут информацию о типе и
   методах, которая живёт в образе модуля. Не храните их в постоянной памяти.
3. **Строковые литералы и константные данные.** `String name = "goblin";` — это указатель
   в `.rodata` модуля (`.rodata` — «read-only data», участок образа с константами). После
   выгрузки строка исчезает. Лечение: копировать строки в память хоста (**интернирование**
   в арене — хранить одну копию каждой строки в общем пуле), хранить идентификаторы.
4. **Глобальные переменные модуля.** Новая копия библиотеки получает свои, свежие, глобалы.
   Если игра хранила счётчик в глобале — он «обнулится». Лечение: никаких глобалов с
   состоянием; всё — в `GameMemory`.
5. **Раскладка структур.** Добавили поле — старые байты интерпретируются по-новому. Лечение:
   заголовок с версией и миграция (`e1703_state_migration`), либо рефлексия и миграция по
   именам полей (глава 13), либо просто перезапуск при изменении раскладки. Подробно — в 3.3.
6. **Стандартная библиотека внутри модуля.** Каждая `.so`, собранная c3c, статически
   содержит свою копию нужных частей стандартной библиотеки C3 — со своими глобалами и
   thread-local данными. Например, временный аллокатор (`tmem`) и `@pool` в модуле и в хосте —
   **разные** объекты. Память, выделенную `tmem` модуля, нельзя передать хосту на следующий
   кадр. Общая куча (`mem`, поверх libc `malloc`) у них одна, поскольку libc загружена в
   процесс один раз, но надёжнее всего, чтобы модуль вообще не выделял память сам, а получал
   аллокаторы/арены от хоста (через `GameMemory` или таблицу API хоста).
7. **Потоки и задачи.** Если job system (глава 12) держит в очереди задачу с указателем на
   функцию модуля, а вы его выгрузили — падение через несколько миллисекунд, в другом потоке,
   с бессмысленным стеком. Перед перезагрузкой: дождаться опустошения очередей (**барьер** —
   точка, где все потоки останавливаются и ждут друг друга), и только потом выгружать.
8. **Статические инициализаторы** (`@init`) модуля выполняются при каждой загрузке; финализаторы
   — при выгрузке. Побочные эффекты в них должны быть **идемпотентны** (повторный запуск
   даёт тот же результат, что и одиночный: «зарегистрировать, если ещё не зарегистрирован»,
   а не «добавить ещё одну регистрацию»).

Отсюда общее правило: **в постоянной памяти — только «простые данные» (POD)**: числа,
массивы, индексы, хендлы, смещения. Никаких указателей в код или в константы модуля.

> **Коротко:** указатели на функции, интерфейсы, строковые литералы, глобалы модуля и
> память его временного аллокатора умирают при выгрузке. В постоянной памяти — только POD.

### 3.2. Указатели на функции → идентификаторы

Пошаговая хронология бага:

| время | событие | `entity.think` | что произойдёт при вызове |
|---|---|---|---|
| 1 | загружен v1 по адресу 0x7f10_0000 | 0x7f10_1230 (v1_chase) | v1_chase |
| 2 | v1 выгружен, v2 загружен по 0x7f55_0000 | всё ещё 0x7f10_1230 | **падение**: там ничего нет |
| 3 | (ещё хуже) ОС положила по 0x7f10_… другую библиотеку | 0x7f10_1230 | выполнится чужой код |

С идентификатором:

```c3
enum Behavior : char { IDLE, WANDER, CHASE }

struct Entity
{
    int x;
    Behavior behavior;     // ДАННЫЕ: «что делать», а не «где лежит код»
}

// у каждого модуля — своя таблица: Behavior -> функция ЭТОЙ сборки
// каждый кадр: table_of_current_module[e.behavior](e)
```

`behavior = CHASE` — это просто число 2. Оно одинаково осмысленно и для v1, и для v2:
каждый модуль сам знает, где у него лежит функция «преследовать». Сущность хранит «что»,
модуль отвечает «как».

Аналогия: в записной книжке хранить не «квартира 15 в доме, который снесли», а «Вася»;
где сейчас живёт Вася — спросим в справочной (таблице текущего модуля).

> **Частые ошибки**
> * Исправить только `update`, но оставить сохранение указателя в `spawn` — поле с
>   указателем продолжит существовать и может быть использовано где-то ещё.
> * Закэшировать адрес «для скорости» на всю игру — тот же баг, только позже.

> **Коротко:** храните enum/индекс поведения и каждый кадр ищите функцию в таблице
> **текущего** модуля.

### 3.3. Изменилась раскладка: версия и миграция

**Раскладка** (layout) структуры — по каким смещениям (в байтах от начала) лежат её поля.
Компилятор решает это по объявлению структуры. Добавили поле — смещения сдвинулись. Но байты
в памяти хоста записаны **по старой** раскладке!

Проверим (программа целиком):

```c3
import std::io;

struct PlayerV1 { int hp; int gold; }              // старая раскладка: 8 байт
struct PlayerV2 { int hp; int mana; int gold; }    // новая: поле вставлено в середину

fn void main()
{
    char[64] memory @align(16);                    // «постоянная память хоста»

    // Старый модуль записал игрока
    PlayerV1* p1 = (PlayerV1*)&memory;
    *p1 = { .hp = 80, .gold = 500 };

    // Новый модуль после перезагрузки читает ТЕ ЖЕ байты по новой раскладке
    PlayerV2* p2 = (PlayerV2*)&memory;
    io::printfn("v2 видит: hp=%d mana=%d gold=%d", p2.hp, p2.mana, p2.gold);
    io::printfn("size v1=%d v2=%d", PlayerV1::size, PlayerV2::size);
}
```

Вывод:

```
v2 видит: hp=80 mana=500 gold=0
size v1=8 v2=12
```

Что произошло — по байтам:

| смещение | 0..3 | 4..7 | 8..11 |
|---|---|---|---|
| записал v1 | hp = 80 | gold = 500 | (не трогал, 0) |
| читает v2 как | hp | **mana** | **gold** |
| v2 видит | 80 | 500 | 0 |

Золото игрока превратилось в ману, а золото обнулилось. Никакой ошибки, никакого падения —
просто тихо перепутанные данные. Это самая коварная поломка горячей перезагрузки.

**Защита — заголовок состояния.** В самом начале постоянной памяти лежит
`{magic, version, size}` — как у таблицы API, только для данных. Новый модуль при `on_load`
смотрит на заголовок:

```
нет magic           -> память чистая: создать состояние новой версии с нуля
version == старая   -> МИГРАЦИЯ: перенести поля в новую раскладку, новым — значения по умолчанию
version == текущая  -> ничего не делать (повторная перезагрузка той же версии)
```

**Миграция** — перенос данных из старой раскладки в новую поле за полем: `hp → hp`,
`gold → gold`, `mana` = значение по умолчанию.

**Почему через временный буфер.** Новая структура больше старой и лежит **в той же памяти**.
Попробуем мигрировать массив из трёх игроков «на месте» (V1 — 8 байт, V2 — 12 байт):

| игрок | v1 занимает байты | v2 будет занимать |
|---|---|---|
| 0 | 0..7 | 0..11 |
| 1 | 8..15 | 12..23 |
| 2 | 16..23 | 24..35 |

Записали нового игрока 0 в байты 0..11 — и затёрли байты 8..11, где лежало `hp` **старого
игрока 1**, которого мы ещё не прочитали. Дальше ошибка только множится. Поэтому: сначала
собрать новое состояние целиком во **временной** структуре (на стеке или в отдельном
буфере), читая из старых, нетронутых байт, и только потом скопировать результат поверх.

Аналогия: переставлять книги на полке, когда новые обложки толще, — нельзя ставить первую
книгу на место, не сняв сначала соседнюю. Проще снять всё на стол, разложить и поставить
заново.

Варианты защиты от изменения раскладки (от простого к сложному):

1. **Перезапуск** игры при изменении раскладки (Handmade Hero: проще всего, и честно —
   горячая перезагрузка нужна для **логики**, а структуры меняются реже).
2. **Заголовок + ручная миграция** (то, что делает `e1703`) — то же версионирование, что в
   главе 13.
3. **Рефлексия**: модуль описывает раскладку (имя, тип, смещение каждого поля), и миграция
   делается автоматически по **именам** полей.

> **Частые ошибки**
> * Мигрировать на месте — затираются ещё не прочитанные данные.
> * Забыть обновить заголовок (version/size) после миграции — следующая перезагрузка
>   мигрирует ещё раз.
> * Мигрировать при version == текущей — счётчик миграций растёт без причины.
> * Не обработать «чистую память» (magic не совпал) отдельно.

> **Коротко:** в начале состояния — заголовок с версией; новая версия мигрирует старые
> данные поле за полем через временный буфер.

## 4. Детали, о которые спотыкаются все

### 4.1. Копирование перед загрузкой

Компилятор перезаписывает `libgame.so`, пока хост её использует. На Linux это обычно
«работает» (старый **inode** — запись файловой системы о самом файле — остаётся живым, пока
файл открыт), но если компилятор пишет файл на месте, загруженный
образ может измениться под ногами. Плюс `dlopen` кэширует библиотеки **по пути**: повторный
`dlopen` того же пути без `dlclose` вернёт старый хендл. На Windows ещё хуже: загруженная DLL
заблокирована, и линкер не сможет её перезаписать вовсе.

Решение: перед загрузкой **копировать** модуль во временный файл с уникальным именем
(`libgame_7.so`) и загружать копию. Исходник остаётся свободным для компилятора.

```
libgame.so  --копия-->  libgame_1.so  --dlopen-->  [в памяти: поколение 1]
(пересобрали)
libgame.so  --копия-->  libgame_2.so  --dlopen-->  [в памяти: поколение 2]; поколение 1 -> close
```

> **Коротко:** грузите не сам файл, а его копию с уникальным именем — две причины: файл
> свободен для компилятора, и `dlopen` не вернёт закэшированную старую версию.

### 4.2. Недописанный файл

Проверка по времени модификации может сработать, когда компилятор записал файл наполовину.
Варианты: компилятор сначала пишет во временный файл и делает **атомарный `rename`**
(переименование, которое происходит «мгновенно и целиком» — другие процессы видят либо
старый файл, либо новый, но никогда половину; многие системы сборки так и делают), либо
сборочный скрипт после успешной сборки создаёт
файл-маркер `lock.tmp`/`build.done`, и хост перезагружает только по нему (Handmade Hero:
хост ждёт, пока исчезнет `lock.tmp`).

> **Коротко:** не загружайте файл, который, возможно, ещё пишется; ждите сигнала «сборка
> закончена».

### 4.3. PDB на Windows

Visual Studio держит открытым `.pdb` (файл отладочной информации) загруженной DLL, и
следующая сборка не может его перезаписать. Классический трюк: линковать с уникальным
именем PDB на каждую сборку (`/PDB:game_%random%.pdb`). Это деталь, но из-за неё горячая
перезагрузка на Windows у многих «не работает».

### 4.4. Отладчик

Точки останова в перезагруженном модуле отладчики поддерживают с разным успехом. Это нормально:
горячая перезагрузка — инструмент для итерации над логикой, а не замена отладчика.

## 5. Масштабирование: реестр API и плагины

### 5.1. Идея реестра

Один модуль «вся игра» — хорошо для маленького проекта. Большой движок состоит из десятков
подсистем, и хочется перезагружать каждую отдельно, а также подключать сторонние расширения
(**плагины** — модули, которые добавляют движку возможности и подключаются без его
пересборки: плагины редактора, инструменты). Our Machinery (движок авторов
Bitsquid/Stingray, 2018–2022) построил всю архитектуру вокруг **реестра API**:

```
            +------------------------- API REGISTRY ------------------------+
            |  "tm_log_api"     v1.2   [ write | count | ... ]  implemented |
            |  "tm_render_api"  v3.0   [ ...                 ]  implemented |
            |  "tm_physics_api" v1.0   [ 0     | 0     | ... ]  (ещё нет)   |
            +-----^--------------------------^-----------------^------------+
                  | set() копирует таблицу   | get() -> указатель на СЛОТ
                  |                          |
           plugin_log.so               plugin_ui.so  (держит LogApi* навсегда)
```

**Реестр** — общий «справочник» внутри хоста: имя API → **слот** (кусок памяти реестра, где
лежит копия таблицы функций этого API).

Аналогия: доска объявлений в офисе с подписанными ячейками. Отдел логов повесил в ячейку
«log» листок со своими телефонами. Все, кому нужен лог, смотрят **в ячейку**, а не
переписывают телефоны себе. Отдел переехал (плагин перезагрузился) — повесил в ту же ячейку
новый листок, и все автоматически звонят по новым номерам.

* **Всё — плагины**, даже ядро. Каждый плагин экспортирует одну функцию
  `tm_load_plugin(registry, load: bool)`, в которой регистрирует свои API и получает чужие.
* `get(name, version)` возвращает указатель **на слот внутри реестра**. `set()` копирует таблицу
  функций в слот. Перезагрузили плагин — он снова вызвал `set()`, и все, кто давно держит
  указатель на слот, автоматически вызывают новый код. Не нужно рассылать уведомления.
* **Позднее связывание**: `get()` до `set()` создаёт пустой слот. Порядок загрузки плагинов
  перестаёт иметь значение для связывания (но не для инициализации — см. ниже).
* **Семантическое версионирование** API: мажорная версия ломает совместимость, минорная
  добавляет функции только в конец структуры.
* **Интерфейсы** (в терминах OM — `add_implementation`): несколько плагинов могут реализовать
  один интерфейс (например, «импортёр ассетов»), и реестр хранит их список.

Ещё одна деталь: реестр **копирует имя** API в свой буфер. Строковый литерал `"log"`, который
передал плагин, живёт внутри `.so` плагина (раздел 3.1, пункт 3) и исчезнет при его выгрузке.

> **Коротко:** реестр хранит копии таблиц в слотах; клиенты держат указатель на слот; при
> перезагрузке плагин перезаписывает слот — и все сразу видят новый код.

### 5.2. Пошаговая хронология реестра

| шаг | вызов | слот "log": implemented | слот "log": содержимое | у физики в руках |
|---|---|---|---|---|
| 1 | физика: `get("log", 1)` | нет (слот создан пустым) | все функции null | `log` → слот |
| 2 | логгер v1: `set("log", 1, 0, &api_v1)` | да | копия api_v1 | тот же `log` |
| 3 | физика: `log.write("hit")` | да | → функция v1 | |
| 4 | логгер выгружается: `remove("log")` | нет | обнулено | тот же `log` |
| 5 | логгер v2: `set("log", 1, 1, &api_v2)` | да | копия api_v2 | тот же `log` |
| 6 | физика: `log.write("hit")` | да | → функция v2 | |
| 7 | кто-то: `get("log", 2)` | — | — | **null**: мажорная 2 ≠ 1 |

Шаг 4 важен: слот **не удаляется** (на него держат указатели!), а **обнуляется** — чтобы
никто не вызвал код выгруженного плагина. Клиенты должны проверять, что функция не null
(или что API `implemented`) перед вызовом.

**Мажорная и минорная версии.** Версия «1.2» = мажорная 1, минорная 2. Минорная растёт, когда
в **конец** таблицы добавили функцию: старые клиенты про неё не знают и не трогают —
совместимо. Мажорная растёт, когда что-то поменяли или удалили: старые клиенты сломаются,
поэтому `get` с другой мажорной возвращает null.

```
LogApi v1.0: [ write | count ]
LogApi v1.1: [ write | count | flush ]     <- добавлено в КОНЕЦ: клиенты v1.0 работают
LogApi v2.0: [ count | write ]             <- поменяли порядок: клиент v1 вызовет count вместо write!
```

В упражнении `e1704_api_registry` вы реализуете такой реестр.

> **Частые ошибки**
> * Хранить в слоте указатель на таблицу внутри плагина вместо её **копии**.
> * Хранить имя как `String`, указывающую в память плагина, а не копию.
> * В `remove` удалять слот (сдвигать массив) — указатели клиентов поедут.
> * В `get` при отсутствии слота возвращать null вместо создания пустого слота.

> **Коротко:** get = «дай указатель на слот (создай, если нет)»; set = «скопируй таблицу в
> слот»; remove = «обнули слот, но не удаляй».

### 5.3. Зависимости и порядок загрузки

Даже с поздним связыванием порядок важен для **инициализации**: плагин в `load()` может
сразу вызвать API зависимости (например, UI при загрузке спрашивает у шрифтов размер
символов). Значит, зависимости должны загружаться раньше.

**Граф зависимостей** — плагины и стрелки «A нужен B». **Топологическая сортировка** —
такой порядок, в котором каждый плагин идёт после всех, от кого зависит. Аналогия:
одевание — носки раньше ботинок, рубашка раньше пиджака; порядок «носки, рубашка, ботинки,
пиджак» подходит, «ботинки, носки» — нет.

**Алгоритм Кана** (Kahn):

```
indegree[p] = число зависимостей p          ("сколько ещё ждать")
готовые = все p с indegree 0
пока есть готовые:
    взять готовый с НАИМЕНЬШИМ индексом      <- детерминизм!
    добавить в порядок; для всех q, зависящих от него: indegree[q]--
                                             (если стало 0 — q теперь готов)
если в порядке меньше плагинов, чем всего — есть цикл
```

Пошаговый пример (свой, не из упражнения): 0 editor → {ui, scene}, 1 scene → {core},
2 ui → {core, text}, 3 text → {core}, 4 core → {}.

| шаг | indegree [editor, scene, ui, text, core] | готовые | берём | порядок |
|---|---|---|---|---|
| старт | [2, 1, 2, 1, 0] | {core} | core | core |
| 1 | [2, 0, 1, 0, –] | {scene, text} | scene (индекс 1 < 3) | core, scene |
| 2 | [1, –, 1, 0, –] | {text} | text | core, scene, text |
| 3 | [1, –, 0, –, –] | {ui} | ui | …, ui |
| 4 | [0, –, –, –, –] | {editor} | editor | core, scene, text, ui, editor |

После взятия core уменьшились indegree у всех, кто от него зависит: scene (1→0), ui (2→1),
text (1→0). И так далее.

**Цикл**: a → b, b → a. Оба имеют indegree 1, готовых нет с самого начала, порядок пуст —
0 < 2 плагинов, значит цикл. **Отсутствующая зависимость** (плагин ссылается на имя, которого
нет) — тоже ошибка конфигурации. Об обеих надо сообщить **до** загрузки чего-либо.

Почему «наименьший индекс»: из нескольких готовых можно взять любой — сортировка всё равно
будет корректной. Но если выбор зависит от порядка файлов в каталоге или от хеш-таблицы,
порядок будет разным на разных машинах, и баги инициализации станут «плавающими».

**Выгрузка — строго в обратном порядке**: editor, ui, text, scene, core. Как `defer`: никто
не должен пережить то, от чего зависит.

**Перезагрузка одного плагина.** Перезагружаем `text`. От него зависит `ui`, а от `ui` —
`editor` (транзитивно, «через одного»). Их тоже придётся выгрузить и загрузить заново.
Множество «все, кто прямо или косвенно зависит от X, включая X» — **замыкание** зависимых.
Считаем «повторять, пока множество растёт»:

| проход | проверяем каждого: зависит ли от кого-то из множества? | множество |
|---|---|---|
| старт | — | {text} |
| 1 | editor: от ui/scene — нет (пока); scene: нет; ui: от text — **да** | {text, ui} |
| 2 | editor: от ui — **да** | {text, ui, editor} |
| 3 | никто не добавился → стоп | {text, ui, editor} |

Последовательность перезагрузки: выгрузить editor, ui, text (обратный порядок загрузки) →
загрузить text, ui, editor (прямой порядок).

В упражнении `e1705_plugin_manager` вы реализуете менеджер плагинов с топологической
сортировкой зависимостей. Важная деталь: порядок
загрузки должен быть **детерминированным** (сортировка по стабильному ключу, а не по порядку
файлов в каталоге или хеш-таблице), а выгрузка — строго в обратном порядке.

> **Частые ошибки**
> * Брать «первый попавшийся» готовый плагин, а не с наименьшим индексом.
> * Забыть проверку «в порядке меньше, чем всего» — цикл молча даёт неполный порядок.
> * В замыкании сделать один проход вместо «пока растёт» — потеряются транзитивные зависимые.

> **Коротко:** загрузка — в топологическом порядке (Кан, детерминированно), выгрузка — в
> обратном; перезагрузка плагина тянет за собой всех его (транзитивно) зависимых.

## 6. Как это делают в индустрии

* **Handmade Hero** — эталонный учебный пример: хост + `game.dll`, вся память — один блок,
  запись/воспроизведение ввода. Смотрите эпизоды 21–25 и обсуждение «Loop editing».
* **Our Machinery** — реестр API, всё как плагины, перезагрузка любого плагина. Блог Our
  Machinery (статьи «The API registry», «Plugins», «Hot reloading») — лучшее чтение по теме.
* **Unreal Engine Live Coding** (на базе технологии Live++) — патчит функции **внутри
  работающего процесса**: перекомпилирует изменённые единицы трансляции, загружает их и
  переписывает начало старых функций переходом на новые. Позволяет менять код без особой
  дисциплины, но не умеет менять раскладку объектов.
* **Live++** (Molecular Matters) — коммерческий инструмент того же типа для C/C++,
  используется во многих AAA-студиях.
* **Godot / Unity** — горячая перезагрузка уровня скриптового языка (GDScript, C# domain
  reload): та же проблема сохранения состояния, решаемая сериализацией объектов перед
  перезагрузкой и восстановлением после — то есть через рефлексию (глава 13).
* **cr.h** (fungos) — однофайловая C-библиотека горячей перезагрузки с откатом при падении
  нового кода (ловит сигнал и возвращается к предыдущей версии). Полезно почитать исходники.

Разница подходов Handmade Hero и Live++ в одной фразе: Handmade Hero **меняет, куда
смотрит хост** (новая таблица функций), а Live++ **переписывает сами старые функции** —
вставляет в их начало «прыжок» на новую версию, поэтому даже старые указатели продолжают
работать.

## 7. Альтернативы горячей перезагрузке кода

Не всегда стоит строить нативную горячую перезагрузку. Варианты:

* **Скрипты** (глава 14): перезагрузка проще, но два языка, граница вызовов, производительность.
* **Данные вместо кода**: настраиваемые параметры, кривые, графы поведения — перезагружаются
  как ассеты (глава 07), и программист вообще не нужен.
* **Быстрый перезапуск + сериализация состояния**: если игра стартует за секунду и умеет
  сохранять/загружать состояние, можно автоматически перезапускать процесс. Самый надёжный
  вариант, не требует никакой дисциплины кода.
* **Tweak-переменные**: значения в исходнике, помеченные макросом, читаются из файла во время
  работы (трюк из блога Джонатана Блоу / Mollyrocket).

Выбор — инженерный: горячая перезагрузка нативного кода окупается в проектах, где геймплейный
код пишут на том же языке, что движок, и итерации над ним постоянные.

## 8. Проект: настоящая горячая перезагрузка на C3

Этот рецепт проверен на c3c 0.8.5 под Linux. Создайте каталог **вне** курса, например
`~/hotreload/`, и три файла.

**api.c3** — общий договор хоста и модуля (этот файл компилируется **и** в хост, **и** в
модуль — так они договариваются о типах):

```c3
module game_api;

const uint GAME_API_VERSION = 1;

struct GameState
{
    uint version;
    int frame;
    int score;
}

struct GameMemory
{
    void* storage;
    usz size;
    bool initialized;
}

alias GameUpdateFn = fn void(GameMemory*, int);
```

**game.c3** — перезагружаемый модуль:

```c3
module game;
import game_api, std::io;

fn void game_update(GameMemory* mem, int frame) @export("game_update")
{
    GameState* s = (GameState*)mem.storage;
    if (!mem.initialized)
    {
        *s = { .version = game_api::GAME_API_VERSION };
        mem.initialized = true;
    }
    s.frame = frame;
    s.score += 1;   // поменяйте на += 100, пересоберите — и смотрите
    io::printfn("frame %d score %d", s.frame, s.score);
}
```

(Обратите внимание: константу из другого модуля нужно писать с префиксом —
`game_api::GAME_API_VERSION`, иначе компилятор выдаст ошибку.)

Что здесь важно: у модуля **нет глобальных переменных** — всё состояние он получает через
`mem.storage` (память хоста) и интерпретирует как `GameState`. `@export("game_update")`
кладёт функцию в таблицу символов под этим именем, чтобы хост нашёл её через `dlsym`.

**host.c3** — хост:

```c3
module host;
import game_api, std::io, std::os, std::thread, std::io::file, std::time;

struct GameCode
{
    DylibHandle lib;
    GameUpdateFn update;
    Time stamp;
    int generation;
}

fn bool GameCode.load(&self)
{
    Time? t = file::last_modified("libgame.so");
    if (catch t) return false;
    // копия: компилятор может перезаписывать libgame.so, пока мы держим копию,
    // а уникальное имя обходит кэш dlopen по пути
    char[]? data = file::load(mem, "libgame.so");
    if (catch data) return false;
    defer free(data);
    String name = string::tformat("./libgame_%d.so", self.generation);
    if (catch file::save(name, data)) return false;
    DylibHandle lib = os::dlopen(name.zstr_tcopy(), { .resolve_now = true });
    (void)file::delete(name);          // на Linux файл можно удалить сразу после dlopen
    if (!lib) return false;
    void* sym = os::dlsym(lib, "game_update");
    if (!sym) { lib.close(); return false; }   // плохой модуль — остаёмся на старом
    if (self.lib) self.lib.close();
    self.lib = lib;
    self.update = (GameUpdateFn)sym;
    self.stamp = t;
    self.generation++;
    return true;
}

fn void main()
{
    GameMemory gm = { .storage = mem::calloc(1 << 20), .size = 1 << 20 };
    GameCode code;
    if (!code.load()) { io::printn("initial load failed"); return; }
    for (int frame = 0; frame < 40; frame++)
    {
        Time? t = file::last_modified("libgame.so");
        if (try t && t != code.stamp)
        {
            if (code.load()) io::printfn("-- reloaded (generation %d)", code.generation);
        }
        code.update(&gm, frame);
        thread::sleep_ms(100);
    }
    code.lib.close();
}
```

Как работает `GameCode.load` по шагам:

1. Узнать время изменения `libgame.so` (запомним его, чтобы потом понять, что файл обновился).
2. Прочитать файл целиком в память и сохранить копию под уникальным именем
   `libgame_<поколение>.so` (раздел 4.1).
3. `dlopen` копии. На Linux файл можно сразу удалить: загруженный образ остаётся в памяти,
   пока библиотека открыта (тот самый inode).
4. Найти `game_update`. Не нашли — закрыть **новую** библиотеку и вернуть false: старая
   продолжает работать.
5. Только теперь закрыть **старую** и переключиться на новую.

`main` выделяет 1 МБ постоянной памяти (`calloc` — заполненной нулями), каждый кадр
проверяет время файла и, если оно изменилось, перезагружает модуль, а затем вызывает
`update`.

Шаги:

```
$ c3c dynamic-lib -o libgame game.c3 api.c3      # -> libgame.so
$ c3c compile -o host host.c3 api.c3
$ ./host &                                        # печатает frame N score N
$ # через секунду поменяйте в game.c3 "+= 1" на "+= 100" и пересоберите:
$ c3c dynamic-lib -o libgame game.c3 api.c3
```

Реальный вывод при проверке:

```
frame 17 score 18
frame 18 score 19
-- reloaded (generation 2)
frame 19 score 119
frame 20 score 219
```

Счёт продолжился с 19 — состояние пережило замену кода. Что улучшить дальше (это и есть
путь от игрушки к инструменту):

1. Экспортировать не `game_update`, а `get_game_api()`, возвращающую таблицу с
   magic/version/size, как в `e1701`.
2. `file::last_modified` имеет секундную точность: две сборки в одну секунду не заметить.
   Сравнивайте ещё и размер или хеш файла, либо используйте файл-маркер от сборочного скрипта.
3. Защита от недописанного файла: ждите, пока размер/время не перестанут меняться пару
   опросов подряд, или маркер `build.done`.
4. Запись/воспроизведение ввода и «петля» по фрагменту геймплея (Handmade Hero).
5. Вызовы `on_unload/on_load`, барьер для job system перед выгрузкой.
6. На macOS имя будет `libgame.dylib`, на Windows — `game.dll` (+ трюк с PDB).

> **Коротко:** рабочая горячая перезагрузка — это ~60 строк: копия файла, `dlopen`, `dlsym`,
> переключение только после успеха, состояние в памяти хоста.

## 9. Подводные камни (чек-лист)

* Вызов кода модуля без проверки версии/размера таблицы.
* Указатели на функции, интерфейсы, строковые литералы модуля в постоянной памяти.
* Глобальное состояние в модуле.
* Изменение раскладки состояния без версии и миграции; миграция «на месте», когда новая
  структура больше старой и перекрывается с ней (нужен временный буфер).
* `dlopen` того же пути без копирования; блокировки файлов на Windows.
* Перезагрузка, пока другие потоки исполняют код модуля.
* Память, выделенная временным аллокатором модуля и пережившая кадр.
* Падение при неудачной перезагрузке вместо отката к старому модулю.
* Недетерминированный порядок загрузки плагинов; выгрузка не в обратном порядке.

## Словарик

* **ABI** — двоичный договор: как передаются аргументы, как разложены структуры, размеры
  типов.
* **Адрес** — номер байта в памяти процесса, где лежит функция или данные.
* **Алгоритм Кана** — топологическая сортировка через счётчики «сколько зависимостей ещё
  не загружено».
* **Барьер** — точка, где все потоки дожидаются друг друга.
* **Висячий указатель** — указатель на память, которой больше нет.
* **Горячая перезагрузка (hot reload)** — замена кода работающей программы без потери
  состояния.
* **Динамическая библиотека** (`.so`/`.dylib`/`.dll`) — код, загружаемый во время работы.
* **Замыкание зависимых** — плагин и все, кто зависит от него прямо или через других.
* **Идемпотентность** — повторное выполнение даёт тот же результат, что однократное.
* **Интернирование строк** — хранение одной копии каждой строки в общем пуле.
* **Магическое число (magic)** — константа в начале структуры/файла для проверки «это наш
  формат».
* **Миграция** — перенос данных из старой раскладки в новую.
* **Модуль** — перезагружаемая библиотека с игровой логикой.
* **Образ модуля** — код и константы библиотеки, размещённые в памяти.
* **Плагин** — модуль, расширяющий движок без его пересборки.
* **Позднее связывание** — можно получить ссылку на API до того, как его реализация
  загрузилась.
* **Раскладка (layout)** — смещения полей структуры в байтах.
* **Реестр API** — справочник «имя → слот с таблицей функций».
* **Символ** — экспортированное имя функции/переменной в библиотеке.
* **Слот** — ячейка реестра с копией таблицы функций; её адрес не меняется.
* **Таблица функций** — структура из указателей на функции + magic/version/size.
* **Топологическая сортировка** — порядок, где каждый элемент идёт после своих зависимостей.
* **Хост** — исполняемый файл, владеющий памятью и циклом; не перезагружается.
* **Мажорная / минорная версия** — «ломает совместимость» / «только добавляет в конец».
* **POD** — простые данные без указателей на код и чужую память.
* **`.rodata`** — участок образа с константами (строковые литералы и т. п.).
* **vtable** — таблица адресов методов, на которую указывает объект с виртуальными методами.
* **`dlopen` / `dlsym` / `dlclose`** — загрузить библиотеку / найти символ / выгрузить.
