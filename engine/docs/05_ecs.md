# 05 · Entity Component System

> Упражнения главы: `e0501_entity_manager`, `e0502_component_pools`, `e0503_queries_systems`,
> `e0504_archetypes`, `e0505_scheduler`.

## Карта главы

**Что вы узнаете.** Как устроить в движке «игровые объекты» — игроков, врагов, пули,
ящики — так, чтобы их было легко комбинировать и быстро обрабатывать тысячами.
Архитектура называется **ECS** (*Entity Component System* — «сущность, компонент,
система»).

ECS — самая обсуждаемая архитектура игровых движков последних десяти лет. Unity
переписала ядро ради DOTS, Bevy построен на ECS целиком, Unreal добавил Mass, Overwatch
и множество инди-игр (на EnTT и flecs) работают на ECS. В этой главе разберём, *какую
проблему* он решает, два основных способа его реализации (sparse sets и архетипы), запросы,
системы и их планирование — и когда ECS **не** нужен.

| Раздел | О чём | Нужен для |
|---|---|---|
| 1. Проблема | почему наследование и «компоненты-объекты» не справляются | `e0501` (фон) |
| 2. Сущности | сущность = номер + поколение; переиспользование номеров | `e0501` |
| 3.1 Sparse set | хранение «по пулу на тип компонента» | `e0502` |
| 3.2 Архетипы | хранение «по таблице на набор компонентов» | `e0504` |
| 4. Запросы | «дай всех, у кого есть A и B»; отложенные команды | `e0503` |
| 5. Системы | функции, обрабатывающие запросы | `e0503`, `e0505` |
| 6. Планирование | какие системы можно запускать одновременно | `e0505` |
| 7–10 | производительность, доп. темы, когда ECS не нужен, ошибки | все |

**Что нужно знать заранее.** Глава опирается на главы 02 (аллокаторы) и 03 (handles,
sparse set, swap-remove): ECS — это, по сути, грамотная комбинация этих структур.
Если вы не помните, что такое **handle** (номер объекта + «поколение») и
**swap-remove** (удаление из массива переносом последнего элемента на место удалённого) —
полистайте главу 03, это сэкономит много времени. Из C3 понадобятся `List`, generics
(`ComponentPool{Position}`), макросы с trailing-блоком (`@body`) и битовые операции.

## 1. Проблема: модель игровых объектов

Как представить в коде «игровой объект» — игрока, врага, ящик, триггер, лампу?
**Игровой объект** — любая «вещь» в мире игры, у которой есть какие-то данные
(позиция, здоровье, картинка) и какое-то поведение (двигается, стреляет, светится).

### 1.1 Иерархия наследования

Классический подход 90-х–2000-х — дерево классов, где каждый потомок «расширяет»
родителя:

```
 GameObject
 ├── Actor (позиция, рендер)
 │   ├── Pawn (может управляться)
 │   │   ├── Character (скелет, движение)
 │   │   │   ├── Player
 │   │   │   └── Enemy
 │   │   │       ├── FlyingEnemy
 │   │   │       └── ... SwimmingFlyingEnemy?  <- ромбовидное наследование
 │   └── Prop
 │       └── PhysicsProp  ... ExplodingPhysicsProp?
 └── Trigger
```

Проблемы известны («The Blob» — «капля, которая всё поглощает»; «deadly diamond» —
«смертельный ромб», когда класс наследует одно и то же от двух родителей):

* функциональность, нужная двум далёким веткам, поднимается в общий базовый класс —
  базовый класс раздувается (`GameObject` с 200 полями и виртуальными методами);
* новая комбинация свойств («летающий плавающий враг») требует нового класса;
* дизайнер не может создать новый тип объекта без программиста;
* данные одного объекта лежат вместе, а обрабатываются системами по отдельности: физике
  нужны только позиции и скорости, но она тащит в кэш весь объект.

Аналогия: вы классифицируете животных строгим деревом «птицы / рыбы / звери». Тут
появляется утконос (зверь, но несёт яйца и плавает) — и дерево ломается. В играх
«утконосы» появляются каждую неделю: дизайнер хочет бочку, которая ходит, или дверь,
которой можно нанести урон.

**Про кэш** (это понадобится всю главу): процессор читает память не по байту, а
кусками по 64 байта (**кэш-линиями**). Если нужные данные лежат подряд, одно чтение
приносит сразу много полезного. Если они разбросаны, каждое обращение — **промах
кэша**, ожидание в сотни тактов. Подробно — глава 02.

**Коротко:** дерево наследования плохо выражает «произвольные комбинации свойств» и
плохо ложится на кэш.

### 1.2 Компоненты-объекты

Следующий шаг — **композиция**: объект — контейнер компонентов, каждый компонент — объект
со своими данными *и* поведением (`Update()`). «Летающий плавающий враг» — это объект с
компонентами `Flying`, `Swimming`, `Enemy`; новый класс не нужен. Так устроены Unity
GameObject/MonoBehaviour, Unreal Actor/ActorComponent, Godot (через дерево узлов). Нистром
описывает это как паттерн «Component».

Это решает проблему комбинаций, но не производительности: компоненты — объекты
в куче, каждый со своим виртуальным `Update()`, обход — прыжки по памяти; порядок
обновления компонентов размыт; взаимодействие компонентов — через `GetComponent<T>()`
(поиск) и указатели друг на друга.

```
 память (куча):   [Enemy#1 ...]  ...  [Mover#7 ...]  ...  [Enemy#2 ...] ... [Mover#3 ...]
                      ^                    ^                   ^                ^
 обновление кадра:  прыжок             прыжок               прыжок           прыжок
```

**Коротко:** композиция решает «комбинации», но данные всё ещё разбросаны, а логика
размазана по тысячам маленьких `Update()`.

### 1.3 ECS

ECS делает последний шаг — **разделяет данные и поведение**:

* **Entity** (сущность) — просто идентификатор (число с поколением, см. главу 03).
  Ни данных, ни методов. Как номер паспорта: сам по себе ничего не умеет, но по нему
  находят всё остальное.
* **Component** (компонент) — чистые данные (`struct Position { float x, y; }`), без логики.
* **System** (система) — функция, которая обрабатывает *все* сущности с определённым
  набором компонентов: «для всех, у кого есть Position и Velocity: position += velocity * dt».

```
            Position   Velocity   Health   Sprite   AI
 entity 1      ●          ●         ●        ●
 entity 2      ●                    ●        ●       ●
 entity 3      ●          ●                  ●
 entity 4                           ●

 MovementSystem:  Position & Velocity           -> 1, 3
 RenderSystem:    Position & Sprite             -> 1, 2, 3
 AISystem:        AI & Position                 -> 2
```

Читается таблица так: строка — сущность, столбец — тип компонента, точка — «у этой
сущности есть такой компонент». Система описывает, какие столбцы ей нужны, и
обрабатывает все строки, где эти столбцы заполнены.

Это *реляционная* модель (как в базах данных): сущности — первичные ключи, компоненты —
таблицы, системы — запросы. Если вы знаете SQL, MovementSystem — это примерно
`SELECT * FROM Position JOIN Velocity USING (entity)`. Отсюда сила ECS: данные одного
типа лежат подряд (кэш, SIMD), системы явно объявляют, что читают и пишут
(параллелизм), и любой набор компонентов — допустимый «тип объекта» (данные, а не код,
определяют поведение). Хотите, чтобы ящик начал двигаться? Добавьте ему `Velocity` —
MovementSystem подхватит его сама.

> **Частая ошибка новичка:** класть в компонент методы с логикой («`Health.take_damage()`
> сам проверяет смерть и проигрывает звук»). В ECS логика живёт в системах; компонент —
> «голая» структура данных.

**Коротко:** сущность — номер, компонент — данные, система — функция над всеми
сущностями с нужным набором компонентов.

## 2. Сущности

### 2.1 Сущность — это handle

Сущность — handle из главы 03: индекс + поколение. **Индекс** — номер «ячейки»
(слота) во внутренних таблицах. **Поколение** (generation) — счётчик, сколько раз эта
ячейка была освобождена. Зачем поколение: после уничтожения сущности её индекс
переиспользуется, а у кого-то (например, у ракеты, нацеленной на врага) мог остаться
старый id. Поколение позволяет понять, что «враг #5» из ракеты — уже не тот, что
сейчас живёт в ячейке 5.

Аналогия — номерок в гардеробе: номер 5 выдают снова и снова, но если на номерке
ещё и написано «смена №3», то номерок прошлой смены уже не сработает.

В `e0501` 32 бита делятся так:

```
 Entity (32 бита) = [ generation : 10 бит ][ index : 22 бита ]
                      старшие биты            младшие биты

 make_entity(5, 3) = (3 << 22) | 5 = 12582912 + 5 = 12582917
 entity_index(12582917) = 12582917 & 0x3FFFFF        = 5
 entity_gen(12582917)   = 12582917 >> 22             = 3
```

22 бита индекса — до 4 194 303 одновременно существующих сущностей; 10 бит поколения —
значения 0…1023, после 1023 поколение «переполняется» и снова становится 0.

Менеджер сущностей хранит поколения и свободные индексы и отвечает на вопрос «жива ли
сущность»:

```
 generations: [ 2 ][ 0 ][ 5 ][ 1 ]  ...     поколение каждого индекса сейчас
                 0    1    2    3

 жива ли (index=2, gen=5)?  generations[2] == 5  -> да
 жива ли (index=2, gen=4)?  generations[2] == 5  -> нет, это старый handle
 жива ли (index=9, gen=0)?  индекса 9 ещё нет    -> нет
```

### 2.2 Переиспользование индексов и переполнение поколений

Важные детали:

* сущностей могут быть сотни тысяч, создаются и уничтожаются постоянно (пули,
  частицы-сущности) — переиспользование индексов неизбежно, а с ним и переполнение
  поколений. Bitsquid предлагал не переиспользовать индекс, пока в очереди свободных
  меньше 1024 индексов: так каждый индекс переиспользуется реже;
* id должен быть сериализуемым и стабильным при сохранении/загрузке — или при загрузке
  нужна таблица перевода id;
* в сетевой игре у сущности есть ещё «сетевой id», общий для сервера и клиентов.

Почему политика Bitsquid помогает. Если индекс сразу пускать в работу, одна и та же
ячейка может «прокрутиться» через все 1024 поколения за 1024 удаления — и старый
handle внезапно «оживёт» (его поколение совпадёт снова). Если же свободные индексы
стоят в **FIFO-очереди** (*first in, first out* — «первым пришёл, первым ушёл», как
очередь в магазине) и берутся только когда в очереди больше 1024 штук, то каждый
индекс ждёт, пока до него дойдёт очередь из 1024+ других. Между двумя
переиспользованиями одного индекса проходит минимум 1024 удалений других сущностей,
и поколение растёт медленно.

Мини-трассировка (представим `MIN_FREE = 2` вместо 1024 для краткости):

| действие | очередь свободных | новый id (index, gen) | комментарий |
|---|---|---|---|
| create | `[]` | (0, 0) | очередь пуста — новый индекс |
| create | `[]` | (1, 0) | |
| destroy (0,0) | `[0]` | — | gen[0] = 1, индекс 0 в очередь |
| create | `[0]` | (2, 0) | в очереди 1, это не больше 2 — новый индекс |
| destroy (1,0) | `[0, 1]` | — | gen[1] = 1 |
| destroy (2,0) | `[0, 1, 2]` | — | gen[2] = 1 |
| create | `[1, 2]` | (0, 1) | в очереди 3 > 2 — берём из **головы**: 0 |

Тест `e0501` проверяет то же самое: после удаления сущности `a` с индексом 0 следующая
`create` должна получить **новый** индекс 2, потому что очередь ещё короткая.

**Как устроена очередь в упражнении.** `List.pop_first()` сдвигает весь массив —
это O(n). Поэтому очередь — `List{uint}` плюс индекс головы `free_head`: «взять из
очереди» = прочитать `free_queue[free_head]` и сдвинуть `free_head` на 1. Когда голова
уезжает далеко, готовая функция `compact_queue` переносит хвост в начало.

```
 free_queue: [ 7 | 3 | 9 | 12 | 4 ]
                   ^ free_head = 1      free_count = len - free_head = 4
 взять: x = free_queue[1] = 3;  free_head = 2
```

Упражнение **e0501_entity_manager**.

> **Частые ошибки в e0501.**
> * Проверять «очередь не пуста» вместо «в очереди **больше** `MIN_FREE`».
> * Забыть `& GEN_MASK` при увеличении поколения — поколение «вылезет» за 10 бит и
>   испортит индекс при упаковке.
> * В `alive` не проверить, что индекс вообще существует (`index < generations.len()`).
> * В `destroy` не проверить, что сущность жива: повторный `destroy` должен вернуть
>   `false` и ничего не менять (иначе индекс дважды попадёт в очередь и его выдадут
>   двум сущностям сразу).
> * Индексы `List` в C3 0.8.5 — знаковые `sz`; при сравнении с `uint` нужен каст.

**Коротко:** сущность = индекс + поколение в одном `uint`. Жива — если поколение
совпадает с текущим поколением индекса. Индексы переиспользуются через FIFO-очередь
с задержкой.

## 3. Хранение компонентов: две школы

Где хранить сами компоненты? Есть два популярных ответа. Оба держат компоненты
одного типа в **плотных массивах** (без дырок), чтобы обход был быстрым, но
по-разному группируют их.

### 3.1 Sparse set на тип компонента (EnTT, Specs, ранний Bevy)

**Sparse set** («разреженное множество», глава 03) — структура из двух массивов:
**sparse** («разреженный» — большой, с дырками, индексируется номером сущности) и
**dense** («плотный» — без дырок, по порядку). Каждый тип компонента — свой sparse set:
плотный массив сущностей + параллельный плотный массив компонентов + разреженный
индекс `entity → позиция`.

```
 Position pool:  sparse[entity] -> pos     dense entities: [1][3][2]
                                           dense data:     [p1][p3][p2]
 Velocity pool:                            dense entities: [3][1]
                                           dense data:     [v3][v1]
```

Подробнее на одном пуле (`NONE` — «у этой сущности компонента нет»):

```
 sparse (по индексу сущности):  index:  0     1     2     3     4
                                        NONE  0     2     1     NONE
                                              |     |     |
                                              v     |     v
 entities (плотный):             pos:   0 [e1]  1 [e3]  2 [e2]
 data     (плотный):                    0 [p1]  1 [p3]  2 [p2]
                                                        ^
                                         sparse[2] = 2 -+
```

Два плотных массива `entities` и `data` — **параллельные**: в позиции k лежат
сущность и её компонент. `entities` нужен, чтобы знать, *чей* это компонент (например,
при swap-remove надо исправить `sparse` переехавшей сущности).

**Трассировка операций** (пул Position, сущности пишем как «индекс v поколение»):

| операция | sparse | entities | data | комментарий |
|---|---|---|---|---|
| старт | `[]` | `[]` | `[]` | |
| add(1v1, pA) | `[NONE, 0]` | `[1v1]` | `[pA]` | sparse дорос до индекса 1 |
| add(3v1, pB) | `[NONE, 0, NONE, 1]` | `[1v1, 3v1]` | `[pA, pB]` | |
| add(2v1, pC) | `[NONE, 0, 2, 1]` | `[1v1, 3v1, 2v1]` | `[pA, pB, pC]` | |
| remove(1v1) | `[NONE, NONE, 0, 1]` | `[2v1, 3v1]` | `[pC, pB]` | последний (2v1) переехал в позицию 0, `sparse[2] = 0` |

Последняя строка — **swap-remove**: удалить из середины плотного массива, не оставив
дырку, можно, перенеся на освободившееся место последний элемент. Порядок элементов
меняется — но в ECS он и не обещан. Переставлять надо **оба** параллельных массива и
поправить `sparse` у переехавшей сущности.

Свойства:

* Добавление/удаление компонента — O(1), не трогает другие компоненты сущности.
* Обход одного типа — идеально плотный.
* Запрос по нескольким типам — обход самого маленького пула и проверка `contains` в
  остальных (глава 03). Доступ к компонентам других пулов — случайный (через `sparse`).
  EnTT решает это **группами** (groups): пулы, входящие в группу, переупорядочиваются так,
  что сущности с полным набором компонентов лежат в начале каждого пула в одинаковом
  порядке — обход становится параллельно-плотным.

**Устаревший компонент.** `sparse` индексируется только *индексом* сущности, без
поколения. Представьте: сущность 6v1 умерла, **не** удалив свой Health (так бывает,
если кто-то забыл почистить пулы). Индекс 6 переиспользован — теперь там 6v2. `sparse[6]`
всё ещё указывает на старый компонент! Поэтому `has` обязан сравнить `entities[pos]` с
запрошенной сущностью **целиком** (вместе с поколением): `6v1 ≠ 6v2` → компонента нет.
А при `add` для 6v2 место, занятое устаревшим 6v1, можно просто занять.

Упражнения **e0502_component_pools** и **e0503_queries_systems**.

> **Частые ошибки в e0502.**
> * Индексировать `sparse` полным `Entity` (с поколением в старших битах) вместо
>   `entity_index(e)` — получится индекс в миллионы.
> * Не дорастить `sparse` до нужной длины при `add` (дописывать `NONE`, пока
>   `sparse.len() <= index`) — выход за границы.
> * При swap-remove переставить `data`, но забыть `entities` (или наоборот) — тест
>   «entities[] and data[] out of sync».
> * Забыть случай «удаляется последний элемент»: переставлять нечего, но `sparse`
>   удалённой сущности всё равно надо сбросить в `NONE`.
> * `add` для уже существующего компонента должен перезаписать значение, а не
>   добавить дубликат.

**Коротко:** sparse set — пул на тип: `sparse[индекс] → позиция`, плотные
`entities[]` и `data[]`. Удаление — swap-remove обоих массивов + починка sparse.
Проверка `has` сравнивает сущность целиком, с поколением.

### 3.2 Архетипы (Unity DOTS, Bevy tables, flecs, Unreal Mass)

**Архетип** — уникальный набор типов компонентов. Все сущности с одинаковым набором
лежат в одной таблице, где каждый тип — отдельный столбец (SoA — «структура массивов»,
см. главу 04: все позиции подряд, все скорости подряд):

```
 Архетип {Position, Velocity}           Архетип {Position, Sprite, AI}
 ┌────────┬──────────┬──────────┐       ┌────────┬──────────┬────────┬──────┐
 │ entity │ Position │ Velocity │       │ entity │ Position │ Sprite │  AI  │
 ├────────┼──────────┼──────────┤       ├────────┼──────────┼────────┼──────┤
 │   1    │   p1     │   v1     │       │   2    │   p2     │   s2   │  a2  │
 │   3    │   p3     │   v3     │       │   7    │   p7     │   s7   │  a7  │
 └────────┴──────────┴──────────┘       └────────┴──────────┴────────┴──────┘
 entity -> (архетип, строка)
```

Аналогия: склад, где вещи лежат не «по владельцам», а «по комплектам». Все
посетители, у которых ровно «куртка + шапка», — на одной полке; «куртка + шапка +
зонт» — на другой. Если вам нужны все куртки, вы обходите все полки, где есть куртки, —
и на каждой куртки лежат подряд.

**Набор как битовая маска.** Каждому типу компонента дают номер бита: Position = бит 0,
Velocity = бит 1, Health = бит 2, Frozen = бит 3. Набор — `uint`, где включены биты
присутствующих компонентов:

| набор | маска (двоичная) | десятичная |
|---|---|---|
| {} | `0000` | 0 |
| {Position} | `0001` | 1 |
| {Position, Velocity} | `0011` | 3 |
| {Position, Velocity, Frozen} | `1011` | 11 |

«Содержит ли архетип все компоненты запроса» — `(archetype_mask & query_mask) == query_mask`:
`1011 & 0011 = 0011` — да; `0101 & 0011 = 0001 ≠ 0011` — нет (нет Velocity).

* Запрос «Position & Velocity» находит все архетипы, *содержащие* оба типа (по битовой
  маске сигнатуры), и обходит их столбцы линейно, синхронно — без проверок `contains`.
  Это самый быстрый обход из возможных.
* Число архетипов обычно невелико (десятки–сотни), а набор подходящих архетипов для
  запроса **кэшируется** и обновляется только при появлении нового архетипа.
* Плата — **структурные изменения**: добавить или удалить компонент — значит
  *переместить* сущность (все её компоненты) в другой архетип: копирование строки +
  swap-remove в старой таблице. Для «тегов», которые меняются каждый кадр (`IsStunned`),
  это дорого. Отсюда «enableable components» в Unity (бит включения вместо перемещения)
  и гибридное хранение в Bevy (компонент можно пометить `SparseSet`-хранилищем).
* Unity хранит архетипы **чанками** по 16 КБ: в чанке — столбцы для N сущностей.
  Чанки — единица параллельной работы (job на чанк) и аллокации (пул чанков).

**Тег** — компонент без данных (или почти без): само его *наличие* что-то значит
(«заморожен», «игрок», «враг»).

#### Переезд сущности: пошагово

Сущность `e3` живёт в архетипе {Position} в строке 1. Добавляем ей Velocity.

```
 ДО:
 Архетип A {Pos}                  Архетип B {Pos, Vel}
  row  entity  Pos                 row  entity  Pos   Vel
   0    e1     p1                   0    e8     p8    v8
   1    e3     p3   <- переезжает
   2    e5     p5

 records: e3 -> (A, 1),  e5 -> (A, 2)
```

| шаг | действие | результат |
|---|---|---|
| 1 | новая маска = `{Pos} | {Vel}`; найти/создать архетип | B |
| 2 | `push_row` в B → строка 1; скопировать общие компоненты (только Pos — Vel в A нет) | B: `[e8, e3]`, Pos `[p8, p3]`, Vel `[v8, ??]` |
| 3 | `remove_row(1)` в A: последняя строка (e5) переезжает на место 1 | A: `[e1, e5]`; вернуть e5 |
| 4 | поправить `records[e5] = (A, 1)`; записать `records[e3] = (B, 1)` | |
| — | потом `World.add` записывает значение Vel в ячейку `get_raw(e3, VEL)` | B: Vel `[v8, v3]` |

```
 ПОСЛЕ:
 Архетип A {Pos}                  Архетип B {Pos, Vel}
  row  entity  Pos                 row  entity  Pos   Vel
   0    e1     p1                   0    e8     p8    v8
   1    e5     p5   <- переехала    1    e3     p3    v3
```

Удаление компонента — то же самое, только новая маска «меньше», и копируются
компоненты, которые есть в обоих наборах (тот, что удаляется, просто пропадает).

**Type-erased столбцы.** В `e0504` один `Archetype` должен хранить столбцы разных типов.
Поэтому столбец — это просто `char*` (сырые байты) плюс размер элемента из таблицы
`COMPONENT_SIZE`. «Type-erased» — «со стёртым типом»: код архетипа не знает, что там
`Position`, он видит только «блоки по 8 байт». Адрес ячейки — `columns[c] + row * size`
(функция `Archetype.at`), копирование — `mem::copy(dst, src, size)`. Тип
«вспоминается» только снаружи — в системе, которая пишет
`(Position*)a.columns[POS]`.

Упражнение **e0504_archetypes** — архетипная ECS с type-erased столбцами.

> **Частые ошибки в e0504.**
> * В `remove_row` скопировать последнюю строку только в одном столбце — надо во
>   **всех** столбцах, которые есть в маске архетипа (проверка `mask & bit(c)`), и в
>   `entities`.
> * Копировать компоненты, которых нет в новом архетипе (у него для них нет столбца —
>   `columns[c] == null`). Копируются только биты из `old_mask & new_mask`.
> * Забыть поправить `record.row` у сущности, переехавшей при swap-remove.
> * Брать указатель на ячейку **до** `push_row` в новом архетипе: `push_row` может
>   сделать `realloc`, и старые указатели на этот архетип станут недействительными.
>   Сначала добавьте строку, потом вычисляйте адреса.
> * Порядок шагов: если сначала удалить строку из старого архетипа, данные
>   переезжающей сущности будут затёрты раньше, чем скопированы.

**Коротко:** архетип — таблица для одного набора компонентов (маска битов), столбец на
компонент. Обход — линейный. Добавить/удалить компонент = переселить сущность в другую
таблицу.

### 3.3 Сравнение

| | Sparse set | Архетипы |
|---|---|---|
| Добавить/удалить компонент | O(1), дёшево | перемещение всех компонентов сущности |
| Обход одного компонента | идеальный | идеальный (по архетипам) |
| Обход N компонентов | перебор меньшего + случайный доступ (или группы) | идеальный, линейный |
| Память | sparse-массивы на тип (пагинация) | таблицы + граф переходов |
| Сложность реализации | низкая | выше |
| Примеры | EnTT, Specs, Shipyard | Unity DOTS, Bevy, flecs, Unreal Mass, Our Machinery |

(**Пагинация** — sparse-массив делят на страницы и выделяют только те, где есть
сущности, чтобы не держать гигантский массив с дырками. **Граф переходов** — кэш
«из архетипа X при добавлении компонента C переходим в архетип Y», чтобы не искать
архетип каждый раз.)

Нет универсального победителя: игры с частыми структурными изменениями выигрывают от
sparse sets, игры с массовыми однородными симуляциями — от архетипов. Bevy и flecs
поддерживают оба вида хранения.

**Коротко:** sparse set — дешёвые добавления/удаления, архетипы — самый быстрый обход
нескольких компонентов.

## 4. Запросы и итерация

### 4.1 Что такое запрос

**Запрос** (query/view) — описание «какие компоненты нужны и с каким доступом». Вот как
это выглядит в разных библиотеках:

```
 Query<(&mut Position, &Velocity), Without<Frozen>>     // Bevy
 registry.view<Position, const Velocity>(entt::exclude<Frozen>)   // EnTT
 ecs_query(world, { .terms = {{ Position }, { Velocity, .inout = EcsIn }} })  // flecs
```

Все три строки говорят одно и то же: «дай мне все сущности, у которых есть Position
(буду менять) и Velocity (только читаю), но нет Frozen».

### 4.2 Запрос в sparse-set ECS: обходим меньший пул

Пусть Position есть у 240 сущностей, Velocity — у 40. Нужны сущности с обоими.
Вариант 1: пройти 240 позиций и для каждой спросить «есть ли Velocity?» — 240
проверок. Вариант 2: пройти 40 скоростей и для каждой спросить «есть ли Position?» —
40 проверок. Результат одинаковый (пересечение множеств не зависит от того, с какой
стороны начинать), а работы в 6 раз меньше. Поэтому всегда обходят **меньший** пул.
В `e0503` это проверяется счётчиком `view_visits`: 200 декораций + 40 ходоков в
`pos`, 40 в `vel` → должно быть ровно 40 посещений.

```
 pos (240):  [e0 e1 ... e39  d0 d1 ... d199]
 vel  (40):  [e0 e1 ... e39]          <- обходим этот
                  |
                  +-- для каждого: pos.get(e) -> указатель или null
```

Для «своего» пула компонент берётся напрямую по позиции k (`data.get_ref(k)`), для
другого — через `get(e)` (поиск через sparse).

### 4.3 Как такой запрос выглядит в C3: макрос с trailing-блоком

В `e0503` запрос — **макрос с trailing-блоком**: тело цикла пишется *после* вызова
в фигурных скобках, а макрос сам решает, когда и с какими аргументами его вызвать.
Вот самостоятельный пример (не решение упражнения — просто демонстрация механизма):

```c3
import std::io, std::collections::list;

// Макрос принимает список и «тело» @body с двумя параметрами.
macro @each_even(list; @body(sz i, x))
{
    for (sz i = 0; i < list.len(); i++)
    {
        if (list[i] % 2 == 0) @body(i, list[i]);   // вызвать тело для чётных
    }
}

fn void main()
{
    List{int} xs;
    defer xs.free();
    xs.push(3); xs.push(4); xs.push(10); xs.push(7);
    int sum = 0;
    @each_even(xs; sz i, int x)       // после `;` — имена параметров тела
    {
        io::printfn("  [%d] = %d", i, x);
        sum += x;                     // тело видит локальные переменные main
    };                                // точка с запятой после блока обязательна
    io::printfn("sum of even = %d", sum);   // 14
}
```

Что происходит. При компиляции макрос «разворачивается» на месте вызова: цикл `for`
из макроса оказывается прямо в `main`, а там, где написано `@body(i, list[i])`,
подставляется блок `{ io::printfn(...); sum += x; }` с `i` и `x`, привязанными к
переданным значениям. Поэтому тело видит `sum` — это всё тот же `main`. Вывод:
`[1] = 4`, `[2] = 10`, `sum of even = 14`.

Два ограничения, о которых предупреждает упражнение: внутри тела такого блока нельзя
писать `continue` (используйте `if`), а `return` в теле вернёт из *объемлющей
функции*, а не «из итерации».

### 4.4 Важное в реализации запросов

* **Фильтры**: `With`, `Without`, `Optional`, `Changed`. Без фильтров ECS быстро
  превращается в «проверю флаг в каждом компоненте». (`With<T>` — «должен быть T, но
  его данные не нужны», `Without<T>` — «не должно быть T», `Optional<T>` — «дай, если
  есть», `Changed<T>` — «только если T изменился».)
* **Доступ**: read-only или read-write. Нужен для планирования (раздел 6) и для
  change detection.
* **Change detection** («обнаружение изменений»): «обработать только позиции,
  изменившиеся с прошлого запуска системы». Bevy хранит у каждого компонента тик
  последнего изменения; Unity — версию на чанк (грубо, но дёшево).
* **Структурные изменения во время итерации** запрещены или откладываются: удалить
  сущность посреди обхода — значит swap-remove в таблице, которую мы обходим. Решение —
  **command buffer**: система записывает «уничтожить e17», «добавить Burning к e3», а
  применяются команды в точке синхронизации после системы (Unity
  `EntityCommandBuffer`, Bevy `Commands`, flecs deferred mode).

### 4.5 Почему нельзя удалять во время обхода: пример

Обходим пул `health` по позициям 0, 1, 2, 3 и на позиции 1 решаем удалить сущность:

```
 до:      pos: 0    1    2    3
               [eA] [eB] [eC] [eD]        обходим k = 0, 1, ...
 k = 1: удаляем eB (swap-remove): последний eD встаёт на место 1
 после:        [eA] [eD] [eC]
 k = 2: обрабатываем eC.  А eD? Она переехала на позицию 1, которую мы уже прошли —
        eD ПРОПУЩЕНА в этом кадре. А если бы мы удаляли с конца, могли бы выйти за границу.
```

С **command buffer** («буфер команд») система только *записывает намерение*:

```
 во время системы:   commands = [ DESTROY eB, SPAWN_SPARK at (52, 3) ]
 после системы:      flush(): по порядку выполнить, затем очистить commands
```

Аналогия: официант не бежит на кухню после каждого слова гостя, а записывает весь
заказ в блокнот и отдаёт его после. Порядок команд сохраняется — `flush` применяет их
в том порядке, в котором они записаны.

**Двойное уничтожение.** Одна сущность может попасть в буфер дважды за кадр:
«сгорела в лаве» (lava_system) и «истекло время жизни» (lifetime_system). Второй
`DESTROY` должен быть тихо проигнорирован — сущность уже мертва. Именно поэтому
`destroy_now` начинается с проверки «жива ли». Без неё индекс дважды попадёт в список
свободных, и потом две разные сущности получат один индекс.

> **Частые ошибки в e0503.**
> * Обходить всегда первый пул, а не меньший — тест `view_visits == 40` упадёт.
> * Удалять сущность только из одного-двух пулов. `destroy_now` удаляет из **всех**
>   четырёх (у `remove` в пуле уже есть проверка «нет компонента — вернуть false», так
>   что звать его для всех пулов безопасно).
> * Забыть увеличить поколение — старые handles «оживут».
> * Не очистить `commands` после `flush`.
> * Выполнять команды прямо внутри систем — ровно то, от чего command buffer защищает.

**Коротко:** запрос обходит меньший пул и проверяет остальные. Создавать и удалять
сущности во время обхода нельзя — записывайте команды и применяйте их после системы.

## 5. Системы

Система — функция над запросом. Хорошие системы:

* делают одну вещь (движение, урон, время жизни, рендер-экстракция — подготовка данных
  для отрисовки);
* явно объявляют доступ к компонентам и ресурсам (синглтонам: время, ввод, конфиг);
* не держат состояние между кадрами (а если держат — в компонентах или ресурсах);
* не вызывают друг друга напрямую — общаются через данные (компоненты, события).

Пример кадра:

```
 InputSystem        → пишет PlayerIntent
 AISystem           → читает Position, пишет AIIntent
 MovementSystem     → читает Velocity, Intent; пишет Position
 CollisionSystem    → читает Position, Collider; пишет Contacts (события)
 DamageSystem       → читает Contacts; пишет Health; команды «уничтожить»
 LifetimeSystem     → пишет Lifetime; команды «уничтожить»
 [точка синхронизации: применить команды]
 RenderExtract      → читает Position, Sprite; пишет данные для рендера
```

Обратите внимание: системы не знают друг о друге. InputSystem не вызывает
MovementSystem — она просто кладёт данные (PlayerIntent), а MovementSystem их читает.
Это как конвейер на заводе: каждый рабочий делает свою операцию над тем, что пришло
с ленты, и кладёт результат обратно на ленту.

Overwatch (доклад Тима Форда) — около 46 систем, строгое правило «системы не имеют
состояния, компоненты не имеют поведения», и синглтон-компоненты для глобального состояния.

Вот как выглядит система из `e0503` (она уже написана в упражнении):

```c3
fn void movement_system(World* w)
{
    @view2(&w.pos, &w.vel; Entity e, Position* p, Velocity* v)   // все с Pos и Vel
    {
        p.p += v.v;          // позиция += скорость (поэлементно, это float[<2>])
    };
}
```

Вся «логика» — одна строка. Всё остальное (какие сущности, в каком порядке, где
лежат данные) решает инфраструктура ECS.

**Коротко:** система — маленькая функция над запросом, без собственного состояния;
системы общаются только через данные.

## 6. Планирование систем

### 6.1 Конфликты

Если системы объявляют, какие компоненты читают и пишут, движок может *сам* решить,
какие системы выполнять параллельно (в разных потоках одновременно):

* две системы **конфликтуют**, если одна пишет компонент, который другая читает или пишет;
* неконфликтующие системы можно выполнять одновременно;
* среди конфликтующих важен порядок, и он должен быть **детерминированным**
  (одинаковым при каждом запуске): обычно — порядок регистрации, плюс явные
  ограничения `before`/`after`.

Почему именно так. Два **читателя** одних данных друг другу не мешают — как два
человека, читающие одну книгу. **Писатель и читатель** мешают: читатель может увидеть
полуизменённые данные, и результат зависит от того, кто успел первым (это **гонка
данных**). Два **писателя** — тем более.

| система 1 | система 2 | конфликт? |
|---|---|---|
| читает Pos | читает Pos | нет |
| читает Pos | пишет Pos | **да** |
| пишет Pos | пишет Pos | **да** |
| пишет Pos | читает Vel | нет (разные данные) |

С битовыми масками (каждый компонент — бит) это одно выражение:

```
 conflicts(a, b) = (a.writes & (b.reads | b.writes)) != 0
                || (b.writes & (a.reads | a.writes)) != 0
```

Пример: `move` (reads VEL, writes POS) и `ai` (reads POS, writes AI). `move.writes & ai.reads =
POS & POS ≠ 0` → конфликт. А `ai` и `regen` (writes HP): `AI & HP = 0`, `HP & POS = 0` →
не конфликтуют.

### 6.2 Этапы

```
 систем:  A(w Pos)  B(r Vel, w Acc)  C(r Pos)  D(w Vel)  E(r Hp)
 этапы:   [A, B, E]  ->  [C, D]
          A и C конфликтуют (Pos), B и D конфликтуют (Vel)
```

**Этап** (stage) — группа систем, которые можно выполнять в любом порядке или
одновременно; этапы выполняются строго друг за другом. Проследим жадную раскладку
для примера выше (системы в порядке регистрации A, B, C, D, E):

| система | с кем конфликтует среди предыдущих | их этапы | этап системы |
|---|---|---|---|
| A | — | — | 0 |
| B | — | — | 0 |
| C | A (A пишет Pos, C читает) | 0 | 0 + 1 = **1** |
| D | B (D пишет Vel, B читает) | 0 | **1** |
| E | — | — | 0 |

Правило: этап системы = (максимальный этап среди тех, с кем она конфликтует и кто
раньше неё) + 1, или 0, если таких нет. Это и есть «длина самого длинного пути» в
графе зависимостей.

Bevy строит граф зависимостей из access-наборов и явных ограничений и раздаёт системы
пулу потоков; Unity DOTS — через `JobHandle`-зависимости, вычисляемые по типам
компонентов, которые job читает/пишет; flecs — фазы (pipeline) и автоматические
точки синхронизации. Простой и детерминированный вариант — **жадная раскладка по
этапам** (stages): система попадает в первый этап после последнего этапа, с которым она
конфликтует или после которого должна идти. Упражнение **e0505_scheduler**.

### 6.3 Явные ограничения и топологическая сортировка

Иногда порядок важен, даже если системы не конфликтуют по данным, — или нужно, чтобы
система, зарегистрированная *раньше*, выполнилась *позже* («render после camera»). Для
этого есть явные ограничения `after`. Они образуют **граф**: стрелка `j → i` значит
«j раньше i». Расставить вершины графа в порядке, совместимом со всеми стрелками, —
задача **топологической сортировки**.

Аналогия: одевание. «Носки до ботинок», «брюки до ботинок», «рубашка до пиджака».
Правильных порядков много; нужен любой, не нарушающий правил. А если правила
говорят «носки до ботинок» и «ботинки до носков» — это **цикл**, порядка не существует.

**Алгоритм Кана** (как в `e0505`): повторять — среди ещё не взятых систем, у которых
**все** предшественники уже взяты, взять ту, у которой **меньший индекс**
регистрации. Если взять некого, а системы остались — цикл.

Пример: системы 0:`render` (after 2), 1:`input`, 2:`camera` (after 1).

| шаг | уже взяты | готовые (все предшественники взяты) | берём |
|---|---|---|---|
| 1 | — | 1 (`input`; у 0 и 2 есть невзятые предшественники) | 1 |
| 2 | 1 | 2 (`camera`) | 2 |
| 3 | 1, 2 | 0 (`render`) | 0 |

`order = [1, 2, 0]`, `rank[1] = 0`, `rank[2] = 1`, `rank[0] = 2`. Выбор «меньшего
индекса среди готовых» делает результат детерминированным: при одинаковых входных
данных план всегда одинаков.

Затем этапы считаются обходом в порядке `order`, а зависимостями считаются и явные
`after`, и конфликты с системами, стоящими раньше по `order` (меньший `rank`). Все такие
стрелки идут «вперёд», поэтому при подсчёте этапа системы этапы всех её
предшественников уже известны.

**Проверка правильности плана в `e0505`** — красивая идея: симуляция запускается
дважды, с прямым и обратным порядком систем *внутри* этапов. Если план верен (внутри
этапа никто не конфликтует), результаты обязаны совпасть бит в бит. Это дешёвый
способ поймать гонку, не запуская потоков.

Многопоточное выполнение этапов — тема главы 12 (job system); здесь мы строим сам
план и выполняем его последовательно.

> **Частые ошибки в e0505.**
> * В `conflicts` учесть только «a пишет — b читает», забыв симметричный случай и
>   «оба пишут».
> * Считать этапы в порядке регистрации, а не в порядке `order` — тогда этап
>   предшественника может быть ещё не посчитан.
> * Учитывать конфликт с системами, стоящими **позже** по `order` (нужны только
>   `rank[j] < rank[i]`).
> * Выбирать среди готовых не минимальный индекс — план станет зависеть от деталей
>   реализации.
> * Не обнаружить цикл: если за проход не нашлось ни одной готовой системы, а
>   взяты не все, — `return false`.
> * Забыть выставить `stage_count` (максимальный этап + 1).

**Коротко:** системы конфликтуют, если одна пишет то, что другая трогает. Порядок —
топологическая сортировка явных `after` (меньший индекс среди готовых). Этап =
1 + максимум этапов предшественников.

## 7. Производительность: откуда берётся выигрыш

Обход 100 000 сущностей «позиция += скорость * dt»:

* **OOP с виртуальным Update**: 100 000 косвенных вызовов, объекты по 200+ байт в
  разных местах кучи — каждая итерация тащит в кэш лишние данные и, скорее всего,
  промахивается;
* **ECS (архетип)**: два плотных массива по 1.2 МБ (`float[3]`), линейный проход,
  автовекторизация. Разница на практике — от 5 до 50 раз.

Откуда цифры: `float[3]` — 12 байт; 100 000 × 12 = 1.2 МБ на массив. Кэш-линия 64 байта
вмещает 5 таких позиций — одно чтение памяти обслуживает 5 итераций, и процессор
заранее подгружает следующие линии (**prefetch**), видя, что мы идём подряд. В OOP-варианте
одна кэш-линия часто содержит 12 нужных байт из 64, а следующий объект лежит
неизвестно где. **Автовекторизация** — компилятор сам превращает простой цикл над
массивом в SIMD-инструкции (глава 04).

Но цифры зависят от задачи. Если у вас 200 объектов со сложной уникальной логикой, ECS
ничего не ускорит, а код станет сложнее. Майк Актон: «Where there is one, there are many»
(«Где один — там много») — ECS выигрывает там, где много однородных объектов.

**Коротко:** выигрыш ECS — от плотных массивов и линейного обхода; он заметен,
когда однородных объектов тысячи.

## 8. Дополнительные темы

### 8.1 Ресурсы (синглтоны)

Не всё в игре — сущности: время кадра, ввод, настройки, генератор случайных чисел,
навигационная сетка уровня существуют в одном экземпляре. **Синглтон** — объект,
который существует в единственном экземпляре. В Bevy это `Resource`
(доступ `Res<Time>` / `ResMut<Score>`), в Unity DOTS — singleton-компоненты, в
Overwatch — «singleton components» на специальной сущности. Важно, чтобы доступ к
ресурсам тоже объявлялся системой (read/write) — иначе планировщик не увидит
конфликт, и две параллельные системы будут писать в один и тот же ГПСЧ
(генератор псевдослучайных чисел). В `e0505` `INPUT` и `CAMERA` — как раз такие
ресурсы: у них тоже есть свои биты в масках.

### 8.2 События в ECS

Как системе сообщить другой, что «произошло столкновение»? Варианты:

* **События как компоненты**: добавить сущности компонент `Hit { damage }` на один
  кадр. В sparse-set ECS это дёшево, в архетипной — структурное изменение.
* **События как сущности**: создать сущность-событие с компонентом `Collision { a, b }`
  и удалить её в конце кадра. Просто и укладывается в модель.
* **Очереди событий как ресурсы**: `Events<Collision>` в Bevy — двойной буфер (глава 06),
  системы-писатели и системы-читатели объявляют доступ.

### 8.3 Иерархии и отношения

Трансформ ребёнка зависит от родителя. В ECS это компоненты `Parent { Entity }` и
`Children { List }` плюс система, которая обходит сущности в порядке иерархии (сначала
родители). flecs пошёл дальше и сделал **отношения** первоклассными: пара
`(ChildOf, parent)` — это особый «компонент», а запрос может сказать «для каждого
ребёнка — его родитель» или «все сущности в одной иерархии». Архетипы flecs учитывают
пары, поэтому дети одного родителя лежат в одной таблице — обход иерархии становится
линейным. Глава 08 подробно разбирает иерархии трансформаций.

### 8.4 Сериализация и префабы

Мир ECS сериализуется (сохраняется в байты/файл, глава 13) естественно: для каждой
сущности — список компонентов, для каждого компонента — данные (рефлексия, глава 13).
**Префаб** (prefab, blueprint, archetype в смысле «шаблона») — это просто сохранённый
набор компонентов, который при создании копируется в новую сущность. Например, префаб
«гоблин» = {Position, Health 30, Sprite "goblin.png", AI "melee"}. В архетипной ECS
создание тысячи одинаковых сущностей из префаба — это одно выделение тысячи строк в
нужном архетипе и `memcpy` столбцов — очень быстро. Ссылки между сущностями (Entity
внутри компонентов) при загрузке надо **переназначить**: id в файле и id в мире разные.

### 8.5 Change detection и реактивность

Многие системы должны работать «только если что-то изменилось»: пересчитать мировую
матрицу, если изменился локальный трансформ; обновить UI, если изменилось здоровье.
Bevy хранит у каждого компонента тик последнего изменения (`Changed<T>`, `Added<T>`),
EnTT — сигналы `on_construct`/`on_update`/`on_destroy`, flecs — observers и
мониторы. Реализуя ECS, решите заранее: изменение фиксируется при *записи* (дорого —
каждый `get_mut` ставит флаг) или при *сравнении* (ещё дороже); гранулярность —
компонент, чанк или пул целиком.

**Коротко:** глобальные данные — ресурсы с объявленным доступом; события — компоненты,
сущности или очереди; иерархии — компоненты-ссылки или отношения; префаб — шаблон набора
компонентов.

## 9. Когда ECS — плохой выбор

* **Иерархии и графы**: дерево сцены, UI, скелеты — естественно выражаются деревьями;
  в ECS это компоненты `Parent`/`Children` и отдельные системы обхода (flecs
  поддерживает отношения «пары» `(ChildOf, parent)` как первоклассную концепцию).
* **Уникальная сложная логика**: боссы, катсцены, квесты — часто проще писать
  обычным кодом или скриптами поверх ECS.
* **Маленькие игры**, где производительность не проблема, а скорость прототипирования важна.
* **Godot** сознательно не стал ECS (статья Хуана Линецкого «Why isn't Godot an ECS-based
  game engine?»): дерево узлов удобнее для пользователей, а производительно-критичные
  части (рендер, физика) и так написаны в data-oriented стиле внутри «серверов».
* **Unreal** сохранил Actor/Component для геймплея и добавил Mass для массовых
  симуляций (толпы, трафик) — гибрид, который выбирают многие студии.

ECS — это инструмент для данных, а не религия. Частая архитектура: ECS как «ядро
симуляции», а поверх — удобный объектный слой для геймплей-программистов.

## 10. Подводные камни

* **«Бог-компонент»**: `Player` с 50 полями. Компоненты должны быть маленькими и
  специализированными.
* **Зависимость от порядка обхода**: порядок сущностей в таблицах меняется (swap-remove);
  если логика от него зависит — недетерминизм. Сортируйте или делайте логику
  независимой от порядка.
* **Указатели на компоненты**, сохранённые между кадрами, — висячие после перемещения
  (архетипы, swap-remove). Храните Entity. (Даже внутри кадра: `&list[i]` повисает
  после `push`, если `List` перевыделил память.)
* **Слишком мелкие системы**: тысяча систем по 3 сущности — накладные расходы
  планирования больше работы.
* **Структурные изменения в горячем цикле** архетипной ECS: добавление тега каждый кадр
  тысячам сущностей = тысячи перемещений.
* **Синглтоны как обычные компоненты** на «специальной» сущности — работает, но
  запутывает; лучше явные ресурсы.

## Словарик

* **ECS** — Entity Component System: архитектура «сущности + компоненты + системы».
* **Игровой объект** — любая «вещь» в игровом мире.
* **Сущность (entity)** — идентификатор объекта, без данных и поведения.
* **Компонент** — структура чистых данных, прикреплённая к сущности.
* **Система** — функция, обрабатывающая все сущности с нужным набором компонентов.
* **Handle** — «умный номер»: индекс + поколение, безопасный к переиспользованию.
* **Индекс** — номер ячейки во внутренних таблицах.
* **Поколение (generation)** — счётчик переиспользований ячейки; отличает новый объект от старого.
* **FIFO-очередь** — «первым пришёл — первым ушёл».
* **Наследование / композиция** — «является» (класс-потомок) / «состоит из» (контейнер частей).
* **Кэш, кэш-линия, промах кэша** — быстрая память процессора, кусок в 64 байта, обращение мимо кэша.
* **Sparse set** — разреженный массив `индекс → позиция` + плотные массивы.
* **Плотный (dense) массив** — массив без дырок.
* **Параллельные массивы** — массивы, где элементы с одной позицией относятся к одному объекту.
* **Swap-remove** — удаление переносом последнего элемента на место удалённого.
* **Пул (компонентов)** — хранилище всех компонентов одного типа.
* **Устаревший (stale) компонент/handle** — принадлежащий уже умершей сущности.
* **Архетип** — уникальный набор типов компонентов; таблица для сущностей с этим набором.
* **Битовая маска** — число, где каждый бит означает «есть/нет» чего-то.
* **Тег** — компонент без данных, значимо само наличие.
* **Структурное изменение** — добавление/удаление компонентов или сущностей.
* **Type-erased** — «со стёртым типом»: работа с сырыми байтами и размером.
* **Чанк** — блок памяти фиксированного размера с частью таблицы архетипа.
* **Запрос (query, view)** — описание нужных компонентов и доступа к ним.
* **Фильтр** — условие запроса: With, Without, Optional, Changed.
* **Change detection** — отслеживание, какие компоненты изменились.
* **Command buffer** — список отложенных команд, применяемых после системы.
* **Точка синхронизации** — место в кадре, где применяются отложенные изменения.
* **Trailing-блок (`@body`)** — тело, передаваемое макросу после вызова.
* **Ресурс (синглтон)** — глобальные данные в одном экземпляре.
* **Конфликт систем** — одна пишет данные, которые другая читает или пишет.
* **Гонка данных** — результат зависит от того, какой поток успел первым.
* **Этап (stage)** — группа систем без взаимных конфликтов.
* **Топологическая сортировка** — упорядочивание вершин графа, совместимое со стрелками.
* **Алгоритм Кана** — топосортировка «бери готовые вершины по одной».
* **Детерминированность** — одинаковый результат при одинаковых входных данных.
* **Префаб** — шаблон набора компонентов для создания сущностей.
* **Автовекторизация** — компилятор сам превращает цикл в SIMD-код.
