# Глава 10. Ввод

> Упражнения главы: `e1001_edge_detection` → `e1002_device_abstraction` →
> `e1003_action_mapping` → `e1004_combo_buffer` → `e1005_replay`.

Ввод кажется самой скучной частью движка: «спроси у ОС, нажата ли клавиша». На
практике это одна из подсистем, которые игроки чувствуют сильнее всего. Плохая
графика — «некрасиво», плохой ввод — «игра не слушается», «я нажимал прыжок!»,
«геймпад сам по себе крутит камеру». Хорошие новости: правильная архитектура ввода
небольшая, хорошо изучена и почти не зависит от жанра. Плохие: почти каждая её
часть имеет неочевидную ловушку, на которую наступают все по очереди.

В этой главе мы пройдём путь от сырого события ОС до «игрок сделал хадокен», а в
конце запишем ввод в файл и воспроизведём матч бит-в-бит.

```
 ┌───────────┐   ┌────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────┐
 │ ОС/драйвер│──>│ платформа: │──>│ состояние    │──>│ action map + │──>│ геймплей │
 │ HID, XInput│  │ сырые      │   │ устройств:   │   │ контексты:   │   │ (системы │
 │ evdev, ... │  │ события    │   │ кнопки, оси, │   │ JUMP, FIRE,  │   │  ECS,    │
 └───────────┘   │ (kind,code,│   │ фронты, dz   │   │ MOVE (ось)   │   │  UI)     │
                 │  value)    │   └──────────────┘   └──────┬───────┘   └──────────┘
                 └────────────┘                             │
                                                   ┌────────┴────────┐
                                                   │ буфер ввода,    │
                                                   │ запись реплея   │
                                                   └─────────────────┘
```

Каждый слой знает только о соседних. Геймплей никогда не видит scancode, а
платформенный слой никогда не знает, что такое «прыжок».

## 1. Слой платформы и сырые события

Каждая ОС отдаёт ввод по-своему:

* **Windows** — сообщения окна `WM_KEYDOWN`/`WM_KEYUP` (с автоповтором и флагом
  «была ли клавиша нажата»), `WM_INPUT` (Raw Input — сырые дельты мыши без
  ускорения курсора), XInput (опрос состояния геймпада раз в кадр, 4 слота),
  GameInput (новый унифицированный API).
* **Linux** — evdev: поток структур `input_event { time, type, code, value }`;
  type = `EV_KEY`/`EV_REL`/`EV_ABS`, code = номер клавиши/оси, value = 0/1/2
  (2 — автоповтор) или значение оси. Поверх — X11/Wayland для клавиатуры окна и
  SDL для геймпадов.
* **macOS** — `NSEvent` для клавиатуры/мыши, GameController.framework для
  геймпадов.
* **Консоли** — собственные SDK, как правило опросного типа: «вот структура
  состояния контроллера на этот кадр».

Движки прячут это за тонким платформенным слоем, который превращает всё в
единый поток нормализованных событий. Хорошая модель — та же тройка, что у
evdev: `(kind, code, value)`. Она тривиально сериализуется, её легко логировать
и подсовывать в тесты (весь стенд в `e1002` — это массив таких троек).

```c3
enum RawKind : char { KEY, MOUSE_BUTTON, MOUSE_MOVE, PAD_BUTTON, PAD_AXIS }
struct RawEvent { RawKind kind; uint code; int value; }
```

**Scancode vs keycode.** Scancode — физическое положение клавиши (USB HID usage:
`4` — клавиша, где на QWERTY нарисовано A). Keycode — символ с учётом раскладки.
Для управления (WASD) почти всегда нужен **scancode**: на AZERTY клавиши «вперёд»
физически там же, где W на QWERTY, но печатают Z. Для ввода текста — наоборот,
нужны символы, причём не keycode, а отдельные текстовые события (IME, мёртвые
клавиши, композиция иероглифов). Смешивать эти два потока — классическая ошибка:
«в чате нельзя напечатать букву W, потому что персонаж убегает».

**Таблицы трансляции.** Сопоставление платформенных кодов с внутренним перечислением
`Control` лучше держать данными (таблица на платформу), а не разбросанными
`switch`-ами. В `e1002` это функции `key_from_scancode` и `pad_button_from_index`,
возвращающие `Control?` — нераспознанное событие не роняет игру, а считается.

**Геймпады — зоопарк.** Xbox, PlayStation, Switch Pro и сотни noname-устройств
имеют разные индексы кнопок и осей. SDL поддерживает базу `gamecontrollerdb.txt`
(строка на модель с GUID устройства и маппингом), Steam Input делает то же на
своём уровне. Внутри движка нужна абстракция «позиционных» кнопок: `PAD_SOUTH`
(A на Xbox, крестик на PlayStation, B на Nintendo!), `PAD_EAST` и т.д.
Названия на кнопках — дело UI-слоя.

**Hot-plug.** Геймпады подключают и отключают во время игры. Устройство получает
стабильный идентификатор (слот + поколение — те же handles из главы 03), а при
отключении игра обычно ставит паузу и показывает «Подключите контроллер». На
консолях это требование сертификации.

## 2. Опрос или события

Есть две модели получения ввода.

**Опрос (polling):** раз в кадр спрашиваем «каково состояние устройства сейчас?».
XInput, большинство консольных API, `GetAsyncKeyState`. Просто, но между двумя
опросами может случиться что угодно, и мы этого не увидим.

**События (events):** ОС присылает очередь «нажато», «отпущено», «сдвинулось».
Ничего не теряется, порядок сохраняется, у событий есть временная метка.

Игровой код при этом почти всегда хочет **состояние на кадр**, а не поток событий:
системе движения нужно «держит ли игрок вправо», а не «в 12:00:01.337 пришёл
KEY_DOWN». Поэтому стандартная схема — гибрид:

```
начало кадра:
    keyboard.begin_frame()          // сбросить защёлки фронтов
    while (platform.poll_event(&e)) // выкачать ВСЕ события ОС
        input.apply(e)              // обновить состояние + защёлкнуть фронты
    gamepads.poll()                 // опросные устройства — снимком
    actions = action_map.resolve(input)
затем фиксированные шаги симуляции читают actions
```

Важно: события выкачиваются **все** и **в начале кадра**. Опрашивать ввод
«когда понадобится» из глубины геймплейного кода — значит получить разное
состояние в разных системах одного кадра.

### Ввод и фиксированный шаг

Глава 01: симуляция идёт фиксированными шагами, их может быть 0, 1 или несколько
за кадр рендера. Если на кадре было 2 шага, а «нажатие прыжка» — защёлкнутый
фронт этого кадра, то кто его увидит? Варианты:

* фронт «съедается» первым шагом, второй его уже не видит (обычно правильно:
  одно нажатие — один прыжок);
* при 0 шагах за кадр (рендер быстрее симуляции) фронт нельзя сбрасывать —
  иначе нажатие пропадёт. Поэтому защёлки сбрасывают не в начале кадра рендера,
  а после того, как их **потребил** шаг симуляции.

Это первая причина, по которой ввод живёт ближе к симуляции, чем к рендеру. Вторая
— сетевые игры и реплеи (раздел 7): симуляции нужен ввод, привязанный к номеру
**тика**, а не кадра.

### Задержка ввода

Каждый слой добавляет задержку: опрос устройства (USB 125–1000 Гц), очередь ОС,
момент выкачивания в кадре, шаг симуляции, рендер, буферизация кадров в
драйвере (тройная буферизация), развёртка монитора. Итог в 50–100 мс — обычное
дело. Движковые меры: выкачивать ввод как можно позже перед симуляцией, не
держать лишних кадров в очереди GPU (NVIDIA Reflex, AMD Anti-Lag по сути
делают именно это), для курсора/камеры — «late latching» (перечитывать мышь
прямо перед отправкой кадра на GPU). Файтинги отдельно публикуют «input lag» в
кадрах — игроки это измеряют.

## 3. Фронты: pressed/held/released

Геймплею нужны три вопроса:

| запрос | смысл | пример |
|---|---|---|
| `held(k)` | клавиша удерживается (уровень) | бег, прицеливание |
| `pressed(k)` | нажата в этом кадре (передний фронт) | прыжок, выстрел |
| `released(k)` | отпущена в этом кадре (задний фронт) | отпустить натянутый лук |

Наивная реализация хранит снимок прошлого кадра:

```c3
pressed  = down & ~prev_down;
released = ~down & prev_down;
```

Сравните с временной диаграммой быстрого тапа, уложившегося между двумя кадрами:

```
кадр:        N               N+1
             |               |
клавиша:  ___|___/‾‾‾\_______|_______
                  down  up
снимки:   down=0           down=0     => pressed = 0 & ~0 = 0. Прыжка нет.
```

На 60 FPS тап короче 16 мс редкость, но на 30 FPS, при подтормаживании,
загрузке или на сенсорном экране — обычное дело. То же с «отпустил и сразу нажал
снова» — снимок покажет `held` без единого фронта, хотя игрок явно хотел второе
действие.

Правильно — **защёлкивать** фронты в обработчике событий:

```c3
fn void Keyboard.on_event(&self, Key k, bool is_down)
{
    ulong b = bit(k);
    if (is_down == ((self.down & b) != 0)) return;   // автоповтор / лишний up
    if (is_down) { self.down |= b; self.pressed_bits |= b; }
    else         { self.down &= ~b; self.released_bits |= b; }
}
```

и очищать защёлки после того, как их потребили. Тогда тап даст в одном кадре и
`pressed`, и `released`, а `held` будет ложным — и это правильный ответ.

Детали, о которых стоит помнить:

* **Автоповтор** ОС присылает повторные «down». Для текстового поля это
  полезно, для геймплея — нет: повтор не должен быть новым нажатием.
* **Потеря фокуса.** Игрок нажал W и сделал Alt+Tab — «up» придёт в другое
  окно. Без обработки персонаж бежит вперёд вечно. При потере фокуса окно
  обязано «отпустить» всё (сгенерировать released для всех down).
* **Битовые маски.** 64 клавиши — один `ulong`; полная клавиатура — `ulong[2]`
  или `ulong[4]`. Весь снимок ввода — несколько машинных слов: копировать,
  сравнивать, писать в реплей и пересылать по сети дёшево. Это лучше, чем
  `bool[256]` или, тем более, хеш-таблица.
* **Длительность удержания** (`held_frames`) — полезное расширение для
  «заряжаемых» действий и для различения тапа и удержания. Её тоже считают по
  тикам симуляции, а не по времени стены.

В `e1001` вы реализуете эту схему и увидите в выводе, где наивная версия теряет
нажатия.

## 4. Аналоговые оси и мёртвые зоны

Стик геймпада отдаёт `short` от -32768 до 32767 по каждой оси, триггер — от 0 до
32767 (или 0–255 в XInput). Механический стик **никогда** не возвращается точно в
0: шум ±1000–3000 у нового геймпада и заметно больше у изношенного («stick drift»).
Отсюда мёртвая зона (deadzone).

### Осевая зона

Простейший вариант — обнулить малые значения: `|v| < dz → 0`. Плохо: на выходе из
зоны значение скачком прыгает с 0 до `dz` (25% хода), точное прицеливание на малых
отклонениях невозможно. Поэтому значение **перемасштабируют**:

```
            0,                                  |v| <= dz
out(v) = {
            sign(v) * (|v| - dz) / (max - dz),  иначе (с ограничением 1.0)
```

```
out
1.0 |                       ____
    |                   ___/
    |               ___/
    |           ___/
0.0 |__________/
    +---------+-------------+---> |v|
    0        dz            max
```

Осторожно с -32768: модуль не помещается в `short`, а `32768 > 32767`, поэтому
нужен `int` и ограничение сверху.

### Радиальная зона

Если применить осевую зону к x и y стика **по отдельности**, зона получится
крестом: при движении почти вдоль оси вторая компонента обнуляется, и стик
«прилипает» к восьми направлениям. Это одна из самых частых жалоб на
самописный ввод в шутерах. Правильно — считать зону по длине вектора:

```
           y                                    y
           |                                    |
      +----+----+   осевая (крест):        .----+----.   радиальная (круг):
      |    |####|   в заштрихованной       /    |    \   внутри круга — 0,
  ----+####+####+-- полосе вторая ось     |   (###)   |  снаружи — направление
      |####|    |   обнуляется             \    |    /   сохраняется, длина
      +----+----+                           '---+---'    плавно растёт от 0
```

```
m = sqrt(x² + y²)
m <= dz          -> (0, 0)
иначе nm = min(1, (m - dz) / (max - dz)),  (x, y) * nm / m
```

Профессиональные реализации добавляют ещё **внешнюю** мёртвую зону (стик физически
не доходит до 32767 по диагонали — без неё «полный ход» недостижим), кривые
отклика (квадратичная/кубическая — точность на малых отклонениях), раздельные
настройки для горизонтали и вертикали камеры и, иногда, «гибридную»
радиально-осевую зону. Хороший обзор — статья Josh Sutphin «Doing Thumbstick Dead
Zones Right» и разбор камеры в GDC-докладах по Destiny и Halo.

### Фиксированная точка

В `e1002` оси хранятся целыми в промилле (-1000..1000), корень — целочисленный.
Зачем, если есть `float`? Ради детерминизма: значение оси уходит в реплей и в
сетевой пакет, и симуляция на другом компьютере обязана получить **те же биты**.
Квантование ввода на входе в симуляцию — стандартная практика сетевых движков
(Overwatch, Rocket League квантуют стики до 8–16 бит).

### Последнее активное устройство

UI показывает подсказки «Нажмите [A]» или «Нажмите [Space]» в зависимости от
того, чем пользуется игрок. Ловушка: если любое событие оси переключает
устройство на геймпад, то лежащий на столе геймпад с дрейфующим стиком непрерывно
перехватывает подсказки. Переключаться нужно только по значимому вводу — после
мёртвой зоны. Мышь — аналогично: дрожание на 1 пиксель не повод.

### Мышь

Мышь — не абсолютная ось, а **дельты**. Их суммируют за кадр (за кадр приходит
много событий движения) и обнуляют в начале следующего. Для камеры нужны сырые
дельты (Raw Input на Windows, `EV_REL` на Linux), а не позиция курсора ОС: курсор
упирается в край экрана и проходит через «ускорение указателя». Чувствительность
мыши ни в коем случае не умножают на `dt` — дельта и так уже «за кадр»; это
классическая ошибка, из-за которой чувствительность зависит от FPS.

## 5. Действия вместо клавиш

Геймплейный код, который спрашивает `keyboard.pressed(KEY_SPACE)`, приговорён:
переназначение клавиш невозможно, геймпад надо поддерживать отдельным `||` в
каждом месте, а «пробел» в меню и в игре означает разное. Решение — уровень
**действий** (actions):

```
  Control (физика)           Binding                Action (смысл)
  KEY_SPACE   ─────────────┐
  PAD_SOUTH   ─────────────┴──>  JUMP      (кнопка: pressed/held/released)
  KEY_A, KEY_D, PAD_LX ────────>  MOVE_X    (ось: -1..1)
  MOUSE_DX, PAD_RX ────────────>  LOOK_X    (ось, разные множители!)
```

Действия бывают **кнопочные** (bool + фронты) и **осевые** (число; иногда 2D).
Привязка может превращать одно в другое: две клавиши дают ось (-1/0/+1), ось
с порогом даёт кнопку (триггер > 0.5 → FIRE).

Так устроено почти всё:

* **Unreal Engine 4** — Action/Axis Mappings в `DefaultInput.ini`.
* **Unreal Engine 5 Enhanced Input** — `InputAction` (тип значения: bool, axis1D,
  axis2D, axis3D), `InputMappingContext` с приоритетами, **модификаторы**
  (deadzone, negate, swizzle, scalar) и **триггеры** (pressed, released, hold,
  tap, chorded action, combo) на каждой привязке. Хороший образец «декларативного
  ввода».
* **Unity Input System** — `InputActionAsset` → Action Maps → Actions →
  Bindings с Composite (WASD → Vector2), Interactions (Hold, Tap, MultiTap) и
  Processors (deadzone, invert, scale), Control Schemes для групп устройств.
* **Godot** — `InputMap` с именованными действиями, `Input.is_action_just_pressed`,
  `get_vector()` для 2D-осей с радиальной зоной.

Общий архитектурный вывод: action map — это **данные**. Привязки загружаются из
файла настроек, правятся в меню, сохраняются для профиля игрока. Код игры знает
только перечисление действий.

### Переназначение и конфликты

Меню переназначения — это «нажмите новую клавишу для JUMP». Подводные камни:

* **Конфликты.** Новая клавиша уже занята в том же контексте — нужно либо
  отказать, либо поменять местами (swap), либо снять старую привязку. Конфликт
  проверяется **внутри контекста**: E может быть «взаимодействовать» в игре и
  «следующая реплика» в диалоге — это не конфликт.
* **Запрещённые клавиши.** Esc (меню), PrintScreen, системные кнопки консоли.
* **Во время ожидания** «нажмите клавишу» сам ввод не должен обрабатываться
  игрой — это отдельный модальный контекст.
* **Подсказки в UI** должны строиться по текущим привязкам (обратный поиск
  action → controls для текущего устройства), а не быть захардкожены в
  текстурах.

## 6. Контексты ввода

Одна и та же клавиша означает разное в разных ситуациях: пробел — «прыжок» в игре,
«следующая реплика» в диалоге, «подтвердить» в меню. Наивное решение — флаги
`if (in_menu) ... else if (in_dialog) ...` во всём геймплейном коде — быстро
превращается в кашу. Правильно — **стек контекстов**:

```
         ┌──────────────────────────────┐
  top    │ menu      (blocking)         │  W->MENU_UP, SPACE->CONFIRM, ESC->BACK
         ├──────────────────────────────┤
         │ dialog    (non-blocking)     │  SPACE->DIALOG_NEXT, E->DIALOG_NEXT
         ├──────────────────────────────┤
  bottom │ gameplay  (non-blocking)     │  W->MOVE, SPACE->JUMP, E->INTERACT, ESC->PAUSE
         └──────────────────────────────┘

  нажато {W, SPACE}, стек = [gameplay, dialog]:
      dialog:   SPACE -> DIALOG_NEXT, SPACE поглощён
      gameplay: W -> MOVE           (SPACE уже съеден — прыжка нет)
```

Алгоритм разрешения: идём от вершины вниз, каждый сработавший control
**поглощается** и не виден нижним контекстам; blocking-контекст (модальное меню)
не пропускает вниз ничего. Это ровно то, что вы реализуете в `e1003`.

Вариации в реальных движках:

* **Приоритеты вместо стека** (UE5 Enhanced Input: `AddMappingContext(ctx,
  priority)`). Стек — частный случай.
* **Consume per binding** — привязка решает, поглощать ли control (UE:
  флаг `bConsumeInput` на привязке в старой системе).
* **Маршрутизация в UI** — у UI своя иерархия фокуса (Unreal Slate/UMG «input
  routing», Godot `_gui_input` → `_unhandled_input`): событие сначала получает
  виджет под фокусом, и если он его не обработал — оно спускается в игру.
  Godot в этом смысле очень показателен: цепочка `_input` → `_gui_input` →
  `_shortcut_input` → `_unhandled_key_input` → `_unhandled_input`.
* **Несколько игроков** — у каждого свой стек контекстов и своё множество
  устройств (local multiplayer: «нажмите A, чтобы присоединиться» назначает
  геймпад игроку).

Ловушка смены контекста: игрок держит W, открывает меню (blocking), отпускает W,
закрывает меню. Если gameplay-контекст не получил released, персонаж бежит
дальше. Решения: при активации blocking-контекста посылать нижним «всё
отпущено»; либо, проще, нижние контексты вычисляют held из текущего состояния
устройств, а не из потока событий. Обратная проблема — нажатие ESC, закрывшее
меню, не должно в том же кадре открыть его снова: фронт поглощён контекстом,
который его обработал.

## 7. Буферизация ввода и комбо

Человек не попадает в кадр. Если игра требует нажать прыжок ровно в кадр
приземления, она ощущается «глухой». Поэтому почти любой экшен использует
**буфер ввода**: нажатие хранится N кадров и срабатывает, как только действие
становится возможным.

* **Jump buffering** — нажал прыжок за 5 кадров до приземления, прыжок
  случится в кадр приземления.
* **Coyote time** — ещё несколько кадров после схода с края платформы прыжок
  разрешён (родственная идея, но буферизуется не ввод, а состояние).
* **Буферизация в файтингах** — следующий приём, введённый во время анимации
  восстановления предыдущего, выполнится в первый доступный кадр.

### Распознавание движений

Файтинги записывают направления в нумпад-нотации (`5` — нейтраль, `6` — вперёд,
`2` — вниз), а спецприёмы — как последовательности: `236P` (хадокен), `623P`
(шорюкен), `41236K` (полукруг). Буфер — кольцевой буфер записей `{frame, dir,
buttons}`, запись добавляется при **изменении** состояния (удержание стика не
забивает буфер).

```
кольцевой буфер (новые справа):
  frame:  3    5    7    9
  dir:    2    3    6    6
  punch:  .    .    .    P      <- распознаём ОТ НОВЫХ К СТАРЫМ:
                                   P@9, затем 6, 3, 2 в обратном порядке
```

Распознавание идёт от свежего нажатия кнопки назад во времени, ища шаги движения в
обратном порядке. Параметры, определяющие «чувство» игры:

* **Окно кнопки** (button buffer) — насколько старым может быть нажатие.
* **Зазор между шагами** — максимум кадров между соседними направлениями.
* **Общее окно движения** — от первого шага до кнопки.
* **Leniency** — допускаются посторонние направления между шагами (`2-5-3-6`
  засчитывается как `236`), иногда пропуск диагонали (`26P` = `236P` в
  некоторых играх), «шорткаты» (`6236` → шорюкен).
* **Приоритеты** — `6236P` подходит под оба приёма; таблица движений проверяется
  в порядке приоритета.
* **Зеркалирование** — если персонаж смотрит влево, зеркалим **вход**
  (4↔6, 1↔3, 7↔9), а не дублируем таблицу движений.
* **Поглощение (consume)** — нажатие и направления, использованные сработавшим
  приёмом, помечаются потраченными. Без этого (а) приём срабатывает повторно в
  следующих кадрах, пока нажатие в окне буфера, и (б) хвост одного приёма
  склеивается с началом следующего: при серии хадокенов «6» первого и «23»
  второго дают `623` — и вместо хадокена вылетает шорюкен. Тест «two fireballs»
  в `e1004` ловит именно это.
* **Negative edge** — в Street Fighter отпускание кнопки тоже считается
  нажатием для спецприёмов. Это легко добавить флагом в запись буфера.

Все окна задаются **в кадрах симуляции**, а не в миллисекундах: файтинги
детерминированы и привязаны к 60 тикам в секунду. Именно поэтому буфер живёт
в симуляции и попадает в реплей и в rollback-неткод (GGPO): при откате
симуляции откатывается и буфер ввода.

### Не только файтинги

Тот же механизм — «буфер событий с окнами и последовательностями» — используется
для чит-кодов (Konami code), жестов (двойной тап для рывка, «тап vs удержание»),
QTE и даже голосовых/сенсорных жестов. UE5 Enhanced Input реализует «Combo»
триггер именно так: цепочка действий с временными окнами.

## 8. Запись ввода и реплеи

Если симуляция детерминирована (глава 01: фиксированный шаг, никаких
зависимостей от времени стены, ГСЧ с известным seed, одинаковые результаты
арифметики), то весь матч восстанавливается из:

```
seed + версия + ввод каждого тика
```

Так работают реплеи StarCraft и Age of Empires (минуты матча — десятки
килобайт), демо Doom (`.lmp` — буквально поток `ticcmd_t` по 4 байта на тик на
игрока), Trackmania, «призраки» в гонках, а также lockstep-сеть (глава 18):
по сети передаётся тот же поток ввода, что и в реплей.

Альтернатива — **snapshot-реплеи**: записывается состояние мира (как в сетевом
snapshot-протоколе, Quake 3 demos, CS:GO/Source demos). Они устойчивы к
недетерминизму и позволяют перематывать, но на порядки больше. Многие игры
комбинируют: поток ввода + периодические ключевые кадры состояния для быстрой
перемотки (как I-кадры в видео).

### Что записывать

Не сырые события и не scancode — а ввод **после action mapping**, привязанный к
тику: маску кнопочных действий и квантованные оси. Тогда реплей не зависит от
раскладки, привязок и устройства зрителя. Поток очень хорошо сжимается: соседние
тики почти всегда одинаковы, и даже простое RLE `{mask, count}` даёт сжатие в
десятки раз (в `e1005` 600 тиков укладываются в ~150 байт).

```
тики:   R R R R R R J J . . . . . . F F F F ...
RLE:    (R,6) (J,2) (.,6) (F,4) ...
```

### Рассинхрон и чекпоинты

Главный враг — desync: одна неинициализированная переменная, обход хеш-таблицы
в порядке адресов, `float`, посчитанный иначе на другом CPU или другим
компилятором, вызов `rand()` без seed, зависимость от FPS — и реплей «уплывает».
Хуже всего, что заметно это бывает через минуты после причины.

Защита — **чекпоинты**: при записи каждые N тиков сохраняется хеш состояния
симуляции; при воспроизведении хеши сверяются. Первый несовпавший чекпоинт
локализует ошибку с точностью до N тиков. Дальше — бинарный поиск: уменьшаем N
или пишем хеши подсистем по отдельности (физика, ИИ, инвентарь), чтобы найти,
**что** разошлось. Ровно так же отлаживают lockstep-сеть, и ровно так в
`e1005` ловятся подменённый ввод, чужой seed и обрезанный файл.

Хеш состояния должен покрывать всё, что влияет на будущее — включая состояние
ГСЧ. Хеш по полям, а не по байтам структуры (паддинг может содержать мусор).

### Формат файла

Минимальный заголовок реплея: магическое число, **версия формата**, версия
билда игры (реплей старой версии на новом коде почти наверняка рассинхронится —
многие игры просто отказываются его играть), seed, параметры матча (карта,
персонажи), число тиков. Данные — little-endian, побайтово (не `fwrite`
структуры — см. главу 13). Загрузчик обязан проверять каждое чтение на выход
за границы: реплеи передают между игроками, и это недоверенный ввод.

### Реплеи как инструмент разработки

Запись ввода — один из самых окупаемых инструментов движка:

* **Воспроизведение багов.** Тестировщик прикладывает реплей к баг-репорту —
  программист получает баг детерминированно, с отладчиком.
* **Регрессионные тесты.** Набор реплеев гоняется на CI; финальный хеш
  состояния сравнивается с эталоном. Изменился — либо баг, либо осознанное
  изменение геймплея (тогда эталон обновляют).
* **Профилирование** на одинаковой нагрузке от билда к билду.
* **Killcam, повторы голов, «призраки»** в гонках.

Ограничение: всё, что не детерминировано (физика с `float` на разных
платформах, многопоточность с недетерминированным порядком), нужно либо
сделать детерминированным, либо исключить из записываемой симуляции
(косметические частицы, звук и анимации можно не воспроизводить точно).

## 9. Производительность и устройство данных

Ввод — не горячая точка: десятки событий за кадр. Но несколько правил всё же
важны:

* Состояние ввода — плоские POD-структуры и битовые маски. Их копируют в буфер
  ввода, в реплей, в сетевой пакет и в историю для rollback (GGPO хранит ввод
  за 8+ кадров для каждого игрока).
* Платформенный поток событий может приходить из другого потока (на Windows
  окно и ввод часто живут в отдельном потоке, чтобы не блокироваться при
  перетаскивании окна). Тогда между потоками — SPSC-очередь событий (трек 1,
  упражнение 112), а состояние собирает поток симуляции.
* Никаких выделений памяти на событие. Кольцевые буферы фиксированного
  размера.

## 10. Типичные ошибки (сводка)

1. Фронты по снимкам — потеря быстрых нажатий (`e1001`).
2. Автоповтор ОС как новое нажатие.
3. Нет сброса при потере фокуса — «залипшие» клавиши.
4. Keycode вместо scancode для управления (AZERTY).
5. Осевая мёртвая зона на 2D-стике — «прилипание» к осям; зона без
   перемасштабирования — скачок на выходе (`e1002`).
6. Чувствительность мыши, умноженная на `dt`.
7. Геймплей опрашивает клавиши напрямую вместо действий.
8. Флаги `in_menu` вместо контекстов; утечка нажатий сквозь меню (`e1003`).
9. Окна ввода в миллисекундах в детерминированной симуляции; повторное
   срабатывание буферизованного нажатия; склейка приёмов (`e1004`).
10. Реплеи без версии, без seed и без чекпоинтов (`e1005`).

## Вопросы для самопроверки

1. Почему защёлкнутые фронты нельзя сбрасывать в начале каждого кадра рендера,
   если симуляция идёт фиксированным шагом? Что будет, если за кадр прошло 0
   шагов? 2 шага?
2. Чем scancode отличается от keycode? Что нужно для WASD, а что для чата?
3. Нарисуйте область мёртвой зоны для осевой и радиальной схем. Почему для
   стика камеры осевая схема плоха?
4. Зачем перемасштабировать значение после мёртвой зоны?
5. Почему значения осей квантуют до целых перед симуляцией в сетевых играх?
6. Как стек контекстов решает задачу «пробел в диалоге не должен заставлять
   персонажа прыгать»? Чем blocking-контекст отличается от non-blocking?
7. Игрок держит W, открывает меню паузы, отпускает W, закрывает меню. Что
   может пойти не так и как это предотвратить?
8. Почему при распознавании `236P` поиск идёт от новых записей к старым?
9. Какую ошибку предотвращает поглощение направлений сработавшего приёма?
10. Почему в реплей пишут действия, а не сырые события устройства?
11. Что должно входить в хеш состояния для чекпоинта реплея? Почему нельзя
    хешировать структуру побайтово?
12. Чем реплеи на вводе отличаются от реплеев на снимках? Когда какой выбрать?
