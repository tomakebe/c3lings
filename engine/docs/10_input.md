# Глава 10. Ввод

> Упражнения главы: `e1001_edge_detection` → `e1002_device_abstraction` →
> `e1003_action_mapping` → `e1004_combo_buffer` → `e1005_replay`.

## Карта главы

**О чём глава.** Как нажатие пальца на кнопку превращается в «персонаж прыгнул».
Мы пройдём весь путь: от того, что присылает операционная система, до
распознавания приёмов в файтинге и записи матча в файл.

**Зачем это нужно.** Игрок может простить некрасивую графику, но не простит
игру, которая «не слушается». Почти все жалобы вида «я нажимал прыжок, а он не
прыгнул!» — это ошибки в подсистеме ввода, а не «кривые руки» игрока.

**Что нужно знать заранее.**

* C3 на уровне трека по языку: структуры, методы, `enum`, `switch`, Optional
  (`int?`, `return ERR~;`), `List`.
* Битовые операции: `|` (ИЛИ), `&` (И), `~` (инверсия), `<<` (сдвиг). Если они
  подзабылись — в разделе 3.1 есть короткое напоминание на примерах.
* Глава 01 (игровой цикл): что такое **фиксированный шаг** и **детерминизм**.
  Коротко: симуляция игры обновляется ровными «тиками» (например, 60 раз в
  секунду), и при одинаковом вводе даёт одинаковый результат.
* Глава 03 (контейнеры): кольцевой буфер и handles — упоминаются мимоходом.

Никакой сложной математики не будет. Самое «математическое» место — длина
вектора по теореме Пифагора в разделе про мёртвые зоны, и мы разберём его на
числах.

**Что в какой части и какое упражнение её использует.**

| раздел | о чём | упражнение |
|---|---|---|
| 1. Слой платформы и сырые события | что присылает ОС, scancode, геймпады | `e1002` |
| 2. Опрос или события | как и когда забирать ввод | `e1001` |
| 3. Фронты: pressed/held/released | «нажал в этом кадре» без потерь | `e1001` |
| 4. Аналоговые оси и мёртвые зоны | стики, триггеры, мышь | `e1002` |
| 5. Действия вместо клавиш | JUMP вместо SPACE, переназначение | `e1003` |
| 6. Контексты ввода | меню/диалог/игра — кто «съедает» клавишу | `e1003` |
| 7. Буферизация ввода и комбо | хадокен, прощение неточности | `e1004` |
| 8. Запись ввода и реплеи | матч в 150 байт, поиск рассинхрона | `e1005` |
| 9. Производительность | как хранить данные ввода | все |

## Вступление

Ввод кажется самой скучной частью движка: «спроси у ОС, нажата ли клавиша». На
практике это одна из подсистем, которые игроки чувствуют сильнее всего. Плохая
графика — «некрасиво», плохой ввод — «игра не слушается», «я нажимал прыжок!»,
«геймпад сам по себе крутит камеру». Хорошие новости: правильная архитектура ввода
небольшая, хорошо изучена и почти не зависит от жанра. Плохие: почти каждая её
часть имеет неочевидную ловушку, на которую наступают все по очереди.

В этой главе мы пройдём путь от сырого события ОС до «игрок сделал хадокен», а в
конце запишем ввод в файл и воспроизведём матч бит-в-бит.

### Аналогия: почта в большой компании

Представьте, что игра — это директор компании, а ввод — входящая почта.

* **Почтальон (ОС, драйвер)** приносит конверты в своём формате: у Windows одни
  конверты, у Linux другие, у консоли третьи.
* **Экспедиция (платформенный слой)** вскрывает конверты и переписывает всё на
  единые бланки: «тип, код, значение».
* **Секретарь (состояние устройств)** ведёт журнал: какие кнопки сейчас зажаты,
  что нажали за этот кадр, куда отклонён стик.
* **Референт (action map + контексты)** переводит с «языка кнопок» на «язык
  намерений»: «нажат пробел» → «игрок хочет прыгнуть». Причём учитывает
  ситуацию: во время совещания (диалога) тот же пробел значит «следующая
  реплика».
* **Директор (геймплей)** читает только короткую сводку намерений. Он не
  знает и не должен знать, на какой клавиатуре сидит игрок.

Параллельно **архивариус (буфер ввода, запись реплея)** складывает копии сводок
в архив — чтобы можно было «переиграть» любой день компании заново.

### Общая схема

```
 ┌───────────┐   ┌────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────┐
 │ ОС/драйвер│──>│ платформа: │──>│ состояние    │──>│ action map + │──>│ геймплей │
 │ HID, XInput│  │ сырые      │   │ устройств:   │   │ контексты:   │   │ (системы │
 │ evdev, ... │  │ события    │   │ кнопки, оси, │   │ JUMP, FIRE,  │   │  ECS,    │
 └───────────┘   │ (kind,code,│   │ фронты, dz   │   │ MOVE (ось)   │   │  UI)     │
                 │  value)    │   └──────────────┘   └──────┬───────┘   └──────────┘
                 └────────────┘                             │
                                                   ┌────────┴────────┐
                                                   │ буфер ввода,    │
                                                   │ запись реплея   │
                                                   └─────────────────┘
```

Каждый слой знает только о соседних. Геймплей никогда не видит scancode, а
платформенный слой никогда не знает, что такое «прыжок».

Несколько слов из схемы, которые встретятся дальше постоянно:

* **Кадр (frame)** — один проход игрового цикла: собрать ввод, обновить мир,
  нарисовать картинку. При 60 FPS кадр длится примерно 16,7 мс.
* **Тик (tick)** — один шаг симуляции с фиксированным шагом времени (глава 01).
  Тиков за кадр может быть 0, 1 или несколько.
* **Событие (event)** — сообщение от ОС «что-то произошло»: клавиша нажата,
  мышь сдвинулась.
* **dz** на схеме — deadzone, мёртвая зона (раздел 4).

> **Коротко:** ввод — это конвейер из слоёв. Каждый слой переводит данные на
> «следующий уровень смысла»: байты ОС → единые события → состояние кнопок →
> намерения игрока. Геймплей видит только намерения.

## 1. Слой платформы и сырые события

### 1.1. Каждая ОС говорит на своём языке

Каждая ОС отдаёт ввод по-своему:

* **Windows** — сообщения окна `WM_KEYDOWN`/`WM_KEYUP` (с автоповтором и флагом
  «была ли клавиша нажата»), `WM_INPUT` (Raw Input — сырые дельты мыши без
  ускорения курсора), XInput (опрос состояния геймпада раз в кадр, 4 слота),
  GameInput (новый унифицированный API).
* **Linux** — evdev: поток структур `input_event { time, type, code, value }`;
  type = `EV_KEY`/`EV_REL`/`EV_ABS`, code = номер клавиши/оси, value = 0/1/2
  (2 — автоповтор) или значение оси. Поверх — X11/Wayland для клавиатуры окна и
  SDL для геймпадов.
* **macOS** — `NSEvent` для клавиатуры/мыши, GameController.framework для
  геймпадов.
* **Консоли** — собственные SDK, как правило опросного типа: «вот структура
  состояния контроллера на этот кадр».

Расшифровка терминов из списка:

* **API** — набор функций, которые ОС или библиотека даёт программисту.
* **Драйвер** — программа внутри ОС, которая умеет разговаривать с конкретным
  железом (клавиатурой, геймпадом).
* **HID** (Human Interface Device) — стандарт USB для «устройств, которыми
  управляет человек»: клавиатуры, мыши, геймпады. Он задаёт, например, номера
  клавиш (см. scancode ниже).
* **Автоповтор** — если долго держать клавишу в текстовом редакторе, буква
  начинает печататься снова и снова. Это ОС сама присылает повторные «нажато».
* **Дельта** — изменение, «насколько сдвинулось» (а не «где находится»).
* **Ускорение курсора** — ОС двигает курсор тем дальше, чем быстрее вы ведёте
  мышь. Для указателя на рабочем столе это удобно, для прицеливания в игре —
  вредно (одно и то же движение руки даёт разный поворот камеры).

### 1.2. Единый формат: тройка `(kind, code, value)`

Движки прячут это за тонким платформенным слоем, который превращает всё в
единый поток нормализованных событий. Хорошая модель — та же тройка, что у
evdev: `(kind, code, value)`. Она тривиально сериализуется, её легко логировать
и подсовывать в тесты (весь стенд в `e1002` — это массив таких троек).

```c3
enum RawKind : char { KEY, MOUSE_BUTTON, MOUSE_MOVE, PAD_BUTTON, PAD_AXIS }
struct RawEvent { RawKind kind; uint code; int value; }
```

Что здесь написано:

* `RawKind` — **вид** события: клавиша, кнопка мыши, движение мыши, кнопка
  геймпада, ось геймпада. `: char` значит «храни номер вида в одном байте».
* `code` — **какая именно** клавиша/кнопка/ось. Для клавиатуры это scancode,
  для оси — её номер.
* `value` — **что с ней случилось**: 1 — нажата, 0 — отпущена; для оси —
  текущее значение; для мыши — на сколько пикселей сдвинулась.

«Нормализованный» здесь значит «приведённый к одному виду»: неважно, пришло
событие из Windows или Linux, в игру оно попадёт одной и той же тройкой.
«Сериализуется» — легко превращается в байты для записи в файл или отправки по
сети (подробно — в главе 13).

Несколько событий в этом формате:

| что сделал игрок | kind | code | value |
|---|---|---|---|
| нажал W | `KEY` | 26 | 1 |
| отпустил W | `KEY` | 26 | 0 |
| сдвинул мышь вправо на 3 px | `MOUSE_MOVE` | 0 (ось x) | 3 |
| отклонил левый стик влево до упора | `PAD_AXIS` | 0 (LX) | -32768 |
| нажал «нижнюю» кнопку геймпада | `PAD_BUTTON` | 0 | 1 |

Почему это удобно для тестов: чтобы проверить слой ввода, не нужно подключать
настоящий геймпад. Достаточно написать массив таких троек и «скормить» его коду
— ровно так устроен стенд в `e1002`.

> **Коротко:** платформенный слой переписывает «зоопарк» форматов ОС в одну
> простую тройку `(kind, code, value)`. Дальше по конвейеру ОС уже не видна.

### 1.3. Scancode и keycode

**Scancode vs keycode.** Scancode — физическое положение клавиши (USB HID usage:
`4` — клавиша, где на QWERTY нарисовано A). Keycode — символ с учётом раскладки.
Для управления (WASD) почти всегда нужен **scancode**: на AZERTY клавиши «вперёд»
физически там же, где W на QWERTY, но печатают Z. Для ввода текста — наоборот,
нужны символы, причём не keycode, а отдельные текстовые события (IME, мёртвые
клавиши, композиция иероглифов). Смешивать эти два потока — классическая ошибка:
«в чате нельзя напечатать букву W, потому что персонаж убегает».

Аналогия: scancode — это **номер места в зрительном зале** («ряд 3, место 2»), а
keycode — **имя зрителя**, который на нём сидит. Для управления важно место
(где лежит палец), а не то, что на клавише нарисовано. Французский игрок с
раскладкой AZERTY держит пальцы там же, где американец держит WASD, — но на его
клавишах нарисовано ZQSD. Если игра читает символы, у француза «вперёд» окажется
неудобно сбоку.

```
QWERTY:   Q [W] E           AZERTY:   A [Z] E
         [A][S][D]                   [Q][S][D]
           ↑                            ↑
  scancode 26 в обоих случаях — «верхняя клавиша под левой рукой»
```

Новые слова:

* **Раскладка** — соответствие «клавиша → символ», которое выбирает
  пользователь (русская, английская, французская...).
* **IME** (Input Method Editor) — программа ОС для ввода сложных
  письменностей: набираете латиницей, а получаете иероглифы.
* **Мёртвая клавиша** — клавиша, которая сама ничего не печатает, но меняет
  следующую букву (например, `´` + `e` = `é`).

**Частые ошибки**

> * Управление по символам (keycode) — у игроков с другой раскладкой WASD
>   «разъезжается».
> * Один и тот же поток событий и для чата, и для управления — пишешь в чат
>   «where», а персонаж бегает. Правильно: когда открыто текстовое поле,
>   игровые действия не обрабатываются (это решают контексты, раздел 6).

### 1.4. Таблицы трансляции

**Таблицы трансляции.** Сопоставление платформенных кодов с внутренним перечислением
`Control` лучше держать данными (таблица на платформу), а не разбросанными
`switch`-ами. В `e1002` это функции `key_from_scancode` и `pad_button_from_index`,
возвращающие `Control?` — нераспознанное событие не роняет игру, а считается.

`Control` — это наше собственное перечисление «органов управления»: `KEY_W`,
`KEY_SPACE`, `MOUSE_LEFT`, `PAD_SOUTH`... Оно одно на весь движок, а таблиц
«код ОС → Control» столько, сколько платформ.

Почему возвращается `Control?` (Optional), а не просто `Control`? Потому что
игроку ничто не мешает нажать F12, кнопку «громкость» на мультимедийной
клавиатуре или 17-ю кнопку китайского геймпада. Для таких кодов в таблице нет
записи. Правильная реакция — **не паниковать**: вернуть «пусто» (`UNMAPPED~`),
увеличить счётчик нераспознанных событий (пригодится для отладки) и идти
дальше. Падение игры из-за неизвестной клавиши — худшее, что можно сделать.

### 1.5. Геймпады — зоопарк

**Геймпады — зоопарк.** Xbox, PlayStation, Switch Pro и сотни noname-устройств
имеют разные индексы кнопок и осей. SDL поддерживает базу `gamecontrollerdb.txt`
(строка на модель с GUID устройства и маппингом), Steam Input делает то же на
своём уровне. Внутри движка нужна абстракция «позиционных» кнопок: `PAD_SOUTH`
(A на Xbox, крестик на PlayStation, B на Nintendo!), `PAD_EAST` и т.д.
Названия на кнопках — дело UI-слоя.

**GUID** — уникальный идентификатор модели устройства (длинное число). По нему
SDL находит в базе нужную строку: «у этой модели кнопка №3 — это SOUTH».

«Позиционные» кнопки названы по сторонам света — по тому, **где** кнопка лежит в
ромбе из четырёх кнопок справа на геймпаде:

```
            NORTH
              ( )
     WEST ( )     ( ) EAST
              ( )
            SOUTH

 Xbox:        Y            PlayStation:   △          Nintendo:    X
           X     B                     □     ○                 Y     A
              A                           ×                       B
```

Видите ловушку? На Xbox «нижняя» кнопка — A, а на Nintendo A — это «правая».
Если в коде написано «кнопка A = прыжок», на разных геймпадах прыжок окажется
под разными пальцами. Поэтому в движке говорят «SOUTH = прыжок», а какую букву
нарисовать в подсказке — решает интерфейс по типу подключённого геймпада.

### 1.6. Подключение на лету (hot-plug)

**Hot-plug.** Геймпады подключают и отключают во время игры. Устройство получает
стабильный идентификатор (слот + поколение — те же handles из главы 03), а при
отключении игра обычно ставит паузу и показывает «Подключите контроллер». На
консолях это требование сертификации.

Зачем «поколение»? Представьте: геймпад игрока 2 сел и отключился (слот 1
освободился), а через минуту в тот же слот подключили другой геймпад. Если
где-то в коде остался старый номер «слот 1», он начнёт читать **чужой**
геймпад. Номер поколения меняется при каждом переподключении, и старый handle
(«слот 1, поколение 3») перестаёт совпадать с новым («слот 1, поколение 4») —
ошибку видно сразу. **Сертификация** — проверка, которую игра проходит у
владельца консоли (Sony, Microsoft, Nintendo) перед выпуском.

> **Коротко:** платформенный слой переводит коды ОС в собственное перечисление
> `Control` через таблицы-данные; неизвестные коды тихо считаются. Для
> управления берут физическое положение клавиши (scancode), кнопки геймпада
> называют по положению (SOUTH/EAST), а не по нарисованной букве.

## 2. Опрос или события

### 2.1. Две модели

Есть две модели получения ввода.

**Опрос (polling):** раз в кадр спрашиваем «каково состояние устройства сейчас?».
XInput, большинство консольных API, `GetAsyncKeyState`. Просто, но между двумя
опросами может случиться что угодно, и мы этого не увидим.

**События (events):** ОС присылает очередь «нажато», «отпущено», «сдвинулось».
Ничего не теряется, порядок сохраняется, у событий есть временная метка.

Аналогия:

* **Опрос** — вы раз в час выглядываете в окно и смотрите, стоит ли во дворе
  машина. Если машина приехала и уехала за 10 минут между двумя взглядами, вы
  о ней не узнаете.
* **События** — консьерж записывает в журнал «14:05 машина приехала, 14:15
  уехала». Раз в час вы читаете журнал целиком и знаете всё.

Игровой код при этом почти всегда хочет **состояние на кадр**, а не поток событий:
системе движения нужно «держит ли игрок вправо», а не «в 12:00:01.337 пришёл
KEY_DOWN». Поэтому стандартная схема — гибрид:

```
начало кадра:
    keyboard.begin_frame()          // сбросить защёлки фронтов
    while (platform.poll_event(&e)) // выкачать ВСЕ события ОС
        input.apply(e)              // обновить состояние + защёлкнуть фронты
    gamepads.poll()                 // опросные устройства — снимком
    actions = action_map.resolve(input)
затем фиксированные шаги симуляции читают actions
```

Разберём построчно:

1. `keyboard.begin_frame()` — начинаем новый кадр: забываем, что было
   «нажато в прошлом кадре» (что такое «защёлки фронтов», объясним в разделе 3).
2. `while (platform.poll_event(&e))` — забираем из очереди ОС **все** события,
   накопившиеся с прошлого кадра, по одному, пока очередь не опустеет.
   (Да, функция называется `poll_event` — «опросить очередь», но читает она
   именно поток событий.)
3. `input.apply(e)` — каждое событие меняет наш журнал состояния.
4. `gamepads.poll()` — геймпады, которые умеют только опрос, читаем снимком.
5. `action_map.resolve(input)` — переводим кнопки в действия (раздел 5).
6. Дальше симуляция читает **готовые** действия и ничего не спрашивает у ОС.

Важно: события выкачиваются **все** и **в начале кадра**. Опрашивать ввод
«когда понадобится» из глубины геймплейного кода — значит получить разное
состояние в разных системах одного кадра.

Пример, как это ломается: система движения в начале кадра спросила ОС «нажат
ли пробел?» — нет. Через 2 мс система анимации спросила то же самое — уже да
(игрок как раз нажал). В итоге анимация прыжка играет, а персонаж не прыгнул.
Если же ввод собран один раз в начале кадра, все системы видят **одну и ту же**
картину.

> **Коротко:** события ничего не теряют, а игре удобно состояние. Поэтому в
> начале кадра выкачиваем все события, строим из них состояние, и весь кадр
> работаем только с ним.

### 2.2. Ввод и фиксированный шаг

Глава 01: симуляция идёт фиксированными шагами, их может быть 0, 1 или несколько
за кадр рендера. Если на кадре было 2 шага, а «нажатие прыжка» — защёлкнутый
фронт этого кадра, то кто его увидит? Варианты:

* фронт «съедается» первым шагом, второй его уже не видит (обычно правильно:
  одно нажатие — один прыжок);
* при 0 шагах за кадр (рендер быстрее симуляции) фронт нельзя сбрасывать —
  иначе нажатие пропадёт. Поэтому защёлки сбрасывают не в начале кадра рендера,
  а после того, как их **потребил** шаг симуляции.

Напомним, откуда берётся 0 или 2 шага. Пусть симуляция идёт 60 тиков в секунду
(шаг 16,7 мс), а рендер — как получится:

| кадр рендера | длился | накоплено времени | тиков в этом кадре |
|---|---|---|---|
| 1 | 7 мс (144 FPS) | 7 | 0 |
| 2 | 7 мс | 14 | 0 |
| 3 | 7 мс | 21 → тик, остаток 4,3 | 1 |
| 4 | 30 мс (лаг) | 34,3 → 2 тика, остаток 0,9 | 2 |

Если игрок нажал прыжок в кадре 1, а мы сбросили «нажато» в начале кадра 2 —
прыжок потерян: в кадрах 1 и 2 не было ни одного тика, который мог бы его
прочитать. Поэтому «нажато» должно дожить до кадра 3, где тик его потребит.
А в кадре 4 два тика: первый увидит нажатие и прыгнет, второй уже не должен
(иначе двойной прыжок от одного нажатия).

Это первая причина, по которой ввод живёт ближе к симуляции, чем к рендеру. Вторая
— сетевые игры и реплеи (раздел 8): симуляции нужен ввод, привязанный к номеру
**тика**, а не кадра.

> **Коротко:** «нажато» сбрасывают не по таймеру кадра, а когда его
> **прочитал** тик симуляции. Иначе при быстром рендере нажатия теряются, а при
> медленном — срабатывают дважды.

### 2.3. Задержка ввода

**Задержка ввода (input lag)** — время от нажатия кнопки до момента, когда
результат появился на экране.

Каждый слой добавляет задержку: опрос устройства (USB 125–1000 Гц), очередь ОС,
момент выкачивания в кадре, шаг симуляции, рендер, буферизация кадров в
драйвере (тройная буферизация), развёртка монитора. Итог в 50–100 мс — обычное
дело. Движковые меры: выкачивать ввод как можно позже перед симуляцией, не
держать лишних кадров в очереди GPU (NVIDIA Reflex, AMD Anti-Lag по сути
делают именно это), для курсора/камеры — «late latching» (перечитывать мышь
прямо перед отправкой кадра на GPU). Файтинги отдельно публикуют «input lag» в
кадрах — игроки это измеряют.

Примерная «смета» задержки при 60 FPS (числа порядка величины, не точные):

| этап | примерно |
|---|---|
| USB-опрос геймпада (125 Гц) | до 8 мс |
| ожидание начала следующего кадра | до 16 мс |
| симуляция + рендер кадра | 16 мс |
| очередь кадров в драйвере (2 кадра) | 33 мс |
| вывод на экран монитором | 5–15 мс |
| **итого** | **~60–90 мс** |

Видно, что сама «обработка ввода» почти ничего не стоит — время теряется на
ожиданиях. **Тройная буферизация** — драйвер держит в очереди до трёх готовых
кадров, чтобы GPU не простаивал; цена — каждый кадр в очереди добавляет 16 мс
задержки. **Развёртка** — монитор рисует картинку построчно сверху вниз, это
тоже занимает время.

> **Коротко:** задержка складывается из многих мелких ожиданий. Движок
> уменьшает её, читая ввод как можно позже и не копя кадры в очереди GPU.

## 3. Фронты: pressed/held/released

### 3.1. Три вопроса к клавише

Геймплею нужны три вопроса:

| запрос | смысл | пример |
|---|---|---|
| `held(k)` | клавиша удерживается (уровень) | бег, прицеливание |
| `pressed(k)` | нажата в этом кадре (передний фронт) | прыжок, выстрел |
| `released(k)` | отпущена в этом кадре (задний фронт) | отпустить натянутый лук |

Слова «уровень» и «фронт» пришли из электроники. Нарисуем сигнал клавиши во
времени: внизу — отпущена, вверху — нажата.

```
              передний фронт      задний фронт
                    ↓                  ↓
 нажата    ........./‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\.........
 отпущена  ‾‾‾‾‾‾‾‾‾                    ‾‾‾‾‾‾‾‾‾  (низ)
                    |<--- уровень: held --->|
```

* **Уровень** — «в каком состоянии сигнал сейчас». Отвечает на вопрос «держит
  ли игрок кнопку?» — `held`.
* **Передний фронт** (rising edge) — момент перехода «отпущена → нажата».
  Это `pressed`. Случается **один раз** на нажатие, сколько бы игрок ни держал.
* **Задний фронт** (falling edge) — переход «нажата → отпущена». Это
  `released`.

Почему прыжок вешают на фронт, а не на уровень? Если прыгать, «пока нажат
пробел», персонаж будет прыгать снова и снова, пока игрок держит клавишу. А
игрок хотел **один** прыжок на **одно** нажатие.

#### Напоминание: битовые маски

Состояние клавиш удобно хранить **битовой маской**: одно число `ulong` (64 бита),
где бит номер `k` равен 1, если клавиша номер `k` нажата. Нам понадобятся
четыре операции:

| операция | запись | что делает |
|---|---|---|
| бит клавиши | `1ul << k` | число, где включён только бит `k` |
| поставить бит | `m \|= b` | включить бит, остальные не трогать |
| сбросить бит | `m &= ~b` | выключить бит, остальные не трогать |
| проверить бит | `(m & b) != 0` | включён ли бит |

Пример на клавишах `A=0, D=1, W=2, S=3, SPACE=4`:

```c3
import std::io;

enum Key : char { A, D, W, S, SPACE, ESC }

macro ulong bit(Key k) => 1ul << k.ordinal;

fn void main()
{
    ulong down = 0;                      // все клавиши отпущены
    down |= bit(W);                      // нажали W   -> поставили бит 2
    down |= bit(SPACE);                  // нажали SPACE -> бит 4
    io::printfn("down = %b", down);      // 10100
    bool w_held = (down & bit(W)) != 0;  // проверка одного бита
    io::printfn("W held: %s", w_held);
    down &= ~bit(W);                     // отпустили W -> сбросили бит 2
    io::printfn("down = %b", down);      // 10000
    io::printfn("W held: %s", (down & bit(W)) != 0);
}
```

Программа печатает `down = 10100`, `W held: true`, `down = 10000`,
`W held: false`. Читаем двоичное число справа налево: бит 0 (A) = 0, бит 1 (D)
= 0, бит 2 (W) = 1, бит 3 (S) = 0, бит 4 (SPACE) = 1. `k.ordinal` — порядковый
номер значения в `enum` (A — 0, D — 1, ...), `%b` — печать в двоичном виде.

Ещё одна полезная запись: `a & ~b` — «биты, которые есть в `a`, но нет в `b`».
Именно она даёт наивные фронты ниже.

> **Коротко:** `held` — состояние «сейчас», `pressed`/`released` — моменты
> перехода. Всё это удобно хранить битами в `ulong`.

### 3.2. Наивный способ и где он ломается

Наивная реализация хранит снимок прошлого кадра:

```c3
pressed  = down & ~prev_down;
released = ~down & prev_down;
```

Перевод на русский: «нажато в этом кадре = нажато сейчас И НЕ было нажато в
прошлом кадре». «Отпущено = не нажато сейчас И было нажато раньше».

Пример, где всё хорошо (клавиша W, бит 2; показываем только этот бит):

| кадр | prev_down | down | pressed = down & ~prev | released = ~down & prev |
|---|---|---|---|---|
| 0 | 0 | 1 | 1 | 0 |
| 1 | 1 | 1 | 0 | 0 |
| 2 | 1 | 0 | 0 | 1 |

Сравните с временной диаграммой быстрого тапа, уложившегося между двумя кадрами:

```
кадр:        N               N+1
             |               |
клавиша:  ___|___/‾‾‾\_______|_______
                  down  up
снимки:   down=0           down=0     => pressed = 0 & ~0 = 0. Прыжка нет.
```

**Тап** — короткое нажатие «нажал-отпустил». Снимок смотрит только на
состояние **в моменты кадров**, а всё, что случилось между ними, для него
невидимо — как машина во дворе между двумя взглядами в окно.

На 60 FPS тап короче 16 мс редкость, но на 30 FPS, при подтормаживании,
загрузке или на сенсорном экране — обычное дело. То же с «отпустил и сразу нажал
снова» — снимок покажет `held` без единого фронта, хотя игрок явно хотел второе
действие.

Второй случай тоже по шагам. Игрок держит W, между кадрами отпускает и сразу
снова нажимает (например, «двойной тап вперёд» для рывка):

| момент | событие | down |
|---|---|---|
| кадр N | — | 1 |
| между кадрами | W up | 0 |
| между кадрами | W down | 1 |
| кадр N+1 | — | 1 |

Снимки: `prev_down = 1`, `down = 1` → `pressed = 0`, `released = 0`. Наивный
способ считает, что игрок просто держал клавишу. Второе нажатие потеряно.

> **Коротко:** сравнение двух снимков видит только то, что было **на границах
> кадров**. Короткие нажатия и быстрые перенажатия между кадрами пропадают.

### 3.3. Защёлкивание фронтов

Правильно — **защёлкивать** фронты в обработчике событий:

```c3
fn void Keyboard.on_event(&self, Key k, bool is_down)
{
    ulong b = bit(k);
    if (is_down == ((self.down & b) != 0)) return;   // автоповтор / лишний up
    if (is_down) { self.down |= b; self.pressed_bits |= b; }
    else         { self.down &= ~b; self.released_bits |= b; }
}
```

и очищать защёлки после того, как их потребили. Тогда тап даст в одном кадре и
`pressed`, и `released`, а `held` будет ложным — и это правильный ответ.

Построчно:

1. `ulong b = bit(k);` — маска с одним битом нашей клавиши.
2. `if (is_down == ((self.down & b) != 0)) return;` — если событие говорит
   «нажата», а клавиша **уже** нажата (это автоповтор), или говорит
   «отпущена», а она **уже** отпущена (лишнее событие, например после потери
   фокуса) — ничего не меняется, выходим.
3. Событие «нажата»: ставим бит в `down` (теперь держим) **и** в
   `pressed_bits` (за этот кадр было нажатие).
4. Событие «отпущена»: снимаем бит в `down` **и** ставим в `released_bits`.

Главное слово — **защёлка** (latch). Как защёлка на двери: однажды
захлопнувшись, она остаётся закрытой, пока её специально не откроют. Бит в
`pressed_bits` ставится при нажатии и **не снимается** при отпускании — его
очищает только `begin_frame` (или «потребивший» тик, см. раздел 2.2). Поэтому
нажатие, которое длилось 3 мс, всё равно «доживёт» до чтения.

Трассировка быстрого тапа SPACE (бит 4) в одном кадре:

| шаг | что произошло | down | pressed_bits | released_bits |
|---|---|---|---|---|
| begin_frame | маски очищены | 0 | 0 | 0 |
| SPACE down | бит в down и pressed | 1 | 1 | 0 |
| SPACE up | бит снят с down, поставлен в released | 0 | 1 | 1 |
| итог кадра | held=нет, pressed=**да**, released=да | | | |

Прыжок состоялся. А перенажатие W (держали, отпустили, нажали) даст в кадре
`held=да, pressed=да, released=да` — видно и отпускание, и новое нажатие.

Детали, о которых стоит помнить:

* **Автоповтор** ОС присылает повторные «down». Для текстового поля это
  полезно, для геймплея — нет: повтор не должен быть новым нажатием.
* **Потеря фокуса.** Игрок нажал W и сделал Alt+Tab — «up» придёт в другое
  окно. Без обработки персонаж бежит вперёд вечно. При потере фокуса окно
  обязано «отпустить» всё (сгенерировать released для всех down).
* **Битовые маски.** 64 клавиши — один `ulong`; полная клавиатура — `ulong[2]`
  или `ulong[4]`. Весь снимок ввода — несколько машинных слов: копировать,
  сравнивать, писать в реплей и пересылать по сети дёшево. Это лучше, чем
  `bool[256]` или, тем более, хеш-таблица.
* **Длительность удержания** (`held_frames`) — полезное расширение для
  «заряжаемых» действий и для различения тапа и удержания. Её тоже считают по
  тикам симуляции, а не по времени стены.

**Фокус** окна — какое окно сейчас получает ввод с клавиатуры. **Время стены**
(wall clock) — обычное «время на часах», в отличие от времени симуляции,
которое идёт ровными тиками. **Машинное слово** — число, с которым процессор
работает за одну операцию (на x86-64 — 64 бита).

В `e1001` вы реализуете эту схему и увидите в выводе, где наивная версия теряет
нажатия.

**Частые ошибки**

> * Сбрасывать `pressed_bits` при событии «up» — тогда тап снова теряется.
>   Защёлки снимает только начало кадра (или потребитель), не события.
> * Забыть проверку на автоповтор — повторное «down» для уже нажатой клавиши
>   становится новым `pressed`, и персонаж стреляет очередью от одного нажатия.
> * Вычислять `held` по `pressed_bits` — после тапа «держит» окажется
>   истиной, хотя клавиша уже отпущена. `held` берётся только из `down`.
> * Забыть обновить `prev_down` для наивного способа (в упражнении он нужен
>   для сравнения в выводе).

> **Коротко:** обработчик события ставит бит «было нажатие/отпускание» и не
> снимает его до начала следующего кадра. Повторное «down» для уже нажатой
> клавиши — автоповтор, его игнорируют.

## 4. Аналоговые оси и мёртвые зоны

### 4.1. Что такое ось

Кнопка — это «да/нет». **Аналоговая ось** — это число из диапазона: насколько
сильно отклонён стик или вдавлен триггер. **Триггер** — «курок» под
указательным пальцем на геймпаде (газ в гонках, выстрел в шутерах).
**Стик** — грибок под большим пальцем, у него две оси: X (влево-вправо) и
Y (вверх-вниз).

Стик геймпада отдаёт `short` от -32768 до 32767 по каждой оси, триггер — от 0 до
32767 (или 0–255 в XInput). Механический стик **никогда** не возвращается точно в
0: шум ±1000–3000 у нового геймпада и заметно больше у изношенного («stick drift»).
Отсюда мёртвая зона (deadzone).

**Шум** — мелкие случайные колебания значения, которых игрок не делал.
**Stick drift** («дрейф стика») — стик в покое показывает заметное
отклонение, и персонаж или камера сами медленно ползут.

**Мёртвая зона** — область около нуля, внутри которой любые значения
считаются нулём. Аналогия: весы на кухне показывают «0 г», пока на них не
положат хотя бы 2 грамма, — иначе цифры прыгали бы от сквозняка.

### 4.2. Осевая зона

Простейший вариант — обнулить малые значения: `|v| < dz → 0`. Плохо: на выходе из
зоны значение скачком прыгает с 0 до `dz` (25% хода), точное прицеливание на малых
отклонениях невозможно. Поэтому значение **перемасштабируют**:

```
            0,                                  |v| <= dz
out(v) = {
            sign(v) * (|v| - dz) / (max - dz),  иначе (с ограничением 1.0)
```

```
out
1.0 |                       ____
    |                   ___/
    |               ___/
    |           ___/
0.0 |__________/
    +---------+-------------+---> |v|
    0        dz            max
```

Обозначения: `|v|` — модуль (значение без знака: `|-5| = 5`), `sign(v)` — знак
(+1 для положительных, -1 для отрицательных), `max` — максимальное сырое
значение (32767).

Идея формулы простыми словами: «отрезаем» от хода стика первые `dz` единиц, а
оставшийся отрезок от `dz` до `max` растягиваем так, чтобы он занимал весь
диапазон от 0 до 1. Как если бы у линейки отпилили первые 2 см, а оставшуюся
часть заново разметили от нуля.

Посмотрим, почему без перемасштабирования плохо. Пусть `dz = 8000`, без
перемасштабирования выход — просто `v / 32767`:

| сырое v | просто обнулить: v/32767 | с перемасштабированием |
|---|---|---|
| 7999 | 0 | 0 |
| 8000 | **0,244** — скачок! | 0 |
| 10000 | 0,305 | 0,081 |
| 20383 | 0,622 | 0,500 |
| 32767 | 1,000 | 1,000 |

Без перемасштабирования стик, едва выйдя из зоны, сразу даёт четверть скорости:
медленно подкрасться или чуть-чуть довести прицел невозможно. С
перемасштабированием выход растёт плавно от нуля.

**В целых числах (как в `e1002`).** Там выход — не дробь 0..1, а целое
-1000..1000 (см. 4.4), то есть формула умножается на 1000:
`(|v| - dz) * 1000 / (32767 - dz)`. Посчитаем вручную для `v = 20383`,
`dz = 8000`:

| шаг | вычисление | результат |
|---|---|---|
| 1 | `|v|` | 20383 |
| 2 | `|v| - dz` | 12383 |
| 3 | `* 1000` | 12 383 000 |
| 4 | `max - dz` = 32767 - 8000 | 24767 |
| 5 | 12 383 000 / 24767 (целочисленно) | **499** (точно было бы 499,98) |
| 6 | знак v положительный | **499** |

Целочисленное деление отбрасывает дробную часть, поэтому 499, а не 500. Это не
ошибка: главное — на любом компьютере получится **ровно 499**.

Ещё несколько точек той же функции (`dz = 8000`):

| v | 8000 | 8500 | 10000 | 16000 | 24000 | 32767 |
|---|---|---|---|---|---|---|
| out | 0 | 20 | 80 | 323 | 646 | 1000 |

Осторожно с -32768: модуль не помещается в `short`, а `32768 > 32767`, поэтому
нужен `int` и ограничение сверху.

Разберём это подробнее, потому что ловушка неочевидная. Диапазон `short`
несимметричен: отрицательных значений на одно больше (-32768..32767). Для
`v = -32768`: `|v| = 32768`, `(32768 - 8000) * 1000 / 24767 = 1000,04` → после
целочисленного деления 1000 — тут повезло, но при другом `dz` или другой
формуле результат может выйти больше 1000. Поэтому выход **ограничивают**
(clamp): «если больше 1000 — сделай 1000». А считать модуль в `short` нельзя
вовсе: 32768 в него не влезает.

**Частые ошибки**

> * Сравнение `<` вместо `<=` на границе зоны: проверьте, что ровно `dz`
>   даёт 0 (в упражнении это проверяется assert-ом).
> * Деление до умножения: `(|v| - dz) / (max - dz) * 1000` в целых числах
>   почти всегда даёт 0, ведь `12383 / 24767 = 0`. Сначала умножаем, потом
>   делим.
> * Потерянный знак: модуль взяли, а знак обратно не вернули — стик влево
>   двигает вправо.
> * Забытый clamp для -32768.

> **Коротко:** мёртвая зона обнуляет шум около нуля, а перемасштабирование
> делает так, чтобы сразу за зоной выход начинался с нуля и плавно рос до
> максимума.

### 4.3. Радиальная зона

Если применить осевую зону к x и y стика **по отдельности**, зона получится
крестом: при движении почти вдоль оси вторая компонента обнуляется, и стик
«прилипает» к восьми направлениям. Это одна из самых частых жалоб на
самописный ввод в шутерах. Правильно — считать зону по длине вектора:

```
           y                                    y
           |                                    |
      +----+----+   осевая (крест):        .----+----.   радиальная (круг):
      |    |####|   в заштрихованной       /    |    \   внутри круга — 0,
  ----+####+####+-- полосе вторая ось     |   (###)   |  снаружи — направление
      |####|    |   обнуляется             \    |    /   сохраняется, длина
      +----+----+                           '---+---'    плавно растёт от 0
```

Пример «прилипания». Игрок ведёт стик немного вверх от направления «вправо»:
`x = 30000`, `y = 6000`, `dz = 8000`. Осевая зона по отдельности:
`x → 888`, `y → 0` (6000 < 8000). Персонаж бежит **строго** вправо, хотя игрок
явно отклонил стик вверх. Чтобы сдвинуть направление хоть чуть-чуть, игроку
приходится отклонить y больше чем на 8000 — направление «прыгает» рывком.

Радиальная зона смотрит не на каждую ось отдельно, а на **длину вектора** —
насколько далеко стик ушёл от центра в любую сторону. Длину считаем по
теореме Пифагора: стик сдвинут на `x` вправо и `y` вверх — это катеты
прямоугольного треугольника, а расстояние от центра — гипотенуза.

```
       y
       |      * (x, y)
       |     /|
       |  m / |  y
       |   /  |
       |  /   |
       +-------------- x
          x
   m = sqrt(x² + y²)
```

```
m = sqrt(x² + y²)
m <= dz          -> (0, 0)
иначе nm = min(1, (m - dz) / (max - dz)),  (x, y) * nm / m
```

Что делает каждая строка:

1. `m` — длина (насколько отклонён стик).
2. Если длина внутри круга радиуса `dz` — выход ноль.
3. Иначе новая длина `nm` считается **той же формулой**, что в осевой зоне,
   только от длины: отрезали `dz`, растянули остаток, ограничили единицей.
4. `(x, y) * nm / m` — сохраняем **направление**, меняем только **длину**.
   Деление на `m` делает вектор длиной 1 (направление «в чистом виде»),
   умножение на `nm` — придаёт ему нужную длину.

Трассировка в целых числах (`dz = 8000`, выход в промилле, `max - dz = 24767`):

| вход (x, y) | m | m <= dz? | nm | выход (x', y') |
|---|---|---|---|---|
| (5000, 5000) | 7071 | да | — | (0, 0) |
| (30000, 0) | 30000 | нет | 22000·1000/24767 = 888 | (30000·888/30000, 0) = (888, 0) |
| (-23170, 23170) | 32767 | нет | 1000 | (-707, 707) |
| (32767, 32767) | 46339 | нет | 1000 (ограничили) | (707, 707) |

Обратите внимание на первую строку: каждая ось по отдельности (5000) меньше
`dz`, и длина (7071) тоже меньше — ноль в обоих подходах. А последняя строка
показывает, зачем `min(1, ...)`: в углу квадрата длина вектора 46339 — больше,
чем 32767, и без ограничения стик по диагонали давал бы скорость 1,4 от
максимальной («диагональный бег быстрее» — известный баг старых игр).

Число 707 — это 1000 · cos 45° ≈ 1000 · 0,707: вектор длины 1000 под углом 45°.

Корень в упражнении целочисленный (`isqrt` уже написан): он возвращает
наибольшее целое, квадрат которого не больше числа, — например,
`isqrt(50 000 000) = 7071`, потому что `7071² = 49 999 041`, а
`7072² = 50 013 184`. Чтобы `x*x + y*y` не переполнился (`32767² · 2` больше,
чем помещается в `int`), считают в `long`.

Профессиональные реализации добавляют ещё **внешнюю** мёртвую зону (стик физически
не доходит до 32767 по диагонали — без неё «полный ход» недостижим), кривые
отклика (квадратичная/кубическая — точность на малых отклонениях), раздельные
настройки для горизонтали и вертикали камеры и, иногда, «гибридную»
радиально-осевую зону. Хороший обзор — статья Josh Sutphin «Doing Thumbstick Dead
Zones Right» и разбор камеры в GDC-докладах по Destiny и Halo.

**Кривая отклика** — дополнительное преобразование выхода, например
возведение в квадрат: `0,5 → 0,25`. Малые отклонения дают ещё меньший
результат (точнее прицеливаться), а полное отклонение по-прежнему даёт 1.

**Частые ошибки**

> * Применить осевую зону к x и y стика по отдельности — получить «крест».
> * Масштабировать `x` и `y` на `nm` без деления на `m` — направление
>   сохранится, но длина будет неправильной.
> * Переполнение `x * x` в `int` (32767² ≈ 1,07 млрд, сумма двух — больше
>   `int::max` ≈ 2,15 млрд).
> * Порядок операций в целых: `x * nm / m`, а не `x / m * nm` (иначе
>   `30000 / 30000 * 888` ещё работает, но `23170 / 32767 * 1000 = 0`).

> **Коротко:** для стика зону считают по длине вектора (круг), а не по
> каждой оси (крест). Направление сохраняют, длину перемасштабируют и
> ограничивают единицей.

### 4.4. Фиксированная точка

В `e1002` оси хранятся целыми в промилле (-1000..1000), корень — целочисленный.
Зачем, если есть `float`? Ради детерминизма: значение оси уходит в реплей и в
сетевой пакет, и симуляция на другом компьютере обязана получить **те же биты**.
Квантование ввода на входе в симуляцию — стандартная практика сетевых движков
(Overwatch, Rocket League квантуют стики до 8–16 бит).

**Фиксированная точка** — способ хранить дробные числа в целых: договариваемся,
что целое 1000 означает 1,0, а 499 — 0,499. Как цены в копейках: 12 345 копеек
— это 123,45 рубля, но складывать и сравнивать копейки можно без всяких
дробей. **Промилле** — «тысячные доли» (как проценты, но на тысячу).

**Квантование** — округление непрерывной величины до одного из конечного
набора значений («ступенек»). У нас стик может принимать только 2001 значение
(-1000..1000).

Почему `float` здесь опасен: результат `sqrt` или деления с плавающей точкой
может отличаться в последнем бите на разных процессорах, при разных флагах
компилятора или разном порядке операций. Для картинки это незаметно, а для
реплея — катастрофа: разница в одном бите через тысячу тиков вырастает в
«персонаж стоит в другом месте». Целые числа считаются одинаково везде.

> **Коротко:** оси хранят как целые «тысячные доли», чтобы любые две машины
> получали из одного и того же ввода одни и те же биты.

### 4.5. Последнее активное устройство

UI показывает подсказки «Нажмите [A]» или «Нажмите [Space]» в зависимости от
того, чем пользуется игрок. Ловушка: если любое событие оси переключает
устройство на геймпад, то лежащий на столе геймпад с дрейфующим стиком непрерывно
перехватывает подсказки. Переключаться нужно только по значимому вводу — после
мёртвой зоны. Мышь — аналогично: дрожание на 1 пиксель не повод.

Сценарий: игрок играет на клавиатуре, геймпад лежит рядом. Стик геймпада шумит
и шлёт события `PAD_AXIS` со значениями 1500, -1200, 900... Если на каждое
такое событие писать `last_device = GAMEPAD`, подсказки на экране будут
мигать «[Space]» ↔ «[A]» несколько раз в секунду. Правильно: сначала прогнать
значение через мёртвую зону, и только если результат **не ноль** — считать, что
игрок взял геймпад.

### 4.6. Мышь

Мышь — не абсолютная ось, а **дельты**. Их суммируют за кадр (за кадр приходит
много событий движения) и обнуляют в начале следующего. Для камеры нужны сырые
дельты (Raw Input на Windows, `EV_REL` на Linux), а не позиция курсора ОС: курсор
упирается в край экрана и проходит через «ускорение указателя». Чувствительность
мыши ни в коем случае не умножают на `dt` — дельта и так уже «за кадр»; это
классическая ошибка, из-за которой чувствительность зависит от FPS.

**Абсолютная** величина — «где находится» (стик отклонён на 0,5). **Дельта**
— «на сколько сдвинулось с прошлого раза» (мышь сдвинулась на 3 пикселя).
**dt** — длительность кадра в секундах.

Пример суммирования: за кадр пришли три события `MOUSE_MOVE`:

| событие | ось | значение | mouse_dx | mouse_dy |
|---|---|---|---|---|
| начало кадра | — | — | 0 | 0 |
| 1 | x | +3 | 3 | 0 |
| 2 | x | +4 | 7 | 0 |
| 3 | y | -2 | 7 | -2 |

Если вместо `+=` написать `=`, останется только последнее событие по каждой
оси, и мышь станет «вязкой».

Почему нельзя умножать на `dt`. Игрок повернул мышь на 100 пикселей за
1 секунду. При 100 FPS это 100 кадров по 1 пикселю, при 50 FPS — 50 кадров по
2 пикселя. Суммарно — 100 пикселей в обоих случаях, камера повернётся одинаково.
А теперь умножим на `dt`:

| FPS | дельта за кадр | dt | дельта · dt | кадров | итого за секунду |
|---|---|---|---|---|---|
| 100 | 1 | 0,01 | 0,01 | 100 | 1,0 |
| 50 | 2 | 0,02 | 0,04 | 50 | 2,0 |

При 50 FPS камера поворачивается **вдвое сильнее** от того же движения руки.
Стик — другое дело: он показывает не «сколько сдвинулось», а «как сильно
отклонён», то есть **скорость**, и её на `dt` умножать как раз нужно.

> **Коротко:** мышь даёт приращения — их складывают за кадр и не умножают на
> `dt`. Стик даёт скорость — её на `dt` умножают. Устройство считается
> «активным» только по значимому вводу после мёртвой зоны.

## 5. Действия вместо клавиш

### 5.1. Зачем нужен слой действий

Геймплейный код, который спрашивает `keyboard.pressed(KEY_SPACE)`, приговорён:
переназначение клавиш невозможно, геймпад надо поддерживать отдельным `||` в
каждом месте, а «пробел» в меню и в игре означает разное. Решение — уровень
**действий** (actions):

```
  Control (физика)           Binding                Action (смысл)
  KEY_SPACE   ─────────────┐
  PAD_SOUTH   ─────────────┴──>  JUMP      (кнопка: pressed/held/released)
  KEY_A, KEY_D, PAD_LX ────────>  MOVE_X    (ось: -1..1)
  MOUSE_DX, PAD_RX ────────────>  LOOK_X    (ось, разные множители!)
```

Три слова с этой схемы:

* **Control** — физический орган управления: клавиша, кнопка, ось.
* **Action (действие)** — намерение игрока: «прыгнуть», «идти», «смотреть».
* **Binding (привязка)** — запись «этот control запускает это действие».

Аналогия: action — это **пункт меню в ресторане** («борщ»), control — **как
вы его заказали** (сказали официанту, ткнули пальцем в меню, заказали через
приложение). Кухне (геймплею) неважно, как сделан заказ, — важно, что нужен
борщ.

Сравните код до и после:

```
// без действий — в каждом месте игры:
if (kb.pressed(KEY_SPACE) || pad.pressed(PAD_SOUTH) || kb.pressed(KEY_W_IF_REBOUND...)) jump();

// с действиями:
if (actions.pressed(JUMP)) jump();
```

Действия бывают **кнопочные** (bool + фронты) и **осевые** (число; иногда 2D).
Привязка может превращать одно в другое: две клавиши дают ось (-1/0/+1), ось
с порогом даёт кнопку (триггер > 0.5 → FIRE).

Примеры превращений:

| controls | действие | правило |
|---|---|---|
| A, D | MOVE_X (ось) | D нажата → +1, A нажата → -1, обе/ни одной → 0 |
| триггер RT (0..1) | FIRE (кнопка) | RT > 0,5 → нажато |
| стик LX и клавиши A/D | MOVE_X | берём то, что по модулю больше |

Последняя строка — ровно функция `move_x` из `e1002`: клавиатура даёт
`(D - A) * 1000`, стик даёт `stick_x`, побеждает больший по модулю. Пример:
нажата A (клавиатура: -1000) и стик чуть влево (после зоны: -161). Модули 1000
и 161 — побеждает клавиатура, `move_x = -1000`.

### 5.2. Как это устроено в реальных движках

Так устроено почти всё:

* **Unreal Engine 4** — Action/Axis Mappings в `DefaultInput.ini`.
* **Unreal Engine 5 Enhanced Input** — `InputAction` (тип значения: bool, axis1D,
  axis2D, axis3D), `InputMappingContext` с приоритетами, **модификаторы**
  (deadzone, negate, swizzle, scalar) и **триггеры** (pressed, released, hold,
  tap, chorded action, combo) на каждой привязке. Хороший образец «декларативного
  ввода».
* **Unity Input System** — `InputActionAsset` → Action Maps → Actions →
  Bindings с Composite (WASD → Vector2), Interactions (Hold, Tap, MultiTap) и
  Processors (deadzone, invert, scale), Control Schemes для групп устройств.
* **Godot** — `InputMap` с именованными действиями, `Input.is_action_just_pressed`,
  `get_vector()` для 2D-осей с радиальной зоной.

Пояснения к терминам из списка:

* **Модификатор** — преобразование значения на пути от control к действию:
  мёртвая зона, смена знака (negate — «инвертировать ось»), перестановка осей
  (swizzle), умножение на число (scalar).
* **Триггер** в UE5 — правило «когда считать действие сработавшим»: при
  нажатии, при отпускании, если держали дольше N секунд (hold), если нажали
  коротко (tap). Не путать с курком геймпада.
* **Chorded action** («аккорд») — действие срабатывает, только если зажата
  ещё одна кнопка (как Ctrl+C).
* **Декларативный** ввод — вы **описываете** в данных, что хотите («JUMP =
  SPACE или SOUTH, при нажатии»), а не пишете код, как это проверять.
* **Composite** в Unity — несколько кнопок, собранных в одно значение (4
  клавиши WASD → двумерный вектор).

Общий архитектурный вывод: action map — это **данные**. Привязки загружаются из
файла настроек, правятся в меню, сохраняются для профиля игрока. Код игры знает
только перечисление действий.

> **Коротко:** геймплей спрашивает про действия (JUMP), а не про клавиши
> (SPACE). Таблица привязок control → action — это данные, которые игрок
> может менять.

### 5.3. Переназначение и конфликты

Меню переназначения — это «нажмите новую клавишу для JUMP». Подводные камни:

* **Конфликты.** Новая клавиша уже занята в том же контексте — нужно либо
  отказать, либо поменять местами (swap), либо снять старую привязку. Конфликт
  проверяется **внутри контекста**: E может быть «взаимодействовать» в игре и
  «следующая реплика» в диалоге — это не конфликт.
* **Запрещённые клавиши.** Esc (меню), PrintScreen, системные кнопки консоли.
* **Во время ожидания** «нажмите клавишу» сам ввод не должен обрабатываться
  игрой — это отдельный модальный контекст.
* **Подсказки в UI** должны строиться по текущим привязкам (обратный поиск
  action → controls для текущего устройства), а не быть захардкожены в
  текстурах.

**Модальный** — «перехватывающий всё внимание»: пока открыто модальное окно,
остальная программа ввод не получает. **Захардкожено** — вписано прямо в код
(или в картинку), а не взято из данных.

Разберём на примере таблицы привязок контекста gameplay из `e1003`:

| control | action |
|---|---|
| KEY_W | MOVE_FORWARD |
| KEY_SPACE | JUMP |
| PAD_SOUTH | JUMP |
| KEY_E | INTERACT |
| PAD_EAST | INTERACT |
| KEY_ESC | PAUSE |
| PAD_START | PAUSE |

Три попытки переназначить JUMP:

| запрос | что видим в таблице | результат |
|---|---|---|
| JUMP: SPACE → E | E уже занят действием INTERACT (другое действие) | **CONFLICT** |
| JUMP: ENTER → J | строки (ENTER, JUMP) нет | **NOT_BOUND** |
| JUMP: SPACE → J | J свободен, строка (SPACE, JUMP) есть | заменяем → (J, JUMP) |
| JUMP: SOUTH → SOUTH | SOUTH занят, но **тем же** действием JUMP | не конфликт, ок |

Последняя строка — тонкость: «занят» значит «занят **другим** действием».
Если игрок «переназначил» кнопку саму на себя, ругаться не на что.

**Частые ошибки**

> * Проверять конфликт по всем контекстам сразу — тогда E нельзя будет
>   использовать и в игре, и в диалоге.
> * Считать конфликтом привязку того же действия к тому же control.
> * Сначала заменить привязку, а потом проверять конфликт — в таблице уже
>   окажется «полуизменённое» состояние. Сначала проверки, потом изменения.

> **Коротко:** переназначение — это замена одной строки таблицы привязок.
> Перед заменой проверяем, что новый control не занят **другим** действием
> **в этом же** контексте, и что заменяемая строка вообще существует.

## 6. Контексты ввода

### 6.1. Одна клавиша — разные смыслы

Одна и та же клавиша означает разное в разных ситуациях: пробел — «прыжок» в игре,
«следующая реплика» в диалоге, «подтвердить» в меню. Наивное решение — флаги
`if (in_menu) ... else if (in_dialog) ...` во всём геймплейном коде — быстро
превращается в кашу. Правильно — **стек контекстов**:

**Контекст ввода** — набор привязок, действующий в определённой ситуации
(«в игре», «в диалоге», «в меню»). **Стек** — стопка: новый контекст кладётся
сверху, при закрытии снимается верхний. Аналогия — стопка прозрачных плёнок
на проекторе: верхняя плёнка может закрасить часть нижней (поглотить клавишу),
а может быть непрозрачной целиком (blocking) — тогда нижние вообще не видны.

```
         ┌──────────────────────────────┐
  top    │ menu      (blocking)         │  W->MENU_UP, SPACE->CONFIRM, ESC->BACK
         ├──────────────────────────────┤
         │ dialog    (non-blocking)     │  SPACE->DIALOG_NEXT, E->DIALOG_NEXT
         ├──────────────────────────────┤
  bottom │ gameplay  (non-blocking)     │  W->MOVE, SPACE->JUMP, E->INTERACT, ESC->PAUSE
         └──────────────────────────────┘

  нажато {W, SPACE}, стек = [gameplay, dialog]:
      dialog:   SPACE -> DIALOG_NEXT, SPACE поглощён
      gameplay: W -> MOVE           (SPACE уже съеден — прыжка нет)
```

Алгоритм разрешения: идём от вершины вниз, каждый сработавший control
**поглощается** и не виден нижним контекстам; blocking-контекст (модальное меню)
не пропускает вниз ничего. Это ровно то, что вы реализуете в `e1003`.

**Поглотить (consume)** — «забрать себе»: control, который сработал в верхнем
контексте, вычёркивается из списка, и нижние контексты его уже не видят.
**Blocking** («блокирующий») — контекст, ниже которого обход не идёт вовсе.

### 6.2. Трассировка по шагам

Будем вести два множества: `remaining` — нажатые controls, которые ещё никто не
забрал, и `actions` — сработавшие действия. Оба удобно хранить битовыми
масками, как в разделе 3.

**Пример 1.** Стек `[gameplay, dialog]` (dialog сверху), нажато `{W, SPACE}`.

| шаг | контекст | remaining до | сработали привязки | поглощено | actions после |
|---|---|---|---|---|---|
| 1 | dialog | {W, SPACE} | SPACE→DIALOG_NEXT | SPACE | {DIALOG_NEXT} |
| 2 | gameplay | {W} | W→MOVE_FORWARD | W | {DIALOG_NEXT, MOVE_FORWARD} |

Результат: персонаж идёт и листает диалог, но не прыгает.

**Пример 2.** Стек `[gameplay, dialog]`, нажато `{E, ESC}`.

| шаг | контекст | remaining до | сработали | поглощено | actions после |
|---|---|---|---|---|---|
| 1 | dialog | {E, ESC} | E→DIALOG_NEXT | E | {DIALOG_NEXT} |
| 2 | gameplay | {ESC} | ESC→PAUSE | ESC | {DIALOG_NEXT, PAUSE} |

**Пример 3.** Стек `[gameplay, dialog, menu]` (menu сверху, blocking), нажато
`{W, E, SPACE}`.

| шаг | контекст | remaining до | сработали | поглощено | actions после |
|---|---|---|---|---|---|
| 1 | menu | {W, E, SPACE} | W→MENU_UP, SPACE→CONFIRM | W, SPACE | {MENU_UP, CONFIRM} |
| — | menu blocking | {E} | обход **останавливается** | — | {MENU_UP, CONFIRM} |

E остался невостребованным, но вниз он не прошёл: меню блокирующее, поэтому
ни диалог, ни игра его не увидят.

### 6.3. Тонкость: поглощение «после контекста»

Внутри **одного** контекста один и тот же control может запускать несколько
действий (например, в гипотетическом контексте SPACE → JUMP и SPACE →
PLAY_SOUND). Поэтому поглощённые controls убирают из `remaining` **после**
обхода всех привязок контекста, а не сразу. Иначе первая привязка «съест»
SPACE, и вторая его уже не увидит.

```
неправильно:  для каждой привязки: сработала -> сразу удалить control
              (вторая привязка того же control в этом контексте не сработает)

правильно:    для каждой привязки: сработала -> запомнить control в consumed
              после всех привязок: remaining = remaining без consumed
```

**Частые ошибки**

> * Идти по стеку снизу вверх — тогда игра «съест» пробел раньше диалога.
>   Вершина — это последний добавленный элемент, `stack[depth - 1]`.
> * Проверять blocking до обработки привязок контекста — тогда само меню
>   ничего не получит. Сначала обработать контекст, потом решить, идти ли ниже.
> * Удалять control из `remaining` сразу при срабатывании (см. 6.3).

### 6.4. Вариации в реальных движках

Вариации в реальных движках:

* **Приоритеты вместо стека** (UE5 Enhanced Input: `AddMappingContext(ctx,
  priority)`). Стек — частный случай.
* **Consume per binding** — привязка решает, поглощать ли control (UE:
  флаг `bConsumeInput` на привязке в старой системе).
* **Маршрутизация в UI** — у UI своя иерархия фокуса (Unreal Slate/UMG «input
  routing», Godot `_gui_input` → `_unhandled_input`): событие сначала получает
  виджет под фокусом, и если он его не обработал — оно спускается в игру.
  Godot в этом смысле очень показателен: цепочка `_input` → `_gui_input` →
  `_shortcut_input` → `_unhandled_key_input` → `_unhandled_input`.
* **Несколько игроков** — у каждого свой стек контекстов и своё множество
  устройств (local multiplayer: «нажмите A, чтобы присоединиться» назначает
  геймпад игроку).

**Виджет** — элемент интерфейса: кнопка, поле ввода, список. **Маршрутизация**
— выбор, кому доставить событие.

### 6.5. Ловушка смены контекста

Ловушка смены контекста: игрок держит W, открывает меню (blocking), отпускает W,
закрывает меню. Если gameplay-контекст не получил released, персонаж бежит
дальше. Решения: при активации blocking-контекста посылать нижним «всё
отпущено»; либо, проще, нижние контексты вычисляют held из текущего состояния
устройств, а не из потока событий. Обратная проблема — нажатие ESC, закрывшее
меню, не должно в том же кадре открыть его снова: фронт поглощён контекстом,
который его обработал.

По шагам:

| кадр | что делает игрок | стек | что видит gameplay |
|---|---|---|---|
| 1 | держит W | [gameplay] | W held → идём |
| 2 | ESC | [gameplay, menu] | ничего (menu blocking) |
| 3 | отпускает W | [gameplay, menu] | ничего — released ушёл в меню! |
| 4 | ESC | [gameplay] | если held хранился «по событиям» — W всё ещё нажат |

С ESC в кадре 4 тоже ловушка: меню на ESC закрывается (BACK), стек снова
`[gameplay]`. Если тот же фронт ESC дойдёт до gameplay, там он означает PAUSE —
и меню тут же откроется снова. Поглощение фронта контекстом, который его
обработал, это предотвращает.

> **Коротко:** контексты лежат стопкой; обходим сверху вниз, сработавший
> control поглощается и не виден ниже, blocking-контекст останавливает обход.
> При смене контекста не забываем про «залипшие» клавиши.

## 7. Буферизация ввода и комбо

### 7.1. Человек не попадает в кадр

Человек не попадает в кадр. Если игра требует нажать прыжок ровно в кадр
приземления, она ощущается «глухой». Поэтому почти любой экшен использует
**буфер ввода**: нажатие хранится N кадров и срабатывает, как только действие
становится возможным.

Масштаб: кадр при 60 FPS — 16,7 мс, а время реакции человека — 150–250 мс, и
разброс между двумя «одинаковыми» нажатиями легко составляет 30–50 мс, то есть
2–3 кадра. Требовать точности «в один кадр» — всё равно что требовать от
человека хлопнуть в ладоши ровно в момент, когда секундная стрелка коснётся
двенадцати.

**Буфер ввода** — аналогия с автоответчиком: вы позвонили, когда хозяин был
занят; сообщение записалось, и как только он освободился — прослушал и
перезвонил. Нажатие «записалось» и сработало, как только персонаж смог.

* **Jump buffering** — нажал прыжок за 5 кадров до приземления, прыжок
  случится в кадр приземления.
* **Coyote time** — ещё несколько кадров после схода с края платформы прыжок
  разрешён (родственная идея, но буферизуется не ввод, а состояние).
* **Буферизация в файтингах** — следующий приём, введённый во время анимации
  восстановления предыдущего, выполнится в первый доступный кадр.

Coyote time назван в честь койота из мультфильма, который успевает сделать
пару шагов в воздухе над пропастью, прежде чем заметит это и упадёт.
**Восстановление (recovery)** — кадры после приёма, когда персонаж
«доигрывает» анимацию и не может начать новый приём.

Трассировка jump buffering (окно 5 кадров, персонаж приземляется в кадре 13):

| кадр | событие | персонаж | буфер прыжка | итог |
|---|---|---|---|---|
| 10 | нажат прыжок | в воздухе | хранит «нажато в 10» | ждём |
| 11 | — | в воздухе | 11 - 10 = 1 ≤ 5 | ждём |
| 12 | — | в воздухе | 2 ≤ 5 | ждём |
| 13 | — | приземлился | 3 ≤ 5 | **прыжок!** нажатие потрачено |

Если бы нажатие было в кадре 7, к кадру 13 оно «устарело» бы (6 > 5) — так и
задумано: игрок, нажавший прыжок за полсекунды до земли, скорее всего не хотел
прыгать после приземления.

> **Коротко:** буфер ввода хранит нажатие несколько кадров и выполняет его,
> как только это стало возможно. Это прощает человеку неточность в 2–5 кадров.

### 7.2. Нумпад-нотация

Файтинги записывают направления в нумпад-нотации (`5` — нейтраль, `6` — вперёд,
`2` — вниз), а спецприёмы — как последовательности: `236P` (хадокен), `623P`
(шорюкен), `41236K` (полукруг).

**Нумпад** — цифровой блок справа на клавиатуре. Цифры там расположены как
направления стика, если персонаж смотрит вправо:

```
   7 8 9        ↖ ↑ ↗
   4 5 6   =    ← · →        5 — стик в центре (нейтраль)
   1 2 3        ↙ ↓ ↘
```

`P` — punch (удар рукой), `K` — kick (удар ногой). `236P` читается: вниз (2),
вниз-вперёд (3), вперёд (6), затем удар — «четверть круга вперёд». Хадокен —
огненный шар из Street Fighter, шорюкен — апперкот в прыжке.

### 7.3. Буфер — кольцевой

Буфер — кольцевой буфер записей `{frame, dir, buttons}`, запись добавляется при
**изменении** состояния (удержание стика не забивает буфер).

**Кольцевой буфер** — массив фиксированного размера, в который пишут «по
кругу»: дойдя до конца, начинают затирать самые старые записи. Нам и не нужны
старые записи — приём, начатый секунду назад, уже не важен. Вот маленький
кольцевой буфер на 4 элемента:

```c3
import std::io;

const int RING = 4;

struct Ring
{
    int[RING] items;
    uint count;     // сколько всего записали за всё время
}

fn void Ring.push(&self, int v)
{
    self.items[self.count % RING] = v;   // пишем по кругу, затирая старое
    self.count++;
}

fn uint Ring.len(&self) => self.count < RING ? self.count : RING;

// i = 0 — самая свежая запись
fn int Ring.back(&self, uint i) => self.items[(self.count - 1 - i) % RING];

fn void main()
{
    Ring r;
    for (int v = 10; v <= 60; v += 10) r.push(v);   // 10 20 30 40 50 60
    for (uint i = 0; i < r.len(); i++) io::printf("%d ", r.back(i));
    io::printn();                                   // 60 50 40 30
}
```

Что происходит:

* `push` пишет в ячейку `count % RING` — остаток от деления «зацикливает»
  индекс: 0, 1, 2, 3, 0, 1, ...
* `len` — сколько записей реально лежит (не больше размера кольца).
* `back(i)` отсчитывает от самой свежей записи назад: `back(0)` — последняя,
  `back(1)` — предпоследняя.

Состояние массива после шести записей:

| count | куда записали | items[0..3] |
|---|---|---|
| 1 | 0 | 10 . . . |
| 4 | 3 | 10 20 30 40 |
| 5 | 0 | **50** 20 30 40 |
| 6 | 1 | 50 **60** 30 40 |

`back(0) = items[(6-1) % 4] = items[1] = 60`, `back(3) = items[2] = 30`.
Программа печатает `60 50 40 30`. В `e1004` буфер устроен точно так же
(методы `feed`, `len`, `back` уже написаны).

Пример наполнения буфера в `e1004` («чистый» хадокен; удар — в первом кадре
отрезка):

| кадры | стик | новая запись? |
|---|---|---|
| 0–2 | 5 | нет (начальное направление уже 5) |
| 3–4 | 2 | в кадре 3: `{3, '2', -}` |
| 5–6 | 3 | в кадре 5: `{5, '3', -}` |
| 7 | 6 + удар | `{7, '6', P}` |
| 8–9 | 6 | нет (направление не менялось) |

Десять кадров ввода — всего три записи.

### 7.4. Распознавание движений

```
кольцевой буфер (новые справа):
  frame:  3    5    7    9
  dir:    2    3    6    6
  punch:  .    .    .    P      <- распознаём ОТ НОВЫХ К СТАРЫМ:
                                   P@9, затем 6, 3, 2 в обратном порядке
```

Распознавание идёт от свежего нажатия кнопки назад во времени, ища шаги движения в
обратном порядке.

Почему от новых к старым? Потому что приём **заканчивается** ударом, и именно
удар — момент «сейчас». Мы спрашиваем: «перед этим ударом было ли 6? а перед
ним 3? а перед ним 2?» Если идти от старых к новым, пришлось бы угадывать, с
какой из старых записей «начинать», и перебирать много вариантов. От удара
назад — один проход. Аналогия: проверяя, правильно ли набран пароль, вы
смотрите на **последние** нажатые символы.

Пошаговая трассировка для буфера из 7.3 и приёма `236` (ищем 6, потом 3, потом
2). Сначала ищем свежий удар — это запись кадра 7.

| смотрим запись | dir | ищем | совпало? | осталось найти |
|---|---|---|---|---|
| кадр 7 (с ударом) | 6 | 6 | да | 3, 2 |
| кадр 5 | 3 | 3 | да | 2 |
| кадр 3 | 2 | 2 | да | — **приём найден** |

Запись с ударом смотрим тоже («включительно»): игрок мог довести стик до 6
в тот же кадр, когда нажал удар.

А вот проверка шорюкена `623` на том же буфере (ищем 3, потом 2, потом 6):

| смотрим запись | dir | ищем | совпало? |
|---|---|---|---|
| кадр 7 | 6 | 3 | нет — пропускаем (leniency) |
| кадр 5 | 3 | 3 | да |
| кадр 3 | 2 | 2 | да |
| записей больше нет | — | 6 | **провал** |

Значит, это хадокен, а не шорюкен.

Параметры, определяющие «чувство» игры:

* **Окно кнопки** (button buffer) — насколько старым может быть нажатие.
* **Зазор между шагами** — максимум кадров между соседними направлениями.
* **Общее окно движения** — от первого шага до кнопки.
* **Leniency** — допускаются посторонние направления между шагами (`2-5-3-6`
  засчитывается как `236`), иногда пропуск диагонали (`26P` = `236P` в
  некоторых играх), «шорткаты» (`6236` → шорюкен).
* **Приоритеты** — `6236P` подходит под оба приёма; таблица движений проверяется
  в порядке приоритета.
* **Зеркалирование** — если персонаж смотрит влево, зеркалим **вход**
  (4↔6, 1↔3, 7↔9), а не дублируем таблицу движений.
* **Поглощение (consume)** — нажатие и направления, использованные сработавшим
  приёмом, помечаются потраченными. Без этого (а) приём срабатывает повторно в
  следующих кадрах, пока нажатие в окне буфера, и (б) хвост одного приёма
  склеивается с началом следующего: при серии хадокенов «6» первого и «23»
  второго дают `623` — и вместо хадокена вылетает шорюкен. Тест «two fireballs»
  в `e1004` ловит именно это.
* **Negative edge** — в Street Fighter отпускание кнопки тоже считается
  нажатием для спецприёмов. Это легко добавить флагом в запись буфера.

**Leniency** — «снисходительность», допуск неточности.

#### Окна на числах

Возьмём параметры из `e1004`: окно кнопки 4 кадра, зазор между шагами 8, окно
хадокена 15 кадров.

* Удар в кадре 20, сейчас кадр 23: `23 - 20 = 3 ≤ 4` — нажатие ещё «живое».
  В кадре 25: `5 > 4` — устарело.
* Шаги «2» в кадре 0, «3» в кадре 12: зазор 12 > 8 — игрок слишком долго
  держал «вниз», это не хадокен (тест «too slow»).
* Шаги «2» в кадре 0, …, удар в кадре 20: всё движение заняло 20 кадров > 15
  — слишком медленно для хадокена, даже если каждый зазор в пределах нормы
  (тест «window 20 > 15»). Тогда сработает просто удар.

#### Зеркалирование на примере

Персонаж стоит справа и смотрит **влево**. «Вперёд» для него — влево, то есть
игрок вводит хадокен как `214` (вниз, вниз-назад-на-экране, влево). Вместо
того чтобы заводить отдельные «левые» версии приёмов, мы отражаем каждое
направление из буфера по горизонтали и сравниваем с обычной таблицей:

```
 7 8 9        9 8 7
 4 5 6   ->   6 5 4        2 1 4  ->  2 3 6   = хадокен
 1 2 3        3 2 1
```

Средний столбец (8, 5, 2) не меняется: «вверх», «нейтраль», «вниз» одинаковы
для обеих сторон. Если же персонаж смотрит **вправо**, ввод `214P` — это
«четверть круга назад», а не хадокен; в `e1004` такой ввод даёт обычный удар.

#### Приоритет на примере

Ввод `6 2 3 6 P`. Шорюкен `623`: ищем 3 → находим, 2 → находим, 6 → находим
(первую шестёрку). Хадокен `236`: 6 → 3 → 2 — тоже находится. Подходят оба.
Таблица проверяется сверху вниз, и шорюкен стоит первым — он и сработает.
Так устроено в большинстве файтингов: «более сложный» приём побеждает.

#### Поглощение на примере («two fireballs»)

Игрок дважды подряд делает хадокен:

| кадр | 0 | 1 | 2 | 3–5 | 6 | 7 | 8 | 9–10 |
|---|---|---|---|---|---|---|---|---|
| стик | 2 | 3 | 6+P | 5 | 2 | 3 | 6+P | 5 |

В кадре 2 срабатывает первый хадокен, и все записи до кадра 2 включительно
помечаются потраченными (`consumed_frame = 2`). В кадре 8 проверяем шорюкен
`623`, идя назад от удара:

| запись | dir | ищем | без поглощения | с поглощением |
|---|---|---|---|---|
| кадр 8 | 6 | 3 | пропуск | пропуск |
| кадр 7 | 3 | 3 | да | да |
| кадр 6 | 2 | 2 | да | да |
| кадр 3 | 5 | 6 | пропуск | пропуск |
| кадр 2 | 6 | 6 | **да → ШОРЮКЕН** (ошибка!) | запись потрачена → провал |

Без поглощения «6» от первого хадокена склеивается с «23» второго. С
поглощением шорюкен не находится, проверка переходит к хадокену — и он
находится в записях 8, 7, 6. Игрок получил то, что хотел.

Все окна задаются **в кадрах симуляции**, а не в миллисекундах: файтинги
детерминированы и привязаны к 60 тикам в секунду. Именно поэтому буфер живёт
в симуляции и попадает в реплей и в rollback-неткод (GGPO): при откате
симуляции откатывается и буфер ввода.

**Rollback-неткод** — сетевая схема, где игра не ждёт ввода соперника, а
предсказывает его; если предсказание не сбылось, игра «откатывается» на
несколько кадров назад и пересчитывает их с правильным вводом (глава 18).
**GGPO** — самая известная библиотека такого неткода.

**Частые ошибки**

> * Искать шаги в прямом порядке (2, 3, 6) при обходе от новых к старым —
>   при обходе назад порядок должен быть обратным (6, 3, 2).
> * Не смотреть на запись с ударом как на кандидата для последнего шага.
> * Проверять зазор между шагами только для **найденных** записей. Пропущенные
>   «лишние» записи тоже стареют: если очередная просмотренная запись слишком
>   далеко от последнего найденного шага — дальше искать бессмысленно.
> * Окна в миллисекундах вместо кадров.
> * Зеркалить таблицу движений вместо входа: таблиц становится две, и они
>   расходятся при правках.
> * Забыть остановиться на потраченных записях (тест «two fireballs»).
> * Беззнаковая арифметика: `now - frame` в `uint` при `frame > now`
>   «заворачивается» в огромное число. В упражнении записи всегда не новее
>   `now`, но помнить об этом стоит.

### 7.5. Не только файтинги

Тот же механизм — «буфер событий с окнами и последовательностями» — используется
для чит-кодов (Konami code), жестов (двойной тап для рывка, «тап vs удержание»),
QTE и даже голосовых/сенсорных жестов. UE5 Enhanced Input реализует «Combo»
триггер именно так: цепочка действий с временными окнами.

**Konami code** — знаменитый чит-код ↑↑↓↓←→←→BA. **QTE** (quick time event) —
сцена, где нужно успеть нажать показанную кнопку.

> **Коротко:** буфер — кольцо записей «кадр, направление, кнопки», куда пишут
> только изменения. Приём ищется от свежего удара назад, шаги — в обратном
> порядке, с допуском лишних направлений, но с ограничениями по кадрам. Для
> персонажа, смотрящего влево, зеркалится вход. Сработавший приём «тратит»
> свои записи.

## 8. Запись ввода и реплеи

### 8.1. Матч = seed + ввод

Если симуляция детерминирована (глава 01: фиксированный шаг, никаких
зависимостей от времени стены, ГСЧ с известным seed, одинаковые результаты
арифметики), то весь матч восстанавливается из:

```
seed + версия + ввод каждого тика
```

**ГСЧ** — генератор случайных чисел. На самом деле он псевдослучайный:
формула, которая из текущего числа делает следующее. **Seed** («зерно») —
начальное число ГСЧ. Одинаковый seed — одинаковая последовательность
«случайных» чисел, каждый раз.

Аналогия: **запись шахматной партии**. Чтобы повторить партию, не нужно
фотографировать доску после каждого хода — достаточно списка ходов `e2-e4,
e7-e5, ...`, потому что правила шахмат детерминированы. Реплей на вводе — это
«список ходов» игрока, а движок — это «правила».

Так работают реплеи StarCraft и Age of Empires (минуты матча — десятки
килобайт), демо Doom (`.lmp` — буквально поток `ticcmd_t` по 4 байта на тик на
игрока), Trackmania, «призраки» в гонках, а также lockstep-сеть (глава 18):
по сети передаётся тот же поток ввода, что и в реплей.

**Lockstep** — сетевая схема, где все компьютеры обмениваются только вводом и
каждый сам считает одну и ту же симуляцию.

Альтернатива — **snapshot-реплеи**: записывается состояние мира (как в сетевом
snapshot-протоколе, Quake 3 demos, CS:GO/Source demos). Они устойчивы к
недетерминизму и позволяют перематывать, но на порядки больше. Многие игры
комбинируют: поток ввода + периодические ключевые кадры состояния для быстрой
перемотки (как I-кадры в видео).

**Снимок (snapshot)** — полная копия состояния мира на какой-то момент. В
шахматной аналогии — фотография доски. **I-кадр** в видео — полный кадр, от
которого отсчитываются следующие «разностные» кадры; благодаря им видео можно
перемотать в середину, не проигрывая всё с начала.

| | реплей на вводе | реплей на снимках |
|---|---|---|
| что пишем | ввод каждого тика | состояние мира |
| размер | крошечный | большой |
| требует детерминизма | да, строго | нет |
| перемотка назад | только пересчётом с начала (или с ключевого кадра) | легко |
| пример | StarCraft, Doom | Quake 3, CS:GO |

> **Коротко:** при детерминированной симуляции для повтора матча достаточно
> seed, версии и ввода каждого тика — как список ходов в шахматах.

### 8.2. Что записывать

Не сырые события и не scancode — а ввод **после action mapping**, привязанный к
тику: маску кнопочных действий и квантованные оси. Тогда реплей не зависит от
раскладки, привязок и устройства зрителя. Поток очень хорошо сжимается: соседние
тики почти всегда одинаковы, и даже простое RLE `{mask, count}` даёт сжатие в
десятки раз (в `e1005` 600 тиков укладываются в ~150 байт).

Почему не сырые события? Зритель смотрит реплей на своём компьютере, где W
может быть привязан к другому действию, а геймпада нет вовсе. Если записать
«нажат scancode 26», у зрителя это может означать что-то другое. А «тик 1234:
MOVE_RIGHT + JUMP» значит одно и то же везде.

**RLE** (run-length encoding, «кодирование длин серий») — простейшее сжатие:
вместо `AAAAAB` пишем «A×5, B×1». **Серия (run)** — несколько одинаковых
значений подряд.

```
тики:   R R R R R R J J . . . . . . F F F F ...
RLE:    (R,6) (J,2) (.,6) (F,4) ...
```

Код, который превращает строку тиков в серии:

```c3
import std::io;
import std::collections::list;

struct Run { char sym; int count; }

fn void main()
{
    String ticks = "RRRRRRJJ......FFFF";
    List{Run} runs;
    defer runs.free();
    foreach (c : ticks)
    {
        // тот же символ, что у последнего отрезка? — удлиняем отрезок
        if (runs.len() > 0 && runs[^1].sym == c)
        {
            runs[^1].count++;
            continue;
        }
        runs.push({ c, 1 });                 // иначе — начинаем новый
    }
    foreach (r : runs) io::printf("(%c,%d) ", r.sym, r.count);
    io::printn();
}
```

Пояснения:

* `runs[^1]` — последний элемент списка (`^1` = «первый с конца»).
* Для каждого тика смотрим: совпадает ли он с символом последней серии? Если
  да — серия стала на 1 длиннее. Если нет (или серий ещё нет) — начинаем новую
  серию длины 1.
* Программа печатает `(R,6) (J,2) (.,6) (F,4)`.

В `e1005` вместо символа — `ushort`-маска действий, и есть ещё одно
ограничение: счётчик серии сам хранится в `ushort`, а он не может быть больше
65535. Подумайте, что делать, если игрок держал одну и ту же комбинацию
дольше.

Обратная операция — **воспроизведение** — выдаёт маску по одному тику: «текущая
серия (R,6): выдано 0 из 6 → R; 1 из 6 → R; ... 6 из 6 → переходим к серии
(J,2)». Когда серии кончились — реплей закончился.

| вызов next | текущая серия | выдано в ней до вызова | результат |
|---|---|---|---|
| 1 | (R,6) | 0 | R |
| ... | (R,6) | ... | R |
| 6 | (R,6) | 5 | R |
| 7 | (J,2) | 0 | J |
| 8 | (J,2) | 1 | J |
| 9 | (.,6) | 0 | . |

Оценим сжатие в `e1005`: сырой ввод — 600 тиков × 2 байта = 1200 байт. Бот
держит комбинацию 5–34 тика, в среднем ~20, значит серий около 30, по 4 байта
каждая — ~120 байт плюс заголовок и чекпоинты.

> **Коротко:** в реплей пишут действия по тикам, а не клавиши. Одинаковые
> соседние тики сжимают в пары «значение, сколько раз».

### 8.3. Рассинхрон и чекпоинты

Главный враг — desync: одна неинициализированная переменная, обход хеш-таблицы
в порядке адресов, `float`, посчитанный иначе на другом CPU или другим
компилятором, вызов `rand()` без seed, зависимость от FPS — и реплей «уплывает».
Хуже всего, что заметно это бывает через минуты после причины.

**Desync (рассинхрон)** — состояние, когда воспроизведение пошло не так, как
оригинал. Аналогия: два человека одновременно вяжут по одной схеме; один
пропустил петлю в 10-м ряду — и через 50 рядов узоры уже совсем разные, но
**где** ошибка, по готовому шарфу не понять.

Защита — **чекпоинты**: при записи каждые N тиков сохраняется хеш состояния
симуляции; при воспроизведении хеши сверяются. Первый несовпавший чекпоинт
локализует ошибку с точностью до N тиков. Дальше — бинарный поиск: уменьшаем N
или пишем хеши подсистем по отдельности (физика, ИИ, инвентарь), чтобы найти,
**что** разошлось. Ровно так же отлаживают lockstep-сеть, и ровно так в
`e1005` ловятся подменённый ввод, чужой seed и обрезанный файл.

**Хеш** — короткое число-«отпечаток пальца», вычисленное из данных. Если данные
отличаются хоть в одном бите, хеш почти наверняка будет другим. Сравнить два
хеша (4 байта) несравнимо дешевле, чем хранить и сравнивать всё состояние.
**Чекпоинт** — контрольная точка; в вязании это как сверять узор с образцом
каждые 10 рядов.

Пример: CHECKPOINT = 60, игра длится 600 тиков — при записи сохраняем 10 хешей
(после тиков 60, 120, ..., 600). Пусть при воспроизведении ввод на тике 310
подменили:

| чекпоинт (после тика) | записанный хеш | хеш при воспроизведении | совпал? |
|---|---|---|---|
| 60 | 1a2b… | 1a2b… | да |
| ... | ... | ... | да |
| 300 | 77c0… | 77c0… | да |
| 360 | 9e41… | 03fd… | **нет → рассинхрон на 360** |

Вывод: ошибка где-то между тиками 301 и 360. Ровно это и проверяет
`e1005`: рассинхрон должен найтись не раньше места подмены и не позже
ближайшего за ним чекпоинта.

Что, если реплей **кончился** раньше, чем нужно (файл обрезан)? Это тоже
рассинхрон, и правильный ответ — номер тика, на котором ввод кончился: дальше
воспроизводить нечего. А с чужим seed всё разойдётся сразу — первым же
несовпавшим окажется самый первый чекпоинт.

Хеш состояния должен покрывать всё, что влияет на будущее — включая состояние
ГСЧ. Хеш по полям, а не по байтам структуры (паддинг может содержать мусор).

**Паддинг** — пустые байты, которые компилятор вставляет между полями
структуры для выравнивания (глава 02). Их содержимое не определено: две
одинаковые по полям структуры могут отличаться мусором в паддинге и давать
разные побайтовые хеши.

**Частые ошибки**

> * Забыть включить в хеш состояние ГСЧ — разные будущие при одинаковом
>   настоящем.
> * Сверять чекпоинт **до** шага симуляции вместо **после** — сравниваете
>   состояние не того тика (сдвиг на 1).
> * Индекс чекпоинта: первый хеш записан после тика 60, значит лежит в
>   ячейке 0 (`60 / 60 - 1`).
> * Реплей кончился раньше времени, а код молча продолжает с маской 0 —
>   рассинхрон «размазывается» и находится позже, чем случился.

> **Коротко:** при записи каждые N тиков сохраняем хеш состояния, при
> воспроизведении сверяем. Первый несовпавший хеш показывает, на каком отрезке
> из N тиков всё разошлось.

### 8.4. Формат файла

Минимальный заголовок реплея: магическое число, **версия формата**, версия
билда игры (реплей старой версии на новом коде почти наверняка рассинхронится —
многие игры просто отказываются его играть), seed, параметры матча (карта,
персонажи), число тиков. Данные — little-endian, побайтово (не `fwrite`
структуры — см. главу 13). Загрузчик обязан проверять каждое чтение на выход
за границы: реплеи передают между игроками, и это недоверенный ввод.

Термины:

* **Магическое число** — несколько фиксированных байт в начале файла (в
  `e1005` это `C3RP`), чтобы сразу отличить «наш» файл от случайного. Так PNG
  начинается с `\x89PNG`, а ZIP — с `PK`.
* **Little-endian** — порядок байт «младший первым»: число 0x01020304
  записывается как `04 03 02 01`.
* **Недоверенный ввод** — данные, которые мог подготовить кто угодно, в том
  числе злоумышленник. Если загрузчик верит полю «в файле 1 000 000 серий» и
  читает дальше конца файла — это падение или уязвимость.

Схема файла из `e1005`:

```
 offset  размер  поле
 0       4       "C3RP"
 4       4       version
 8       4       seed
 12      4       frames
 16      4       run_count
 20      4·N     N × (u16 mask, u16 count)
 ...     4       cp_count
 ...     4·M     M × u32 hash
```

> **Коротко:** файл реплея начинается с подписи и версии, числа пишутся
> побайтово в фиксированном порядке, а при чтении каждая длина проверяется.

### 8.5. Реплеи как инструмент разработки

Запись ввода — один из самых окупаемых инструментов движка:

* **Воспроизведение багов.** Тестировщик прикладывает реплей к баг-репорту —
  программист получает баг детерминированно, с отладчиком.
* **Регрессионные тесты.** Набор реплеев гоняется на CI; финальный хеш
  состояния сравнивается с эталоном. Изменился — либо баг, либо осознанное
  изменение геймплея (тогда эталон обновляют).
* **Профилирование** на одинаковой нагрузке от билда к билду.
* **Killcam, повторы голов, «призраки»** в гонках.

**CI** (continuous integration) — сервер, который автоматически собирает и
тестирует проект после каждого изменения. **Регрессия** — когда то, что
работало, сломалось после правки. **Killcam** — повтор момента, когда вас
убили, глазами противника.

Ограничение: всё, что не детерминировано (физика с `float` на разных
платформах, многопоточность с недетерминированным порядком), нужно либо
сделать детерминированным, либо исключить из записываемой симуляции
(косметические частицы, звук и анимации можно не воспроизводить точно).

> **Коротко:** реплеи — это ещё и бесплатные воспроизводимые баг-репорты,
> регрессионные тесты и стабильная нагрузка для профилирования.

## 9. Производительность и устройство данных

Ввод — не горячая точка: десятки событий за кадр. Но несколько правил всё же
важны:

* Состояние ввода — плоские POD-структуры и битовые маски. Их копируют в буфер
  ввода, в реплей, в сетевой пакет и в историю для rollback (GGPO хранит ввод
  за 8+ кадров для каждого игрока).
* Платформенный поток событий может приходить из другого потока (на Windows
  окно и ввод часто живут в отдельном потоке, чтобы не блокироваться при
  перетаскивании окна). Тогда между потоками — SPSC-очередь событий (трек 1,
  упражнение 112), а состояние собирает поток симуляции.
* Никаких выделений памяти на событие. Кольцевые буферы фиксированного
  размера.

**Горячая точка** — место в программе, где тратится больше всего времени.
**POD** (plain old data) — «простые данные»: структура из чисел и массивов
без указателей и скрытой логики; её можно копировать обычным копированием
байт. **SPSC** (single producer, single consumer) — очередь, в которую пишет
ровно один поток, а читает ровно один другой; такую очередь можно сделать без
блокировок.

Почему маски, а не `bool[256]`? `bool[256]` — 256 байт; 4 × `ulong` — 32 байта.
Сравнить два снимка — 4 сравнения вместо 256. Для 8 кадров истории rollback на
4 игроков это 1 КБ против 8 КБ — мелочь, но на сетевом пакете мелочи
складываются.

> **Коротко:** данные ввода — маленькие плоские структуры, которые дёшево
> копировать; никаких выделений памяти на каждое событие.

## 10. Типичные ошибки (сводка)

1. Фронты по снимкам — потеря быстрых нажатий (`e1001`).
2. Автоповтор ОС как новое нажатие.
3. Нет сброса при потере фокуса — «залипшие» клавиши.
4. Keycode вместо scancode для управления (AZERTY).
5. Осевая мёртвая зона на 2D-стике — «прилипание» к осям; зона без
   перемасштабирования — скачок на выходе (`e1002`).
6. Чувствительность мыши, умноженная на `dt`.
7. Геймплей опрашивает клавиши напрямую вместо действий.
8. Флаги `in_menu` вместо контекстов; утечка нажатий сквозь меню (`e1003`).
9. Окна ввода в миллисекундах в детерминированной симуляции; повторное
   срабатывание буферизованного нажатия; склейка приёмов (`e1004`).
10. Реплеи без версии, без seed и без чекпоинтов (`e1005`).

## Как это связано с упражнениями

### `e1001_edge_detection` — pressed / held / released

**Что просят.** Дописать у `Keyboard` методы `begin_frame`, `on_event`,
`held`, `pressed`, `released`. Стенд подаёт по кадрам события (нажатие,
удержание, тап внутри одного кадра, автоповтор, перенажатие, лишнее «up») и
печатает рядом ваш `pressed` и наивный.

**Что перечитать.** Разделы 2.1, 3.1 (особенно «Напоминание: битовые
маски»), 3.2, 3.3.

**На что обратить внимание.**

* `begin_frame` вызывается **до** событий кадра: в нём запоминают снимок для
  наивного способа и очищают защёлки.
* `held` смотрит только на `down`, `pressed`/`released` — только на свои маски.
* Автоповтор и «up для отпущенной» не должны ничего менять.
* В выводе сравните колонки `pressed` и `naive` в кадрах 3 и 5 — там и видна
  разница.

### `e1002_device_abstraction` — устройства и мёртвые зоны

**Что просят.** Реализовать `axial_deadzone`, `radial_deadzone`,
`InputState.apply` (разбор сырых событий по видам) и `InputState.move_x`.

**Что перечитать.** Разделы 1.2, 1.4, 4.2–4.6, 5.1 (про `move_x`).

**На что обратить внимание.**

* Сверьте свои функции с таблицами из 4.2 и 4.3 — assert-ы в начале `main`
  используют те же числа.
* Ровно `dz` — это ещё ноль. Знак, clamp, -32768, порядок «сначала умножить,
  потом делить».
* В радиальной зоне — `long` для суммы квадратов.
* Стику нужны **обе** сырые оси сразу, поэтому событие одной оси обновляет
  сырое значение и пересчитывает зону по паре.
* Мышь — накапливать (`+=`), а не присваивать; кнопки мыши кроме левой и
  неизвестные коды — в счётчик `unmapped`.
* `last_device` переключается на геймпад только при ненулевом значении после
  зоны (кадр 0 стенда — «шум на столе»).

### `e1003_action_mapping` — действия и контексты

**Что просят.** Реализовать `ActionMap.resolve` (маска нажатых controls →
маска действий) и `Context.rebind` с ошибками `CONFLICT` и `NOT_BOUND`.

**Что перечитать.** Разделы 5.3, 6.1–6.3, 6.5.

**На что обратить внимание.**

* Обход — от вершины стека (`stack[depth - 1]`) к низу.
* Поглощённые controls убираются из «оставшихся» после обхода всего
  контекста (6.3).
* Blocking-контекст сначала обрабатывает свои привязки, потом останавливает
  обход.
* В `rebind` сначала все проверки, потом изменение; «занят тем же действием»
  — не конфликт. Порядок проверок указан в TODO.
* Сверьтесь с таблицами трассировки из 6.2 — это ровно сценарии стенда.

### `e1004_combo_buffer` — буфер и комбо

**Что просят.** Реализовать `mirror` (зеркалирование направления) и
`match_motion` (поиск приёма в буфере). Кольцевой буфер, `detect` и сценарии
уже написаны.

**Что перечитать.** Разделы 7.2–7.4 целиком, особенно трассировки и «Частые
ошибки». Подробный алгоритм по шагам — в шапке упражнения.

**На что обратить внимание.**

* `mirror` — только горизонталь; средний столбец нумпада неподвижен.
* Сначала найти свежее непотраченное нажатие удара; если его нет — сразу -1.
* Шаги движения ищутся с конца строки `m.dirs`; запись с ударом — тоже
  кандидат.
* Три проверки по кадрам: окно кнопки, зазор между шагами (в том числе для
  пропускаемых записей), общее окно движения.
* Дойдя до потраченной записи (или до конца буфера) — провал.
* Прогоните в уме сценарий «two fireballs» по таблице из 7.4.
* Аккуратнее с `uint` и `long` при вычитании кадров и сравнении с
  `consumed_frame` (он может быть -1).

### `e1005_replay` — запись и воспроизведение

**Что просят.** Реализовать `Replay.record_frame` (RLE), `Playback.next`
(выдача масок по одной, `END_OF_REPLAY` в конце) и `verify` (прогон симуляции с
проверкой чекпоинтов).

**Что перечитать.** Разделы 8.1–8.4 и главу 01 про детерминизм.

**На что обратить внимание.**

* `record_frame`: идея — как в примере RLE из 8.2, но с ограничением
  `ushort::max` на длину серии и счётчиком `frames`.
* `Playback.next`: таблица из 8.2 показывает, как двигаться по сериям.
  Серии длины 0 в принципе возможны после ручной правки данных — подумайте,
  не зациклится ли ваш код.
* `verify`: свежая симуляция с seed из реплея; чекпоинт сверяется **после**
  шага; индекс хеша — номер чекпоинта минус один; если ввод кончился раньше
  `frames` — это рассинхрон на текущем тике.
* Ожидаемые ответы для трёх «испорченных» реплеев описаны в 8.3.
