> Упражнения главы: `e0301_swap_remove`, `e0302_handles`, `e0303_slot_map`,

## Карта главы

**Что вы узнаете.** Как в игре безопасно ссылаться на объекты, которые могут в любой момент
исчезнуть; что такое handle (индекс + поколение) и почему он лучше указателя; как удалять

**Зачем это нужно.** Это, пожалуй, самая «движковая» из всех тем про структуры данных:
почти каждая подсистема — рендер, физика, звук, ECS, ресурсы — хранит свои объекты одним

## 1. Проблема: ссылки на объекты, которые умирают

### 1.1 Ситуация

В игре объекты постоянно ссылаются друг на друга: ракета — на цель, ИИ — на врага,
частица — на **эмиттер** (объект, «испускающий» частицы), UI — на персонажа, звук — на
источник. И объекты постоянно умирают: цель уничтожена, враг выгружен вместе с секцией
уровня, звук закончился.

Что хранить в ракете, чтобы она могла найти свою цель?

### 1.2 Варианты

**Сырой указатель** `Entity* target`. Быстро, но если цель уничтожена, указатель
**висит**: память освобождена или, хуже, переиспользована под *другой* объект. Ракета
полетит в случайного персонажа или прочитает мусор. Самый частый класс крашей в играх.

**Аналогия.** Вы записали адрес друга: «ул. Ленина, 5, кв. 12». Друг переехал, в квартиру
въехали другие люди. Вы приходите по адресу — дверь открывают, но это не ваш друг. Вы
даже не узнаете, что ошиблись.

**Умный указатель с подсчётом ссылок** (`shared_ptr`, `TSharedPtr`). **Подсчёт ссылок**
(refcount) — объект хранит число «сколько у меня владельцев» и удаляется, когда оно
падает до нуля. Объект не умрёт, пока на него ссылаются. Но «смерть» в игре — это игровое
событие («враг убит»), а не освобождение памяти: мёртвый враг, которого держит ракета,
продолжает существовать — зомби. Плюс атомарные инкременты на каждое копирование
(**атомарный** — безопасный при одновременной работе потоков, но дорогой), **циклы**
(A держит B, B держит A — оба никогда не удалятся), непредсказуемый момент освобождения
(каскад **деструкторов** — функций очистки — посреди кадра), и память разбросана по куче.

**Слабый указатель** (`weak_ptr`, `TWeakObjectPtr`) — указатель, который не держит объект
живым, но умеет сказать «объект уже удалён». Решает вопрос «жив ли объект», но это всё ещё
указатель на **блок управления** (отдельную маленькую структуру со счётчиками) в куче, и
проверка стоит промаха кэша.

**Handle** — непрозрачное число, по которому система-владелец может найти объект и
*проверить*, что он всё ещё тот самый. «Непрозрачное» значит: пользователь не должен
разбирать число на части, он лишь передаёт его обратно системе.

**Аналогия: номерок в гардеробе.** Вы не знаете, на каком крючке ваше пальто, и не должны
знать. Гардеробщик по номерку находит его — или говорит «такого номерка нет». А если на
номерке ещё и дата — по вчерашнему номерку чужое пальто не выдадут (это поколение,
раздел 2).

Это решение, к которому пришли почти все движки. Андре Вайсфлог сформулировал это в
статье «Handles are the better pointers» (2018):

* владелец (система) хранит объекты в своих массивах и может их двигать;
* пользователь хранит только handle — 32 бита, копируется как `int`, сериализуется;
* разыменование — через систему: `get(handle)` → указатель или «нет такого»;
* висячие handles обнаруживаются, а не приводят к порче памяти.

**Коротко:** указатель на умирающий объект опасен, refcount держит «зомби», weak-указатель
дорог. Handle — число, по которому владелец находит объект и проверяет, что он тот самый.

## 2. Индекс + поколение

### 2.1 Почему индекса мало: проблема ABA

Простейший handle — индекс в массиве. Но индекс тоже «висит»: элемент 5 удалили,
слот 5 переиспользовали под другой объект — старый индекс 5 теперь указывает на
чужой объект. Это классическая **проблема ABA**: значение было A, стало B (удалили), снова
стало «A» (слот занят опять) — и тот, кто проверяет только «есть ли что-то в слоте 5»,
не замечает подмены.

Трассировка:

| время | событие | слот 5 содержит | ракета держит индекс 5 и видит |
|---|---|---|---|
| 1 | создали орка, индекс 5 | орк | орка ✔ |
| 2 | орк убит, слот 5 свободен | — | «пусто» ✔ |
| 3 | создали союзника, ему дали слот 5 | союзник | **союзника** ✘ — ракета летит в своего |

### 2.2 Решение: поколение

Решение — **поколение (generation)**: у каждого слота счётчик, увеличивающийся при
каждом освобождении. Handle хранит и индекс, и поколение, которое было у слота на момент
создания объекта:

```
 handle (32 бита):  [ generation : 12 ][ index : 20 ]

 слоты:   idx:  0      1      2      3
          gen:  4      7      1      2
          live: да     нет    да     да

 handle {idx=1, gen=6}  -> слот 1 имеет gen 7  -> устарел (объект удалён)
 handle {idx=2, gen=1}  -> совпадает           -> валиден
```

Та же история с поколениями:

| время | событие | слот 5: gen / занят | handle у ракеты | проверка |
|---|---|---|---|---|
| 1 | орк создан | 1 / да | {5, 1} | gen 1 == 1, занят → валиден |
| 2 | орк убит → gen++ | 2 / нет | {5, 1} | не занят → невалиден |
| 3 | союзник создан в слоте 5 | 2 / да | {5, 1} | 1 ≠ 2 → **невалиден** ✔ |
| | | | у союзника {5, 2} | валиден |

Проверка — одно сравнение.

### 2.3 Как упаковать два числа в одно

Handle — одно 32-битное число, в котором младшие 20 бит — индекс, старшие 12 — поколение.
Это как телефонный номер «код города + номер»: из одного числа можно достать обе части.

* **Сдвиг влево** `x << 20` — дописать 20 нулевых бит справа (то же, что умножить на 2²⁰ =
  1 048 576). Так поколение «переезжает» в старшие биты.
* **Сдвиг вправо** `x >> 20` — отбросить 20 младших бит. Так достают старшую часть.
* **Маска** `x & ((1 << 20) − 1)` — оставить только 20 младших бит. Так достают индекс.
  (`(1 << 20) − 1` = двадцать единиц, как `a − 1` в главе 02.)

Пример: индекс 5, поколение 3. В шестнадцатеричной записи (каждая цифра = 4 бита) handle
выглядит как `0x00300005`: младшие 5 цифр (20 бит) — `00005`, старшие 3 цифры (12 бит) —
`003`. Удобно: в отладчике handle читается «на глаз».

### 2.4 О чём подумать

Подробности, о которых надо подумать:

* **Разбиение битов.** 20 бит индекса = 1 млн объектов, 12 бит поколения = 4096
  переиспользований слота до совпадения. Для пуль, которые создаются тысячами в секунду,
  поколение переполнится за минуты: старый handle может «ожить». Пример: слот
  переиспользуется 100 раз в секунду — 4096 поколений кончатся через 41 секунду.
  Решения: 64-битные handles (32+32 — Unreal `FObjectHandle`, многие ECS используют
  64-бит entity id); откладывать переиспользование слота (очередь свободных слотов вместо
  стека, — Bitsquid держал минимум 1024 свободных индекса в очереди, прежде чем
  переиспользовать); «выводить из оборота» слот, чьё поколение достигло максимума.
* **Нулевой handle.** Удобно, чтобы handle `0` всегда был невалиден: тогда
  нулевая инициализация структуры даёт «пустую ссылку». Для этого поколения начинают с 1
  (или индекс 0 резервируется). Handle слота 0 с поколением 1 — это `0x00100000`, не ноль.
* **Тип handle.** Handle текстуры и handle меша — разные типы (`typedef` в C3), чтобы
  компилятор не дал перепутать. Это бесплатно и ловит целый класс ошибок.
* **Где хранить тип/систему.** Иногда в handle отводят несколько бит под «тип»
  (ресурс какой системы), чтобы универсальный код мог маршрутизировать запросы.

Пример типизированных handles (проверено на c3c 0.8.5):

```c3
import std::io;

typedef TextureHandle = uint;   // отдельный тип, а не просто синоним
typedef MeshHandle = uint;

fn void bind_texture(TextureHandle h)
{
    io::printfn("bind texture %d", (uint)h);
}

fn void main()
{
    TextureHandle tex = (TextureHandle)42;   // из uint — только явным кастом
    MeshHandle mesh = (MeshHandle)7;
    bind_texture(tex);                       // ok
    // bind_texture(mesh);                   // ошибка компиляции: MeshHandle не TextureHandle
    // bind_texture(42);                     // и голое число тоже нельзя
    io::printfn("mesh %d", (uint)mesh);
}
```

**Что здесь происходит.** `typedef` создаёт **новый отдельный тип** с тем же устройством,
что `uint` (в отличие от `alias`, который даёт лишь второе имя). Если раскомментировать
строку с `mesh`, компилятор скажет: «Implicitly casting 'MeshHandle' to 'TextureHandle' is
not permitted». Внутри функции, где handle нужно разобрать на биты, его явно приводят к
`(uint)`.

### 2.5 Очередь свободных слотов (FIFO)

**Стек** (LIFO) выдаёт первым только что освобождённый слот — он переиспользуется очень
часто, поколение быстро растёт. **Очередь** (FIFO, first in — first out, «первым пришёл —
первым ушёл») выдаёт слот, освобождённый *давнее всех*, — нагрузка размазывается по всем
слотам. А правило «брать из очереди, только если в ней больше `MIN_FREE` слотов» ещё и
гарантирует, что любой освобождённый слот «отлежится», пока не освободятся ещё несколько.
(Исключение — когда новых, ни разу не выданных слотов уже не осталось: тогда берут из
очереди даже короткой, лишь бы она была не пуста.)

Трассировка для `MIN_FREE = 2` (условно; в e0302 значение своё):

| операция | очередь свободных (голова слева) | откуда взяли слот |
|---|---|---|
| create ×3 | [] | новые слоты 0, 1, 2 |
| destroy 0, destroy 1 | [0, 1] | — |
| create | [0, 1] | в очереди 2, не больше 2 → **новый** слот 3 |
| destroy 2 | [0, 1, 2] | — |
| create | [1, 2] | в очереди 3 > 2 → из головы: слот **0** |

Упражнение **e0302_handles** — упаковка/распаковка, проверка, переполнение поколений.

> **Частые ошибки**
>
> * Поколение начинают с 0 — первый handle слота 0 равен «пустому» 0.
> * Проверяют только поколение, но не флаг «занят» (или наоборот).
> * Не проверяют, что индекс меньше числа слотов, — выход за границу массива.
> * При достижении `GEN_LIMIT` поколение «заворачивают» к 1 вместо вывода слота из оборота.
> * Перепутали приоритет: `gen << 20 | idx` в C3 работает, но со скобками надёжнее читать.

**Коротко:** handle = индекс + поколение. Поколение растёт при каждом освобождении, и
старый handle перестаёт совпадать. Следите за переполнением поколения и начинайте с 1.

## 3. Swap-remove и плотные массивы

### 3.1 Удаление за O(1)

Удаление из середины массива с сохранением порядка — O(n) сдвиг: чтобы удалить элемент 1
из 1000, нужно сдвинуть 998 элементов. Если порядок не важен (а в движке чаще всего не
важен: какая разница, в каком порядке обновлять частицы), удаляют за O(1)
**перестановкой с последним**:

```
 до:      [A][B][C][D][E]       remove(1)
 после:   [A][E][C][D]          E переехал на место B
```

**Аналогия: очередь в кассу, где порядок неважен.** Если кто-то посреди очереди ушёл,
вместо того чтобы всем сдвигаться на шаг, последний человек просто встаёт на освободившееся
место.

Массив остаётся **плотным** (packed) — без дыр, и его обход — это идеальный линейный
проход по памяти, который любит **префетчер** (блок процессора, который замечает, что вы
читаете память подряд, и заранее подтягивает следующие кэш-линии).

### 3.2 Обратные ссылки

Но у перемещённого элемента E изменился индекс, и все, кто держал индекс E, должны узнать
об этом. Отсюда обязательный спутник swap-remove — **обратная ссылка**: для каждого
элемента плотного массива мы знаем его «владельца» (id), а для каждого id — его текущую
позицию. При перемещении обновляем обе стороны.

В e0301 это две таблицы: `owner_of[i]` — кто владеет элементом в позиции `i`, и
`index_of[id]` — где сейчас элемент владельца `id` (или −1).

Трассировка. Пять элементов, владельцы — id 7, 2, 5, 9, 4. Удаляем элемент владельца 2.

| | позиция 0 | 1 | 2 | 3 | 4 | len |
|---|---|---|---|---|---|---|
| данные до | A | B | C | D | E | 5 |
| `owner_of` до | 7 | 2 | 5 | 9 | 4 | |
| данные после | A | **E** | C | D | — | 4 |
| `owner_of` после | 7 | **4** | 5 | 9 | — | |

`index_of` до: `[7]=0, [2]=1, [5]=2, [9]=3, [4]=4`.
`index_of` после: `[7]=0, [2]=`**−1**`, [5]=2, [9]=3, [4]=`**1**.

Шаги: (1) нашли позицию удаляемого: `p = index_of[2] = 1`; (2) последний — позиция 4,
его владелец `owner_of[4] = 4`; (3) переносим данные и `owner_of` с 4 на 1; (4) `index_of[4] = 1`;
(5) `index_of[2] = −1`; (6) `len−−`.

Инвариант (проверяется в e0301): для всех `i < len` верно `index_of[owner_of[i]] == i`.
Проверим позицию 1: `owner_of[1] = 4`, `index_of[4] = 1` ✔.

**Особый случай:** удаляемый элемент — сам последний. Тогда «переставлять» не с кем; если
код всё же выполнит шаги 3–4, а затем шаг 5, всё будет правильно — но только если шаг 5
идёт *после* шага 4. Проверьте порядок на бумаге.

### 3.3 Удаление во время обхода

Пусть мы обходим массив и удаляем всех с `life <= 0`. Жизни: `[3, 0, 5, 0]`.

| шаг | i | массив | что делаем |
|---|---|---|---|
| 1 | 0 | [3, 0, 5, 0] | 3 > 0, жив → i = 1 |
| 2 | 1 | [3, 0, 5, 0] | 0 — мёртв → swap-remove: на место 1 встаёт последний (0) → [3, 0, 5]; **i не увеличиваем** |
| 3 | 1 | [3, 0, 5] | снова 0 (переехавший тоже мёртв) → swap-remove → [3, 5]; i не увеличиваем |
| 4 | 1 | [3, 5] | 5 жив → i = 2 |
| 5 | 2 | | i == len, конец |

Если бы на шаге 2 мы сделали `i++`, переехавший мёртвый элемент остался бы непроверенным.

Упражнение **e0301_swap_remove**.

> **Частые ошибки**
>
> * Перенесли данные, но забыли `owner_of` или `index_of`.
> * `index_of[удалённый] = −1` выполняют *до* обновления переехавшего — при удалении
>   последнего элемента это затирается обратно.
> * `i++` после удаления во время обхода.
> * `add` не проверяет, что у владельца уже есть элемент.

**Коротко:** swap-remove — удалить, поставив на место последний. Массив остаётся
плотным, но у переехавшего меняется индекс — поэтому храним обратные ссылки в обе стороны.

## 4. Slot map

### 4.1 Идея

Slot map соединяет обе идеи: стабильные handles + плотное хранение.

**Аналогия: гостиница со стойкой регистрации.** Номер в гостинице (слот) — то, что
записано у вас в карточке (handle). Но вещи гостей хранятся в одном общем плотном складе
(dense). Администратор по номеру смотрит в журнал: «вещи гостя из номера 3 — на полке 0».
Если склад переставили, меняется только запись в журнале, а ваш номер — нет.

```
           handle {idx, gen}
                 │
                 v
 slots (indirection):  [ gen | dense_idx/next_free ] x N
                 │
                 v
 dense data:     [ obj ][ obj ][ obj ][ obj ]          <- плотно, обход линейный
 dense->slot:    [  3  ][  0  ][  5  ][  1  ]          <- обратные ссылки для swap-remove
```

(**Indirection** — «косвенность»: чтобы найти данные, сначала смотрим в промежуточную таблицу.)

### 4.2 Операции

* `insert(obj)`: взять свободный слот (из свободного списка, хранящегося прямо в
  неиспользуемых слотах), дописать объект в конец плотного массива, связать слот и
  плотный индекс, вернуть `{slot, gen}`.
* `remove(h)`: проверить поколение, swap-remove из плотного массива (обновив слот
  перемещённого объекта через `dense->slot`), увеличить поколение слота, вернуть слот в
  свободный список.
* `get(h)`: проверить поколение, вернуть `&dense[slots[h.idx].dense_idx]`.
* Обход: просто цикл по плотному массиву.

### 4.3 Трассировка

Вставляем A, B, C, потом удаляем A, потом вставляем D. `—` — поле не используется.
Свободный список — через `next_free`, `NONE` — конец.

**После insert A, B, C** (все слоты новые, gen = 1):

| слот | gen | занят | dense | next_free |
|---|---|---|---|---|
| 0 | 1 | да | 0 | — |
| 1 | 1 | да | 1 | — |
| 2 | 1 | да | 2 | — |

`dense = [A, B, C]`, `dense_to_slot = [0, 1, 2]`, `free_head = NONE`. Handles: A={0,1}, B={1,1}, C={2,1}.

**remove(A = {0,1})**: слот 0, gen совпадает. Позиция A в dense — 0. Последний в dense —
C (позиция 2, слот `dense_to_slot[2] = 2`). Переносим C на позицию 0, `dense_to_slot[0] = 2`,
**и обновляем слот переехавшего**: `slots[2].dense = 0`. Слот 0: gen → 2, свободен,
`next_free = NONE`, `free_head = 0`.

| слот | gen | занят | dense | next_free |
|---|---|---|---|---|
| 0 | **2** | нет | — | NONE |
| 1 | 1 | да | 1 | — |
| 2 | 1 | да | **0** | — |

`dense = [C, B]`, `dense_to_slot = [2, 1]`, `free_head = 0`.

**insert(D)**: берём слот из головы списка — 0; `free_head = slots[0].next_free = NONE`.
D дописываем в dense на позицию 2.

| слот | gen | занят | dense | next_free |
|---|---|---|---|---|
| 0 | 2 | да | 2 | — |
| 1 | 1 | да | 1 | — |
| 2 | 1 | да | 0 | — |

`dense = [C, B, D]`, `dense_to_slot = [2, 1, 0]`. Handle D = {0, **2**}.

**Проверка:** `get(A = {0,1})` — слот 0 имеет gen 2 ≠ 1 → `null` ✔. `get(C = {2,1})` →
`slots[2].dense = 0` → `dense[0] = C` ✔ — хотя C переехал, его handle по-прежнему работает.

### 4.4 Цена и правило указателей

Все операции O(1), обход — линейный, handles стабильны. Цена: двойная косвенность при
доступе по handle (слот → плотный массив) и то, что указатели на элементы плотного
массива **нестабильны** (swap-remove перемещает объекты, рост массива их
**переаллоцирует** — `List` при нехватке места выделяет новый больший буфер и копирует
туда всё, старый адрес становится висячим). Поэтому правило: указатель, полученный из
`get`, живёт только до следующего изменения контейнера; хранить можно только handle.

### 4.5 Варианты slot map

* **Без плотного массива** (только слоты с данными внутри): нет второй косвенности, но
  обход идёт по дырявому массиву с проверкой `alive`. Если заполненность высокая — это
  быстрее. Так устроен простой пул с handles (как в sokol_gfx).
* **Стабильные адреса**: хранение страницами (chunked/bucket array) — данные не
  переезжают при росте, указатель живёт до удаления объекта. Unreal `TSparseArray`
  (массив + битовая маска занятости + свободный список), `TChunkedArray`; Godot `RID_Owner`
  (страницы фиксированного размера). Плата — дыры при обходе.
* В C++ есть предложение `std::hive` (бывший `plf::colony`) — стабильные адреса,
  быстрый обход блоков с пропуском дыр.

Упражнение **e0303_slot_map** — полный generic slot map с плотным массивом.

> **Частые ошибки**
>
> * В `remove` забыли обновить слот **переехавшего** значения — его handle начинает
>   указывать на чужие данные или за край.
> * Не обработали случай «удаляемый — последний в dense».
> * Не увеличили поколение при удалении.
> * Новый слот (не из свободного списка) создают с gen = 0.

**Коротко:** slot map = таблица слотов (handle → позиция) + плотный массив данных +
обратные ссылки. Handles стабильны, обход быстрый, указатели из `get` — одноразовые.

## 5. Sparse set

### 5.1 Идея

**Sparse set** («разреженное множество») — структура для множества целых чисел (обычно id
сущностей) из диапазона `[0, N)` с операциями `add`, `remove`, `contains` за O(1) и
плотным обходом. Два массива:

* `sparse` («разреженный») — индексируется **по id**, хранит позицию в `dense`;
* `dense` («плотный») — сами id подряд, без дыр.

```
 sparse (по id):   id:   0   1   2   3   4   5   6   7
                        [ - ][ 2 ][ - ][ 0 ][ - ][ 1 ][ - ][ - ]
                                │          │        │
 dense (плотно):               [ 3 ][ 5 ][ 1 ]
                         index:  0    1    2

 contains(id): sparse[id] < dense.len && dense[sparse[id]] == id
```

**Аналогия: список класса и журнал по номерам парт.** У каждой парты (id) есть табличка
«ученик за этой партой записан в строке N журнала» (sparse). Сам журнал (dense) — подряд,
без пустых строк. Чтобы пройти по всем ученикам — читаем журнал. Чтобы узнать, сидит ли
кто-то за партой 5, — смотрим табличку и проверяем, что в строке журнала действительно
парта 5.

### 5.2 Трассировка

Начинаем с пустого множества (`sparse` заполнен `EMPTY`).

| операция | dense | sparse (только заполненные) |
|---|---|---|
| add(3) | [3] | 3→0 |
| add(5) | [3, 5] | 3→0, 5→1 |
| add(1) | [3, 5, 1] | 3→0, 5→1, 1→2 |
| remove(3) | [**1**, 5] | **1→0**, 5→1, 3→EMPTY |
| contains(5)? | sparse[5] = 1, dense[1] = 5 ✔ | да |
| contains(3)? | sparse[3] = EMPTY | нет |

`remove(3)` — это swap-remove из раздела 3: последний (1) переезжает на позицию 0, и
`sparse[1]` исправляется на 0.

### 5.3 Проверка «туда и обратно»

Ключевая хитрость (Briggs & Torczon, 1993): `sparse` можно даже не инициализировать —
проверка `dense[sparse[id]] == id` отсеивает мусор. Если в `sparse[7]` лежит случайное
число 1, то `dense[1] = 5 ≠ 7` — значит, 7 в множестве нет. В движках `sparse` всё равно
инициализируют «пустым» значением, но идея проверки «туда и обратно» остаётся.

### 5.4 Хранилище компонентов

Параллельно `dense` можно хранить массив данных (компонентов) той же длины — получается
**хранилище компонентов** ECS в стиле EnTT: компоненты одного типа лежат плотно, доступ по
id сущности — две загрузки. (**Компонент** — кусок данных сущности: позиция, скорость,
здоровье. **ECS** — Entity Component System, подробно в главе 05.)

### 5.5 Пагинация

**Пагинация.** Если id сущностей достигают миллиона, а компонент есть у 100 сущностей,
полный массив `sparse` на миллион элементов расточителен. Его разбивают на страницы
(например, по 4096 элементов) и выделяют страницу только при первом обращении — так
делает EnTT. Это называется **ленивым выделением** («выделяем, только когда понадобилось»).

Номер страницы и место внутри неё — обычное деление с остатком. Для страниц по 256
(как в e0304):

| id | page = id / 256 | offset = id % 256 |
|---|---|---|
| 5 | 0 | 5 |
| 256 | 1 | 0 |
| 1234 | 4 | 210 |
| 65535 | 255 | 255 |

Важно: `contains(id)` для id из ещё не выделенной страницы просто отвечает «нет» — **без**
выделения. Иначе любая проверка «есть ли у сущности 60 000 компонент X» выделяла бы
страницу и съедала память. Выделять страницу можно только при **записи** (`add`).

Экономия: множество из 10 id в диапазоне до 65 536 при 4-байтовых записях — полный `sparse`
занял бы 256 КБ; с пагинацией — максимум 10 страниц по 1 КБ (а если id рядом — одна).

### 5.6 Пересечение множеств

**Пересечение множеств.** Запрос «все сущности с Position и Velocity» — это пересечение
двух sparse sets. Обходят *меньшее* множество и проверяют `contains` в остальных:
стоимость O(min), а не O(max).

Пример: Position есть у 100 000 сущностей, Velocity — у 10.

* Обход Position и проверка в Velocity: 100 000 проверок.
* Обход Velocity и проверка в Position: **10** проверок.

Результат одинаковый, работы — в 10 000 раз меньше. Для трёх и более множеств — то же:
ищем самое маленькое, обходим его, проверяем во всех остальных. Упражнение
**e0304_sparse_set** (счётчик `probes` там проверяет, что вы выбрали правильное множество).

> **Частые ошибки**
>
> * В `remove` забыли исправить `sparse` у переехавшего id.
> * `contains`/`sparse_get` выделяет страницу.
> * Новая страница не заполнена `EMPTY` (а нулями — и все id выглядят как «позиция 0»).
> * В пересечении обходят первое множество, а не самое маленькое.

**Коротко:** sparse set = «id → позиция» (sparse) + плотный список id (dense). Всё за O(1),
обход плотный, sparse можно разбить на лениво выделяемые страницы. Пересечение — обходом
самого маленького множества.

## 6. Стабильность ссылок: таблица решений

| Что храним у пользователя | Удаление обнаруживается | Объект может двигаться | Стоимость доступа | Сериализация |
|---|---|---|---|---|
| сырой указатель | нет | нет | 1 загрузка | нельзя |
| индекс | нет (ABA) | да* | 1 загрузка | да |
| refcount-указатель | объект жив, пока есть ссылки | нет | 1 загрузка + atomic при копировании | нет |
| weak-указатель | да | нет | 2 загрузки | нет |
| handle idx+gen (без плотного массива) | да | да* | 1 загрузка + сравнение | да |
| handle + slot map | да | да | 2 загрузки + сравнение | да |

\* при перемещении владелец обновляет только свою внутреннюю таблицу.

Как читать: **«загрузка»** — одно чтение из памяти (потенциальный промах кэша).
**«Сериализация»** — можно ли сохранить ссылку в файл и после загрузки она останется верной.
Указатель — нельзя: при следующем запуске объекты будут по другим адресам. Индекс или
handle — можно: это просто число.

Возможность **двигать объекты** — ключ ко многим оптимизациям: дефрагментация памяти
(глава 02), сортировка данных для лучшей локальности (например, по материалу), сжатие
плотного массива, перенос между потоками или в другие пулы, стриминг.

**Коротко:** handle — единственный вариант, который одновременно ловит удаление, позволяет
двигать объекты и сохраняется в файл.

## 7. Кэш и производительность

Почему всё это быстрее, чем «список указателей на объекты в куче»?

```
 Указатели в куче:   [p0][p1][p2][p3] -> разбросанные объекты, каждый — промах кэша
                       │   │   │   │
                       v   v   v   v
                      ...  ...  ...  ...   (~100-300 тактов на промах)

 Плотный массив:     [obj0 obj1 obj2 obj3 obj4 ...]  — последовательно, префетчер
                                                       подгружает заранее
```

* При обходе плотного массива из 10 000 частиц по 32 байта мы читаем 5000 кэш-линий
  подряд (32 байта × 10 000 = 320 000 байт / 64 = 5000) — префетчер справляется, и обход
  идёт со скоростью памяти. С указателями — до 10 000 случайных промахов.
* Handle — 4 байта вместо 8 у указателя: структуры, содержащие ссылки, меньше.
* Плотный массив можно разбить на массивы полей (SoA): обновление позиций читает только
  позиции. Это следующий шаг, к которому мы придём в ECS.

Прикинем порядок величин: 10 000 промахов × ~200 тактов = 2 000 000 тактов ≈ 0,7 мс при
3 ГГц — только на ожидание памяти. Это 4% бюджета кадра на одну простую операцию.

Но и у handles есть цена: доступ по handle в slot map — это две зависимые загрузки,
которые в худшем случае — два промаха. («Зависимые» — вторую нельзя начать, пока не
закончилась первая: адрес второй берётся из результата первой.) Если код постоянно ходит
«по ссылкам» (дерево сцены, граф ИИ), а не обходит массивы, handles сами по себе не помогут —
нужно менять алгоритм так, чтобы он обходил данные пачками.

### Измеряйте, а не верьте

Цифры выше — порядок величин, а не закон. Для 50 объектов любой контейнер работает
одинаково быстро; для миллиона разница между «указатели в куче» и «плотный массив»
легко достигает десятков раз. Прежде чем вводить косвенность, спросите себя: сколько
будет объектов, как часто их создают и удаляют, кто к ним обращается по handle, а кто
обходит все подряд? Если обращений по handle мало, а обходов много — плотный массив
(slot map). Если почти все обращения адресные, а удалений мало — простой пул с
handles без плотной части. Если объекты огромные и редкие — достаточно массива
указателей с поколениями. Выбор контейнера — это всегда ответ на вопрос о паттерне
доступа к данным, а не о «красоте» кода.

**Коротко:** плотные массивы быстры, потому что процессор читает память подряд. Handles
дают компактные ссылки, но доступ по ним — лишняя косвенность. Выбор — по тому, как
код обращается к данным.

## 8. Как это сделано в реальных движках

* **Bitsquid/Stingray** — статьи Никласа Фрикхольма «Managing Decoupling Part 4: The ID
  Lookup Table» и «Building a Data-Oriented Entity System»: ровно slot map (index table +
  packed array + free list), плюс очередь свободных индексов для отложенного
  переиспользования.
* **Unreal**: `UObject` адресуются по указателям, но с глобальной таблицей объектов
  (`GUObjectArray`), `FWeakObjectPtr` = индекс + serial number (поколение!); `TSparseArray`
  для стабильных индексов; Mass Entity — 32+32 бит handle.
* **Unity**: `Entity { int Index; int Version; }` в DOTS — индекс + поколение;
  `InstanceID` у классических объектов.
* **Godot**: `RID` — 64-битный id (индекс + валидатор), `RID_Owner` хранит объекты
  страницами; все серверы (RenderingServer, PhysicsServer) общаются через RID.
* **EnTT**: entity — 32 бита (20 индекс + 12 версия) по умолчанию, настраивается;
  sparse sets с пагинацией.
* **sokol_gfx**: все ресурсы (`sg_buffer`, `sg_image`) — структуры с одним `uint32_t id`,
  пулы с поколениями, проверка при каждом вызове.
* **Our Machinery**: `tm_entity_t` — 64 бита, «The Truth» использует 64-битные id
  объектов с типом и поколением.

Обратите внимание: «version», «serial number», «validator» — всё это разные названия
одного и того же **поколения**.

## 9. Дизайн API: что выставлять наружу

### 9.1 API на handles

Контейнер с handles — это ещё и **граница модуля**. Хорошее API подсистемы на handles
выглядит так (пример в стиле sokol; это набросок объявлений, тела функций опущены):

```c3
typedef MeshHandle = uint;

fn MeshHandle mesh_create(MeshDesc* desc);   // 0 при ошибке
fn void mesh_destroy(MeshHandle h);          // мёртвый handle — молча игнорируется
fn bool mesh_valid(MeshHandle h);
fn MeshInfo mesh_query(MeshHandle h);        // копия данных, не указатель
```

**Что здесь происходит.** Наружу выходят только handles и **копии** данных. Пользователь
никогда не получает указатель на внутренний объект. Внутренняя структура хранения (slot map,
пул, страницы) может меняться без изменения API. Если указатель всё-таки нужен ради
производительности, его называют явно и ограничивают по времени жизни: `mesh_lock(h)` /
`mesh_unlock(h)`, или «указатель действителен до следующего вызова
`mesh_create`/`mesh_destroy`».

Несколько решений, которые стоит принять сознательно:

* **Что делает `destroy` с мёртвым handle?** Молча игнорирует (удобно при каскадном
  удалении) или ругается в отладке (ловит логические ошибки). Часто — второе с флагом.
* **Что возвращает `get` с мёртвым handle?** `null`/Optional — честно; «объект-заглушка»
  (default texture — розовая шахматка) — удобно в рендере: ошибка видна на экране, но
  не роняет игру. Unreal и многие движки делают именно так для ассетов.
* **Кто владеет памятью объектов?** Сама подсистема, выделяя её из своего аллокатора
  с бюджетом (глава 02). Это позволяет одним вызовом узнать «сколько памяти у мешей»
  и одним `reset` выгрузить все меши уровня.
* **Generic или нет?** Generic slot map (`SlotMap{T}`) избавляет от копипаста, но
  каждой подсистеме обычно нужна своя политика (отложенное удаление, refcount,
  заглушки) — поэтому generic-ядро + тонкая обёртка в подсистеме.

### 9.2 Многопоточность

Handles особенно хороши в многопоточном коде: это просто числа, их можно передавать
между потоками, класть в очереди команд и сравнивать без синхронизации. Типичная
схема (используется в рендерах Bitsquid, sokol, многих **RHI** — render hardware interface,
слой над графическим API): поток игры *резервирует* handle атомарным счётчиком сразу
(чтобы вернуть его пользователю), а реальное создание ресурса происходит позже в потоке
рендера, который обрабатывает команду «создать ресурс для handle N». До этого момента
`get` возвращает «ещё не готов».

### 9.3 Отложенное удаление (для e0305)

Аналогично отложенное удаление (упражнение e0305): handle умирает сразу, а память
освобождается, когда все потребители (GPU, другие потоки) гарантированно закончили.

**Почему нельзя сразу.** GPU отстаёт от CPU на несколько кадров (**frames in flight** —
«кадры в полёте», уже отправленные, но ещё не дорисованные). Если в кадре 10 CPU удалил
текстуру, GPU может в этот момент ещё рисовать кадр 9, в котором она используется.

**Аналогия: посуда в ресторане.** Официант уже унёс тарелку со стола (handle недействителен —
новые заказы её не получат), но мыть её начнут, только когда она дойдёт до мойки
(прошло `FRAMES_IN_FLIGHT` кадров).

Трассировка при `FRAMES_IN_FLIGHT = 2`:

| кадр | событие | handle валиден? | слот в очереди удаления? | слот можно выдать заново? |
|---|---|---|---|---|
| 10 | `release(h, 10)`: alive = false, gen++ | нет (сразу) | да, release_frame = 10 | нет |
| 10 | `collect(10)`: 10 − 10 = 0 < 2 | нет | да | нет |
| 11 | `collect(11)`: 11 − 10 = 1 < 2 | нет | да | нет |
| 12 | `collect(12)`: 12 − 10 = 2 ≥ 2 → `destroy_fn`, слот в свободный список | нет | нет | **да** |

Ключевое: `get(h)` начинает возвращать `null` в тот же момент, что и `release`, а вот
слот возвращается в оборот только через два кадра.

**Коротко:** наружу — только handles и копии; решите заранее, что делать с мёртвыми
handles; в многопоточном движке handle можно выдать сразу, а создать/удалить объект позже.

## 10. Подводные камни

* **Хранение указателя из `get` дольше, чем нужно.** После `insert` плотный массив
  может переаллоцироваться, после `remove` — объект переехать. Получили указатель —
  используйте сразу.
* **Удаление во время обхода.** Swap-remove текущего элемента ставит на его место
  последний — его надо обработать (не увеличивать индекс) или откладывать удаления
  до конца обхода (deferred destruction, глава 05). См. трассировку в 3.3.
* **Поколение в 0.** Если поколение начинается с 0, а нулевой handle — «пустой»,
  то handle первого объекта в слоте 0 равен пустому. Начинайте поколения с 1.
* **Переполнение поколения.** Ещё раз: оценивайте, сколько раз слот может быть
  переиспользован за время жизни самого долгого handle.
* **Handle без проверки.** Отладочная сборка обязана проверять поколение при каждом
  доступе; в релизе иногда проверку убирают для «горячих» путей — только если
  уверены, что handle валиден по построению.
* **Многопоточность.** Создание/удаление меняют общие структуры. Типичное решение —
  резервировать handles атомарно, а реальные структурные изменения применять в
  синхронной точке кадра (**command buffer** — список отложенных команд, которые
  выполняются разом в определённый момент).

## 11. Как это связано с упражнениями

### e0301_swap_remove

* **Что просят:** `Packed.add`, `Packed.remove` (swap-remove с обновлением `owner_of` и
  `index_of`) и `Packed.remove_dead` (удаление во время обхода).
* **Что перечитать:** 3.2 (трассировка обратных ссылок), 3.3 (удаление во время обхода).
* **На что обратить внимание:** инвариант `index_of[owner_of[i]] == i`; случай «удаляем
  последний»; `add` отказывает, если нет места или у владельца уже есть элемент; в
  `remove_dead` не увеличивайте `i` после удаления.

### e0302_handles

* **Что просят:** `make_handle`, `handle_index`, `handle_gen`, `is_valid`, `create`, `destroy`.
* **Что перечитать:** 2.2 (поколения), 2.3 (сдвиги и маски), 2.4 (нулевой handle,
  переполнение), 2.5 (FIFO-очередь и `MIN_FREE`).
* **На что обратить внимание:** поколения с 1; `is_valid` проверяет индекс, занятость и
  поколение; слот, достигший `GEN_LIMIT`, выводится из оборота (в очередь не попадает,
  `retired++`); слот из очереди берётся, если в ней **больше** `MIN_FREE`
  (или если новых слотов уже не осталось, а очередь не пуста); если нет ни того, ни
  другого — `NULL_HANDLE`.

### e0303_slot_map

* **Что просят:** `SlotMap.insert`, `remove`, `get`.
* **Что перечитать:** 4.2, 4.3 (полная трассировка), 3.2 (swap-remove).
* **На что обратить внимание:** главная ловушка — обновить `slots[...]` переехавшего
  значения; новый слот — с gen = 1; освобождённый слот — в голову свободного списка.
  Тест сравнивает с эталонной моделью на тысячах случайных операций, так что
  ошибка в редком случае (удаление последнего) обязательно всплывёт.

### e0304_sparse_set

* **Что просят:** `sparse_get`, `sparse_ref` (с ленивым выделением страницы), `add`,
  `remove`, `intersect`.
* **Что перечитать:** 5.2 (трассировка), 5.5 (пагинация, таблица page/offset), 5.6
  (пересечение).
* **На что обратить внимание:** `sparse_get` ничего не выделяет; новая страница
  заполняется `EMPTY`; в `remove` исправить `sparse` у переехавшего id; `intersect`
  обходит самое маленькое множество.

### e0305_resource_pool

* **Что просят:** методы generic `ResourcePool <Type, HandleT>`: `create`, `get`,
  `release`, `collect`.
* **Что перечитать:** 2 (формат handle — как в e0302), 2.4 (типизированные handles и
  пример с `typedef`), 4.5 (пул без плотного массива), 9.3 (отложенное удаление и
  трассировка).
* **На что обратить внимание:** свободный список — LIFO через `next_free`; handle
  умирает сразу в `release`, а слот возвращается только в `collect`, когда
  `frame − release_frame >= FRAMES_IN_FLIGHT`; при переводе handle в число и обратно нужны
  явные касты (`typedef`).

## Словарик

| Термин | Простыми словами |
|---|---|
| **Висячий указатель** | указатель на уже освобождённую или переиспользованную память |
| **Подсчёт ссылок (refcount)** | объект удаляется, когда на него не осталось ссылок |
| **Слабый указатель (weak)** | ссылка, которая не держит объект живым, но знает, что он умер |
| **Handle** | непрозрачное число-ссылка, проверяемое владельцем |
| **Непрозрачный** | пользователь не разбирает его на части, только передаёт обратно |
| **Слот** | ячейка таблицы, в которой живёт (или жил) объект |
| **Поколение (generation, version)** | счётчик слота, растущий при каждом освобождении |
| **Проблема ABA** | слот освободили и заняли снова — старая ссылка «не замечает» подмены |
| **Сдвиг `<<` / `>>`** | перенос битов влево/вправо (умножение/деление на степень двойки) |
| **Маска** | число, которым через `&` оставляют только нужные биты |
| **Нулевой handle** | значение 0, всегда означающее «нет объекта» |
| **typedef (C3)** | новый отдельный тип, не смешивается неявно с исходным |
| **FIFO / LIFO** | очередь («первым пришёл — первым ушёл») / стек («последним пришёл — первым ушёл») |
| **Вывод слота из оборота** | слот больше никогда не выдаётся, чтобы не переполнить поколение |
| **Плотный массив (packed)** | массив без дыр |
| **Swap-remove** | удаление перестановкой с последним элементом, O(1) |
| **Обратная ссылка** | запись «кто владеет этой позицией» для обновления при перемещении |
| **Префетчер** | блок процессора, заранее подгружающий данные при последовательном чтении |
| **Slot map** | слоты (handle → позиция) + плотный массив + обратные ссылки |
| **Indirection (косвенность)** | доступ через промежуточную таблицу |
| **Переаллокация** | перенос массива в новый больший буфер при росте |
| **Sparse set** | множество id: sparse (id → позиция) + dense (id подряд) |
| **Компонент** | порция данных сущности (позиция, скорость…) |
| **Пагинация** | разбиение большого массива на страницы, выделяемые по требованию |
| **Ленивое выделение** | память выделяется только при первой записи |
| **Пересечение множеств** | элементы, которые есть во всех множествах |
| **Загрузка (load)** | одно чтение из памяти |
| **Зависимые загрузки** | вторая не может начаться до окончания первой |
| **Сериализация** | сохранение данных в байты (файл, сеть) и восстановление |
| **Объект-заглушка** | безопасная замена отсутствующего ресурса (розовая шахматка) |
| **RHI** | слой движка над графическим API |
| **Frames in flight** | кадры, отправленные GPU, но ещё не дорисованные |
| **Отложенное удаление** | handle умирает сразу, память освобождается позже |
| **Command buffer** | список команд, выполняемых разом в определённый момент |
