# Глава 18. Сеть

> Упражнения главы: `e1801_bit_packing` … `e1806_prediction`. Сеть в них симулируется внутри
> процесса — с детерминированными задержками и потерями (LCG с фиксированным seed), поэтому
> результаты воспроизводимы и проверяемы.

Сетевой код — это место, где игра встречается с физикой: свет в оптоволокне проходит
Москва — Франкфурт примерно за 10 мс в одну сторону, и никакой оптимизацией это не ускорить.
Сеть теряет пакеты, переставляет их, задерживает на непредсказуемое время. А игрок хочет,
чтобы его персонаж реагировал мгновенно, а чужие двигались плавно и попадания засчитывались
честно. Всё сетевое программирование игр — это набор приёмов, которые прячут задержку и
ненадёжность от игрока, не давая при этом читерам воспользоваться прятками.

## 1. Транспорт: UDP против TCP

TCP даёт надёжный упорядоченный поток байт. Звучит идеально, но:

* **Head-of-line blocking**: если сегмент 5 потерян, сегменты 6, 7, 8 уже лежат в ядре
  получателя, но приложение их не получит, пока 5 не будет переслан (минимум один RTT,
  а с таймаутами — сотни мс). Для игры, где пакет 8 содержит самую свежую позицию игрока,
  ждать устаревший пакет 5 бессмысленно.
* **Управление перегрузкой** TCP резко снижает скорость при потерях — игре нужно отправлять
  20–60 пакетов в секунду при любой погоде.
* **Алгоритм Нейгла** склеивает мелкие записи (лечится `TCP_NODELAY`, но остальное — нет).

UDP — просто датаграммы: может потеряться, может прийти дважды, может прийти не по порядку,
но **каждая датаграмма доходит целиком или не доходит вовсе**, и никто никого не ждёт. Игры
строят поверх UDP **свой протокол**, где надёжность и порядок есть ровно там, где нужны:

| данные | надёжность | порядок | пример |
|---|---|---|---|
| состояние мира | нет (следующий снапшот заменит) | только «новее/старее» | позиции |
| ввод игрока | избыточность (шлём последние N вводов) | да | кнопки |
| события | да | иногда | «игрок вошёл», чат, покупка |
| крупные данные | да | да | карта, кастомизация (фрагментация) |

TCP (или WebSocket/HTTP) вполне годится для лобби, матчмейкинга, чатов, магазинов —
всего, где несколько сотен мс задержки не страшны. Для браузерных игр сейчас есть WebRTC
data channels и WebTransport — тот же «ненадёжный» режим.

Практические числа: MTU интернета ≈ 1500 байт, минус заголовки IP/UDP; безопасный размер
полезной нагрузки — около **1200 байт**. Больше — фрагментация на уровне IP, а потеря
одного фрагмента теряет всю датаграмму.

## 2. Топологии и модели

```
 peer-to-peer (все со всеми)        клиент-сервер
   A ----- B                          A     B
   | \   / |                           \   /
   |  \ /  |                          [SERVER]
   |  / \  |                           /   \
   C ----- D                          C     D
```

Две принципиально разные модели синхронизации:

1. **Детерминированный lockstep** (RTS, файтинги, часто P2P): передаётся только ввод,
   каждый симулирует всё сам.
2. **Авторитетный сервер с передачей состояния** (шутеры, MMO, большинство экшенов):
   клиенты шлют ввод, сервер симулирует и рассылает состояние.

## 3. Детерминированный lockstep

Идея «1500 лучников на модеме 28.8» (Age of Empires): если симуляция детерминирована,
то одинаковый ввод даёт одинаковый мир, и передавать нужно только ввод. Трафик не
зависит от числа юнитов.

```
кадр F:  мой ввод -> запланировать на тик F + DELAY -> отправить всем
         симулировать тик T, только если ввод ВСЕХ на T известен
```

**Задержка ввода** (input delay) прячет сетевую задержку: нажатие применяется через DELAY
тиков, и к этому моменту пакеты успевают дойти. В упражнении `e1804_lockstep` вы увидите
числами: с DELAY = 0 игра подвисает почти каждый кадр, с DELAY = 4 при задержке сети 1–3
тика — ни разу.

Требования и ловушки:

* **Детерминизм — абсолютный.** Одинаковые бинарники, одинаковый порядок итерации (никаких
  хеш-таблиц с адресами в ключах), никакого `rand()` без общего seed, осторожность с
  плавающей точкой (разные компиляторы, FMA, `-ffast-math`, x87 против SSE, `sin` из
  разных libm). Многие RTS используют фиксированную точку целиком.
* **Обнаружение рассинхронизации**: участники обмениваются контрольными суммами состояния
  каждые N тиков. Несовпадение — баг, который надо ловить инструментально: дамп состояния
  по тикам с обеих сторон и поиск первого различия.
* **Самый медленный задаёт темп.** Один лагающий игрок тормозит всех.
* **Подключение посреди игры** требует передачи полного состояния (или реплея всего ввода).
* **Читы**: все знают всё (maphack), зато подделать состояние нельзя — его считает каждый.

### Rollback (GGPO)

Для файтингов задержка ввода в 4–8 кадров неприемлема. **Rollback netcode** (GGPO, Тони
Кэннон) делает иначе: симулирует вперёд сразу, **предсказывая** ввод соперника (обычно —
«нажато то же, что в прошлый раз»). Когда настоящий ввод приходит и отличается — состояние
откатывается к последнему подтверждённому тику, и симуляция **переигрывается** до текущего
кадра с правильным вводом. Требования: дешёвое сохранение/восстановление состояния (снова
— всё состояние в одном блоке памяти, главы 02 и 17) и способность симулировать много
тиков за один кадр. Rollback сегодня — стандарт для файтингов и набирает популярность в
других жанрах.

## 4. Авторитетный сервер

```
 клиент                       сервер                        другие клиенты
 ввод #42 -----------------> симулирует тик ------------>  снапшот мира
 (предсказывает сразу)       (истина)                      (интерполируют)
           <--------------- состояние + last_input=42
```

Сервер — единственный источник истины, клиентам не доверяют. Это решает большинство
проблем читерства (кроме тех, что связаны с информацией — wallhack, aimbot). Но наивная
реализация ужасна: персонаж реагирует на нажатие через полный RTT, а чужие игроки
двигаются рывками с частотой снапшотов. Три техники это исправляют.

### 4.1. Интерполяция снапшотов (для чужих объектов)

Клиент рисует мир **в прошлом** — на `interp_delay` назад (обычно 2–3 интервала
снапшотов, в Source по умолчанию 100 мс) — и интерполирует между двумя снапшотами,
окружающими это время:

```
 снапшоты:   |s100|       |s150|        |s200|       (s250 в пути)
 время:  ----+-----+------+------+------+------+------+---->
                                  ^ render = now - delay = 170
             x = lerp(s150, s200, 0.4)
```

* Потеря одного снапшота незаметна: интерполируем через пропуск.
* Джиттер поглощается буфером.
* Если `render` обогнал свежайший снапшот, буфер «голодает». Варианты: держать последнее
  значение (рывок при возобновлении) или экстраполировать по скорости (dead reckoning;
  ошибка, если объект повернул).
* Буфер должен быть устойчив к перестановкам и дубликатам (`e1805_snapshot_interp`).

Часы: клиенту нужна оценка «серверного времени». Её получают из меток времени в снапшотах
и плавно подстраивают скорость локальных часов (±несколько процентов), а не прыгают.

### 4.2. Предсказание на клиенте и согласование (для своего персонажа)

```
 клиент:  #1  #2  #3  #4  #5  #6       предсказанный x меняется сразу
 сервер:              обработал #3 -> (x=30, last=3) -> приходит клиенту на #6
 клиент:  x = 30; выбросить #1..#3; переиграть #4 #5 #6
```

Ключевое требование — клиент и сервер используют **одну и ту же функцию движения** с
одинаковыми входами. Тогда переигрывание даёт ровно тот результат, что уже был
предсказан, и игрок ничего не замечает. Если на сервере произошло непредвиденное (толчок,
столкновение с другим игроком), клиент получает коррекцию. Хорошие реализации сглаживают
визуальную ошибку за 100–200 мс, а не телепортируют модель.

Gabriel Gambetta показывает это на интерактивных примерах — обязательно посмотрите.
Упражнение `e1806_prediction` реализует ровно этот цикл.

Предсказывать можно не всё. Своё движение и стрельба — да; анимация попадания и смерть
других — обычно нет (иначе «убил, а он ожил»). Overwatch предсказывает почти все
способности и умеет откатывать их (доклад Тима Форда на GDC 2017) — для этого вся игровая
логика написана в ECS с детерминированными системами, которые можно переиграть.

### 4.3. Лаг-компенсация (для попаданий)

Игрок видит противника в прошлом (интерполяция) и стреляет туда. Если сервер проверит
попадание по **текущему** положению — промах, хотя игрок явно попал. Решение (Valve):
сервер хранит историю положений хитбоксов за последнюю секунду и при обработке выстрела
**откатывает** всех к моменту, который видел стрелявший (`время команды − interp_delay −
latency`), проверяет попадание и возвращает обратно. Цена: «меня убили уже за укрытием» —
жертва с хорошим пингом страдает ради стрелка с плохим. Ограничьте окно отката (например,
200 мс).

## 5. Пропускная способность

### Квантование и упаковка битов

Позиция как три float — 96 бит. Позиция на карте 0..4096 м с точностью 1 мм — 22 бита на
ось. Угол поворота — 9–12 бит. Здоровье 0..100 — 7 бит. Булевы флаги — по биту.
Кватернион — «smallest three»: отбросить наибольшую компоненту (2 бита на её индекс) и
три оставшиеся по 9–10 бит.

```
 BitWriter: scratch (64 бита)
   [..............cccc|bbbbbbb|aaa]  -> когда >= 32 бит: слово в буфер
```

Формат задаётся кодом (порядок записи == порядок чтения), без самоописания — каждый бит на
счету. Отсюда требование: читатель обязан **проверять границы** (пакет от злоумышленника
может быть любым) и прекращать чтение при выходе за буфер. Упражнение `e1801_bit_packing`.

Важная тонкость: если сервер симулирует с float, а клиенту отправляет квантованное
значение, состояния расходятся. Сервер должен **сам применять квантование** к своему
состоянию (или хотя бы к тем значениям, что используются в предсказании).

### Дельта-сжатие

За 50 мс меняется малая часть мира. Сервер отправляет разницу с **базой** — последним
снапшотом, получение которого клиент **подтвердил**:

```
 сервер -> snap 14 = delta(база 10 -> 14), «база = 10»
 клиент: найти в своём кольце snap 10, применить дельту -> snap 14, ack 14
```

Нельзя брать базой предыдущий **отправленный** снапшот: он мог потеряться, и клиент не
раскодирует дельту. Отсюда тесная связь с ack-механизмом. Схемы кодирования: бит
«изменилось» на объект и на поле, разность с базой меньшим числом бит, предсказание
(«позиция = база + скорость × dt»), и шлём только ошибку предсказания. Quake 3 сделал
дельта-сжатие относительно последнего подтверждённого снапшота основой всей модели — и
это до сих пор лучшая отправная точка (`e1803_delta_compression`).

### Приоритеты и область интереса

Пакет ограничен. Сервер для каждого клиента решает, **что** отправить: близкие и видимые
объекты — каждый снапшот, далёкие — реже (priority accumulator: приоритет копится, пока
объект не отправлен). Это же защищает от wallhack: то, чего клиент не должен видеть, ему
не отправляют вовсе.

## 6. Надёжность поверх UDP

Каждый пакет несёт:

```
 sequence (16 бит) | ack (16 бит) | ack_bits (32 бита) | payload
```

`ack` — последний полученный номер **от собеседника**, `ack_bits` — какие из 32
предыдущих тоже получены. Подтверждение повторяется в ~33 пакетах, поэтому потеря одного
пакета не теряет подтверждения. Номера 16-битные и заворачиваются, поэтому сравнение «новее»
делается по модулю (`e1802_reliability`):

```c3
fn bool seq_greater(ushort s1, ushort s2)
    => (s1 > s2 && s1 - s2 <= 32768) || (s1 < s2 && s2 - s1 > 32768);
```

Надёжные сообщения строятся сверху: сообщение (с собственным номером) включается в
каждый пакет, пока пакет, содержащий его, не будет подтверждён. Получатель упорядочивает
сообщения по номеру. Тот же механизм ack даёт оценку RTT (время между отправкой пакета и
приходом его подтверждения) и потерь — их полезно показывать в debug-оверлее (глава 15).

Ввод клиента обычно отправляют **с избыточностью**: каждый пакет содержит последние 3–5
вводов, — так потеря пакета почти никогда не теряет ввод, а надёжность не требует ожидания.

## 7. Безопасность и робастность

* Никогда не доверяйте клиенту: проверяйте скорость, кулдауны, дальность, видимость.
* Ограничивайте ресурсы на соединение: размер буферов, число сообщений, частоту.
* Защита от подделки адреса и амплификации: handshake с challenge-токеном до того, как
  сервер начнёт тратить ресурсы; ответ не больше запроса.
* Шифрование и аутентификация пакетов (netcode.io Гленна Фидлера, DTLS, библиотеки
  вроде libsodium) — особенно на выделенных серверах.
* Чтение пакета — это парсинг недоверенных данных: проверки границ на каждом чтении.

## 8. Как тестировать

Сетевой код нельзя проверить «на локалхосте»: там RTT = 0 и потерь нет. Нужен **симулятор
сети** — слой между игрой и сокетом, добавляющий задержку, джиттер, потери, дубликаты и
перестановки (как во всех упражнениях этой главы). Плюс:

* детерминированные тесты: фиксированный seed сети + записанный ввод → контрольная сумма;
* headless-боты, гоняющие сервер под нагрузкой;
* «network conditions» в debug-меню (Unreal: `Net PktLag`, `Net PktLoss`);
* реплеи (lockstep-игры получают их бесплатно — это просто записанный ввод).

## 9. Как это делают настоящие движки

* **Quake 3** — снапшоты, дельта от последнего подтверждённого, интерполяция, предсказание
  своего игрока. Исходники открыты — чтение `sv_snapshot.c`, `cl_parse.c` очень
  поучительно.
* **Source (Valve)** — то же плюс лаг-компенсация, `cl_interp`, `cl_cmdrate/cl_updaterate`,
  подробно описано в Valve Developer Wiki.
* **Unreal** — репликация свойств акторов (`Replicated`, `RepNotify`), RPC, relevancy и
  приоритеты, Replication Graph для больших миров, предсказание движения в
  `CharacterMovementComponent`, «Network Prediction» плагин.
* **Overwatch** — ECS + детерминированные системы, предсказание и откат способностей,
  адаптивная частота ввода.
* **Tribes** — классическая модель «ghost manager» с приоритетами и разными гарантиями
  доставки для разных типов данных (статья Фронмайера и Гифта).
* **GGPO** (теперь открыт) — rollback для файтингов; **Photon Quantum**, **Rocket League**
  (физика с предсказанием и откатом).

## 10. Подводные камни (чек-лист)

* TCP для состояния игры; пакеты больше MTU.
* Сравнение номеров последовательности без учёта заворота.
* Дельта от неподтверждённой базы.
* Разные функции движения на клиенте и сервере; клиент предсказывает с float, сервер
  квантует.
* Недетерминизм в lockstep: хеш-таблицы, float, неинициализированная память, порядок
  потоков.
* Чтение пакета без проверки границ.
* Доверие клиенту.
* Тестирование без симулятора задержки/потерь.
* Время отправки, привязанное к частоте кадров клиента, а не к фиксированному тику.

## 11. Сетевой слой в архитектуре движка

Как всё перечисленное раскладывается по слоям движка:

```
 +---------------------------------------------------------------+
 | геймплей: какие компоненты/поля реплицируются, RPC, правила    |
 +---------------------------------------------------------------+
 | репликация: снапшоты, дельты, приоритеты, область интереса,   |
 |             предсказание/согласование, интерполяция           |
 +---------------------------------------------------------------+
 | сообщения: надёжные/ненадёжные каналы, упорядочивание,        |
 |            фрагментация крупных сообщений                     |
 +---------------------------------------------------------------+
 | соединение: handshake, таймауты, ack/RTT/потери, шифрование   |
 +---------------------------------------------------------------+
 | транспорт: UDP-сокет / WebRTC / платформенный API + симулятор |
 +---------------------------------------------------------------+
```

Несколько практических решений, которые стоит принять заранее:

* **Фиксированный тик сети, отвязанный от кадров рендера.** Отправка 20/30/60 раз в
  секунду по таймеру симуляции, а не «каждый кадр». Иначе клиент со 144 FPS шлёт втрое
  больше, чем клиент с 48 FPS, а сервер получает неравномерный поток.
* **Описание репликации данными.** Поля, которые реплицируются, помечаются (тегами `@tag` в
  C3, `UPROPERTY(Replicated)` в Unreal), а код сериализации, дельты и квантования генерируется
  по рефлексии (глава 13). Ручной код сериализации для каждого компонента — источник
  рассинхронизаций, потому что его забывают обновлять.
* **Сервер — это тот же движок без рендера.** Headless-сборка (глава 20 — пример такой
  сборки) с той же симуляцией. Общий код симуляции — условие корректного предсказания.
* **Детерминизм полезен даже без lockstep**: воспроизводимые баги, реплеи, тесты.
* **Наблюдаемость**: графики RTT, потерь, размера пакетов, числа коррекций предсказания в
  debug-оверлее (глава 15). Без них сетевые баги неотличимы от «интернет плохой».
* **Версионирование протокола**: номер версии в handshake; клиент и сервер разных версий
  должны вежливо отказать, а не рассинхронизироваться.

   игры?

3. Что прячет задержка ввода в lockstep? Как rollback решает ту же проблему иначе?
4. Зачем клиент рисует чужих игроков в прошлом? Как выбрать `interp_delay`?

   общей?
6. Что такое лаг-компенсация и какую несправедливость она создаёт?
7. Почему базой для дельты служит последний **подтверждённый** снапшот?
8. Как работает пара `ack` + `ack_bits`? Почему потеря пакета с подтверждением почти
   ничего не стоит?
9. Сколько бит нужно на позицию в диапазоне 0..2048 м с точностью 0.5 см?

11. Как обнаружить и отладить рассинхронизацию в lockstep?
