# Глава 16. Аудио

> Упражнения главы: `e1601_pcm_basics` … `e1606_wav_writer`. Прочитайте главу целиком до них:
> упражнения проверяют конкретные решения, а здесь объясняется, почему они именно такие.

Аудио в движке — самая «жёсткая» по времени подсистема. Рендер может пропустить кадр: игрок
увидит подлагивание и, возможно, даже не заметит. Звук пропустить нельзя: если звуковая карта
пришла за очередными 10 мс сэмплов, а их нет, получится громкий щелчок (underrun), который
слышит каждый. Поэтому аудиодвижок — это, по сути, маленькая система реального времени внутри
игры, со своим потоком, своими правилами и своей архитектурой. При этом сама математика звука
удивительно проста: сложение и умножение массивов чисел.

## 1. Что такое цифровой звук

Звук — колебания давления воздуха. Микрофон превращает давление в напряжение, АЦП измеряет его
`sample_rate` раз в секунду. Каждое измерение — **сэмпл**, последовательность сэмплов — **PCM**
(pulse-code modulation). Воспроизведение — обратный процесс.

```
 давление
   +1 |     ..                 ..
      |   .    .             .    .
    0 +-.--------.---------.--------.---> время
      |            .     .
   -1 |              ...
        | | | | | | | | | | | | | | |   <- моменты измерения (1/sample_rate)
```

Ключевые числа:

* **Частота дискретизации** (sample rate). 44 100 Гц (CD), 48 000 Гц (видео, консоли, почти все
  современные устройства), 22 050 Гц — экономный вариант для звуков, где нет высоких частот.
  По теореме Котельникова–Найквиста частота `f` позволяет без потерь представить сигнал с
  частотами до `f / 2`. Человек слышит примерно до 20 кГц, отсюда 44.1/48 кГц.
* **Разрядность** (формат сэмпла). Файлы и устройства: int16 (−32768…32767), иногда int24.
  Внутри микшера — float32 в «номинальном» диапазоне [−1, 1].
* **Каналы**. Моно, стерео, 5.1, 7.1. Многоканальные данные обычно хранят **перемежённо**
  (interleaved): `L0 R0 L1 R1 …`. Набор сэмплов «по одному на канал» называется **кадром**
  (frame) — не путать с кадром игры. «Буфер на 512 кадров стерео» = 1024 сэмпла.

Почему микшер работает во float, хотя на выходе int16? Потому что float даёт **запас по
амплитуде** (headroom): сумма нескольких звуков может временно выйти за ±1 и потом быть
уменьшена мастер-громкостью без потерь. Int16 в такой ситуации просто переполнится: 30000 +
10000 в short — это −25536, т. е. вместо громкого звука вы получите треск полной амплитуды.

### Преобразования форматов

Преобразование float → int16 — первая точка, где новички ошибаются (упражнение `e1601`):

```c3
fn short f32_to_s16(float x)
{
    if (x > 1.0f) x = 1.0f;            // 1. clamp — иначе переполнение
    if (x < -1.0f) x = -1.0f;
    float s = x * 32767.0f;            // 2. масштаб
    return (short)(s >= 0 ? s + 0.5f : s - 0.5f);   // 3. округление к ближайшему
}
```

Отбрасывание дробной части вместо округления даёт систематическое смещение к нулю —
по сути, добавляет к сигналу шум, коррелированный с ним самим. В профессиональных
системах при понижении разрядности добавляют ещё и **дизеринг** (немного специального шума),
чтобы ошибка квантования стала некоррелированной; для игр это обычно излишне.

Отдельная тонкость — асимметрия int16: −32768 есть, +32768 нет. Поэтому обратное
преобразование делят на 32768, а «модуль» сэмпла считают в `int`.

### Децибелы

Громкость человек воспринимает логарифмически. Поэтому звукорежиссёры задают громкости в
децибелах: `gain = 10^(dB / 20)`. −6 dB ≈ 0.5 (вдвое по амплитуде), −20 dB = 0.1, −60 dB —
практически тишина. Ползунок громкости в настройках игры, который линейно меняет амплитуду,
ощущается неправильно: первая половина хода почти ничего не делает, а у нуля громкость
обрывается. Правильно — линейно по dB (с обрезкой ниже, скажем, −60 dB), либо хотя бы
`gain = slider^2` или `slider^3` как дешёвая аппроксимация.

## 2. Архитектура аудиодвижка

Типичная схема (FMOD, Wwise, miniaudio, SoLoud, аудио в Unreal устроены очень похоже):

```
  ПОТОК ИГРЫ                                          АУДИОПОТОК (high priority)
  ----------                                          -------------------------
  gameplay: play("explosion", pos)                    callback(device_buffer):
      |                                                   1. забрать команды
      v                                                   2. для каждого голоса:
  AudioSystem (API, high level)                              декодировать -> ресэмплинг
   - события, банки, параметры                               -> DSP (фильтры, огибающие)
   - 3D: позиции, затухание, доплер                          -> громкость/панорама
   - виртуализация голосов                                   -> += в шину (bus)
      |                                                   3. шины -> эффекты -> мастер
      |  lock-free очередь команд  ------------------>    4. лимитер / clip -> int16/float
      |  <------------ очередь событий/статистики         5. отдать устройству
      v
  стриминг с диска (поток IO) --> кольцевые буферы декодированных данных
```

Слои сверху вниз:

1. **Высокоуровневый API** для геймплея: «события» (event) вместо файлов. Геймдизайнер
   запускает `"footstep_grass"`, а звукорежиссёр в своём инструменте решает, что это —
   случайный из 8 вариантов с разбросом высоты ±5 % и громкости ±2 dB. Это главная идея
   Wwise/FMOD Studio: **данные отделены от кода**, звук настраивают без программиста.
2. **Голосовой менеджер**: какие звуки реально микшируются, какие «виртуальны», кого
   вытеснить (раздел 4).
3. **Микшер и граф шин**: голоса → шины (SFX, Music, Voice, UI) → мастер. На шинах — эффекты
   (реверберация, компрессор), громкость категорий (те самые ползунки в настройках), «ducking»
   (музыка приглушается, когда говорит персонаж).
4. **Бэкенд устройства**: WASAPI, CoreAudio, ALSA/PulseAudio/PipeWire, консольные API.
   Обычно устройство само вызывает ваш callback из своего потока и просит N кадров.

### Размер блока и задержка

Устройство забирает звук блоками. Размер блока — компромисс:

| блок (48 кГц) | задержка блока | риск underrun | накладные расходы |
|---|---|---|---|
| 128 кадров | 2.7 мс | высокий | высокие (часто просыпаемся) |
| 512 кадров | 10.7 мс | средний | низкие |
| 2048 кадров | 42.7 мс | низкий | минимальные |

Полная задержка «нажал кнопку → услышал» складывается из ожидания ближайшего кадра игры,
передачи команды, буфера микшера и буфера устройства (часто ещё два-три блока). Для ритм-игр
и музыкальных приложений это критично, для шутера 30–50 мс вполне терпимо, но больше 100 мс
игрок начнёт замечать рассинхрон звука выстрела и вспышки.

## 3. Микширование

Микширование — это **сложение**. Для каждого кадра выходного буфера:

```
out[f] = Σ  sample_v(pos_v + f) * gain_v * pan_v
         v
```

Всё остальное — детали, от которых зависит, хорошо ли это звучит.

### Headroom и клиппинг

Если каждый голос нормализован к ±1 и их играет 10, сумма легко достигает ±5. Варианты:

* **Мастер-громкость с запасом** (headroom). Сумма делится на константу (например, −6…−12 dB).
  Просто и честно, но при тихой сцене всё становится тише.
* **Hard clip** — обрезать по ±1. Последняя линия обороны: лучше, чем переполнение, но
  обрезанная волна содержит много высоких гармоник — звучит как хрип и треск.
* **Soft clip** — гладкая нелинейность, например кубическая `1.5x − 0.5x³` на [−1, 1]. Пики
  «закругляются», искажения мягче. Но она искажает и сигнал ниже порога.
* **Лимитер / компрессор** на мастер-шине — правильное решение в продакшене: следит за
  огибающей сигнала и плавно снижает громкость **перед** пиком (с look-ahead в несколько мс).
  Это уже настоящий DSP со своим состоянием и временем атаки/восстановления.
* **HDR audio** (DICE, Battlefield): громкости хранятся в «физических» dB, а окно
  слышимого диапазона динамически сдвигается под самый громкий звук сцены. Тихие звуки,
  выпавшие из окна, отбрасываются целиком — это одновременно и решение проблемы клиппинга, и
  критерий для виртуализации голосов.

В упражнении `e1602_mixer` вы увидите разницу числами: с мастер-громкостью 1.0 часть сэмплов
выходит за ±1, с 0.5 — ни одного.

### Панорама

Моно-звук распределяется между L и R. Наивный «линейный» закон `gl = (1 − pan)/2`,
`gr = (1 + pan)/2` в центре даёт 0.5 + 0.5. Но воспринимаемая громкость пропорциональна
**мощности** (квадрату амплитуды): 0.25 + 0.25 = 0.5, т. е. −3 dB — звук «проваливается»,
проходя через центр. Закон постоянной мощности:

```
angle = (pan + 1) * PI / 4         gl = cos(angle), gr = sin(angle)
pan = -1: (1, 0)    pan = 0: (0.707, 0.707)    pan = +1: (0, 1)
gl² + gr² = 1 при любом pan
```

Для 3D-звука панорама — частный случай **спатиализации**: позиция источника относительно
слушателя превращается в коэффициенты для каждого динамика (VBAP для многоканальных систем),
а для наушников используют HRTF — свёртку с импульсной характеристикой головы и ушей.
Плюс затухание с расстоянием (кривые min/max distance), доплер (это ресэмплинг!), окклюзия
(это фильтр нижних частот!). Видите, как всё сводится к нескольким примитивам?

### Порядок цикла и производительность

Микшер — горячий цикл, через который проходят сотни тысяч сэмплов в секунду. Правила:

* Работайте блоками, а не по сэмплу через виртуальный вызов. «Обработать 512 сэмплов голоса»
  — одна функция с плотным циклом, который компилятор векторизует.
* Вычисляйте коэффициенты (pan, gain) **один раз на блок**, но интерполируйте их линейно
  внутри блока, если они изменились, — иначе скачок громкости на границе блока даёт щелчок
  («zipper noise»).
* Планарная раскладка (отдельный массив на канал) удобнее для DSP и SIMD; перемежённая
  нужна только на выходе в устройство.

## 4. Голоса и кража голосов

Реальных голосов мало: каждый стоит декодирования (Vorbis/Opus — дорого), ресэмплинга,
фильтров, спатиализации. На консолях бюджет — десятки, максимум пара сотен. А запросов
«сыграй» в кадр боя может быть сотни: каждая пуля, гильза, шаг, крик.

Решение — **приоритеты + виртуализация**:

```
  запрос play(sound, prio, volume)
        |
        v
  есть свободный реальный голос? --да--> играть
        | нет
        v
  найти жертву: min(priority), затем min(слышимая громкость), затем самый старый
        |
  жертва важнее нового звука? --да--> отклонить (или сделать виртуальным)
        | нет
        v
  украсть: жертва -> стоп (или в виртуальные), новый звук -> в её слот
```

**Виртуальный голос** — звук, который «играет» логически (его позиция продолжает расти),
но не микшируется. Когда освобождается реальный голос или виртуальный становится громче
(игрок подошёл), он возвращается на своё место во времени. Для длинных зацикленных звуков
(водопад, двигатель) это обязательно: иначе, вернувшись к водопаду, игрок услышит тишину.

Критерий «слышимости» — не громкость в настройках, а **итоговая громкость у слушателя**:
громкость × затухание с расстоянием × громкость шины. Звук взрыва в двух километрах тише шага
под ногами.

Ещё один уровень защиты — **лимиты на категорию/событие**: «не больше 4 одновременных
звуков гильз», «не больше 1 экземпляра реплики персонажа». Это дешевле, чем общий менеджер,
и лучше звучит: 30 одинаковых шагов в одном кадре сливаются в фазовую кашу.

И, как всегда в движке, — **хендлы** (глава 03). Игровой код хранит `VoiceHandle {index, gen}`.
Когда голос крадут, `gen` растёт, и `stop(old_handle)` больше не остановит чужой звук,
занявший тот же слот. Это реальный класс багов: «почему при смерти врага иногда обрывается
музыка?» — потому что враг хранил индекс голоса, который давно отдали музыке.

Упражнение `e1603_voice_stealing` реализует именно эту логику.

## 5. Ресэмплинг

Ресэмплинг нужен постоянно:

* звук записан на 22 050 Гц, устройство работает на 48 000 Гц;
* **pitch**: случайный разброс высоты (±5 %, чтобы 100 одинаковых выстрелов не звучали как
  пулемёт клонов), обороты двигателя, slow-motion;
* **доплер**: высота меняется со скоростью источника.

Во всех случаях источник читается с дробным шагом `step = src_rate / dst_rate * pitch`.

```
src:   a0        a1        a2        a3
       |---------|---------|---------|
out:   o0     o1     o2     o3     o4          step = 0.7
       pos=0  0.7    1.4    2.1    2.8
o2 = a1 + (a2 - a1) * 0.4
```

Позицию храните в **фиксированной точке** (например, 32.32 или 16.16): индекс — старшие биты,
дробь — младшие. Это даёт точный и детерминированный шаг, без дрейфа, который накапливается
при `pos += 0.7f` на миллионах сэмплов (float с большим значением теряет младшие разряды:
на позиции 2^24 шаг 0.7 вообще перестаёт что-либо прибавлять).

Качество:

* **Без интерполяции** (nearest) — грязно, слышен алиасинг.
* **Линейная** — дёшево, приемлемо для большинства игровых звуков; слегка «глушит» верха
  и пропускает часть алиасинга при понижении частоты.
* **Кубическая (Hermite)**, **windowed sinc / polyphase FIR** — качество студийного уровня,
  стоит в разы дороже. Хороший компромисс в движке: качественный ресэмплинг при импорте
  ассета (офлайн), линейный — в рантайме только для pitch/доплера.

Важно: при понижении частоты (pitch вверх, step > 1) сигнал нужно сначала отфильтровать
ниже новой частоты Найквиста, иначе высокие частоты «завернутся» в слышимый диапазон
(алиасинг). Линейная интерполяция этого не делает.

## 6. Простой DSP

### Однополюсный фильтр нижних частот

```
y[n] = y[n-1] + a * (x[n] - y[n-1])
```

Это экспоненциальное сглаживание (то же, что вы, возможно, делали для камеры в главе 01).
Связь коэффициента с частотой среза `fc`: `a = 1 - exp(-2π · fc / sample_rate)`. Применения:
окклюзия (звук за стеной), «под водой», затухание высоких частот с расстоянием (воздух
поглощает верха). Для более крутых срезов используют biquad-фильтры (формулы — в «Audio EQ
Cookbook» Роберта Бристоу-Джонсона).

**У фильтра есть состояние**, и это архитектурное решение, а не деталь: `y[n-1]` должно
жить **в голосе** (или в узле графа шин) между вызовами микшера. Если обнулять его в начале
каждого блока — на каждой границе блока будет щелчок. Если хранить один фильтр на все голоса
— голоса начнут «протекать» друг в друга.

Ещё один подводный камень — **денормализованные числа**. Когда сигнал затухает к нулю, `y`
становится крошечным (1e-40), и операции с денормалами на x86 замедляются в десятки раз.
Аудиокод выставляет флаги FTZ/DAZ процессора или добавляет к сигналу неслышимый «шум» 1e-20.

### Огибающая ADSR

```
level
 1 |   /\
   |  /  \________            A — attack: рост 0 -> 1
 S | /            \           D — decay: спад 1 -> S
   |/              \          S — sustain: держим, пока нота «нажата»
 0 +----------------\---->    R — release: спад от ТЕКУЩЕГО уровня к 0
    A   D    S     R
                ^ note_off
```

ADSR — классика синтезаторов, но в играх огибающие повсюду: плавное появление/исчезновение
звука (fade), «атака» шагов, ducking музыки. Главные ошибки:

* note_off во время атаки начинает release с уровня `S` или 1, а не с текущего — скачок
  громкости, щелчок;
* остановка звука «мгновенно» (`active = false`) вместо короткого (5–10 мс) fade-out. **Любой
  разрыв волны слышен как щелчок.** Поэтому «stop» в хорошем аудиодвижке — это всегда
  короткий release, а не обнуление.

Огибающая — это конечный автомат по сэмплам; упражнение `e1604_resample_dsp` реализует его
вместе с ресэмплингом и фильтром.

## 7. Аудиопоток

### Золотые правила реального времени

Callback аудиоустройства вызывается из потока с высоким (часто realtime) приоритетом, и у
него жёсткий дедлайн. В нём **нельзя**:

* брать мьютекс, который может держать поток игры (priority inversion: аудиопоток ждёт
  низкоприоритетный поток, который вытеснен кем-то ещё);
* выделять/освобождать память (malloc внутри берёт локи, может уйти в ядро за страницами);
* делать IO, логировать в файл, печатать;
* ждать чего-либо с неограниченным временем.

Ross Bencina сформулировал это в статье «Real-time audio programming 101: time waits for
nothing» — обязательное чтение.

### Как общаться с аудиопотоком

```
   поток игры                                            аудиопоток
  +-----------+   SPSC: команды (play/stop/param)   +-----------------+
  |  Audio    | ----------------------------------> |   микшер        |
  |  System   | <---------------------------------- |                 |
  +-----------+   SPSC: события (finished, stats)   +-----------------+
         |                                                   ^
         |  ассеты: загружены заранее, неизменяемы,          |
         +---- передаются указателем; освобождаются ---------+
               только после подтверждения от аудиопотока
```

1. **Команды** — маленькие POD-структуры фиксированного размера в lock-free кольцевом буфере
   с одним производителем и одним потребителем. Это самая простая lock-free структура, и её
   надо уметь написать с закрытыми глазами (см. также главу 12):

```c3
fn bool CommandQueue.push(&self, Command c)
{
    uint t = self.tail.load(RELAXED);        // свой индекс
    uint h = self.head.load(ACQUIRE);        // чужой индекс
    if (t - h == CAP) return false;          // полно
    self.buf[t % CAP] = c;                   // 1. данные
    self.tail.store(t + 1, RELEASE);         // 2. публикация
    return true;
}
```

   RELEASE на публикации гарантирует, что потребитель, увидевший новый `tail` через ACQUIRE,
   увидит и записанную ячейку. Без этого на ARM (и даже на x86 после оптимизаций компилятора)
   потребитель может прочитать мусор.

2. **Обратный канал** — вторая SPSC-очередь: «голос 17 доиграл», «уровень громкости шины
   такой-то» (для индикаторов). Поток игры разбирает её раз в кадр.

3. **Владение данными.** Сэмплы ассета, которые сейчас играет голос, нельзя освободить из
   потока игры. Типичная схема: игра отправляет команду «отпусти звук X», аудиопоток
   перестаёт его использовать и отвечает событием «X свободен», и только тогда игра
   освобождает память. Альтернатива — отложенное освобождение через N кадров или подсчёт
   ссылок с атомарным счётчиком.

4. **Время в командах.** Если команда применяется «в начале следующего блока», время звука
   квантуется размером блока, а ещё «дрожит» вместе с частотой кадров игры. Для ритмичных
   звуков (автоматная очередь, музыка) это слышно. Решение — **sample-accurate scheduling**:
   команда несёт абсолютное время в сэмплах, и микшер применяет её точно на нужном сэмпле
   внутри блока. Игра планирует команды чуть-чуть в будущее (на величину задержки).

Упражнение `e1605_audio_thread` демонстрирует побочный бонус такого подхода: результат
микширования перестаёт зависеть от планировщика ОС. Два потока, очередь на 8 команд,
которая постоянно переполняется, — а контрольная сумма выхода всегда одна и та же.

### Почему не просто мьютекс?

На практике многие инди-движки и даже некоторые AAA делают проще: мьютекс с очень короткой
критической секцией. Это «почти всегда работает», пока поток игры не будет вытеснен ОС,
держа этот мьютекс. На ПК с запасом CPU это случается редко, на перегруженной системе —
регулярно, и проявляется как редкие необъяснимые щелчки, которые невозможно воспроизвести
в отладчике. Lock-free очередь стоит 30 строк кода и снимает проблему навсегда.

## 8. Стриминг и форматы ассетов

Короткие звуки (выстрелы, UI) хранят распакованными в памяти: PCM или ADPCM (сжатие 4:1,
дешёвое декодирование). Длинные (музыка, диалоги, эмбиенты) — **стримят** с диска сжатыми
(Vorbis, Opus, на консолях — аппаратные кодеки): поток IO читает куски в кольцевой буфер,
декодер (часто тоже в отдельном потоке) наполняет буфер PCM, микшер читает из него.
Микшер никогда не ждёт IO: если данных нет — тишина и счётчик underrun в статистике.

Ассеты на этапе импорта (глава 07) нормализуют: приводят к частоте устройства, считают
громкость (LUFS) для нормализации, подрезают тишину, кодируют. Всё, что можно сделать
офлайн, делайте офлайн.

## 9. Отладка: пишите WAV

Лучший отладочный инструмент аудиопрограммиста — дамп в WAV. Записали выход мастер-шины или
одного голоса, открыли в Audacity — и глазами видно щелчки (вертикальные разрывы волны),
клиппинг (плоские «полки» на ±1), сдвиги фазы, пропуски блоков. На слух «что-то
потрескивает» локализовать почти невозможно, на картинке — сразу.

Формат WAV (RIFF) тривиален: 44 байта заголовка и сырые сэмплы. Заголовок пишется поле за
полем в little-endian (упражнение `e1606_wav_writer`):

```
"RIFF" | size-8 | "WAVE" | "fmt " | 16 | fmt=1 | ch | rate | byte_rate | align | bits | "data" | n | ...
```

Не делайте `memcpy` структуры заголовка в файл: выравнивание полей и порядок байт — свойства
платформы, а не формата. Это тот же принцип, что в главе 13 о сериализации.

Ещё полезно иметь в движке:

* **оффлайн-рендер**: прогнать микшер быстрее реального времени, без устройства, — для
  автотестов («после этой последовательности команд контрольная сумма выхода такая-то»);
* **визуализатор голосов** в debug-оверлее (глава 15): какие голоса реальные, какие
  виртуальные, их громкость, приоритеты, сколько было краж за секунду;
* **профилирование** времени callback'а: процент от бюджета блока. 50 % — тревожный звонок.

## 10. Как это делают настоящие движки

* **FMOD / Wwise** — промышленный стандарт middleware. Отдельные редакторы для
  звукорежиссёров, события и параметры (RTPC в Wwise), банки, граф шин, виртуальные голоса,
  профайлер, подключающийся к запущенной игре по сети. Движок общается с ними через
  высокоуровневый API «событий».
* **miniaudio** (один заголовочный файл на C) — бэкенды для всех платформ, декодеры,
  ресэмплер, граф узлов. Отличный код для чтения: как выглядит абстракция над WASAPI/
  CoreAudio/ALSA.
* **SoLoud** — компактный игровой аудиодвижок: голоса, шины, фильтры, 3D, виртуализация.
  Хорошая точка для изучения «как это собрать вместе».
* **Unreal Audio Mixer** — свой программный микшер поверх платформенных API, патч-кабели
  между эффектами (MetaSounds — граф DSP, редактируемый дизайнерами).
* **DICE HDR Audio** (Frostbite) — динамическое окно громкости, о котором говорилось выше.

Общее у всех: отдельный аудиопоток, lock-free связь с игрой, данные-ориентированная
настройка звука людьми, а не кодом, и «голоса» как управляемый ресурс с бюджетом.

## 11. Подводные камни (чек-лист)

* Переполнение int16 при микшировании в целых — микшируйте во float (или int32).
* Отбрасывание дробной части вместо округления при конвертации.
* Любой разрыв волны — щелчок: старт/стоп без fade, обнуление состояния фильтра, скачок
  громкости/панорамы на границе блока.
* Мьютексы и аллокации в аудиопотоке.
* Освобождение памяти ассета, который ещё играет.
* Float-позиция в ресэмплере на длинных звуках.
* Денормалы в хвостах фильтров и реверберации.
* Хранение индекса голоса вместо хендла с поколением.
* Линейный ползунок громкости.
* Предположение, что устройство всегда просит одинаковое число кадров (не всегда!) и что
  его частота совпадает с частотой ассетов (не совпадает).
