# Глава 12. Системные вызовы Linux напрямую

Ваша программа живёт в «песочнице» пользовательского режима: она не может
сама прочитать диск, нарисовать пиксель, получить память или даже
завершиться. Всё это делает ядро операционной системы по просьбе
программы — через **системные вызовы**. `printf`, `malloc`, `fopen`, `io::printn`,
`mem::new` — всё это обёртки, которые в конце концов выполняют
инструкцию `syscall`.

В этой главе мы уберём обёртки и поговорим с ядром напрямую. Это нужно,
чтобы понимать, что на самом деле стоит за стандартной библиотекой, как
устроены `strace` и песочницы (seccomp), и чтобы написать JIT в главе 15
(`mmap` + `mprotect`).

Упражнения: `a1201`–`a1205`.

## 1. Как устроен системный вызов

Инструкция `syscall` (x86-64):

1. сохраняет `rip` следующей инструкции в `rcx`, а `rflags` — в `r11`;
2. переключает процессор в режим ядра (ring 0) и прыгает на адрес из
   MSR `LSTAR` — точку входа ядра;
3. ядро берёт номер вызова из `rax`, аргументы — из регистров, выполняет
   работу, кладёт результат в `rax` и возвращается инструкцией `sysret`.

Соглашение Linux x86-64:

| | Регистр |
|---|---|
| номер вызова | `rax` |
| аргументы 1–6 | `rdi`, `rsi`, `rdx`, **`r10`**, `r8`, `r9` |
| результат | `rax` |
| портятся | `rcx`, `r11` (и, конечно, `rax`) |
| сохраняются | все остальные, включая xmm |

Отличие от обычного вызова функции — четвёртый аргумент в `r10` вместо
`rcx`, ведь `rcx` занят адресом возврата. Аргументов в стеке не бывает
никогда (максимум 6).

Стоимость: сам переход в ядро и обратно — порядка 50–100 нс на
современном процессоре (больше с митигациями Spectre/Meltdown: KPTI
переключает таблицы страниц). Это в сотни раз дороже вызова функции —
поэтому стандартные библиотеки **буферизуют** вывод и выделяют память
крупными кусками.

Некоторые «вызовы» (`clock_gettime`, `gettimeofday`, `getcpu`) ядро
реализует без перехода в ядро — через vDSO, маленькую библиотеку,
которую ядро отображает в адресное пространство каждого процесса.

Старый 32-битный механизм — `int 0x80` с номерами из другой таблицы и
аргументами в `ebx, ecx, edx, ...`. В 64-битном коде его использовать не
надо (он обрезает указатели до 32 бит).

## 2. Самые нужные вызовы

| Номер | Имя | Сигнатура |
|---|---|---|
| 0 | `read` | `(fd, buf, count) → байтов` |
| 1 | `write` | `(fd, buf, count) → байтов` |
| 2 | `open` | `(path, flags, mode) → fd` (современные libc используют `openat` = 257) |
| 3 | `close` | `(fd) → 0` |
| 9 | `mmap` | `(addr, len, prot, flags, fd, off) → addr` |
| 10 | `mprotect` | `(addr, len, prot) → 0` |
| 11 | `munmap` | `(addr, len) → 0` |
| 12 | `brk` | `(addr) → новый конец кучи` |
| 39 | `getpid` | `() → pid` |
| 60 | `exit` | `(code)` — завершает поток |
| 231 | `exit_group` | `(code)` — завершает процесс |
| 228 | `clock_gettime` | `(clk, timespec*)` |
| 202 | `futex` | основа мьютексов и condvar |
| 56/435 | `clone`/`clone3` | создание потоков и процессов |

Полная таблица: `/usr/include/asm/unistd_64.h`, `man 2 syscalls`,
`man 2 syscall` (раздел про соглашения для всех архитектур). Номера
различаются между архитектурами (на aarch64 `write` = 64)!

## 3. Ошибки и errno

Ядро возвращает ошибку как **отрицательное число** `-errno` в диапазоне
`[-4095, -1]`. Всё остальное — успех. Проверка — одна беззнаковая
инструкция:

```asm
    syscall
    cmp  rax, -4096
    ja   .error           ; rax ∈ [-4095, -1] (беззнаково — самые большие числа)
```

Почему не `test rax, rax; js`? Потому что некоторые успешные результаты
выглядят отрицательными: `mmap` на системах с большим адресным
пространством, `lseek` с огромным смещением, `getpriority`.

Переменная `errno` — чисто **библиотечная** конвенция. libc превращает
`-EBADF` в `return -1` + `errno = 9`. При этом `errno` у каждого потока
своя (thread-local, в glibc — через сегмент `fs`). Частые коды:

| errno | Код | Значение |
|---|---|---|
| EPERM | 1 | нет прав |
| ENOENT | 2 | нет файла |
| EINTR | 4 | прерван сигналом — повторите |
| EBADF | 9 | плохой файловый дескриптор |
| EAGAIN | 11 | попробуйте позже (неблокирующий ввод-вывод) |
| ENOMEM | 12 | нет памяти |
| EFAULT | 14 | плохой указатель (ядро не может читать/писать по нему) |
| EINVAL | 22 | неверный аргумент |
| ENOSYS | 38 | нет такого вызова |

Заметьте `EFAULT`: передав ядру мусорный указатель, вы не получите
segfault — ядро аккуратно проверит адрес и вернёт ошибку. А вот если
вы сами разыменуете тот же указатель — SIGSEGV.

## 4. write и буферизация

```asm
; long sys_write(int fd, char* buf, long len)
sys_write:
    mov eax, 1
    syscall
    ret
```

Аргументы функции уже лежат в `rdi`, `rsi`, `rdx` — там, где их ждёт ядро.
Обёртки glibc выглядят почти так же (плюс обработка errno и отмены
потоков).

Ловушка — **буферизация**. Стандартная библиотека копит вывод в буфере и
отдаёт ядру крупными порциями. Если вы смешиваете `io::print` и прямой
`write`, порядок строк на выходе может не совпасть с порядком вызовов.
В C3 `io::printn`/`io::printfn` сбрасывают буфер stdout после каждой
строки, а `io::print`/`io::printf` — нет. Надёжное правило: перед прямым
системным вызовом сделайте `(void)io::stdout().flush();`.

`write` может записать **меньше**, чем просили (короткая запись в pipe
или сокет, прерывание сигналом). Правильная обёртка повторяет вызов в
цикле, пока не запишет всё или не получит настоящую ошибку. Для `EINTR`
— просто повторить.

## 5. Память: mmap, mprotect, munmap

```asm
; void* page_alloc(long len)
page_alloc:
    mov  rsi, rdi          ; len
    xor  edi, edi          ; addr = NULL — пусть ядро выберет
    mov  edx, 3            ; PROT_READ | PROT_WRITE
    mov  r10d, 0x22        ; MAP_PRIVATE | MAP_ANONYMOUS
    mov  r8, -1            ; fd = -1
    xor  r9d, r9d          ; offset = 0
    mov  eax, 9
    syscall
    cmp  rax, -4096
    ja   1f
    ret
1:  xor  eax, eax          ; ошибка → NULL
    ret
```

| Константа | Значение |
|---|---|
| `PROT_NONE / READ / WRITE / EXEC` | 0 / 1 / 2 / 4 |
| `MAP_SHARED / PRIVATE` | 0x01 / 0x02 |
| `MAP_FIXED` | 0x10 |
| `MAP_ANONYMOUS` | 0x20 |
| `MAP_NORESERVE` | 0x4000 |
| `MAP_POPULATE` | 0x8000 |

Что важно знать:

* Память выдаётся **страницами** (4096 байт; есть и «огромные» страницы
  2 МиБ/1 ГиБ). Адрес выровнен на страницу, длина округляется вверх.
* Анонимная память **гарантированно обнулена** — ядро не может отдать вам
  чужие данные.
* Память выделяется **лениво**: `mmap` лишь резервирует диапазон адресов.
  Физическая страница появится при первом обращении (page fault, ~1 мкс,
  включая обнуление). Поэтому можно зарезервировать 64 ГиБ адресного
  пространства под арену и платить только за то, что тронули, —
  излюбленный приём аллокаторов движков.
* `mprotect` меняет права уже выделенных страниц; адрес должен быть
  выровнен на страницу (иначе `EINVAL`).
* Страница с `PROT_WRITE|PROT_EXEC` одновременно — дыра в безопасности.
  Правило W^X: сначала пишем код (RW), потом переключаем на RX. Так
  работают все JIT-компиляторы (глава 15). На некоторых системах (SELinux,
  OpenBSD, macOS с hardened runtime) W+X запрещено вовсе.
* `malloc` в glibc использует `brk` для маленьких блоков и `mmap` — для
  больших (> 128 КиБ по умолчанию).

## 6. Завершение процесса

`exit_group(code)` (231) завершает все потоки процесса; `exit` (60) —
только текущий поток (так завершаются потоки, созданные `clone`).
Функция `_exit()` из libc — это `exit_group`. А `exit()` из libc сначала
вызывает обработчики `atexit`, сбрасывает буферы stdio и только потом
`exit_group`. Прямой системный вызов ничего этого не делает: если
что-то лежит в буфере stdout — оно потеряно.

Код выхода — младшие 8 бит: `exit_group(256)` даст код 0.

## 7. Программа совсем без libc

Для полноты — минимальная программа, которой не нужна ни libc, ни
рантайм C3:

```asm
    .intel_syntax noprefix
    .section .rodata
msg:    .ascii "hello, kernel\n"
    .set msg_len, . - msg     # константа ДО использования (см. ниже)

    .text
    .globl _start
_start:                       # точка входа: rsp указывает на argc
    mov  eax, 1               # write
    mov  edi, 1
    lea  rsi, [rip + msg]
    mov  edx, msg_len
    syscall
    mov  eax, 231             # exit_group(0)
    xor  edi, edi
    syscall
```

```
cc -nostdlib -static -o hello hello.s && ./hello
```

Тонкость GNU as в Intel-синтаксисе: символ, который ещё не определён в
момент использования, считается **адресом в памяти**, и `mov edx, msg_len`
превратится в загрузку из памяти по адресу 14 — segfault. Поэтому `.set`
стоит раньше `mov`; либо пишите явно `mov edx, OFFSET msg_len`.

Бинарник займёт несколько килобайт. При входе в `_start` на стеке лежат
`argc`, `argv[]`, `NULL`, `envp[]`, `NULL`, затем вектор auxv — это всё,
что ядро передаёт программе.

## 8. Инструменты

* `strace ./prog` — показывает каждый системный вызов с аргументами и
  результатом. `strace -c` — статистика. Попробуйте на любом упражнении
  курса: увидите `mmap`/`mprotect` при старте (загрузчик), `write` при
  печати, `exit_group` в конце.
* `ltrace` — то же для вызовов библиотечных функций.
* `/proc/self/maps` — карта памяти процесса (что и с какими правами
  отображено).
* `man 2 <вызов>` — документация по каждому вызову.

## 9. Подводные камни

* Четвёртый аргумент — `r10`, не `rcx`.
* `syscall` портит `rcx` и `r11` — не держите там живые значения.
* Ошибка — `[-4095, -1]`, проверка беззнаковая (`ja`).
* Порядок вывода при смешивании буферизованного вывода и прямого `write`.
* Короткие записи и `EINTR`.
* `exit_group` не сбрасывает буферы.
* Номера вызовов зависят от архитектуры.
