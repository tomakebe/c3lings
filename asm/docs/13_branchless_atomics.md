# Глава 13. Branchless-код, атомарные операции, барьеры памяти

Две темы этой главы объединяет одно: в них поведение программы зависит
не только от того, *что* вычисляется, но и от того, *как* процессор это
исполняет — спекулятивно, с переупорядочиванием, на нескольких ядрах.

Упражнения: `a1301`–`a1305`.

## Карта главы

**Что вы узнаете.**

* Почему обычный `if` иногда стоит процессору 15–20 тактов и как
  написать то же самое вообще без условного перехода (`cmov`, `setcc`,
  `sbb`, битовые маски).
* Почему `count++` из нескольких потоков теряет увеличения и как это
  чинит префикс `lock`.
* Что такое CAS (compare-and-swap) и как на нём строится любая атомарная
  операция.
* Как устроен спинлок — простейшая блокировка.
* Что такое «модель памяти», какую единственную перестановку разрешает
  x86 и что такое барьеры (`mfence`, `lfence`, `sfence`).

**Зачем это нужно.** Branchless-код — основной инструмент ускорения
«горячих» циклов на непредсказуемых данных (поиск, сортировка,
фильтрация, физика в играх). Атомики и барьеры — фундамент любого
многопоточного кода: пула задач в движке, счётчиков ссылок, очередей
между потоком рендера и логики.

**Что нужно знать заранее.**

* Флаги и `cmp`/`test` (глава 02), условные переходы `jcc` (глава 03).
* Адресация памяти `[rdi + rcx*4]` (глава 04).
* Соглашение о вызовах: аргументы в `rdi, rsi, rdx`, результат в `rax`
  (глава 05).
* Битовые операции и `sar` (глава 08) — для трюков с масками.

**Какие упражнения какие разделы используют.**

| Упражнение | Разделы |
|---|---|
| `a1301_setcc_cmov` | 1–3 |
| `a1302_branchless_search` | 2–4 (особенно 3.4 и 4.1) |
| `a1303_atomic_add` | 6–7 |
| `a1304_cas` | 7–8 |
| `a1305_spinlock` | 7, 9, 10 |

## Часть 1. Код без ветвлений

### 1. Цена ветвления

#### 1.1. Конвейер: процессор как кухня

**Конвейер** (pipeline) — это способ исполнять инструкции «внахлёст».
Представьте кухню ресторана: один повар режет, второй жарит, третий
выкладывает на тарелку. Пока третий выкладывает блюдо №1, второй уже
жарит №2, а первый режет №3. Каждое блюдо проходит все стадии, но
кухня в целом выдаёт по блюду каждую минуту.

Процессор устроен так же: инструкция проходит стадии «выбрать из
памяти → декодировать → переименовать регистры → дождаться операндов
→ выполнить → завершить». Современный процессор — конвейер глубиной
15–20 стадий, который одновременно держит в работе сотни инструкций.

#### 1.2. Предсказатель переходов

Проблема: что делать с условным переходом `jl metka`? Чтобы узнать,
куда идти, нужно дождаться `cmp`, а он ещё где-то в середине конвейера.
Ждать — значит простаивать 15–20 тактов на каждом `if`.

Поэтому процессор **не ждёт**. Встретив условный переход, он спрашивает
**предсказатель переходов** (branch predictor) — блок, который помнит,
как этот переход вёл себя раньше, — и угадывает направление. Дальше
процессор **спекулятивно** (то есть «на всякий случай, без гарантии»)
выполняет код по угаданному пути.

* **Угадал** — переход стоит почти ноль.
* **Не угадал** (misprediction, «промах предсказания») — всё начатое
  после перехода выбрасывается, и конвейер заполняется заново:
  **15–20 тактов** штрафа (на Zen 2 / Skylake).

Аналогия: официант, не дожидаясь заказа, несёт постоянному гостю
«как обычно». Если гость сегодня хочет то же — сэкономили время. Если
нет — блюдо в мусор, готовим заново.

#### 1.3. Когда предсказатель бессилен

Предсказатель очень хорош на регулярных паттернах (циклы, «почти всегда
да», повторяющиеся последовательности) и беспомощен на случайных данных.
Если условие истинно в 50% случаев случайным образом, он ошибается
примерно в половине случаев — и каждый раз платит 15–20 тактов.

Классическая демонстрация — суммирование элементов больше 128 в массиве:
на отсортированном массиве код работает в несколько раз быстрее, чем на
перемешанном, хотя инструкции те же самые. На отсортированном массиве
условие выглядит как «нет, нет, нет, …, да, да, да» — это легко угадать.

> **Коротко:** условный переход — это ставка. Выигранная ставка почти
> бесплатна, проигранная стоит 15–20 тактов. На случайных данных
> ставки проигрываются часто — и тогда выгодно вообще не делать ставку,
> а вычислить результат без перехода.

### 2. Инструкции

#### 2.1. Сводная таблица

| Инструкция | Действие |
|---|---|
| `setCC r/m8` | байт = условие ? 1 : 0 |
| `cmovCC r, r/m` | если условие — `r = src` (16/32/64 бит) |
| `adc`/`sbb` | прибавить/вычесть CF — «условие» как число |
| `sbb eax, eax` | eax = CF ? -1 : 0 (маска!) |

Здесь `CC` — это не буквы «CC», а место, куда подставляется код условия:
`setl`, `cmovge`, `setne` и т.д. Условия CC — те же, что у `jcc`:

| CC | Условие | Флаги |
|---|---|---|
| `e`/`z`, `ne`/`nz` | равно / не равно | ZF |
| `l`, `le`, `g`, `ge` | знаковые <, ≤, >, ≥ | SF, OF, ZF |
| `b`/`c`, `be`, `a`, `ae`/`nc` | беззнаковые <, ≤, >, ≥ | CF, ZF |
| `s`, `ns` | отрицательно / нет | SF |
| `o`, `no` | переполнение | OF |
| `p`, `np` | чётность (NaN после `ucomisd`) | PF |

Напоминание из главы 02: `l/g` (less/greater) — для **знаковых**
чисел, `b/a` (below/above) — для **беззнаковых**. Перепутать их — одна
из самых частых ошибок.

#### 2.2. `setCC` — «условие в число»

`setl al` читает флаги (как это сделал бы `jl`) и вместо перехода
пишет в байт `al` число: 1, если условие истинно, иначе 0.

Важно: `setcc` пишет **один байт** — остальные 56 бит `rax` остаются
какими были. Если там лежал мусор, то `rax` после `setl al` — это не 0/1,
а мусор с подменённым младшим байтом.

Пример (было `rax = 0x0000_0000_DEAD_BE00`, условие истинно):

| Шаг | `rax` |
|---|---|
| до `setl al` | `0x00000000DEADBE00` |
| после `setl al` | `0x00000000DEADBE01` ← не 1! |

Поэтому регистр обнуляют **заранее**, причём **до `cmp`**:

```asm
xor   eax, eax        ; rax = 0 (и флаги испорчены — но cmp ещё впереди)
cmp   rdi, rsi        ; теперь флаги отражают сравнение
setl  al              ; rax = 0 или 1 — чисто
```

Если поставить `xor` **между** `cmp` и `setl`, то `xor` перезапишет флаги
(он ставит ZF=1, CF=0, OF=0, SF=0), и `setl` прочитает уже флаги от
`xor`, а не от `cmp`. Альтернатива — `setl al` и потом `movzx eax, al`
(расширение байта нулями, флаги не трогает).

#### 2.3. `cmovCC` — «условное копирование»

`cmovl rax, rsi` значит: «если по флагам выходит "меньше" — скопировать
`rsi` в `rax`, иначе оставить `rax` как есть». Перехода нет: процессор
всегда выполняет одну и ту же инструкцию, просто её результат —
одно из двух значений.

Аналогия: вместо «если идёт дождь, пойду по левой дороге, иначе по
правой» вы говорите «возьму с собой зонт = (идёт дождь ? зонт : ничего)»
и идёте по одной дороге.

#### 2.4. Особенности

* `setcc` пишет **один байт** — обнуляйте регистр заранее (`xor eax, eax`
  **до** `cmp`, потому что `xor` портит флаги) или используйте `movzx`.
* `cmov` не принимает непосредственный операнд. `cmovl rax, 0` — ошибка
  ассемблера; сначала положите 0 в какой-нибудь регистр.
* `cmov` с памятью читает её **всегда** — даже когда условие ложно. Нельзя
  заменять `p ? *p : 0` на `cmov` с разыменованием `p`: при `p == null`
  программа упадёт, хотя «по смыслу» чтения быть не должно.
* `cmov` — не «бесплатная» ветка: он создаёт **зависимость по данным** от
  обоих входов и флагов. Если ветка хорошо предсказывается, `jcc` быстрее:
  процессору не надо ждать сравнения.

Последний пункт стоит разжевать. **Зависимость по данным** — это когда
инструкция не может начаться, пока не готовы её входы. `cmov` нужны оба
значения *и* флаги — он обязан ждать `cmp`. А `jcc` с верным
предсказанием не ждёт ничего: процессор уже работает дальше. Поэтому:

| Ситуация | Что быстрее |
|---|---|
| условие случайное (≈50/50) | `cmov`/`setcc` |
| условие почти всегда одно и то же (99/1) | `jcc` |
| в ветке много работы | `jcc` (иначе придётся считать обе ветки) |
| в ветке чтение по возможно-невалидному указателю | только `jcc` |

> **Частые ошибки**
> * `xor eax, eax` между `cmp` и `setcc` — флаги затёрты.
> * `setl al` без обнуления — в старших байтах мусор.
> * `cmovl rax, 0` — нельзя, нужен регистр.
> * `setl` вместо `setb` (или наоборот) — знаковость перепутана.

> **Коротко:** `setCC` превращает условие в 0/1 (только байт!),
> `cmovCC` выбирает одно из двух значений без перехода. Оба читают те же
> флаги, что и `jcc`.

### 3. Приёмы

Ниже — все приёмы одним листингом (как в исходной версии главы), а
потом каждый разобран по шагам.

```asm
; max(a, b)
mov   rax, rdi
cmp   rdi, rsi
cmovl rax, rsi

; abs(x)
mov   rax, rdi
neg   rax
cmovs rax, rdi        ; если -x < 0, значит x > 0 — берём x

; sign(x) = (x > 0) - (x < 0)
xor   eax, eax
xor   ecx, ecx
test  rdi, rdi
setg  al
setl  cl
sub   eax, ecx

; count += (a[i] < p)
cmp   [rdi + rcx*4], edx
setl  r8b             ; r8 обнулён один раз вне цикла
add   rax, r8

; маска без ветвлений: m = (x < y) ? -1 : 0  (беззнаково)
cmp   rdi, rsi
sbb   rax, rax
```

Все эти фрагменты собраны и проверены (`cc` + GNU as).

#### 3.1. `max(a, b)` по шагам

```asm
mov   rax, rdi        ; предполагаем, что ответ — a
cmp   rdi, rsi        ; флаги по a - b
cmovl rax, rsi        ; если a < b (знаково) — ответ b
```

Трасса для `a = 3, b = 9`:

| Инструкция | `rax` | флаги | комментарий |
|---|---|---|---|
| `mov rax, rdi` | 3 | — | |
| `cmp rdi, rsi` | 3 | 3−9 < 0 → «меньше» истинно | |
| `cmovl rax, rsi` | 9 | | условие истинно, копируем |

Для `a = -5, b = -7`: `cmp` даёт −5 − (−7) = 2 > 0, «меньше» ложно,
`cmovl` ничего не делает, `rax = -5`. Правильно.

Идея «сначала положить один ответ, потом условно заменить другим» —
главный шаблон branchless-кода. Запомните его.

Для сравнения — что генерирует компилятор C3 (`-O3`) для
`fn long kmax(long a, long b) => a < b ? b : a;`:

```asm
mov    rax, rsi       ; предполагаем ответ b
cmp    rdi, rsi
cmovg  rax, rdi       ; если a > b — ответ a
ret
```

Тот же шаблон, просто «предположение» другое.

#### 3.2. `abs(x)` по шагам

```asm
mov   rax, rdi        ; rax = x
neg   rax             ; rax = -x; SF = знак результата (-x)
cmovs rax, rdi        ; если -x < 0, значит x > 0 — берём x
```

`neg` вычисляет `0 - x` и выставляет флаги как обычное вычитание. `SF` —
старший (знаковый) бит результата.

| x | после `neg`: `rax` | SF | `cmovs` | результат |
|---|---|---|---|---|
| −42 | 42 | 0 | не копирует | 42 |
| 42 | −42 | 1 | копирует x | 42 |
| 0 | 0 | 0 | не копирует | 0 |

Особый случай: `x = long::min = -2⁶³`. Число `+2⁶³` в `long` не
помещается, и `neg` возвращает то же `-2⁶³` (SF=1, OF=1). `cmovs` берёт
`x` — тоже `-2⁶³`. Так же ведёт себя `abs` в C3/C — это переполнение,
и правильного ответа тут нет. Тесты упражнения этот случай для `abs` не
проверяют.

#### 3.3. `sign(x)` по шагам

Формула `sign(x) = (x > 0) - (x < 0)`: ровно одно из условий истинно
(или ни одного при `x = 0`).

```asm
xor   eax, eax        ; rax = 0 — ДО test, т.к. xor портит флаги
xor   ecx, ecx        ; rcx = 0
test  rdi, rdi        ; флаги по x & x, то есть по самому x
setg  al              ; al = (x > 0)
setl  cl              ; cl = (x < 0)  — флаги те же, setg их не трогает
sub   eax, ecx        ; (x > 0) - (x < 0)
```

| x | `al` | `cl` | `eax` |
|---|---|---|---|
| −100 | 0 | 1 | 0 − 1 = −1 |
| 0 | 0 | 0 | 0 |
| 5 | 1 | 0 | 1 |
| `long::min` | 0 | 1 | −1 |

Заметьте: `setcc` флаги **не меняет**, поэтому два `setcc` подряд читают
одни и те же флаги от `test`. А вот `sub` их меняет — но он последний.

Почему `test rdi, rdi`, а не `cmp rdi, 0`? Результат по флагам тот же
(для сравнения с нулём `test` выставляет OF=0, а SF/ZF — по `x`), но
`test` короче в кодировке. Это идиома.

#### 3.4. Подсчёт `count += (a[i] < p)`

Вместо `if (a[i] < p) count++` мы **всегда** прибавляем — но прибавляем
0 или 1:

```asm
cmp   [rdi + rcx*4], edx   ; флаги по a[i] - p (32-битные int)
setl  r8b                  ; r8b = (a[i] < p); r8 обнулён один раз вне цикла
add   rax, r8              ; count += 0 или 1
```

Почему `r8` достаточно обнулить один раз вне цикла? Потому что `setl r8b`
пишет только младший байт, а старшие байты `r8` никто внутри цикла не
трогает — они так и остаются нулями. Значение в `r8` всегда 0 или 1.

Трасса для `a = {5, -3, 12, 7}`, `p = 7`:

| i | a[i] | a[i] < 7 | `r8` | `rax` (count) |
|---|---|---|---|---|
| 0 | 5 | да | 1 | 1 |
| 1 | −3 | да | 1 | 2 |
| 2 | 12 | нет | 0 | 2 |
| 3 | 7 | нет | 0 | 2 |

Компилятор C3 (`-O3`) делает для цикла `if (a[i] < p) c++;` ровно это в
«хвосте» цикла (основную часть он вдобавок векторизует — глава 10):

```asm
xor    r8d, r8d
cmp    DWORD PTR [rdi+rcx*4], edx
setl   r8b
add    rax, r8
```

Здесь `xor r8d, r8d` стоит внутри цикла **перед** `cmp` — тоже
правильно (флаги портятся до сравнения).

#### 3.5. Маска через `sbb`

**Маска** — число, в котором все биты либо единицы (`-1` =
`0xFFFF…FFFF`), либо нули (`0`). С маской удобно делать «условный
выбор» обычными `and`/`or`/`xor`.

```asm
cmp   rdi, rsi        ; CF = 1, если rdi < rsi БЕЗЗНАКОВО (нужен заём)
sbb   rax, rax        ; rax = rax - rax - CF = -CF
```

`sbb` — «вычесть с заёмом»: `dst = dst - src - CF`. Когда `dst` и `src`
— один регистр, остаётся `-CF`: либо `0`, либо `-1`.

| x, y (беззнак.) | CF после `cmp` | `rax` после `sbb` |
|---|---|---|
| 3, 5 | 1 | `0xFFFFFFFFFFFFFFFF` (−1) |
| 5, 3 | 0 | `0x0000000000000000` |
| 1, `0xFFFF…FFFF` | 1 | −1 |

Помните: CF — флаг **беззнакового** сравнения. Для знаковых чисел этот
трюк не работает (в `a1302` элементы — знаковые `int`, поэтому там
нужен `setl`).

#### 3.6. Арифметические трюки без флагов

Арифметические трюки без флагов: `x >> 63` (sar) — маска «x отрицателен»;
`(x ^ m) - m` — abs через эту маску; `y ^ ((x ^ y) & -(x < y))` — min.

Разберём на 8-битных числах (на 64 битах всё то же, просто длиннее).

**abs через маску**, `x = -7` = `1111 1001`:

| Шаг | Значение (8 бит) | Десятичное |
|---|---|---|
| `x` | `1111 1001` | −7 |
| `m = x sar 7` (для 64 бит — `sar 63`) | `1111 1111` | −1 |
| `x ^ m` | `0000 0110` | 6 |
| `(x ^ m) - m` | `0000 0111` | 7 |

Для положительного `x` маска `m = 0`, и `(x ^ 0) - 0 = x`. Смысл: `x ^ -1`
— это `~x`, а `~x + 1` — это `-x` (дополнительный код, глава 02).

**min через маску**, `x = 3, y = 9`:

| Шаг | Значение |
|---|---|
| `x < y` | 1 |
| `-(x < y)` | −1 = все единицы |
| `(x ^ y) & -1` | `x ^ y` |
| `y ^ (x ^ y)` | `x` = 3 |

Если `x ≥ y`, маска 0, `(x ^ y) & 0 = 0`, и результат — `y`.

> **Частые ошибки**
> * Знаковое сравнение через CF/`sbb`/`setb` — даёт неверный ответ на
>   отрицательных числах.
> * `shr` вместо `sar` для маски знака: `shr` даст 0 или 1, а не 0 или −1.

> **Коротко:** шаблоны — «положи один ответ, `cmov` заменяет другим»;
> «`setcc` → 0/1 → прибавить»; «маска 0/−1 → выбрать через `and`/`xor`».

### 4. Branchless-алгоритмы

* **Бинарный поиск** с `cmov` (упражнение `a1302`) обычно в 2–3 раза быстрее
  ветвящегося на массивах, помещающихся в кеш: каждая итерация
  одинакова, предсказывать нечего. Для больших массивов добавляют
  prefetch обеих возможных следующих позиций.
* **Партиционирование** в quicksort (branchless Lomuto, «BlockQuicksort»).
* **Фильтрация** массива: записываем каждый элемент по индексу `j` и
  делаем `j += условие` — запись безусловная, сдвигается только индекс.
* В SIMD (глава 10) ветвлений нет вообще — маски и смешивание.

Термины: **кеш** — небольшая быстрая память рядом с ядром (подробнее в
главе 14); **prefetch** — подсказка процессору «скоро понадобятся эти
данные, начни загружать заранее».

#### 4.1. Бинарный поиск без ветвлений: идея

Обычный бинарный поиск на каждом шаге решает «идти влево или вправо?».
Для случайного ключа это монетка — предсказатель ошибается в половине
шагов.

Branchless-версия переформулирует поиск: держим «окно» `[base, base+len)`
и на каждом шаге отрезаем от него половину. Решение «сдвинуть `base`
или нет» — это одно `cmov`, а **число** шагов зависит только от `n`, не
от данных, — значит, переход цикла предсказывается идеально.

Псевдокод из упражнения:

```
base = 0; len = n
while (len > 1) {
    half = len / 2
    if (a[base + half - 1] < key) base += half   // <- cmov
    len -= half
}
if (len == 1 && a[base] < key) base++            // последний шаг
return base
```

Трасса на массиве `a = {-20, -17, -14, -11, -8, -5, -2, 1}` (`n = 8`),
`key = -4`. Ответ `lower_bound` — первый индекс, где `a[i] >= key`, то
есть 6 (`a[6] = -2`).

| Шаг | base | len | half | смотрим `a[base+half-1]` | `< key`? | новый base | новый len |
|---|---|---|---|---|---|---|---|
| 1 | 0 | 8 | 4 | `a[3] = -11` | да | 4 | 4 |
| 2 | 4 | 4 | 2 | `a[5] = -5` | да | 6 | 2 |
| 3 | 6 | 2 | 1 | `a[6] = -2` | нет | 6 | 1 |
| финал | 6 | 1 | — | `a[6] = -2` | нет | 6 | — |

Ответ 6. Обратите внимание: на каждом шаге выполняется одно и то же —
прочитать, сравнить, условно прибавить, уменьшить `len`.

#### 4.2. Фильтрация без ветвлений

Задача: скопировать из `src` только положительные числа. Вместо «если
положительно — записать» пишем **всегда**, а сдвигаем индекс записи
только когда надо:

```asm
# long filter_pos(long* dst /*rdi*/, long* src /*rsi*/, long n /*rdx*/)
filter_pos:
    xor   eax, eax                # j = 0 (сколько записали)
    xor   ecx, ecx                # i = 0
    xor   r9d, r9d                # r9 = 0, setg будет писать только r9b
    jmp   2f
1:
    mov   r8, [rsi + rcx*8]       # r8 = src[i]
    mov   [rdi + rax*8], r8       # dst[j] = src[i] — ВСЕГДА
    test  r8, r8                  # флаги по src[i]
    setg  r9b                     # r9 = (src[i] > 0)
    add   rax, r9                 # j += 0 или 1
    inc   rcx                     # i++
2:
    cmp   rcx, rdx                # i < n ?
    jl    1b                      # единственный переход — переход цикла
    ret                           # rax = сколько элементов осталось
```

Трасса для `src = {5, -3, 0, 7}`:

| i | src[i] | пишем в dst[j] | > 0? | j после |
|---|---|---|---|---|
| 0 | 5 | dst[0] = 5 | да | 1 |
| 1 | −3 | dst[1] = −3 | нет | 1 |
| 2 | 0 | dst[1] = 0 (перезапись) | нет | 1 |
| 3 | 7 | dst[1] = 7 (перезапись) | да | 2 |

Итог `dst = {5, 7, …}`, `j = 2`. «Лишние» записи безвредны: их перезапишет
следующий подходящий элемент. Нужно только, чтобы в `dst` хватало места
на `n` элементов.

> **Коротко:** branchless-алгоритм делает на каждом шаге *одинаковую*
> работу, а условие превращает в число (сдвиг индекса, выбор значения).

### 5. Что делает компилятор

LLVM охотно превращает `a < b ? b : a` в `cmov`, а `if (x) count++` — в
`setcc`+`add` (листинги — в разделах 3.1 и 3.4). Но он не знает ваших
данных: иногда ставит `cmov` там, где ветка была бы лучше, и наоборот.
GCC: `__builtin_expect_with_probability`, `__builtin_unpredictable`
(Clang). Решение всегда принимается измерением (глава 14), а не
интуицией.

> **Коротко:** компилятор уже знает эти приёмы; ассемблер нужен, когда
> вы знаете о данных больше, чем он, — и это подтверждено замером.

## Часть 2. Атомарные операции

Сначала пара слов, которые понадобятся дальше.

* **Поток** (thread) — независимая «линия исполнения» программы; потоки
  одной программы разделяют общую память. Разные потоки могут
  исполняться на разных **ядрах** процессора одновременно.
* **Атомарная операция** — операция, которую никто не может «увидеть
  наполовину»: для всех остальных ядер она либо ещё не случилась, либо
  уже случилась целиком. Слово от греческого «неделимый».
* **Кеш-линия** — блок памяти из 64 байт, которым ядра обмениваются
  между собой и с памятью. Кеш хранит не отдельные байты, а целые линии.

### 6. Почему `count++` не работает в нескольких потоках

`add dword ptr [rdi], 1` — для процессора это «прочитать, сложить,
записать». Два ядра могут прочитать одно и то же значение, и одно из
увеличений потеряется.

Посмотрим на это как на хронологию (`counter = 5`):

| Время | Ядро A | Ядро B | `counter` в памяти |
|---|---|---|---|
| 1 | читает 5 | | 5 |
| 2 | | читает 5 | 5 |
| 3 | считает 6 | считает 6 | 5 |
| 4 | пишет 6 | | 6 |
| 5 | | пишет 6 | 6 ← должно быть 7 |

Аналогия: два кассира одновременно смотрят остаток на складе (5 штук),
каждый продаёт одну и записывает «осталось 4». Продано две, а списана одна.

Проверить легко: 4 потока по 200 000 инкрементов без `lock` дадут не
800 000, а случайное меньшее число. Мы проверили на 12-ядерной машине
(C-программа с `addl $1, counter` в asm-вставке): два запуска дали
**259 002** и **259 647** вместо 800 000 — потеряно больше двух третей!
С `lock addl` — ровно 800 000.

> **Коротко:** одна инструкция ассемблера ≠ одна неделимая операция.
> Чтение-изменение-запись в памяти без `lock` не атомарна.

### 7. Префикс lock

#### 7.1. Что делает `lock`

`lock` делает операцию «чтение-изменение-запись» атомарной. Ядро
получает кеш-линию в эксклюзивное состояние (M в протоколе MESI) и не
отвечает на запросы других ядер к ней, пока операция не закончится
(«cache lock»; шинная блокировка — только для невыровненных операндов,
пересекающих линии, и это **очень** дорого — «split lock»).

Разжуём. **Протокол MESI** — правила, по которым ядра договариваются о
кеш-линиях. Каждая линия в кеше ядра находится в одном из состояний:

| Буква | Состояние | Смысл |
|---|---|---|
| M | Modified | линия только у меня, и я её изменил |
| E | Exclusive | линия только у меня, не изменена |
| S | Shared | копия есть у нескольких ядер, все только читают |
| I | Invalid | у меня этой линии нет (или копия устарела) |

Писать можно только в линию в состоянии M/E. Если ядру надо записать, а
линия у него в S, оно рассылает «отдайте/выбросьте свои копии» и ждёт.

Аналогия: кеш-линия — книга в библиотеке. Читать её копии могут многие
(S), а исправлять текст можно, только забрав единственный экземпляр
себе (M). `lock` — это «забрал книгу, запер дверь, исправил, отпер».
Пока дверь заперта, ядро B, пришедшее за книгой, ждёт — и не может
прочитать старое значение посередине операции.

**Split lock** — когда операнд лежит на границе двух кеш-линий (например,
8-байтное число по адресу, кратному 64, минус 4). Тогда одной линией не
обойтись, и процессор блокирует всю шину памяти для всех ядер. Поэтому
атомарные переменные всегда **выравнивают** (по своему размеру).

#### 7.2. Таблица атомарных инструкций

| Инструкция | Атомарная операция | C3 (`std::atomic`) |
|---|---|---|
| `lock add/sub/and/or/xor [m], r` | `*p op= v` | `a.add(v)` и т.п. |
| `lock inc/dec [m]` | `++*p` | |
| `lock xadd [m], r` | `r = fetch_add(p, r)` | `a.add(v)` возвращает старое |
| `xchg [m], r` | `r = exchange(p, r)` — `lock` неявный! | `a.store` (seq_cst) / swap |
| `lock cmpxchg [m], r` | CAS c `rax` как ожидаемым | `compare_exchange` |
| `lock cmpxchg16b [m]` | CAS 128 бит (`rdx:rax` vs `rcx:rbx`) | указатель + счётчик |
| `lock bts/btr/btc [m], r` | атомарная установка бита | |

#### 7.3. `xadd` по шагам

`xadd` = exchange-and-add, «обменять и сложить». `lock xadd [m], r` за
одну неделимую операцию делает:

```
tmp  = [m]
[m]  = [m] + r
r    = tmp          ; r получает СТАРОЕ значение
```

Трасса: `[m] = 10`, `eax = 5`, `lock xadd dword ptr [rdi], eax`:

| | `[rdi]` | `eax` |
|---|---|---|
| до | 10 | 5 |
| после | 15 | 10 |

Это и есть `fetch_add`: «прибавь и скажи, что было». Если нужно **новое**
значение, достаточно после `xadd` прибавить к результату то же
слагаемое (старое + v = новое) — уже в регистре, без всякой атомарности.

Компилятор C3 для `fn int fadd(Atomic{int}* a) => a.add(1);` (`-O3`)
генерирует ровно это:

```asm
mov    eax, 0x1                   ; слагаемое
lock xadd DWORD PTR [rdi], eax    ; [rdi] += 1, eax = старое значение
ret                               ; вернуть старое
```

Почему просто `lock add` не годится для `fetch_add`? `lock add` ничего не
возвращает — только меняет память. А прочитать значение отдельным `mov`
до или после нельзя: между `mov` и `lock add` другое ядро успеет что-то
изменить, и вы вернёте «чужое» значение.

#### 7.4. `xchg` — всегда атомарный

`xchg [m], r` меняет местами память и регистр. С операндом в памяти он
**всегда** ведёт себя как с `lock`, даже если префикс не написан. Это
историческое решение Intel, и на нём держится спинлок (раздел 9).

Обратите внимание на асимметрию: `xadd`, `cmpxchg`, `add` **без** `lock`
— не атомарны. `xchg` — атомарен всегда.

#### 7.5. Цена

Цена `lock`-инструкции без конкуренции — ~10–20 тактов (на Zen 2 ~8, на
Skylake ~18). При конкуренции нескольких ядер за одну кеш-линию —
сотни тактов: линия «пинг-понгом» летает между ядрами.

**Конкуренция** (contention) — когда несколько ядер одновременно хотят
одну и ту же линию. Обычный `add` к регистру стоит 1 такт, так что
атомики — дорогое удовольствие; в горячем цикле их избегают (например,
каждый поток считает в свою локальную переменную и прибавляет к общей
один раз в конце).

> **Частые ошибки**
> * `xadd` без `lock` — компилируется, проходит однопоточный тест, но
>   теряет обновления в многопоточном.
> * Перепутать, что возвращает `xadd`: в регистре — **старое** значение.
> * `lock` с регистровым операндом (`lock add eax, 1`) — ошибка: `lock`
>   допустим только когда приёмник — память.
> * Размер операнда: `CInt` — 32 бита (`dword ptr`, `esi`/`eax`), `long` —
>   64 бита (`qword ptr`, `rax`).

> **Коротко:** `lock` + операция с памятью = атомарно. `xadd` возвращает
> старое значение. `xchg` с памятью атомарен сам по себе.

### 8. CAS-циклы

#### 8.1. `cmpxchg` — «сравнить и обменять»

**CAS** (compare-and-swap) — операция «если в ячейке всё ещё то, что я
ожидаю, запиши новое; иначе скажи мне, что там теперь».

Аналогия: вы правите общий документ. Перед сохранением система
проверяет: «документ не изменился с тех пор, как вы его открыли?». Если
нет — сохраняет вашу версию. Если кто-то успел внести правки — отказ,
и вам показывают свежую версию, чтобы вы применили свои правки к ней.

`lock cmpxchg [p], new`: если `[p] == rax`, записать `new` и ZF=1; иначе
`rax = [p]` и ZF=0. Через CAS выражается любая операция.

`rax` здесь — **неявный** операнд: в тексте инструкции его не видно, но
`cmpxchg` всегда сравнивает именно с `rax` (или `eax` для 32 бит).
Результат сообщается **флагом ZF**: его можно проверить `jne`/`je` или
превратить в число через `sete`.

Трасса успешного CAS: `[p] = 5`, `rax = 5` (ожидаем), `rcx = 9` (новое):

| | `[p]` | `rax` | ZF |
|---|---|---|---|
| до | 5 | 5 | — |
| после `lock cmpxchg [p], rcx` | 9 | 5 | 1 (успех) |

Неуспешный CAS: `[p] = 9`, `rax = 5`, `rcx = 100`:

| | `[p]` | `rax` | ZF |
|---|---|---|---|
| до | 9 | 5 | — |
| после | 9 (не тронуто) | 9 (свежее значение!) | 0 (неудача) |

#### 8.2. Цикл CAS

Общая схема любой атомарной операции `*p = f(*p)`:

```asm
    mov  rax, [rdi]            ; прочитали текущее значение (можно не атомарно)
retry:
    mov  rcx, rax              ; rcx = f(rax) — вычисляем новое значение
    or   rcx, rsi              ;   (для примера f = «OR с маской»)
    lock cmpxchg [rdi], rcx    ; если [rdi] всё ещё == rax — записать rcx
    jne  retry                 ; не вышло: rax уже обновлён, пробуем снова
    ; здесь rax = старое значение, которое мы успешно заменили
```

Важная деталь: после неудачи **не нужно** заново читать `[rdi]` —
`cmpxchg` уже положил свежее значение в `rax`.

Хронология с двумя ядрами (`[p] = 5`, оба хотят прибавить 1):

| Время | Ядро A | Ядро B | `[p]` |
|---|---|---|---|
| 1 | `rax = 5` | `rax = 5` | 5 |
| 2 | `rcx = 6`, CAS(5→6): успех | | 6 |
| 3 | | `rcx = 6`, CAS(5→6): неудача, `rax = 6` | 6 |
| 4 | | `rcx = 7`, CAS(6→7): успех | 7 |

Обновление B не потерялось — оно просто повторилось с правильными данными.

#### 8.3. `atomic_max`

Иногда писать вообще не надо — тогда из цикла выходим без CAS:

```asm
; atomic_max(p, v)
    mov  rax, [rdi]
retry:
    cmp  rax, rsi
    jge  done                       ; уже >= v
    lock cmpxchg [rdi], rsi
    jne  retry                      ; rax обновлён свежим значением
done:
```

По шагам: `rax` — текущее значение. Если оно уже не меньше `v`, максимум
менять не нужно. Иначе пытаемся заменить `rax` на `v`. Если кто-то успел
изменить ячейку, `rax` теперь свежее — и мы снова проверяем, нужно ли
вообще что-то писать (вдруг другой поток записал число ещё больше).
На выходе в `rax` лежит значение `*p`, которое было до нашей записи
(или текущее, если писать не пришлось).

Трасса однопоточно: `*p = 3`, `v = 10`:

| Шаг | `rax` | `[p]` | действие |
|---|---|---|---|
| `mov` | 3 | 3 | |
| `cmp 3, 10` | 3 | 3 | 3 < 10 — идём дальше |
| `lock cmpxchg` | 3 | 10 | успех, ZF=1 |
| выход | 3 | 10 | вернули старое |

Свойства и ловушки:

* **lock-free**: если CAS не удался, значит, *другой* поток продвинулся;
* **ABA**: значение A → B → A, CAS не заметит изменения. Для
  lock-free стека указателей это фатально; лечится счётчиком версий
  (`cmpxchg16b`) или схемами освобождения памяти (hazard pointers, epoch);
* **false sharing**: две независимые переменные в одной 64-байтной
  кеш-линии ведут себя как одна — ядра отбирают линию друг у друга.
  Горячие атомики выравнивают на 64 байта (`@align(64)` в C3).

Пояснения:

* **Lock-free** («без блокировок») — гарантия, что система в целом всегда
  продвигается: поток может «проиграть» CAS, но только потому, что
  кто-то другой выиграл. Никто не держит блокировку, которую мог бы
  забыть отпустить.
* **ABA** на примере: стек `top → A → B`. Поток 1 прочитал `top = A`,
  `next = B` и собирается сделать CAS(`top`: A → B). Его прервали.
  Поток 2 снял A, снял B, освободил B, снова положил A. Теперь
  `top → A → C`. Поток 1 просыпается: `top` всё ещё A, CAS успешен,
  `top = B` — а B уже освобождён! Счётчик версий решает это: CAS
  сравнивает пару (указатель, версия), а версия при каждом изменении
  растёт, поэтому «A с версией 1» ≠ «A с версией 3».
* **False sharing** («ложное разделение») — переменные логически не
  связаны, но физически в одной кеш-линии. Ядро A пишет в `x`, ядро B —
  в `y`, а линия всё равно пинг-понгом летает между ними.

> **Частые ошибки**
> * Забыть, что `cmpxchg` сравнивает с `rax`, — и положить ожидаемое
>   значение в другой регистр.
> * После неудачи перечитывать `[p]` отдельным `mov` — лишне (но не
>   ошибка); а вот забыть **пересчитать** новое значение от свежего `rax`
>   — ошибка.
> * Хотеть вернуть 0/1, а вернуть мусор: `sete al` пишет только байт.
> * Испортить флаги между `cmpxchg` и `jne`/`sete` (например, `xor`).

> **Коротко:** CAS = «запиши, если не изменилось; иначе дай свежее».
> Цикл CAS превращает любую функцию `f` в атомарное `*p = f(*p)`.

### 9. Спинлок

#### 9.1. Идея

**Блокировка** (lock, мьютекс) защищает **критическую секцию** — кусок
кода, который в каждый момент может выполнять только один поток.
**Спинлок** — блокировка, которая ждёт, «крутясь» (spin) в цикле, а не
засыпая.

Аналогия: туалет в поезде с табличкой «занято/свободно». Подошли,
дёрнули ручку: открыто — зашли и заперлись; заперто — стоим и смотрим
на табличку, пока не станет «свободно».

Представление: одно число, `0` — свободно, `1` — занято.

#### 9.2. Код

Упражнение `a1305`:

```asm
spin_lock:
    mov   eax, 1
    xchg  [rdi], eax          ; атомарно: захватить и узнать, что было
    test  eax, eax
    jz    acquired
spin:
    pause
    cmp   dword ptr [rdi], 0  ; ждём, только читая
    jne   spin
    jmp   spin_lock
acquired:
    ret

spin_unlock:
    mov   dword ptr [rdi], 0  ; обычная запись = release на x86
    ret
```

Главный приём — `xchg` с единицей. Он атомарно кладёт 1 и возвращает
старое значение:

| Было в `[rdi]` | Стало | `eax` после `xchg` | Смысл |
|---|---|---|---|
| 0 | 1 | 0 | было свободно — мы захватили |
| 1 | 1 | 1 | было занято — ничего не изменили |

Во втором случае запись 1 поверх 1 ничего не портит. Поэтому `xchg`
одновременно и «попытка захвата», и «проверка результата».

Хронология двух потоков:

| Время | Поток A | Поток B | `lock` |
|---|---|---|---|
| 1 | `xchg` → 0, захватил | | 1 |
| 2 | в критической секции | `xchg` → 1, не вышло | 1 |
| 3 | … | `pause`; читает 1 — ждём | 1 |
| 4 | `mov [rdi], 0` | `pause`; читает 1 | 0 |
| 5 | | читает 0 → `jmp spin_lock` | 0 |
| 6 | | `xchg` → 0, захватил | 1 |

#### 9.3. Почему так, а не проще

* «test and test-and-set»: ждём обычным чтением — кеш-линия в общем
  (Shared) состоянии у всех ждущих, трафика нет. Пытаемся `xchg`, только
  увидев 0.
* `pause` — подсказка процессору; без неё выход из спин-цикла вызывает
  сброс конвейера (memory order violation), а соседний гиперпоток
  простаивает.
* Спинлоки хороши для очень коротких критических секций. Если владелец
  блокировки будет вытеснен планировщиком, остальные будут крутиться
  впустую весь квант — поэтому мьютексы ОС (`futex`) сначала немного
  крутятся, а потом засыпают в ядре.

Разжуём каждый пункт.

**Почему не крутить `xchg` в цикле?** `xchg` — это запись, а писать можно
только в линию в состоянии M (раздел 7.1). Три ждущих ядра, каждое
крутящее `xchg`, непрерывно отбирают линию друг у друга — и у владельца
тоже, который хочет записать 0 при освобождении. Обычное чтение же
держит линию в S у всех: каждый читает свою копию, никакого трафика.
Когда владелец пишет 0, копии инвалидируются, ждущие перечитывают
и только тогда пробуют `xchg`.

**`pause`.** Инструкция «я в спин-цикле, не торопись». Она:
* немного задерживает (на Skylake+ ~140 тактов, раньше ~10) — снижает
  энергопотребление;
* отдаёт ресурсы ядра второму **гиперпотоку** (hyper-threading — два
  логических потока на одном физическом ядре);
* избавляет от штрафа при выходе из цикла: без `pause` процессор
  спекулятивно набивает конвейер десятками чтений `[rdi]`, а когда
  значение меняется, вынужден их все выбросить.

**Квант и планировщик.** Операционная система даёт потоку поработать
«квант» времени (порядка миллисекунд), потом может его снять. Если сняли
владельца спинлока, остальные потоки бесполезно крутятся до его
возвращения. **futex** — механизм Linux «усыпить поток, пока значение по
адресу не изменится».

#### 9.4. Почему unlock — обычный `mov`

Освобождение — это просто запись 0. Не нужен ни `lock`, ни `xchg`, ни
барьер: на x86 обычная запись не может «обогнать» более ранние чтения и
записи (см. таблицу TSO в разделе 10). Значит, к моменту, когда другие
ядра увидят 0, они гарантированно увидят и все изменения, сделанные
внутри критической секции. Такая гарантия называется **release**
(«отпустить»): «всё, что я сделал до этой записи, видно тому, кто
увидел эту запись».

> **Частые ошибки**
> * `trylock` возвращает инвертированный результат: `xchg` дал 0 —
>   значит **захватили** (вернуть 1), дал 1 — занято (вернуть 0).
> * В цикле ожидания снова делать `xchg` — работает, но медленно (и
>   именно это упражнение просит не делать).
> * После выхода из цикла ожидания сразу считать блокировку своей, не
>   повторив `xchg`: между чтением 0 и захватом её мог взять другой поток.
> * Размер: блокировка — `CInt` (32 бита), значит `dword ptr` и `eax`.

> **Коротко:** захват — `xchg` с 1 (0 в ответ = успех); ожидание —
> чтение + `pause`; освобождение — обычный `mov` нуля.

## Часть 3. Модель памяти и барьеры

### 10. Модель памяти x86 (TSO)

#### 10.1. Что такое «модель памяти»

Процессор и компилятор могут переставлять обращения к памяти, если
однопоточная программа этого не заметит. Многопоточная — заметит. Что
именно разрешено, описывает **модель памяти**. У x86 она одна из самых
строгих — Total Store Order:

| Перестановка | x86 |
|---|---|
| load → load | запрещена |
| store → store | запрещена |
| load → store (более поздняя запись раньше чтения) | запрещена |
| **store → load** (более позднее чтение раньше записи) | **разрешена** |
| `lock`-инструкции и `xchg` | полный барьер |

Термины: **load** — чтение из памяти, **store** — запись в память.
**Memory ordering** (порядок памяти) — в каком порядке *другие ядра*
видят ваши чтения и записи. «Перестановка store → load» значит: в
программе сначала запись, потом чтение (другого адреса), а другое ядро
может увидеть эффект так, будто чтение случилось раньше.

#### 10.2. Откуда берётся перестановка: буфер записи

Единственная разрешённая перестановка — следствие **буфера записи**
(store buffer): ядро кладёт запись в буфер и идёт дальше, а чтение
другого адреса может выполниться раньше, чем запись станет видна
другим ядрам.

Аналогия: вы пишете письмо и кладёте его в свой почтовый ящик «на
отправку» — и сразу идёте читать новости. Письмо вы уже «написали», но
адресат его ещё не получил. Почтальон (кеш) заберёт его чуть позже.
Сами вы своё письмо видите (ядро читает из своего буфера), а другие —
нет.

Классический тест (Dekker / «store buffering»):

```
поток 1:  x = 1;  r1 = y;        поток 2:  y = 1;  r2 = x;
```

На x86 возможно `r1 == 0 && r2 == 0` — оба чтения «обогнали» записи. Чтобы
это запретить, между записью и чтением нужен `mfence` (или любая
`lock`-инструкция, которая обычно дешевле).

Как это получается:

| Время | Ядро 1 | Ядро 2 | Память x, y |
|---|---|---|---|
| 1 | `x = 1` → в буфер записи | `y = 1` → в буфер записи | 0, 0 |
| 2 | `r1 = y` → читает 0 из кеша | `r2 = x` → читает 0 из кеша | 0, 0 |
| 3 | буфер сливается: x = 1 | буфер сливается: y = 1 | 1, 1 |

Итог: `r1 = 0`, `r2 = 0` — хотя «по логике» хотя бы одна запись должна была
случиться раньше обоих чтений.

Мы проверили это на реальной машине: два потока, записи и чтения —
обычные `mov` в asm-вставке, миллион повторений. Результат
`r1 == 0 && r2 == 0` встретился **6 и 114 раз** в двух запусках (редко,
но встречается!). С `mfence` после записи — **0 из 1 000 000**. Отсюда
урок: многопоточная ошибка может проявляться раз в миллион запусков.

#### 10.3. Атомики языка → инструкции x86

Следствия для C3/C++-атомиков на x86:

| Операция | Инструкция x86 |
|---|---|
| load (acquire, seq_cst) | обычный `mov` |
| store (release) | обычный `mov` |
| store (seq_cst) | `xchg` (или `mov` + `mfence`) |
| fetch_add, CAS (любой порядок) | `lock xadd`, `lock cmpxchg` |
| fence(acquire/release) | ничего (только запрет для компилятора) |
| fence(seq_cst) | `mfence` (или `lock or [rsp], 0`) |

Термины порядков:

* **acquire** («приобрести») — для чтения: ничто после него не может
  «переехать» раньше. Ставится при захвате: «увидел, что блокировка
  моя, — дальше читаю защищённые данные».
* **release** («отпустить») — для записи: ничто до неё не может
  «переехать» позже. Ставится при освобождении (раздел 9.4).
* **seq_cst** (sequential consistency, «последовательная согласованность»)
  — самый строгий: все потоки видят все такие операции в одном общем
  порядке. Именно он запрещает перестановку store → load, поэтому
  seq_cst-запись на x86 — `xchg`, а не `mov`.

Поэтому код с ошибками в упорядочивании часто «работает» на x86 и
ломается на ARM, где модель слабее и переставлять можно почти всё. Но
**компилятор** переставлять может и на x86! Атомарные операции в языке —
это обещание и процессору, и компилятору.

Пример с компилятором: в цикле `while (flag == 0) {}` по обычной
(неатомарной) переменной компилятор вправе прочитать `flag` один раз,
положить в регистр и крутиться вечно — ведь «в однопоточной программе
`flag` в цикле не меняется». Атомарное чтение запрещает такую
оптимизацию.

> **Коротко:** x86 переставляет только «запись, потом чтение другого
> адреса» (из-за буфера записи). Запрещается `mfence` или любой
> `lock`-инструкцией (включая `xchg`).

### 11. Барьеры

**Барьер памяти** (fence) — инструкция «все обращения к памяти до меня
должны стать видимы до любых обращений после меня».

| Инструкция | Что упорядочивает |
|---|---|
| `mfence` | все загрузки и записи до/после |
| `sfence` | записи (нужен только для non-temporal `movnt*`) |
| `lfence` | загрузки; на практике — «дождаться завершения всех предыдущих инструкций» (сериализация для `rdtsc`, защита от Spectre v1) |
| `lock`-инструкции | полный барьер, как `mfence` |

Пояснения:

* `mfence` фактически «дождаться, пока опустеет буфер записи».
* **Non-temporal** запись (`movntdq` и др.) — запись в обход кеша, прямо
  в память (полезно для больших буферов, которые не будут скоро
  читаться). Такие записи не подчиняются обычным правилам TSO, поэтому
  после них ставят `sfence`.
* `lfence` пригодится в главе 14: `rdtsc` (чтение счётчика тактов) без
  него может выполниться раньше предыдущего кода и исказить замер.
  **Spectre v1** — атака, использующая спекулятивное исполнение (раздел 1.2);
  `lfence` её останавливает.

> **Коротко:** в обычном коде на x86 нужен только `mfence` (или `lock`-
> инструкция) — и только когда важен порядок «запись → чтение».

## Подводные камни

* `setcc` без обнуления старших битов.
* `cmov` с памятью по возможно-невалидному указателю.
* Неатомарный «прочитать-изменить-записать» в многопоточном коде.
* `xadd` без `lock` — не атомарен (а `xchg` — всегда атомарен).
* Тесты многопоточного кода, «проходящие» случайно. Хороший тест должен
  ломаться детерминированно (как однопоточные проверки в упражнениях) или
  с подавляющей вероятностью.
* Атомарные переменные в одной кеш-линии с горячими данными (false sharing).
* «На x86 работает» ≠ корректно.

## Как это связано с упражнениями

### `a1301_setcc_cmov` — `bl_max`, `bl_abs`, `bl_sign`, `bl_clamp`

**Что просят:** четыре функции без единого условного перехода.

**Перечитать:** разделы 2.2–2.4, 3.1–3.3.

**На что обратить внимание:**
* В `bl_max` заготовка уже почти готова — условие перепутано. Сверьтесь
  с трассой в 3.1: какое условие должно приводить к замене `rax` на `b`?
* `bl_abs`: после `neg` у вас уже есть флаг SF «знака −x». Нужна ровно
  одна инструкция.
* `bl_sign` возвращает `CInt` (32 бита, `eax`), и тест проверяет
  `long::min` — у `long::min` нет положительной пары, так что `neg` здесь
  не помощник; используйте прямое сравнение с нулём. Не забудьте, когда
  обнулять регистры.
* `bl_clamp(x, lo, hi)` = `min(max(x, lo), hi)`: два шаблона «положи
  ответ — сравни — `cmov`» подряд. Аргументы: `rdi = x`, `rsi = lo`,
  `rdx = hi`. Сравнивайте то, что *уже* лежит в `rax`, а не исходный `x`.

### `a1302_branchless_search` — `count_less`, `lower_bound`

**Что просят:** подсчёт элементов меньше `pivot` без ветвления в теле
цикла и branchless `lower_bound`.

**Перечитать:** 3.4, 3.5 (почему CF здесь не подходит), 4.1.

**На что обратить внимание:**
* Элементы — **знаковые** 32-битные `int`: `cmp dword ptr [...]`, `edx`,
  условие `l`, не `b`.
* В заготовке `count_less` уже обнулён `r8d` до цикла — догадайтесь
  зачем (раздел 3.4).
* `lower_bound`: переведите псевдокод из 4.1 построчно. `half = len / 2`
  — это сдвиг вправо. Для «условно прибавить `half` к `base`» удобно
  заранее посчитать `base + half` в отдельном регистре и выбрать `cmov`.
  Адрес элемента: `[rdi + индекс*4]`.
* Тест перебирает **все** `n` от 0 до 64, включая `n = 0` и `n = 1`.
  Проверьте свою реализацию по трассе 4.1 и отдельно на этих краевых
  случаях (при `n = 0` массив читать нельзя).
* Финальный шаг (`len == 1`) — единственное место, где переход
  допустим, но его тоже можно сделать через `setl`/`cmov`.

### `a1303_atomic_add` — `atomic_fetch_add`, `atomic_inc64`

**Что просят:** атомарно прибавить и вернуть **старое** (32 бита);
атомарно прибавить 1 и вернуть **новое** (64 бита).

**Перечитать:** 6, 7.2, 7.3.

**На что обратить внимание:**
* Однопоточные проверки идут первыми: «must return the OLD value» /
  «must return the NEW value» — значит, вы перепутали, что лежит в
  регистре после `xadd`.
* «lost updates: not atomic?» — забыт `lock`.
* Следите за размерами: `CInt*` → `dword ptr`, `esi`, `eax`; `long*` →
  `qword ptr`, `rax`.

### `a1304_cas` — `atomic_cas`, `atomic_max`

**Что просят:** CAS, возвращающий 1/0, и атомарный максимум через CAS-цикл,
возвращающий старое значение.

**Перечитать:** 8.1–8.3, а также 2.2 (про `setcc` и обнуление).

**На что обратить внимание:**
* `cmpxchg` сравнивает с `rax` — `expected` приходит в `rsi`, его надо
  туда переложить.
* Результат — `CInt` 0/1: флаг ZF после `cmpxchg` → `sete`. Как обнулить
  `eax`, не испортив флаги и не потеряв ожидаемое значение в `rax`?
  Подумайте о `movzx` (раздел 2.2).
* `atomic_max` сравнивает **знаково** (`long`).

### `a1305_spinlock` — `spin_trylock`, `spin_lock`, `spin_unlock`

**Что просят:** блокировку «test and test-and-set» с `pause`.

**Перечитать:** 7.4, 9.1–9.4, 10.

**На что обратить внимание:**
* `trylock` возвращает 1 при **успехе** — а `xchg` при успехе даёт 0.
  См. таблицу в 9.2.
* Тест проверяет, что после `spin_unlock` в блокировке лежит ровно 0.
* Блокировка — 32-битный `CInt`.
* Многопоточная часть проверяет инвариант `a == b` внутри критической
  секции; если он ломается — у вас «окно», где два потока внутри
  одновременно (например, ожидание закончилось без повторного `xchg`).

## Словарик

| Термин | Простыми словами |
|---|---|
| Конвейер (pipeline) | Исполнение инструкций «внахлёст», по стадиям, как на кухне ресторана |
| Предсказатель переходов | Блок процессора, угадывающий направление условного перехода по прошлому поведению |
| Спекулятивное исполнение | Выполнение кода «наперёд» по угаданному пути, с откатом при ошибке |
| Промах предсказания (misprediction) | Неверная догадка; стоит 15–20 тактов на сброс конвейера |
| Branchless-код | Код, где условие превращается в данные (0/1, маска, `cmov`), а не в переход |
| Зависимость по данным | Инструкция ждёт, пока будут готовы её входы |
| Маска | Число из одних нулей (0) или одних единиц (−1) для выбора через `and`/`xor` |
| Поток (thread) | Независимая линия исполнения с общей памятью |
| Атомарная операция | Операция, которую другие ядра не могут увидеть «наполовину» |
| Кеш-линия | Блок из 64 байт — единица обмена между ядрами и памятью |
| MESI | Протокол состояний кеш-линий: Modified, Exclusive, Shared, Invalid |
| Split lock | `lock`-операция над данными на границе двух линий; блокирует шину, очень дорого |
| Конкуренция (contention) | Несколько ядер одновременно хотят одну линию/блокировку |
| CAS (compare-and-swap) | «Запиши новое, если там всё ещё ожидаемое; иначе дай текущее» |
| Lock-free | Алгоритм, в котором какой-то поток всегда продвигается, без блокировок |
| ABA | CAS не замечает изменения A → B → A |
| False sharing | Независимые переменные в одной кеш-линии мешают друг другу |
| Спинлок | Блокировка, которая ждёт активным циклом |
| Критическая секция | Код, который одновременно может выполнять только один поток |
| Гиперпоток | Второй логический поток на том же физическом ядре |
| futex | Механизм Linux: усыпить поток до изменения значения по адресу |
| Модель памяти | Правила о том, в каком порядке другие ядра видят ваши чтения и записи |
| Memory ordering | Порядок, в котором обращения к памяти становятся видимы другим ядрам |
| load / store | Чтение из памяти / запись в память |
| TSO (Total Store Order) | Модель памяти x86: переставляется только «запись → чтение» |
| Буфер записи (store buffer) | Очередь записей ядра, ещё не видимых другим ядрам |
| acquire / release | Порядки: ничего не переезжает раньше чтения / позже записи |
| seq_cst | Самый строгий порядок: единый общий порядок для всех потоков |
| Барьер (fence) | Инструкция, запрещающая перестановки обращений к памяти через себя |
| Non-temporal запись | Запись в обход кеша (`movnt*`) |
