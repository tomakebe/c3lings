# Глава 11. Inline-ассемблер C3 и чтение кода компилятора

Писать целые функции в `.s`-файлах — хороший способ учиться, но в
реальных проектах ассемблер чаще встречается в двух других видах:

1. **Inline-ассемблер** — несколько инструкций прямо внутри функции на
   высокоуровневом языке: доступ к инструкции, до которой язык «не
   дотягивается» (`rdtsc`, `cpuid`, `crc32`, `pdep`), или гарантия
   конкретной последовательности.
2. **Чтение вывода компилятора** — гораздо более частая задача. Чтобы
   понять, почему код медленный, векторизовался ли цикл, убрал ли
   компилятор проверку границ, — вы открываете дизассемблер. Писать
   ассемблер приходится редко, читать — постоянно.

Упражнения: `a1101`–`a1105`. В этой главе вы правите `.c3`-файлы.

## Карта главы

**Что вы узнаете.**

* Как вставить несколько инструкций ассемблера прямо в функцию на C3 и
  чем «строковая» вставка `asm("...")` отличается от «блочной» `asm { ... }`.
* Почему компилятору важно знать, какие регистры ваш ассемблер читает, а
  какие портит, — и как c3c выясняет это сам.
* Как работать с инструкциями, которые намертво привязаны к конкретным
  регистрам (`mul`, `div`, `rdtsc`).
* Как посмотреть, во что компилятор превратил вашу программу, и как
  читать этот вывод: синтаксис AT&T, разница `-O0` и `-O3`, типичные
  «фокусы» оптимизатора (деление через умножение, `lea` вместо `imul`,
  `cmov` вместо ветвлений).

**Зачем это нужно.** Inline-ассемблер — это «отвёртка для особых
случаев»: пользуются им редко, но когда нужен — без него никак. А вот
чтение кода компилятора — повседневный навык любого, кто пишет быстрый
код (игровые движки, базы данных, кодеки): именно так проверяют, что
компилятор сделал то, на что вы рассчитывали.

**Что нужно знать заранее.**

* Регистры и их «половинки» (`rax`/`eax`/`ax`/`al`) — глава 01.
* `mul`/`div` и пара `rdx:rax` — глава 02.
* `cmov`, флаги, `test`/`cmp` — главы 02–03.
* `lea` и адресация `[base + index*scale + disp]` — глава 04.
* Соглашение о вызовах System V (аргументы в `rdi`, `rsi`, `rdx`, `rcx`,
  результат в `rax`) — глава 05.
* Битовые инструкции `popcnt`, `tzcnt`, `bswap`, `pext` — глава 08.

**Какие разделы нужны для каких упражнений.**

| Упражнение | Что делает | Разделы |
|---|---|---|
| `a1101_asm_block` | чинит три простых блока `asm` | 1.2, 1.3 |
| `a1102_bits_inline` | `popcnt`, `tzcnt`, `bswapl`, `pext` в блоке | 1.3, 1.4 |
| `a1103_fixed_regs` | `mulq`, `divq`, `rdtsc` | 2 |
| `a1104_crc32` | аппаратная контрольная сумма `crc32` | 1.3, 1.4, 4.3 |
| `a1105_read_compiler` | по ассемблеру восстановить исходник на C3 | 3, 4, 5 |

## 1. Два вида `asm` в C3

Сначала — главная идея, на которой держится весь раздел.

Компилятор, когда переводит вашу функцию в машинный код, всё время
решает задачу «кто где лежит»: переменная `a` — в `edi`, `b` — в `esi`,
промежуточный результат — в `eax`, флаги после сравнения ещё нужны… Это
называется **распределением регистров** (register allocation). И вдруг
посреди функции появляется ваш кусочек ассемблера. Компилятору жизненно
важно знать про этот кусочек три вещи:

1. **Что он читает** — какие значения надо подготовить *до* него и в
   каких регистрах.
2. **Что он пишет** — где после него лежат результаты.
3. **Что он портит** (по-английски *clobbers*, «затирает») — какие
   регистры, флаги или память после него содержат мусор, так что
   хранить там что-то ценное нельзя.

Бытовая аналогия: вы делите кухню с соседом. Если сосед предупредил «я
возьму большую кастрюлю и обе конфорки, а вернём суп в синей миске», —
всё в порядке, вы спланируете готовку вокруг. Если он молча пришёл и
вылил ваш бульон из кастрюли, чтобы сварить своё, — катастрофа, и
обнаружится она не сразу.

Эти три списка в мире компиляторов называют **ограничениями**
(*constraints*). Два вида `asm` в C3 отличаются ровно тем, кто их
составляет.

### 1.1 Строка

```c3
asm("nop");
```

Строка передаётся в LLVM без изменений, как «module-level» вставка внутри
функции. Компилятор не знает, какие регистры она читает и портит, —
поэтому годится только для инструкций без операндов и побочных эффектов
на регистры: `nop`, `pause`, `int3`. Синтаксис — AT&T (по умолчанию в
LLVM).

Разжуём. **LLVM** — это «движок» внутри c3c (и внутри Clang, Rust,
Swift…), который берёт программу в промежуточном виде, оптимизирует её
и выдаёт машинный код. c3c разбирает ваш C3, а дальше отдаёт работу
LLVM. Строку из `asm("...")` c3c даже не читает — она уходит в LLVM как
непрозрачная записка: «вставь вот это как есть».

Раз никто не знает, что внутри записки, никто и не защищает от неё
регистры. Если вы напишете `asm("movl $5, %eax");`, а компилятор в этот
момент держал в `eax` вашу переменную, — переменная молча испортится.
Поэтому строковую форму используют только для инструкций, которые
ничего не трогают:

| Инструкция | Что делает | Зачем |
|---|---|---|
| `nop` | ничего | метка/выравнивание, «здесь был я» в дизассемблере |
| `pause` | подсказка процессору «я жду в цикле» | спин-локи (глава 13) |
| `int3` | точка останова | отладчик остановится здесь |

Обратите внимание: внутри строки — синтаксис **AT&T** (регистры с `%`,
константы с `$`, источник первым), потому что это «родной» язык
ассемблера LLVM. О нём — в разделе 3.

> **Коротко:** `asm("...")` — непрозрачная записка для LLVM. Компилятор
> не знает, что она трогает, поэтому туда кладут только безвредные
> инструкции без операндов.

### 1.2 Блок

```c3
fn int add(int a, int b)
{
    int r;
    asm
    {
        movl r, a;      // r = a
        addl r, b;      // r += b
    }
    return r;
}
```

Блок — «понимаемый» компилятором ассемблер. c3c разбирает каждую
инструкцию, сверяется с таблицей (какие операнды читаются, какие пишутся,
что портится) и генерирует для LLVM inline-asm с правильными
ограничениями (constraints) — то, что в GCC вы бы писали вручную
(`"=r"(r) : "r"(a), "0"(b) : "cc"`), и где так легко ошибиться.

**Что здесь происходит по шагам.** В блоке вы пишете не регистры, а
*имена переменных C3*: `r`, `a`, `b`. Компилятор смотрит на них и
рассуждает так:

* `movl r, a` — по таблице у `movl` первый операнд «только пишется»,
  второй «читается». Значит, `a` надо подать *на вход*, а `r` появится
  *на выходе*.
* `addl r, b` — первый операнд «читается и пишется» (`r = r + b`),
  второй читается. Значит, `b` — тоже вход. `addl` меняет флаги — флаги
  испорчены.
* Сам выбирает регистры: куда положить `a`, `b` и `r`.

Вот что реально получилось на `-O3` (c3c 0.8.5, вывод `--emit-asm`,
отладочные строки убраны):

```asm
t.add:
    #APP                    # начало вашего блока
    movl  %edi, %eax        # r (в eax) = a (пришёл в edi)
    addl  %esi, %eax        # r += b (пришёл в esi)
    #NO_APP                 # конец вашего блока
    retq                    # r уже в eax — это и есть возвращаемое значение
```

Это AT&T-синтаксис (источник слева, приёмник справа), в Intel он
выглядел бы как `mov eax, edi` / `add eax, esi`. Компилятор оказался
умным: он выбрал для `r` регистр `eax`, потому что `r` всё равно
возвращается, а результат функции по соглашению лежит в `eax`. Лишних
пересылок — ноль.

Проследим значения для вызова `add(2, 40)`:

| Шаг | `edi` (a) | `esi` (b) | `eax` (r) |
|---|---|---|---|
| вход в функцию | 2 | 40 | ? |
| `movl r, a` → `mov eax, edi` | 2 | 40 | 2 |
| `addl r, b` → `add eax, esi` | 2 | 40 | 42 |
| `ret` | | | **42** |

**Почему это важно.** В GCC/Clang для C то же самое пишется так:

```c
asm("addl %2, %0" : "=r"(r) : "0"(a), "r"(b) : "cc");
```

Здесь вы сами перечисляете: `"=r"(r)` — «r выход, в любом регистре»,
`"0"(a)` — «a вход, в том же регистре, что операнд 0», `"r"(b)` — «b
вход», `"cc"` — «портятся флаги». Ошибётесь в одном символе — получите
код, который работает на `-O0` и ломается на `-O2`. c3c делает эту
бухгалтерию за вас, читая инструкции.

> **Коротко:** в блоке `asm { ... }` вы пишете инструкции с именами
> переменных C3, а компилятор сам выясняет, что читается, что пишется и
> что портится, и сам раскладывает переменные по регистрам.

### 1.3 Правила синтаксиса блока

Синтаксис блока — гибрид: **мнемоники** (названия инструкций) как в
AT&T, с суффиксом размера, а **порядок операндов** как в Intel. Сначала
вся таблица, потом разбор по пунктам.

| Правило | Пример |
|---|---|
| мнемоника с суффиксом размера AT&T: `b`/`w`/`l`/`q` | `movl`, `addq`, `xaddl` |
| у части инструкций суффикса нет, размер — по операндам | `popcnt r, x;`, `tzcnt`, `pdep`, `crc32` |
| порядок операндов **Intel**: приёмник первый | `subq r, b;` → r -= b |
| регистры с `$` | `$eax`, `$rdx`, `$xmm0` |
| переменные C3 — по имени | `movq $rax, a;` |
| память через переменную-указатель | `[p]`, `[p + 8]`, `[p + i * 4 + 4]` |
| адрес переменной | `&x` |
| выражение в скобках вычисляется до блока | `movl $eax, (a + 1);` |
| размер переменной = размер инструкции | `movl` + `ulong` → ошибка |
| каждая инструкция завершается `;` | |

#### Суффикс размера

Буква в конце мнемоники говорит, сколько бит обрабатывает инструкция:

| Суффикс | Расшифровка | Бит | Типы C3 |
|---|---|---|---|
| `b` | byte | 8 | `char`, `ichar` |
| `w` | word | 16 | `short`, `ushort` |
| `l` | long (в смысле AT&T: «длинное» = 32 бита) | 32 | `int`, `uint` |
| `q` | quad (четыре слова) | 64 | `long`, `ulong`, указатели |

Не путайте: `l` — это **32** бита, хотя в C3 `long` — 64. Названия
исторические, со времён 16-битных процессоров, где «слово» было 16 бит.

#### Размер переменной должен совпадать

Если суффикс говорит «32 бита», а переменная 64-битная, компилятор
откажется:

```c3
fn int f(ulong x) { int r; asm { movl r, x; } return r; }
```

```
error: 'ulong' is not supported in this position, convert it to a valid type, like 'int'.
```

Это защита, а не придирка: процессор не умеет «положить 64 бита в 32».
Нужно либо взять `movq` и 64-битные переменные, либо заранее привести
тип в C3 (`uint x32 = (uint)x;`).

У инструкций **без суффикса** (`popcnt`, `tzcnt`, `lzcnt`, `pdep`,
`pext`, `crc32`, `rorx`) размер выводится из переменных. Поэтому
`popcnt r, x` с двумя `ulong` — это 64-битный `popcnt`, а с двумя
`uint` — 32-битный. Операнды должны быть согласованы (у `crc32` правило
своё — см. раздел 4.3 про упражнение и комментарий в `a1104`).

#### Порядок операндов: приёмник первый

Как в Intel-синтаксисе и как в присваивании `r = ...`: слева то, *куда*
пишем.

```c3
subq r, b;     // r = r - b
movl r, a;     // r = a
```

А вот в выводе `--emit-asm` (AT&T) порядок будет **обратный**. Это
главный источник путаницы в этой главе, к нему мы вернёмся в разделе 3.

#### Регистры и переменные

* Конкретный регистр пишется с `$`: `$eax`, `$rdx`, `$xmm0`. Используйте
  это, только когда инструкция *требует* конкретный регистр (раздел 2).
* Во всех остальных случаях пишите **имя переменной** — пусть компилятор
  сам выберет регистр. Так он сможет избежать лишних пересылок.

#### Память, адреса и выражения

Проверенный пример (c3c 0.8.5, `-O3`):

```c3
// Сложить второй элемент массива с a + 1
fn int second_plus(int* p, int a)
{
    int r;
    asm
    {
        movl r, [p + 4];     // r = p[1]  (смещение в байтах!)
        addl r, (a + 1);     // r += a + 1  (выражение посчитано до блока)
    }
    return r;
}
// second_plus({10, 20, 30}, 5) == 26
```

Что сгенерировал компилятор:

```asm
second_plus:
    incl  %esi              # (a + 1) посчитано ДО блока: esi = a + 1
    #APP
    movl  4(%rdi), %eax     # eax = *(int*)(p + 4 байта) = p[1] = 20
    addl  %esi, %eax        # eax += 6  → 26
    #NO_APP
    retq
```

Три важных наблюдения:

1. **`[p + 4]` — смещение в байтах**, а не в элементах: так принято
   в ассемблере, в отличие от C3, где `p[1]` считает в элементах. Для `int` второй элемент — это
   `+4`, для `ulong` — `+8`. В записи `[p + i * 4 + 4]` множитель `4`
   вы тоже пишете сами.
2. Выражение в скобках `(a + 1)` компилятор вычислил обычным C3-кодом
   (`incl %esi`) *перед* блоком и подал в блок уже готовым значением.
3. `&x` даёт адрес переменной — компилятору тогда придётся держать `x`
   в памяти (в стеке), а не в регистре.

#### Строковая вставка внутри функции

`asm("nop");` можно писать где угодно внутри функции, например в
`main`, — она просто вставит `nop` в это место.

> **Частые ошибки (синтаксис блока)**
>
> * Перепутан порядок операндов: `addl a, r;` пишет в `a`, а не в `r`.
>   Приёмник — **первый**.
> * Суффикс не совпадает с типом: `movl` с `ulong`, `movq` с `int`.
>   Читайте сообщение `'ulong' is not supported in this position`.
> * Забыта `;` в конце инструкции.
> * `[p + 1]` вместо `[p + 4]` для второго `int`: смещения — в байтах.
> * Константа там, где инструкция её не принимает: `pext r, x, 0x1111;`
>   даёт `'pext' does not support a direct integer constant here.` —
>   положите константу в переменную.
> * Регистр `$eax` там, где хватило бы переменной: компилятору
>   приходится добавлять лишние `mov`.

> **Коротко:** мнемоника с суффиксом (`l` = 32 бита, `q` = 64), приёмник
> первым, переменные по имени, регистры с `$`, память в квадратных
> скобках с байтовыми смещениями, размеры обязаны совпадать.

### 1.4 Поддерживаемые инструкции

Блок понимает не весь набор x86, а только инструкции, для которых в
c3c есть «паспорт» — запись о том, что они читают и портят. Полный
список для текущей цели печатает

```
c3c compile --list-asm file.c3
```

(с колонками «clobbers» и шаблоном аргументов: `rw:` — читается и
пишется, `w:` — только пишется). В c3c 0.8.5 для x86-64 это примерно:

* пересылки: `movb/w/l/q`, `movzbl`, `movsbq`, `movslq`, …, `xchg*`, `push*`, `pop*`;
* арифметика: `add*`, `adc*`, `sub*`, `inc*`, `dec*`, `neg*`, `mul*`,
  `div*`, `idiv*`, `mulx`, `adcx`, `adox`;
* логика: `or*`, `xor*`, `not*`, `andn`, BMI (`blsi`, `blsr`, `blsmsk`,
  `bextr`, `bzhi`, `pdep`, `pext`, `shlx`, `shrx`, `sarx`, `rorx`);
* подсчёт битов: `popcnt`, `lzcnt`, `tzcnt`; `bswapl`/`bswapq`;
* атомарные: `xadd*`, `cmpxchg*`, `cmpxchg8b`, `cmpxchg16b`;
* `cmova*`, `cmovae*`, `cmovb*`, `cmovbe*` (только беззнаковые условия);
* системные: `cpuid`, `rdtsc`, `rdtscp`, `rdrand`, `rdseed`, `xgetbv`,
  `syscall`, `clflush`, `int3`, `hlt`, `nop`;
* немного SSE/AVX: `addss/sd/ps/pd`, `vadd*`, `crc32`, `pclmulqdq`, AES, SHA;
  `vzeroupper`, `vzeroall`.

**Нет**: `and`, `shl`/`shr`/`sar`, `rol`, `imul`, `cmp`, `test`, `lea`,
`setcc`, переходов, префикса `lock`, барьеров `mfence`/`pause`. Мануал
честно предупреждает: inline-ассемблер — «work in progress». На практике
это не страшно: всё перечисленное C3 сам выражает отлично, а в блок
выносится только то, чего в языке нет.

#### Как читать таблицу `--list-asm`

Несколько настоящих строк из вывода (c3c 0.8.5):

```
| instr      | clobbers                       | args                                    |
| addl       | cc                             | rw:r32/mem, immu32/imm32/imm8/r32/mem   |
| movl       |                                | w:r32/mem, immu32/imm32/r32/mem         |
| incl       | cc                             | rw:r32/mem                              |
| bswapl     |                                | rw:r32                                  |
| popcnt     | cc                             | w:r64/r32/r16, r64/r32/r16/mem          |
| pext       |                                | w:r64/r32, r64/r32, r64/r32/mem         |
| mulq       | cc, rax, rdx                   | rw:r64/mem                              |
| divq       | cc, rax, rdx                   | r64/mem                                 |
| rdtsc      | rax, rdx                       |                                         |
```

Расшифровка колонок:

* **instr** — мнемоника, как её писать в блоке.
* **clobbers** — что инструкция портит *помимо* своих операндов. `cc`
  (*condition codes*) — флаги. `rax, rdx` у `mulq` — она неявно пишет
  в эти регистры, хотя в тексте инструкции их нет.
* **args** — операнды через запятую. Префикс говорит о направлении:
  `rw:` — читается и пишется (`addl r, b`: `r = r + b`), `w:` — только
  пишется (`movl r, a`: старое `r` не важно), без префикса — только
  читается. Дальше через `/` — какие виды допустимы:

| Обозначение | Значит |
|---|---|
| `r32`, `r64` | регистр (или переменная, которую положат в регистр) нужного размера |
| `mem` | операнд в памяти `[p + ...]` |
| `imm8`, `imm32`, `immu32` | непосредственная константа (знаковая/беззнаковая) такой ширины |
| `v128`, `v256` | векторный регистр `xmm`/`ymm` |

Например, у `pext` во всех трёх позициях нет `imm` — отсюда и правило
из `a1102`: маску нужно положить в переменную. А у `popcnt` первый
операнд `w:` — значит, его старое значение не важно, можно не
инициализировать `r`.

> **Коротко:** блок знает только подмножество инструкций; `--list-asm`
> показывает, какие именно, что они портят (`cc` = флаги) и какие
> операнды принимают (`rw:`/`w:`/чтение, `r`/`mem`/`imm`).

### 1.5 Найденные шероховатости (c3c 0.8.5)

Таблица `--list-asm` — это «обещания», на которые компилятор опирается
при распределении регистров. Если обещание неверно, компилятор честно
сгенерирует неправильный код. Поэтому читать таблицу полезно и для того,
чтобы ловить ошибки самого компилятора:

* `cmov*` описаны как `w:r32, r32/mem` — приёмник «только пишется». Но
  `cmov` пишет приёмник *условно*: если условие ложно, остаётся старое
  значение, т.е. приёмник ещё и **читается**. Из-за этого на `-O3`
  компилятор вправе не загружать в регистр начальное значение
  переменной — и результат станет мусорным. Посмотрите сами:

  ```c3
  fn uint umax(uint a, uint b) { uint r = a; asm { movl $eax, a; subl $eax, b; cmovbl r, b; } return r; }
  ```

  в `-O3`-выводе `cmovb ecx, esi` пишет в `ecx`, в который `a` никто не
  положил. Используйте `cmov` в блоках только с явной инициализацией
  внутри блока через фиксированный регистр, а лучше — пишите
  `a < b ? b : a` и доверьтесь компилятору.
* `cmpxchgl` описан с 16-битными операндами, поэтому `cmpxchgl [p], x`
  с `int x` не компилируется.
* Нет `lock`: `xaddl [p], v` в блоке **не атомарен**. Атомарен только
  `xchg` с памятью — у него `lock` подразумевается всегда. Для атомиков
  используйте `std::atomic` (глава 13) или `.s`-файл.

Если нужно что-то за пределами этого подмножества — пишите функцию в
`.s`-файле и вызывайте её через `extern fn`, как в главах 00–10. Это
переносимее и проще отлаживать.

#### Разбор ошибки с `cmov` по шагам

Вот реальный вывод `--emit-asm -O3` для `umax`:

```asm
umax:                       # a в edi, b в esi
    #APP
    movl   %edi, %eax       # eax = a
    subl   %esi, %eax       # eax = a - b, CF = 1, если a < b (беззнаково)
    cmovbl %esi, %ecx       # если CF: ecx = b, иначе ecx НЕ МЕНЯЕТСЯ
    #NO_APP
    movl   %ecx, %eax       # вернуть r (живёт в ecx)
    retq
```

Компилятор решил: «`cmovbl r, b` *только пишет* `r`, значит, строка
`uint r = a;` бесполезна — её результат всё равно перезапишут». И
выбросил её. В итоге:

| Вызов | Условие `a < b` | Что в `ecx` после `cmovb` | Результат |
|---|---|---|---|
| `umax(3, 7)` | истинно | `b` = 7 | 7 — верно |
| `umax(7, 3)` | ложно | **то, что было в `ecx` до вызова** | мусор |

Коварство в том, что иногда «мусор» случайно оказывается правильным
(в нашем тесте `ecx` по совпадению содержал 7), и программа выглядит
рабочей. Такую ошибку очень трудно поймать тестами.

#### Почему `xadd` без `lock` не атомарен

**Атомарная** операция — та, которую никто не может «разрезать
посередине»: другое ядро видит либо состояние «до», либо «после», но не
промежуточное. `xadd [p], v` внутри процессора — это три шага:
прочитать `[p]`, сложить, записать. Если два ядра делают это
одновременно, оба могут прочитать одно и то же старое значение, и одно
прибавление потеряется. Префикс `lock` заставляет ядро «захватить»
кэш-линию (64-байтный кусок памяти, которым обмениваются ядра) на все
три шага. У `xchg` с памятью этот захват встроен всегда, поэтому он
атомарен и без префикса. Подробно — в главе 13.

> **Частые ошибки (шероховатости)**
>
> * Писать `cmov` в блоке с переменной-приёмником, проинициализированной
>   *вне* блока, — инициализация может исчезнуть.
> * Считать `xaddl`/`cmpxchgl` в блоке атомарными — без `lock` они нет.
> * Бороться с ограничениями блока там, где проще написать маленький
>   `.s`-файл.

> **Коротко:** таблица c3c не идеальна. `cmov` в блоке опасен, `lock`
> нет, `cmpxchgl` описан неверно. Для атомиков — `std::atomic`, для
> экзотики — отдельный `.s`-файл.

## 2. Фиксированные регистры

`mul`, `div`, `rdtsc`, `cpuid`, `syscall` работают с конкретными
регистрами. В блоке это выражается явными пересылками:

```c3
fn ulong muldiv(ulong a, ulong b, ulong c)
{
    ulong q;
    asm
    {
        movq $rax, a;
        mulq b;          // rdx:rax = rax * b
        divq c;          // rax = rdx:rax / c
        movq q, $rax;
    }
    return q;
}
```

Компилятор видит, что `mulq` портит `rax` и `rdx`, и не разместит там
ваши переменные. Сравните с GCC-синтаксисом, где это надо было бы
написать самому: `asm("mulq %2; divq %3" : "=a"(q) : "a"(a), "r"(b), "r"(c) : "rdx", "cc");`.

### 2.1 Почему регистры «зашиты»

Большинство инструкций x86 разрешают выбрать любые регистры:
`add r8, r12` ничем не хуже `add rax, rbx`. Но несколько старых
инструкций родом из 1970-х, когда у процессора был один главный регистр
— **аккумулятор** (`a` → `ax` → `eax` → `rax`), и они до сих пор
работают только с ним. Вместо того чтобы указывать регистры в тексте
инструкции, они используют их **неявно**:

| Инструкция | Читает | Пишет | Смысл |
|---|---|---|---|
| `mulq src` | `rax`, `src` | `rdx:rax` | беззнаковое 64×64 → 128 бит |
| `divq src` | `rdx:rax`, `src` | `rax` (частное), `rdx` (остаток) | 128 / 64 |
| `rdtsc` | — | `edx:eax` | счётчик тактов процессора |
| `cpuid` | `eax` (и `ecx`) | `eax`, `ebx`, `ecx`, `edx` | «кто ты, процессор?» |
| `syscall` | `rax`, `rdi`, `rsi`, … | `rax`, портит `rcx`, `r11` | системный вызов (глава 12) |

Запись `rdx:rax` значит «128-битное число, у которого старшие 64 бита
лежат в `rdx`, а младшие — в `rax`», как две половинки одного длинного
числа. Аналогично `edx:eax` — 64 бита из двух 32-битных половинок.

### 2.2 Как это пишется в блоке

Раз инструкция берёт данные из `rax`, вы сами кладёте их туда
(`movq $rax, a;`), а после — сами забираете результат
(`movq q, $rax;`). Всё, что между, — работа инструкции. Переменные
`b` и `c` при этом передаются по имени: компилятор положит их в
*какие-нибудь* регистры, но заведомо не в `rax`/`rdx`, потому что знает
из таблицы, что `mulq` их портит.

Вот что получилось на самом деле (`-O3`):

```asm
muldiv:                     # a в rdi, b в rsi, c в rdx (по соглашению!)
    movq   %rdx, %rcx       # спасаем c из rdx в rcx — rdx сейчас испортится
    #APP
    movq   %rdi, %rax       # rax = a
    mulq   %rsi             # rdx:rax = rax * b
    divq   %rcx             # rax = rdx:rax / c, rdx = остаток
    movq   %rax, %rcx       # q = rax
    #NO_APP
    movq   %rcx, %rax       # вернуть q
    retq
```

Посмотрите на первую строку: третий аргумент `c` по соглашению System V
приходит в `rdx`. Но `mulq` перезапишет `rdx`! Компилятор это понял и
**сам** переложил `c` в `rcx`. Если бы вы писали `.s`-файл, об этом
пришлось бы помнить вам.

### 2.3 Трассировка `muldiv(10^12, 10^12, 10^9)`

`10^12 · 10^12 = 10^24` — это больше `2^64 ≈ 1.8 · 10^19`, в 64 бита не
влезает. Но после деления на `10^9` получится `10^15` — влезает.

| Шаг | `rdx` | `rax` | Комментарий |
|---|---|---|---|
| `movq $rax, a` | (c) | `0xE8D4A51000` | `10^12` |
| `mulq b` | `0xD3C2` | `0x1BCECCEDA1000000` | `rdx:rax = 10^24`, старшая часть ненулевая |
| `divq c` | `0` (остаток) | `0x38D7EA4C68000` | `10^24 / 10^9 = 10^15` |
| `movq q, $rax` | | | `q = 1 000 000 000 000 000` |

Обычное `a * b / c` в 64-битной арифметике дало бы неверный ответ: `a * b`
переполнилось бы ещё до деления.

**Опасность `divq`.** Если частное не помещается в 64 бита (например,
`rdx:rax` огромное, а делитель маленький — или делитель 0), процессор
бросает исключение **#DE** (*divide error*), а Linux превращает его в
сигнал `SIGFPE` — программа падает. Поэтому `divq` безопасен, только
когда вы уверены, что результат влезает.

### 2.4 `rdtsc`: склеиваем две половинки

`rdtsc` (*read time-stamp counter*) читает 64-битный счётчик, который
процессор увеличивает с постоянной частотой с момента включения. Но,
по историческим причинам, отдаёт его двумя 32-битными половинками:
младшие 32 бита в `eax`, старшие в `edx`. Склеиваем:

```
результат = (hi << 32) | lo
            hi = 0x00000012          lo = 0x3456789A
            → 0x00000012_00000000 | 0x3456789A = 0x000000123456789A
```

Как это выглядит в коде — смотрите сам шаблон в `a1103`: вы забираете
`$eax` и `$edx` в две переменные `uint`, а склейку делает уже C3.
Проверено, что компилятор после блока генерирует ровно `shl rsi, 32` и
`or rax, rsi`.

> **Частые ошибки (фиксированные регистры)**
>
> * Забрать старшую половину произведения из `$rax` вместо `$rdx`.
> * Использовать `movl` для `$rax` или `movq` для `$eax`: суффикс и размер
>   регистра тоже должны совпадать.
> * Вызвать `divq` после того, как `rdx` что-то содержит «случайно»:
>   `divq` делит **всё** 128-битное `rdx:rax`. После `mulq` это ровно то,
>   что надо, а вот «голое» деление требует сначала обнулить `rdx`.
> * Ожидать, что `muldiv` с маленьким `c` не упадёт: частное, не
>   влезающее в 64 бита, — это `SIGFPE`.

> **Коротко:** «старые» инструкции работают с `rax`/`rdx` неявно. Вы
> кладёте вход в `$rax`, выполняете инструкцию и забираете результат из
> `$rax`/`$rdx`; остальные операнды — переменные, и компилятор сам
> уберёт их из-под удара.

## 3. Как получить вывод компилятора

```
c3c compile -O3 --emit-asm main.c3      # файлы в ./asm/linux-x64/<модуль>.s
c3c compile -O3 --emit-llvm main.c3     # LLVM IR — промежуточный уровень
objdump -d -M intel --no-show-raw-insn ./main | less   # дизассемблер готового бинарника
```

Что делает каждая команда:

* `--emit-asm` — компилятор кроме программы сохраняет текст ассемблера,
  который он сгенерировал. Папка `asm/linux-x64/` создаётся **в текущем
  каталоге**; удобно запускать это в отдельной временной папке, чтобы не
  мусорить рядом с упражнением.
* `--emit-llvm` — сохраняет **LLVM IR** (*intermediate representation*,
  «промежуточное представление»): программа уже не на C3, но ещё и не
  на ассемблере конкретного процессора. Полезно, когда хочется понять,
  на каком этапе что-то пошло не так.
* `objdump -d` — **дизассемблер**: читает готовый исполняемый файл и
  переводит байты машинного кода обратно в текст инструкций. Работает с
  любым бинарником, даже без исходников. `-M intel` — в Intel-синтаксисе,
  `--no-show-raw-insn` — не показывать сами байты.

Особенности вывода:

* `--emit-asm` выдаёт **AT&T-синтаксис** (`movl %edi, %eax` — источник
  первым, регистры с `%`, константы с `$`, суффиксы размера). Читать его
  надо уметь: его же выдают GCC/Clang по умолчанию и `gdb`.
* Имена функций — `модуль.функция` (`main.add`); можно задать своё через
  `@export("name")`.
* Между `#APP` и `#NO_APP` — ваш inline-ассемблер.
* Строки `.loc`, `.cfi_*`, `#DEBUG_VALUE` — отладочная информация, их
  можно пропускать глазами.
* Compiler Explorer (godbolt.org) поддерживает C3 — самый удобный
  способ смотреть вывод интерактивно.
* `objdump -M intel` переводит в Intel-синтаксис; `-S` вперемешку с
  исходником (если есть отладочная информация).

Как быстро найти нужную функцию в большом выводе:

```
objdump -d -M intel --no-show-raw-insn ./main | awk '/<main.add>:/,/ret/'
grep -n 'main.add:' asm/linux-x64/main.s
```

### 3.1 AT&T: четыре отличия от Intel

До этой главы вы писали в Intel-синтаксисе (`.intel_syntax noprefix`).
AT&T описывает те же самые инструкции, просто другой записью — как
одна и та же дата `18.11.2026` и `2026-11-18`.

| Что | Intel | AT&T |
|---|---|---|
| порядок операндов | `mov приёмник, источник` | `mov источник, приёмник` |
| регистры | `eax` | `%eax` |
| константы | `5` | `$5` |
| размер | по регистрам или `dword ptr` | суффикс: `movl`, `movq`, `movzbl` |
| память | `[base + index*scale + disp]` | `disp(base, index, scale)` |

Обратите внимание: `$` в AT&T означает **константу**, а в блоке C3 — **регистр**
(`$eax`). Это разные вещи из разных миров; не перепутайте.

### 3.2 Перевод AT&T ↔ Intel

| AT&T | Intel |
|---|---|
| `movl %edi, %eax` | `mov eax, edi` |
| `movl $5, %eax` | `mov eax, 5` |
| `movq 8(%rdi,%rcx,4), %rax` | `mov rax, [rdi + rcx*4 + 8]` |
| `leal (%rdi,%rdi,4), %eax` | `lea eax, [rdi + rdi*4]` |
| `imulq %rcx, %rax` | `imul rax, rcx` |
| `cmpq %rsi, %rdi; jl` | `cmp rdi, rsi; jl` (!) |
| `movzbl (%rdi), %eax` | `movzx eax, byte ptr [rdi]` |
| `cltq` / `cqto` | `cdqe` / `cqo` |
| `vfmadd231ps %ymm2, %ymm1, %ymm0` | `vfmadd231ps ymm0, ymm1, ymm2` |

Обратите внимание на `cmp`: в AT&T операнды переставлены, поэтому
`cmpq %rsi, %rdi; jl` значит «если rdi < rsi».

**Как переводить адрес в памяти.** Формула AT&T `disp(base, index, scale)`
читается как `base + index*scale + disp`. Разберём
`8(%rdi,%rcx,4)`:

| Часть | Значение |
|---|---|
| `8` | смещение (disp) |
| `%rdi` | база |
| `%rcx` | индекс |
| `4` | масштаб |
| итого | `[rdi + rcx*4 + 8]` |

Пустые места допустимы: `(%rdi)` = `[rdi]`, `4(%rdi)` = `[rdi + 4]`,
`(%rdi,%rdi,4)` = `[rdi + rdi*4]`.

**Суффиксы у расширяющих пересылок** читаются как «из чего в что»:
`movzbl` = **mov** с **z**ero-extension из **b**yte в **l**ong (32
бита), то есть `movzx eax, byte ptr [...]`. `movslq` = из `l` (32) в `q`
(64) со знаком = `movsxd`.

> **Частые ошибки (AT&T)**
>
> * Читать `subl %esi, %eax` как «esi -= eax». На самом деле
>   `eax -= esi` — приёмник **справа**.
> * Неправильно понимать условие после `cmp`: `cmpq %rsi, %rdi; jl`
>   — это «`rdi < rsi`», а не наоборот.
> * Путать `$5` (константа 5) и `5` (в AT&T без `$` — это **адрес** 5 в
>   памяти!).

> **Коротко:** `--emit-asm` даёт AT&T, `objdump -M intel` — Intel. В
> AT&T всё «зеркально»: источник слева, приёмник справа, `%` у
> регистров, `$` у констант, память `disp(base,index,scale)`.

## 4. -O0 против -O3

**Уровень оптимизации** (`-O0`, `-O1`, `-O2`, `-O3`) говорит компилятору,
насколько сильно стараться. `-O0` — «переведи буквально, как написано»;
`-O3` — «сделай как можно быстрее, лишь бы результат был тот же».
Аналогия: `-O0` — дословный перевод с подстрочником, `-O3` — литературный
перевод, где фраза может быть переставлена и сокращена, но смысл тот же.

Функция `fn int m3(int x, int y) => x * 5 + y * 8 + 3;`

`-O0` (Intel-синтаксис):

```asm
m3:
    push rbp
    mov  rbp, rsp
    mov  dword ptr [rbp - 4], edi     ; аргументы сохраняются в стек
    mov  dword ptr [rbp - 8], esi
    imul eax, dword ptr [rbp - 4], 5  ; и читаются обратно
    mov  ecx, dword ptr [rbp - 8]
    shl  ecx, 3
    add  eax, ecx
    add  eax, 3
    pop  rbp
    ret
```

`-O3`:

```asm
m3:
    lea eax, [rdi + rdi*4]       ; x*5
    lea eax, [rax + rsi*8]       ; + y*8
    add eax, 3
    ret
```

Что видно:

* на `-O0` каждая переменная живёт в памяти (это нужно отладчику —
  можно поменять её значение в gdb), стековый кадр через `rbp`;
* на `-O3` — только регистры, никакого кадра, умножение заменено `lea`;
* `-O0` — честный перевод «строка за строкой», `-O3` — вычисление того же
  результата любым способом.

(Оба листинга проверены на c3c 0.8.5 через `objdump -M intel`.)

### 4.1 Разбор `-O0` построчно

```asm
push rbp                          ; сохранить rbp вызывающего (глава 06)
mov  rbp, rsp                     ; свой кадр: rbp указывает на него
mov  dword ptr [rbp - 4], edi     ; x  → в стек, в «ячейку переменной x»
mov  dword ptr [rbp - 8], esi     ; y  → в стек
imul eax, dword ptr [rbp - 4], 5  ; eax = x * 5 (x прочитан из памяти)
mov  ecx, dword ptr [rbp - 8]     ; ecx = y (тоже из памяти)
shl  ecx, 3                       ; ecx = y * 8 (сдвиг вместо умножения — это даже -O0 умеет)
add  eax, ecx                     ; eax = x*5 + y*8
add  eax, 3                       ; eax = x*5 + y*8 + 3
pop  rbp                          ; восстановить rbp
ret
```

### 4.2 Разбор `-O3` с числами

Трассировка для `x = 1`, `y = 2` (ожидаем `5 + 16 + 3 = 24`):

| Инструкция | `rdi` (x) | `rsi` (y) | `eax` |
|---|---|---|---|
| вход | 1 | 2 | ? |
| `lea eax, [rdi + rdi*4]` | 1 | 2 | `1 + 1·4 = 5` |
| `lea eax, [rax + rsi*8]` | 1 | 2 | `5 + 2·8 = 21` |
| `add eax, 3` | 1 | 2 | `24` |

Обратите внимание: если бы в исходнике было `- 3`, вы бы, скорее всего,
увидели не `sub eax, 3`, а `add eax, -3`. LLVM нормализует вычитание
константы в прибавление отрицательной, и `objdump` может показать это как
`add eax, 0xfffffffd` — то же `-3` в дополнительном коде. Встретив
`0xffff…` в `add`, переведите его в отрицательное число.

### 4.3 Безопасный и быстрый режимы C3

У c3c уровни `-O0`/`-O1` — «безопасные» (проверки границ, переполнения
сдвигов, выравнивания, контракты), `-O2` и выше — без проверок. Поэтому
при сравнении кода C3 с кодом C учитывайте, что в «безопасном» режиме
появятся сравнения и вызовы паники. (Кстати, именно проверка выравнивания
поймала бы в `a1104` разыменование `ulong*` по нечётному адресу — для
невыровненного чтения в C3 есть `mem::load(ptr, align)`.)

Посмотрим, как это выглядит. Функция:

```c3
fn int get(int[] a, usz i) => a[i];
```

Срез `int[]` передаётся двумя регистрами: указатель в `rdi`, длина в
`rsi`; индекс `i` — в `rdx`. На `-O1` (c3c 0.8.5; сокращено, метки переименованы для читаемости):

```asm
get:
    push rbp
    mov  rbp, rsp
    sub  rsp, 0xd0
    test rdx, rdx            ; старший бит индекса установлен? ("отрицательный" индекс)
    js   .panic_negative     ;   → паника «отрицательный индекс»
    cmp  rdx, rsi            ; i >= len?
    jge  .panic_bounds       ;   → паника «выход за границу»
    lea  rax, [rdi + rdx*4]  ; адрес элемента
    mov  rcx, rax
    and  rcx, 3              ; адрес кратен 4?
    jne  .panic_align        ;   → паника «невыровненный указатель»
    mov  eax, dword ptr [rax]; наконец-то читаем a[i]
    add  rsp, 0xd0
    pop  rbp
    ret
    ...                      ; дальше ~50 инструкций подготовки сообщений паники
```

На `-O3`:

```asm
get:
    mov eax, dword ptr [rdi + rdx*4]   ; просто a[i]
    ret
```

Видите три проверки? Границы, знак и **выравнивание** (адрес `int`
должен делиться на 4: `and rcx, 3` выделяет два младших бита адреса).
Ровно последняя сработала бы, если бы вы прочитали `ulong` через
`*(ulong*)(data.ptr + 3)` — адрес не кратен 8. Отсюда совет в `a1104`
использовать `mem::load((ulong*)(...), 1)`: последний аргумент говорит
«я знаю, что адрес может быть не выровнен, выравнивание 1».

> **Частые ошибки (-O0/-O3)**
>
> * Смотреть на `-O0`-код и делать выводы о скорости: он специально
>   неоптимален.
> * Сравнивать «безопасный» `-O1` C3 с `-O2` C и удивляться лишним
>   сравнениям.
> * Искать в `-O3` ваши переменные в стеке — их там нет, они только в
>   регистрах (или вообще исчезли).

> **Коротко:** `-O0` — дословно, всё через стек; `-O3` — только
> регистры и хитрые замены. В C3 `-O0`/`-O1` ещё и добавляют проверки
> границ и выравнивания.

## 5. Типичные паттерны оптимизатора

Оптимизатор знает десятки «рецептов», как заменить дорогую операцию
дешёвой. Если знать самые частые, ассемблер начинает читаться как
открытая книга. Сводная таблица, а ниже — разбор каждого рецепта с
числами.

| Исходник | Что вы увидите | Почему |
|---|---|---|
| `x / 3` (uint) | `mov eax, 0xAAAAAAAB; imul rax, rcx; shr rax, 33` | деление ~25–40 тактов, умножение 3 |
| `x % 3` | частное × 3 через `lea`, затем `sub` | |
| `x / 8` (int) | `lea eax,[rdi+7]; test edi,edi; cmovns eax,edi; sar eax,3` | `sar` округляет вниз, C3 — к нулю |
| `x * 3`, `x * 5`, `x * 9` | `lea eax, [rdi + rdi*2]` и т.п. | `lea` — 1 такт |
| `x > y ? x : y` | `mov eax,esi; cmp edi,esi; cmovg eax,edi` | без ветвлений |
| `a < b` (bool) | `cmp; setl al` | |
| `return f(x);` | `jmp f` | хвостовой вызов |
| цикл суммы int | `vpaddd` ×4, развёртка, хвост | автовекторизация (глава 10) |
| `memset`/обнуление массива | `rep stosb` или вызов `memset`, или `vmovups` | |
| `switch` с плотными метками | `jmp [rip + table + rax*8]` | таблица переходов |
| неиспользуемый результат | ничего | удаление мёртвого кода |

Слово **«такт»** здесь — один «тик» процессора; при частоте 4 ГГц это
четверть наносекунды. «Деление ~25–40 тактов» значит, что одна
инструкция `div` стоит как десяток сложений.

### 5.1 Деление на константу через умножение

Магические числа для деления: `x / d = (x * M) >> s`, где
`M = ceil(2^s / d)` подобрано так, чтобы результат был точным для всех
32-битных `x`. Для `d = 3`: `2^33 / 3 = 2863311530.67`, `M = 2863311531 =
0xAAAAAAAB`. Подробности — Hacker's Delight, гл. 10, и libdivide.

**Интуиция.** Делить на 3 — это то же самое, что умножить на 1/3. С
дробями процессор (в целых регистрах) не работает, но можно схитрить:
умножить на `(1/3) · 2^33` (это уже большое целое, ≈ 2863311530.67,
округляем вверх), а потом сдвигом вправо на 33 поделить на `2^33`. Сдвиг
— это деление на степень двойки, бесплатное. Чуть округлённое вверх `M`
подобрано так, чтобы погрешность никогда не «перескакивала» через целое.

Реальный вывод для `fn uint d3(uint x) => x / 3;`:

```asm
d3:
    mov  ecx, edi           ; ecx = x (заодно старшие 32 бита rcx = 0)
    mov  eax, 0xAAAAAAAB    ; eax = M (rax = M, тоже без мусора сверху)
    imul rax, rcx           ; rax = x * M — 64-битное произведение
    shr  rax, 33            ; rax = (x * M) >> 33 = x / 3
    ret
```

Зачем `mov ecx, edi`? Запись в 32-битный регистр обнуляет старшую
половину 64-битного (глава 01). Так `x` превращается в 64-битное число
без знака, и произведение двух 32-битных чисел целиком помещается в
64-битный `rax`.

Трассировка для `x = 12346`:

| Шаг | Значение |
|---|---|
| `x` | `12346` |
| `M` | `0xAAAAAAAB` = `2863311531` |
| `x * M` | `35350444161726` = `0x2026AAAABABE` |
| `>> 33` | `35350444161726 / 8589934592` = `4115.33…` → **4115** |

И для крайнего случая `x = 0xFFFFFFFF` (4294967295): `(x * M) >> 33 =
1431655765`, точно `4294967295 / 3`. Ради этого `M` и подбирают.

**Как опознать в дизассемблере:** огромная «странная» константа
(`0xAAAAAAAB`, `0x55555556`, `0x92492493`…), `imul` или `mul`, затем
`shr`/`sar`. Чтобы восстановить делитель, посчитайте `2^s / M` (где `s`
— суммарный сдвиг) и округлите: `2^33 / 2863311531 ≈ 2.9999999997` → 3.
Этот приём работает для любого делителя — именно им вы будете
пользоваться в упражнении `a1105`, где константа и сдвиг другие.

### 5.2 Остаток: `x % d = x - (x / d) * d`

Для `fn uint r3(uint x) => x % 3;` компилятор выдал:

```asm
r3:
    mov  eax, edi           ; eax = x (понадобится в конце)
    mov  ecx, edi           ; ecx = x
    mov  edx, 0xAAAAAAAB
    imul rdx, rcx           ; rdx = x * M
    shr  rdx, 33            ; edx = q = x / 3
    lea  ecx, [rdx + rdx*2] ; ecx = q + q*2 = 3q
    sub  eax, ecx           ; eax = x - 3q = x % 3
    ret
```

Для `x = 12346`: `q = 4115`, `3q = 12345`, `x - 3q = 1`.

Обратите внимание, как собирается умножение частного на делитель: одним
`lea` (`·3` = `q + q*2`), а если множитель не помещается в одну формулу
`lea`, — цепочкой: например, `·6` = сначала `·2` (`add r, r`), потом
`·3`. Узнав такую цепочку после «магического» деления, вы узнаёте остаток.

### 5.3 `lea` как калькулятор

`lea` (глава 04) вычисляет адрес `base + index*scale + disp` — но адрес
никто не обязан использовать как адрес. Это просто дешёвая формула
«сложить и умножить на 1/2/4/8», да ещё и не трогающая флаги:

| `lea` | Считает |
|---|---|
| `lea eax, [rdi + rdi]` | `x · 2` |
| `lea eax, [rdi + rdi*2]` | `x · 3` |
| `lea eax, [rdi + rdi*4]` | `x · 5` |
| `lea eax, [rdi + rdi*8]` | `x · 9` |
| `lea eax, [rdi + rsi*8]` | `x + y · 8` |
| `lea eax, [rdi + 5]` | `x + 5` |
| `lea eax, [rdi + rsi - 2]` | `x + y - 2` |

Цепочку из двух-трёх `lea` читайте как формулу, подставляя предыдущий
результат в следующую строку, — так мы делали в разделе 4.2.

### 5.4 Знаковое деление на степень двойки

`sar x, k` — это деление на `2^k` с округлением **вниз** (к −∞). А в C3
`/` для знаковых округляет **к нулю**. Для положительных это одно и то
же, для отрицательных — нет:

| `x` | `x / 8` в C3 | `x sar 3` |
|---|---|---|
| 15 | 1 | 1 |
| -15 | **-1** | **-2** |
| -16 | -2 | -2 |

Решение: для отрицательных перед сдвигом прибавить `2^k - 1` (для деления на 8
это 7): `(-15 + 7) sar 3 = -8 sar 3 = -1`. Реальный вывод
`fn int d8(int x) => x / 8;`:

```asm
d8:
    lea    eax, [rdi + 7]   ; eax = x + 7 («поправленный» вариант)
    test   edi, edi         ; SF = знак x
    cmovns eax, edi         ; если x >= 0 (not sign), eax = x — поправка не нужна
    sar    eax, 3           ; деление на 8 сдвигом
    ret
```

Трассировка:

| `x` | `eax` после `lea` | `x >= 0`? | `eax` после `cmovns` | после `sar 3` |
|---|---|---|---|---|
| 15 | 22 | да | 15 | 1 |
| -15 | -8 | нет | -8 | -1 |
| -16 | -9 | нет | -9 | -2 |

Как опознать: `lea [rdi + (2^k − 1)]`, `test`, `cmovns`, `sar k`.
Константа в `lea` и величина сдвига подсказывают делитель.

### 5.5 Без ветвлений: `cmp` + `cmovcc`

Реальный вывод `fn int mx(int x, int y) => x > y ? x : y;`:

```asm
mx:
    mov   eax, esi          ; eax = y (вариант «по умолчанию»)
    cmp   edi, esi          ; сравнить x с y — выставить флаги
    cmovg eax, edi          ; если x > y (знаково) — взять x
    ret
```

| `x` | `y` | после `mov` | `x > y`? | после `cmovg` |
|---|---|---|---|---|
| 7 | 3 | 3 | да | 7 |
| 2 | 9 | 9 | нет | 9 |
| 4 | 4 | 4 | нет | 4 |

Шаблон всегда один: в регистр результата сначала кладётся один вариант,
потом флаги выставляет `cmp`, `test` или **сама арифметика** (`neg`,
`sub`, `add` тоже меняют SF/ZF/CF), и `cmovcc` при выполнении условия
подменяет результат вторым вариантом. Чтобы понять такую функцию,
ответьте на три вопроса: что лежит в регистре до `cmov`, какую операцию
описывают флаги и что означает суффикс условия (таблица в главе 03).

Ни одного перехода — процессору нечего «угадывать» (подробно о
предсказании ветвлений — глава 13). Шаблон «вычислить оба варианта,
выбрать `cmov`» — очень частый.

### 5.6 Остальные строки таблицы

* **`cmp; setl al`** — `setcc` записывает в байт 1 или 0 по флагу: так
  сравнение превращается в `bool` без ветвлений.
* **`jmp f` вместо `call f; ret`** — **хвостовой вызов**: если последнее,
  что делает функция, — вызывает другую, можно просто «прыгнуть» в неё,
  и та вернётся сразу нашему вызывающему.
* **`vpaddd` ×4 и «хвост»** — **автовекторизация**: компилятор сам
  переписал цикл на SIMD (глава 10), развернул его (обрабатывает
  несколько векторов за итерацию) и добавил отдельный короткий цикл для
  оставшихся элементов.
* **`jmp [rip + table + rax*8]`** — **таблица переходов**: вместо цепочки
  сравнений `switch` берёт адрес нужной ветки из массива адресов по
  индексу.
* **«ничего»** — **удаление мёртвого кода**: если результат никто не
  использует, вычислять его незачем. Поэтому в бенчмарках результат
  обязательно надо как-то «использовать» (глава 14).

### Ещё признаки, на которые стоит смотреть

* `call` внутри горячего цикла — функция не встроилась (inline);
* `ud2`/вызов паники после сравнения — проверка границ (в безопасном режиме);
* `movaps [rsp + ...]` в прологе — сохранение векторных регистров;
* `vzeroupper` перед `ret` — функция трогала ymm;
* много `mov` в/из стека в цикле — нехватка регистров (spilling);
* `cmov` вместо `jcc` — компилятор решил, что ветка непредсказуема или
  дешёвая (глава 13).

Пояснения:

* **Встраивание** (*inlining*) — компилятор копирует тело маленькой
  функции прямо в место вызова, экономя `call`/`ret` и открывая
  дальнейшие оптимизации. `call` в горячем (часто выполняемом) цикле
  — повод проверить, почему этого не случилось.
* **`ud2`** — специальная «недопустимая инструкция»: если до неё дошли,
  процесс падает. Компилятор ставит её на путях, которые «не должны
  случаться».
* **Spilling** («выплёскивание») — переменных больше, чем регистров, и
  часть приходится хранить в стеке, постоянно читая и записывая. Это
  медленнее.
* **`vzeroupper`** — сбрасывает старшие половины `ymm`-регистров, чтобы
  избежать штрафа при переходе между AVX и старым SSE-кодом.

> **Частые ошибки (чтение оптимизированного кода)**
>
> * Пытаться найти в ассемблере «деление», когда его заменили умножением.
> * Не заметить `mov ecx, edi` перед `imul rax, rcx` и думать, что это
>   бессмысленная пересылка: она расширяет число до 64 бит нулями.
> * Читать `cmovns`/`cmovs` наоборот: `s` — «если знак (отрицательно)»,
>   `ns` — «если НЕ отрицательно».
> * Забывать, что флаги описывают **последнюю** операцию, которая их
>   меняла: после `neg eax` они говорят о знаке уже результата, а не
>   исходного значения.

> **Коротко:** большая странная константа + `imul` + `shr` = деление на
> константу; `lea` = маленькие умножения и сложения; `lea +(2^k−1)` +
> `cmovns` + `sar` = знаковое деление на `2^k`; флаги + `cmov` = выбор
> без ветвлений.

## 6. Когда inline-ассемблер — плохая идея

* Компилятор не умеет оптимизировать сквозь `asm`-блок: не переставит,
  не векторизует, не свернёт константы. Короткая функция с `asm` может
  оказаться медленнее аналога на C3.
* Inline-ассемблер непереносим (x86 vs ARM) — нужна версия на чистом C3
  для других платформ (`$if env::X86_64:` … `$else` … `$endif`).
* Для большинства «особых» инструкций в C3 уже есть встроенные функции:
  `x.popcount()`, `x.clz()`, `x.ctz()`, `$$sysclock()` (rdtsc),
  `$$prefetch`, `$$fma`, атомики `std::atomic`, вектора `float[<8>]`.
  Они видимы оптимизатору — используйте их в первую очередь.

Разберём первый пункт. Для оптимизатора `asm`-блок — «чёрный ящик»:
он знает, что ящик читает и пишет, но не знает, *что* там считается.
Например, `popcount64(0xF0F0)` с `x.popcount()` компилятор может
вычислить ещё при компиляции и подставить `8`. С `asm { popcnt r, x; }`
— не может: он обязан честно выполнить инструкцию во время работы.
**Свёртка констант** (*constant folding*) — вычисление выражений из
констант на этапе компиляции — это лишь одна из оптимизаций, которые
блок останавливает.

Второй пункт — как выглядит «запасной вариант» для других процессоров
(проверено, компилируется и работает):

```c3
fn uint pc32(uint x)
{
    $if env::X86_64:            // этот кусок попадёт в программу только на x86-64
        uint r;
        asm { popcnt r, x; }
        return r;
    $else                       // на ARM, RISC-V и т. д. — переносимый вариант
        return x.popcount();
    $endif
}
```

`$if` — проверка **во время компиляции**: ненужная ветка вообще не
попадает в программу.

> **Коротко:** сначала ищите встроенную функцию C3, потом — `.s`-файл, и
> только для пары инструкций — `asm`-блок, с запасным вариантом через
> `$if`.

## Как это связано с упражнениями

Все упражнения этой главы правят **`main.c3`** — `.s`-файлы здесь не
пишутся. Проверить себя полезно ещё и так: собрать с `--emit-asm` в
отдельной папке и посмотреть, что получилось между `#APP` и `#NO_APP`.

**`a1101_asm_block` — первый блок `asm`.** Три функции, в каждой
сломана или пропущена одна инструкция: в первой результат пишется не
туда, во второй нет вычитания, в третьей — прибавления единицы.
Перечитайте 1.2 (что такое «приёмник») и 1.3 (порядок операндов,
суффиксы `l`/`q`). Внимание: `sub64` работает с `long`, значит, нужен
64-битный суффикс; а «прибавить 1» удобно сделать инструкцией из
списка 1.4, о которой подсказывает сам комментарий.

**`a1102_bits_inline` — битовые инструкции.** Нужно написать четыре
блока: подсчёт единиц, количество нулей справа, разворот байтов и сбор
битов маской. Перечитайте 1.3 (инструкции без суффикса, размер по
переменным) и 1.4 (`w:`/`rw:`, отсутствие `imm` у `pext`). На что
смотреть: какой из операндов приёмник; что `tzcnt` (в отличие от `bsf`
из главы 08) для нуля возвращает ширину операнда; у `bswapl` один
операнд, который и читается, и пишется; маску для `pext` нужно сначала
положить в переменную.

**`a1103_fixed_regs` — `mulq`, `divq`, `rdtsc`.** Перечитайте весь
раздел 2. На что смотреть: в какой половине `rdx:rax` лежат старшие 64
бита; что `divq` делит именно то, что оставил `mulq`; что после `rdtsc`
результат в 32-битных `$eax`/`$edx`, поэтому и пересылка должна быть
32-битной. Проверьте свою трассировку таблицей из 2.3.

**`a1104_crc32` — аппаратный CRC32C.** Инструкция `crc32 crc, src`
обновляет контрольную сумму по 1/2/4/8 байтам — размер определяется
типом `src`. Перечитайте 1.3 (размеры), 1.4 (строку `crc32` в
`--list-asm`: `rw:r64/r32, r64/r32/r16/r8/mem`) и 4.3 (почему
невыровненное чтение `ulong` надо делать через `mem::load`). На что
смотреть: в версии по 8 байт `crc` — 64-битная переменная, а для
побайтного хвоста нужна 32-битная копия (так сказано в комментарии
задания); не забудьте сам хвост — длина не обязана делиться на 8;
сдвигайте индекс на столько байт, сколько обработали.

**`a1105_read_compiler` — восстановить исходник.** Четыре функции в
`mystery.s` — реальный вывод `-O3`, переведённый в Intel. Ваша задача —
написать на C3 по одному выражению, дающему те же ответы. Перечитайте
разделы 4 и 5 целиком. Как действовать:

1. Для каждой функции распишите таблицу регистров, как в 4.2 и 5.x, —
   подставьте два-три числа (`x = 7`, `x = -7`, `x = 12345`).
2. Ищите знакомые «рецепты» из раздела 5: магическую константу, цепочки
   `lea`, `test` + `cmov`, `neg`.
3. Учтите, что функция может *комбинировать* рецепты: частное и
   остаток, например, могут встретиться в одной функции.
4. Проверьте типы: `mystery_a` беззнаковая (`uint`), остальные знаковые
   — это влияет на то, как ведут себя деление и сдвиг.

Проверка в `main` прогоняет и отрицательные числа — тут чаще всего и
ошибаются, если перепутать округление вниз и к нулю.

## Вопросы для самопроверки

1. Чем `asm("...")` отличается от `asm { ... }` с точки зрения компилятора?
2. В каком порядке записываются операнды в блоке `asm` C3? А в AT&T-выводе
   `--emit-asm`?
3. Почему `movl r, x;` не компилируется, если `x` — `ulong`?
4. Как в блоке `asm` вызвать `rdtsc` и получить 64-битный результат?
5. Почему `xaddl [p], v` в блоке `asm` C3 не атомарен, а `xchgl [p], v` атомарен?
6. Что не так с описанием `cmov*` в таблице `--list-asm`, и чем это грозит
   на `-O3`?
7. Как по ассемблеру опознать деление на константу и восстановить делитель? Знаковое деление на степень двойки?
8. Почему на `-O0` все переменные лежат в стеке?

Дополнительные:

9. В выводе `muldiv` первой стоит инструкция `movq %rdx, %rcx`, которой
   нет в вашем блоке. Откуда она и зачем?
10. Переведите в Intel: `movl 12(%rdi,%rsi,4), %eax` и `cmpl %esi, %edi; jg`.
    Когда сработает переход?
11. Чему равно `-17 / 8` в C3 и `-17 sar 3`? Проследите `lea`/`cmovns`/`sar`
    для `x = -17`.
12. В `[p + 4]` внутри блока `asm` — это 4 элемента или 4 байта?

## Словарик

| Термин | Простыми словами |
|---|---|
| **inline-ассемблер** | ассемблерные инструкции, вставленные прямо внутрь функции на языке высокого уровня |
| **LLVM** | «движок» компилятора: оптимизирует программу и генерирует машинный код; c3c использует его «под капотом» |
| **LLVM IR** | промежуточное представление программы между C3 и ассемблером |
| **распределение регистров** | решение компилятора, какая переменная в каком регистре живёт в каждый момент |
| **ограничения (constraints)** | описание для компилятора, что вставка читает, пишет и в каких регистрах |
| **clobber** («затирает») | регистр/флаги/память, которые вставка портит |
| **`cc`** | condition codes — флаги процессора в колонке clobbers |
| **суффикс размера** | `b`/`w`/`l`/`q` = 8/16/32/64 бита в конце мнемоники |
| **мнемоника** | текстовое имя инструкции: `mov`, `addl`, `popcnt` |
| **AT&T-синтаксис** | запись ассемблера: источник первым, `%` у регистров, `$` у констант |
| **Intel-синтаксис** | запись ассемблера: приёмник первым, `[...]` для памяти |
| **неявный операнд** | регистр, с которым инструкция работает, хотя он не написан (`rax`/`rdx` у `mul`) |
| **`rdx:rax`** | 128-битное число из двух половинок: старшая в `rdx`, младшая в `rax` |
| **аккумулятор** | исторически «главный» регистр (`a`/`rax`), с которым работают `mul`, `div` и др. |
| **#DE / SIGFPE** | исключение деления (на 0 или частное не влезает) и сигнал, который получает процесс |
| **TSC, `rdtsc`** | счётчик тактов процессора и инструкция его чтения |
| **атомарная операция** | операция, которую другие ядра видят целиком «до» или «после», без середины |
| **`lock`** | префикс, делающий операцию с памятью атомарной |
| **дизассемблер** | программа, переводящая байты машинного кода обратно в текст (`objdump -d`) |
| **уровень оптимизации** | `-O0`…`-O3`: насколько сильно компилятор переделывает код ради скорости |
| **безопасный режим C3** | `-O0`/`-O1`: проверки границ, выравнивания, переполнения сдвигов |
| **выравнивание** | требование, чтобы адрес значения делился на его размер (4 для `int`, 8 для `ulong`) |
| **магическое число** | константа `M` для замены деления умножением: `x / d = (x * M) >> s` |
| **такт** | один «тик» процессора; мера стоимости инструкций |
| **хвостовой вызов** | вызов в самом конце функции, заменённый на `jmp` |
| **автовекторизация** | компилятор сам переписывает цикл на SIMD-инструкции |
| **таблица переходов** | массив адресов ветвей `switch`, по которому делается `jmp` |
| **мёртвый код** | вычисления, результат которых не используется; оптимизатор их удаляет |
| **встраивание (inlining)** | подстановка тела функции в место вызова |
| **spilling** | хранение переменных в стеке из-за нехватки регистров |
| **свёртка констант** | вычисление выражений из констант во время компиляции |
| **`$if`** | условие времени компиляции в C3: лишняя ветка не попадает в программу |
