# Глава 06. Стековые кадры, локальные переменные, рекурсия

## Карта главы

**Что вы узнаете.**

* Что такое **стековый кадр** и что в нём лежит.
* Классический пролог/эпилог с `rbp` и инструкцию `leave`.
* Где живут локальные переменные и локальные массивы и почему их нельзя
  возвращать по указателю.
* Как выравнивать стек, когда есть кадр, локальный массив или и то и
  другое.
* Почему рекурсия в ассемблере — это просто `call` самого себя, и что
  должно пережить рекурсивный вызов.
* Что такое хвостовой вызов и как он превращает рекурсию в цикл.
* Как читать стек в gdb: `backtrace`, `x/gx $rsp`, `info frame`.

**Зачем это нужно.** Стек — это не отдельная «память для функций», а
обычная память, на которую указывает `rsp`, плюс дисциплина её
использования. В этой главе мы разберём, как функция заводит себе
**кадр** (stack frame), где живут локальные переменные и массивы, как
устроен backtrace в отладчике и почему рекурсия в ассемблере — это
просто `call` самого себя.

**Что нужно знать заранее.** Главу 05 обязательно: `push`/`pop`,
`call`/`ret`, адрес возврата, caller-/callee-saved регистры,
выравнивание `rsp` по 16 перед `call`, 7-й аргумент на стеке. Из главы
04 — адресация `[rbp - 8]`, `[rsp + rcx*4]`.

**Упражнения:** `a0601`–`a0606`.

| Упражнение | Разделы |
|---|---|
| `a0601` frame | 1 |
| `a0602` local_buf | 3, 3.3 |
| `a0603` fact | 4 |
| `a0604` fib | 4, 4.3 |
| `a0605` tree | 6 |
| `a0606` ackermann | 4.4, 5 |

## 1. Что лежит на стеке

### 1.1. Кадр — личная «комната» вызова

Аналогия: стек — многоэтажная стопка комнат. Каждый раз, когда кто-то
вызывает функцию, сверху (у x86 — снизу, к меньшим адресам) пристраивают
новую комнату — **кадр** (stack frame). В ней лежат: записка «куда
вернуться» (адрес возврата), вещи предыдущего жильца, которые надо
вернуть (сохранённые регистры), и рабочий стол функции (локальные
переменные). Когда функция возвращается, её комнату сносят — `rsp`
поднимается обратно.

Для каждого активного вызова на стеке есть кусок — кадр. Типичный кадр
функции, построенный «классическим» прологом:

```
старшие адреса
   ...                          кадр вызывающего
   [rbp + 24]   8-й аргумент
   [rbp + 16]   7-й аргумент
   [rbp + 8]    адрес возврата            <- положил call
   [rbp]        сохранённый rbp вызывающего <- push rbp
   [rbp - 8]    локальная переменная 1
   [rbp - 16]   локальная переменная 2
   ...
   [rsp]        вершина стека
младшие адреса
```

### 1.2. Пролог и эпилог

**Пролог** — первые инструкции функции, которые «строят» кадр.
**Эпилог** — последние, которые его «сносят» перед `ret`.

```asm
f:
    push rbp            # сохранить rbp вызывающего (он callee-saved)
    mov rbp, rsp        # rbp = основание нашего кадра
    sub rsp, 32         # 32 байта под локальные (кратно 16 — стек выровнен)
    ...
    mov rsp, rbp        # освободить всё, что выделили
    pop rbp             # вернуть rbp вызывающего
    ret
```

Пролог по шагам (на входе `rsp = 0x7FF8`, у вызывающего `rbp = 0x8040`):

| После | `rsp` | `rbp` | Что появилось в памяти |
|---|---|---|---|
| вход | `0x7FF8` | `0x8040` | `[0x7FF8]` = адрес возврата |
| `push rbp` | `0x7FF0` | `0x8040` | `[0x7FF0]` = `0x8040` |
| `mov rbp, rsp` | `0x7FF0` | `0x7FF0` | |
| `sub rsp, 32` | `0x7FD0` | `0x7FF0` | `0x7FD0…0x7FEF` — наши локальные |

Эпилог в обратную сторону:

| После | `rsp` | `rbp` | |
|---|---|---|---|
| `mov rsp, rbp` | `0x7FF0` | `0x7FF0` | локальные «освобождены» |
| `pop rbp` | `0x7FF8` | `0x8040` | `rbp` вызывающего вернулся |
| `ret` | `0x8000` | `0x8040` | прыжок по адресу из `[0x7FF8]` |

Картинка кадра после пролога:

```
 0x7FF8 | адрес возврата     |  = [rbp + 8]
 0x7FF0 | старый rbp (0x8040)|  = [rbp]       <- rbp
 0x7FE8 | локальная 1        |  = [rbp - 8]
 0x7FE0 | локальная 2        |  = [rbp - 16]
 0x7FD8 | локальная 3        |  = [rbp - 24]
 0x7FD0 | локальная 4        |  = [rbp - 32]  <- rsp
```

Пара `mov rsp, rbp; pop rbp` — это одна инструкция `leave`. Обратная ей
`enter N, 0` существует, но медленная, и её не используют.

### 1.3. Зачем `rbp`

Зачем нужен `rbp`, если есть `rsp`? Внутри функции `rsp` меняется
(push, временные выделения, выравнивание), и смещения относительно него
«плавают». `rbp` фиксирован на весь вызов — адреса локальных и
аргументов постоянны. Кроме того, сохранённые `rbp` образуют
**связный список кадров**: `[rbp]` указывает на кадр вызывающего,
`[[rbp]]` — на кадр его вызывающего… Так работают простые профайлеры и
backtrace без отладочной информации.

`rbp` — «якорь»: как колышек, вбитый в землю у входа в комнату. Что бы
ни происходило с `rsp`, `[rbp + 16]` — это всегда 7-й аргумент, а
`[rbp - 8]` — всегда первая локальная.

> **Коротко:** пролог `push rbp; mov rbp, rsp; sub rsp, N` строит кадр;
> эпилог `leave; ret` (или `mov rsp, rbp; pop rbp; ret`) его сносит.
> Выше `rbp` — адрес возврата и аргументы, ниже — локальные.

> **Частые ошибки**
> * Забыть `pop rbp` (или `leave`) — `ret` возьмёт старый `rbp` как
>   адрес возврата.
> * Искать 7-й аргумент по `[rbp + 8]` — там адрес возврата; аргумент на
>   `[rbp + 16]`.

## 2. Frame pointer: есть или нет

**Frame pointer** («указатель кадра») — это и есть `rbp`, когда его
используют как якорь.

* `-O0`: всегда кадр с `rbp`, каждая переменная в памяти.
* `-O2`: обычно без `rbp` (`-fomit-frame-pointer`) — освобождается ещё
  один регистр, локальные адресуются через `rsp`; для раскрутки стека
  используется таблица `.eh_frame` (это и есть директивы `.cfi_*` в
  выводе компилятора).
* c3c, как видно из дизассемблера, на `-O0`/`-O1` оставляет `push rbp;
  mov rbp, rsp` даже в мелких функциях.

В последние годы многие дистрибутивы (Fedora, Ubuntu) вернули frame
pointers по умолчанию — ради дешёвого профилирования (`perf`). Цена —
около 1% скорости.

**Раскрутка стека** (unwinding) — восстановление цепочки «кто кого
вызвал» по содержимому стека: нужно отладчику (backtrace), профайлеру и
механизмам исключений.

## 3. Локальные переменные

### 3.1. Скаляры

Скаляры — слоты в кадре:

```asm
    push rbp
    mov rbp, rsp
    sub rsp, 16
    mov [rbp - 8], rdi          # long a — в локальную
    mov dword ptr [rbp - 12], 0 # int counter = 0
    ...
```

Слот — это просто несколько байт кадра, которые вы «назначили»
переменной. Компилятор сам раздаёт смещения; вы делаете то же самое
вручную. Удобно записать в комментарии карту: `[rbp-8] = a`,
`[rbp-12] = counter`.

### 3.2. Массивы

Массивы — непрерывный кусок:

```asm
    sub rsp, 72                 # int buf[16] = 64 байта + 8 на выравнивание
    mov rdi, rsp                # &buf[0]
    mov esi, 16
    call fill                   # fill(buf, 16)
    mov eax, [rsp + 4*3]        # buf[3]
    add rsp, 72
```

Почему `rsp` указывает на начало массива? После `sub rsp, 72` свободный
кусок — от `rsp` до `rsp + 71`. Массив растёт «вверх» внутри этого
куска: `buf[0]` по `[rsp]`, `buf[1]` по `[rsp + 4]`, … `buf[15]` по
`[rsp + 60]`. Байты `[rsp + 64]…[rsp + 71]` — набивка для выравнивания.

```
 rsp+72 | адрес возврата        |  <- rsp на входе
 rsp+64 | (8 байт набивки)      |
 rsp+60 | buf[15]               |
  ...   | ...                   |
 rsp+4  | buf[1]                |
 rsp+0  | buf[0]                |  <- rsp после sub, передаём в rdi
```

Важно: после `call fill` `rsp` тот же, что и до (`call` положил, `ret`
снял) — значит, `[rsp + 4*3]` по-прежнему `buf[3]`.

Локальный массив выделяется за одну инструкцию и освобождается за одну
— в этом причина, по которой стековые аллокации дешевле любого `malloc`.
Обратная сторона: память живёт только до `ret`. Вернуть указатель на
локальный массив — классическая ошибка (dangling pointer): после
возврата этот участок займёт следующий вызов.

**Висячий указатель** (dangling pointer) — указатель на память, которая
уже освобождена или занята чем-то другим.

Размер стека потока ограничен (обычно 8 МБ для главного потока Linux,
`ulimit -s`; часто меньше для дополнительных). Массив на мегабайты
на стеке — путь к SIGSEGV. Для больших буферов есть «stack probing»:
компилятор трогает каждую страницу по очереди, чтобы не перепрыгнуть
сторожевую страницу.

**Сторожевая страница** (guard page) — участок памяти сразу за концом
стека, к которому запрещён доступ. Если стек «упёрся» в неё — SIGSEGV
вместо тихой порчи соседней памяти. **Страница** — блок памяти в 4 КБ,
единица, которой ОС выдаёт память.

### 3.3. Выравнивание локальных

Если кадр строится через `push rbp`, после него `rsp ≡ 0 (mod 16)`, и
размер `sub` должен быть кратен 16. Без `push rbp` — размер `≡ 8 (mod 16)`.
Проверка в упражнении `a0602`.

Сводка (функция что-то вызывает):

| Пролог | Остаток `rsp` после | Пример хорошего `N` |
|---|---|---|
| `sub rsp, N` | `8 + N` должно делиться на 16 | 8, 24, 72 |
| `push rbp; mov rbp, rsp; sub rsp, N` | `16 + N` → `N` кратно 16 | 16, 32, 64 |
| `push rbx; sub rsp, N` | `16 + N` → `N` кратно 16 | 0, 16, 64 |

Как выбрать `N` для массива из 64 байт без `push rbp`: 64 даёт остаток
8 (плохо), значит берём 72 (64 + 8 набивки).

> **Коротко:** локальные — это кусок стека ниже адреса возврата. Выделили
> `sub rsp, N`, освободили `add rsp, N` (или `leave`). Размер `N`
> выбирайте так, чтобы перед `call` `rsp` был кратен 16. Не возвращайте
> указатели на локальные.

> **Частые ошибки**
> * `sub rsp, 64` и `add rsp, 72` (или наоборот) — разные числа.
> * Массив по `[rsp]`, но после `push` внутри функции `rsp` сдвинулся.
> * Выход за конец массива затирает адрес возврата.

## 4. Рекурсия

### 4.1. Идея

Рекурсивный вызов ничем не отличается от обычного: `call` самой себя.
Каждый вызов получает собственный кадр, поэтому «копии» не мешают друг
другу — при условии, что всё нужное после вызова лежит **в кадре** или
в **callee-saved регистрах**, а не в volatile.

Главный вопрос рекурсивной функции: **что должно пережить вызов?**
Выпишите это до кода. Для факториала — `n` (умножаем на него после
возврата). Для Фибоначчи — `n` и результат первого вызова.

### 4.2. Вариант 1: значение в callee-saved регистре

```asm
# ulong fact(ulong n)
fact:
    test rdi, rdi
    jnz .Lrec
    mov eax, 1
    ret
.Lrec:
    push rbx            # rbx чужой — сохранить; заодно стек выровнен
    mov rbx, rdi        # n переживёт call
    dec rdi
    call fact           # rax = fact(n - 1)
    imul rax, rbx
    pop rbx
    ret
```

Почему это корректно, хотя все уровни рекурсии используют один и тот же
`rbx`? Каждый уровень сохраняет **значение вызывающего** в своём кадре
(`push rbx`) и восстанавливает его перед `ret`. После возврата из
`fact(n - 1)` в `rbx` снова наше `n`. Это и есть смысл callee-saved:
стек хранит историю.

Трассировка `fact(3)` (уровни отмечены по значению `n`):

| Шаг | Уровень | Действие | `rbx` | стек (сверху — вершина) |
|---|---|---|---|---|
| 1 | n=3 | `push rbx` (rbx вызывающего = X) | X | `X` |
| 2 | n=3 | `mov rbx, rdi` | 3 | `X` |
| 3 | n=2 | `push rbx` | 3 | `3, X` (+ адреса возврата) |
| 4 | n=2 | `mov rbx, rdi` | 2 | `3, X` |
| 5 | n=1 | `push rbx`, `mov rbx, rdi` | 1 | `2, 3, X` |
| 6 | n=0 | `mov eax, 1; ret` | 1 | `2, 3, X` |
| 7 | n=1 | `imul rax, rbx` → 1; `pop rbx` | 2 | `3, X` |
| 8 | n=2 | `imul rax, rbx` → 2; `pop rbx` | 3 | `X` |
| 9 | n=3 | `imul rax, rbx` → 6; `pop rbx` | X | — |

Каждый `pop rbx` возвращает значение **предыдущего** уровня — ровно то
`n`, которое ему нужно. Стек работает как стопка записок.

### 4.3. Вариант 2: значение в локальной переменной кадра

Тот же приём, но через кадр с `rbp`. Пример — рекурсивная сумма
`rsum(n) = n + rsum(n - 1)`, `rsum(0) = 0`:

```asm
    .globl asm_rsum
asm_rsum:                   # ulong asm_rsum(ulong n)
    push rbp                # сохранить rbp вызывающего
    mov rbp, rsp            # rbp = якорь нашего кадра
    sub rsp, 16             # место под одну локальную (16 — для выравнивания)
    test rdi, rdi           # n == 0?
    jz .Lrsum_zero
    mov [rbp - 8], rdi      # локальная: сохранить n в СВОЁМ кадре
    dec rdi                 # аргумент = n - 1
    call asm_rsum           # rax = rsum(n - 1); rdi испорчен — не важно
    add rax, [rbp - 8]      # rax += n (n взяли из своего кадра)
    leave                   # = mov rsp, rbp; pop rbp
    ret
.Lrsum_zero:
    xor eax, eax            # rsum(0) = 0
    leave
    ret
```

Каждый уровень тратит 32 байта: адрес возврата (8) + сохранённый `rbp`
(8) + локальные (16). Вот настоящий дамп стека из gdb в момент входа в
`asm_rsum(1)` при вызове `asm_rsum(3)` (`x/12gx $rsp`, адреса укорочены,
пояснения добавлены):

```
адрес   значение            смысл
...e58  0x...c20e5          адрес возврата в уровень n=2 (после его call)
...e60  0x2                 [rbp-16] уровня n=2: набивка (мусор)
...e68  0x2                 [rbp-8]  уровня n=2: сохранённое n = 2
...e70  0x7fffffffde90      [rbp]    уровня n=2: rbp уровня n=3   <- rbp(n=2)
...e78  0x...c20e5          адрес возврата в уровень n=3
...e80  0x100               [rbp-16] уровня n=3: набивка (мусор)
...e88  0x3                 [rbp-8]  уровня n=3: сохранённое n = 3
...e90  0x7fffffffdf00      [rbp]    уровня n=3: rbp main         <- rbp(n=3)
...e98  0x...c1ee6          адрес возврата в main
```

Видно и связный список: в `...e70` лежит `...e90` — адрес кадра
следующего (более старого) уровня. А `bt` в gdb в этот момент показывает:

```
#0  asm_rsum () at t6.s:5
#1  0x00005555555c20e5 in asm_rsum () at t6.s:12
#2  0x00005555555c20e5 in asm_rsum () at t6.s:12
#3  0x00005555555c1ee6 in m6.main () at m6.c3:3
```

(`asm_rsum(0)` = 0, `asm_rsum(3)` = 6, `asm_rsum(100000)` = 5000050000 —
пример собран и проверен.)

Если между вызовами нужно два значения (как в `fib(n-1) + fib(n-2)`), —
два callee-saved регистра или две локальные переменные.

### 4.4. Глубина рекурсии

Каждый уровень стоит размер кадра: адрес возврата (8) + сохранённые
регистры + локальные. `fact` выше тратит 16 байт на уровень, и при 8 МБ
стека выдержит полмиллиона уровней. Компилятор на `-O0` тратит больше
(все переменные в памяти). Функция Аккермана или наивный обход
вырожденного дерева легко исчерпывают стек — SIGSEGV при обращении к
сторожевой странице.

> **Коротко:** рекурсия = `call` себя. Всё, что нужно после вызова,
> держите в callee-saved регистре (сохранив его) или в локальной
> переменной своего кадра. Каждый уровень стоит байтов стека.

> **Частые ошибки**
> * Держать `n` в `rcx`/`rdi` через рекурсивный вызов. Коварно: тест на
>   маленьких `n` может случайно пройти.
> * Забыть выравнивание: у рекурсивной функции тоже должен быть
>   выровнен стек перед `call`.
> * Несколько выходов (`ret`) — и не все восстанавливают регистры.

## 5. Хвостовые вызовы

Если функция заканчивается `return g(args)`, её кадр больше не нужен в
момент вызова `g`. Можно снять кадр *до* перехода и прыгнуть, а не
вызвать:

```asm
    # вместо:  call g / (эпилог) / ret
    # пишем:   (эпилог) / jmp g
```

`g` вернётся сразу туда, куда должны были вернуться мы. Стек не растёт —
хвостовая рекурсия становится циклом. Так, `A(m, 0) = A(m-1, 1)` в
функции Аккермана превращается в `dec rdi; mov esi, 1; jmp asm_ack`.
Компиляторы делают это с `-O2` (tail call optimization), c3c — тоже:
`fn long tail(long x) => g(x * 2);` компилируется в
`add rdi, rdi; jmp g`.

Почему это работает: на вершине стека в момент `jmp g` лежит **наш**
адрес возврата (кадр мы уже сняли). Когда `g` сделает `ret`, она снимет
этот адрес и вернётся прямо к нашему вызывающему, минуя нас.

```
обычный вызов:   вызывающий -> f -> g -> (ret в f) -> (ret к вызывающему)
хвостовой:       вызывающий -> f -jmp-> g -> (ret сразу к вызывающему)
```

Аналогия: вместо «спрошу у коллеги и передам ответ клиенту» — «соединю
клиента с коллегой напрямую и повешу трубку».

Условия: аргументы хвостового вызова должны поместиться в регистры
(или в стековую область вызывающего), а после вызова не должно
оставаться работы (сложения, деструкторов, `defer`).

Как узнать, хвостовой ли вызов: спросите, «что функция делает с
результатом?». Если «сразу возвращает» — хвостовой. Если «прибавляет,
умножает, сравнивает» — нет.

> **Коротко:** `return g(...)` можно заменить на «эпилог + `jmp g`».
> Стек не растёт, рекурсия становится циклом.

> **Частая ошибка:** сделать `jmp`, не сняв кадр и не восстановив
> callee-saved регистры, — тогда `g` вернётся к вызывающему с испорченным
> стеком.

## 6. Рекурсивные структуры данных

Обход дерева — естественная рекурсия. Для узла
`struct Node { long value; Node* left; Node* right; }` (24 байта,
смещения 0, 8, 16):

```
адрес узла -> +0  | value |
              +8  | left  |  -> другой узел или 0 (null)
              +16 | right |  -> другой узел или 0
```

```asm
tree_sum:
    test rdi, rdi
    jnz .Lrec
    xor eax, eax            # пустое дерево
    ret
.Lrec:
    push rbx
    push r12
    sub rsp, 8              # 2 push — доравнять
    mov rbx, rdi            # узел
    mov r12, [rbx]          # value
    mov rdi, [rbx + 8]
    call tree_sum           # left
    add r12, rax
    mov rdi, [rbx + 16]
    call tree_sum           # right
    add rax, r12
    add rsp, 8
    pop r12
    pop rbx
    ret
```

Что живёт в каком регистре: `rbx` — текущий узел (нужен, чтобы после
первого вызова прочитать `right`); `r12` — частичная сумма (`value`,
потом `value + sum(left)`). Оба переживают вызовы, потому что
callee-saved; каждый уровень рекурсии сохраняет значения своего
вызывающего.

Второй вызов не хвостовой (после него — сложение). Его можно сделать
хвостовым, передавая аккумулятор аргументом: `sum(node, acc)` —
но тогда нужна вторая функция-обёртка. Для глубоких деревьев рекурсию
заменяют явным стеком (массивом указателей) — так устроены обходы в
игровых движках (BVH, scene graph), где глубина непредсказуема.

**BVH** (bounding volume hierarchy) — дерево вложенных «коробок» вокруг
объектов сцены, используется для быстрой проверки столкновений и
трассировки лучей. **Scene graph** — дерево объектов сцены (родитель →
дети).

## 7. Отладка: backtrace и кадры в gdb

```
(gdb) break asm_fib if $rdi == 2     # условная точка останова
(gdb) run
(gdb) backtrace                       # bt: цепочка вызовов
(gdb) frame 3                         # перейти к кадру №3
(gdb) info frame                      # где сохранены регистры, адрес возврата
(gdb) x/6gx $rsp                      # содержимое стека
(gdb) p $rsp & 15                     # проверка выравнивания
(gdb) finish                          # выполнить до конца текущего вызова
(gdb) watch *(long*)($rsp + 8)        # остановиться, когда изменится слово стека
```

Как читать `x/6gx $rsp`: шесть 8-байтовых слов, начиная с вершины стека,
в hex. Адреса, похожие на `0x5555555…`, обычно указывают в код
(адреса возврата); похожие на `0x7fffffff…` — в стек (сохранённые `rbp`,
указатели на локальные); маленькие числа — данные. Сравните с дампом в
разделе 4.3.

Если backtrace выглядит как мусор (`?? ()`), стек почти наверняка
испорчен: несбалансированные push/pop, запись за пределы локального
массива, `ret` не туда. Хорошая тактика — поставить точку останова на
`ret` (`break *адрес`) и проверить `x/gx $rsp`: там должен быть адрес
внутри вызывающей функции.

Сборка `.s` с `-g` даёт gdb номера строк, но не информацию для
раскрутки (CFI). gdb всё равно найдёт вызывающих, если вы используете
кадр с `rbp` или если стек простой. В «настоящем» ассемблерном коде
пишут директивы `.cfi_startproc`, `.cfi_def_cfa_offset 16`, … — их
генерирует компилятор, и их можно увидеть в выводе `--emit-asm`.

**CFI** (call frame information) — таблица «как найти адрес возврата и
сохранённые регистры в каждой точке функции»; по ней отладчик
раскручивает стек без `rbp`.

## 8. Как это делает компилятор

`fn ulong fact(ulong n) => n == 0 ? 1 : n * fact(n - 1);` на `-O2`
компиляторы на LLVM превращают… в цикл. Рекурсия, где после вызова
идёт только умножение, переписывается с аккумулятором (accumulator
introduction), и `call` исчезает вовсе. c3c `-O2` идёт дальше: в
`fact` нет ни одного `call`, а получившийся цикл ещё и развёрнут по 8
умножений за итерацию (глава 14). Проверьте сами
(`c3c compile-only -O2` + `objdump -d -M intel`) и сравните с `-O0`,
где честно строится кадр на каждый уровень.

С `fib` так не получится — два вызова; компилятор оставит рекурсию, но
одну ветку может превратить в цикл.

## 9. Подводные камни

> **Частые ошибки**
>
> * **Несбалансированный эпилог.** Забыли `pop rbp` или `add rsp, N` —
>   `ret` прыгает по мусору (SIGSEGV, часто с бессмысленным backtrace).
> * **Значение в volatile-регистре через рекурсивный вызов.** Особенно
>   коварно: вызываемая функция — это вы сами, и она «случайно» может
>   оставить в регистре похожее значение. Тест на n = 0, 1 пройдёт.
> * **Выход за пределы локального массива** перезаписывает сохранённый
>   `rbp` и адрес возврата — это классический buffer overflow.
>   (Компиляторы ставят «stack canary» — `-fstack-protector`.)
> * **Указатель на локальную переменную после возврата.**
> * **Слишком глубокая рекурсия** — переполнение стека.
> * **Стековые аргументы через `rsp` после push** — смещение уехало;
>   через `rbp` — стабильно.

**Stack canary** — случайное число, которое компилятор кладёт между
локальными массивами и адресом возврата и проверяет перед `ret`: если
массив переполнили, канарейка изменится, и программа аварийно
завершится раньше, чем атакующий получит управление.

## Как это связано с упражнениями

* **`a0601` frame** — починить эпилог и прочитать 7-й аргумент через
  `rbp`. Раздел 1 целиком: таблицы пролога/эпилога в 1.2 и картинку
  кадра в 1.1. Спросите себя: что лежит по `[rbp + 8]`, а что — по
  `[rbp + 16]`? Стенд проверяет, что `rsp` и `rbp` вернулись на место.
* **`a0602` local_buf** — массив из 16 `int` на стеке, вызов `c3_fill` и
  сумма. Разделы 3.2 (картинка массива) и 3.3 (таблица выравнивания).
  Кадра с `rbp` здесь нет — какой остаток должен быть у размера? Не
  забудьте исправить **и** `sub`, **и** `add`. Сумму считайте после
  вызова (в volatile-регистрах — уже можно, вызовов больше нет).
* **`a0603` fact** — `n` теряется при рекурсивном вызове. Раздел 4.1–4.2:
  какой регистр переживает `call`? В шапке предложены два решения —
  годится любое; проверьте выравнивание.
* **`a0604` fib** — два рекурсивных вызова, нужно хранить два значения.
  Разделы 4.2 и 4.3. Решите заранее, что где живёт (`n` и результат
  первого вызова), и посчитайте `push` для выравнивания. База: `n < 2`.
* **`a0605` tree** — сумма и глубина дерева. Раздел 6 (там разобран
  обход). Для глубины вместо сложения — максимум двух глубин + 1;
  максимум — как в главе 03. `null` — это 0.
* **`a0606` ackermann** — три правила, глубокая рекурсия. Разделы 4.4 и 5.
  Определите, какие вызовы хвостовые (подсказка в шапке), — их можно
  сделать `jmp`. Тогда через настоящий `call` нужно сохранять только
  одно значение. «В лоб» тремя `call` тоже засчитается.

## Словарик

| Термин | Простыми словами |
|---|---|
| **стековый кадр (stack frame)** | кусок стека одного вызова: адрес возврата, сохранённые регистры, локальные |
| **пролог / эпилог** | инструкции в начале/конце функции, строящие/сносящие кадр |
| **frame pointer (`rbp`)** | регистр-якорь, неподвижный на время вызова; от него считают локальные и аргументы |
| **`leave`** | `mov rsp, rbp; pop rbp` одной инструкцией |
| **локальная переменная** | слот в кадре, например `[rbp - 8]` |
| **набивка (padding)** | неиспользуемые байты ради выравнивания |
| **висячий указатель** | указатель на уже освобождённую память (например, на локальную после `ret`) |
| **страница** | блок памяти в 4 КБ |
| **сторожевая страница** | недоступная страница за концом стека; касание → SIGSEGV |
| **рекурсия** | функция вызывает сама себя; у каждого вызова свой кадр |
| **глубина рекурсии** | сколько уровней вызовов одновременно на стеке |
| **хвостовой вызов** | `return g(...)`: можно снять кадр и сделать `jmp g` |
| **раскрутка стека (unwinding)** | восстановление цепочки вызовов по стеку |
| **backtrace** | список «кто кого вызвал» (`bt` в gdb) |
| **CFI / `.eh_frame`** | таблицы для раскрутки стека без `rbp` |
| **buffer overflow** | запись за конец буфера, затирающая соседние данные (в т. ч. адрес возврата) |
| **stack canary** | контрольное число перед адресом возврата для обнаружения переполнения |
| **явный стек** | свой массив вместо рекурсии, для обхода глубоких структур |
